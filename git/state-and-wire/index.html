Mutable state and the wireTeardown

Git's objects never change, so they need no lock. Everything around them does change: the index, the refs, the reflogs, and the conversation between two repositories. This part reads those small mutable files and the wire protocol from git v2.55.0: the index as a stat cache that becomes a tree, racy git, what a reader sees while refs move, reftable's one-rename commit, why every publish is atomic but nothing is fsynced by default, pkt-lines and protocol v2, negotiation, and the push quarantine.

How to read the badges

This is Part 2 of 3 of Git, taken apart. Part 1 covers the commit and its objects; Part 3 covers merging, upkeep and history.

01The index: a stat cache that becomes a tree

Part 1 ended with a store that never changes. An object is named by the hash of its bytes, so a writer never needs a lock: if the name exists, the content is already there. Everything else in .git does change. The index, the refs, the reflogs and the conversation between two repositories are small, mutable and shared. Each is either a pointer or a cache, and each has its own consistency story. This part reads those stories from git v2.55.0, starting with the file every git add rewrites.

The index (.git/index) is one binary file: a 12-byte header, the entries sorted by path, typed extensions, and a trailing hash. The header is DIRC ("dircache"), a version from 2 to 4 and an entry count, all big-endian from the code. An entry is ten 32-bit stat words, the object id and a 16-bit flags word, then the path. read-cache.c:1667-1684: 

struct ondisk_cache_entry {
	struct cache_time ctime;
	struct cache_time mtime;
	uint32_t dev;
	uint32_t ino;
	uint32_t mode;
	uint32_t uid;
	uint32_t gid;
	uint32_t size;
	/*
	 * unsigned char hash[hashsz];
	 * uint16_t flags;
	 * if (flags & CE_EXTENDED)
	 *	uint16_t flags2;
	 */
	unsigned char data[GIT_MAX_RAWSZ + 2 * sizeof(uint16_t)];
	char name[FLEX_ARRAY];
};

That is 62 fixed bytes under SHA-1. The flags word holds assume-valid (bit 15), extended (bit 14), a 2-bit merge stage and a 12-bit name length (read-cache-ll.h:34-37). In versions 2 and 3 the name is NUL-padded so each entry ends on an 8-byte boundary. Figure 1 is a real entry, from a three-file repository whose index came to 317 bytes measured here.

The whole 317-byte file adds up: a 12-byte header, three entries of 72, 72 and 80 bytes (src/main.c is a 10-character name and so gets 8 bytes of padding), a 61-byte TREE extension, and a 20-byte SHA-1 over everything before it. The recorded nanoseconds are real even though this build never compares them measured here.

The default version is 3, and it is demoted to 2 on every write unless some entry needs the extended flags (read-cache.c:1628, 2848-2850) from the code. Version 4 prefix-compresses paths. The strip count uses the same +1-bias varint that Part 1 showed in OFS_DELTA offsets. On git.git it saved 18%. On a 400,000-entry synthetic index it saved 24% but read slower single-threaded, 127 against 106 ms measured here.

Why stat data

The stat words let git status say "unchanged" without reading a file. match_stat_data() (statinfo.c:64-105) always compares mtime and size; ctime, uid, gid and inode only under core.trustctime and core.checkStat; nanoseconds only when built with USE_NSEC, which Linux builds lack from the code. One lstat and a compare per path. On git.git a default status made 4,764 lstat calls. With the fsmonitor daemon (new for Linux in v2.55.0) it made 0, and the median fell from 28.7 to 10.2 ms with fsmonitor and the untracked cache, n = 31 measured here, matrix.sh. A read-only command can still write: status rewrites the index when something changed or an entry is racy, and only if the file on disk still has the hash it read (repo_update_index_if_able(), read-cache.c:2748-2757) from the code.

How the index becomes a tree

The TREE extension caches one tree id per directory, in preorder: path\0, an entry count, a subtree count, the id. In the repository of Figure 1 the root node reads '' 3 1 followed by cf9d639a…, which is HEAD^{tree}. Every index change sets the count to −1 on each directory up to the root. update_one() skips a valid node whose tree object exists (cache-tree.c:294-297): 

	if (0 <= it->entry_count &&
	    odb_has_object(the_repository->objects, &it->oid,
			   ODB_HAS_OBJECT_RECHECK_PACKED | ODB_HAS_OBJECT_FETCH_PROMISOR))
		return it->entry_count;

git commit then hands cache_tree->oid straight to commit_tree_extended() (builtin/commit.c:1938) from the code. On git.git, write-tree with the extension stripped spent 48.5 ms rebuilding trees; with it intact the region was never entered measured here.

Extensions whose name starts A–Z are optional caches a reader may skip. Lowercase link (split index) and sdir (sparse index) change the meaning of the entries, so an older reader must refuse (read-cache.c:59-76). The trailing hash is checked only by git fsck, since v2.13.0, because checking it on every read cost too much.

Three things that are wrong in v2.55.0

All three are still present at origin/seen from the code. First, index.skipHash plus core.splitIndex loses staged entries. Skip-hash writes a null trailer, the shared index is named after it, and the reader treats a null base as "not split" (read-cache.c:2369). Five files added, ls-files shows zero measured here. Second, the EOIE extension can never validate in a SHA-256 repository: EOIE_SIZE is 4 + GIT_SHA1_RAWSZ (read-cache.c:3543) while the writer emits a 32-byte hash, so threaded index loading silently never runs there. Third, Documentation/config/index.adoc says index.threads "Defaults to 'true'", but unset has meant one thread since v2.20.0 (read-cache.c:2257-2258). Part 3 lists reproductions.

02Racy git and the lock that never waits

A cache whose freshness test is a timestamp has a blind spot: anything that happens within one tick of the clock. Git closes that hole twice. It also guards the index with the least patient lock in the repository.

The blind spot is easy to state. git add records a file's mtime and size, and writes the index in the same second. The file is then rewritten with different content of the same size, still in that second. Its stat data matches the cache, so it looks unchanged. Petr Baudis (Pasky) reported this on 24 October 2005, and the fix, "Racy GIT" (29e4d36357), shipped in v1.0.0 from the code.

The first defence is a content check. An entry whose mtime is not older than the index file's own mtime is "racily clean": its stat match proves nothing, so git hashes the file. The test is is_racy_stat(), read-cache.c:355-367. Without USE_NSEC it compares whole seconds: 

static int is_racy_stat(const struct index_state *istate,
			const struct stat_data *sd)
{
	return (istate->timestamp.sec &&
#ifdef USE_NSEC
		 /* nanosecond timestamped files can also be racy! */
		(istate->timestamp.sec < sd->sd_mtime.sec ||
		 (istate->timestamp.sec == sd->sd_mtime.sec &&
		  istate->timestamp.nsec <= sd->sd_mtime.nsec))
#else
		istate->timestamp.sec <= sd->sd_mtime.sec
#endif
		);
}

That check works only while the index stays as old as the entry. The next index write would give the index a newer mtime and make the stale entry look trustworthy again. So the second defence runs on every write. A racily clean entry whose content really differs is "smudged": its cached size is set to 0 (read-cache.c:2606, in ce_smudge_racily_clean_entry()). Size 0 will not match a 6-byte file, so a plain stat compare catches it forever after from the code.

The counterfactual in Figure 2 is the proof that the smudge matters. Moving the index's mtime forward by hand, without letting git rewrite it, leaves the size at 6 and the edit falsely clean measured here. The window is common in practice: right after cloning git.git, 119 of 4,765 entries were racily clean, and the first status rewrote the index to settle them. Git also once tried a third defence. A 2006 commit made the writer sleep before finishing the index (b7e58b17b5), and 0fc82cff12 removed it; both first appear in v1.4.3-rc1, so the sleep never reached a release from the code.

A lock with zero patience

Every index writer creates index.lock with O_CREAT|O_EXCL, writes the whole new file into it, and renames it over index, so each write gets a new inode and readers see the old file or the new one. The lock is taken once. lockfile.h:205-209: 

static inline int hold_lock_file_for_update(
	struct lock_file *lk, const char *path, int flags)
{
	return hold_lock_file_for_update_timeout(lk, path, flags, 0);
}

Timeout 0 means one attempt. A stale index.lock makes git add fail at once measured here. The other locks are more patient: a loose ref retries for 100 ms (core.filesRefLockTimeout, refs.c:993-1004), packed-refs.lock for 1000 ms (refs/packed-backend.c:1223), reftable's tables.list.lock for 100 ms (refs/reftable-backend.c:404), and loose objects take no lock at all from the code. So "git retries locks for 100 ms" is wrong for the index. A core.indexLockTimeout exists only on the seen branch (fd1a1fc743). Since v2.54.0 core.lockfilePid writes the holder's pid beside the lock, as index~pid.lock, so a failure can say whether that process is still alive. The practical answer to two writers on one index is not to have one index: each worktree gets its own, which is why parallel agents belong in separate worktrees reconstruction.

03Refs and what readers see

A ref is a name that points at an object, or, for a symbolic ref, at another name. Moving a branch is the moment a commit becomes real. The files backend makes each single move atomic, but not a group of them, and a reader can watch the group land one ref at a time.

On disk, in the default files backend, a loose ref is 40 hex digits and a newline: 41 bytes, which on ext4 costs a full 4 KiB block. HEAD is usually a symref, ref: refs/heads/main\n, 21 bytes measured here. Names pass a 256-entry character table plus rules: no leading dot, no .., no @{, no trailing .lock (refs.c:69-324). The code sorts names into classes. Root refs are all-caps names such as HEAD, ORIG_HEAD and AUTO_MERGE. Exactly two are pseudorefs, FETCH_HEAD and MERGE_HEAD, which transactions refuse to write (refs.c:888-901). Root refs and anything under refs/worktree/, refs/bisect/ or refs/rewritten/ are per-worktree (881-886); the glossary still lists only HEAD and refs/bisect/ from the code.

Storage sits behind struct ref_storage_be (refs/refs-internal.h:573), a table of about 25 function pointers. Two backends can be chosen, files and reftable. Inside files there is a second store, packed-refs: one sorted text file of <hex> <name> lines, with a ^<hex> line after an annotated tag giving what it peels to. Above 32 KiB it is mmapped and binary-searched (refs/packed-backend.c:523-640). Reads overlay loose refs on packed ones, and loose wins. Loose refs are read first, so a concurrent pack-refs, which writes the packed copy and then deletes the loose file, cannot make a ref vanish between the two reads from the code.

A transaction is many renames

Every ref update goes through a transaction: begin, queue updates, prepare, commit. In files, prepare locks every ref by creating <ref>.lock, retrying for up to 100 ms. Under the locks it compares each ref's current value with the expected old value, then writes the new value into the lockfile. A stale lock fails after 0.150 s of wall time measured here. Moving a branch that HEAD points at also takes HEAD.lock, to log the move in HEAD's reflog. Commit then renames the lockfiles over the refs, one at a time (refs/files-backend.c:3268-3421) from the code.

There is no global lock, by choice. Before touching packed-refs.lock, prepare checks that no new loose ref collides with a packed one, such as a/b against a. The comment at refs/files-backend.c:3011-3022 says why the check is not done under a lock: 

	 * Verify that none of the loose reference that we're about to write
	 * conflict with any existing packed references. Ideally, we'd do this
	 * check after the packed-refs are locked so that the file cannot
	 * change underneath our feet. But introducing such a lock now would
	 * probably do more harm than good as users rely on there not being a
	 * global lock with the "files" backend.
	 ...
	 * So instead, we accept the race for now.

Failure is all-or-nothing: if prepare cannot lock or verify every ref, nothing moves. A reader gets no such promise. To see what it gets, I ran a 10,000-ref update-ref --stdin while a second process looped for-each-ref --points-at=<new> and recorded each distinct count (refs-visibility.sh). Figure 3 shows the result.

Under files the reader saw 0, then 252, 838, 1,758, 3,254, 5,762 and 9,514 refs moved, then 10,000. A verifier's re-run saw eight in-between counts; under reftable both runs saw only 0 and 10,000 measured here. This is documented: Documentation/BreakingChanges.adoc says that with files, "Git may see in-between states when it reads references while a reference transaction is in the process of being committed to disk." Commands that must see a consistent set of refs, such as a server advertising them during a large push, get no such guarantee reconstruction.

Reflogs, and a regression already fixed

Each ref move also appends one line to logs/<ref>: old id, new id, committer, epoch, timezone, a tab and the message. A first commit's line is 129 bytes. Appends use O_APPEND and take no lock of their own. Branches, remote-tracking refs, notes and HEAD get reflogs by default; tags do not from the code. Expiry has a known bug in v2.50.0 through v2.55.0. reflog.h:25-28 swaps the two defaults: 

#define REFLOG_EXPIRE_OPTIONS_INIT(now) { \
	.default_expire_total = now - 30 * 24 * 3600, \
	.default_expire_unreachable = now - 90 * 24 * 3600, \
}

The documentation says 90 days for all entries and 30 for unreachable ones. With the swap, a gc or the maintenance reflog task prunes reachable entries older than 30 days; I reproduced the loss of 45- and 60-day entries measured here. It came in with 8565827570 (v2.50.0) and was reported and fixed upstream by 60cf500551 (24 September 2026), which is on master but in no tag yet. Until a release carries it, setting gc.reflogExpire and gc.reflogExpireUnreachable explicitly restores the documented behaviour, because the config parser overwrites both defaults (reflog.c:48-66) from the code.

04reftable: one rename per transaction

reftable stores refs the way git stores objects: in immutable files that are never edited, only replaced. A transaction writes one new table and publishes it with one rename, so a reader sees all of it or none.

Shawn Pearce specified the format in 2017. Its stated objectives (Documentation/technical/reftable.adoc:28-38) include "Near constant time lookup for any single reference, even when the repository is cold", "Support atomic push with O(size_of_update) operations", and combined reflog storage. Git imported the spec in v2.28.0, the library in v2.35.0 and the backend in v2.45.0 from the code.

A table is a 24-byte header (REFT, a version, a 3-byte block size of 4096 by default, and the lowest and highest update index it covers), then blocks, then a footer with a CRC-32. Ref blocks hold records sorted by name, each stored as "reuse N bytes of the previous name, then this suffix". Every 16th record, and any record that reuses nothing, is a restart point: its offset goes in a table at the end of the block, so a reader can binary-search the restarts and then scan at most 16 records (reftable/writer.c:79-80). Log blocks hold reflog records and are zlib-compressed. Figure 4 decodes a whole table next to the packed-refs file for the same refs.

The stack and its one rename

Tables live in .git/reftable/, listed in tables.list. A writer takes tables.list.lock (100 ms, reftable.lockTimeout), writes its table as <name>.temp.XXXXXX and renames it to a name like 0x000000000001-0x000000000004-ae42d254.ref. Nobody reads that file yet. Then reftable/stack.c:781-799 publishes it: 

	err = reftable_write_data(add->tables_list_lock.fd,
				  table_list.buf, table_list.len);
	reftable_buf_release(&table_list);
	if (err < 0) {
		err = REFTABLE_IO_ERROR;
		goto done;
	}

	err = fsync(add->tables_list_lock.fd);
	if (err < 0) {
		err = REFTABLE_IO_ERROR;
		goto done;
	}

	err = flock_commit(&add->tables_list_lock);

The rename inside flock_commit() is the commit point. The fsync is a macro (reftable/reftable-system.h:16) for git's component-gated fsync, which by default does nothing (§05). Readers that find a table gone mid-open retry for about three seconds, and keep the list's file descriptor open so a reused inode cannot fool them. After every commit the stack auto-compacts toward a geometric sequence with factor 2; in my benchmarks it stayed at one to four tables measured here. The atomicity is per stack. The main repository and each linked worktree have their own stack, and a transaction that spans them commits one stack after another (refs/reftable-backend.c:1012-1016) from the code.

Two loose ends. The writer still emits an obj index, mapping object-id prefixes to ref blocks, which served the 2017 goal of answering "does any ref point here?" quickly. Git never queries it: reftable_table_refs_for() is called only from a unit test. And reftable still rejects a beside a/b, though the format could hold both from the code. A reftable repository also keeps decoys for older tools: .git/HEAD reads ref: refs/heads/.invalid and refs/heads is a regular file, not a directory measured here. A small doc drift: reftable.geometricFactor is documented up to 256, and the code dies above 255. The numbers favour it anyway: 26 bytes per ref against 62, 167 against 3,100 ms to create 10,000 refs, 20 against 604 ms to delete 1,000 of 100,000, with full listing at 100,000 refs about even (96 against 90 ms) measured here, refs-bench.sh. files stays the default unless git is built WITH_BREAKING_CHANGES, the Git 3.0 switch, which BreakingChanges.adoc ties to JGit, libgit2 and Gitoxide supporting the format.

05Atomic, not durable

Every mutable file so far is published the same way: write a complete new file, then rename it over the old one. A reader never sees a torn file. Whether the new file survives a power cut is a separate question, and by default git answers it for packs only.

Durability is configured by core.fsync, a set of components. The default is write-or-die.h:27-35: 

#define FSYNC_COMPONENTS_OBJECTS (FSYNC_COMPONENT_LOOSE_OBJECT | \
				  FSYNC_COMPONENT_PACK)

#define FSYNC_COMPONENTS_DERIVED_METADATA (FSYNC_COMPONENT_PACK_METADATA | \
					   FSYNC_COMPONENT_COMMIT_GRAPH)

#define FSYNC_COMPONENTS_DEFAULT ((FSYNC_COMPONENTS_OBJECTS | \
				   FSYNC_COMPONENTS_DERIVED_METADATA) & \
				  ~FSYNC_COMPONENT_LOOSE_OBJECT)

Packs, pack indexes and bitmaps, and the commit-graph are synced. Loose objects are masked out. The index and refs are not in the set at all from the code. Counting trace2 hardware flushes: git update-ref, git add and hash-object -w each made 0 by default; core.fsync=reference gave 1 under files and 2 under reftable, and core.fsync=index gave 1. A whole traced add plus commit made no fsync or fdatasync call measured here.

Two details. Documentation/config/core.adoc says committed "is currently equivalent to objects", but since bc22d845c4 (v2.36.0) the code adds reference (write-or-die.h:37-38); measured, update-ref flushes once under committed and never under objects. And reflog appends have no fsync call at all: the only one in refs/files-backend.c is at line 2016, for the loose-ref lockfile from the code. After a crash the rename can outlive the bytes it published, a ref naming an object whose file was never flushed. Whether that happens depends on the filesystem's ordering. Anyone who needs commits to survive should set core.fsync=committed or added reconstruction. Figure 5 lists every structure in the collection, with its lock, its patience and its commit point.

06The wire: pkt-lines and protocol v2

Moving state between repositories means agreeing on refs, then shipping a pack. Every byte of that conversation, in every transport, is framed the same way, and protocol v2 changed the conversation far more than the framing.

The frame is the pkt-line: four hex digits giving a length that counts the four digits themselves, then the payload. 000eversion 2\n is 14 bytes, 4 plus 10. The maximum is 65,520 bytes in total (LARGE_PACKET_MAX, pkt-line.h:233). Lengths that cannot hold a payload are reused as markers, in pkt-line.c:434-451: 

	} else if (!len) {
		packet_trace("0000", 4, 0);
		*pktlen = 0;
		return PACKET_READ_FLUSH;
	} else if (len == 1) {
		packet_trace("0001", 4, 0);
		*pktlen = 0;
		return PACKET_READ_DELIM;
	} else if (len == 2) {
		packet_trace("0002", 4, 0);
		*pktlen = 0;
		return PACKET_READ_RESPONSE_END;
	} else if (len < 4) {

0000 ends a message, 0001 separates sections within one, 0002 ends a response over stateless HTTP, and 0003 is an error. When a pack and progress share one stream, each pkt-line carries a band byte after its length: 1 for pack data, 2 for progress (printed as remote: …), 3 for a fatal error. New in v2.55.0, control characters in remote sideband text are masked, with ANSI colour still allowed by default (sideband.allowControlCharacters) from the code.

Asking for v2

A client asks for v2 unless protocol.version says otherwise (protocol.c:46); the comment in protocol.h:32-37 still says the unconfigured default is v0, stale since v2.29.0. The server takes the highest version=N it finds in GIT_PROTOCOL and falls back to v0. Each transport smuggles that variable its own way from the code. git:// appends version=2 after a second NUL in its first packet (connect.c:1263-1267). ssh passes -o SendEnv=GIT_PROTOCOL, which works only with OpenSSH and only if the server's sshd accepts the variable. file:// sets the environment variable directly, and HTTP sends a Git-Protocol: version=2 header. An old server ignores all of these and speaks v0, which is why the scheme could ship without a flag day reconstruction.

v2 became the default in v2.26.0 (684ceae32d), was reverted in v2.27.0 (11c7f2a30b) after fetches of the kernel gave up negotiating too early, sat behind feature.experimental in v2.28.0, and has been the default since v2.29.0 (eb049759fb). The fix that made the second attempt stick is in §07.

Where v2 saves bytes

In v0 the server writes every ref before reading anything, with its capabilities hidden after a NUL on the first line. In v2 it sends a short capability list and waits. The client then sends commands. Each is a capability block, a 0001 delimiter, arguments and a flush. A clone sends ref-prefix refs/heads/, ref-prefix refs/tags/ and ref-prefix HEAD, and the server hands the prefixes straight to the ref backend's prefix iterator (ls-refs.c:202-211) from the code. The spec calls ref-prefix "purely for optimization". Here is the clone's ls-refs request as it crossed the pipe, one pkt-line per row measured here: 

0014 command=ls-refs\n
001a agent=git/2.55.0-Linux        no LF: written with packet_write_fmt("agent=%s")
0016 object-format=sha1            no LF either; receivers must accept both
0001                               delim: capabilities end, arguments begin
0009 peel\n
000c symrefs\n
000b unborn\n
001b ref-prefix refs/heads/\n
001a ref-prefix refs/tags/\n
0014 ref-prefix HEAD\n
0000                               flush: end of command

The server had advertised agent, ls-refs=unborn, fetch=shallow wait-for-done, server-option and object-format=sha1. Optional features such as filter appear only when the server's config turns them on. Its first reply line was 0050: 80 bytes holding HEAD's id and symref-target:refs/heads/main.

It is the whole optimization. In a repository with 11,101 refs the full listing is about 704 KB in either version. An up-to-date git fetch origin main --no-tags exchanged 202 bytes in v2 against 704,410 in v0 measured here. Most fetches do not look like that. Plain git fetch origin main also asks for refs/tags/ to follow tags, and received 72,892 bytes. git ls-remote origin main sends no prefix at all, because its patterns are tail matches done on the client, and got the full 702,972 bytes.

Over HTTP, v2 is stateless-connect. GET info/refs with the Git-Protocol header returns only capabilities, 144 bytes against v0's 560 for the small test repository. Every command is then one POST: 181 bytes up and 313 down for ls-refs, 323 up and 1,140 down for the fetch. The server holds no state between POSTs. The remote helper injects a 0002 after each response, and fetch-pack checks for it, so a truncated HTTP body is an error rather than a short answer. The byte counts are measured here; the reason for the marker is my reconstruction.

07Negotiation and push

A fetch has to work out which commits the two sides share before the server can build a pack of only what is missing. A push skips that and sends objects into a quarantine, where they stay until a hook accepts them.

The v2 fetch command is stateless. Each round the client sends its wants, every have the server has already acknowledged, and a fresh batch of haves (send_fetch_request(), fetch-pack.c:1411-1489). Batches start at 16 and double up to 16,384, then grow by 10%; over a v0 pipe they double to 32 and then add 32 each round (next_flush(), 277-291) from the code. The server answers with upload-pack.c:1686-1708: 

static int send_acks(struct upload_pack_data *data, struct object_array *acks)
{
	int i;

	packet_writer_write(&data->writer, "acknowledgments\n");

	/* Send Acks */
	if (!acks->nr)
		packet_writer_write(&data->writer, "NAK\n");

	for (i = 0; i < acks->nr; i++) {
		packet_writer_write(&data->writer, "ACK %s\n",
				    oid_to_hex(&acks->objects[i].item->oid));
	}

	if (!data->wait_for_done && ok_to_give_up(data)) {
		/* Send Ready */
		packet_writer_write(&data->writer, "ready\n");
		return 1;
	}

	return 0;
}

Every have the server owns is marked, with its parents, as something the client has. ok_to_give_up() is true once every want reaches such a commit. Then the server says ready, a 0001, and the pack follows in the same response; otherwise it sends a flush and waits for another round. The client stops sending haves after MAX_IN_VAIN, 256, without a new ACK. Since 4fa3f00abb (v2.27.0) that count starts only after the first ACK (fetch-pack.c:1476). That was the fix that let v2 become the default again from the code.

Which haves to send is the negotiator's choice. consecutive, the default, walks the client's history newest first and sends every commit not known to be common. skipping sends a commit, then skips gaps that grow as ttl*3/2+1. noop sends nothing. Figure 7 shows what each cost on this machine.

In scenario A, consecutive sent all 5,000 unshared commits and, because its last doubled batch ran 2,000 commits into shared history, 7,000 haves in 9 rounds; v0's slower growth needed 159 rounds. skipping got the exact 3 objects with 16 haves, because the remote-tracking tip is in its first batch. In scenario C it skipped past the common commit and received 6,001 objects where 3,004 were needed measured here.

How the pack is made and sent

upload-pack does not build packs. It spawns pack-objects --revs --stdout, feeds it the wants, --not, and the common haves, and relays its output in band 1, with empty band-1 packets as keepalives. It holds back the last byte. The comment in upload-pack.c:225-234 says why: "unpack-objects would happily accept a valid packdata with trailing garbage". If pack-objects dies, the client gets a pack missing its final byte, a truncated pack. In the captured clone that byte travelled alone as 0006 01 58 measured here.

Two documented surprises sit here. A v2 want only checks that the object exists, so a dangling commit or the tip of a ref hidden with uploadpack.hideRefs can be fetched by id; v0 refuses with "Server does not allow request for unadvertised object". gitprotocol-v2.adoc says wants "are not limited to advertised objects", but the uploadpack.allow*SHA1InWant pages do not say they apply only to v0. And from v2.19.0, a server with uploadpack.allowRefInWant sent wanted-refs before shallow-info, the reverse of what the client reads, so git clone --depth 1 died with "expected 'packfile', received 'shallow-info'". That was fixed upstream by 191740edaa (16 September 2026), on master and in no tag yet.

Push is still v0

Every push speaks protocol v0, over every transport. connect.c:1410-1417: 

	/*
	 * NEEDSWORK: If we are trying to use protocol v2 and we are planning
	 * to perform any operation that doesn't involve upload-pack (i.e., a
	 * fetch, ls-remote, etc), then fallback to v0 since we don't know how
	 * to do anything else (like push or remote archive) via v2.
	 */
	if (version == protocol_v2 && service != GIT_CONNECT_UPLOAD_PACK)
		version = protocol_v0;

remote-curl.c:494-501 does the same for HTTP, and receive-pack ignores a v2 request (builtin/receive-pack.c:2662-2668) from the code. The client sends one old new ref line per update, its capabilities after a NUL on the first, a flush, any push options, a flush, and then the pack, raw and unframed. A captured push --atomic -o ci.skip began 00ca + 40 zeros (a create) and ended with 000bci.skip, 0000 and PACK measured here. Figure 8 follows the pack through the server.

The server unpacks into objects/tmp_objdir-incoming-XXXXXX, exploding fewer than 100 objects (transfer.unpackLimit) and otherwise keeping the pack with index-pack --fix-thin --keep. Child processes see the quarantine as GIT_OBJECT_DIRECTORY with the real store as an alternate. The connectivity check proves every new ref leads only to objects the repository now has; it does not prove they are well formed. Only after pre-receive accepts does builtin/receive-pack.c:2105-2109 move them into place: 

	/*
	 * Now we'll start writing out refs, which means the objects need
	 * to be in their final positions so that other processes can see them.
	 */
	if (tmp_objdir_migrate(tmp_objdir) < 0) {

--atomic pushes use one ref transaction; others, since v2.51.0, a batched one that lets single refs fail. The report is pkt-lines nested inside band-1 pkt-lines: 002f 01 wrapping 000eunpack ok\n, 0018ok refs/heads/topic\n and 0000 measured here. Merging what arrives is Part 3's subject.
