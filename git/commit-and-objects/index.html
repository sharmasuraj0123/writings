The commit and its objectsTeardown

A git commit is five small zlib files, two rewrites of the index, six lock files and one rename. This first part of a three-part teardown traces one git add and one git commit through git v2.55.0, call by call, then follows the objects they write: how an object is named, where git looks for it, how packs store it as a backwards byte delta, and how fanout tables and bitmaps make finding and counting objects cheap.

01One commit, every write

Git is an append-only, content-addressed object store surrounded by a handful of small mutable files. Each of those files is either a pointer or a cache, and each has its own consistency story. Objects never change, so writing one needs no lock. The mutable files are published by writing a complete new copy and renaming it over the old one. Everything that makes git fast is derived data that can be rebuilt from the objects. This collection reads git v2.55.0 along those lines. Part 1 covers the store: one traced commit, then the objects it writes and the packs, indexes and bitmaps that hold them.

The lab repository holds two files, README (hello\n) and src/main.c, with author and committer dates pinned so every object id below is reproducible. The machine has no strace, so an LD_PRELOAD shim (fstrace.c) logged every open, rename, link, unlink, mkdir and exec with a microsecond offset measured here. Before doing anything, every git process walks up from the current directory and asks is_git_directory() three questions: is there a valid HEAD, an objects/ directory and a refs/ directory (setup.c:414-452) from the code. It then reads .git/config three times measured here.

git add: lock first, then hash

git add README src/main.c takes index.lock before it reads the index (builtin/add.c:454, 495). The lock is a tempfile opened O_RDWR|O_CREAT|O_EXCL, the same create-exclusively-then-rename protocol Linus wrote into update-cache.c on 7 April 2005 from the code. For each file, git hashes "blob <size>\0" plus the content, calls access() on the final path to see whether the object already exists, and creates tmp_obj_XXXXXX, mode 0444, in the two-hex-digit fan-out directory. On a fresh repository that open fails with ENOENT, so git makes the directory and retries. It deflates at zlib level 1, then link()s the temp file to its final name and unlink()s the temp measured here. The 21-byte file for hello\n is exactly zlib.compress(b"blob 6\x00hello\n", 1). Its name, ce013625…, is the SHA-1 of the uncompressed bytes. §02 takes that apart.

Then the 184-byte index is written into the lock, the lock is stated to record its mtime for the racy-git check (Part 2), and the lock is renamed over index. The whole add is 92 intercepted calls, 15 of which change .git/; the median wall time over 21 fresh repositories is 2.3 ms measured here.

git commit: trees before hooks

A plain git commit -m with no paths takes the COMMIT_AS_IS branch, builtin/commit.c:482-494 from the code: 

	if (!only && !pathspec.nr) {
		repo_hold_locked_index(the_repository, &index_lock,
				       LOCK_DIE_ON_ERROR);
		refresh_cache_or_die(refresh_flags);
		if (the_repository->index->cache_changed
		    || !cache_tree_fully_valid(the_repository->index->cache_tree))
			cache_tree_update(the_repository->index, WRITE_TREE_SILENT);
		if (write_locked_index(the_repository->index, &index_lock,
				       COMMIT_LOCK | SKIP_IF_UNCHANGED))
			die(_("unable to write new index file"));
		commit_style = COMMIT_AS_IS;
		ret = repo_get_index_file(the_repository);
		goto out;

cache_tree_update() writes the src tree (51 bytes on disk) and the root tree (80 bytes), and the index is rewritten with a 53-byte TREE extension, all before git even looks for a pre-commit hook. A rejecting pre-commit therefore leaves both trees and the new index on disk; the verification pass reproduced that measured here. Hooks are found by access(X_OK) on exact names (hook.c:26-36), so the shipped *.sample files never run from the code. The commit object (122 bytes on disk) follows.

The commit becomes visible through one ref transaction on HEAD (sequencer.c:1282-1290). The files backend splits it in two: a log-only update of HEAD, whose HEAD.lock is created and released empty, and a real update of refs/heads/main, whose lock receives 41 bytes, 40 hex digits and a newline (refs/files-backend.c:2537-2551) from the code. Both reflogs are appended with O_APPEND, 160 bytes each. Then rename(main.lock, main). That rename is the instant the commit exists. Before it, a reader sees the old branch; after it, the new one. Figure 1 shows every write in order.

The cleanup costs as much as the commit

Every commit then deletes AUTO_MERGE unconditionally (sequencer.c:2988-2989). Since v2.44.0 that is a ref deletion, and a deletion in the files backend opens a packed-refs transaction. So a clean commit in a repository with neither file still creates and removes AUTO_MERGE.lock and packed-refs.lock from the code. A stale packed-refs.lock left by a crashed process makes every commit wait about one second and print an error, though the commit still succeeds measured here.

Finally git maintenance run --auto runs as a child. It takes objects/maintenance.lock, estimates the loose objects by reading only objects/17/, finds nothing to do and exits. On this tiny repository that child is about half the wall time: 8.4 ms median per commit by default against 3.9 ms with maintenance.auto=false (N=21 each; a re-run gave 7.8 against 3.8) measured here. In total, the root commit is 286 intercepted calls, 46 of which change .git/, across six lock files. There is no fsync or fdatasync anywhere in the trace measured here, because the default core.fsync set leaves out loose objects, the index and refs (write-or-die.h:27-35) from the code.

The second commit, and the plumbing underneath

Changing README and committing again writes one blob, one tree and one commit. The src subtree is not re-hashed: its cache-tree node is still valid and its object exists, so update_one() returns early (cache-tree.c:294-297) from the code. Replaying both commits with plumbing (hash-object -w, update-index, write-tree, commit-tree, update-ref) produced all eight loose files and both reflogs byte for byte measured here. The porcelain adds no hidden state.

02An object is a header and a hash

Git stores four kinds of object: commit, tree, blob and tag, enum values 1 to 4 (object.h:98-111). Every object is a short text header, a NUL, and a payload. Its name is one hash over all of it. Nothing else about an object is part of its identity: not the file name, not the compression, not where it is stored.

The header is built by format_object_header(), object-file.c:90-99 from the code. The + 1 counts the NUL that xsnprintf writes: 

int format_object_header(char *str, size_t size, enum object_type type,
			 size_t objsize)
{
	const char *name = type_name(type);

	if (!name)
		BUG("could not get a type name for 'enum object_type' value %d", type);

	return xsnprintf(str, size, "%s %"PRIuMAX, name, (uintmax_t)objsize) + 1;
}

hash_object_body() (object-file.c:318-327) then feeds the header and the payload into one hash context. So the name can be reproduced with any hashing tool measured here: 

$ printf 'blob 6\0hello\n' | sha1sum
ce013625030ba8dba906f756967f9e9ca394464a  -
$ git hash-object README
ce013625030ba8dba906f756967f9e9ca394464a

Compression is not identity

Loose objects are deflated at Z_BEST_SPEED (environment.c:722), which is why every loose file starts 78 01. At level 9 it would start 78 da; the name and the adler32 trailer stay the same (Figure 2) measured here. One object can therefore have several valid files. That is why the byte-for-byte collision check added in v2.47.0 (b1b8dfde69) exempts loose objects from the code. A writer that finds the object already present only freshens its mtime and discards the new data (odb/source-loose.c:613-624). The rule has flipped once: in the first commit, e83c5163, the name was the SHA-1 of the compressed file, and d98b46f8d9 reversed that on 20 April 2005 from the code.

Collisions and the second SHA-1

The header is also why the SHAttered PDFs do not collide as blobs: the blob 422435\0 prefix moves the colliding blocks, and the two files get different ids measured here. The real defence is sha1dc, the default since v2.13.0. When it detects a collision attack, git_SHA1DCFinal() dies with "SHA-1 appears to be part of a collision attack" (sha1dc_git.c:17-26) instead of carrying on with the suspect hash from the code. Git also carries an "unsafe" SHA-1 in struct git_hash_algo, without collision detection, for speed. It is used only for the checksums that hashfd() writes at the end of files git generates itself: packs, .idx, .rev, bitmaps, the multi-pack-index, the commit-graph and the index (csum-file.c:178, 246) from the code.

Trees and commits

A tree entry is "<octal mode> <name>\0" followed by the child's id as raw bytes, 20 for SHA-1 and 32 for SHA-256. Directories are written 40000, not 040000; a zero-padded mode would change the hash, and fsck warns about it. Entries are sorted by base_name_compare() (tree.c:99-116), which treats the end of a directory's name as /. That is why the file a.c sorts before the directory a (Figure 3) from the code. The bytes also keep history that the tools hide: mktree preserves a 100664 mode, left over from early git, which recorded every permission bit, which ls-tree prints as 100644 and fsck tolerates unless run with --strict measured here.

A commit is tree, zero or more parent lines, author, committer, optional headers, a blank line and the message. parse_commit_buffer() is positional: it expects tree <hex>\n at byte 0, then parents, then reads only the committer date (commit.c:516-598) from the code. Parent order is part of the identity. Linus's comment from e83c5163 still sits in commit.c:1708-1712: "This ordering means that the same exact tree merged with a different order of parents will be a _different_ changeset even if everything else stays the same."

SHA-256: repositories yes, interop no

SHA-256 repositories have worked since v2.29.0, and Documentation/BreakingChanges.adoc makes SHA-256 the default for new repositories in Git 3.0, with "no plan to deprecate the 'sha1' object format". Interoperability is unfinished from the code. Translating between the two hashes (compatObjectFormat) needs a Rust build since v2.54.0, or git dies with "compatibility hash algorithm support requires Rust" (repository.c:197-209). The mapping is kept in a text objects/loose-object-idx, while gitformat-loose(5) documents a binary object-map/ that 2.55 never writes. And pack index v3, which the transition plan needs for packs, does not exist: the reader rejects every .idx version except 2 (packfile.c:200-207) measured here.

03Finding an object

A name says nothing about where an object lives. It might be a loose file, an entry in one of several packs, an object in an alternate repository, or nowhere yet in a partial clone. Git answers with one ordered chain of places to look, and the first hit wins.

The entry point is odb_read_object_info_extended(), which calls do_oid_object_info_extended() (odb.c:550-617, 699-714) from the code. An id in the repository's compat hash is first mapped to the storage hash. Replace refs are applied, the null id is rejected, and the in-memory source is asked. That source holds one object: the empty tree, for either hash. The empty blob is not virtual measured here. One nuance: the in-memory source is probed with the original id, not the replaced one. Then come the real sources, odb.c:563-573: 

	if (!odb_source_read_object_info(odb->inmemory_objects, oid, oi, flags))
		return 0;

	odb_prepare_alternates(odb);

	while (1) {
		struct odb_source *source;

		for (source = odb->sources; source; source = source->next)
			if (!odb_source_read_object_info(source, real, oi, flags))
				return 0;

The list holds the primary .git/objects first, then each alternate in order. Within a "files" source the pack store answers before the loose store (odb/source-files.c:51-62), and within the pack store the multi-pack-index answers before the individual packs, which are tried in most-recently-used order (packfile.c:2149-2170) from the code. Before answering, fill_pack_entry() checks that the pack can still be opened, because a concurrent repack may have deleted it. Figure 4 draws the whole chain.

If every source misses, git tries once more with OBJECT_INFO_SECOND_READ, unless the caller asked for a quick answer. The pack directories are rescanned and loose objects are skipped (packfile.c:2201-2202; odb/source-loose.c:213-217). That catches a pack a concurrent fetch or repack published after the first pass reconstruction. Then registered submodule sources are added and the chain retried. Finally, in a partial clone, one promisor_remote_get_direct() fetches the object from the server, unless the caller passed SKIP_FETCH_OBJECT from the code.

Two details contradict common belief. Git does not check loose objects first; for object info, packs come first in every source. And the comparator sort_pack() still contains a branch that puts local packs before alternate packs, but in 2.55 that branch is dead: each source now owns its own pack store, so a store never mixes local and alternate packs from the code. Local-first comes from the source order alone. The exception is the streaming path for small blobs: the pack stream refuses small objects, so loose is tried next, and a corrupt loose copy prints inflate: data stream error before git falls back to the pack and outputs the right content measured here.

This structure is new. The "files" source arrived in v2.54.0 (cb506a8a69), the loose-object source struct in v2.53.0 (ece43d9dc7) with its pluggable read callback in v2.55.0 (584338ed92), and the in-memory source in v2.55.0 (822d403651) from the code. Each source is a struct odb_source with its own callbacks, which leaves room for object stores that are not directories of files. reconstruction

04Packs and deltas

Loose objects are fine for the last few commits. For everything else git uses packs: one file holding many objects, most of them stored as a delta against another object in the same pack. The delta format is two operations, copy and insert, on raw bytes. Git does not store diffs of files. It stores byte recipes, usually pointing backwards in time.

A pack begins with PACK, a network-order version (git writes 2, reads 2 or 3) and an object count (pack.h:14-22). The entries follow, and the file ends with a hash of every preceding byte, which is also the pack's file name from the code. The examples below come from a lab repository with one 40-line file, a.txt, committed twice: the second commit changed line 020 and appended a line, and git repack -adq produced a 574-byte pack of six objects measured here.

Entry headers and the two delta types

Each entry starts with a type and an inflated size, written by encode_in_pack_object_header(), pack-write.c:516-526 from the code: 

	c = (type << 4) | (size & 15);
	size >>= 4;
	while (size) {
		if (n == hdr_len)
			die("object size is too enormous to format");
		*hdr++ = c | 0x80;
		c = size & 0x7f;
		size >>= 7;
		n++;
	}
	*hdr = c;

The high bit means "more bytes follow", bits 4-6 hold the type, and the size is spread low bits first. The first commit in the lab pack starts 96 0a: type 1, size 6 + (10 << 4) = 166. The newer blob starts bb 88 01: type 3, size 2,187 measured here. Types 6 and 7 are deltas. OBJ_REF_DELTA names its base by object id. OBJ_OFS_DELTA names it by a distance back from its own offset, encoded with a twist: packfile.c:1288-1302 from the code. 

	if (type == OBJ_OFS_DELTA) {
		unsigned used = 0;
		unsigned char c = base_info[used++];
		base_offset = c & 127;
		while (c & 128) {
			base_offset += 1;
			if (!base_offset || MSB(base_offset, 7))
				return 0;  /* overflow */
			c = base_info[used++];
			base_offset = (base_offset << 7) + (c & 127);
		}
		base_offset = delta_obj_offset - base_offset;
		if (base_offset <= 0 || base_offset >= delta_obj_offset)
			return 0;  /* out of bound */

The offset is big-endian, and each continuation adds 1 before shifting. So a two-byte offset starts at 128, not 0, and no value has two encodings reconstruction. The same +1-bias varint reappears in index v4 and in reftable (Part 2). The last check rejects any base at or after the delta itself, and the writer guarantees that never happens: write_one() writes a delta's base first, using offset 1 as a recursion sentinel (builtin/pack-objects.c:806-835) from the code. OFS offsets always point backwards. REF deltas remain mainly for thin packs, sent over the wire, whose bases are on the receiver and not in the pack; index-pack --fix-thin appends those bases, turning a 3-object pack into a 4-object one measured here.

The copy/insert codec

A delta is the base size, the result size, then opcodes. A byte with the high bit set is a COPY: bits 0-3 say which offset bytes follow and bits 4-6 which size bytes. Any other non-zero byte is an INSERT of that many literal bytes, 1 to 127. Opcode 0 is reserved and rejected. The interpreter is patch_delta(), patch-delta.c:39-71 (macro body and bounds checks trimmed) from the code: 

	while (data < top) {
		cmd = *data++;
		if (cmd & 0x80) {
			unsigned long cp_off = 0, cp_size = 0;
			…
			PARSE_CP_PARAM(0x01, cp_off, 0);
			PARSE_CP_PARAM(0x02, cp_off, 8);
			PARSE_CP_PARAM(0x04, cp_off, 16);
			PARSE_CP_PARAM(0x08, cp_off, 24);
			PARSE_CP_PARAM(0x10, cp_size, 0);
			PARSE_CP_PARAM(0x20, cp_size, 8);
			PARSE_CP_PARAM(0x40, cp_size, 16);
#undef PARSE_CP_PARAM
			if (cp_size == 0) cp_size = 0x10000;
			…
			memcpy(out, (char *) src_buf + cp_off, cp_size);
			out += cp_size;
			size -= cp_size;
		} else if (cmd) {
			…
			memcpy(out, data, cmd);
			out += cmd;
			data += cmd;
			size -= cmd;

The decoder accepts 24-bit copy sizes, but the encoder in diff-delta.c never emits a copy longer than 64 KiB (diff-delta.c:434-466) from the code. In the lab pack, the older 2,160-byte blob is a 22-byte delta against the newer one. Figure 5 decodes it. The old line 020 was not copied as a line. It was rebuilt from 7 bytes of line 028, one inserted "0", and 53 bytes that straddle two other lines measured here.

How pack-objects picks a base

pack-objects does not look at history to choose bases. It sorts candidates with type_size_sort() (builtin/pack-objects.c:2641-2681): by type, by a hash of the path name, preferred bases first, then delta islands, then size from largest down. The comment above it gives the reason for the last key: "the bigger file is likely the more recent one. The deepest deltas are therefore the oldest objects which are less susceptible to be accessed often" from the code. It then slides a window of 10 candidates over that list, with a maximum chain depth of 50, clamped at 4,095 because depth lives in a 12-bit field (OE_DEPTH_BITS). Existing deltas are reused when their base is also being written. The result is the lab pack's shape: the newer blob whole, the older one a delta measured here.

On git.git the pack holds 421,871 objects in 324,086,703 bytes. Undeltified, the same objects total 8.35 GB, so the pack is 25.8 times smaller. Trees are 95.5% deltified and blobs 92.5%; commits only 5.3% measured here. A sweep of window and depth on a 34,297-object subset (git.git at v1.5.0, one thread, no reuse) shows the defaults sit near the knee: 10/50 gave 8,260,676 bytes in 10.7 s, 250/250 gave 7,195,904 bytes (13% smaller) in 49.4 s, and 0/0, no deltas, gave 121,877,126 bytes measured here. On the same subset --name-hash-version=2 came out 0.4% larger and --path-walk 6.2% smaller. That path-walk run was given a plain object list rather than --revs, so treat it as indicative.

05Indexes over packs

A pack can only be parsed from the front. Random access needs a side file that maps an object id to an offset. That is the .idx, and like every other speed structure in git it is derived data: git index-pack can rebuild it from the pack alone.

An .idx v2 file is the magic \377tOc, the version, a 256-entry fanout table, the sorted object ids, their CRC32s, their 4-byte offsets, an optional table of 8-byte offsets, the pack's checksum and its own (Documentation/gitformat-pack.adoc:285-319). The magic was chosen so that v1 readers fail: read as fanout[0] it is an impossible object count (pack.h:24-41) from the code. The lab pack's index is 1,240 bytes: 8 + 1,024 + 6 × (20 + 4 + 4) + 20 + 20 measured here.

fanout[b] counts the objects whose first byte is at most b, so the objects starting with byte b sit in rows fanout[b-1] to fanout[b]. bsearch_hash(), hash-lookup.c:112-129, bisects only that slice from the code: 

	hi = ntohl(fanout_nbo[*hash]);
	lo = ((*hash == 0x0) ? 0 : ntohl(fanout_nbo[*hash - 1]));

	while (lo < hi) {
		unsigned mi = lo + (hi - lo) / 2;
		int cmp = hashcmp(table + mi * stride, hash,
				  the_repository->hash_algo);

		if (!cmp) {
			if (result)
				*result = mi;
			return 1;
		}
		if (cmp > 0)
			hi = mi;
		else
			lo = mi + 1;
	}

The same function serves the multi-pack-index and the commit-graph. An offset with the high bit set is not an offset but 0x80000000 | n, a row in the 64-bit table, used once a pack passes 2 GiB (pack-write.c:150-172). The CRC table exists so a repack can copy compressed bytes from one pack into another without inflating them and still detect corruption from the code. Figure 6 traces one lookup.

Side files, and the order they appear in

The .idx stores no sizes. An object's extent is the next offset minus its own, which needs the objects in pack order. The .rev file (RIDX) stores exactly that mapping, one u32 per object; without it git sorts the offsets in memory, and it is written by default since v2.41.0. Cruft packs add a .mtimes file, one timestamp per object, because expiry needs per-object ages that only loose files used to carry (Part 3 covers why) from the code.

When a pack is written, the .pack, .rev, .mtimes and bitmap are renamed into place first and the .idx last (pack-write.c:561-599). Readers find packs by their .idx, so that last rename publishes the pack. Pushed objects are the exception: quarantine migration orders .keep, .pack, .rev, .idx, then every other file after the .idx (tmp-objdir.c:193-206) from the code. On receipt, index-pack also compares every incoming object that already exists locally byte for byte and dies with "SHA1 COLLISION FOUND" on a mismatch (builtin/index-pack.c:883-926).

Many packs mean many binary searches. The multi-pack-index repeats the same tables in chunks (OIDF, OIDL, OOFF, LOFF) across all packs, keeping one copy of each object: from the preferred pack, else the newest (midx-write.c:203-224) from the code. Its format documentation has drifted. It says the version defaults to 2, while the code writes 1 (measured byte 01); it says packs in the bitmap order are sorted descending, while the comparator sorts ascending; and it says the BTMP chunk "encodes three pieces of information" and then lists two measured here. Part 3's findings register lists these with the rest.

06Bitmaps: counting without walking

To serve a clone or a fetch, git must know which objects are reachable from the wanted commits and not from the ones the client has. Without help that means walking every commit and every tree. A reachability bitmap stores the answer for selected commits as one bit per object, so the walk becomes a few bitwise operations.

Bit n is the nth object in pack order, not in object-id order. Ids are effectively random, and bitmaps over them "would have no locality, and thus compress poorly" (Documentation/technical/bitmap-format.adoc:13-30) from the code. Each bitmap is EWAH-compressed: run-length words that skip long stretches of zeros or ones, followed by literal words. A .bitmap file holds a header (BITM, version 1, flags 0x5 by default), four type bitmaps marking which positions are commits, trees, blobs and tags, one entry per selected commit, and a name-hash cache last (pack-bitmap-write.c:1365-1441). Figure 7 shows the lab file. The format document says the type bitmaps come "after the hash cache"; in the file they start at byte 32, right after the header measured here.

Not every commit gets a bitmap. The writer takes all of the 100 most recent commits, then one commit per gap, with gaps growing from about 100 to 5,000 commits, preferring ref tips and merges (pack-bitmap-write.c:1014-1101). The heuristic is JGit's, and the 2013 commit that added it calls it "a simplified version" from the code. On git.git, with 85,708 commits and 1,031 refs, the writer chose 321 commits and wrote a 2,043,482-byte .bitmap measured here.

The walk, as set operations

prepare_bitmap_walk() splits the requested tips into wants and haves. For each tip it ORs in a stored bitmap if there is one. Otherwise it walks back from the tip until it reaches a commit that has a bitmap, ORs that in, and adds the objects it passed on the way. It then computes wants AND NOT haves, and counting by type is a popcount of the result ANDed with each type bitmap (pack-bitmap.c:1514-1638, 2103-2257, 2612-2658) from the code. It gives up when the walk is limited by a pathspec, because bits know nothing about paths.

On git.git, rev-list --count --objects --all counted 421,871 objects in 9.3 to 9.5 s without bitmaps and 0.136 to 0.144 s with a multi-pack bitmap, about 66 times faster; a later re-run gave 9.055 and 0.127 s measured here. The two methods also disagree, and the bitmap is the one that is right. For v2.55.0 ^v2.54.0 the plain walk reported 3,815 objects and the bitmap 3,813. The two extra objects, a blob and a tree, are reachable from v2.54.0; the walk over-approximates the difference measured here.

Bitmaps also let pack-objects skip work when serving a clone. If the leading words of the result are all ones, the matching prefix of the existing pack is copied byte for byte, builtin/pack-objects.c:1219-1233 (one comment and bookkeeping line trimmed) from the code: 

	while (pos < end && reuse_packfile_bitmap->words[pos] == (eword_t)~0)
		pos++;

	if (pos) {
		off_t to_write;

		written = (pos * BITS_IN_EWORD);
		to_write = pack_pos_to_offset(reuse_packfile->p, written)
			- sizeof(struct pack_header);
		…
		hashflush(out);
		copy_pack_data(out, reuse_packfile->p, w_curs,

A clone-style pack-objects --all --stdout on git.git took 2.56 s with bitmaps, reported pack-reused 421871 (from 1), and produced exactly the 324,086,703 bytes of the pack on disk. Without bitmaps it took 17.37 s, counting and compressing objects first measured here. pack-objects uses bitmaps by default only when writing to stdout, which is how it serves fetches and clones. For an on-disk repack it avoids them, citing pack quality and robustness (builtin/pack-objects.c:5322-5342) from the code.
