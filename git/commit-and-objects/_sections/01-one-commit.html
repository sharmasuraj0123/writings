{{S}}One commit, every write

Git is an append-only, content-addressed object store surrounded by a handful of small mutable files. Each of those files is either a pointer or a cache, and each has its own consistency story. Objects never change, so writing one needs no lock. The mutable files are published by writing a complete new copy and renaming it over the old one. Everything that makes git fast is derived data that can be rebuilt from the objects. This collection reads git v2.55.0 along those lines. Part 1 covers the store: one traced commit, then the objects it writes and the packs, indexes and bitmaps that hold them.

The lab repository holds two files, README (hello\n) and src/main.c, with author and committer dates pinned so every object id below is reproducible. The machine has no strace, so an LD_PRELOAD shim (fstrace.c) logged every open, rename, link, unlink, mkdir and exec with a microsecond offset measured here. Before doing anything, every git process walks up from the current directory and asks is_git_directory() three questions: is there a valid HEAD, an objects/ directory and a refs/ directory (setup.c:414-452) from the code. It then reads .git/config three times measured here.

git add: lock first, then hash

git add README src/main.c takes index.lock before it reads the index (builtin/add.c:454, 495). The lock is a tempfile opened O_RDWR|O_CREAT|O_EXCL, the same create-exclusively-then-rename protocol Linus wrote into update-cache.c on 7 April 2005 from the code. For each file, git hashes "blob <size>\0" plus the content, calls access() on the final path to see whether the object already exists, and creates tmp_obj_XXXXXX, mode 0444, in the two-hex-digit fan-out directory. On a fresh repository that open fails with ENOENT, so git makes the directory and retries. It deflates at zlib level 1, then link()s the temp file to its final name and unlink()s the temp measured here. The 21-byte file for hello\n is exactly zlib.compress(b"blob 6\x00hello\n", 1). Its name, ce013625…, is the SHA-1 of the uncompressed bytes. §02 takes that apart.

Then the 184-byte index is written into the lock, the lock is stated to record its mtime for the racy-git check (Part 2), and the lock is renamed over index. The whole add is 92 intercepted calls, 15 of which change .git/; the median wall time over 21 fresh repositories is 2.3 ms measured here.

git commit: trees before hooks

A plain git commit -m with no paths takes the COMMIT_AS_IS branch, builtin/commit.c:482-494 from the code: 

	if (!only && !pathspec.nr) {
		repo_hold_locked_index(the_repository, &index_lock,
				       LOCK_DIE_ON_ERROR);
		refresh_cache_or_die(refresh_flags);
		if (the_repository->index->cache_changed
		    || !cache_tree_fully_valid(the_repository->index->cache_tree))
			cache_tree_update(the_repository->index, WRITE_TREE_SILENT);
		if (write_locked_index(the_repository->index, &index_lock,
				       COMMIT_LOCK | SKIP_IF_UNCHANGED))
			die(_("unable to write new index file"));
		commit_style = COMMIT_AS_IS;
		ret = repo_get_index_file(the_repository);
		goto out;

cache_tree_update() writes the src tree (51 bytes on disk) and the root tree (80 bytes), and the index is rewritten with a 53-byte TREE extension, all before git even looks for a pre-commit hook. A rejecting pre-commit therefore leaves both trees and the new index on disk; the verification pass reproduced that measured here. Hooks are found by access(X_OK) on exact names (hook.c:26-36), so the shipped *.sample files never run from the code. The commit object (122 bytes on disk) follows.

The commit becomes visible through one ref transaction on HEAD (sequencer.c:1282-1290). The files backend splits it in two: a log-only update of HEAD, whose HEAD.lock is created and released empty, and a real update of refs/heads/main, whose lock receives 41 bytes, 40 hex digits and a newline (refs/files-backend.c:2537-2551) from the code. Both reflogs are appended with O_APPEND, 160 bytes each. Then rename(main.lock, main). That rename is the instant the commit exists. Before it, a reader sees the old branch; after it, the new one. The cleanup costs as much as the commit

Every commit then deletes AUTO_MERGE unconditionally (sequencer.c:2988-2989). Since v2.44.0 that is a ref deletion, and a deletion in the files backend opens a packed-refs transaction. So a clean commit in a repository with neither file still creates and removes AUTO_MERGE.lock and packed-refs.lock from the code. A stale packed-refs.lock left by a crashed process makes every commit wait about one second and print an error, though the commit still succeeds measured here.

Finally git maintenance run --auto runs as a child. It takes objects/maintenance.lock, estimates the loose objects by reading only objects/17/, finds nothing to do and exits. On this tiny repository that child is about half the wall time: 8.4 ms median per commit by default against 3.9 ms with maintenance.auto=false (N=21 each; a re-run gave 7.8 against 3.8) measured here. In total, the root commit is 286 intercepted calls, 46 of which change .git/, across six lock files. There is no fsync or fdatasync anywhere in the trace measured here, because the default core.fsync set leaves out loose objects, the index and refs (write-or-die.h:27-35) from the code.

The second commit, and the plumbing underneath

Changing README and committing again writes one blob, one tree and one commit. The src subtree is not re-hashed: its cache-tree node is still valid and its object exists, so update_one() returns early (cache-tree.c:294-297) from the code. Replaying both commits with plumbing (hash-object -w, update-index, write-tree, commit-tree, update-ref) produced all eight loose files and both reflogs byte for byte measured here. The porcelain adds no hidden state.
