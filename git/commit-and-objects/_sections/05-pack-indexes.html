{{S}}Indexes over packs

A pack can only be parsed from the front. Random access needs a side file that maps an object id to an offset. That is the .idx, and like every other speed structure in git it is derived data: git index-pack can rebuild it from the pack alone.

An .idx v2 file is the magic \377tOc, the version, a 256-entry fanout table, the sorted object ids, their CRC32s, their 4-byte offsets, an optional table of 8-byte offsets, the pack's checksum and its own (Documentation/gitformat-pack.adoc:285-319). The magic was chosen so that v1 readers fail: read as fanout[0] it is an impossible object count (pack.h:24-41) from the code. The lab pack's index is 1,240 bytes: 8 + 1,024 + 6 × (20 + 4 + 4) + 20 + 20 measured here.

fanout[b] counts the objects whose first byte is at most b, so the objects starting with byte b sit in rows fanout[b-1] to fanout[b]. bsearch_hash(), hash-lookup.c:112-129, bisects only that slice from the code: 

	hi = ntohl(fanout_nbo[*hash]);
	lo = ((*hash == 0x0) ? 0 : ntohl(fanout_nbo[*hash - 1]));

	while (lo < hi) {
		unsigned mi = lo + (hi - lo) / 2;
		int cmp = hashcmp(table + mi * stride, hash,
				  the_repository->hash_algo);

		if (!cmp) {
			if (result)
				*result = mi;
			return 1;
		}
		if (cmp > 0)
			hi = mi;
		else
			lo = mi + 1;
	}

The same function serves the multi-pack-index and the commit-graph. An offset with the high bit set is not an offset but 0x80000000 | n, a row in the 64-bit table, used once a pack passes 2 GiB (pack-write.c:150-172). The CRC table exists so a repack can copy compressed bytes from one pack into another without inflating them and still detect corruption from the code. Figure {{fig-idx}} traces one lookup.

Side files, and the order they appear in

The .idx stores no sizes. An object's extent is the next offset minus its own, which needs the objects in pack order. The .rev file (RIDX) stores exactly that mapping, one u32 per object; without it git sorts the offsets in memory, and it is written by default since v2.41.0. Cruft packs add a .mtimes file, one timestamp per object, because expiry needs per-object ages that only loose files used to carry (Part 3 covers why) from the code.

When a pack is written, the .pack, .rev, .mtimes and bitmap are renamed into place first and the .idx last (pack-write.c:561-599). Readers find packs by their .idx, so that last rename publishes the pack. Pushed objects are the exception: quarantine migration orders .keep, .pack, .rev, .idx, then every other file after the .idx (tmp-objdir.c:193-206) from the code. On receipt, index-pack also compares every incoming object that already exists locally byte for byte and dies with "SHA1 COLLISION FOUND" on a mismatch (builtin/index-pack.c:883-926).

Many packs mean many binary searches. The multi-pack-index repeats the same tables in chunks (OIDF, OIDL, OOFF, LOFF) across all packs, keeping one copy of each object: from the preferred pack, else the newest (midx-write.c:203-224) from the code. Its format documentation has drifted. It says the version defaults to 2, while the code writes 1 (measured byte 01); it says packs in the bitmap order are sorted descending, while the comparator sorts ascending; and it says the BTMP chunk "encodes three pieces of information" and then lists two measured here. Part 3's findings register lists these with the rest.
