Git, taken apart

Git is an append-only store of content-addressed objects, surrounded by a handful of small mutable files: the index, the refs, a few caches. Each of those files has its own lock, its own commit point and its own consistency story. This collection reads all of it from the git v2.55.0 source, measures it on a real repository, and keeps a register of where the code and the documentation disagree.

Three parts, read in order or alone. Every claim cites a file and line at git@e9019fca (v2.55.0, 29 June 2026) or a measurement run on a 2-vCPU Linux box with git 2.55.0. Each part is one self-contained HTML file.

The collection

  • Part 1·23 October 2026·25 min read

    The commit and its objects

    A git commit is five small zlib files, two rewrites of the index, six lock files and one rename. This first part of a three-part teardown traces one git add and one git commit through git v2.55.0, call by call, then follows the objects they write: how an object is named, where git looks for it, how packs store it as a backwards byte delta, and how fanout tables and bitmaps make finding and counting objects cheap.

  • Part 2·23 October 2026·26 min read

    Mutable state and the wire

    Git's objects never change, so they need no lock. Everything around them does change: the index, the refs, the reflogs, and the conversation between two repositories. This part reads those small mutable files and the wire protocol from git v2.55.0: the index as a stat cache that becomes a tree, racy git, what a reader sees while refs move, reftable's one-rename commit, why every publish is atomic but nothing is fsynced by default, pkt-lines and protocol v2, negotiation, and the push quarantine.

  • Part 3·23 October 2026·29 min read

    Combining, keeping, and how it got here

    How git combines two histories: merge bases painted with generation numbers, merge-ort's one map and three phases, staged rename detection, conflict styles and rerere. How it keeps a repository fast without locking deletion: auto-maintenance, geometric repacks, prune's two-week clock, the commit-graph and Bloom filters. How a 1,244-line commit from 2005 became v2.55.0, what Git 3.0 will change, and the full register of bugs, documentation drift and gotchas found while reading.
