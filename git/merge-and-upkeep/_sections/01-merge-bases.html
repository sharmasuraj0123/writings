{{S}}Where two histories meet

Part 1 showed that git's history is an append-only store of objects named by their hashes. Part 2 showed the small mutable files around it: the index and the refs, each published by a rename. This part covers the two jobs that run on top of both. Merging combines two lines of history, and it only ever adds objects. Upkeep keeps the store fast, and it does that by rebuilding derived data and by deleting with a clock instead of a lock. The collection's thesis holds here too: everything that makes git fast can be thrown away and rebuilt from the objects.

A merge starts by finding the merge base: the newest commit both sides share. That commit is the "before" for a three-way merge. Git finds it in paint_down_to_common() in commit-reach.c. It walks a priority queue backwards from both tips. Commits reached from the first tip get the flag PARENT1; commits reached from the second get PARENT2. A commit that ends up with both flags is a common ancestor. It is marked RESULT, and its parents are marked STALE, because anything older than a common ancestor cannot be the best one. The four flags are object flag bits 16 to 19 from the code.

The core of the loop is commit-reach.c:144-160:

		flags = commit->object.flags & (PARENT1 | PARENT2 | STALE);
		if (flags == (PARENT1 | PARENT2)) {
			if (!(commit->object.flags & RESULT)) {
				commit->object.flags |= RESULT;
				tail = commit_list_append(commit, tail);
				/*
				 * The queue is generation-ordered; no
				 * remaining common ancestor can be a
				 * descendant of this one.
				 */
				if (!(mb_flags & MERGE_BASE_FIND_ALL) &&
				    generation < GENERATION_NUMBER_INFINITY)
					break;
			}
			/* Mark parents of a found merge stale */
			flags |= STALE;
		}

The break is new in v2.55.0. Commit 93e5b1680e lets plain git merge-base stop at the first common ancestor when the queue is ordered by generation number. Its message reports 5,229 ms falling to 24 ms. The same release made the loop's "is anything left to do" check O(1) (a186b7797a), about 27× faster inside this function on a 3.7-million-commit monorepo, per its message from the code. Merges never take the shortcut. They pass MERGE_BASE_FIND_ALL, because a merge needs every base.

Generation numbers come from the commit-graph file (section 06). They are what make this walk cheap. On git.git, the merge behind bc5204569f ("Git 2.43-rc0") has 54 merge bases. git merge-base --all on its two parents took 21 ms with a commit-graph and 1,142 ms without, median of 5 runs with lab/scratch/merge/tools/mb-time.sh. The single-base form took 11 ms measured here.

Several bases is the "criss-cross" case: each side has already merged the other once. It is not rare. In a 1-in-6 sample of git.git's two-parent merges, 125 of 3,498 (3.6%) had more than one base measured here. The next section shows what merge-ort does with more than one base.
