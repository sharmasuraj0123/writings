{{S}}The commit-graph and Bloom filters

Walking history means parsing commits: inflate each one, read its parent lines, look each parent up. The commit-graph file (v2.18.0) stores the answers in fixed-width rows instead. It is derived data, like a pack index: delete it and git falls back to parsing. Rows are in object-id order, so a commit's row number is its position. Each 36-byte CDAT row holds the root tree id, the positions of the first two parents (0x70000000 means none; a set top bit points into the EDGE list for octopus merges), and a 30-bit topological level packed with a 34-bit commit date from the code. Figure {{fig-cgraph}} decodes a five-commit file.

Generation numbers make the walk stop early: if gen(A) < gen(B), A cannot reach B. Version 1 used the topological level. Version 2 uses the corrected date, max(date, 1 + the parents'), stored as an offset in GDA2 (commit-graph.c:1630-1648). The 2018 levels made some merge-base walks worse, which is why v2 exists. On git.git, rev-list --count fell from 1.38 to 0.11 s and log --topo-order -n 10 from 1.59 to 0.018 s; plain log --oneline gained nothing measured here.

Path-limited history needs more. git log -- path must diff each commit's tree against its first parent. A changed-path Bloom filter answers "did this commit touch the path?" first (Figure {{fig-bloom}}). Each commit gets one filter, sized in bytes at 10 bits per changed path plus each leading directory, probed with 7 hashes; over 512 paths it becomes one all-ones byte (bloom.c:483-547).

Filters cost a write 8× slower (16.0 s against 2.0 s) and a file 16% bigger. The format document gets two details wrong: it sizes filters in 64-bit words, and it prints the second seed as 0x7e646e2, which does not reproduce git's bytes (findings C10, C11). Git still writes murmur3 v1 by default, which mishandles bytes ≥ 0x80 on signed-char platforms, and git gc ignores commitGraph.changedPaths by documented design (D11, D2) from the code.

Maintenance writes the graph as a chain of layers, merging layers when the new one is at least half the size of the one below. A v2.52.0 refactor (199d452758) broke the chain's shared level cache at commit-graph.c:2607-2608: 

	for (struct commit_graph *chain = g; chain; chain = chain->base_graph)
		g->topo_levels = &topo_levels;

It assigns g-> where chain-> was meant, so lower layers recompute levels: 0.10 s instead of 0.016 s to add one commit on git.git, with correct output measured here. 8ea36f63d8 fixed it after the tag; it is on master, untagged (finding A3). Scalar, for its part, pins commitGraph.generationVersion=1 and gc.auto=0 (scalar.c:142, 152).
