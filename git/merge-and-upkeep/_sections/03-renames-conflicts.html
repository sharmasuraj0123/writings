{{S}}Renames, line diffs and conflicts

Git stores no renames. The first README called that a design choice: rename information is "implicit in the trees involved" (section 07). So every merge and every diff -M has to guess. diffcore_rename_extended() guesses in three stages, cheapest first, and each stage removes pairs before the next one runs (Figure {{fig-renames}}).

Stage one pairs deleted and added paths whose blob ids are equal. Stage two pairs paths whose basename appears exactly once on each side, if their contents are similar enough. The bar is set in diffcore-rename.c:1495-1504: 

		/* Determine minimum score to match basenames */
		double factor = 0.5;
		char *basename_factor = getenv("GIT_BASENAME_FACTOR");
		int min_basename_score;

		if (basename_factor)
			factor = strtol(basename_factor, NULL, 10)/100.0;
		assert(factor >= 0.0 && factor <= 1.0);
		min_basename_score = minimum_score +
			(int)(factor * (MAX_SCORE - minimum_score));

At the default 50% threshold that is 75%. The environment variable is undocumented from the code. Only what is left reaches stage three: a matrix that scores every remaining source against every remaining destination. Each file is cut into chunks (a line, or 64 bytes), the chunks are hashed modulo 107927, and the score is the bytes copied times 60000 over the larger size. The rename limit is checked just before the matrix, and it bounds the matrix's area: sources × destinations against the limit squared. The limit is 1000 for diffs (diff.c:58) and 7000 for merges (merge-ort.c:3442-3443).

The scaling is what the funnel predicts. Moving 3,200 edited files under new names took 10,984 ms. Keeping their basenames took 683 ms; unedited moves took 18 ms measured here. One documented surprise sits in the option parser: -M5 means 50%, because the digits are read as a decimal fraction (diff.c:6344-6377; Documentation/diff-options.adoc:585-589).

Once paths are paired, file contents go to xdl_merge(). One-sided changes are taken, identical changes accepted, and overlaps become conflicts. Git asks for the ZEALOUS level, which shrinks a conflict by moving lines both sides share outside the markers. The diff3 and zdiff3 styles are capped at EAGER, because diff3 output "does not make sense for anything more aggressive"; zdiff3 then trims identical lines at the edges (xdiff/xmerge.c:534-541, 655-663). ort diffs with histogram, chosen in v2.31.0 because, in its author's words, "I really don't like silent mismerges". Plain git diff still defaults to Myers with cost cut-offs. On the whole v2.30.0..v2.55.0 diff it took 2,286 ms and printed the most lines; histogram took 1,820 ms and patience 1,547 ms. The excess came from po/*.po translation files measured here.

That id matters for git rerere, which replays recorded resolutions. It names a conflict by hashing its two sides, labels and base removed, sorted. In the reproduction, merge and zdiff3 styles gave the same id; diff3 gave a different one, because the shared line stayed inside its sides. Documentation/technical/rerere.adoc:9-19 promises normalisation across styles, which holds for zdiff3 only (finding C16) measured here.

One cache goes unused. ort can reuse renames found for the previous pick of a rebase, but the sequencer zeroes its result for each pick (sequencer.c:781) and merge_switch_to_result() frees the cache. git replay keeps one result and benefits: on an 8-commit topic over 800 renamed files it ran rename detection once (995 ms), where git rebase ran it 8 times (2,981 ms) measured here. That is finding B4.
