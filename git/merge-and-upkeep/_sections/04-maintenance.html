{{S}}Who tidies up: gc --auto and maintenance

Every write in Part 1 adds a loose object, and every fetch adds a pack. Left alone, lookups slow down as both pile up. Git has always tidied as a side effect of ordinary commands. What changed recently is which command does it.

The old answer is git gc --auto. Its first test is a guess at the number of loose objects, in builtin/gc.c:470-482: 

	/*
	 * This is weird, but stems from legacy behaviour: the GC auto
	 * threshold was always essentially interpreted as if it was rounded up
	 * to the next multiple 256 of, so we retain this behaviour for now.
	 */
	int auto_threshold = DIV_ROUND_UP(limit, 256) * 256;
	…
	return loose_count > auto_threshold;

The count comes from one directory. odb/source-loose.c:539 opens objects/17, counts the names in it, and line 560 returns count * 256. With gc.auto at 6700 the threshold is 6912, so gc fires at 28 objects in that one shard. A synthetic repository with 27 there did nothing; one more object triggered a repack measured here. More than 50 packs selects an all-into-one repack, by default with --cruft. A non-empty gc.log younger than a day blocks every later detached auto-gc, because the next run "is likely to fail in the same way" from the code.

But porcelain no longer calls gc --auto. commit, fetch, merge, rebase, am and receive-pack spawn git maintenance run --auto, gated by maintenance.auto, which falls back to gc.auto > 0 (run-command.c:1956-1993). Since v2.54.0 (452b12c2e0) an unscheduled run uses the geometric strategy, because gc's all-into-one repack "is wasteful in small- and medium-sized repositories, in large repos it may even be prohibitively expensive". Figure {{fig-maint}} shows both paths.

The geometric task weighs packs by object count. It finds the smallest packs that break a factor-2 progression and rolls them into one with pack-objects --stdin-packs, which copies objects without walking reachability. Only when every pack would roll up does it fall back to gc's all-into-one --cruft repack (builtin/gc.c:1570-1671). The difference shows. A repository with 700 reachable loose objects, 3 of them in 17/, is below gc's threshold. Yet a single git commit there ran a cruft repack and wrote a multi-pack index, because with no packs at all, "every pack" rolls up measured here.

The ten tasks run under objects/maintenance.lock, and a busy lock makes --auto exit 0 silently. In v2.55 the lock passes to the detached child (6e95b07e5f) from the code. The trade-off is in the strategy's own commit, d9bccf2ec3: "pruning of unreferenced objects is not going to happen regularly anymore". The next section is about that pruning.
