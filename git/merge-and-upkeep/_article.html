This is Part 3 of 3 of Git, taken apart. Part 1 covers the commit and its objects, packs and bitmaps; Part 2 covers the index, refs, durability and the wire protocol. This part assumes both and does not re-explain their formats.

01Where two histories meet

Part 1 showed that git's history is an append-only store of objects named by their hashes. Part 2 showed the small mutable files around it: the index and the refs, each published by a rename. This part covers the two jobs that run on top of both. Merging combines two lines of history, and it only ever adds objects. Upkeep keeps the store fast, and it does that by rebuilding derived data and by deleting with a clock instead of a lock. The collection's thesis holds here too: everything that makes git fast can be thrown away and rebuilt from the objects.

A merge starts by finding the merge base: the newest commit both sides share. That commit is the "before" for a three-way merge. Git finds it in paint_down_to_common() in commit-reach.c. It walks a priority queue backwards from both tips. Commits reached from the first tip get the flag PARENT1; commits reached from the second get PARENT2. A commit that ends up with both flags is a common ancestor. It is marked RESULT, and its parents are marked STALE, because anything older than a common ancestor cannot be the best one. The four flags are object flag bits 16 to 19 from the code.

The core of the loop is commit-reach.c:144-160:

		flags = commit->object.flags & (PARENT1 | PARENT2 | STALE);
		if (flags == (PARENT1 | PARENT2)) {
			if (!(commit->object.flags & RESULT)) {
				commit->object.flags |= RESULT;
				tail = commit_list_append(commit, tail);
				/*
				 * The queue is generation-ordered; no
				 * remaining common ancestor can be a
				 * descendant of this one.
				 */
				if (!(mb_flags & MERGE_BASE_FIND_ALL) &&
				    generation < GENERATION_NUMBER_INFINITY)
					break;
			}
			/* Mark parents of a found merge stale */
			flags |= STALE;
		}

The break is new in v2.55.0. Commit 93e5b1680e lets plain git merge-base stop at the first common ancestor when the queue is ordered by generation number. Its message reports 5,229 ms falling to 24 ms. The same release made the loop's "is anything left to do" check O(1) (a186b7797a), about 27× faster inside this function on a 3.7-million-commit monorepo, per its message from the code. Merges never take the shortcut. They pass MERGE_BASE_FIND_ALL, because a merge needs every base.

Generation numbers come from the commit-graph file (section 06). They are what make this walk cheap. On git.git, the merge behind bc5204569f ("Git 2.43-rc0") has 54 merge bases. git merge-base --all on its two parents took 21 ms with a commit-graph and 1,142 ms without, median of 5 runs with lab/scratch/merge/tools/mb-time.sh. The single-base form took 11 ms measured here.

Several bases is the "criss-cross" case: each side has already merged the other once. It is not rare. In a 1-in-6 sample of git.git's two-parent merges, 125 of 3,498 (3.6%) had more than one base measured here. The next section shows what merge-ort does with more than one base.

02merge-ort: one map, three phases

Since v2.34.0 the default merge strategy is ort, Elijah Newren's rewrite (6a5fb96672). The old recursive strategy is gone: commit ad45b327c0 moved its shared helpers into merge-ort.c and deleted merge-recursive.[ch], 4,212 lines, in v2.50.0. -s recursive is now a synonym for ort from the code.

ort keeps one map. opt->priv->paths is a strmap from every relevant path to a merged_info or, if the path still needs work, a conflict_info. Path strings are interned, so later phases compare pointers instead of strings (merge-ort.c:318-528). The merge itself is three phases and an optional restart, in merge-ort.c:5250-5275: 

redo:
	trace2_region_enter("merge", "collect_merge_info", opt->repo);
	if (collect_merge_info(opt, merge_base, side1, side2) != 0) {
	…
	trace2_region_enter("merge", "renames", opt->repo);
	result->clean = detect_and_process_renames(opt);
	trace2_region_leave("merge", "renames", opt->repo);
	if (opt->priv->renames.redo_after_renames == 2) {
		trace2_region_enter("merge", "reset_maps", opt->repo);
		clear_or_reinit_internal_opts(opt->priv, 1);
		trace2_region_leave("merge", "reset_maps", opt->repo);
		goto redo;
	}

collect_merge_info() walks the base and both sides' trees together. Its callback builds a 3-bit match_mask. If all three versions of a subtree have the same id, the subtree is resolved without opening it. That is why a merge touching three files in a large repository costs little: unchanged directories are compared by hash and skipped (merge-ort.c:1253-1453). Rename detection comes next, then process_entries(), which visits paths children first, merges file contents and writes the result trees bottom-up from the code. Figure 1 lays out the phases and what each one writes.

"In memory" needs care. git merge-tree --write-tree and git replay never touch the index or the worktree. They still write objects. On a freshly gc'd clone, a conflicted merge-tree left 2 new loose objects, and --quiet (v2.50.0) left 0 measured here. The two are the merged blob, conflict markers included, and the tree that holds it; inner merges of a criss-cross record objects even under --quiet from the code. Only merge_switch_to_result() touches the checkout. It runs a two-way checkout, appends the stage 1, 2 and 3 entries of conflicted paths and sorts the index once (merge-ort.c:4594-4967).

It also points AUTO_MERGE at the result tree, and it does so on clean merges too. Documentation/revisions.adoc:75-78 says the ref records the tree "when a merge operation resulted in conflicts". A clean git merge --no-commit writes it anyway (merge-ort.c:4924-4955). This is finding C15 in the register.

Several bases are merged pairwise into a virtual commit first. Its diff3 label is "merged common ancestors", and when the bases themselves conflict, the virtual base carries 9-character markers labelled "Temporary merge branch 1" and "2" from the code. The 54-base merge above ran the collect, renames and process cycle 55 times in 0.53 s measured here.

03Renames, line diffs and conflicts

Git stores no renames. The first README called that a design choice: rename information is "implicit in the trees involved" (section 07). So every merge and every diff -M has to guess. diffcore_rename_extended() guesses in three stages, cheapest first, and each stage removes pairs before the next one runs (Figure 2).

Stage one pairs deleted and added paths whose blob ids are equal. Stage two pairs paths whose basename appears exactly once on each side, if their contents are similar enough. The bar is set in diffcore-rename.c:1495-1504: 

		/* Determine minimum score to match basenames */
		double factor = 0.5;
		char *basename_factor = getenv("GIT_BASENAME_FACTOR");
		int min_basename_score;

		if (basename_factor)
			factor = strtol(basename_factor, NULL, 10)/100.0;
		assert(factor >= 0.0 && factor <= 1.0);
		min_basename_score = minimum_score +
			(int)(factor * (MAX_SCORE - minimum_score));

At the default 50% threshold that is 75%. The environment variable is undocumented from the code. Only what is left reaches stage three: a matrix that scores every remaining source against every remaining destination. Each file is cut into chunks (a line, or 64 bytes), the chunks are hashed modulo 107927, and the score is the bytes copied times 60000 over the larger size. The rename limit is checked just before the matrix, and it bounds the matrix's area: sources × destinations against the limit squared. The limit is 1000 for diffs (diff.c:58) and 7000 for merges (merge-ort.c:3442-3443).

The scaling is what the funnel predicts. Moving 3,200 edited files under new names took 10,984 ms. Keeping their basenames took 683 ms; unedited moves took 18 ms measured here. One documented surprise sits in the option parser: -M5 means 50%, because the digits are read as a decimal fraction (diff.c:6344-6377; Documentation/diff-options.adoc:585-589).

Once paths are paired, file contents go to xdl_merge(). One-sided changes are taken, identical changes accepted, and overlaps become conflicts. Git asks for the ZEALOUS level, which shrinks a conflict by moving lines both sides share outside the markers. The diff3 and zdiff3 styles are capped at EAGER, because diff3 output "does not make sense for anything more aggressive"; zdiff3 then trims identical lines at the edges (xdiff/xmerge.c:534-541, 655-663). ort diffs with histogram, chosen in v2.31.0 because, in its author's words, "I really don't like silent mismerges". Plain git diff still defaults to Myers with cost cut-offs. On the whole v2.30.0..v2.55.0 diff it took 2,286 ms and printed the most lines; histogram took 1,820 ms and patience 1,547 ms. The excess came from po/*.po translation files measured here.

That id matters for git rerere, which replays recorded resolutions. It names a conflict by hashing its two sides, labels and base removed, sorted. In the reproduction, merge and zdiff3 styles gave the same id; diff3 gave a different one, because the shared line stayed inside its sides. Documentation/technical/rerere.adoc:9-19 promises normalisation across styles, which holds for zdiff3 only (finding C16) measured here.

One cache goes unused. ort can reuse renames found for the previous pick of a rebase, but the sequencer zeroes its result for each pick (sequencer.c:781) and merge_switch_to_result() frees the cache. git replay keeps one result and benefits: on an 8-commit topic over 800 renamed files it ran rename detection once (995 ms), where git rebase ran it 8 times (2,981 ms) measured here. That is finding B4.

04Who tidies up: gc --auto and maintenance

Every write in Part 1 adds a loose object, and every fetch adds a pack. Left alone, lookups slow down as both pile up. Git has always tidied as a side effect of ordinary commands. What changed recently is which command does it.

The old answer is git gc --auto. Its first test is a guess at the number of loose objects, in builtin/gc.c:470-482: 

	/*
	 * This is weird, but stems from legacy behaviour: the GC auto
	 * threshold was always essentially interpreted as if it was rounded up
	 * to the next multiple 256 of, so we retain this behaviour for now.
	 */
	int auto_threshold = DIV_ROUND_UP(limit, 256) * 256;
	…
	return loose_count > auto_threshold;

The count comes from one directory. odb/source-loose.c:539 opens objects/17, counts the names in it, and line 560 returns count * 256. With gc.auto at 6700 the threshold is 6912, so gc fires at 28 objects in that one shard. A synthetic repository with 27 there did nothing; one more object triggered a repack measured here. More than 50 packs selects an all-into-one repack, by default with --cruft. A non-empty gc.log younger than a day blocks every later detached auto-gc, because the next run "is likely to fail in the same way" from the code.

But porcelain no longer calls gc --auto. commit, fetch, merge, rebase, am and receive-pack spawn git maintenance run --auto, gated by maintenance.auto, which falls back to gc.auto > 0 (run-command.c:1956-1993). Since v2.54.0 (452b12c2e0) an unscheduled run uses the geometric strategy, because gc's all-into-one repack "is wasteful in small- and medium-sized repositories, in large repos it may even be prohibitively expensive". Figure 4 shows both paths.

The geometric task weighs packs by object count. It finds the smallest packs that break a factor-2 progression and rolls them into one with pack-objects --stdin-packs, which copies objects without walking reachability. Only when every pack would roll up does it fall back to gc's all-into-one --cruft repack (builtin/gc.c:1570-1671). The difference shows. A repository with 700 reachable loose objects, 3 of them in 17/, is below gc's threshold. Yet a single git commit there ran a cruft repack and wrote a multi-pack index, because with no packs at all, "every pack" rolls up measured here.

The ten tasks run under objects/maintenance.lock, and a busy lock makes --auto exit 0 silently. In v2.55 the lock passes to the detached child (6e95b07e5f) from the code. The trade-off is in the strategy's own commit, d9bccf2ec3: "pruning of unreferenced objects is not going to happen regularly anymore". The next section is about that pruning.

05Deleting by the clock

Adding objects needs no lock, because an object never changes (Part 1). Deleting them is harder. git prune cannot lock out every process that might be about to reference an object, so it uses time instead. It deletes an unreachable loose object only if the file's mtime is older than --expire, two weeks by default since v1.5.5 (25ee9731c1). Its roots are the index, every ref, every worktree's HEAD and every reflog entry. Since v2.2.0 (d3038d22f9) it also keeps anything reachable from a recent unreachable object, so a tree written a minute ago keeps an old blob alive (builtin/prune.c:84-109) from the code.

The clock only works if writers reset it. When a writer finds that an object it wants to write already exists, it "freshens" it instead: utime() on the loose file, or on the whole pack. packfile.c:2172-2186: 

int packfile_store_freshen_object(struct packfile_store *store,
				  const struct object_id *oid)
{
	struct pack_entry e;
	if (!find_pack_entry(store, oid, &e))
		return 0;
	if (e.p->is_cruft)
		return 0;
	if (e.p->freshened)
		return 1;
	if (utime(e.p->pack_name, NULL))
		return 0;
	e.p->freshened = 1;
	return 1;
}

A pack is touched once per process. A cruft pack is never touched, because its per-object mtimes live in a .mtimes file; returning 0 makes the caller write the object loose again, with a fresh mtime. Both paths showed up in the lab. Rewriting an old loose blob reset its mtime and took it off prune -n's list, and rewriting a cruft-packed blob produced a new loose file measured here.

The manual is candid about what is left. Users "who run commands concurrently have to live with some risk of corruption (which seems to be low in practice)" (Documentation/git-gc.adoc:167-169). And since gc and the maintenance reflog task both expire reflogs, their roots were thinned by a v2.50.0 regression: the built-in defaults expire all entries after 30 days and unreachable ones after 90, the reverse of the documentation (reflog.h:25-28). It was reported and fixed upstream after the v2.55.0 tag by 60cf500551, which is on master but in no release yet (finding A1). Reflogs themselves are covered in Part 2, and worktree pruning in One repository, many agents.

06The commit-graph and Bloom filters

Walking history means parsing commits: inflate each one, read its parent lines, look each parent up. The commit-graph file (v2.18.0) stores the answers in fixed-width rows instead. It is derived data, like a pack index: delete it and git falls back to parsing. Rows are in object-id order, so a commit's row number is its position. Each 36-byte CDAT row holds the root tree id, the positions of the first two parents (0x70000000 means none; a set top bit points into the EDGE list for octopus merges), and a 30-bit topological level packed with a 34-bit commit date from the code. Figure 5 decodes a five-commit file.

Generation numbers make the walk stop early: if gen(A) < gen(B), A cannot reach B. Version 1 used the topological level. Version 2 uses the corrected date, max(date, 1 + the parents'), stored as an offset in GDA2 (commit-graph.c:1630-1648). The 2018 levels made some merge-base walks worse, which is why v2 exists. On git.git, rev-list --count fell from 1.38 to 0.11 s and log --topo-order -n 10 from 1.59 to 0.018 s; plain log --oneline gained nothing measured here.

Path-limited history needs more. git log -- path must diff each commit's tree against its first parent. A changed-path Bloom filter answers "did this commit touch the path?" first (Figure 6). Each commit gets one filter, sized in bytes at 10 bits per changed path plus each leading directory, probed with 7 hashes; over 512 paths it becomes one all-ones byte (bloom.c:483-547).

Filters cost a write 8× slower (16.0 s against 2.0 s) and a file 16% bigger. The format document gets two details wrong: it sizes filters in 64-bit words, and it prints the second seed as 0x7e646e2, which does not reproduce git's bytes (findings C10, C11). Git still writes murmur3 v1 by default, which mishandles bytes ≥ 0x80 on signed-char platforms, and git gc ignores commitGraph.changedPaths by documented design (D11, D2) from the code.

Maintenance writes the graph as a chain of layers, merging layers when the new one is at least half the size of the one below. A v2.52.0 refactor (199d452758) broke the chain's shared level cache at commit-graph.c:2607-2608: 

	for (struct commit_graph *chain = g; chain; chain = chain->base_graph)
		g->topo_levels = &topo_levels;

It assigns g-> where chain-> was meant, so lower layers recompute levels: 0.10 s instead of 0.016 s to add one commit on git.git, with correct output measured here. 8ea36f63d8 fixed it after the tag; it is on master, untagged (finding A3). Scalar, for its part, pins commitGraph.generationVersion=1 and gc.auto=0 (scalar.c:142, 152).

07From e83c5163 to Git 3.0

Git's first commit, e83c5163, is dated 7 April 2005. It is 11 files and 1,244 lines that build seven programs, from update-cache to cat-file, linked against OpenSSL. Its README calls git "the stupid content tracker" and names the two ideas this collection has followed: a content-addressable object database and a "current directory cache", today's index. It already rules out rename tracking, and it puts trust outside git: "the trust has to come from outside", by signing one top-level hash from the code.

The object in git.git today is not the one Linus wrote. Its dates are epoch seconds with a timezone, which the original ctime() code could not produce. Early history was rewritten by convert-cache after the format changed measured here. And the format changed fast. Within a fortnight came recursive trees (9 April), the rename of .dircache to .git (11 April, "That's clearly moronic"), a network-byte-order index (15 April), hashing before compression and the index's trailing checksum (20 April), and tag objects (25 April). Figure 7 sets the two designs side by side.

After v0.99 (10 July 2005) the object and index model kept its shape. Everything since is a layer. Packs arrived 11 weeks after the first commit. Junio C Hamano has tagged every release since v0.99.2. Then came offset deltas and packed-refs, the v1.5.0 staging-area interface, smart HTTP, bitmaps, collision-detecting SHA-1, protocol v2 and the commit-graph in the same release, SHA-256 repositories, ort, reftable and geometric maintenance. Each is derived data or an alternative encoding. None replaced the object model, and some, like Z_BEST_SPEED for loose objects since v1.5.3, are only tuning reconstruction.

Some code is older than the format. write_commit_tree() still carries Linus's comment that "the same exact tree merged with a different order of parents will be a _different_ changeset", and alloc_nr() is byte-identical to 2005 from the code. C grew from 34,041 lines at v1.0.0 to 436,044 at v2.55.0, shell (mostly the test suite) from 12,072 to 337,602. 2,335 people have authored commits. Since mid-2024 Patrick Steinhardt has written 27% of non-merge commits, more than three times Junio's count, much of it the refs, object-database and Rust work measured here.

Rust is one 1,571-line crate, gitcore, built by default since v2.55.0 and opted out with NO_RUST; Documentation/BreakingChanges.adoc:201-203 still says to opt in with WITH_RUST=YesPlease, a knob that does not exist (C20). The same document lists Git 3.0: SHA-256 and reftable as defaults for new repositories, main as the default branch, Rust required. It says there is "no plan to deprecate" the SHA-1 format and "no planned release date" for 3.0 from the code.

08The findings register

Reading v2.55.0 line by line against its manual turns up mismatches. Figure 8 lists all of them, in four groups. Group A is three real bugs in v2.55.0 that upstream has already fixed after the tag: the fixes are on master, next and seen but in no release yet. None of them was found here; each was reported or fixed upstream, and the register records the introducing commit, the fix and a reproduction. Group B is five latent bugs or gaps still present at origin/seen as fetched on 21 October 2026. Group C is 29 places where the documentation and the code disagree; the code wins. Group D is behaviour that is documented, or deliberate, but surprises people.

The reproductions for A1, A2, B1, B2, B3 and D1 were re-run for this post with git version 2.55.0, and each printed what the register says measured here. The others come from the dossier's lab runs and the verification passes behind it.

Upstream keeps moving, and a few changes since the tag touch rows below. On master: USE_NSEC became the runtime setting core.useNanosec (3a21fe8cf9, D24), reftable's reflog timezones were fixed (e14e2b6cf2), and init.defaultRefFormat was renamed init.defaultRefStorageFormat (53d995c53f). Only on seen, core.indexLockTimeout (fd1a1fc743) would let the index lock wait (D19). None is in a release yet.

Read by subsystem, the register follows the collection's thesis. Git is an append-only store of objects surrounded by a few small mutable files, and each file is either a pointer or a cache with its own consistency story. Objects need no lock, and no finding touches how an object is named or stored. Mutable files publish by rename, and two of the fixed bugs sit at that edge: reflog expiry, which decides what a pointer's history protects, and the shallow-clone section order on the wire. The rest cluster around derived data: the index as a cache (B1, B2, C2), the commit-graph and its filters (A3, B5, C10, C11, D2, D11), packs and their indexes (C3 to C7) reconstruction.

That is where git's surprises live: where one consistency story meets another. A cache whose freshness test is a timestamp. A ref backend atomic per ref, not per transaction. A deletion that relies on a two-week clock and on writers touching mtimes. Publishing that is atomic but, by default, not durable. Merging and upkeep add no new kind of state. They add objects, rebuild what can be rebuilt, and wait for the clock before throwing anything away.
