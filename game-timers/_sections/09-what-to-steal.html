{{S}}What the rest of us should steal

The engineering half of this note transplants almost without modification, and most of it costs nothing to adopt. Four things are worth taking, and one is worth taking carefully.

Lazy accrual is the one most teams are missing

Look for any scheduled job whose output is a pure function of elapsed time and delete it. Trial countdowns, credit top-ups, quota resets, subscription entitlement, aging counters, anything that "fills up". Store the last update and the rate; compute the value on read. Rate limiters already work this way — a token bucket is exactly min(cap, tokens + rate × Δt) — which is a good sign the pattern holds up in infrastructure, and a strange one that it so rarely escapes that corner of the stack.

The audit case, which is where I actually use this

The replay structure in §5 is the one worth internalising if you work on agents. A battle is auditable because it is a snapshot plus a command list plus a deterministic engine: three kilobytes that can be re-executed to check a claim. A recording of the same battle is fifteen thousand times larger and proves nothing, because you cannot re-run it.

Agent sessions have the same shape and are usually stored the wrong way round — a long transcript, which is a recording, rather than an environment snapshot plus the commands that were issued against it. I made this argument at more length in The State Is Enough: the transcript is an observation, the environment is the state, and evidence has to be captured from the state. The games got there first, for the entirely mercenary reason that video is expensive and determinism is free.

And the product transplant, with care

Appointments are legitimate when the thing genuinely finishes and the user asked for it. A long build completing, a large import finishing, a scheduled report becoming ready — these are real events, and telling someone about them respects their attention rather than competing for it. The engineering test from §8 transfers directly and is easy to apply in a code review: is there a finish_at that corresponds to something actually finishing? If the notification exists because engagement was down, there is no finish_at — there is only a calendar entry with your product's name on it, and the user will eventually work that out.
