01An image is a tree of hashes

A container is an ordinary Linux process, and Docker is five programs that agree on names made of sha256 hashes. This part is about those names. An image is a tree of JSON documents and tarballs. Every node is named by the sha256 of its exact bytes, so a name you trust fixes everything below it. The registry is trusted at one point only: the response header that turns a tag into a digest. Everything after that is checked on arrival.

The unit is the descriptor: a mediaType, a digest and a size, with optional urls, annotations and data (image-spec/descriptor.md:27-60) from the code. A digest is <alg>:<encoded> over the exact bytes; for sha256 that is 64 lowercase hex characters. The spec asks a consumer to check size before hashing, which bounds the read. Three document types use descriptors. An index points at one manifest per platform. A manifest points at one config and an ordered list of layers, base first. The config is the runtime defaults plus the list of uncompressed layer hashes. Its sha256 is the OCI ImageID (image-spec/config.md:85-89). Both index and manifest carry schemaVersion: 2, which the spec says exists only for Docker compatibility and will never change. Each index entry carries a platform. containerd's matcher normalises the arm64 variant v8 to the empty string, so linux/arm64 and linux/arm64/v8 select the same entry (moby/vendor/github.com/containerd/platforms/database.go:87-94) from the code.

alpine:latest, fetched on 23 October 2026

Fetched anonymously from Docker Hub at 14:38 UTC, the tag resolves to an OCI index of 9,218 bytes. Its sha256 equals the docker-content-digest header the registry sent measured here: 

content-type: application/vnd.oci.image.index.v1+json
content-length: 9218
docker-content-digest: sha256:be2656061b536c1883c4034790e21d0a09c5aaaf51968b89368a3c0371ea2c9a

$ sha256sum index.json
be2656061b536c1883c4034790e21d0a09c5aaaf51968b89368a3c0371ea2c9a  index.json

The index holds 16 descriptors: eight platforms (amd64, arm/v6, arm/v7, arm64/v8, 386, ppc64le, riscv64, s390x), each followed by a second manifest whose platform is unknown/unknown. Half the entries are not runnable images. They are BuildKit attestations: an SPDX SBOM and SLSA provenance, stored as two uncompressed application/vnd.in-toto+json "layers" of 79,673 and 5,639 bytes. Seven attestation manifests are 838 bytes; the arm/v6 one is 566. The amd64 path is short. Its manifest c26612752c78… is 1,022 bytes and names a 611-byte config b92841763c5c… and one gzip layer 7b229517ed22… of 3,853,109 bytes measured here. Figure 1 draws the tree.

The config is 611 bytes of BuildKit output. Its two history entries are the Dockerfile lines with # buildkit appended, and the second is marked empty_layer, so history has two entries and diff_ids one measured here: 

"created_by":"ADD alpine-minirootfs-3.24.3-x86_64.tar.gz / # buildkit"
"created_by":"CMD [\"/bin/sh\"]","comment":"buildkit.dockerfile.v0","empty_layer":true
"rootfs":{"type":"layers","diff_ids":["sha256:75c137aedfb2760f88629236cb7b797630aed0c3d91d626d1d1bb694878fc2ba"]}

The attestations point at their image through the annotation vnd.docker.reference.digest, not through subject. Hub does implement the OCI referrers endpoint. Asked for the amd64 digest, it returns 200 with an empty index measured here. A tool that finds SBOMs only through referrers finds none (register D29). That is the legacy layout: since v0.32, BuildKit's image exporter also writes each attestation manifest as an OCI artifact with subject by default, so images built that way can be found through referrers on registries that index it (exporter/containerimage/writer.go:613-678) from the code. Older tags show the format before BuildKit: alpine:3.10 and 3.15 are still served as Docker manifest lists, and their configs carry the Docker-only keys container, container_config and docker_version. The two families map one to one: the manifest list is the index, and the Docker gzip layer type is "interchangeable and fully compatible" with OCI's (image-spec/media-types.md:41-64). Part 3 shows where BuildKit writes the attestations.

02Digest, DiffID, ChainID

"The same layer" has three hashes, and they answer three different questions. The digest in the manifest is the sha256 of the bytes as stored and shipped, which are usually gzip. The DiffID in the config is the sha256 of the uncompressed tar (image-spec/config.md:26-31). The ChainID names a stack of layers applied in order (config.md:42-53) from the code. The first is for transport, the second pins content, the third names a filesystem state.

Each exists because one consumer needs it. A registry and a downloader verify a blob by its digest without decompressing anything. A runtime verifies what it extracted by the DiffID, whatever compression arrived. A snapshotter asks "do I already have exactly this filesystem?" by ChainID, without knowing which image or registry the layers came from reconstruction. Mixing them up is the usual source of "why are these two digests different?"

One tar, many digests

The alpine layer checks out at both ends. The 3,853,109 bytes served by the CDN hash to the manifest's 7b229517…. Inflated, they are an 8,709,632-byte tar that hashes to the config's 75c137ae… measured here. Recompressing that tar breaks the first hash and keeps the second: 

# same tar, different compressors -> different digest, same diffID
75c137aedfb2760f88629236cb7b797630aed0c3d91d626d1d1bb694878fc2ba  diffID (uncompressed tar)
7b229517ed222597277036d94892173207d01a731ab3a88eeb1de2e963a2c788  registry blob (gzip as published)
112b2e6f53918c25745148597450376649b5b7f41a2e0fe78d1e3ab13b2422fd  gzip -9 -n recompress
11bb4b9d8a07090f1d678ade19e579845d0ffe39eec23557d3f79f69081b19fb  gzip -1 -n recompress

So two registries, or two builders, can hold the same image content under different manifest digests. The gzip header shows what the builder did to stay reproducible. Hub's alpine layer starts 1f 8b 08 00 00 00 00 00 00 ff: deflate, no flags, MTIME zero, OS 0xff (unknown). The distroless layers also zero MTIME but write OS 0x03 (Unix) measured here. A zero timestamp is what lets the same input give the same bytes.

Inside the gzip is a POSIX ustar archive: ustar\0 and version 00 at offset 257 of the first header. It has 515 entries, of which 335 are symlinks, 96 directories and 84 regular files, with no hardlinks and no PAX headers. Nearly every applet is a symlink to /bin/busybox (804,616 bytes). Every entry is owned 0/0 except etc/shadow, which is 0/42 measured here.

The padding is part of the name

A tar ends with two 512-byte zero blocks, and writers pad further to a record size. The alpine tar ends with 1,192 zero bytes after its last non-zero byte, and all of them are inside the 8,709,632 hashed bytes measured here. An extractor that stops reading at the end-of-archive marker hashes fewer bytes and computes the wrong DiffID. containerd's applier drains the stream after the tar reader stops, in containerd/core/diff/apply/apply.go:134-137 from the code: 

	// Read any trailing data
	if _, err := io.Copy(io.Discard, rc); err != nil {
		return emptyDesc, err
	}

The same fact makes DiffIDs fragile across tools. Python's tarfile pads to a 10,240-byte record (20 × 512), so the five-entry layer of the hand-built image in §03 is 10,240 bytes of tar measured here. Another writer would pad differently and produce another DiffID for the same files. The spec asks for reproducible packing and suggests tar-split to keep the original headers (image-spec/config.md:29), and moby's legacy store does exactly that (§07).

ChainID is one line of string concatenation

ChainID(L0) is DiffID(L0). Each later ChainID is the sha256 of the previous ChainID, one ASCII space, and the next DiffID, with the sha256: prefixes included in the hashed string. The reference implementation is image-spec/identity/chainid.go:56-67 from the code: 

func ChainIDs(dgsts []digest.Digest) []digest.Digest {
	if len(dgsts) < 2 {
		return dgsts
	}

	parent := digest.FromBytes([]byte(dgsts[0] + " " + dgsts[1]))
	next := dgsts[1:]
	next[0] = parent
	ChainIDs(next)

	return dgsts
}

Because each rung hashes the one below, a ChainID names an ordered application. Layer C on top of A and B has a different ChainID from C alone, although both end in the same changeset (config.md:65-83). Alpine has one layer, so its ChainID equals its DiffID. The gcr.io/distroless/static-debian12 amd64 image has twelve. Recomputed by hand, every layer digest and DiffID matched its manifest and config, and the ladder ends at sha256:5e555e7975e2…80db measured here. Figure 2 draws both halves.

distroless shows two more things a consumer must tolerate. Bazel writes every timestamp at the epoch, and the layers mix path styles: some entries are ./etc/passwd, others etc/nsswitch.conf. Appliers clean names before use; containerd calls filepath.Clean(hdr.Name) (containerd/pkg/archive/tar.go:248-249) from the code. The smallest layer is 67 gzip bytes. It inflates to 1,536 bytes: one header for . and the two end blocks. It is a real layer whose only content is the root directory's metadata measured here. The ChainID's job comes in §06: it is the name under which an unpacked filesystem is stored and shared.

03Layers are tar changesets

A layer is a tar of changes against the layers below it. Additions and modifications look the same: the file is simply in the tar. Duplicate paths are forbidden (image-spec/layer.md:22-34). When an entry lands on an existing path, two directories merge their attributes; in every other case the old path is unlinked and recreated, so a file can replace a directory (layer.md:235-242) from the code. Removals need a marker, because a tar cannot hold an absence.

The marker is a whiteout: an empty regular file named .wh.<name>. It hides only lower layers, so a whiteout and a same-named file in the same layer do not cancel, and no image may contain a real file whose name starts with .wh. (layer.md:245-252). An opaque marker, .wh..wh..opq, hides every lower child of its directory. It takes effect before any sibling entry in the same layer, wherever it sits in the stream (layer.md:336) from the code.

A hand-built image with both kinds

To see real bytes I built a two-layer OCI image with Python's tarfile, gzip and hashlib alone: oci-layout, index.json and four blobs under blobs/sha256/. The second layer deletes etc/motd and replaces the contents of app/ measured here:

What the kernel sees instead

The kernel's overlayfs has its own whiteout forms: a character device with device number 0/0 (or a zero-size file with trusted.overlay.whiteout), and an opaque directory carrying trusted.overlay.opaque=y (kernel Documentation/filesystems/overlayfs.rst:147-156). containerd translates while it untars. containerd/pkg/archive/tar_opts_linux.go:29-52 from the code: 

	// if a directory is marked as opaque, we need to translate that to overlay
	if base == whiteoutOpaqueDir {
		// don't write the file itself
		return false, unix.Setxattr(dir, "trusted.overlay.opaque", []byte{'y'}, 0)
	}

	// if a file was deleted and we are using overlay, we need to create a character device
	if strings.HasPrefix(base, whiteoutPrefix) {
		originalBase := base[len(whiteoutPrefix):]
		originalPath := filepath.Join(dir, originalBase)

		if err := unix.Mknod(originalPath, unix.S_IFCHR, 0); err != nil {
			return false, err
		}
		// don't write the file itself
		return false, os.Chown(originalPath, hdr.Uid, hdr.Gid)
	}

The marker files are never written. Figure 3 shows the same deletion three ways. The conversion step is read from the code; I could not mount overlayfs on this box.

Producers disagree on the details

The spec says producers SHOULD emit explicit whiteouts rather than opaque markers (layer.md:315). Overlay-native differs still emit .wh..wh..opq whenever they find trusted.overlay.opaque=y in an upperdir: moby's go-archive (archive_linux.go:69-93) and continuity (fs/diff_linux.go:60-75). An applier that handles only .wh.<name> leaks lower files (register D27). The header bytes differ too. moby turns a 0/0 device back into a whiteout with mode 0o600 (go-archive/archive_linux.go:54-63), while containerd's differ writes mode 0 and epoch-zero times "since containerd v2.0" (containerd/pkg/archive/tar.go:557-580). The same deletion yields different tar bytes, so different DiffIDs (D28) from the code.

Overlay's semantics leak into containers. Copy-up copies the whole file on the first write-access open, even if nothing is written (overlayfs.rst:265-288). Renaming a lower directory fails with EXDEV unless redirect_dir is on; this host's module has it off, and metacopy too measured here. In a user namespace moby's converter switches to user.overlay.* xattrs, while containerd skips its fast path and mounts and deletes instead (D32).

04Pulling alpine, request by request

A pull is a short conversation over HTTPS. The client pings the registry, gets a token from a different host, asks once which digest the tag means, and from then on asks for content only by digest. The trace below is curl on 23 October 2026, anonymous, from this box to Docker Hub, issuing the same requests containerd's resolver issues measured here. It is not dockerd's own traffic: dockerd could not run here, so its request shapes are read from the code.

docker.io is not a host that serves the API. containerd hard-codes the mapping to registry-1.docker.io (containerd/core/remotes/docker/resolver.go:141-146) from the code. The first request, GET /v2/, gets a 401 whose challenge names where to go next: 

< HTTP/2 401
< www-authenticate: Bearer realm="https://auth.docker.io/token",service="registry.docker.io"
--timing-- dns=0.008915 connect=0.038051 tls=0.074767 ttfb=0.105519 total=0.105744 code=401
{"errors":[{"code":"UNAUTHORIZED","message":"authentication required","detail":null}]}

The challenge has no scope, because nothing has been asked for yet; distribution's challenge builder only appends one when the access set is non-empty (distribution/registry/auth/token/accesscontroller.go:125-146). The client then asks auth.docker.io for scope=repository:library/alpine:pull. Hub returns a 2,698-character RS256 JWT with an x5c certificate chain, aud registry.docker.io, an empty sub and a 300-second life, with nbf back-dated 300 seconds. It sends the same value under both token and access_token, the compatibility mode the token spec allows measured here. The token endpoint sits behind Cloudflare with its own limit (x-ratelimit-limit: 3000, 3000;w=60).

The one trusted header

With the token, the client sends HEAD /v2/library/alpine/manifests/latest. The answer is a content type, a length of 9,218 and a docker-content-digest, with an etag equal to the quoted digest. That is all a resolver needs. containerd takes the header as the image's identity and only GETs and hashes the manifest itself when the header or the length is missing. containerd/core/remotes/docker/resolver.go:391-405 says so in a comment from the code: 

// trusted registry was contacted, in this case use
// the digest header (or content from GET)
if dgst == "" {
	// this is the only point at which we trust the registry. we use the
	// content headers to assemble a descriptor for the name. when this becomes
	// more robust, we mostly get this information from a secure trust store.
	dgstHeader := digest.Digest(resp.Header.Get("Docker-Content-Digest"))

	if dgstHeader != "" && size != -1 {
		if err := dgstHeader.Validate(); err != nil {
			return "", ocispec.Descriptor{}, fmt.Errorf("%q in header not a valid digest: %w", dgstHeader, err)
		}
		dgst = dgstHeader
	}
}

Everything after this point is checked. Integrity is enforced at the content store rather than in HTTP: content.Copy commits with the expected digest and the local writer fails on a mismatch (containerd/plugins/content/local/writer.go:134-136). A registry that lies in the HEAD can name the wrong image, but cannot serve bytes that disagree with the name it gave reconstruction. Resolution also caps manifests at MaxManifestSize, defined as 4 * 1048 * 1048: 4,393,216 bytes, a harmless typo for 1024 (register D42).

The resolver's Accept lists Docker schema2 manifest, Docker manifest list, OCI manifest, OCI index and */*, in that order (resolver.go:171-178). Hub ignores it for this tag: seven different Accept values, including none at all, all got the same OCI index with the same digest measured here. §08 shows a registry that does not.

By digest, then to the CDN

The client fetches the index and the amd64 manifest by digest, then the blobs. A blob GET on Hub is a 307 with an empty body. The Location is on production.cloudfront.docker.com, and its path is distribution's blob layout under a /registry-v2 root, signed with CloudFront parameters: 

location: https://production.cloudfront.docker.com/registry-v2/docker/registry/v2/blobs/sha256/7b/
          7b229517ed222597277036d94892173207d01a731ab3a88eeb1de2e963a2c788/data?<signed-query-redacted>

The CDN answered from S3 (server: AmazonS3, x-cache: Hit from cloudfront), with age: 141278 on the layer: cached for about 39 hours. A Range: bytes=0-15 request through the same redirect got a 206 with content-range: bytes 0-15/3853109 and the gzip magic 1f 8b 08 measured here. curl sent no Authorization on the CDN hop because it drops credentials on cross-host redirects. containerd sends none either: it follows up to 10 redirects and re-runs its authorizer on each, and the authorizer is keyed by host (resolver.go:703-712, authorizer.go:121-125) from the code. Figure 4 lays out the whole exchange.

Added up, the eight requests before the range probe take about 1.18 seconds; the 3.85 MB layer body itself arrived in the 74 ms between its first byte and its last. For a small image a pull is bound by round trips, not bandwidth reconstruction. How the client handles failures matters on that path. In containerd every request goes through doWithRetries with maxAttempts = 5 total. A 401 feeds the authorizer; 408 and 429 retry at once, with no backoff and no reading of Retry-After (resolver.go:772, :884-885). Only transport errors sleep, a fixed 50 ms (:816-844) from the code. Against a registry that is rate-limiting, each retried GET may count (register D43).

The rate limit's window

Hub's manifest responses carry both x-ratelimit-* and IETF-draft ratelimit-* headers. Docker's documentation says anonymous users get 100 pulls per 6 hours and shows w=21600; the JWT says pull_limit_interval: 21600; the live header says w=3600, re-probed at 15:20:40 UTC with the same result. Which is authoritative is unresolved (D45). The docs also say HEAD does not count and GET does. On ratelimitpreview/test, two HEADs left remaining at 92, one GET dropped it to 91, and a HEAD after it stayed at 91 measured here. The egress IP is shared, so others may have pulled too.

Other registries differ in small ways measured here. ghcr.io issues an opaque 56-character token instead of a JWT, 404s the referrers endpoint, and redirects blobs to Azure Blob SAS URLs. public.ecr.aws uses realm https://public.ecr.aws/token/, and the slash-less URL 301s. mcr.microsoft.com answers GET /v2/ with 200 and needs no token at all.

05Credentials, and dockerd as the client

Credentials live with the CLI, not the daemon. The docker CLI looks them up, encodes them into one request header, and hands them to dockerd for that request only. dockerd then speaks HTTP to the registry itself. containerd's daemon never sees the registry; it stores what dockerd fetched.

Where the CLI looks

For each registry the CLI picks a store: a per-registry credHelpers[host] entry, else the global credsStore, else the plaintext file store in config.json. If DOCKER_AUTH_CONFIG is set, an in-memory store built from it is layered on top, with the chosen store as fallback. cli/cli/config/configfile/file.go:395-402 from the code: 

func getConfiguredCredentialStore(c *ConfigFile, registryHostname string) string {
	if c.CredentialHelpers != nil && registryHostname != "" {
		if helper, exists := c.CredentialHelpers[registryHostname]; exists {
			return helper
		}
	}
	return c.CredentialsStore
}

Docker Hub's key is still the historical https://index.docker.io/v1/; every other registry is keyed by its bare hostname (file.go:27-49). A helper is an external program named docker-credential-<suffix>. It gets the action (get, store, erase, list) as argv[1] and the payload on stdin. get reads a server URL and prints {ServerURL,Username,Secret}; "not found" is the exact text credentials not found in native keychain with a non-zero exit. OAuth identity tokens are stored under the fake username <token> (native_store.go:11). Without a helper, the file store writes auth: base64(user:password) into config.json and warns once.

To watch the protocol I put a fake docker-credential-xolab on PATH that logs its argv and stdin, and drove it with the machine's docker CLI, version 29.8.2 rather than the 29.9.2 pin measured here: 

$ docker manifest inspect alpine:latest   (rc=0)
    argv=[get] stdin=[https://index.docker.io/v1/]
    argv=[get] stdin=[https://index.docker.io/v1/]
$ docker pull alpine:latest   (rc=1)
    argv=[get] stdin=[https://index.docker.io/v1/]
    stderr: failed to connect to the docker API at unix:///var/run/docker.sock; …
$ docker logout ghcr.io   (rc=0)
    argv=[erase] stdin=[ghcr.io]
    argv=[erase] stdin=[ghcr.io]
    argv=[erase] stdin=[http://ghcr.io]
    argv=[erase] stdin=[https://ghcr.io]

Three things show. docker pull asked the helper before it tried the daemon socket, so the lookup is client-side. manifest inspect asks twice per image and logout erases four spellings of one host (register D48); buildx imagetools inspect asked once. And manifest inspect succeeded with no daemon at all: it talks to the registry from the CLI process.

One header to the daemon

docker pull reaches the daemon as POST /images/create?fromImage=…&tag=…, with a digest reference carried in the tag parameter. The credentials ride in X-Registry-Auth: base64url of the JSON AuthConfig, with fields username, password, auth, serveraddress, identitytoken and registrytoken (cli/vendor/github.com/moby/moby/api/pkg/authconfig/authconfig.go:18-29). It is encoded, not encrypted. Part 1 shows the socket it travels on. On a pull, the daemon ignores a header it cannot decode, in moby/daemon/server/router/image/image_routes.go:102-106 from the code: 

		// For a pull it is not an error if no auth was given. Ignore invalid
		// AuthConfig to increase compatibility with the existing API.
		//
		// TODO(thaJeztah): accept empty values but return an error when failing to decode.
		authConfig, _ := authconfig.Decode(r.Header.Get(registry.AuthHeader))

A broken helper therefore produces an anonymous, rate-limited pull rather than an error (D47).

With the containerd store, pullTag builds a containerd resolver from that AuthConfig and calls containerd.Client.Pull inside dockerd (moby/daemon/containerd/image_pull.go:99-257). A registrytoken becomes a static Bearer; an identitytoken becomes a refresh-token grant; Hub's index.docker.io key maps to registry-1.docker.io. The static Bearer never retries on 401, because its AddResponses returns ErrNotImplemented, so an expired token fails the pull outright (moby/daemon/containerd/resolver.go:125-128) from the code.

Concurrency is capped per daemon. The defaults are 3 concurrent downloads and 5 uploads, and the download limiter is a single semaphore.Weighted on the ImageService (moby/daemon/containerd/service.go:127-131, daemon/config/config.go:28-40). Each open blob stream holds one unit until its body closes. Two parallel docker pulls share three slots (D44). containerd can also split one blob into parallel Range requests, but dockerd never sets ConcurrentLayerFetchBuffer, so that path stays off from the code.

06Content store, snapshots and unpack

On a Docker 29 host using the containerd image store, a pulled image lives in three places. Blobs sit in containerd's content store, named by digest. Unpacked layers sit in the overlayfs snapshotter, named by ChainID. A bbolt database ties them together with labels that the garbage collector follows. dockerd keeps all of its objects in the containerd namespace moby (moby/daemon/config/config.go:58) from the code.

Blobs land by rename

A committed blob lives at <root>/blobs/<alg>/<encoded>, which is exactly the OCI image-layout rule: the content store is an image layout without an index.json. A write in progress lives under ingest/, in a directory named by a hash of the ref string, not of the content. containerd/plugins/content/local/store.go:646-658 from the code: 

func (s *store) blobPath(dgst digest.Digest) (string, error) {
	if err := dgst.Validate(); err != nil {
		return "", fmt.Errorf("cannot calculate blob path from invalid digest: %v: %w", err, errdefs.ErrInvalidArgument)
	}

	return filepath.Join(s.root, "blobs", dgst.Algorithm().String(), dgst.Encoded()), nil
}

func (s *store) ingestRoot(ref string) string {
	// we take a digest of the ref to keep the ingest paths constant length.
	// Note that this is not the current or potential digest of incoming content.
	dgst := digest.FromString(ref)
	return filepath.Join(s.root, "ingest", dgst.Encoded())

The ingest directory holds data, ref, startedat, updatedat and optionally total. Opening a writer for a digest that already exists fails fast with ErrAlreadyExists; that is how a pull skips blobs it has. An interrupted ingest resumes by re-reading data to rebuild the digester. Commit is fsync, stat, size check, digest check, os.Rename into blobs/, fsync of the directory, optional fs-verity, and a chmod that strips write bits (writer.go:79-200). A blob is never visible half-written from the code.

Labels are the reference graph

All metadata lives in one bbolt file, bucketed under v1/<namespace>/ into labels, images, containers, snapshots, content, sandboxes and leases. The schema comment calls the bucket image; the code says images (core/metadata/buckets.go:65 vs :150, D33). Blob files are shared across namespaces; only the metadata is namespaced. GC is a tri-colour mark from roots over an explicit graph, then one sweep in a single write transaction. The edges are labels. During a pull each parent blob is labelled with its children by role: containerd.io/gc.ref.content.m.<i> for manifests, .config, .l.<i> for layers. After unpack, the config blob gets containerd.io/gc.ref.snapshot.overlayfs=<top ChainID> (core/unpack/unpacker.go:751-765), so the unpacked filesystem lives as long as the image record does from the code.

Two leases cover the gaps. dockerd wraps every pull in a random-ID lease with an expiry, so half-downloaded blobs survive a GC during the pull and become collectible if it is abandoned. Each container's read-write snapshot is held by a lease whose ID is the container ID, because a container can be removed and recreated with nothing else holding the snapshot in between (moby/daemon/containerd/image_snapshot.go:59-68). Figure 5 puts the three directories and the edges together.

Unpack: ChainIDs name the snapshots

The unpacker computes every ChainID up front from rootfs.diff_ids and refuses an image whose layer count differs from its DiffID count. Each layer is extracted into an Active snapshot keyed extract-<nanos>-<rand> <chainID>. If Prepare reports that the ChainID already exists, extraction is skipped. That is deduplication across images: two images on the same base share the base's snapshots (unpacker.go:503-528). Decompression is a chain of stream processors chosen by media type, running until it reaches a plain tar. For gzip containerd shells out to igzip or unpigz if either is on PATH. The plain tar is teed into a sha256 digester and checked against the config as it lands. core/unpack/unpacker.go:653-658 from the code: 

			if diff.Digest != diffIDs[i] {
				cleanup.Do(ctx, abort)
				status.err = fmt.Errorf("wrong diff id %q calculated on extraction %q, desc %q", diff.Digest, diffIDs[i], desc.Digest)
				resCh <- status
				return
			}

On Linux, when the target is one overlay mount and not in a user namespace, the applier does not mount at all. It untars straight into the snapshot's upperdir with OverlayConvertWhiteout (core/diff/apply/apply_linux.go:34-73). Commit then only records disk usage and flips metadata; no data is copied, so the committed layer is the directory the extraction wrote into. The overlay mount is built as in §03: parents' fs dirs joined by :, immediate parent first, which matches the kernel's leftmost-is-top order. The snapshotter appends index=off when the kernel has that parameter from the code.

Two costs follow. dockerd pulls with WithUnpackFetchAllContent, so every layer blob is fetched and kept even when its snapshot exists, "so the pulled image can also be saved or pushed"; disk use is compressed plus uncompressed (image_pull.go:228-237, D25). And it never sets an unpack limiter, so layers unpack one at a time, each Prepared on its parent's ChainID from the code.

The box this was written on shows the result from inside. Files on its overlay root report the overlay's device, 133, while the bind-mounted /etc/hostname reports 2049: a different filesystem laid over the rootfs one file at a time, the per-file bind mount that Docker and Kubernetes place over a container's root measured here.

07Two image stores, two meanings of "image ID"

Docker 29 ships two image stores and picks one at daemon start. On Linux the default is containerd's store, the one §06 described (moby/daemon/image_store_choice.go:105-108). But if the data root already holds a non-empty prior graphdriver directory other than vfs, the choice flips to graphdriver-prior, and the host stays on overlay2 (:130-134, register D24). Setting storage-driver or $DOCKER_DRIVER also selects the graphdriver from the code. Engine 29.0.0 (10 November 2025) made the containerd store the default for fresh installs; it had been experimental since 24.0.0. So an upgraded host and a fresh one, running the same binary, store images differently.

The feature flag has a quiet asymmetry. Docker's storage docs show only "containerd-snapshotter": true, which the code now answers with a warning that it is the default. false is the explicit opt-out, imageStoreChoiceGraphdriverExplicit (image_store_choice.go:115-123, D35). userns-remap disables the containerd store, and fails startup if it was explicitly enabled, because BuildKit breaks with that combination (moby/daemon/command/daemon_linux.go:28-40, moby#47377, D26).

Same pull, two IDs

In the containerd store, the "ID" that docker images and inspect show is the digest of the target descriptor, the index or manifest the tag points at (moby/daemon/containerd/image_list.go:439: ID: target.Digest.String()). In the legacy store it is digest.FromBytes(config), written to image/<driver>/imagedb/content/sha256/<id> (moby/daemon/internal/image/fs.go:112-126), which is the OCI ImageID from the code. Applied to the measured digests, the same docker pull alpine shows be2656061b53 on a fresh 29.x host and b92841763c5c on an upgraded one (D23) reconstruction. Scripts that compare image IDs across hosts compare different things.

Twenty-six characters and a page

The legacy driver keeps each layer under overlay2/<cacheID>/ with diff/, work/, merged/, a lower file listing the chain, and a link file holding a short name. The short names exist for the mount syscall, whose options must fit in one page. moby/daemon/graphdriver/overlay2/overlay.go:76-85 from the code: 

	maxDepth      = 128

	// idLength represents the number of random characters
	// which can be used to create the unique link identifier
	// for every layer. If this value is too long then the
	// page size limit for the mount command may be exceeded.
	// The idLength should be selected such that following equation
	// is true (512 is a buffer for label metadata).
	// ((idLength + len(linkDir) + 1) * maxDepth) <= (pageSize - 512)
	idLength = 26

The equation is tight: (26 + 1 + 1) × 128 = 3,584 = 4,096 − 512 exactly, and this host's getconf PAGESIZE is 4,096 measured here. The links are used only on a fallback. When the absolute-path options exceed pageSize-1, which happens far below 128 layers, overlay2 rewrites them relative to its home and mounts through mountFrom, a re-exec that chroots first. The 512-byte reserve must then also hold index=off,, userxattr,, the relative upper and work paths and any SELinux label. Past that, Get fails with "cannot mount layer, mount label too large"; there is no further fallback (overlay.go:580-602, D31) from the code.

08Push, and inside a registry

Push runs the pull backwards: blobs first, manifest last. containerd's pusher HEADs each blob and treats a 200 as ErrAlreadyExists, which is client-side layer deduplication. It then tries a cross-repo mount from a repository named in the blob's containerd.io/distribution.source.<host> label, written at pull time, and falls back to a normal upload if the mount gets a 401. The upload is one POST for a session and one streamed PUT <location>?digest=, with the comment // TODO: Support chunked upload at containerd/core/remotes/docker/pusher.go:316. If the Location moves to another host, the pusher drops the authorizer for that hop from the code.

The reference server, measured

I ran distribution v3.1.2's release binary on 127.0.0.1:5055 and pushed alpine's amd64 image by hand, including the chunked path containerd never uses measured here: 

HEAD  /v2/lab/alpine/blobs/sha256:7b2295…        404   not there yet
POST  /v2/lab/alpine/blobs/uploads/               202   Range: 0-0   Docker-Upload-Uuid: 01a1693a-8dbb-…
PATCH <location>  bytes 0-1926553                 202   Range: 0-1926553
PATCH <location>  Content-Range: 10-20            416   {"code":"RANGE_INVALID","message":"invalid content range"}
GET   <location>                                  204   Range: 0-1926553
PUT   <location>&digest=sha256:7b2295…  (rest)   201   Docker-Content-Digest: sha256:7b2295…

An empty session answers Range: 0-0, which under the spec's inclusive ranges claims byte 0 arrived (D40). The 416 carries RANGE_INVALID, a code absent from the spec's table (D41). The single-POST upload is ignored, which the spec permits (D39). And the manifest PUT returned Hub's digest: stored byte-exact, the same bytes have the same name on any registry.

The server keeps no session table. The Location carries _state, signed in distribution/registry/handlers/hmac.go:64-73 from the code: 

func (secret hmacKey) packUploadState(lus blobUploadState) (string, error) {
	mac := hmac.New(sha256.New, []byte(secret))
	p, err := json.Marshal(lus)
	if err != nil {
		return "", err
	}

	mac.Write(p)

	return base64.URLEncoding.EncodeToString(append(mac.Sum(nil), p...)), nil

Decoded, the first _state is 155 bytes: a 32-byte HMAC, then the JSON measured here: 

{"Name":"lab/alpine","UUID":"01a1693a-8dbb-7340-9a86-b8806bf53f4d","Offset":0,
 "StartedAt":"2026-10-23T14:46:47.483213373Z"}

Without http.secret each process invents its own key, so behind a load balancer the next PATCH fails on another replica (D49). On disk, the bytes accumulate in _uploads/<uuid>/data beside 108-byte resumable-hash snapshots. Committed, the registry is one global blobs/sha256/<2 hex>/<hex>/data store plus per-repository trees of link files. Every link is 71 bytes: sha256: and 64 hex characters.

Accept is enforced here

distribution parses Accept into four booleans, ignoring q-values, and refuses OCI content the client did not name. distribution/registry/handlers/manifests.go:171-178 from the code: 

if manifestType == ociSchema && !supports[ociSchema] {
	imh.Errors = append(imh.Errors, errcode.ErrorCodeManifestUnknown.WithMessage("OCI manifest found, but accept header does not support OCI manifests"))
	return
}

So */*, or no Accept, gets a 404 for an OCI manifest. Hub and ghcr ignore Accept entirely. The spec's own content-negotiation.md is still a schema1-era TODO (D46). Figure 7 sets them side by side, including one path the guard misses.

v3.1.2 registers seven routes and none is referrers; upstream main still has seven, with referrers in open PR #4828 (D38). Tag listing sends a Link whenever a page is full, including the last page, which costs a client one empty round trip (D50) measured here.

Garbage collection can delete a mounted blob

Deletion is two steps. DELETE /manifests/<digest> removes the revision link and untags every tag pointing at it, without checking whether a list in the same repository still references it. The blob data stays until an offline registry garbage-collect. That marks each manifest in each repository's _manifests/revisions and recurses into a child only if the child still exists as a revision. distribution/registry/storage/garbagecollect.go:228-234 from the code: 

		if ingester(descriptor.Digest) {
			continue
		}

		if ok, _ := manifestService.Exists(ctx, descriptor.Digest); ok {
			err := markManifestReferences(descriptor.Digest, manifestService, ctx, ingester)

Then it deletes every unmarked blob and every unmarked _layers link. Figure 8 shows what that did in the lab.

Two holes result (D37). lab/other links to a blob that no longer exists: a repository whose only claim is a mount is invisible to the mark phase. And the still-tagged list points at a child that 404s measured here. Both follow from the mark rule above.
