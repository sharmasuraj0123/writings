{{S}}Layers are tar changesets

A layer is a tar of changes against the layers below it. Additions and modifications look the same: the file is simply in the tar. Duplicate paths are forbidden (image-spec/layer.md:22-34). When an entry lands on an existing path, two directories merge their attributes; in every other case the old path is unlinked and recreated, so a file can replace a directory (layer.md:235-242) from the code. Removals need a marker, because a tar cannot hold an absence.

The marker is a whiteout: an empty regular file named .wh.<name>. It hides only lower layers, so a whiteout and a same-named file in the same layer do not cancel, and no image may contain a real file whose name starts with .wh. (layer.md:245-252). An opaque marker, .wh..wh..opq, hides every lower child of its directory. It takes effect before any sibling entry in the same layer, wherever it sits in the stream (layer.md:336) from the code.

A hand-built image with both kinds

To see real bytes I built a two-layer OCI image with Python's tarfile, gzip and hashlib alone: oci-layout, index.json and four blobs under blobs/sha256/. The second layer deletes etc/motd and replaces the contents of app/ measured here:

What the kernel sees instead

The kernel's overlayfs has its own whiteout forms: a character device with device number 0/0 (or a zero-size file with trusted.overlay.whiteout), and an opaque directory carrying trusted.overlay.opaque=y (kernel Documentation/filesystems/overlayfs.rst:147-156). containerd translates while it untars. containerd/pkg/archive/tar_opts_linux.go:29-52 from the code: 

	// if a directory is marked as opaque, we need to translate that to overlay
	if base == whiteoutOpaqueDir {
		// don't write the file itself
		return false, unix.Setxattr(dir, "trusted.overlay.opaque", []byte{'y'}, 0)
	}

	// if a file was deleted and we are using overlay, we need to create a character device
	if strings.HasPrefix(base, whiteoutPrefix) {
		originalBase := base[len(whiteoutPrefix):]
		originalPath := filepath.Join(dir, originalBase)

		if err := unix.Mknod(originalPath, unix.S_IFCHR, 0); err != nil {
			return false, err
		}
		// don't write the file itself
		return false, os.Chown(originalPath, hdr.Uid, hdr.Gid)
	}

The marker files are never written. Figure {{fig-overlay-whiteouts}} shows the same deletion three ways. The conversion step is read from the code; I could not mount overlayfs on this box.

Producers disagree on the details

The spec says producers SHOULD emit explicit whiteouts rather than opaque markers (layer.md:315). Overlay-native differs still emit .wh..wh..opq whenever they find trusted.overlay.opaque=y in an upperdir: moby's go-archive (archive_linux.go:69-93) and continuity (fs/diff_linux.go:60-75). An applier that handles only .wh.<name> leaks lower files (register D27). The header bytes differ too. moby turns a 0/0 device back into a whiteout with mode 0o600 (go-archive/archive_linux.go:54-63), while containerd's differ writes mode 0 and epoch-zero times "since containerd v2.0" (containerd/pkg/archive/tar.go:557-580). The same deletion yields different tar bytes, so different DiffIDs (D28) from the code.

Overlay's semantics leak into containers. Copy-up copies the whole file on the first write-access open, even if nothing is written (overlayfs.rst:265-288). Renaming a lower directory fails with EXDEV unless redirect_dir is on; this host's module has it off, and metacopy too measured here. In a user namespace moby's converter switches to user.overlay.* xattrs, while containerd skips its fast path and mounts and deletes instead (D32).
