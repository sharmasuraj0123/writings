01After start: pipes and small state machines

A container is an ordinary Linux process, and Docker is a relay of five programs that mostly get out of its way. Mostly. After runc start the relay is gone, but dockerd keeps three jobs: it carries the container's bytes, it answers the container's questions, and it decides what happens when the process stops. This part claims that each of those jobs is either a byte pipeline or a small state machine, and that both lose or block data more often than users assume.

Part 1 ended with a process parked on a FIFO while dockerd wired its network (§06 there). This part starts at that wire. A bridge network is a Linux bridge, a veth pair and a set of netfilter rules. Publishing a port binds a real socket on the host, attaches a filter so it hears nothing, and lets the kernel's DNAT carry almost every packet. A user-space relay, docker-proxy, is left with three narrow cases: loopback, hairpin and IPv6 to an IPv4-only container. Name resolution is stranger. The DNS server at 127.0.0.11 is a goroutine inside dockerd, and NAT rules in the container's own namespace steer the queries to it. It forwards some of them from the host's namespace, past the firewall you may have written for the container from the code.

The bytes come next. Attach, exec and docker logs share one frame format: eight header bytes, then a payload. The reader on the client drops a frame cut short without saying so. Logging is synchronous and unbounded by default. A slow log driver can back-pressure the container's own write(2), and a json-file log with no max-size grows until the disk fills. The two buffers that do not block are the ones that drop data, and one of them is on by default from the code.

Then the long run. docker stop signals PID 1 only. The kernel's rule for a namespace's init process means a plain sh never sees that SIGTERM, so stop becomes a ten-second wait and a SIGKILL. The restart manager is a few booleans and a backoff timer, and one of those booleans is set by every docker kill -s. So sending SIGHUP to reload nginx can quietly switch off an unless-stopped policy. That is finding D77, the headline of the collection's register. It is still on moby's master, and a fix has been open since August 2026. Health checks, OOM flags, docker stats and docker events turn out to be thin readers over cgroup files and in-memory rings. Each one answers a slightly different question from the one its name suggests.

The last two content sections step back. §07 tells the history as thirteen years of moving work out of one binary: LXC, then libcontainer, runc and the OCI, containerd and its shim, the Moby split, and Kubernetes moving off dockerd. In 2026 the movement reversed for the first time, with containerd running inside dockerd when no system copy is installed. §08 is the register of all 100 findings from the four parts, grouped by class, each with its upstream status and a way to check it.

None of this ran live. No container could start on the research box, so the CLI traces here are the real docker CLI 29.8.2 against a mock daemon. The firewall rules are moby's own golden test files, and the stats arithmetic uses this sandbox's own cgroup files. Each figure says which of those it is reconstruction.

02A bridge, a veth and a published port

runc makes the network namespace; dockerd adopts it. For a bridge container the OCI spec carries a network namespace entry with an empty path, so runc creates a fresh one (moby/daemon/oci_linux.go:242-270). After the task is created, and before its process runs, initializeCreatedTask calls sb.SetKey("/proc/<pid>/ns/net") and then allocateNetwork (moby/daemon/start_linux.go:17-43). No OCI hook is involved for docker run any more. The old libnetwork-setkey prestart hook was removed in 26.0, restored in 26.1 and removed again in 28.0. It survives only for BuildKit's RUN steps on the default bridge from the code. SetKey pins the namespace with a bind mount, so it outlives any one process, in moby/daemon/libnetwork/osl/namespace_linux.go:152-158: 

func mountNetworkNamespace(basePath string, lnPath string) error {
	err := syscall.Mount(basePath, lnPath, "bind", syscall.MS_BIND, "")
	if err != nil {
		return fmt.Errorf("bind-mount %s -> %s: %w", basePath, lnPath, err)
	}
	return nil
}

The target is a file under /var/run/docker/netns/ named by a 12-character key. The bridge driver then creates a veth pair. The host end is veth plus seven random hex characters, enslaved to docker0 or br-<12 chars of network ID>. When the namespace path is already known, the peer is created directly inside it and renamed to the lowest free ethN. Since 28.0.0 the container's MAC is random and locally administered. Before that it was 02:42: plus the IPv4 address, and overlay endpoints still are (bridge_linux.go:1249-1299, netutils/utils.go:40-46) from the code. One detail of the setup steps is a doc drift. The driver sets the filter-FORWARD policy to DROP only when it flipped ip_forward from 0 to 1, while the docs state the DROP unconditionally (D64, setup_ip_forwarding.go:38-59).

What -p 8080:80 builds

Publishing starts by normalising the request. With no host IP and the default --ip=0.0.0.0, one -p becomes two bindings: one on 0.0.0.0 and one on [::]. If the container has no IPv6 address, the IPv6 binding targets its IPv4 address, which only a user-space relay can do (D67, port_mapping_linux.go:195-289). The nat portmapper then reserves the host port for real: dockerd calls socket, bind and, for TCP, listen on each host address. A listening socket could accept connections before any DNAT rule exists, so a one-instruction cBPF program is attached first. It returns 0, which tells the kernel to drop every packet, and TCP clients simply retransmit their SYN (portallocator/osallocator_linux.go:192-200, 300-305) from the code. Ephemeral ports for -p 80 or -P come from the kernel's ip_local_port_range, which on this sandbox reads 32768–60999 with no reserved ports measured here.

The order inside mapPorts is: bind the sockets, add the firewall rules, detach the filter, start docker-proxy with the bound socket as fd 4 and a status pipe as fd 3, and close dockerd's copy (port_mapping_linux.go:105-193). Each proxy is started from a goroutine locked to its OS thread, because Pdeathsig fires when the creating thread dies (go.dev/issue/27505). That is one dockerd thread per published binding, two per -p with IPv6 (D76) from the code. The installed docker-proxy -help lists exactly -container-ip, -container-port, -host-ip, -host-port, -proto, -use-listen-fd, -v and -version measured here. The DNAT rule itself is built in moby/daemon/libnetwork/drivers/bridge/internal/iptabler/port.go:94-114: 

hostIP := "0/0"
if !b.HostIP.IsUnspecified() {
	hostIP = b.HostIP.String()
}
args := []string{
	"-p", b.Proto.String(),
	"-d", hostIP,
	"--dport", strconv.Itoa(int(b.HostPort)),
	"-j", "DNAT",
	"--to-destination", net.JoinHostPort(b.IP.String(), strconv.Itoa(int(b.Port))),
}
if !n.ipt.config.Hairpin {
	args = append(args, "!", "-i", n.config.IfName)
}

Hairpin is true only when the userland proxy is off. With the default proxy on, the rule skips packets that arrive on the bridge, and the nat-OUTPUT jump skips 127.0.0.0/8. So the kernel DNATs every remote connection, and docker-proxy carries three cases: connections to a loopback host address, a container reaching a published port through a host address, and host IPv6 to a container's IPv4 (Figure 1). The proxy holds the port in every case, but carries almost none of the traffic reconstruction.

The chains

Docker puts one rule into the built-in filter FORWARD chain, -j DOCKER-FORWARD. The controller later inserts -j DOCKER-USER above it, so user rules run first, and dockerd never deletes rules there. DOCKER-FORWARD fans out to DOCKER-CT, DOCKER-INTERNAL and DOCKER-BRIDGE, which jumps to DOCKER. There, one ACCEPT per published port sits above a final DROP for traffic entering the bridge (iptabler/iptabler.go:205-226, firewall_linux.go:30-77). The old DOCKER-ISOLATION-STAGE-1/2 chains are now only deleted from the code. Each endpoint also gets a raw-table DROP for packets addressed to the container that did not arrive on its bridge, the "direct routing" block of 28.x. Publishing on 127.0.0.1 adds raw PREROUTING -d 127.0.0.1 --dport 8080 ! -i lo -j DROP. Before 28.0.0 such a port was reachable from the same L2 segment, and DOCKER_INSECURE_NO_IPTABLES_RAW=1 still removes both kinds of drop silently (D75). In routed gateway mode there is no NAT, so the host port is ignored and -p 8080:80 opens container port 80 (D74). Figure 2 draws the default rule set and its nftables twin.

Four smaller findings sit in the same tree. Endpoint.Less's comment names ep.name as the last tie-break, but the code compares network names (D66). Both branches of selectFirewallBackend return nil (D71). docs/networkdb.md links an overlay.md that does not exist (D73). And joining several containers' namespaces under userns-remap silently overwrites the user namespace, a known FIXME, moby#46210 (D72) from the code.

The nftables backend is experimental and opt-in in 29.x (--firewall-backend=nftables). It has no DOCKER-USER chain, does not enable IP forwarding, and refuses swarm mode unless the swarm-nftables feature is set (D70) from the code. One more measurement for scale: this sandbox's own eth0 is also a veth (eth0@if26, a random locally administered MAC, a /32 address, gateway 169.254.1.1). That is a CNI-style network built by another runtime, not a Docker bridge measured here.

03127.0.0.11 is dockerd

On a user-defined network, a container's /etc/resolv.conf lists one nameserver, 127.0.0.11. No process inside the container listens there. The resolver is a Go DNS server, miekg/dns v1.1.73, running as goroutines inside dockerd. Its UDP and TCP sockets are opened inside the container's network namespace, on 127.0.0.11 with port 0, by a function run on a thread that dockerd has switched into that namespace (moby/daemon/libnetwork/resolver.go:146-203, sandbox_dns_unix.go:87-94) from the code. One resolver starts per sandbox, the first time an endpoint joins with resolution enabled.

Port 0 means the kernel picks a random port, so something has to turn :53 into that port. dockerd writes NAT rules into the container's own nat table, in moby/daemon/libnetwork/resolver_unix.go:37-42: 

rules := [][]string{
	{"-t", "nat", "-I", outputChain, "-d", resolverIP, "-p", "udp", "--dport", dnsPort, "-j", "DNAT", "--to-destination", laddr},
	{"-t", "nat", "-I", postroutingChain, "-s", resolverIP, "-p", "udp", "--sport", ipPort, "-j", "SNAT", "--to-source", ":" + dnsPort},
	{"-t", "nat", "-I", outputChain, "-d", resolverIP, "-p", "tcp", "--dport", dnsPort, "-j", "DNAT", "--to-destination", ltcpaddr},
	{"-t", "nat", "-I", postroutingChain, "-s", resolverIP, "-p", "tcp", "--sport", tcpPort, "-j", "SNAT", "--to-source", ":" + dnsPort},
}

The chains are DOCKER_OUTPUT and DOCKER_POSTROUTING, jumped to from nat OUTPUT and POSTROUTING for -d 127.0.0.11. A query to 127.0.0.11:53 is DNATed to the real port, and the answer's source port is SNATed back to 53, so the application sees an ordinary server. In nftables mode the same trick lives in a per-namespace table ip docker-dns. Every one of these rules is IPv4. The file carries // TODO IPv6 support, and an IPv6-only network still gets nameserver 127.0.0.11 (D69) from the code.

Names come first from libnetwork's service records: container names, aliases, the 12-character short ID and the hostname. A name with only an IPv4 record gets an empty authoritative AAAA answer rather than being forwarded from the code. Everything else goes upstream, and where the dial happens depends on where the upstream came from, in moby/daemon/libnetwork/resolver.go:490-505: 

if server.HostLoopback {
	return net.DialTimeout(proto, addr, extIOTimeout)
}

var (
	extConn net.Conn
	dialErr error
)
err := r.backend.ExecFunc(func() {
	extConn, dialErr = net.DialTimeout(proto, addr, extIOTimeout)
})

Servers copied from the host's resolv.conf are marked HostLoopback and dialed from the host namespace. That is what lets a host-local resolver such as 127.0.0.53 work. It also means the query leaves with the host's address and never crosses the bridge's FORWARD chain (D63). Servers given with --dns are dialed from inside the container. When /etc/resolv.conf names only 127.0.0.53, libnetwork reads /run/systemd/resolve/resolv.conf instead from the code.

The container's file is generated and bind-mounted. It lists nameserver 127.0.0.11, keeps the host's search and options, adds ndots:0 if no ndots is present, and records the stashed upstreams in a trailing # ExtServers: [...] comment. A hash file lets dockerd notice user edits, and after one it stops rewriting the file. The default bridge gets none of this. Resolution is disabled there, so containers cannot find each other by name; loopback nameservers are stripped, and 8.8.8.8 and 8.8.4.4 are substituted if nothing remains (D68). One comment has drifted too: TransformForIntNS promises to "use the defaults" when there are no external nameservers, but the code only appends a warning (D65) from the code. None of this could be observed here. The commands in §09 show what a live host would print reconstruction.

04Frames and logs

A container without a TTY has two output streams, but an HTTP response is one byte stream. Docker multiplexes them with a frame: eight header bytes, then a payload. Byte 0 is the stream (0 stdin, 1 stdout, 2 stderr, 3 "systemerr"), bytes 1–3 are zero, and bytes 4–7 are the payload length as a big-endian uint32 (moby/api/pkg/stdcopy/stdcopy.go:14-27). The daemon emits one frame per Write call, header and payload in a single write from a pooled buffer, with no coalescing or splitting (moby/daemon/internal/stdcopymux/writer.go:32-55). Three producers use it: non-TTY attach, non-TTY exec, and GET /containers/{id}/logs. Only the logs path ever sends type 3 from the code. Part 1 shows the hijacked attach connection these frames travel on.

To watch the reader work, the real docker CLI 29.8.2 was pointed at a mock daemon that writes hand-made frames measured here. The CLI asked GET …/json before GET …/logs: it decides framed or raw from the container's Config.Tty, not from the Content-Type the daemon labels since API 1.42. The bytes it decoded are in Figure 4.

Two reader paths are worth seeing in code. In moby/api/pkg/stdcopy/stdcopy.go:107-127 from the code: 

for nr < frameSize+stdWriterPrefixLen {
	var nr2 int
	nr2, err = multiplexedSource.Read(buf[nr:])
	nr += nr2
	if errors.Is(err, io.EOF) {
		if nr < frameSize+stdWriterPrefixLen {
			return written, nil
		}
		break
	}
	…
}
if stream == Systemerr {
	return written, fmt.Errorf("error from daemon in stream: %s", string(buf[stdWriterPrefixLen:frameSize+stdWriterPrefixLen]))
}

A stream that ends inside a frame returns nil: a clean EOF, with the partial frame silently dropped. The mock's truncated stream ended with exit 0. The buffer also grows to whatever the header announces, up to 4 GiB, with no cap. Both are in the public api/pkg/stdcopy package, which the CLI vendors unchanged (D79).

Logs: one copier, blocking, unbounded

Every container gets one logger.Copier, with a goroutine per stream reading the broadcaster into a 16 KiB buffer. It splits on \n and stamps each line with time.Now() at copy time, not when the process wrote it. Longer lines become "partial" messages that share an ID; json-file does not store that ID, so a missing trailing newline is the only trace (moby/daemon/logger/copier.go:102-165) from the code. Figure 5 follows a line from the container to docker logs.

Logging is blocking by default. Unless mode=non-blocking is set, the copier calls the driver inline, so a slow driver back-pressures the FIFO, the shim and finally the container's write(2). json-file is also unbounded by default: with no max-size the capacity is −1 and nothing rotates from the code. Setting max-size without max-file is worse than it looks, in moby/daemon/logger/loggerutils/logfile.go:227-230: 

if w.maxFiles < 2 {
	if err := unlink(fname); err != nil && !errors.Is(err, fs.ErrNotExist) {
		log.G(context.TODO()).WithError(err).Error("Error unlinking current log file")
	}

max-file defaults to 1, so every rotation throws the whole history away. The docs say no rotation happens by default; they do not say this (D78). Rotation never truncates in place, because a reader may still hold the old file open.

The non-blocking alternative trades stalls for loss. A ring buffer, 1 MB of line bytes by default (max-buffer-size), sits in front of the driver; when it is full, the newest message is dropped and Enqueue returns nil (moby/daemon/logger/ring.go:163-183). The budget counts only len(Line): each message costs roughly 380 bytes of heap, so short lines can use tens of times the nominal 1 MB, and empty lines count zero and are never dropped from the code. Drivers that cannot be read back, such as syslog or fluentd, get a hidden local-format cache so that docker logs still works. That cache is wrapped in the same ring when mode is unset, so it is lossy by default while the primary driver blocks (D86). The formats lose things too. json-file escapes like Go's encoding/json and replaces invalid UTF-8 with �, so binary output does not survive. local refuses any record whose length header exceeds 1,000,000 bytes, and that refusal is the text in Figure 4's type-3 frame from the code. One last surprise: docker logs -f on a stopped container prints the history and exits, and a later docker start does not reattach it (D87).

05Signals, stop and restart

docker stop is a signal, a wait and a SIGKILL. On the wire it is one request. Against the mock daemon, docker stop -t 3 -s SIGINT web sent POST /v1.56/containers/web/stop?signal=SIGINT&t=3, and a plain docker stop web sent no query at all, so the container's own StopTimeout applies measured here. docker kill -s HUP became kill?signal=HUP. The daemon side is in moby/daemon/stop.go:85-89, 115-118 from the code: 

	// 1. Send a stop signal
	err := daemon.killPossiblyDeadProcess(ctx, ctr, stopSignal)
	if err != nil {
		wait = 2 * time.Second
	}
…
	// Stop either failed or container didn't exit, so fallback to kill.
	if err := daemon.kill(ctx, ctr); err != nil {

The signal is the container's StopSignal, else SIGTERM. The wait is the request's t, else the container's StopTimeout, else 10 seconds on Linux. A negative timeout waits forever. The stop runs under context.WithoutCancel, so pressing Ctrl-C on docker stop does not abort it, and stopping a stopped container returns 304 from the code.

Only PID 1 hears it

The signal travels dockerd → containerd Task.Kill → shim → a fresh runc kill <id> <sig> → the container's init process. Nothing else in the container is signalled; only SIGKILL with a shared PID namespace is fanned out to the whole cgroup (runc/libcontainer/container_linux.go:396-426). Then the kernel applies its rule for a namespace's init process: a signal for which init has no handler is dropped, even when root sends it. Only SIGKILL and SIGSTOP from an ancestor namespace are forced (pid_namespaces(7)). A sh or a naive binary as PID 1 never sees the SIGTERM. docker stop therefore always waits the full timeout and ends in SIGKILL. The exit code is 137 because the shim's reaper encodes a signal death as 128 plus the signal number (containerd/pkg/sys/reaper/reaper_unix.go:280-289) from the code. Figure 6 draws the clock. --init puts tini v0.19.0 in front as PID 1; it has handlers and forwards the signal to the real program, which then dies of the default action (Part 1 §03 shows the rewrite).

The restart manager, and D77

After an exit, the restart manager decides. Its backoff is 100 ms, doubling on each restart, capped at one minute, and reset whenever the last run lasted 10 seconds or more (moby/daemon/internal/restartmanager/restartmanager.go:11-15, 65-78). always restarts, unless-stopped restarts unless hasBeenManuallyStopped, on-failure[:N] restarts on a non-zero exit while the count is below N, and no returns before taking any lock. A manual stop also cancels the manager outright, so after docker stop no policy restarts at exit. The policies diverge only at daemon startup, where a stopped always container comes back and an unless-stopped one does not from the code.

The flag that makes a stop "manual" is set in moby/daemon/kill.go:80-103, and its placement is finding D77 from the code: 

var unpause bool
if container.Config.StopSignal != "" && stopSignal != syscall.SIGKILL {
	containerStopSignal, err := signal.ParseSignal(container.Config.StopSignal)
	if err != nil {
		return err
	}
	if containerStopSignal == stopSignal {
		container.ExitOnNext()
		unpause = container.State.Paused
	}
} else {
	container.ExitOnNext()
	unpause = container.State.Paused
}

if !daemon.IsShuttingDown() {
	container.HasBeenManuallyStopped = true
	if err := container.CheckpointTo(ctx, daemon.containersReplica); err != nil {
	…
}

ExitOnNext cancels the manager. Without a StopSignal in the config, the else branch runs for any signal, so docker kill -s HUP cancels always and on-failure too. And HasBeenManuallyStopped = true sits outside the if/else, so every docker kill -s marks the container as manually stopped, even with a STOPSIGNAL. It is checkpointed to disk, so it also survives a daemon restart. Send SIGHUP to reload nginx, and the next crash of an unless-stopped container is never restarted. PR #26464 (v1.13.0, 2016) fixed only the ExitOnNext half. Issues #41302 and #47792 are open, and fix PR #53415 has been open and unmerged since 2026-08-19. kill.go is byte-identical on master. The workaround is to signal the process directly, with docker exec c kill -HUP 1. Figure 7 lays out every case.

06Health, OOM, stats, events, cp and pause

Docker's observability commands are thin readers. Each reads a cgroup file, an in-memory ring or a container lock, and each answers a slightly different question from the one its name suggests.

Health checks

A probe is an ordinary exec in the container: same user, working directory and environment, no TTY, no stdin, with output captured into a 4,096-byte buffer. It shows up in docker events as exec_create. The defaults are interval 30 s, timeout 30 s, retries 3, start period 0 and start interval 5 s, and the first probe runs one interval after start. A container therefore stays starting for at least 30 seconds. A timeout kills the probe and records exit code −1. Only the last five results are kept, and an event fires only on a transition (moby/daemon/health.go:23-44, 111-152, 238-251). Then nothing happens. The restart manager never looks at health, so unhealthy acts on nothing outside swarm and other orchestrators (D88) from the code. The same finding adds that --tmpfs mounts default to noexec,nosuid,nodev, so a script copied into a --tmpfs /tmp will not run.

OOM

On cgroup v2 the shim watches the container cgroup's memory.events with inotify, re-reads it on every wakeup and publishes TaskOOM whenever oom_kill grows (containerd/internal/oom/watcher.go:102-141). The watcher is armed right after runc create, while init still waits on the FIFO, so an early OOM is not missed. On any TaskOOM, dockerd sets State.OOMKilled. The victim may be a child while PID 1 keeps running. Docker sets no memory.oom.group, and runc's systemd scopes default to OOMPolicy=continue, so the kernel normally kills one process it chooses. OOMKilled: true means "something in this cgroup was OOM-killed during this run" (D82) from the code. This sandbox's own cgroup shows why the counters need care (comments mine) measured here: 

$ cat /sys/fs/cgroup/memory.events      # this sandbox, not a Docker container
low 0
high 0
max 7452          # times usage hit memory.max
oom 0             # times the cgroup went OOM
oom_kill 0        # the counter the shim watches
oom_group_kill 0

docker stats reports cgroup v2 failcnt as oom, not max. Here the two read 0 and 7,452 (D83). This sandbox's cgroup also has memory.oom.group set to 1, which a Docker container's would not.

Stats

One daemon-wide goroutine samples every watched container in turn, then sleeps one second, so the real period is a second plus the sampling time. Each sample is a containerd Task.Metrics round trip to the shim, which reads cpu.stat, memory.stat, memory.current and the rest. The "system" side is not from cgroups at all: dockerd sums the first seven fields of /proc/stat's cpu line and counts cpuN lines as online CPUs (moby/daemon/stats_unix.go:296-357). The CLI then computes, in cli/cli/command/container/stats_helpers.go:196-198: 

	if systemDelta > 0.0 && cpuDelta > 0.0 {
		cpuPercent = (cpuDelta / systemDelta) * onlineCPUs * 100.0
	}

That is a percentage of one CPU, scaled by the host's CPU count, never by the container's cpu.max quota. A Python re-implementation over this sandbox's files gives a cpuDelta of 2,005,555,000 ns against a systemDelta of 7,930,000,000 ns on 8 CPUs: 202.33 %, for a cgroup whose cpu.max reads 200000 100000, a two-CPU quota measured here. It is arithmetic over real files, not dockerd output. MEM USAGE is memory.current − inactive_file: 8,190,771,200 − 370,188,288 bytes, or 7.28 GiB. Two more quirks. The first streamed sample has empty precpu_stats, so it is a lifetime average. And --no-stream sends stream=false without one-shot, as the mock trace shows, so the daemon waits for two samples first from the code.

Events

The event history is an in-memory slice of the last 256 events. --since can replay only that, and nothing from before a daemon restart. Live delivery goes through a publisher that waits at most 100 ms per subscriber per event, then skips that subscriber, silently. The 256 is documented; the drop is not (D85, moby/daemon/events/events.go:13-31). Container labels are copied over the event's attributes, so a label named exitCode falsifies every die event (D84, an inference from maps.Copy). The wire format is JSON lines, served as application/jsonl from API 1.52, although the API changelog lists the change under 1.53 (D90) from the code. Fed four mock events, the CLI rendered kill … signal=15, then die … exitCode=143, health_status: unhealthy and oom measured here.

docker cp, pause and checkpoints

docker cp is three verbs on /containers/{id}/archive: HEAD to stat, GET for a tar and PUT to extract one. Copying out, the CLI sent a single GET with no HEAD measured here. Since 24.0 the daemon does the copy in a private mount namespace, so symlinks resolve inside the container. That code was still being patched for CVEs in 2026. The GET holds the container lock until the client has read the whole tar, so a slow copy blocks docker stop, kill and pause on that container (D81, inferred from code, not observed). Pause writes 1 to cgroup.freeze, and runc polls cgroup.events every 10 ms, up to 1,000 times, for frozen 1. The processes receive no signal. Pausing a paused container is a 409; unpausing a running one is an untyped error, so HTTP 500. docker commit pauses by default and ignores both errors (D89). The experimental checkpoint path has the part's one latent bug. When containerd's index lacks the checkpoint manifest, CreateCheckpoint wraps a nil error, which yields nil, and reports success. Stock containerd never reaches that branch (D80) from the code.

07Thirteen years of moving work out of one binary

The five-program relay of Part 1 was not designed. It accreted, one extraction at a time, and the code still carries the seams. moby's first commit is dated 2013-01-18. The next day's commit is "Prototyping with a mock CLI and daemon", and a month later the code was already split into docker/server and docker/client. The client/daemon boundary is as old as the project measured here, from git history. Docker 0.1.0, the "Initial public release", is dated 2013-03-23 in the changelog. It already had push, pull and layers. dotCloud renamed itself Docker, Inc. that October. Figure 8 lays the extractions out in three lanes.

Out of the binary

First the kernel interface left LXC's userland. libcontainer began in the Docker repository on 2014-02-18, and 0.9 (2014-03-10) made its "native" driver the default. LXC was deprecated in 1.8 and removed in 1.10. The announcement gave the reason as LXC's userland changing from one distribution to the next. Then the runtime left the company. The Open Container Initiative launched on 2015-06-22, with runc donated to it. runc's history begins with libcontainer's first commit, because the code moved with its history. runc then stayed a "1.0 release candidate" for five years while Docker shipped it: v1.0.0-rc1 came on 2016-06-03 and v1.0.0 on 2021-06-22 measured here.

Then supervision left dockerd. containerd's first commit is 2015-11-05, and Docker 1.11.0 (2016-04-13) was the first release to run containers through containerd and runc. It shipped four Linux binaries: docker, docker-containerd, docker-containerd-shim and docker-runc. Containers survived a daemon restart only from 1.12, which added --live-restore and split out docker-proxy. containerd joined the CNCF on 2017-03-29 and graduated on 2019-02-28. The graduation release says "Born at Docker in 2014", more than a year before the repository's first commit (D93). containerd's SCOPE.md still excludes networking, build, volumes and logging. That is why libnetwork, BuildKit and the log drivers of §02–§04 live in dockerd from the code.

The project itself split. docker/docker became the Moby Project on 2017-04-18, and the client moved to docker/cli that month. In 2026 the CLI imports github.com/moby/moby/api v1.56.1 and client v0.6.2 as separate modules. The client folder has moved back into moby (cli/vendor.mod:36-37). Kubernetes moved off dockerd next. dockershim, the CRI adapter that lived inside the kubelet, was deprecated in 1.20 and removed in 1.24, and Docker itself did not change. CRI was merged into containerd's tree on 2020-10-07. At the pin, dockerd starts its managed containerd with CRI off unless --cri-containerd is set from the code. Judging by their titles, that keeps a default Docker Engine out of reach of containerd's 2026 batch of CRI-plugin advisories reconstruction.

The company split as well. On 2019-11-13 Mirantis bought Docker's Enterprise business, and Swarm went with it; in July 2025 Mirantis extended Swarm support for five more years. From 2021-08-31, Docker Desktop needed a paid subscription in organisations with 250 or more employees or $10 million in revenue. The Engine, containerd, runc and BuildKit stayed Apache-2.0. Compose followed the plugin pattern: the Python docker-compose of 2014 became the Go docker compose CLI plugin in 2021, and the next major, v5.0.0 in December 2025, skipped 3 and 4 to avoid confusion with the old file-format versions. On this machine Compose answers v5.6.0 to the hidden docker-cli-plugin-metadata subcommand measured here.

The docs around this history have drifted in small ways. dockerd-rootless.sh calls gvisor-tap-vsock the default in one place and the last fallback in another, and the 29.5.0 notes call it the "new default" (D91). Docker's VMM page gives two ranges for libkrun that cannot both be right (D92). The 19.03 notes' link text reads moby/moby#380050 for pull 38050 (D94).

Versions, defaults and the reversal

Version numbers moved too. 17.03 switched to YY.MM CalVer, there was never a stable 22.x, and 23.0 went to SemVer while making buildx the default builder. There is no Engine 27.0.0: a tag made by mistake was cached by the Go module mirror, so 27.0.1 came first (D96). The 25–29 defaults are in Parts 1 and 2. Two belong here. Read-only binds became recursively read-only in 25.0, except for API < 1.44 clients (D98). 29.0 raised the minimum API version to 1.44 and 29.3 lowered it back to 1.40, so old SDKs behave differently by minor release (D97).

In 2026 the extraction reversed for the first time. 29.7.0 added an experimental embedded-containerd that runs containerd's gRPC server inside dockerd. Since 29.8.0, dockerd falls back to it automatically when the containerd binary is missing, no system containerd runs and no --containerd is set. Shims remain separate processes, so the container still has no daemon ancestor (Part 1 §04, D7). Pinned is not installed either. The 29.9.2 source pins containerd 2.4.2 and runc 1.5.2, but packages ship their own containerd.io. This box runs Engine 29.8.2 with containerd 2.3.6 and runc 1.5.1 (D95) measured here.

The code at the pins shows where the work went. Counting hand-written Go and excluding vendored and generated files: moby 382,553 lines, containerd 239,292, BuildKit 216,094, cli 110,387, distribution 55,769 and runc 31,969. Only 22,321 of runc's lines are non-test, about a tenth of dockerd's. moby's vendor/ holds 2.23 million lines, and libnetwork, at 48,507 non-test lines, is its largest subsystem measured here. Repository advisory lists count moby 26 (1 critical), containerd 33 (5 critical), runc 13 and BuildKit 24, but they start in 2020–2021. Landmark CVEs such as 2019-5736 are absent (D100). moby's one critical, CVE-2024-41110 (2024-07-23), is a regression of an AuthZ bug fixed in 18.09.1 in January 2019, and CVE-2026-34040, fixed in 29.3.1, is an incomplete fix for it (D99).

08The findings register

Reading the pinned sources line by line against their docs, and measuring what this machine allowed, left 100 findings across the four parts. Figure 9 lists every one. They come from eight topic dossiers, each checked by a separate verification pass, then deduplicated. Verification overrode the dossiers wherever they disagreed. Findings it could not confirm were narrowed or dropped. The ptrace half of D16 is gone, for example, and nothing is called a bug that verification did not leave a bug.

The classes are fixed. A is a latent bug. B would be a bug fixed upstream after the pin. C is doc drift: docs, comments or changelogs that disagree with the code or with each other, where the code wins. D is a gotcha, correct by design or by accident but surprising. E is a behaviour change, a default that moved at or after the pin. The counts are A 6, B 0, C 21, D 67 and E 6. By part: D1–D22 in Part 1, D23–D50 in Part 2, D51–D62 in Part 3 and D63–D100 here.

Class B is empty for a measured reason. On 2026-10-23 the verifiers checked each finding against the default branch of its repository: moby and docker/cli master, runc and containerd main, BuildKit master, distribution main and docker/docs main. None had been fixed since the pin. The "Upstream" column records what they saw; "on master" means the cited code is still there. No reports were filed by this project. Where an upstream issue or pull request is named, as for D77 and D38, it was found, not filed measured here, from GitHub and the clones. Upstream did move near some rows. runc's main replaced the exec.fifo poll after v1.5.2 (D22), and containerd 2.4 records exit status in the bundle while moby keeps its own duplicate-exit filter (D11). Those are behaviour changes, not fixes.

What the classes hold

The six latent bugs are small. A bad detachKeys in the config fails only after the container exists (D3). One attach write ignores its error (D10). distribution's downgrade path hands an OCI manifest to a client that asked for schema2 only (D36). 4 * 1048 * 1048 is a typo for 1024 (D42). Joined namespaces under userns-remap overwrite each other's user namespace (D72). And CreateCheckpoint reports success by wrapping a nil error, in a branch stock containerd never reaches (D80). None is a security issue as found.

The 21 doc drifts mostly share a cause: the code moved and the prose did not. The live-restore page still speaks of YY.MM releases (D12). The API changelog puts a 1.52 change under 1.53 (D90). The firewall docs state a DROP policy that the code sets only conditionally (D64). Some drifts are inside the code: comments that name the wrong field (D66), the wrong runc version (D19) or a fallback that does nothing (D65).

The 67 gotchas fall into four patterns. Several decisions rest on string matching: exit codes 125–127 (D1) and the "created" state after a failed start (D9). Some paths drop data silently: a cut frame (D79), a slow event subscriber (D85), the dual-logging cache (D86) and a broken credential helper (D47). Some names say less than they seem to: "image ID" (D23), OOMKilled (D82) and CPU % (D83). And the code a host runs is not always the code that was pinned (D95). The six behaviour changes are all deliberate, and most are in the release notes. They matter because a host's behaviour now depends on the 29.x minor: the time namespace (D17), the API floor (D97) and recursive read-only binds (D98).

Why D77 heads the list

D77 is the one most likely to hurt someone today. It is triggered by an ordinary operation, a reload signal sent with docker kill -s. It fails silently, much later, at the next crash. It persists across daemon restarts because the flag is checkpointed. It has an open fix and open issues going back to 2020, and its first half was fixed in 2016. Its reproduction is three commands, in the D group's notes below. A reader with a Docker host can run it in under a minute.
