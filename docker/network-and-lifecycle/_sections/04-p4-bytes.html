{{S}}Frames and logs

A container without a TTY has two output streams, but an HTTP response is one byte stream. Docker multiplexes them with a frame: eight header bytes, then a payload. Byte 0 is the stream (0 stdin, 1 stdout, 2 stderr, 3 "systemerr"), bytes 1–3 are zero, and bytes 4–7 are the payload length as a big-endian uint32 (moby/api/pkg/stdcopy/stdcopy.go:14-27). The daemon emits one frame per Write call, header and payload in a single write from a pooled buffer, with no coalescing or splitting (moby/daemon/internal/stdcopymux/writer.go:32-55). Three producers use it: non-TTY attach, non-TTY exec, and GET /containers/{id}/logs. Only the logs path ever sends type 3 from the code. Part 1 shows the hijacked attach connection these frames travel on.

To watch the reader work, the real docker CLI 29.8.2 was pointed at a mock daemon that writes hand-made frames measured here. The CLI asked GET …/json before GET …/logs: it decides framed or raw from the container's Config.Tty, not from the Content-Type the daemon labels since API 1.42. The bytes it decoded are in Figure {{fig-stdcopy-frame}}.

A stream that ends inside a frame returns nil: a clean EOF, with the partial frame silently dropped. The mock's truncated stream ended with exit 0. The buffer also grows to whatever the header announces, up to 4 GiB, with no cap. Both are in the public api/pkg/stdcopy package, which the CLI vendors unchanged (D79).

Logs: one copier, blocking, unbounded

Every container gets one logger.Copier, with a goroutine per stream reading the broadcaster into a 16 KiB buffer. It splits on \n and stamps each line with time.Now() at copy time, not when the process wrote it. Longer lines become "partial" messages that share an ID; json-file does not store that ID, so a missing trailing newline is the only trace (moby/daemon/logger/copier.go:102-165) from the code. Figure {{fig-log-pipeline}} follows a line from the container to docker logs.

Logging is blocking by default. Unless mode=non-blocking is set, the copier calls the driver inline, so a slow driver back-pressures the FIFO, the shim and finally the container's write(2). json-file is also unbounded by default: with no max-size the capacity is −1 and nothing rotates from the code. Setting max-size without max-file is worse than it looks, in moby/daemon/logger/loggerutils/logfile.go:227-230: 

if w.maxFiles < 2 {
	if err := unlink(fname); err != nil && !errors.Is(err, fs.ErrNotExist) {
		log.G(context.TODO()).WithError(err).Error("Error unlinking current log file")
	}

max-file defaults to 1, so every rotation throws the whole history away. The docs say no rotation happens by default; they do not say this (D78). Rotation never truncates in place, because a reader may still hold the old file open.

The non-blocking alternative trades stalls for loss. A ring buffer, 1 MB of line bytes by default (max-buffer-size), sits in front of the driver; when it is full, the newest message is dropped and Enqueue returns nil (moby/daemon/logger/ring.go:163-183). The budget counts only len(Line): each message costs roughly 380 bytes of heap, so short lines can use tens of times the nominal 1 MB, and empty lines count zero and are never dropped from the code. Drivers that cannot be read back, such as syslog or fluentd, get a hidden local-format cache so that docker logs still works. That cache is wrapped in the same ring when mode is unset, so it is lossy by default while the primary driver blocks (D86). The formats lose things too. json-file escapes like Go's encoding/json and replaces invalid UTF-8 with �, so binary output does not survive. local refuses any record whose length header exceeds 1,000,000 bytes, and that refusal is the text in Figure {{fig-stdcopy-frame}}'s type-3 frame from the code. One last surprise: docker logs -f on a stopped container prints the history and exits, and a later docker start does not reattach it (D87).
