01A process and five programs

A container is an ordinary Linux process. Docker is a relay of five separate programs: the docker CLI, dockerd, containerd, one containerd-shim-runc-v2 per container, and a short-lived runc. They agree on names made of sha256 hashes and on one JSON spec. They ask the kernel to narrow one process's view of the machine, and then most of them get out of the way. This part follows a single docker run -it alpine sh from the keystroke to the running shell and back to its exit code. Its claim is that the run path is choreography with a hold point in the middle: the CLI makes five calls, create only writes JSON, start rebuilds the spec, runc builds namespaces before Go even boots, and the new process waits on a FIFO while dockerd plugs in its network.

Start with the end state. On a systemd host with a system containerd, one running docker run -it alpine sh leaves this process tree: systemd is the parent of dockerd, of containerd, and of a containerd-shim-runc-v2 started as -namespace moby -id <id> -address /run/containerd/containerd.sock, and the shim is the parent of sh, which is PID 1 inside the container. No runc process remains. No process links dockerd to the container; only named FIFOs do from the code. That tree is an inference from the code, not an observation: no container could run on the research box, so nobody ran pstree on one reconstruction. §08 reads the one real container that was available, the sandbox itself.

Figure 1 labels each edge with its transport. The CLI speaks HTTP/1.1 to dockerd on a Unix socket, and turns that socket into a raw byte pipe for attach. dockerd speaks gRPC to containerd in the namespace moby. containerd calls the shim over ttrpc on a socket whose name is a sha256, and the shim calls back up on a second ttrpc socket to publish events. The shim runs runc with plain fork and exec, a config.json on disk and a Unix socket that carries the pty's master file descriptor from the code.

The shape explains the most useful property of the design. The shim's start step re-executes itself as a long-lived server in its own process group and exits, so the server is orphaned and adopted by the nearest subreaper (containerd/cmd/containerd-shim-runc-v2/manager/manager_linux.go:84-114). The shim then marks itself a child subreaper with prctl(PR_SET_CHILD_SUBREAPER, 1), so when runc create exits the container's init is reparented to the shim, which later reaps it with wait4 (containerd/pkg/shim/shim_linux.go:29-30; containerd/pkg/sys/reaper/reaper_unix.go:258-266). Container processes are therefore children of the shim, not of dockerd or containerd. Killing dockerd does not kill them. A containerd that dockerd itself supervises dies with dockerd, because it is started with Pdeathsig: SIGKILL (moby/daemon/internal/containerd/server/supervisor/utils_linux.go:10), but the shims run in their own process groups and survive that too (manager_linux.go:110-111) from the code.

It was not always this way. Docker 1.11.0 (13 April 2016) was the first release to run containers through containerd and runc, and it shipped four Linux binaries: docker, docker-containerd, docker-containerd-shim and docker-runc. Containers kept running across a daemon shutdown only from 1.12.0 (28 July 2016), which added --live-restore, per the changelog in moby's v1.13.0 tag from the code. Part 4 tells that history.

The rest of this part walks the tree top to bottom and back up. §02 is the CLI's five calls. §03 is what dockerd does at create and at start. §04 is containerd and the shim. §05 is runc's init, where the namespaces are actually made. §06 is the FIFO that separates create from start. §07 is the exit climbing back up, and what survives a dockerd restart. §08 reads a real container from the inside. The image that alpine names is Part 2's subject; the network that §06 plugs in is Part 4's.

02Five calls on three connections

docker run is not one request. The daemon has no "run" endpoint. The CLI composes run out of five API calls: a ping, a create, a hijacked attach, a wait and a start, in that order. Attach and wait are issued before start, so no early output and no fast exit can be missed. cli/cli/command/container/run.go:151, 186, 203-206 is the core of it from the code: 

	containerID, err := createContainer(ctx, dockerCli, containerCfg, &runOpts.createOptions)
…
		closeFn, err := attachContainer(ctx, dockerCli, containerID, &errCh, config, client.ContainerAttachOptions{
…
	statusChan := waitExitOrRemoved(statusCtx, apiClient, containerID, copts.autoRemove)

	// start the container
	if _, err := apiClient.ContainerStart(ctx, containerID, client.ContainerStartOptions{}); err != nil {

To watch the bytes, the real docker CLI 29.8.2 was pointed at a mock daemon: a Python server shaped after moby's router code. Everything the CLI sent is real. Everything the "daemon" sent back was invented by the mock, and its Server header says [MOCK] measured here. Figure 2 is that trace.

Ping, create, and the pull you didn't ask for

The ping comes first because flag parsing depends on the daemon's OS: runRun calls Ping and passes serverInfo.OSType into parse (run.go:104-109). The client hits the unversioned /_ping with HEAD, reads API-Version, and lowers its own maximum, MaxAPIVersion = "1.56", to the server's if that is lower; below MinAPIVersion = "1.40" it refuses (moby/client/client.go:111, 115). Every later path carries the prefix /v1.56/ from the code. Over a Unix socket the Host header is the placeholder api.moby.localhost, and the user agent is Docker-Client/29.8.2 (linux) measured here.

The create body is the whole container config. With -it it says "Tty":true,"OpenStdin":true,"StdinOnce":true; the CLI sets StdinOnce whenever stdin is both open and attached (opts.go:729-732). The terminal size rides along as HostConfig.ConsoleSize (create.go:327), so the pty can be sized before any resize call from the code. It was [0,0] in the first trace, which ran without a real terminal size; after stty rows 40 cols 120 it was [40,120], followed by POST …/resize?h=40&w=120 right after start measured here. The pull is not part of create either. If create returns NotFound and --pull=missing is in force, the CLI prints "Unable to find image", calls ImagePull and retries create (create.go:338-358) from the code.

Attach is a hijack; wait is a long-poll

Attach asks for Connection: Upgrade and Upgrade: tcp. The daemon takes the socket away from Go's HTTP server and writes the status line itself, moby/daemon/server/router/container/container_routes.go:1142, 1150-1159 from the code:

After that line the socket is raw bytes both ways. With a TTY there is no framing at all; without one, output is multiplexed into 8-byte-header frames, which Part 4 takes apart. Errors after the hijack are hand-written HTTP too, and the FIXME above is still on moby master (finding D10, class A, low) from the code. Wait is the opposite trick. container_routes.go:444-453 writes 200 OK and flushes at once, then blocks on status := <-waitC, so the body is written only when the container exits. The CLI waits with condition=next-exit (removed under --rm) and maps any wait error to status 125 (utils.go:18-38). Start follows on a third connection, because connection #1 is held by the pending wait. It takes no body and answers 204 only after containerd has started the process (container_routes.go:283-309) from the code.

The terminal side

With -t the CLI puts its own stdin and stdout into raw mode and wraps stdin in an escape proxy whose default detach sequence is Ctrl-P Ctrl-Q, defaultEscapeKeys = []byte{16, 17} (hijack.go:19) from the code. Typing a, b, Ctrl-P, Ctrl-Q sent only ab to the daemon, and the CLI exited 0 measured here. The daemon enforces the same keys again for TTY attaches (moby/daemon/internal/stream/attach.go:14). There is a gap in the CLI's check: runContainer falls back to detachKeys from ~/.docker/config.json but validates only the flag (run.go:143-149), so a bad config value fails after create and attach and leaves a created container behind (finding D3, class A, still on cli master) from the code.

When local stdin ends, the CLI half-closes the socket with CloseWrite rather than closing it (hijack.go:194-196), so output keeps flowing. What the daemon does with that end depends on the TTY. StdinOnce closes the container's stdin only when there is no TTY; with -it, the end of client stdin closes this attach's stdout and stderr instead and leaves the container's stdin open (stream/attach.go:69-80; finding D4, class D) from the code. Signals take a fifth path: with --sig-proxy (default true) the CLI turns each caught signal into POST /containers/{id}/kill?signal=NAME, and SIGWINCH into POST …/resize (signals.go:16-56, tty.go:80-106) from the code.

03Create is bookkeeping; start builds the world

POST /containers/create touches no runtime at all. It resolves the image locally, merges the config, allocates an ID and a name, creates the read-write layer, writes JSON to disk and emits a create event (moby/daemon/create.go:171-290). containerd is not called until start. A missing image gives the 404 that the CLI's pull-and-retry waits for from the code.

The ID is 32 random bytes in hex, 64 characters, drawn again if its 12-character short form is all digits, because the short ID becomes the default hostname (moby/daemon/internal/stringid/stringid.go:36-60). The program is fixed now from Entrypoint and Cmd; for alpine sh that is Path:"sh" with no args (moby/daemon/container.go:134-157). The record lands in /var/lib/docker/containers/<id>/, created mode 0710, as two files written atomically with mode 0600: config.v2.json and hostconfig.json. They are split on purpose. HostConfig carries json:"-" with the comment "do not serialize the host config in the json, otherwise we'll make the container unportable" (moby/daemon/container/container.go:105) from the code. Every later state change is checkpointed twice, to disk and into an in-memory go-memdb replica that answers docker ps without taking container locks (container/container.go:225-238).

One CLI flag writes more than JSON. After create, --use-api-socket copies a config.json holding the user's resolved registry credentials to /run/secrets/docker/config.json in the writable layer (cli/cli/command/container/create.go:244-310). The comment there admits it: "This can leave around the config if the container doesn't get deleted" (create.go:268-269; finding D8, class D) from the code.

Start, under one lock

containerStart runs under the container lock: mount the read-write layer, set up the network sandbox and mounts, createSpec, ReplaceContainer in containerd, NewTask (shim plus runc create), initializeCreatedTask (network into the new netns), tsk.Start (runc start), SetRunning, health monitor, checkpoint, start event (moby/daemon/start.go:82-271) from the code.

The OCI spec is not stored at create. It is regenerated on every start: oci.DefaultSpec() plus about seventeen SpecOpts in a fixed order, from cgroups through namespaces, capabilities, seccomp and mounts to the masked paths (moby/daemon/oci_linux.go:1024-1079) from the code. So a daemon upgrade changes the sandbox of an existing container the next time it starts reconstruction. Figure 3 lists what that spec takes away, who applies each part, and what the same files read on this sandbox, which is itself a container.

Defaults worth knowing

Since docker-v29.5.0 the default namespace list includes a private time namespace (moby/daemon/pkg/oci/defaults.go:117-124; commit d5370d34d3, 7 April 2026), dropped on kernels older than 5.6 or with the daemon feature "time-namespaces": false. Tools that compare /proc/<pid>/ns/time, or run nsenter without -T, now see a new namespace (finding D17, class E) from the code. The 14 capabilities are CHOWN, DAC_OVERRIDE, FSETID, FOWNER, MKNOD, NET_RAW, SETGID, SETUID, SETFCAP, SETPCAP, NET_BIND_SERVICE, SYS_CHROOT, KILL and AUDIT_WRITE, in the bounding, permitted and effective sets only (moby/daemon/pkg/oci/caps/defaults.go:4-21). For a private network namespace dockerd also sets net.ipv4.ip_unprivileged_port_start to 0, so ports below 1024 bind without CAP_NET_BIND_SERVICE (oci_linux.go:753-775). Seccomp is inlined into the spec, and not applied at all for --privileged unless a profile is given (moby/daemon/seccomp_linux.go:19-58) from the code.

--init is a spec rewrite, and only for a private PID namespace, moby/daemon/oci_linux.go:731-745 from the code:

		path, err := daemonCfg.LookupInitPath() // this will fall back to DefaultInitBinary and return an absolute path

		}
		s.Mounts = append(s.Mounts, specs.Mount{
			Destination: inContainerInitPath,

	}

The binary bind-mounted read-only at /sbin/docker-init is tini: the installed /usr/libexec/docker/docker-init --version prints tini version 0.19.0 - git.de40ad0 measured here. Without it, sh is PID 1, which per pid_namespaces(7) gets only the signals it has handlers for reconstruction. The CLI sends "Init":true only when the flag is given, and null otherwise so the daemon's own default applies (cli/cli/command/container/opts.go:724-727) from the code.

04containerd, the shim and a protobuf on stdin

dockerd does not run containers. It asks containerd to, through libcontainerd/remote, a thin wrapper over the containerd Go client (v2.4.2 is vendored), always in the containerd namespace moby (moby/daemon/daemon.go:1052-1066) from the code. Which containerd it talks to is decided once, at daemon start, moby/daemon/command/daemon_unix.go:132-149 from the code: 

func (cli *daemonCLI) initContainerd(ctx context.Context) (func(time.Duration) error, error) {
	// Check embedded-containerd first so daemon.json can opt in even when
	// packaged service units pass a default --containerd socket.
	if cli.Config.Features["embedded-containerd"] {
		return cli.initEmbeddedContainerd(ctx)
	}
	if cli.Config.ContainerdAddr != "" {
		// use system containerd at the given address.
		return nopWaitFunc, nil
	}

	waitTimeout, err := cli.initializeContainerd(ctx)
	if errors.Is(err, exec.ErrNotFound) {
		log.G(ctx).WithError(err).Info("containerd binary not found, starting embedded containerd")
		return cli.initEmbeddedContainerd(ctx)
	}
	return waitTimeout, err
}

The two embedded branches are new. The experimental feature arrived in 29.7.0 (a8a1cfd111); the automatic fallback when the binary is missing, no system containerd runs and no address is set arrived in 29.8.0 (b25f366ced). Packaged installs never hit it, because contrib/init/systemd/docker.service:15 starts dockerd -H fd:// --containerd=/run/containerd/containerd.sock. A hand-started dockerd can. It then registers a smaller plugin set (no CRI, sandbox, streaming, transfer, NRI or restart monitor), and docker info shows nothing: the warning is gated on the feature flag the fallback never sets, and even Containerd.Address is the same path a supervised daemon would use (moby/daemon/info.go:255-268; finding D7, class D) from the code. Embedded mode still runs separate shims and still serves a real ttrpc socket for their events (moby/daemon/internal/containerd/server/embedded/server.go:87-90) from the code.

A container with no rootfs

At start, ReplaceContainer creates the containerd container object, deleting any stale one with the same ID first (moby/daemon/internal/libcontainerd/replace.go:17-60). It carries the OCI spec, the runtime name and options, and a label com.docker/engine.bundle.path, but no snapshot key, so containerd never mounts the root filesystem for Docker. dockerd mounted it already and put the absolute path in the spec (libcontainerd/remote/client.go:119-146) from the code. I/O is named FIFOs in /var/run/docker/containerd/<id>/, named after the process: for the container's own process <id>-stdin, <id>-stdout, and <id>-stderr only without a TTY (libcontainerd/remote/client.go:218; client_linux.go:92-120).

containerd's task manager writes the bundle first, /run/containerd/io.containerd.runtime.v2.task/moby/<id>/ with config.json, then starts the shim, then calls its Create (containerd/core/runtime/v2/task_manager.go:158-200). The runtime name io.containerd.runc.v2 becomes the binary containerd-shim-runc-v2 (containerd/pkg/shim/util.go:41-49) from the code.

The shim starts twice

containerd launches the shim in its own process group with GOMAXPROCS=2, TTRPC_ADDRESS, GRPC_ADDRESS and NAMESPACE in its environment:

containerd-shim-runc-v2 -namespace moby -address <containerd.sock> \
    -publish-binary <containerd> -id <id> [-bundle <bundle>] start

Since containerd v2.3.0 it also writes a protobuf BootstrapParams message to the shim's stdin (containerd/core/runtime/v2/command.go:67-158) from the code. That start process is only a launcher. It re-execs itself without the action as the long-lived server, with GOMAXPROCS=4 and its own process group, hands it a listening socket, writes the answer to stdout and exits, containerd/cmd/containerd-shim-runc-v2/manager/manager_linux.go:188-190, 253, 296-297 from the code: 

	var params bootapi.BootstrapResult
	params.Version = 3
	params.Protocol = "ttrpc"
…
	if err := cmd.Start(); err != nil {
…
	params.Address = sockets[0].addr
	return &params, nil

The address is a hash. containerd/pkg/shim/util_unix.go:82-87 joins containerd's socket path, the namespace and the container ID and takes the sha256: d := sha256.Sum256([]byte(path)), then fmt.Sprintf("unix://%s/%x", socketRoot, d) with the root /run/containerd/s. For the ID in the trace, 4f1c0ffee000…, that gives the following, computed from the code and not observed reconstruction:

unix:///run/containerd/s/3cbd891cf0891a016d6a3084ea8be730eb173321caf9b4c613b53c828d5e8bb0

containerd saves that address in the bundle as bootstrap.json, so a restarted containerd can find running shims again (containerd/core/runtime/v2/binary.go:124-142). Calls go down on the ttrpc service containerd.task.v3.Task, whose proto calls the shim "the parent of each container" (containerd/api/runtime/task/v3/shim.proto:29-32) from the code. The shim then makes that true with PR_SET_CHILD_SUBREAPER. Its Create runs runc through go-runc, with runc's state under Docker's exec root, and waits for it to exit (process/init.go:82-94, 110-151):

runc --root /var/run/docker/runtime-runc/moby --log <bundle>/log.json --log-format json \
    create --bundle <bundle> --pid-file <bundle>/init.pid --console-socket <tmp.sock> <id>

With -t no pipes are made: runc's init allocates the pty inside the container and sends the master fd back over the console socket with SCM_RIGHTS, and the shim pumps master and FIFOs with an epoll copier (process/init.go:110-168) from the code.

Exit codes, and who computes them

Failures on this path come back as exit codes, and Figure 5 shows that three different places compute them. Two of them compare error text. The CLI's toStatusError maps "executable file not found" or "no such file or directory" to 127 and EACCES or EISDIR text to 126 (cli/cli/command/container/run.go:326-356). The daemon appends EACCES text to an EISDIR error "because docker/cli checks whether the error message contains syscall.EACCESS.Error()" and maps ENOTDIR, a file bind-mounted onto a directory, to 127 "command not found" (moby/daemon/errors.go:136-157; findings D1 and D2, class D) from the code.

05runc init: namespaces from a C constructor

runc create runs the full container setup and then detaches; it enters the same startContainer path as runc run with the action CT_ACT_CREATE (runc/create.go:59-70) from the code. The interesting work happens in a child that runc spawns by re-executing itself as runc init. Three things are prepared before that child exists.

First, the binary. runc never lets the container see its own executable. If /proc/self/exe is not already a sealed copy, exeseal.CloneSelfExe makes one, and init is executed through /proc/self/fd/N (runc/libcontainer/container_linux.go:507-530). The preferred seal is a detached, read-only overlayfs view; a sealed memfd copy is the fallback, priced in the code at "around ~60% overhead during container startup" (exeseal/cloned_binary_linux.go:229) from the code. The defence dates from CVE-2019-5736, where a container could overwrite the host's runc through /proc/self/exe. Second, file descriptors: before cmd.Start() runc marks every fd from 3 up close-on-exec "as some additional protection against attacks like CVE-2024-21626" (container_linux.go:341-349). Only the deliberate ExtraFiles reach the child, each named by an environment variable: _LIBCONTAINER_INITPIPE, _LIBCONTAINER_SYNCPIPE, _LIBCONTAINER_LOGPIPE and, for -t, _LIBCONTAINER_CONSOLE (container_linux.go:547-575) from the code.

Third, the cgroup. The parent puts the child into the container's cgroup before it sends a single byte of configuration, so every descendant is born inside it, runc/libcontainer/process_linux.go:824-827, 849 from the code: 

	// Do this before syncing with child so that no children can escape the
	// cgroup. We don't need to worry about not doing this and not being root
	// because we'd be using the rootless cgroup manager in that case.
	if err := p.manager.Apply(p.pid()); err != nil {
…
	if _, err := io.Copy(p.comm.initSockParent, p.bootstrapData); err != nil {

40 bytes of netlink

bootstrapData is a hand-rolled netlink message, not JSON. Its type is InitMsg uint16 = 62000 and its attributes are numbered 27281 to 27290 (clone flags, namespace paths, uid and gid maps, setgroups, oom_score_adj, rootless, the newuidmap paths, time offsets), numbers "randomly chosen to not conflict" (runc/libcontainer/message_linux.go:11-25). An unknown attribute is fatal on the C side (nsenter/nsexec.c:374-451) from the code. For a default Docker container only three attributes are present, and the whole message is 40 bytes. Figure 6 shows them. They were computed from the code, not captured from a live runc reconstruction.

Three stages, all before main

The receiver is C because these namespace operations "require single-threaded program execution" (runc/libcontainer/nsenter/nsenter.go:3-7), which a running Go runtime cannot promise. So the package is a cgo constructor that runs before Go boots, nsenter.go:10-17 from the code: 

/*
#cgo CFLAGS: -Wall
extern void nsexec();
void __attribute__((constructor)) init(void) {
	nsexec();
}
*/
import "C"

Every runc invocation runs it, and it returns at once unless _LIBCONTAINER_INITPIPE is set (nsexec.c:743-747). In runc init it becomes a state machine built on setjmp and longjmp: clone_parent() calls clone(child_func, ca.stack_ptr, CLONE_PARENT | SIGCHLD, &ca) and the child jumps back into the same switch with the next stage number (nsexec.c:314-323). CLONE_PARENT makes each new stage a sibling, a child of runc create, not of the stage that cloned it from the code. Figure 7 follows the stages for Docker's default spec.

The second clone exists because unshare(CLONE_NEWPID) does not move the caller; only its children enter the new PID namespace (nsexec.c:1122-1134). The other namespaces come from one unshare(config.cloneflags), not clone flags, partly because clone(CLONE_PARENT|CLONE_NEWPID) was broken on kernels up to 3.12. A user namespace, when present, is unshared alone and first so stage-0 can write its maps from the code. Stage-2 then calls setsid(), setuid(0) and setgid(0) and returns from the constructor, so the Go runtime boots inside every new namespace, locked to one thread with GOMAXPROCS(1) (init_linux.go:106-123) from the code.

After Go starts: an order shaped by CVEs

Go-side init runs a fixed sequence (standard_init_linux.go:51-304): keyring, network, rootfs, console, hostname, AppArmor, sysctls, read-only and masked paths, seccomp, capabilities and user, LookPath, the FIFO wait (§06), execve. The rootfs step makes / recursively slave, bind-mounts the rootfs onto itself and pivots, runc/libcontainer/rootfs_linux.go:1159-1166, 1173, 1182-1188 from the code: 

	// Change to the new root so that the pivot_root actually acts on it.
	if err := unix.Fchdir(int(root.Fd())); err != nil {
		return &os.PathError{Op: "chdir", Path: root.Name(), Err: err}
	}

	if err := unix.PivotRoot(".", "."); err != nil {
		return &os.PathError{Op: "pivot_root", Path: ".", Err: err}
	}
…
	if err := unix.Fchdir(oldroot); err != nil {
…
	if err := mount("", ".", "", unix.MS_SLAVE|unix.MS_REC, ""); err != nil {
		return err
	}
	// Perform the unmount. MNT_DETACH allows us to unmount /proc/self/cwd.
	if err := unmount(".", unix.MNT_DETACH); err != nil {
		return err

New root and old root on the same directory, then a lazy detach: no temporary directory inside the rootfs is needed. Masked files get the container's own /dev/null, opened O_PATH and inode-checked as char 1:3 before it is mounted by fd. That check is the fix for CVE-2025-31133, where a symlinked /dev/null turned a mask into a read-write bind (rootfs_linux.go:1318-1330) from the code. runc also appends its own device rules, including "mknod any char/block device", which no user can remove; its own comment calls this "questionable" (specconv/spec_linux.go:225; finding D13, class D).

Seccomp placement depends on no_new_privs. Without it, loading a filter needs CAP_SYS_ADMIN, so the filter goes in before capabilities are dropped, and Docker sets noNewPrivileges only when asked. A tight custom profile must therefore allow the syscalls runc init itself makes afterwards (standard_init_linux.go:188-200, 234-248; finding D14) from the code. runc loads the program itself, after prepending a stub that returns -ENOSYS for syscalls newer than the profile (seccomp/patchbpf/enosys_linux.go:627-650). Docker's profile is 926 lines, 14,122 bytes, 426 syscall names and 361 unconditional allows; clone3 gets errno 38 (ENOSYS) rather than EPERM, so glibc falls back to clone, whose namespace flags are filtered measured here. Unconditional socketcall(2) plus x86_64's 32-bit sub-arch sidesteps the AF_ALG and AF_VSOCK socket() block when no LSM backs it (D15, class D); the docs call clock_adjtime blocked, yet the profile allows it (D16, class C).

Immediately before execve init closes every fd from 3 + PassedFilesCount up, the core CVE-2024-21626 defence. That CVE leaked a handle to the host's /sys/fs/cgroup into init. 1.5.2 also re-marks fds close-on-exec in finalizeNamespace and rejects a cwd outside the container with verifyCwd (init_linux.go:271-306). runc exec and create arm AppArmor at different points (after finalizeNamespace versus before the masks), but both only write an on-exec profile (aa_change_onexec), so confinement is identical from execve on (apparmor_linux.go:52-68; D18, class D; runc#5362 would unify it) from the code.

06The FIFO between create and start

The OCI runtime spec splits a container's birth in two. At create, "the user-specified program … MUST NOT be run at this time"; start runs it, and starting a container that is not created "MUST generate an error" (runtime-spec/runtime.md:60, 127) from the code. runc implements the gap with one named pipe. Its state directory holds state.json and exec.fifo; under Docker that directory is /var/run/docker/runtime-runc/moby/<id>/, because the shim passes --root with the namespace appended (runc/libcontainer/factory_linux.go:21-22; containerd/cmd/containerd-shim-runc-v2/process/init.go:82-94).

runc creates the FIFO mode 0622 and chowns it to the container's host-side root, so an init inside a user namespace can still write it (container_linux.go:447-471). It hands the FIFO to init only as an O_PATH file descriptor named by _LIBCONTAINER_FIFOFD, so the container never holds a usable handle on the state directory (container_linux.go:478-494) from the code. At the very end of setup, init re-opens it for writing, runc/libcontainer/standard_init_linux.go:260-271, 300-303 from the code: 

	// Wait for the FIFO to be opened on the other side before exec-ing the
	// user process. We open it through /proc/self/fd/$fd, because the fd that
	// was given to us was an O_PATH fd to the fifo itself. Linux allows us to
	// re-open an O_PATH fd through /proc.
	fifoFile, err := pathrs.Reopen(l.fifoFile, unix.O_WRONLY|unix.O_CLOEXEC)
	if err != nil {
		return fmt.Errorf("reopen exec fifo: %w", err)
	}
	defer fifoFile.Close()
	if _, err := fifoFile.Write([]byte("0")); err != nil {
		return &os.PathError{Op: "write exec fifo", Path: fifoFile.Name(), Err: err}
	}
…
	if err := utils.UnsafeCloseFrom(l.config.PassedFilesCount + 3); err != nil {
		return err
	}
	return linux.Exec(name, l.config.Args, l.config.Env)

Opening a FIFO for writing blocks until something opens it for reading. That open is the whole barrier. Everything before it, namespaces, mounts, the pivot, seccomp and capabilities, belongs to create. Just before it, init calls exec.LookPath(l.config.Args[0]), "to make sure it exists and it is returned as a create time error" (standard_init_linux.go:227-232). It also checks that its parent is still the runc process that started it, and kills itself with SIGKILL if that parent died mid-setup (standard_init_linux.go:220-226) from the code. Figure 8 lays the barrier out in time.

What dockerd does in the gap

After NewTask returns the init pid, dockerd points the libnetwork sandbox at that process's network namespace, moby/daemon/start_linux.go:27-36 from the code: 

nspath, ok := oci.NamespacePath(spec, specs.NetworkNamespace)
if ok && nspath == "" { // the runtime has been instructed to create a new network namespace for tsk.
	sb, err := daemon.netController.GetSandbox(ctr.ID)
	if err != nil {
		return errdefs.System(err)
	}
	if err := sb.SetKey(ctx, fmt.Sprintf("/proc/%d/ns/net", tsk.Pid())); err != nil {
		return errdefs.System(err)
	}
}

Endpoints are then allocated inside it. No OCI prestart hook is involved. That was not always true: the SetKey hook was removed in v26.0.0 (0046b16d87), restored in v26.1.0 (fde80fe2e7) and removed again (933fcc9814, May 2024) from the code. The veth, bridge and NAT rules that land in that namespace are Part 4's subject.

runc start is then almost nothing. It refuses any state but Created and calls container.Exec() (runc/start.go:33-52). In v1.5.2 that is a goroutine doing a blocking open(exec.fifo, O_RDONLY), checking every 100 ms whether init has died; on success it reads the byte and deletes the FIFO (container_linux.go:233-265, 288-302). Init's write returns, it closes every fd from 3 + PassedFilesCount up, and execve replaces runc init with sh in the same pid from the code. After the pin, runc main swapped the open-poll for handleFifo with poll(2) and a pidfd, and moved poststart hooks from create to start; neither is in v1.5.2 (finding D22, class E) from the code.

07Exit, and what survives dockerd

When sh exits, the kernel tells its parent, and its parent is the shim. On SIGCHLD the shim's reaper calls wait4(-1, …, WNOHANG) (containerd/pkg/sys/reaper/reaper_unix.go:258-266) and turns a signal death into 128 + signal via exitSignalOffset = 128 (reaper_unix.go:280-289), so SIGKILL is 137 and SIGTERM 143. Docker did not invent those numbers; the shim computes them from the code. From there the status climbs three protocols to reach the CLI. Figure 9 is the whole climb.

The shim publishes last

For an init exit the shim first kills any remaining processes if the PID namespace is shared, waits until every running exec has reported, then records the status and only then publishes, containerd/cmd/containerd-shim-runc-v2/task/service.go:769-791 from the code: 

if isInit {
	e.Timestamp = p.ExitedAt()
	if err := runc.WriteExitStatus(c.Bundle, e); err != nil {
		log.G(s.context).
			WithField("container_id", c.ID).
			WithError(err).
			Error("failed to store exit status in bundle")
	}

	if err := s.cg2oom.Stop(c.ID); err != nil {
		log.G(context.Background()).
			WithField("container_id", c.ID).
			WithError(err).
			Error("failed to stop oom event watcher")
	}
}
s.send(&eventstypes.TaskExit{
	ContainerID: c.ID,
	ID:          p.ID(),
	Pid:         uint32(e.Pid),
	ExitStatus:  uint32(e.Status),
	ExitedAt:    protobuf.ToTimestamp(p.ExitedAt()),
})

Recording the status in the bundle is new in containerd 2.4.0 (3264a09df). It makes the second, shim delete-generated exit carry the recorded status instead of 137, but containerd still publishes that second exit when a shim disconnects before task delete (cleanupAfterDeadShim, core/runtime/v2/shim.go:146-196); the 128+SIGKILL fallback now applies only to a lost process with no recorded status (manager_linux.go:360-364). moby still carries its own duplicate-exit filter, shouldIgnoreExitEventWithLock, citing moby#46212 (moby/daemon/monitor.go:54-55; finding D11, class E) from the code. It is still needed on 2.4: duplicates still arrive, and its state checks also stop a late exit from a previous run hitting a restarted container (monitor.go:359-440). The event goes up as a ttrpc Events.Forward call to <grpc address>.ttrpc, from a queue of queueSize = 2048 with maxRequeue = 5 (containerd/pkg/shim/publisher.go:36-37) from the code.

dockerd's side

dockerd holds one containerd event subscription per namespace, filtered to task topics, and re-subscribes if the stream breaks (libcontainerd/remote/client.go:595-628). Events go through a per-container serial queue, so one container's exits are handled in order (client.go:640-698). handleContainerExit drops duplicates, stops health checks, calls containerd Delete on the task, waits for stdio to drain with context.WithTimeout(context.Background(), 2*time.Second), asks the restart manager, then sets restarting or exited, checkpoints and emits die (moby/daemon/monitor.go:35-147) from the code. Output still in the FIFOs after two seconds may never reach an attached client (D5, class D, not measured). A TaskOOM event only sets OOMKilled; the exit still comes as a normal TaskExit. A start that died during network setup keeps the container created, detected by strings.Contains(c.State.ErrorMsg, errSetupNetworking) (monitor.go:48; D9, class D). --rm is the daemon's AutoRemove; the CLI only waits with condition=removed from the code.

Exec exits take another road

docker exec -it has no wait endpoint. The CLI creates the exec with POST /containers/{id}/exec, hijacks POST /exec/{execid}/start exactly like attach, and after the stream ends reads ExitCode from GET /exec/{execid}/json (cli/cli/command/container/exec.go:88-130, 204-218) from the code. Against the mock, which answered "ExitCode": 3, the real CLI exited 3 measured here. In the daemon the exec becomes task.Exec, and the shim runs runc exec --process <json> --detach, which takes the same nsexec path with clone flags 0 and only joins the container's namespaces (containerd/cmd/containerd-shim-runc-v2/process/exec.go:181-215). Exec exits are never the container's last word: the shim holds back init's TaskExit until running execs have reported, and dockerd handles both in the same per-container queue (task/service.go:745-764) from the code.

Killing dockerd

Because sh is the shim's child, kill -9 on dockerd leaves it running. On the next start, restore reloads each container from disk, loads it in containerd and re-attaches to its existing FIFOs (moby/daemon/daemon.go:453). Then, without live-restore, it does the surprising thing: it logs "shutting down container considered alive by containerd" and stops it (daemon.go:475). A container whose task vanished is marked stopped with exit code 255 (daemon.go:528; finding D6, class D) from the code. So containers outlive a dockerd crash, but by default not the next dockerd start reconstruction.

With "live-restore": true the shutdown path skips stopping running containers and leaves mounts and networking in place for the next daemon to adopt; it is rejected in swarm mode (daemon.go:1553-1564; config/config_linux.go:130-133) from the code. While no dockerd reads the FIFOs, a chatty container can write only until the pipe buffer fills, then blocks until dockerd re-attaches reconstruction. Docker's live-restore page still says upgrades are supported only between "patch releases (YY.MM.x)", a version scheme Engine left at 23.0 (finding D12, class C).

08Reading a real container from the inside

No Docker container ran for this teardown, but one container was always available: the research sandbox itself. It is a Kubernetes pod on containerd, not a Docker container, so its choices are Kubernetes' choices. The mechanics are the same ones §03 and §05 read in the code, and they can be read back from /proc and /sys/fs/cgroup without any privilege. The bounding set 0xa80425fb decodes to exactly Docker's fourteen default capabilities, the same list moby/daemon/pkg/oci/caps/defaults.go:4-21 gives. The permitted and effective sets are empty because the shell runs as uid 1000, but not because of the setuid: runc keeps the capabilities across it (PR_SET_KEEPCAPS) and re-applies them. The spec has no ambient set (CRI strips it) and /bin/sh has no file capabilities, so the execve transformation leaves permitted and effective empty (capabilities(7)) from the code. Six namespaces are private. Time and user are not: their inodes are the kernel's initial ones, and the uid_map is the identity 0 0 4294967295. The identity map alone would not prove that, since a non-initial user namespace can carry the full identity map; the initial inode is the decisive part. So this sandbox has no private time namespace, which Docker would have given it since 29.5 (§03). There is no seccomp filter, Kubernetes' default "Unconfined", unlike Docker's default profile, but the process is AppArmor-confined as cri-containerd.apparmor.d (enforce) measured here.

The mount table shows runc's mask and read-only mechanics directly. These lines from /proc/self/mountinfo are abridged with … measured here:
