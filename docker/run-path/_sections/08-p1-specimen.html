{{S}}Reading a real container from the inside

No Docker container ran for this teardown, but one container was always available: the research sandbox itself. It is a Kubernetes pod on containerd, not a Docker container, so its choices are Kubernetes' choices. The mechanics are the same ones §03 and §05 read in the code, and they can be read back from /proc and /sys/fs/cgroup without any privilege. Everything below was read on 23 October 2026 measured here; the annotations on the right are mine. 

$ grep -E "^(…|Cap|NoNewPrivs|Seccomp|…)" /proc/self/status     # abridged
CapEff:	0000000000000000                         uid 1000: nothing effective
CapBnd:	00000000a80425fb                         bits 0,1,3-8,10,13,18,27,29,31
NoNewPrivs:	0
Seccomp:	0                                       no filter at all
$ ls -l /proc/self/ns                            # abridged
cgroup -> cgroup:[4026533018]                    private
pid -> pid:[4026533017]                          private (so are ipc, mnt, net, uts)
time -> time:[4026531834]                        0xeffffffa: the initial time ns
user -> user:[4026531837]                        0xeffffffd: the initial user ns
$ cat /proc/self/cgroup
0::/                                             private cgroupns: own cgroup is "/"
$ cat /sys/fs/cgroup/cpu.max
200000 100000                                    2 CPUs of quota per period
$ cat /sys/fs/cgroup/memory.max
8589934592                                       8 GiB

The bounding set 0xa80425fb decodes to exactly Docker's fourteen default capabilities, the same list moby/daemon/pkg/oci/caps/defaults.go:4-21 gives. The permitted and effective sets are empty because the shell runs as uid 1000, but not because of the setuid: runc keeps the capabilities across it (PR_SET_KEEPCAPS) and re-applies them. The spec has no ambient set (CRI strips it) and /bin/sh has no file capabilities, so the execve transformation leaves permitted and effective empty (capabilities(7)) from the code. Six namespaces are private. Time and user are not: their inodes are the kernel's initial ones, and the uid_map is the identity 0 0 4294967295. The identity map alone would not prove that, since a non-initial user namespace can carry the full identity map; the initial inode is the decisive part. So this sandbox has no private time namespace, which Docker would have given it since 29.5 (§03). There is no seccomp filter, Kubernetes' default "Unconfined", unlike Docker's default profile, but the process is AppArmor-confined as cri-containerd.apparmor.d (enforce) measured here.

The mount table shows runc's mask and read-only mechanics directly. These lines from /proc/self/mountinfo are abridged with … measured here: 

2513 3701 0:444 /bus /proc/bus ro,…  - proc proc rw     read-only sub-bind of the one proc mount
2519 3701 0:452 /null /proc/interrupts … - tmpfs …     /dev's tmpfs file "null" bound over it
2518 3701 0:455 / /proc/acpi ro,relatime - tmpfs tmpfs ro     a masked dir: its own ro tmpfs
3706 3705 0:28 / /sys/fs/cgroup ro,… - cgroup2 cgroup rw     read-only at the mount, rw superblock

/proc/{interrupts,kcore,keys,timer_list} are all binds of /null from the container's own /dev tmpfs (device 0:452). /proc/acpi, /proc/scsi and /sys/firmware are three separate tmpfs instances, so this node's runtime does not share one mask tmpfs: it is runc older than 1.5.0-rc.3, or not runc at all reconstruction. The root is an overlay mount with 23 lowerdirs under /var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/ and upper directory 619, the layer shape Part 2 builds. The cgroup files show live counters too: memory.oom.group is 1, and memory.events read max 1499 with oom_kill 0 at that moment, so the limit was hit often but nothing was killed measured here.
