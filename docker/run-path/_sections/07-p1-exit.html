{{S}}Exit, and what survives dockerd

When sh exits, the kernel tells its parent, and its parent is the shim. On SIGCHLD the shim's reaper calls wait4(-1, …, WNOHANG) (containerd/pkg/sys/reaper/reaper_unix.go:258-266) and turns a signal death into 128 + signal via exitSignalOffset = 128 (reaper_unix.go:280-289), so SIGKILL is 137 and SIGTERM 143. Docker did not invent those numbers; the shim computes them from the code. From there the status climbs three protocols to reach the CLI. Figure {{fig-exit-cascade}} is the whole climb.

The shim publishes last

For an init exit the shim first kills any remaining processes if the PID namespace is shared, waits until every running exec has reported, then records the status and only then publishes, containerd/cmd/containerd-shim-runc-v2/task/service.go:769-791 from the code: 

if isInit {
	e.Timestamp = p.ExitedAt()
	if err := runc.WriteExitStatus(c.Bundle, e); err != nil {
		log.G(s.context).
			WithField("container_id", c.ID).
			WithError(err).
			Error("failed to store exit status in bundle")
	}

	if err := s.cg2oom.Stop(c.ID); err != nil {
		log.G(context.Background()).
			WithField("container_id", c.ID).
			WithError(err).
			Error("failed to stop oom event watcher")
	}
}
s.send(&eventstypes.TaskExit{
	ContainerID: c.ID,
	ID:          p.ID(),
	Pid:         uint32(e.Pid),
	ExitStatus:  uint32(e.Status),
	ExitedAt:    protobuf.ToTimestamp(p.ExitedAt()),
})

Recording the status in the bundle is new in containerd 2.4.0 (3264a09df). It makes the second, shim delete-generated exit carry the recorded status instead of 137, but containerd still publishes that second exit when a shim disconnects before task delete (cleanupAfterDeadShim, core/runtime/v2/shim.go:146-196); the 128+SIGKILL fallback now applies only to a lost process with no recorded status (manager_linux.go:360-364). moby still carries its own duplicate-exit filter, shouldIgnoreExitEventWithLock, citing moby#46212 (moby/daemon/monitor.go:54-55; finding D11, class E) from the code. It is still needed on 2.4: duplicates still arrive, and its state checks also stop a late exit from a previous run hitting a restarted container (monitor.go:359-440). The event goes up as a ttrpc Events.Forward call to <grpc address>.ttrpc, from a queue of queueSize = 2048 with maxRequeue = 5 (containerd/pkg/shim/publisher.go:36-37) from the code.

dockerd's side

dockerd holds one containerd event subscription per namespace, filtered to task topics, and re-subscribes if the stream breaks (libcontainerd/remote/client.go:595-628). Events go through a per-container serial queue, so one container's exits are handled in order (client.go:640-698). handleContainerExit drops duplicates, stops health checks, calls containerd Delete on the task, waits for stdio to drain with context.WithTimeout(context.Background(), 2*time.Second), asks the restart manager, then sets restarting or exited, checkpoints and emits die (moby/daemon/monitor.go:35-147) from the code. Output still in the FIFOs after two seconds may never reach an attached client (D5, class D, not measured). A TaskOOM event only sets OOMKilled; the exit still comes as a normal TaskExit. A start that died during network setup keeps the container created, detected by strings.Contains(c.State.ErrorMsg, errSetupNetworking) (monitor.go:48; D9, class D). --rm is the daemon's AutoRemove; the CLI only waits with condition=removed from the code.

Exec exits take another road

docker exec -it has no wait endpoint. The CLI creates the exec with POST /containers/{id}/exec, hijacks POST /exec/{execid}/start exactly like attach, and after the stream ends reads ExitCode from GET /exec/{execid}/json (cli/cli/command/container/exec.go:88-130, 204-218) from the code. Against the mock, which answered "ExitCode": 3, the real CLI exited 3 measured here. In the daemon the exec becomes task.Exec, and the shim runs runc exec --process <json> --detach, which takes the same nsexec path with clone flags 0 and only joins the container's namespaces (containerd/cmd/containerd-shim-runc-v2/process/exec.go:181-215). Exec exits are never the container's last word: the shim holds back init's TaskExit until running execs have reported, and dockerd handles both in the same per-container queue (task/service.go:745-764) from the code.

Killing dockerd

Because sh is the shim's child, kill -9 on dockerd leaves it running. On the next start, restore reloads each container from disk, loads it in containerd and re-attaches to its existing FIFOs (moby/daemon/daemon.go:453). Then, without live-restore, it does the surprising thing: it logs "shutting down container considered alive by containerd" and stops it (daemon.go:475). A container whose task vanished is marked stopped with exit code 255 (daemon.go:528; finding D6, class D) from the code. So containers outlive a dockerd crash, but by default not the next dockerd start reconstruction.

With "live-restore": true the shutdown path skips stopping running containers and leaves mounts and networking in place for the next daemon to adopt; it is rejected in swarm mode (daemon.go:1553-1564; config/config_linux.go:130-133) from the code. While no dockerd reads the FIFOs, a chatty container can write only until the pipe buffer fills, then blocks until dockerd re-attaches reconstruction. Docker's live-restore page still says upgrades are supported only between "patch releases (YY.MM.x)", a version scheme Engine left at 23.0 (finding D12, class C).
