{{S}}The FIFO between create and start

The OCI runtime spec splits a container's birth in two. At create, "the user-specified program … MUST NOT be run at this time"; start runs it, and starting a container that is not created "MUST generate an error" (runtime-spec/runtime.md:60, 127) from the code. runc implements the gap with one named pipe. Its state directory holds state.json and exec.fifo; under Docker that directory is /var/run/docker/runtime-runc/moby/<id>/, because the shim passes --root with the namespace appended (runc/libcontainer/factory_linux.go:21-22; containerd/cmd/containerd-shim-runc-v2/process/init.go:82-94).

runc creates the FIFO mode 0622 and chowns it to the container's host-side root, so an init inside a user namespace can still write it (container_linux.go:447-471). It hands the FIFO to init only as an O_PATH file descriptor named by _LIBCONTAINER_FIFOFD, so the container never holds a usable handle on the state directory (container_linux.go:478-494) from the code. At the very end of setup, init re-opens it for writing, runc/libcontainer/standard_init_linux.go:260-271, 300-303 from the code: 

	// Wait for the FIFO to be opened on the other side before exec-ing the
	// user process. We open it through /proc/self/fd/$fd, because the fd that
	// was given to us was an O_PATH fd to the fifo itself. Linux allows us to
	// re-open an O_PATH fd through /proc.
	fifoFile, err := pathrs.Reopen(l.fifoFile, unix.O_WRONLY|unix.O_CLOEXEC)
	if err != nil {
		return fmt.Errorf("reopen exec fifo: %w", err)
	}
	defer fifoFile.Close()
	if _, err := fifoFile.Write([]byte("0")); err != nil {
		return &os.PathError{Op: "write exec fifo", Path: fifoFile.Name(), Err: err}
	}

	if err := utils.UnsafeCloseFrom(l.config.PassedFilesCount + 3); err != nil {

	return linux.Exec(name, l.config.Args, l.config.Env)

Opening a FIFO for writing blocks until something opens it for reading. That open is the whole barrier. Everything before it, namespaces, mounts, the pivot, seccomp and capabilities, belongs to create. Just before it, init calls exec.LookPath(l.config.Args[0]), "to make sure it exists and it is returned as a create time error" (standard_init_linux.go:227-232). It also checks that its parent is still the runc process that started it, and kills itself with SIGKILL if that parent died mid-setup (standard_init_linux.go:220-226) from the code. What dockerd does in the gap

After NewTask returns the init pid, dockerd points the libnetwork sandbox at that process's network namespace, moby/daemon/start_linux.go:27-36 from the code: 

nspath, ok := oci.NamespacePath(spec, specs.NetworkNamespace)
if ok && nspath == "" { // the runtime has been instructed to create a new network namespace for tsk.
	sb, err := daemon.netController.GetSandbox(ctr.ID)
	if err != nil {
		return errdefs.System(err)
	}
	if err := sb.SetKey(ctx, fmt.Sprintf("/proc/%d/ns/net", tsk.Pid())); err != nil {
		return errdefs.System(err)
	}
}

Endpoints are then allocated inside it. No OCI prestart hook is involved. That was not always true: the SetKey hook was removed in v26.0.0 (0046b16d87), restored in v26.1.0 (fde80fe2e7) and removed again (933fcc9814, May 2024) from the code. The veth, bridge and NAT rules that land in that namespace are Part 4's subject.

runc start is then almost nothing. It refuses any state but Created and calls container.Exec() (runc/start.go:33-52). In v1.5.2 that is a goroutine doing a blocking open(exec.fifo, O_RDONLY), checking every 100 ms whether init has died; on success it reads the byte and deletes the FIFO (container_linux.go:233-265, 288-302). Init's write returns, it closes every fd from 3 + PassedFilesCount up, and execve replaces runc init with sh in the same pid from the code. After the pin, runc main swapped the open-poll for handleFifo with poll(2) and a pidfd, and moved poststart hooks from create to start; neither is in v1.5.2 (finding D22, class E) from the code.
