01BuildKit never runs your Dockerfile

A container is an ordinary Linux process, and Docker is a relay of programs that agree on names made of sha256 hashes. A build adds two more names to that relay and one more compiler. BuildKit never executes a Dockerfile. It compiles the text into LLB, a graph of protobuf records, each named by the sha256 of its own bytes. It keys its cache on that graph and on file content, never on timestamps. And it asks the client for the build context; the client does not push it.

02From Dockerfile to LLB

A frontend is a compiler. Its input is a Dockerfile and a set of options; its output is an LLB definition the solver can run. Dockerfile2LLB works in three stages. parser.Parse turns bytes into an AST of Nodes. instructions.Parse turns the AST into typed Stages plus the global ARGs. A dispatch loop then turns each stage into an llb.State. An empty Dockerfile, or one with no stages, is an error (buildkit/frontend/dockerfile/dockerfile2llb/convert.go:236-279) from the code.

What the parser keeps

Each AST node keeps the instruction's value, its flags, any heredoc bodies, and the comment lines just above it as PrevComment, which only the linter reads. Every other comment is thrown away, including one inside a line continuation (parser/parser.go:31-42, 334-338). That one decision explains a cache behaviour in §04: editing a comment cannot change anything downstream, because no comment survives the parser. There are exactly three parser directives, syntax, escape and check. Scanning stops at the first line that is not a # comment of the form key=value with a known key, and a repeated directive is an error (parser/directives.go:14-24, 50-96). DetectSyntax also accepts // syntax= and a JSON {"syntax": …} form and skips a leading #!, so a file that is not a Dockerfile can pick its compiler the same way from the code.

What each instruction becomes

Most instructions produce no vertex at all. ENV, ARG, USER, LABEL, CMD, ENTRYPOINT, EXPOSE and the metadata part of WORKDIR only edit the state and the image config. ENV and ARG call State.AddEnv, so they reach the graph only through the Meta.env of later RUNs. Every instruction still appends a history entry to the image config, with EmptyLayer: true for the metadata-only ones (convert.go:1331-1344, 1708-1713, 1817-1829) from the code. The rest map one to one:

  • FROM image is resolved to a digest during compilation. ResolveImageConfig fetches the config, the reference is rewritten to name:tag@sha256:…, and the pinned reference becomes a docker-image:// SourceOp. A base whose config has no DiffIDs and no non-empty history becomes llb.Scratch() (convert.go:695-753).
  • RUN becomes an ExecOp whose root mount output is the next state. Shell form is prefixed with the image's SHELL or the OS default. A heredoc that starts with #! is written into a 0755 file by a scratch FileOp, mounted read-only under /dev/pipes/, and executed directly (convert.go:1360-1384, 1405-1508).
  • COPY and ADD become a FileOp copy action with CopyDirContentsOnly, FollowSymlinks, AllowWildcard, AllowEmptyWildcard and CreateDestPath set; ADD adds AttemptUnpack for local archives, and a URL or git source becomes its own SourceOp (convert_copy.go:180-293).

COPY --link takes a different shape. The copy goes onto an empty llb.Scratch() and the result is joined to the current state with a MergeOp, so the new layer does not depend on the layers below it. The condition is one line, convert_copy.go:337, and the two branches are :352-355: 

	if cfg.opt.llbCaps != nil && cfg.opt.llbCaps.Supports(pb.CapMergeOp) == nil && cfg.link && cfg.chmod == "" {
…
		d.state = d.state.WithOutput(llb.Merge([]llb.State{d.state, llb.Scratch().File(a, copyOpts...)}, mergeOpts...).Output())
	} else {
		d.state = d.state.File(a, fileOpt...)
	}

cfg.chmod == "" means a COPY --link --chmod=… silently becomes an ordinary copy. Meanwhile the Dockerfile reference suggests --chmod as one fix for directory modes under --link (frontend/dockerfile/docs/reference.md:2008-2014), and --link --chown=<name> is a hard error by contrast. This is register D51, class C (doc drift), still the same on BuildKit's master from the code.

Stages that never exist

Stage dependencies come from FROM <stage>, COPY --from and RUN --mount=from=. Cycles are rejected, and ONBUILD triggers are re-resolved in a loop because they can add edges (convert.go:518-586). The frontend then computes allReachableStages(target) and never dispatches any other stage unless AllStages is set; the default target is the last stage (convert.go:507-510, 589, 779-783). An unused stage is not skipped at run time. It never becomes LLB. Base images of every stage are resolved concurrently, one goroutine per stage, but only reachable stages fetch a config from the code. Nothing in the frontend schedules parallel work: independent stages are disjoint subgraphs of one DAG, and the solver runs independent edges at the same time (docs/dev/solver.md:225-232).

03LLB: a Merkle DAG of protobuf

LLB, BuildKit's low-level build format, is defined in one protobuf file, solver/pb/ops.proto. One Op is one vertex of the graph: a list of input edges, then exactly one of seven op kinds, then an optional platform and worker constraints. An input edge is not a pointer. It is the sha256 digest of the input op's marshaled bytes plus an output index (buildkit/solver/pb/ops.proto:10-25, 37-42) from the code: 

message Op {
	// changes to this structure must be represented in json.go.
	// inputs is a set of input edges.
	repeated Input inputs = 1;
	oneof op {
		ExecOp exec = 2;
		SourceOp source = 3;
		FileOp file = 4;
		BuildOp build = 5;
		MergeOp merge = 6;
		DiffOp diff = 7;
		PassthroughOp passthrough = 8;
	}
	Platform platform = 10;
	WorkerConstraints constraints = 11;
}
…
message Input {
	// digest of the marshaled input Op
	string digest = 1;
	// output index of the input Op
	int64 index = 2;
}

Naming each input by the hash of its bytes makes the graph a Merkle DAG, the same construction as an image (Part 2) or a git commit. The four kinds a Dockerfile uses are small. SourceOp is a URL-like identifier (local://, docker-image://, git://, https://) plus string attributes. FileOp is a chain of actions: copy, mkfile, mkdir, rm, symlink. ExecOp carries Meta (args, env, cwd, user, proxy env, extra hosts, hostname, ulimits, cgroup parent, valid exit codes), mounts, a network mode, a security mode, secret env vars and CDI devices. MergeOp and DiffOp let a build stack and subtract layers; Merge(A,B) lays B over A with B winning, and the docs call it associative (ops.proto:45-69, 196-203, 320-341; docs/dev/merge-diff.md:25-40) from the code.

A Definition, the thing a client sends in Solve, is a flat list of marshaled ops, a separate metadata map keyed by op digest, and a source map (ops.proto:309-318). Descriptions, the ignore-cache flag, progress groups and Dockerfile line numbers all live in the side maps, outside the hashed bytes. State.Marshal marshals inputs first, depth-first, so the list comes out in topological order with duplicates removed. It hashes each op with protobuf's deterministic mode, which sorts map keys (client/llb/marshal.go:167-169). Last it appends one op with no kind at all, whose single input points at the result. That terminal vertex is how the solver finds the root (client/llb/state.go:156-165) from the code.

alpine's three vertices, re-derived

A max provenance record embeds the whole definition as JSON, plus a digestMapping from each op's digest to a name like step1. alpine:latest's amd64 record holds three ops: a git SourceOp, a FileOp copy that reads the tarball out of that checkout, and the terminal op. JSON is not the hashed form, so the digests can only be checked by re-encoding. A 37-line Python script writes each op back as proto3 by hand (varint tags, length-prefixed strings, zero values omitted, map entries in key order) and hashes the result. All three digests match the published ones measured here:

Two versions of the script exist. The first takes each input digest from the published mapping, so it checks each vertex on its own. The second, llbdigest-chained.py, feeds each computed digest into the next op, so the match above checks the chain end to end. Both hard-code the six copy booleans as 1, which is what this record holds; a record with a false flag would need the encoder extended measured here. The bytes are short enough to read whole. The ripple in the right-hand column is the point. Because inputs are named by digest, editing one character of the root SourceOp changes the digest of every vertex downstream measured here. The reverse also holds, and it explains most of §04. Anything kept outside the op bytes cannot change a digest. Comments never reach LLB, and line numbers travel in the source map, so moving a Dockerfile line or editing a comment leaves every vertex digest as it was (parser/parser.go:334-338; ops.proto:309-318) from the code, reconstruction for the conclusion.

A vertex digest is still not a cache key. The solver uses it to merge identical work inside one run: two jobs that load the same digest share one state in Solver.actives, and the step runs once (solver/jobs.go:41-50, 547-611). But docker-image://alpine:latest means different bytes next week, so the solver's design doc says the digest is good only for deduplication during a run (docs/dev/solver.md:61-67) from the code. Persistent caching needs something else.

04The solver and the two cache keys

Take a small two-stage Dockerfile with a third stage nobody uses. Figure 3 draws the graph the frontend would emit for it and, on each vertex, the keys the solver would compute. The example is mine and was not built here; every mapping in it is read from the code cited in §02 and below reconstruction.

Edges, states and a scheduler

Every op implements CacheMap (how to key it), Exec (run it) and Acquire. CacheMap.Digest is the op's own checksum; each Deps[i] may add a Selector and a ComputeDigestFunc that keys input i by its content (buildkit/solver/types.go:169-249). Both calls run at most once per vertex, behind flightcontrol groups (solver/jobs.go:1164-1166, 1243-1250). One scheduler goroutine pops edges off a queue and calls edge.unpark; the real work runs in async functions connected to edges by "pipes" (solver/scheduler.go:61-96). Each edge moves through four states, declared in solver/edge.go:14-21 as edgeStatusInitial, edgeStatusCacheFast, edgeStatusCacheSlow and edgeStatusComplete. The solver raises an input's desired state only as far as the current edge needs from the code. So if one input already gives a definition-based match, the others are never content-hashed, and an image input is never pulled (docs/dev/solver.md:25-29). Layers are lazy anyway: the puller records a handle per layer at key time and fetches bytes only when a later step needs the snapshot (source/containerimage/pull.go:156-171). Figure 4 shows the two tiers.

The fast key: a scrubbed definition

A root key is sha256("<cacheMapDigest>@<output>") (solver/cachemanager.go:451-457). A key with dependencies is not a hash chain. It is a node in a link graph, found by following CacheInfoLink{Input, Output, Digest, Selector} edges out of each dependency's keys, and given a random ID when no link exists yet. The links persist in cache.db's four bbolt buckets, _result, _links, _byresult and _backlinks from the code. For an ExecOp, CacheMap hashes JSON {Type: "buildkit.exec.v0", Exec: op, OS, Arch, …} of a cleaned copy of the op (solver/llbsolver/ops/exec.go:114-132):

Proxy settings, --add-host IPs, mount selectors and a cache mount's custom id or non-default sharing all drop out (register D53, D54, both class D, intended). Separately, getMountDeps skips secret, SSH and tmpfs mounts, so a rotated secret value never invalidates a cached RUN (exec.go:297-303; D52, class D). A RUN mount gets a content key only when that is safe, with no output or read-only (exec.go:315-337) from the code. All three are unchanged on BuildKit's master.

The slow key: a tarsum without mtime

A FileOp copy's own digest keeps only the basename of each source. The full paths, with wildcard, include and exclude settings, become that input's Selector, and a ComputeDigestFunc content-hashes exactly those paths (ops/file.go:110-119, 160-180). A file's record starts as a tar header built from its stat, with the file bytes after it. The header is serialised in "V1 tarsum" order, which is the legacy v0 field list minus one field (buildkit/cache/contenthash/tarsum.go:60-67): 

// Copy all headers from v0 excluding the 'mtime' header (the 5th element).
v0headers := v0TarHeaderSelect(h)
orderedHeaders = append(orderedHeaders, v0headers[0:5]...)
orderedHeaders = append(orderedHeaders, v0headers[6:]...)

A directory hashes each child's key and digest in radix-tree order, several selectors are hashed in parallel, and the input's key is sha256 of their NUL-joined digests. When it is ready, edge.go:708-721 builds NewCacheKey(dgst, "", -1) and calls Cache().Query to link the definition keys to it from the code. That link is the payoff. The local context's own key includes the session ID, so [internal] load build context never matches across builds (source/local/source.go:129-162); a COPY hits only because identical bytes produce an identical content key. Mode, owner and xattrs count; mtime does not (D61, class D). Image sources key on {Digest: <manifest digest>, OS, Arch, …}. Since v0.34.0, commit 5cf302ff6, the config's DiffIDs are no longer an alternate key, because they are unverified at lookup and could poison the cache (source/containerimage/pull.go:62-84, 175-183; D62, class E). 05The context is pulled, not pushed

A client that sends a build might be expected to upload its directory. BuildKit reverses the direction: the client is the gRPC server. buildx registers a file-sync provider in its session, and BuildKit calls FileSync.DiffCopy (or the older TarStream) back into it, both bidirectional streams of fsutil.types.Packet (buildkit/session/filesync/filesync.proto:10-13). What to send travels as gRPC metadata on that call, under four keys (session/filesync/filesync.go:25-30) from the code: 

const (
	keyIncludePatterns    = "include-patterns"
	keyExcludePatterns    = "exclude-patterns"
	keyFollowPaths        = "followpaths"
	keyDirName            = "dir-name"
	keyExporterMetaPrefix = "exporter-md-"

The client applies those filters itself before anything is sent, by wrapping the directory in fsutil.NewFilterFS (filesync.go:110-145). An excluded file is never read and never leaves the client from the code. That is the practical meaning of .dockerignore now: it trims what is sent, not only what COPY sees.

Three transfers per build

A Dockerfile build makes three separate local transfers, and they are the first three lines of --progress=plain output (frontend/dockerui/config.go:348-363, 522-585). [internal] load build definition reads the Dockerfile from the dockerfile local, with FollowPaths limited to the Dockerfile, <Dockerfile>.dockerignore and dockerfile. load .dockerignore reads .dockerignore from the context local, used only if no per-Dockerfile ignore file was found. load build context is the filtered main context from the code. The last one is narrowed twice. The exclude patterns come from .dockerignore. The FollowPaths come from the Dockerfile: each COPY/ADD source and each RUN --mount bind source is added to ctxPaths, which becomes llb.FollowPaths on the context source (dockerfile2llb/convert.go:1145-1150, 1850-1875; convert_runmount.go:141-146). For Figure 3 that is go.mod and main.go and nothing else. COPY . . names the path / and switches the narrowing off.

The wire: STAT, REQ, DATA, FIN

DiffCopy speaks fsutil's packet protocol, five types in one enum (buildkit/vendor/github.com/tonistiigi/fsutil/types/wire.proto:10-23; fsutil v0.0.0-20260819142231-83cac42c1c52 as vendored): 

  enum PacketType {
    PACKET_STAT = 0;
    PACKET_REQ = 1;
    PACKET_DATA = 2;
    PACKET_FIN = 3;
    PACKET_ERR = 4;
  }

The sender streams one STAT for every file that survived the filters and ends the list with an empty STAT (fsutil/send.go:182). The receiver compares each record with what it already holds and answers REQ <id> only for files that differ (receive.go:425). The sender returns DATA chunks for each requested id, with an empty DATA to close a file (send.go:146). The receiver sends FIN and the sender answers it (receive.go:224; send.go:101-106) from the code. Figure 6 draws one exchange.

The incremental part lives on the daemon side. BuildKit keeps a retained mutable snapshot per name:sharedKeyHint:<client shared key> and syncs into it again on the next build, so a second build sends only the files that changed, and a cacheUpdater updates the content-hash records of §04 as files land (source/local/source.go:204-280) from the code. The content key a COPY needs is therefore mostly computed before the solver asks for it reconstruction.

The same inversion covers everything else a build takes from the client. A secret's bytes are fetched over the session with secrets.GetSecret when a RUN mounts it, and an SSH mount is a socket that proxies back to the client's agent over the same session (solver/llbsolver/mounts/secretmount_unix.go:16-75; mounts/mount.go:200-239) from the code. Nothing is uploaded in advance; dockerd asks when a step needs it.

One boundary surprises people. .dockerignore patterns are applied to context COPYs as an ignore matcher, but not to COPY --from=<stage>, whose source is another stage's filesystem (dockerfile2llb/convert.go:1120-1132). That is register D60, class D: expected from the code, often assumed otherwise from the code.

The network: the last prestart hook

The default build network is a libnetwork sandbox on Docker's bridge network; host and none are BuildKit's built-in providers (executor_linux.go:23-31). Attaching a build container to bridge uses an older mechanism than docker run does. The sandbox is created with OptionUseExternalKey, and runc runs a libnetwork-setkey re-exec of dockerd as an OCI prestart hook. The hook reads the runtime's specs.State JSON on stdin and sends {ContainerID, Key} over the unix socket /run/docker/libnetwork/<short-controller-id>.sock (moby/daemon/libnetwork/sandbox_externalkey_unix.go:26-190). The network namespace does not exist yet when the endpoint joins, so sbJoin defers addresses and routes until SetKey arrives (libnetwork/endpoint.go:544-567). The endpoint is created with CreateOptionDisableResolution, so a build step does not get the embedded DNS server that Part 4 describes from the code. Since v0.31.0 BuildKit also has an optional proxy network mode, and dockerd wires it when proxyprovider.Supported() holds, with a loopback-filtered host provider (executor_linux.go:62-78).

Five mount types

RUN --mount accepts bind (the default), cache, tmpfs, secret and ssh, with sharing modes shared, private and locked; mode, uid and gid are rejected on bind and tmpfs (frontend/dockerfile/instructions/commands_runmount.go:13-42, 268-280) from the code. Each lowers to an exec mount in LLB, and each has its own runtime shape:

  • bind is read-only unless rw is given. With rw it is marked ForceNoOutput, so writes are discarded and never become a layer (dockerfile2llb/convert_runmount.go:103-107).
  • cache without id uses the cleaned target path as its ID, namespaced by the frontend's cacheIDNamespace, and becomes llb.AsPersistentCacheDir (convert_runmount.go:69-120). At run time it is a retained mutable snapshot found through the metadata index cache-dir:<id>[:<base ref>]. shared hands one ref to every concurrent user, private makes a new ref when the existing one is locked, and locked polls every 100 ms until the holder lets go (solver/llbsolver/mounts/mount.go:68-154, 459-460).
  • secret is a fresh tmpfs (nodev,nosuid, plus noexec unless the mode has an exec bit) in a 0711 temporary directory. The bytes are written to a random file name with mode 0600 and chowned to the requested uid and gid; the default target is /run/secrets/<id> (mounts/secretmount_unix.go:16-75).
  • ssh defaults to /run/buildkit/ssh_agent.<n> and sets SSH_AUTH_SOCK to the first one if the user has not (client/llb/exec.go:155-164).

Read together with §04, the rules line up. Secret, SSH and tmpfs mounts never feed the cache key, and a writable mount with output stays definition-keyed. A cache mount is state outside the graph: its contents can differ between two runs of a step with the same key reconstruction.

Garbage collection takes cache mounts first

dockerd's builder GC is on unless explicitly disabled. With nothing configured, the limits are 10 % of the disk reserved, 80 % max used and 20 % min free, each computed as (whole GiB in that share of the disk + 1) × 10^9 bytes, or 2 GB reserved if the disk cannot be stat'ed (moby/daemon/config/builder.go:94-96; worker/gc.go:74-79). The first rule is the odd one (moby/daemon/internal/builder-next/worker/gc.go:18, 44-50): 

// tempCachePercent represents the percentage ratio of the cache size in bytes to temporarily keep for a short period of time (couple of days)
…
	return []client.PruneInfo{
		// if build cache uses more than 512MB delete the most easily reproducible data after it has not been used for 2 days
		{
			Filter:       []string{"type==source.local", "type==exec.cachemount", "type==source.git.checkout"},
			KeepDuration: 48 * time.Hour,
			MaxUsedSpace: tempCacheReservedSpace,
		},

tempCachePercent is math.E * math.Pi * math.Phi, which the comment calls "a mathematically pleasing" choice of about 13.8, with a 512 MB floor. So cache mounts, synced contexts and git checkouts unused for 48 hours go first once they pass about 13.8 % of the reserved space (register D58, class D) from the code. A worked case: on a disk of 100 × 10^9 bytes, 10 % is 10^10 bytes, which diskPercentage counts as 9 whole GiB, so the reserve is (9 + 1) × 10^9 = 10 GB and the cache-mount threshold is about 1.38 GB reconstruction, arithmetic on worker/gc.go:74-77.

07Exporters, cache export and attestations

A solved build is a set of snapshots, not an image. An exporter turns the result into something outside BuildKit. The client defines five exporter names, image, local, tar, oci and docker (buildkit/client/exporters.go:9-15), and dockerd adds a sixth, moby, which the classic /build path checks for (moby/daemon/internal/builder-next/builder.go:408). The image exporter accepts push, push-by-digest and unpack, returns containerimage.digest (the root manifest or index) plus the config digest, and pushes in a finalize callback after the export is written (exporter/containerimage/export.go:66-68, 373-402) from the code.

Layers are made at the end

No step in §04 produced a tarball. Layer blobs are computed lazily, at export, from pairs of snapshots. On the overlayfs or stargz snapshotters BuildKit first tries an "overlay differ" that reads the upper directory directly, then falls back to containerd's walking differ; fuse-overlayfs and native skip the fast path (cache/blobs.go:168-250) from the code. The digests, DiffIDs and ChainIDs of those blobs are Part 2's subject. The frontend's history entries land in the config. alpine's amd64 config shows them as published, with the same DiffID Part 2 derived from the layer measured here: 

"created_by": "ADD alpine-minirootfs-3.24.3-x86_64.tar.gz / # buildkit",
"comment": "buildkit.dockerfile.v0"
"created_by": "CMD [\"/bin/sh\"]", "comment": "buildkit.dockerfile.v0", "empty_layer": true
"diff_ids": ["sha256:75c137aedfb2760f88629236cb7b797630aed0c3d91d626d1d1bb694878fc2ba"]

All three timestamps in that config are 2026-10-21T22:37:22.870489069Z. With SOURCE_DATE_EPOCH set, the exporter clamps created to the epoch; with no created at all it uses the last history timestamp (writer.go:830-857) from the code.

Cache export flattens the link graph

Remote cache (registry, local, gha) is an OCI index or manifest of layer blobs plus one JSON document of type application/vnd.buildkit.cacheconfig.v0. It holds layers, each a blob with a parent index, and records, each a digest with layer pointers and inputs links to other records (cache/remotecache/v1/types/spec.go:9-49). That is the bbolt link graph of §04 written out as arrays. --cache-to type=inline exports no separate artifact. It puts the same JSON into the image config under the key moby.buildkit.cache.v0 (exporter/containerimage/writer.go:859-865) from the code. Mode min, the default, exports the final result's chain; max exports every intermediate vertex. An unknown mode is dropped with a debug log (control/control.go:491-495): 

		if exportMode, supported := parseCacheExportMode(e.Attrs["mode"]); !supported {
			bklog.G(ctx).Debugf("skipping invalid cache export mode: %s", e.Attrs["mode"])
		} else {
			exp.CacheExportMode = exportMode
		}

So mode=maximum silently means min (register D56, class D, unchanged on master). Which backends exist at all depends on dockerd's image store (moby/daemon/internal/builder-next/controller.go:227-237, 512-519). With the containerd store, dockerd's BuildKit imports gha, local and registry and exports those plus inline. With the legacy graphdriver store it imports registry (through a moby-specific localinlinecache) and local, and exports only inline. Neither registers s3 or azblob, though BuildKit ships both (D55, class D) from the code. buildx never sends that request to a graphdriver host. With the docker driver there, it rejects every --cache-to type except inline on the client and prints "Cache export is not supported for the docker driver. Switch to a different driver, or turn on the containerd image store, and try again." (buildx/build/opt.go:271-275, build/utils.go:193-197; asserted by buildx's own test, tests/build.go:973-983) from the code.

Attestations in the index

Attestations are extra manifests in the image index with platform unknown/unknown, annotated vnd.docker.reference.type: attestation-manifest and vnd.docker.reference.digest: <subject manifest>, whose layers are in-toto statements (docs/attestations/attestation-storage.md:92-122) from the code. Since BuildKit v0.32 they are also OCI artifacts by default: artifactType: application/vnd.docker.attestation.manifest.v1+json, an empty config and a subject descriptor, with the annotations kept (exporter/containerimage/writer.go:613-716). alpine's index pairs every platform that way; amd64 sha256:c26612752c78… pairs with attestation sha256:964745728d17… measured here. The provenance default differs by layer (solver/llbsolver/provenance.go:408-418): 

	mode := "max"
	if v, ok := attrs["mode"]; ok {
		switch v {
		case "full":
			mode = "max"
		case "max", "min":
			mode = v

buildx adds mode=min,inline-only=true by default, but only when the builder supports attestations, so the docker driver on the graphdriver store gets no provenance at all (buildx/build/opt.go:349-373). An explicit --provenance=true reaches BuildKit with no mode (util/buildflags/attests.go:173-181), and so does raw buildctl with attest:provenance=; both get max, which records the Dockerfile, build-arg values and secret IDs (register D59, class D). A max record embeds the full LLB with its digestMapping, which is what made §03 possible. alpine's lists GIT_AUTH_HEADER and GIT_AUTH_TOKEN as optional secrets, by ID only measured here.
