The network: the last prestart hook

The default build network is a libnetwork sandbox on Docker's bridge network; host and none are BuildKit's built-in providers (executor_linux.go:23-31). Attaching a build container to bridge uses an older mechanism than docker run does. The sandbox is created with OptionUseExternalKey, and runc runs a libnetwork-setkey re-exec of dockerd as an OCI prestart hook. The hook reads the runtime's specs.State JSON on stdin and sends {ContainerID, Key} over the unix socket /run/docker/libnetwork/<short-controller-id>.sock (moby/daemon/libnetwork/sandbox_externalkey_unix.go:26-190). The network namespace does not exist yet when the endpoint joins, so sbJoin defers addresses and routes until SetKey arrives (libnetwork/endpoint.go:544-567). The endpoint is created with CreateOptionDisableResolution, so a build step does not get the embedded DNS server that Part 4 describes from the code. Since v0.31.0 BuildKit also has an optional proxy network mode, and dockerd wires it when proxyprovider.Supported() holds, with a loopback-filtered host provider (executor_linux.go:62-78).

Five mount types

RUN --mount accepts bind (the default), cache, tmpfs, secret and ssh, with sharing modes shared, private and locked; mode, uid and gid are rejected on bind and tmpfs (frontend/dockerfile/instructions/commands_runmount.go:13-42, 268-280) from the code. Each lowers to an exec mount in LLB, and each has its own runtime shape:

  • bind is read-only unless rw is given. With rw it is marked ForceNoOutput, so writes are discarded and never become a layer (dockerfile2llb/convert_runmount.go:103-107).
  • cache without id uses the cleaned target path as its ID, namespaced by the frontend's cacheIDNamespace, and becomes llb.AsPersistentCacheDir (convert_runmount.go:69-120). At run time it is a retained mutable snapshot found through the metadata index cache-dir:<id>[:<base ref>]. shared hands one ref to every concurrent user, private makes a new ref when the existing one is locked, and locked polls every 100 ms until the holder lets go (solver/llbsolver/mounts/mount.go:68-154, 459-460).
  • secret is a fresh tmpfs (nodev,nosuid, plus noexec unless the mode has an exec bit) in a 0711 temporary directory. The bytes are written to a random file name with mode 0600 and chowned to the requested uid and gid; the default target is /run/secrets/<id> (mounts/secretmount_unix.go:16-75).
  • ssh defaults to /run/buildkit/ssh_agent.<n> and sets SSH_AUTH_SOCK to the first one if the user has not (client/llb/exec.go:155-164).

Read together with §04, the rules line up. Secret, SSH and tmpfs mounts never feed the cache key, and a writable mount with output stays definition-keyed. A cache mount is state outside the graph: its contents can differ between two runs of a step with the same key reconstruction.

Garbage collection takes cache mounts first

dockerd's builder GC is on unless explicitly disabled. With nothing configured, the limits are 10 % of the disk reserved, 80 % max used and 20 % min free, each computed as (whole GiB in that share of the disk + 1) × 10^9 bytes, or 2 GB reserved if the disk cannot be stat'ed (moby/daemon/config/builder.go:94-96; worker/gc.go:74-79). The first rule is the odd one (moby/daemon/internal/builder-next/worker/gc.go:18, 44-50): 

// tempCachePercent represents the percentage ratio of the cache size in bytes to temporarily keep for a short period of time (couple of days)
…
	return []client.PruneInfo{
		// if build cache uses more than 512MB delete the most easily reproducible data after it has not been used for 2 days
		{
			Filter:       []string{"type==source.local", "type==exec.cachemount", "type==source.git.checkout"},
			KeepDuration: 48 * time.Hour,
			MaxUsedSpace: tempCacheReservedSpace,
		},

tempCachePercent is math.E * math.Pi * math.Phi, which the comment calls "a mathematically pleasing" choice of about 13.8, with a 512 MB floor. So cache mounts, synced contexts and git checkouts unused for 48 hours go first once they pass about 13.8 % of the reserved space (register D58, class D) from the code. A worked case: on a disk of 100 × 10^9 bytes, 10 % is 10^10 bytes, which diskPercentage counts as 9 whole GiB, so the reserve is (9 + 1) × 10^9 = 10 GB and the cache-mount threshold is about 1.38 GB reconstruction, arithmetic on worker/gc.go:74-77.
