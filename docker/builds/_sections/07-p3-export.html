{{S}}Exporters, cache export and attestations

A solved build is a set of snapshots, not an image. An exporter turns the result into something outside BuildKit. The client defines five exporter names, image, local, tar, oci and docker (buildkit/client/exporters.go:9-15), and dockerd adds a sixth, moby, which the classic /build path checks for (moby/daemon/internal/builder-next/builder.go:408). The image exporter accepts push, push-by-digest and unpack, returns containerimage.digest (the root manifest or index) plus the config digest, and pushes in a finalize callback after the export is written (exporter/containerimage/export.go:66-68, 373-402) from the code.

Layers are made at the end

No step in §04 produced a tarball. Layer blobs are computed lazily, at export, from pairs of snapshots. On the overlayfs or stargz snapshotters BuildKit first tries an "overlay differ" that reads the upper directory directly, then falls back to containerd's walking differ; fuse-overlayfs and native skip the fast path (cache/blobs.go:168-250) from the code. The digests, DiffIDs and ChainIDs of those blobs are Part 2's subject. The frontend's history entries land in the config. alpine's amd64 config shows them as published, with the same DiffID Part 2 derived from the layer measured here: 

"created_by": "ADD alpine-minirootfs-3.24.3-x86_64.tar.gz / # buildkit",
"comment": "buildkit.dockerfile.v0"
"created_by": "CMD [\"/bin/sh\"]", "comment": "buildkit.dockerfile.v0", "empty_layer": true
"diff_ids": ["sha256:75c137aedfb2760f88629236cb7b797630aed0c3d91d626d1d1bb694878fc2ba"]

All three timestamps in that config are 2026-10-21T22:37:22.870489069Z. With SOURCE_DATE_EPOCH set, the exporter clamps created to the epoch; with no created at all it uses the last history timestamp (writer.go:830-857) from the code.

Cache export flattens the link graph

Remote cache (registry, local, gha) is an OCI index or manifest of layer blobs plus one JSON document of type application/vnd.buildkit.cacheconfig.v0. It holds layers, each a blob with a parent index, and records, each a digest with layer pointers and inputs links to other records (cache/remotecache/v1/types/spec.go:9-49). That is the bbolt link graph of §04 written out as arrays. --cache-to type=inline exports no separate artifact. It puts the same JSON into the image config under the key moby.buildkit.cache.v0 (exporter/containerimage/writer.go:859-865) from the code. Mode min, the default, exports the final result's chain; max exports every intermediate vertex. An unknown mode is dropped with a debug log (control/control.go:491-495): 

		if exportMode, supported := parseCacheExportMode(e.Attrs["mode"]); !supported {
			bklog.G(ctx).Debugf("skipping invalid cache export mode: %s", e.Attrs["mode"])
		} else {
			exp.CacheExportMode = exportMode
		}

So mode=maximum silently means min (register D56, class D, unchanged on master). Which backends exist at all depends on dockerd's image store (moby/daemon/internal/builder-next/controller.go:227-237, 512-519). With the containerd store, dockerd's BuildKit imports gha, local and registry and exports those plus inline. With the legacy graphdriver store it imports registry (through a moby-specific localinlinecache) and local, and exports only inline. Neither registers s3 or azblob, though BuildKit ships both (D55, class D) from the code. buildx never sends that request to a graphdriver host. With the docker driver there, it rejects every --cache-to type except inline on the client and prints "Cache export is not supported for the docker driver. Switch to a different driver, or turn on the containerd image store, and try again." (buildx/build/opt.go:271-275, build/utils.go:193-197; asserted by buildx's own test, tests/build.go:973-983) from the code.

Attestations in the index

Attestations are extra manifests in the image index with platform unknown/unknown, annotated vnd.docker.reference.type: attestation-manifest and vnd.docker.reference.digest: <subject manifest>, whose layers are in-toto statements (docs/attestations/attestation-storage.md:92-122) from the code. Since BuildKit v0.32 they are also OCI artifacts by default: artifactType: application/vnd.docker.attestation.manifest.v1+json, an empty config and a subject descriptor, with the annotations kept (exporter/containerimage/writer.go:613-716). alpine's index pairs every platform that way; amd64 sha256:c26612752c78… pairs with attestation sha256:964745728d17… measured here. The provenance default differs by layer (solver/llbsolver/provenance.go:408-418): 

	mode := "max"
	if v, ok := attrs["mode"]; ok {
		switch v {
		case "full":
			mode = "max"
		case "max", "min":
			mode = v

buildx adds mode=min,inline-only=true by default, but only when the builder supports attestations, so the docker driver on the graphdriver store gets no provenance at all (buildx/build/opt.go:349-373). An explicit --provenance=true reaches BuildKit with no mode (util/buildflags/attests.go:173-181), and so does raw buildctl with attest:provenance=; both get max, which records the Dockerfile, build-arg values and secret IDs (register D59, class D). A max record embeds the full LLB with its digestMapping, which is what made §03 possible. alpine's lists GIT_AUTH_HEADER and GIT_AUTH_TOKEN as optional secrets, by ID only measured here.
