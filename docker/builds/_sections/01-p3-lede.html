{{S}}BuildKit never runs your Dockerfile

A container is an ordinary Linux process, and Docker is a relay of programs that agree on names made of sha256 hashes. A build adds two more names to that relay and one more compiler. BuildKit never executes a Dockerfile. It compiles the text into LLB, a graph of protobuf records, each named by the sha256 of its own bytes. It keys its cache on that graph and on file content, never on timestamps. And it asks the client for the build context; the client does not push it.

The first hop is a rename. The docker CLI treats build, builder, image build and bake as calls to a plugin whose default name is buildx, and forwardBuilder rewrites the argument vector before the CLI runs the plugin as a child process from the code. The table that does it is cli/cmd/docker/builder.go:149-164:

On the forwarded path the CLI also prepends BUILDX_BUILDER=<current context> to the plugin's environment, so docker build targets the daemon's own builder and loads a local image even after docker buildx use picked a container builder (builder.go:132-141). DOCKER_BUILDKIT=0 still selects the legacy builder on Linux, now with a deprecation warning. A missing plugin falls back to the legacy builder with a "DEPRECATED" warning, unless DOCKER_BUILDKIT=1 forced BuildKit, in which case it fails from the code. Engine 23.0.0 (released 2023-02-01) made this the default on Linux. On this machine the rewrite is visible without a daemon: docker build --help prints buildx's usage line, and docker buildx ls shows the default builder in an error state because nothing listens on the socket measured here:

The second hop shares a socket with everything else. dockerd's httpHandler.ServeHTTP sends any HTTP/2 request whose Content-Type starts with application/grpc to a gRPC server (or to an optional grpcProxy that claims the service), and every other request to the REST API (moby/daemon/command/httphandler.go:38-48). The listener speaks HTTP/1, HTTP/2 and cleartext HTTP/2 (h2c) at once. buildx does not use that route. Its docker driver opens POST /grpc with Upgrade: h2c, an HTTP/1.1 upgrade that dockerd answers with a 101 and serves with a deprecated http2.Server.ServeConn, and calls BuildKit's Control service inside it: Solve to start a build, Status to stream progress (buildkit/api/services/control/control.proto:15-24). The session goes over a second hijacked connection, POST /session, not Control.Session (buildx/driver/docker/driver.go:62-75; moby/daemon/server/router/grpc/grpc_routes.go:11-52). Both routes are marked deprecated, and buildx v0.37.1 still uses them, as do v0.37.2 and buildx master from the code.

Inside dockerd sit two builders. The daemon still constructs the legacy dockerfile.NewBuildManager and an embedded BuildKit rooted at <data-root>/buildkit (moby/daemon/command/daemon.go:471-480). The embedded controller registers exactly two frontends: dockerfile.v0, compiled into dockerd, and gateway.v0, which runs a frontend shipped as an image. It keeps its cache index in a bbolt file, cache.db, and runs every RUN step by exec'ing runc itself, with no containerd task from the code. Figure {{fig-build-process-map}} draws the whole relay. The direction of the thin arrows is the surprise this part keeps returning to.
