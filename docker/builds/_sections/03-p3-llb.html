{{S}}LLB: a Merkle DAG of protobuf

LLB, BuildKit's low-level build format, is defined in one protobuf file, solver/pb/ops.proto. One Op is one vertex of the graph: a list of input edges, then exactly one of seven op kinds, then an optional platform and worker constraints. An input edge is not a pointer. It is the sha256 digest of the input op's marshaled bytes plus an output index (buildkit/solver/pb/ops.proto:10-25, 37-42) from the code: 

message Op {
	// changes to this structure must be represented in json.go.
	// inputs is a set of input edges.
	repeated Input inputs = 1;
	oneof op {
		ExecOp exec = 2;
		SourceOp source = 3;
		FileOp file = 4;
		BuildOp build = 5;
		MergeOp merge = 6;
		DiffOp diff = 7;
		PassthroughOp passthrough = 8;
	}
	Platform platform = 10;
	WorkerConstraints constraints = 11;
}
…
message Input {
	// digest of the marshaled input Op
	string digest = 1;
	// output index of the input Op
	int64 index = 2;
}

Naming each input by the hash of its bytes makes the graph a Merkle DAG, the same construction as an image (Part 2) or a git commit. The four kinds a Dockerfile uses are small. SourceOp is a URL-like identifier (local://, docker-image://, git://, https://) plus string attributes. FileOp is a chain of actions: copy, mkfile, mkdir, rm, symlink. ExecOp carries Meta (args, env, cwd, user, proxy env, extra hosts, hostname, ulimits, cgroup parent, valid exit codes), mounts, a network mode, a security mode, secret env vars and CDI devices. MergeOp and DiffOp let a build stack and subtract layers; Merge(A,B) lays B over A with B winning, and the docs call it associative (ops.proto:45-69, 196-203, 320-341; docs/dev/merge-diff.md:25-40) from the code.

A Definition, the thing a client sends in Solve, is a flat list of marshaled ops, a separate metadata map keyed by op digest, and a source map (ops.proto:309-318). Descriptions, the ignore-cache flag, progress groups and Dockerfile line numbers all live in the side maps, outside the hashed bytes. State.Marshal marshals inputs first, depth-first, so the list comes out in topological order with duplicates removed. It hashes each op with protobuf's deterministic mode, which sorts map keys (client/llb/marshal.go:167-169). Last it appends one op with no kind at all, whose single input points at the result. That terminal vertex is how the solver finds the root (client/llb/state.go:156-165) from the code.

alpine's three vertices, re-derived

A max provenance record embeds the whole definition as JSON, plus a digestMapping from each op's digest to a name like step1. alpine:latest's amd64 record holds three ops: a git SourceOp, a FileOp copy that reads the tarball out of that checkout, and the terminal op. JSON is not the hashed form, so the digests can only be checked by re-encoding. A 37-line Python script writes each op back as proto3 by hand (varint tags, length-prefixed strings, zero values omitted, map entries in key order) and hashes the result. All three digests match the published ones measured here:

Two versions of the script exist. The first takes each input digest from the published mapping, so it checks each vertex on its own. The second, llbdigest-chained.py, feeds each computed digest into the next op, so the match above checks the chain end to end. Both hard-code the six copy booleans as 1, which is what this record holds; a record with a false flag would need the encoder extended measured here. The bytes are short enough to read whole. Figure {{fig-vertex-bytes}} annotates them field by field.

The ripple in the right-hand column is the point. Because inputs are named by digest, editing one character of the root SourceOp changes the digest of every vertex downstream measured here. The reverse also holds, and it explains most of §04. Anything kept outside the op bytes cannot change a digest. Comments never reach LLB, and line numbers travel in the source map, so moving a Dockerfile line or editing a comment leaves every vertex digest as it was (parser/parser.go:334-338; ops.proto:309-318) from the code, reconstruction for the conclusion.

A vertex digest is still not a cache key. The solver uses it to merge identical work inside one run: two jobs that load the same digest share one state in Solver.actives, and the step runs once (solver/jobs.go:41-50, 547-611). But docker-image://alpine:latest means different bytes next week, so the solver's design doc says the digest is good only for deduplication during a run (docs/dev/solver.md:61-67) from the code. Persistent caching needs something else.
