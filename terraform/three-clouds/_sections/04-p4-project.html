{{S}}The multicloud project

The rest of this part is one project, ~/terraform-ref/lab/multicloud/, written for Terraform v1.17.0 and the four cached providers. It builds the same shape on each cloud: a network, private artifact storage, a container runtime, and a Postgres database whose password, in the README's words, "never touches state or plan files". It uses the newest language features on purpose, and it was taken as far as a machine with no cloud account can take it. Its claim: every one of those features can be exercised offline on all three clouds, except the ones that must talk to a cloud.

The shape

A root module calls three cloud modules. aws-stack builds a VPC with two private subnets, a security group, a versioned and public-access-blocked S3 bucket, RDS Postgres, a Secrets Manager secret, an IAM role and a container-image Lambda that triggers an action. gcp-stack builds a VPC with two subnets, a GCS bucket with public access prevention enforced, a service account, a Cloud Run v2 service, Cloud SQL Postgres with a google_sql_user, and a Secret Manager secret. azure-stack builds a resource group, a VNet with two delegated subnets (from a dynamic block), a ZRS storage account with TLS 1.2, a Log Analytics workspace, a Container Apps environment and app, a Postgres flexible server and an RBAC Key Vault with one secret. Around them: three test files, four mock-data directories, a .tfquery.hcl file, one policy file with its tests, and a fake az script.

Every module call fans out over environments. The password is per environment and cloud, built from a flattened key set (multicloud/main.tf:8-10): 

  db_keys = toset(flatten([
    for env in keys(var.environments) : [for c in local.clouds : "${env}-${c}"]
  ]))

and then, main.tf:17-36, an ephemeral resource over those keys and the first of the three module calls: 

ephemeral "random_password" "db" {
  for_each = local.db_keys

  length           = 28
  special          = true
  override_special = "-_~"
}

module "aws" {
  source   = "./modules/aws-stack"
  for_each = var.environments

  name                = "${var.project}-${each.key}${local.name_suffix}"
  cidr_block          = each.value.cidr_block
  db_size             = each.value.db_size
  db_password         = ephemeral.random_password.db["${each.key}-aws"].result
  db_password_version = var.db_password_version
  lambda_image_uri    = var.lambda_image_uri
  adopt_buckets       = var.adopt_buckets
}

var.environments is a map(object({ cidr_block = string, db_size = optional(string, "small") })) with two validation rules, one built on can(cidrnetmask(...)). local.name_suffix is "-invalid" whenever var.offline is true, so that no fake-credential run can name a real bucket, vault or account. gcp_project carries a cross-object rule (1.9) that reads another variable: var.offline || var.gcp_project != "xolab-offline-000000". The provider versions come from a local, which Terraform 1.17 allows in required_providers (#39153) as long as it is statically known, multicloud/versions.tf:3-19: 

locals {
  provider_pins = {
    aws     = "6.70.0"
    google  = "8.8.0"
    azurerm = "5.10.0"
    random  = "3.9.1"
  }
}

terraform {
  required_version = ">= 1.17.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = local.provider_pins.aws
    }

Only const variables and locals built from them or from literals work there. A plain variable fails init with "Only literal values and const variables can be evaluated during init." (Part 1 has the init graph that enforces it). The rest of the root holds two check blocks, three moved blocks recording the move from module.aws_dev to module.aws["dev"], and provider-defined functions on literals.

The schemas are the ground truth

Nothing in the project was written from memory of what a provider supports. It was checked against terraform providers schema -json for the cached versions, a 32.8 MB dump that a census script counted and a verifier re-ran byte for byte. Figure 24 is that census. Two of its rows decided the design. Every cloud has a write-only database password, so the same ephemeral pattern works on all three. And the list-resource coverage is uneven: google 8.8.0 has a list type for google_storage_bucket but none for google_compute_network, google_cloud_run_v2_service or google_sql_database_instance, which is why discover.tfquery.hcl lists buckets on GCP and resource groups on Azure.

What passes, and what it costs

All of the following ran on 2026-10-23 on the 2-vCPU box, from a shared plugin cache, with fake credentials where a provider demanded something measured here. Times vary with page cache and load, so they are ranges.

  • init passes in about 20 seconds and reports "Using … from the shared cache directory" for all four providers, but it is not offline: inside a network namespace with no network it fails "could not connect to registry.terraform.io".
  • validate takes 16 to 33 seconds, with one cold run at 1 minute 57; validate -query, which also checks the .tfquery.hcl file, takes 16 to 49 seconds and is not intrinsically slower. fmt -check -recursive passes, including test and query files.
  • terraform test: "Success! 7 passed, 0 failed." in about 42 to 65 seconds, every provider mocked (section 7).
  • terraform plan for one environment: "Plan: 36 to add, 0 to change, 0 to destroy. Actions: 1 to invoke." in about 35 seconds with the network up, under TF_LOG=DEBUG. Two environments plan 72 creates and 2 actions, 20.3 seconds on a warm run without debug logging. Fully air-gapped, the single-environment plan still succeeds and takes about 5 minutes 15 seconds (section 6 explains why).

The plan's costs are the ones Part 2 predicted. It started 18 provider processes, 5 each for aws, google and azurerm and 3 for random; each cloud provider was first started alone to serve its schema, which took about 7.2 seconds and about 580 MB for aws. At peak 7 providers were alive at once, about 1.38 GB of resident memory. The plan graph has 115 vertices and 217 edges, 84 of them (expand) nodes, plus 12 variables and 3 (validation) vertices, four providers and their four closers, three module closers, one ephemeral (close), two check (report) vertices, the action's (config) vertex and the root. The apply graph has 113 and 215; the default resource graph 37 and 39. There are still no instance nodes in it (Part 2). The saved plan is 28,866 to 28,900 bytes, and its show -json form 120,110 bytes, with a top-level action_invocations array beside resource_changes.

Functions that run offline, and one that surprises

Provider-defined functions run inside the provider process over CallFunction, on an unconfigured instance, so with literal arguments they evaluate at plan time without credentials. The root's function_demo output calls provider::aws::arn_parse, arn_build, provider::google::region_from_zone("us-central1-a"), which returns "us-central1", and provider::azurerm::parse_resource_id. Functions on computed attributes stay "(known after apply)" in a plan; under mocks they return real results because the mocks supply realistic ids.

One function does not do what its name suggests. provider::aws::trim_iam_role_path returns the role ARN with its path removed, not the role name; a test expecting "xolab-dev-api" failed, and the final assertion is "arn:aws:iam::123456789012:role/xolab-dev-invalid-api" measured here. If you need a role name, parse the ARN.
