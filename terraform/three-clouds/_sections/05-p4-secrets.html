{{S}}Where the password goes

The project's most deliberate design choice is the database password. No variable holds it, no output shows it, and no file on disk should ever contain it. Part 3 read the mechanism, ephemeral values and write-only arguments, from the code. This section follows one password through a real three-cloud plan and checks every file it could have landed in. Its claim: the secret never touches disk, and the provider, not core, decides when it reaches the cloud.

One ephemeral value, six write-only arguments

Two releases built the pieces. v1.10 added ephemeral resources, which are opened anew in each phase and never persisted, together with ephemeral input variables and outputs; v1.11 (#36031) added write-only attributes, which a provider declares, which accept ephemeral values, and which are never stored from the code. The project's ephemeral "random_password" "db" makes one value per environment and cloud. Crossing into a module needs the child variable to be ephemeral too, as in modules/aws-stack/variables.tf:19-24: 

variable "db_password" {
  description = "Master password. Ephemeral: never persisted in state or plan."
  type        = string
  ephemeral   = true
  sensitive   = true
}

Inside each module the value goes to exactly two places: the database and a secret store. The AWS module's pair, modules/aws-stack/database.tf:25-43: 

  # Write-only argument (Terraform >= 1.11): sent to the provider on apply,
  # never stored in state or plan. Bump the version to push a new value.
  password_wo         = var.db_password
  password_wo_version = var.db_password_version
}

resource "aws_secretsmanager_secret" "db" {
  name = "${var.name}/db"
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id = aws_secretsmanager_secret.db.id
  secret_string_wo = jsonencode({
    host     = aws_db_instance.this.address
    username = aws_db_instance.this.username
    password = var.db_password
  })
  secret_string_wo_version = var.db_password_version
}

GCP uses google_sql_user.password_wo and google_secret_manager_secret_version.secret_data_wo; Azure uses administrator_password_wo on the flexible server and value_wo on the Key Vault secret. That is six write-only arguments fed from three ephemeral instances per environment. One comment in the project is slightly wrong: write-only values are not sent "on apply" only, as the next subsection shows.

The version triggers are not uniform. *_wo_version is a number on aws_db_instance and google_sql_user but a string on google_secret_manager_secret_version, so the GCP module converts it (modules/gcp-stack/main.tf:107-108): 

  secret_data_wo         = var.db_password
  secret_data_wo_version = tostring(var.db_password_version)

And write-only does not imply sensitive. aws's password_wo is both sensitive and write-only; azurerm's administrator_password_wo is only write-only measured here. The project marks the module variable sensitive = true anyway, which covers both.

The ephemeral resource itself

An ephemeral resource is not a resource with a hidden value; it has its own lifecycle in the graph. ephemeralResourceOpen (internal/terraform/node_resource_ephemeral.go:90-118, 140-189) first looks at the configuration. If it is not wholly known, core makes a synthetic unknown, marks it ephemeral and calls no provider at all. Otherwise it calls ValidateEphemeralResourceConfig and then OpenEphemeralResource, and marks the whole result with marks.Ephemeral from the code. Each ephemeral configuration resource also gets a (close) vertex in the plan graph, so its instances are closed as soon as nothing needs them; the project's plan graph has exactly one. One apply of a configuration like this makes two OpenEphemeralResource and two CloseEphemeralResource calls, one pair per walk measured here.

Two neighbours behave differently and are worth knowing before you reuse the pattern. Since v1.16, terraform_data has a store block whose write-only store.input accepts an ephemeral value and copies it into sensitive_output, which is persisted: stored with sensitive = true, a random_password result lands in state. It is a durability tool, not a secrecy tool. And a test assert cannot read an ephemeral resource at all, mocked or not ("Ephemeral resources cannot be asserted"); the project's mock simply returns "mock-password-not-secret".

What the plan shows, and what the files hold

The offline plan opens the ephemeral instances and renders the argument without a value measured here, trimmed: 

ephemeral.random_password.db["dev-aws"]: Opening...
ephemeral.random_password.db["dev-aws"]: Opening complete after 0s
  # module.aws["dev"].aws_db_instance.this will be created
      + password_wo                           = (write-only attribute)
      + password_wo_version                   = 1

The renderer has a second form, (sensitive, write-only attribute) (internal/command/jsonformat/computed/renderers/write_only.go:24-28), but aws's sensitive password_wo still printed the plain one. In show -json, every *_wo is null and every *_wo_version holds its configured value: the six arguments, plus an unused pair on azurerm_subnet.

A null in the JSON view does not prove the bytes are absent from the plan file. A canary does. A one-resource configuration fed an ephemeral root variable into password_wo and was planned with a recognisable value measured here: 

$ TF_VAR_pw=CANARY-7f3a-SECRET $T plan -out=wo6.tfplan    # Plan: 1 to add
$ python3 -m zipfile -e wo6.tfplan unz6 && grep -a -c CANARY unz6/tfplan
0
$ python3 -c "d=open('unz6/tfplan','rb').read(); print(d[-12:])"
b'\xc8\x01\x01\xd0\x01\x01\xe2\x01\x02pw'     # field 28 apply_time_variables = ["pw"]

The canary is in none of the ZIP's members: not tfplan, tfstate, tfstate-prev, tfconfig/* or the lock file. A verifier repeated it with a fresh canary, CANARY-d9e1-SECRET, and got the same result. What the plan does keep is the variable's name. internal/plans/plan.go:58-67 from the code: 

	// ApplyTimeVariables retains the names of any ephemeral variables that were
	// set (non-null) during the planning phase and must therefore be
	// re-supplied by the caller (potentially with different values) during
	// the apply phase. Ephemeral input variables are intended for populating
	// arguments for other ephemeral objects in the configuration, such as
	// provider configurations. Although the values for these variables can
	// change between plan and apply, their "nullness" may not.
	VariableValues     map[string]DynamicValue
	VariableMarks      map[string][]cty.PathValueMarks
	ApplyTimeVariables collections.Set[string]

Those are the trailing bytes above: tag e2 01 is field 28, length 2, then pw. The show -json view lists only the non-ephemeral variable, {'mode': {'value': 'wo'}}. The practical consequence: to apply a saved plan you must pass the ephemeral variables again, and an ephemeral resource such as the project's random_password is reopened at apply, so the password applied is a fresh random value, not the one that existed during plan.

Try to put the value somewhere persistent and core refuses before any provider call: feeding it into an ordinary password argument fails "Invalid use of ephemeral value … not a write-only attribute and must be persisted to state." Figure 25 maps where the ephemeral mark may go.

Core validates; it does not scrub

The mechanism behind the nulls is a check, not a filter. After PlanResourceChange, core runs internal/terraform/node_resource_abstract_instance.go:1081-1092 from the code: 

		// Providers are supposed to return null values for all write-only attributes
		writeOnlyDiags := ephemeral.ValidateWriteOnlyAttributes(
			"Provider produced invalid plan",
			func(path cty.Path) string {
				return fmt.Sprintf(
					"Provider %q returned a value for the write-only attribute \"%s%s\" during planning. Write-only attributes cannot be read back from the provider. This is a bug in the provider, which should be reported in the provider's own issue tracker.",
					n.ResolvedProvider, n.Addr, tfdiags.FormatCtyPath(path),
				)
			},
			plannedNewVal,
			schema.Body,
		)

The same check runs at refresh, apply and import. Core nulls write-only attributes itself only where it fabricates an object: test overrides, mock providers and Stacks stubs. That is internal/lang/ephemeral/strip.go:29-41, which keeps the marks on the null it substitutes: 

func (w *writeOnlyTransformer) Enter(path cty.Path, value cty.Value) (cty.Value, error) {
	attr := w.schema.AttributeByPath(path)
	if attr == nil {
		return value, nil
	}

	if attr.WriteOnly {
		value, marks := value.Unmark()
		return cty.NullVal(value.Type()).WithMarks(marks), nil
	}

	return value, nil
}

So "write-only" does not mean "sent once". Core sends the value in the configuration of every PlanResourceChange and ApplyResourceChange and demands only that it not come back. The provider decides when to act on it: at create, or when the *_wo_version changes. That is why the version argument exists, and why rotating means bumping db_password_version, not changing the password.

That design has one caveat for this project, which is reasoning and was not tested reconstruction. The ephemeral random_password is different on every run, and providers push a write-only value only when its version changes. If the database or the secret is ever recreated without a version bump, the two can silently hold different passwords, and nothing outside Terraform recorded either one except the secret store. If you copy this pattern, treat the secret store as the only record and bump the version whenever either side is replaced.
