{{S}}The fork, measured

OpenTofu began as Terraform 1.5 with a different licence. Three years on it is a different tool. It still loads .tf files, builds the same kind of graph and drives the same provider binaries, but its language, its state format and its CLI have each moved in directions Terraform did not follow, and Terraform has moved in directions it did not follow either. This section compares Terraform v1.17.0 with OpenTofu v1.13.2 (765062032c46, released 2026-10-21) with both binaries on the same box. Its claim: the two share the providers but not the newest RPCs, and two of OpenTofu's features are one-way doors.

The project, from its tree

The repository says what it is. LICENSE is MPL 2.0 with a dual copyright, the OpenTofu Authors and HashiCorp's from 2014, and forked files keep HashiCorp's MPL header under OpenTofu's. v1.13.x is supported until 1 August 2027. MAINTAINERS.md lists, among others, Martin Atkins, the go-cty author, and Spacelift's James Humphries from the code. The dependency pins have drifted: OpenTofu replaces hashicorp/hcl/v2 v2.20.1 with its own opentofu/hcl fork, while Terraform uses upstream v2.24.0, and OpenTofu is ahead on go-cty (v1.19.0 against v1.18.1) and go-plugin (v1.8.0 against v1.7.0). OpenTofu defaults to urfave/cli/v3 and keeps mitchellh/cli only behind TOFU_EXPERIMENTAL_CLI_ENABLED=false. It has a second execution engine under internal/engine, selectable only in nightly or dev builds through TOFU_X_EXPERIMENTAL_RUNTIME; releases still run the inherited graph engine. And it has no telemetry: Terraform's main.go:244-245 starts go runCheckpoint(ctx, config) on every run, which calls HashiCorp Checkpoint unless the CLI config disables it, and OpenTofu has no checkpoint code at all from the code.

Door one: providers with for_each

Terraform reserves for_each on a provider block. OpenTofu allows it, but only on an aliased configuration ("Alias required when using "for_each"", opentofu:internal/configs/provider.go:110-117), and it expands the instances at configuration load, before any graph exists. opentofu:internal/configs/provider.go:172-195 from the code:

Door two: encrypted state and plans

OpenTofu's terraform {} block accepts an encryption block. It holds labelled key_provider and method blocks plus three targets, state, plan and remote_state_data_sources, each with a method, an optional fallback for rotation, and enforced. v1.13.2 ships the key providers pbkdf2, aws_kms, gcp_kms, azure_vault, openbao and external (plus test-only ones) and the methods aes_gcm, unencrypted and external. pbkdf2 defaults to SHA-512, 600,000 iterations, a 32-byte salt and a 32-byte key from the code. The cipher is Go's GCM with a fresh nonce per write, opentofu:internal/encryption/method/aesgcm/aesgcm.go:25-45: 

func (a aesgcm) Encrypt(data []byte) ([]byte, error) {
	result, err := handlePanic(
		func() ([]byte, error) {
			gcm, err := a.getGCM(a.encryptionKey)
			if err != nil {
				return nil, &method.ErrEncryptionFailed{Cause: err}
			}

			nonce := make([]byte, gcm.NonceSize())
			if _, err := rand.Read(nonce); err != nil {
				return nil, &method.ErrEncryptionFailed{Cause: &method.ErrCryptoFailure{
					Message: "could not generate nonce",
					Cause:   err,
				}}
			}

			encrypted := gcm.Seal(nil, nonce, data, a.aad)

			return append(nonce, encrypted...), nil
		},
	)

The state file is a JSON envelope of about 1.4 kB (1,407 bytes in one run, 1,411 in a re-run; salt and base64 vary). serial and lineage stay in plaintext and are cross-checked after decryption, so backends and locks keep working. The saved plan is no longer a ZIP but the same envelope, 3,315 bytes, and tofu show decrypts it. Handed the encrypted state alone, Terraform says "Unsupported state file format: The state file does not have a "version" attribute". Figure 22 lays the envelope out. If your team might ever run Terraform against the same state, do not turn on either feature.

Smaller divergences, all measured

Version constraints. OpenTofu ignores required_version in a plain .tf file, on the assumption that it was written for "our predecessor", and enforces it only in .tofu files or through language { compatible_with }. With required_version = ">= 99.0.0" in main.tf, terraform init fails "Unsupported Terraform Core version" while tofu init and plan succeed; the same line in main.tofu makes tofu fail "Incompatible module" measured here.

Shadow files. When name.tf and name.tofu sit side by side, tofu silently ignores the .tf twin; the same holds for .tofu.json and .tofutest.hcl. With output "who" in both main.tf and main.tofu, tofu plans "tofu file", Terraform plans "tf file", and neither reports a duplicate. Code review that reads only .tf files can miss what tofu actually runs.

Exclusion. tofu plan -exclude is targeting by complement, and it removes graph descendants too. The comment on removeExcludedNodes says so (opentofu:internal/tofu/transform_targets.go:105-108):

Lifecycle. OpenTofu 1.11 added lifecycle { enabled = <bool> }, a zero-or-one repetition that excludes count and for_each; with enabled = var.on (default false) tofu planned two of three resources, and terraform validate failed "Unsupported argument". Both tools have lifecycle { destroy = false }, but they decode it differently (internal/configs/resource.go:225-229 against opentofu:internal/configs/resource.go:221-223; the two labels are mine):

A nil EvalContext means Terraform accepts only a literal; destroy = !var.keep works only in tofu. The same split runs through static evaluation in general. OpenTofu evaluates backend blocks with its StaticEvaluator, so path = var.p works; Terraform decodes backends with a nil context, so even a const variable fails "Variables not allowed" (Part 1). A module source computed from a non-const variable works in tofu and fails in Terraform 1.17 with "Only literal values and const variables can be evaluated during init." OpenTofu parses Terraform's const attribute only for compatibility, calling it, in a source comment, an "imitation of our static eval concept".

Functions. metadata functions -json lists 134 names in tofu and 119 in Terraform; every Terraform function exists in tofu, which adds fifteen: twelve assume*, base64gunzip, cidrcontains and urldecode. Both have convert(value, type), Terraform since v1.15.0 (#38160) and tofu since 1.13 (#4449), and both consoles evaluate it, yet neither tool's metadata functions lists it measured here.

Distribution. A bare hashicorp/random resolves to registry.terraform.io in Terraform and registry.opentofu.org in tofu, and tofu rewrites in-memory state addresses from the first to the second unless the configuration uses the full form. tofu installs providers and modules from OCI registries; Terraform's oci backend is Oracle Object Storage, unrelated, and is the one backend tofu lacks. tofu takes a global flock per provider, version and platform beside the plugin cache, so parallel inits can share TF_PLUGIN_CACHE_DIR; Terraform has none, which bit this lab (section 8).

One protocol, two clients

Both trees carry the same 36 RPCs. OpenTofu's tfplugin6.10.proto defines everything in Terraform's 6.11 except the 6.11 computed-block and planned-private fields; as Part 2 showed, the labels no longer track the contents in either project. The difference is in the client. Terraform core calls 34 of the 36. OpenTofu's internal/plugin6/grpc_provider.go calls 21: schemas, validation, configure, the managed-resource and ephemeral RPCs and functions, and never the list-resource, action, state-store or GenerateResourceConfig RPCs, although their messages exist in its proto file. The CLI says the same thing from the outside: modules, query and stacks are Terraform-only commands, and the other 24 are common.

The direction of travel is visible in that gap. Every surface Terraform added since 1.13 (list resources and query, actions, state_store, Stacks, Policy) sits on an RPC or a plugin that OpenTofu does not call. OpenTofu's additions (encryption, provider iteration, -exclude, enabled, OCI) sit in the language, state and distribution, where Terraform cannot read them. The providers are the shared ground. Whether OpenTofu will add client support for the newer RPCs was not established.
