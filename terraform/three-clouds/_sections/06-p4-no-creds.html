{{S}}Planning without credentials

A plan of an empty state has nothing to refresh, so in principle it needs no cloud at all. In practice every provider runs ConfigureProvider first, and what each one does there decides whether a credential-free plan is possible. The usual advice is "fake credentials plus skip flags". On these three clouds that advice is three different stories, and on one of them it does not work. This section measures each provider alone, then the full offline plan.

The probe

Each provider was planned on its own with no credentials and every ambient identity source blocked: AWS_EC2_METADATA_DISABLED=true, the GCE metadata server pointed at the closed port 127.0.0.1:9, and no az on PATH measured here.

  • aws 6.70.0 refuses. ConfigureProvider fails "No valid credential sources found", exit 1, after 9.5 seconds.
  • google 8.8.0 plans. Exit 0 after 13.9 seconds. Its authentication is lazy: it logs "Authenticating using DefaultClient", fails the universe-domain lookup, and fails the userinfo lookup locally, because the token fetch from the blocked metadata server is refused. No request reaches Google in this mode, and the plan never needs an API call.
  • azurerm 5.10.0 refuses. It must build an authorizer during configure, and with nothing else available it tries the CLI: exec: "az": executable file not found in $PATH, exit 1, after 2.3 seconds.
  • random 3.9.1 needs nothing.

AWS: a fake key and four switches

AWS is the easy case. The project's providers.tf:7-15 gives it a placeholder key pair and turns on every skip the provider offers when var.offline is true: 

provider "aws" {
  region = var.aws_region

  access_key                  = var.offline ? "AKIAOFFLINEOFFLINE00" : null
  secret_key                  = var.offline ? "offline-secret-key-not-real" : null
  skip_credentials_validation = var.offline
  skip_requesting_account_id  = var.offline
  skip_metadata_api_check     = var.offline
  skip_region_validation      = var.offline

With those four switches the provider never calls STS or the instance metadata service, and the TF_LOG=DEBUG log of the full plan has zero HTTP Request Sent lines for aws. The two data sources the module uses, aws_region and aws_iam_policy_document, compute locally measured here. This shows the set is sufficient, not that every switch is necessary. One caution comes from the lab's own history: an earlier run with a plausible bucket name reached a real bucket, which is why every globally unique name now ends in -invalid when offline is set. Fake credentials do not stop a provider from sending a request; they only make it fail.

Google: one real call, and five minutes without a network

Google would plan with nothing at all, but the project gives it access_token = "offline-token-not-real" so the provider skips its metadata probe. That mode has a cost. During ConfigureProvider the provider makes one real HTTPS request to openidconnect.googleapis.com/v1/userinfo with the fake token. Google answers 401 "Invalid Credentials"; the provider logs it at INFO, carries on with an empty identity, and the plan succeeds. The six www.googleapis.com URLs elsewhere in the log are OAuth scope strings, not requests measured here.

Take the network away and the same request becomes expensive. Run inside a network namespace with no network (unshare -rn), the full plan still succeeds with the same 36 creates and 1 action, but takes about 5 minutes 15 seconds instead of about 35: google retries the userinfo call about 68 times, logging "Dismissed an error as retryable", before it gives up. The provider work itself is about 15 seconds of that. No supported switch to suppress the call was found. If you plan in an air-gapped CI runner with the google provider, that retry loop is where the time goes.

Azure: Entra ID says no, so fake the CLI

azurerm cannot configure without a token. The obvious fake, client-secret authentication with all-zero ids, is not offline: the provider sends the ids to the Microsoft Entra ID token endpoint, which rejects them with HTTP 400 and "AADSTS700038: 00000000-0000-0000-0000-000000000000 is not a valid application identifier" measured here. So the project uses CLI authentication against a fake az, providers.tf:36-49: 

provider "azurerm" {
  features {}

  subscription_id                 = var.azure_subscription_id
  tenant_id                       = var.azure_tenant_id
  resource_provider_registrations = "none"

  # azurerm cannot be configured without a token: client-secret auth with fake
  # ids is rejected by Entra ID (AADSTS700038). Offline we use CLI auth against
  # tools/fakeaz/az (an unsigned placeholder token, put it first on PATH);
  # online we use OIDC workload identity federation from CI.
  use_cli  = var.offline
  use_oidc = !var.offline
}

tools/fakeaz/az is a 21-line shell script. It answers exactly four commands, az version, az account show, az account list and az account get-access-token, the last with a JWT whose header is {"alg":"none","typ":"JWT"}, and exits 1 on anything else. Its own comment says it "grants nothing: any real ARM call with it fails with 401". During the plan the provider called it exactly four times, the last time asking for a Microsoft Graph token (--scope https://graph.microsoft.com/.default), and made no network calls. The first version of the shim lacked account list, and configure failed until it was added measured here.

The audit, and what cannot be faked

Put together, the offline plan's traffic is small and fully accounted for. aws sends nothing: no STS, no IMDS, no API call, because state is empty and nothing refreshes. google sends one HTTPS request and gets a 401. azurerm runs four local az commands. random does nothing. Re-running the plan with no network at all confirmed it: only google attempted a connection measured here.

terraform query is the command no fake can rescue. A list block calls the provider's ListResource RPC, which makes live API calls by design. With the aws s3 and sts endpoints pointed at the closed port, the run logged nine HTTP Request Sent … tf_rpc=ListResource lines, turned limit = 5 into max-buckets=5 on S3 ListBuckets, and failed after 58 seconds with "exceeded maximum number of attempts, 9". In another lab, a query against the real AWS endpoint with fake keys got "401 … AuthFailure" and wrote no configuration. Offline, only terraform validate -query is available, and it checks the file, not the cloud. Part 3 covers what query does with real credentials.

The general lesson is about where authentication happens. aws checks credentials only if asked to, google checks them lazily and tolerates failure, and azurerm cannot build a client without a token. None of that is in Terraform core; it is each provider's ConfigureProvider, one RPC from Part 2's table, doing what its SDK and authors chose.
