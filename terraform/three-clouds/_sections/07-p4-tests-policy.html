{{S}}Tests and policy on the project

Two features promise to check a configuration before anything is applied: terraform test with mock providers, and Terraform Policy. Both ran on the project with no credentials. Both did something, and neither did quite what its name suggests. The claim of this section: mocks are not isolation, and local policy is not enforcement.

The suite

Seven runs in three files. tests/plan.tftest.hcl has five plan-only runs: the default shapes, a two-environment fan-out asserting two instances of each cloud module, a bad CIDR and an online-mode project id that must fail validation (expect_failures = [var.environments] and [var.gcp_project]), and two environments with the same CIDR, which must only warn (expect_failures = [check.environment_cidrs_disjoint] passes because a failing check is a warning). tests/apply.tftest.hcl runs one mocked apply of all three clouds and asserts on provider-function outputs. tests/override.tftest.hcl holds one run with an override_resource. The result is "Success! 7 passed, 0 failed." in about 42 to 65 seconds on two vCPUs measured here.

A mock wraps the real binary

mock_provider does not replace the provider. Its doc comment says the mock "wraps an instance of an actual provider so it can return the correct schema and validate the configuration accurately", and only intercepts creating resources and reading data sources (internal/providers/mock.go:18-25). The mock empties the provider's own configuration schema, so mock_provider "aws" needs no region or keys, and keeps every resource, data source and ephemeral schema. Some calls go straight through, mock.go:314-321 and 410-416 from the code: 

func (m *Mock) ImportResourceState(request ImportResourceStateRequest) (response ImportResourceStateResponse) {
	// You can't import via mock providers. The users should write specific
	// `override_resource` blocks for any resources they want to import, so we
	// just make them think about it rather than performing a blanket import
	// of all resources that are backed by mock providers.
	response.Diagnostics = response.Diagnostics.Append(tfdiags.Sourceless(tfdiags.Error, "Invalid import request", "Cannot import resources from mock providers. Use an `override_resource` block to targeting the specific resource being imported instead."))
	return response
}
…
func (m *Mock) CallFunction(request CallFunctionRequest) CallFunctionResponse {
	return m.Provider.CallFunction(request)
}

func (m *Mock) ListResource(request ListResourceRequest) ListResourceResponse {
	return m.Provider.ListResource(request)
}

In a traced test, the real plugin started once to serve its schema; no ConfigureProvider, plan or apply call crossed the wire, but ValidateResourceConfig did (Part 2). The project ran into all three consequences measured here:

  • Mock values must pass real validation. The mock invents random strings for computed attributes, and the real provider then validated them where they flowed into arguments. Random strings failed azurerm's ARM-id parsing, google's network-URL pattern and aws's IAM policy JSON until the tests/mocks/*/*.tfmock.hcl files supplied realistic defaults.
  • Functions run for real. Because CallFunction is forwarded, a test asserting on provider::aws::trim_iam_role_path exercised the real implementation, which is how the ARN-not-name behaviour of section 4 was found.
  • A list block in a test would call the cloud. ListResource is forwarded too, so the project keeps list blocks out of its tests. That one is read from the code, not exercised.

Actions are faked in the other direction: the mock's PlanAction returns an empty response and InvokeAction yields one Completed event, so a mocked action_trigger always "succeeds" (mock.go:450-461). The lower table of Figure 26 summarises the boundary. A test with every provider mocked still needs the real provider binaries, still validates against real rules, and is not proof that anything would work against a cloud.

Runs share state, and overrides only fill computed values

Runs in one test file share one state per module. The project's first attempt put an override_resource on the VPC in a later apply run of apply.tftest.hcl; the VPC already existed from the earlier run, kept its mocked id, and the assertion failed. Moved to its own file it passed, tests/override.tftest.hcl:22-37: 

run "override_one_resource" {
  command = apply

  # override_resource pins values for one address, beating mock defaults.
  override_resource {
    target = module.aws["dev"].aws_vpc.this
    values = {
      id = "vpc-0123456789abcdef0"
    }
  }

  assert {
    condition     = output.aws["dev"].vpc_id == "vpc-0123456789abcdef0"
    error_message = "override_resource should fix the VPC id."
  }
}

Ephemeral resources are mockable since v1.17 (#38928, commit 61ef933f6f of 2026-09-04): mock_ephemeral "random_password" in tests/mocks/random/random.tfmock.hcl supplies result = "mock-password-not-secret", the mock's OpenEphemeralResource fills from those defaults, and renew and close are no-ops.

Policy offline, and policy in plan

policies/storage.policy.hcl has one rule per cloud. The AWS rule, lines 22-27: 

resource_policy "aws_s3_bucket_public_access_block" "all_blocked" {
  enforce {
    condition     = attrs.block_public_acls && attrs.block_public_policy && attrs.ignore_public_acls && attrs.restrict_public_buckets
    error_message = "S3 public access block must enable all four switches."
  }
}

The language is HCL with its own blocks: a policy block with its own required_providers, then resource_policy and module_policy blocks whose enforce blocks pair a condition with an error_message, plus filter, enforcement_level, input and locals; a rule reads the planned values through attrs, the prior ones through prior_attrs, and metadata through meta from the docs. The project's Azure rule is marked enforcement_level = "advisory", the GCP rule has two enforce blocks.

The standalone tfpolicy CLI evaluates that offline against its own tests, and the same policy handed to terraform plan is not evaluated at all measured here:

The six policy tests (three pass, three expected failures) took 12.9 to 24.2 seconds. --policies and --tests must name directories; the docs' single-file form failed "not a directory". The first runs installed both the lowest and the highest provider version matching each constraint, about 2.2 GB, after which a 17 MB schema cache sufficed. A verifier did not re-run the tfpolicy side; the plan side is confirmed from the recorded run.

The plan result has two causes. The fail-open is deliberate, internal/command/plan.go:106-116: 

	if len(args.PolicyPaths) > 0 {
		client, policyDiags, stopClient := c.PolicyClient(c.CommandContext(), args.PolicyPaths, backendPolicyEntitlement(be, policy.PlanEvaluationStage))
		// if there has been any errors when setting up the policy client, we log them but
		// we still proceed with the operation, as a failure to set up the policy client
		// should not prevent the plan operation from running
		if opReq.View != nil && policyDiags != nil {
			opReq.View.PolicyDiagnostics(policyDiags)
		}
		opReq.PolicyClient = client
		defer stopClient()
	}

apply behaves the same, while init -policies returns 1 on the same setup diagnostics (internal/command/init_run.go:294-299). And the setup fails because a local backend supplies no entitlement. Core's comment on the field says "Nil means the plugin skips the check" (internal/policy/policy.go:71-74); tfpolicy-plugin 0.5.0 does not skip it. Real enforcement appears to need a cloud or remote backend with an entitled organization; that is inferred from backendPolicyEntitlement, not measured. Whether any plugin version honours the nil comment is open; only 0.5.0 was tested.

The practical rule: in CI, a zero exit code from plan -policies proves nothing about policy. Run tfpolicy test as its own step, or check the output for "Failed to setup Terraform Policy connection". Figure 23 shows where the plugin sits, and Part 3 traces the GA entry and its PR-number mismatch.
