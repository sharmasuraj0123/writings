01One plan, five data structures

Terraform is a compiler whose intermediate representation is a dependency graph and whose back end is somebody else's process. A terraform plan turns bytes into tokens, tokens into a syntax tree, the tree into a configuration tree, the configuration into a graph, the graph into calls to provider processes, and the answers into a plan file. Each stage hands the next a different Go type. This collection reads Terraform v1.17.0 along those boundaries, because that is where its surprises live. Part 1 covers the front end: everything up to the moment a configs.Config exists and its providers are installed. Parts 2 to 4 take the graph, the state and the outside world.

Three design choices explain most of what follows. HCL parses without meaning: its parser builds attributes and blocks without knowing which names are legal, and meaning arrives only when a schema is applied. The graph is the program: ordering, parallelism and failure isolation are edges, not code paths. And trust lives in core while data lives outside: providers are untrusted child processes whose answers are checked, and the record of what exists is one JSON document. This part is about the first choice and what it costs.

The five hand-offs

Bytes to a syntax tree. HCL's native syntax is three sub-languages in one file: structural (bodies, blocks, attributes), expression, and template (hcl/hclsyntax/spec.md:10-21) from the code. hclsyntax.ParseConfig runs a scanner generated by Ragel from five state machines, then a hand-written recursive-descent parser, and returns an *hclsyntax.Body: a map of attributes and a slice of blocks. §02 and §03 take those two apart.

Syntax tree to configuration. configs.Parser.LoadConfigDir sorts a directory's files into categories, decodes each .tf file against configFileSchema (15 block types, no attributes) and folds the results into one configs.Module (internal/configs/parser_config_dir.go:48-64; parser_config.go:324-387) from the code. Since v1.15 the tree of modules, a configs.Config, is built by walking a small graph of its own, the init graph, with operation walkInit and parallelism 1 (internal/terraform/config_graph_build.go:15-38, 97-112). In v1.17.0 the old recursive builder, configs.BuildConfig, is gone; it was deleted on 4 September 2026 in c6e867653. The init graph is small: for a configuration whose only early expression is a provider requirement, a trace shows three vertices, and one terraform init builds and walks it twice measured here. §04 to §09 cover this stage, including what terraform init installs.

Configuration to graph. The plan builder runs 31 top-level GraphTransformers (36 counting the five provider sub-steps) over a dag.AcyclicGraph of resources, checks it for cycles with Tarjan's strongly-connected-components algorithm, and walks it with one goroutine per vertex under a -parallelism semaphore of 10 (internal/terraform/graph_builder_plan.go:174-331; internal/dag/dag.go:244-265) from the code. Resource instances do not exist in that graph; they appear in subgraphs once count and for_each are known. That is Part 2.

Graph to provider calls. Each provider is a separate executable started by go-plugin, which checks a magic cookie in the environment and then talks gRPC: the tfplugin6 service declares 36 RPCs (docs/plugin-protocol/tfplugin6.proto:350-430) from the code. One terraform plan of one random resource started the provider three times: once for the schema, once for the validate walk, once for the plan walk measured here. Part 2 follows those processes.

Answers to a plan and a state. A saved plan is a ZIP holding a protobuf plan, two state snapshots, a snapshot of the configuration and the lock file (internal/plans/planfile/writer.go:54-139). State is one version-4 JSON document per workspace, rewritten whole through a statemgr.Full (internal/states/statemgr/statemgr.go:12-29) from the code. Part 3 starts there.

Where the surprises sit

Each boundary in Figure 1 is a point where one stage knows something the next does not, and the well-known Terraform puzzles line up with them. dynamic "lifecycle" is rejected because the syntax tree is decoded twice, and only the second decode, against the provider's schema, expands dynamic blocks (§04). prevent_destroy = var.protect fails with "Variables not allowed" because meta-arguments are decoded at the configuration stage, before any value exists (§04). local.u == "x" || true is true at plan time although local.u is unknown, because values carry more information than "known" or "unknown" (§05). A module source may now be local.mod_dir, but only if that local comes from a const variable, because the configuration tree is built on a graph where nothing else has a value yet (§08). And terraform init asks the registry for versions even with a lock file and a warm cache, because the installer was built to complete the lock file, not to work offline (§09). The later boundaries have their own: core rejects a provider's answer that contradicts its own plan (Part 2), and an S3 backend configured with neither use_lockfile nor a DynamoDB table takes no lock at all (Part 3).

None of these is a bug. Each follows from which stage owns which fact. A practitioner reading a confusing error can usually ask one question first: which of the five structures existed when this was checked?

The examples below come from a lab directory per topic, run with the v1.17.0 binary and only the built-in terraform provider or random, so nothing in this part touched a cloud measured here. Section 10 lists what each claim rests on.

02Bytes to tokens

HCL's specification describes three sub-languages that share one file. The structural language is bodies, blocks and attributes. The expression language is values, operators and calls. The template language is what lives between quotes and inside heredocs (hcl/hclsyntax/spec.md:10-21) from the code. The structural grammar is five productions, and it is short enough to quote whole (hcl/hclsyntax/spec.md:160-164): 

ConfigFile   = Body;
Body         = (Attribute | Block | OneLineBlock)*;
Attribute    = Identifier "=" Expression Newline;
Block        = Identifier (StringLit|Identifier)* "{" Newline Body "}" Newline;
OneLineBlock = Identifier (StringLit|Identifier)* "{" (Identifier "=" Expression)? "}" Newline;

Two details in it matter later. An attribute ends with a Newline, so line breaks are part of the grammar and the parser has to know when to ignore them (§03). And nothing in it names a block type: there is no resource or variable keyword. Identifiers are Unicode UAX #31, ID_Start (ID_Continue | '-')*, and HCL has no globally reserved words, only words that mean something in a given position (spec.md:98, 115-116) from the code. Every word Terraform cares about is given meaning later, by a schema.

Five machines in one generated file

hclsyntax.ParseConfig calls LexConfig, which runs scanTokens in scanNormal mode. The scanner is written in Ragel, a state-machine compiler, in scan_tokens.rl. It is compiled into scan_tokens.go, which is 5,273 lines at HCL v2.24.0, the version Terraform v1.17.0 ships, and 6,042 on HCL main after a Unicode 17 regeneration measured here. The .rl file defines five machines: main for structure and expressions, stringTemplate for quoted strings, heredocTemplate, bareTemplate for standalone templates and JSON strings, and identOnly (scan_tokens.rl:255-315). The scan mode picks the entry machine: scanNormal starts in main, scanTemplate in bareTemplate, scanIdentOnly in identOnly (scan_tokens.rl:330-339) from the code.

Before any machine runs, scanTokens calls stripUTF8BOM on the input and shifts the start position by however many bytes it removed (scan_tokens.rl:20-23). Hold that thought; the spec says something different.

Templates inside expressions inside templates

The scanner's hard job is nesting. A template can contain an interpolation, the interpolation is an expression, the expression can contain an object constructor with braces, and the object can contain another string with a } in it. A regular language cannot count, so the scanner uses two Ragel features and a little Go state. fcall pushes the current machine on a stack and jumps to another; fret pops back. A counter, braces, tracks brace depth, and a slice, retBraces, remembers the depth at which each interpolation began. hcl/hclsyntax/scan_tokens.rl:171-179 and 196-206 from the code: 

        action beginTemplateInterp {
            token(TokenTemplateInterp);
            braces++;
            retBraces = append(retBraces, braces);
            if len(heredocs) > 0 {
                heredocs[len(heredocs)-1].StartOfLine = false;
            }
            fcall main;
        }
        …
        action closeBrace {
            if len(retBraces) > 0 && retBraces[len(retBraces)-1] == braces {
                token(TokenTemplateSeqEnd);
                braces--;
                retBraces = retBraces[0:len(retBraces)-1]
                fret;
            } else {
                token(TokenCBrace);
                braces--;
            }
        }

A " in main emits TokenOQuote and fcalls into stringTemplate. Inside the string, ${ or %{ emits an interpolation or control token, increments braces, pushes it, and fcalls back into main. From then on every } asks one question: is the brace depth exactly the depth this interpolation opened at? If so, the } closes the interpolation, emits TokenTemplateSeqEnd and returns to the string. If not, it is an ordinary TokenCBrace. A } inside a nested string never reaches closeBrace at all, because stringTemplate treats it as literal text. Figure 2 runs one line through these rules by hand.

Heredocs, escapes and the token alphabet

Heredocs need their own state because the closing marker is a whole line. beginHeredocTemplate slices the marker out of <<EOT or <<-EOT and pushes it on a heredocs stack. A line ending in a newline is the closer only if its bytes.TrimSpaced text equals the marker. When it is, the scanner emits TokenCHeredoc and then, separately, a TokenNewline for the newline after it. The comment says why: otherwise the closing marker would swallow "a newline that would normally be used to mark the end of an attribute definition" (scan_tokens.rl:100-157) from the code. That is the grammar's Newline rule leaking into the lexer. Escapes are similar small rules: $${ and %%{ produce a literal ${ and %{, and a $ not followed by { is held back and stays text (scan_tokens.rl:235-237).

Token types are Go runes chosen to be readable in a debugger: TokenOQuote = '«', TokenCQuote = '»', TokenTemplateInterp = '∫', TokenTemplateControl = 'λ', TokenTemplateSeqEnd = '∎', TokenEOF = '␄' and, for invalid UTF-8, TokenBadUTF8 = '💩' (hclsyntax/token.go:28-109) from the code. Single-line comments absorb their newline, so when the peeker filters comments out it puts a TokenNewline back, and x = 1 # note still ends its attribute (peeker.go:73-104).

Tokens for characters HCL does not use

The scanner also recognises characters the language never uses: &, |, ^, ~, ;, the backtick and the apostrophe. It emits tokens for them so that checkInvalidTokens can say something useful, such as "Single quotes are not valid", instead of a bare parse error (token.go:87-103, 186-323) from the code. Two of those friendly messages can never fire. checkInvalidTokens has cases for TokenStarStar ("**" is not a supported operator) and TokenTabs ("Tab characters may not be used"), but nothing in the scanner emits either token: they appear only at token.go:96, 100, 224 and 273, and main's whitespace rule is Spaces = (' ' | 0x09)+, tab included (scan_tokens.rl:88). The result, from terraform validate measured here: 

x = 2 ** 3          → Error: Invalid expression (Expected the start of an expression, but found an invalid expression token.)
x = 'a'             → Error: Invalid character (Single quotes are not valid...)
<TAB>x = 1          → Success!   (despite the "Tab characters may not be used" diagnostic existing)
<BOM>locals {...}   → Success!

Line breaks inside quotes get a token of their own too. In stringTemplate a newline emits TokenQuotedNewline, so a quoted string that runs onto a second line produces "Invalid multi-line string" and "Unterminated template string" rather than silently joining the lines (scan_tokens.rl:260; token.go:295-301) from the code. Multi-line text belongs in a heredoc. Once the parser has reported one syntax error it sets a recovery flag that suppresses the follow-on "bad token" errors, so a file with two mistakes reported only the first measured here. Fix, re-run, repeat.

The spec and the scanner disagree; the code wins

Three statements in spec.md are not what the scanner does. The spec says "UTF-8 encoded Unicode byte order marks are not permitted" (spec.md:61-62); the scanner has stripped a leading BOM since HCL commit 291f7fb, "Accept and ignore UTF-8 byte order marks", on 19 December 2018, and the spec text was never updated. The tab diagnostic implies tabs are rejected; they are whitespace. And the spec's Identifier starts with ID_Start, while the scanner's rule is Ident = (ID_Start | '_') (ID_Continue | '-')*, so a leading underscore is accepted (scan_tokens.rl:46 against spec.md:98) from the code.

For a practitioner the rule is simple: when the HCL spec and terraform validate disagree, validate is the language. A file indented with tabs, or saved by an editor that writes a BOM, is valid Terraform; terraform fmt will turn the tabs into two spaces. The scanner is wider than the spec, never narrower: every gap found accepts more input, not less reconstruction.

03Recursive descent, and why parser shape is graph shape

HCL's parser is hand-written recursive descent: one Go function per grammar rule, each calling the next. It reads tokens through a peeker, and the interesting state in the peeker is a single slice of booleans. Line numbers below are from HCL main; at v2.24.0, the version Terraform v1.17.0 ships, parser.go lines above about 370 sit 9 or 10 lower, with identical code.

Newlines are a stack

The grammar says an attribute ends with a newline, but nobody wants a newline inside a function call's argument list to end anything. The peeker solves this with IncludeNewlinesStack, initialised to []bool{true} (hclsyntax/peeker.go:41-48). Opening a parenthesis, a bracket, a call or a for expression pushes false; an object constructor pushes true; each closer pops. While the top is false, Peek skips TokenNewline. ParseConfig checks that the stack is back to its one entry at the end (peeker.go:106-123; parser.go:882, 968, 1239, 1426-1434, 1590) from the code. The consequences are easy to reproduce with terraform validate measured here: 

x = 1 +⏎ 2          → Error: Invalid expression
x = (1 +⏎ 2)        → Success!
x = true⏎ ? 1⏎ : 2  → Error: Argument or block definition required
locals { x = 1, y = 2 } → Error: Invalid single-argument block definition
x = foo.0.0         → Error: Invalid legacy index syntax

At body level the newline after + ends the attribute, so the expression is incomplete. Inside parentheses the same newline is invisible. A ternary cannot start a continuation line with ?, because by then the attribute has ended and the parser expects a new attribute or block. The practical rule: to break a long expression across lines, wrap it in parentheses. The last line is a lexer effect, not a parser one: 0.0 scans as one number, so the legacy foo.0 index syntax still works once but not twice (parser.go:660-705) from the code.

A body is a map and a slice, with no schema

ParseBody loops until its end token. It skips newlines, and for each identifier calls ParseBodyItem, which decides between attribute and block by looking one token ahead. hcl/hclsyntax/parser.go:157-161 from the code: 

	switch next.Type {
	case TokenEqual:
		return p.finishParsingBodyAttribute(ident, false)
	case TokenOQuote, TokenOBrace, TokenIdent:
		return p.finishParsingBodyBlock(ident)

Attributes go into a map keyed by name, where a duplicate is the only structural error ("Attribute redefined"). Blocks go into a slice in source order (parser.go:27-139). Nothing here knows that resource takes two labels or that count is special. A misspelled block type parses perfectly; it fails later, when a schema is applied (§04). The parser does have opinions about block shape, and they show as specific messages: locals = {} is "Unsupported argument", locals followed by { on the next line is "Argument or block definition required", and commas between arguments are "Unexpected comma after argument" measured here.

Precedence is the order of a slice

Expressions descend through four functions. parseTernaryConditional parses a condition with parseBinaryOps(binaryOps), and if a ? follows, parses both arms with the full ParseExpression, which makes ?: right-associative and looser than || (parser.go:491-550). parseBinaryOps handles the operators. parseExpressionWithTraversals handles .attr, [index] and splats after a term. parseExpressionTerm handles literals, names, calls, parentheses and the unary - and !, whose operand is a term with traversals, so -46+5 is (-46)+5 and a negative number is a UnaryOpExpr, not a literal (parser.go:1074-1103) from the code.

There is no precedence table in the usual sense, and no operation.go. The levels are the order of a Go slice of maps, lowest first. hcl/hclsyntax/expression_ops.go:167-193 from the code: 

	binaryOps = []map[TokenType]*Operation{
		{
			TokenOr: OpLogicalOr,
		},
		{
			TokenAnd: OpLogicalAnd,
		},
		{
			TokenEqualOp:  OpEqual,
			TokenNotEqual: OpNotEqual,
		},
		{
			TokenGreaterThan:   OpGreaterThan,
			TokenGreaterThanEq: OpGreaterThanOrEqual,
			TokenLessThan:      OpLessThan,
			TokenLessThanEq:    OpLessThanOrEqual,
		},
		{
			TokenPlus:  OpAdd,
			TokenMinus: OpSubtract,
		},
		{
			TokenStar:    OpMultiply,
			TokenSlash:   OpDivide,
			TokenPercent: OpModulo,
		},
	}

parseBinaryOps(ops) takes ops[0] as "this level" and ops[1:] as everything tighter. It parses a left operand by recursing on the tighter levels, then loops while the next token is one of this level's operators, folding left. hcl/hclsyntax/parser.go:585-607 (576-598 at v2.24.0) from the code: 

	for {
		next := p.Peek()
		var newOp *Operation
		var ok bool
		if newOp, ok = thisLevel[next.Type]; !ok {
			break
		}

		// Are we extending an expression started on the previous iteration?
		if operation != nil {
			lhs = &BinaryOpExpr{
				LHS: lhs,
				Op:  operation,
				RHS: rhs,

				SrcRange: hcl.RangeBetween(lhs.Range(), rhs.Range()),
			}
		}

		operation = newOp
		p.Read() // eat operator token
		var rhsDiags hcl.Diagnostics
		rhs, rhsDiags = p.parseBinaryOps(remaining)

This is precedence climbing with the table as data. When the slice runs out, the recursion bottoms out in parseExpressionWithTraversals. Adding an operator level would be one more map in the slice. The measured results match the table: 1 + 2 * 3 - 4 / 2 is 5, true || false && false is true, -2 * -3 is 6, and false ? 1 : true ? 2 : 3 is 2 measured here. true, false and null are keywords only in term position and only when not followed by ( or ::; every other leading identifier becomes a ScopeTraversalExpr (parser.go:1016-1050).

Traversals: extended in place, or broken out

After a term, parseExpressionWithTraversals loops over .name, [key], .* and [*]. For an attribute step, or an index whose key is a literal or a literal-only string template, it calls makeRelativeTraversal, which appends the step to an existing ScopeTraversalExpr "in place (mutating it)". For any other key, such as var.i, it wraps what it has so far in an IndexExpr, and later steps become a RelativeTraversalExpr around that (parser.go:901-927, 938-959) from the code. Splats compile to SplatExpr{Source, Each, Item}, where Item is an AnonSymbolExpr placeholder that Each is evaluated against once per element (parser.go:859-877).

The two splat spellings are not synonyms. The full splat [*] applies every following step to each element, so x[*].a[0] takes element 0 of each a. The attribute-only splat .*, kept from Terraform 0.11's HIL, stops absorbing steps at the first index, so x.*.a[0] indexes the resulting list and returns the first element's a (spec.md:594-610; parser.go:707-811) from the code. A splat on a single non-list value wraps it in a one-element tuple, and on a null non-list value gives [], while a splat of a null list is the error "Splat of null value" (expression.go:1807-1823, 1800-1816 at v2.24.0) measured here. A splat is a cheap way to turn "maybe one object" into "a list of zero or one".

The reason this is more than tidiness: Terraform builds its dependency graph from references, and it finds references by calling Expression.Variables(), which returns the expression's root traversals, then parsing each with addrs.parseRef. The roots it understands are count, each, data, resource, ephemeral, list, local, module, path, self, caller, terraform, var and action; template, lazy and arg are reserved; any other root is a managed resource type (internal/addrs/parse_ref.go:199-437) from the code. So aws_instance.web[0].id arrives as one traversal that names an instance, and aws_instance.web[var.i].id arrives as two: the resource as a whole, and var.i. The parser decides which references exist, and the graph in Part 2 is built from exactly those reconstruction.

Templates that unwrap, and the newest token

Two more parser rules surprise people. A template that is exactly one interpolation is a passthrough: when the parts are one interpolation plus the synthetic end token, parseTemplateInner sets passthru, and the result is a TemplateWrapExpr that keeps the inner value's type (parser_template.go:39-60). So type("${true}") is bool, while type("x${true}") is string measured here. That is why terraform fmt can rewrite a lone "${var.x}" to var.x without changing meaning.

And :: is the newest token. Namespaced function calls such as provider::aws::arn_parse(…) arrived in HCL v2.20.0 for Terraform 1.8. The scanner emits TokenDoubleColon, and the parser glues the segments into one name string, nameStr + "::" + …, with a comment explaining that this keeps the API unchanged for code written before namespaces existed (parser.go:1178-1208) from the code. The grammar in spec.md still has no :: in its FunctionCall rule; it is one more place where the code is the specification.

04Decode twice

The parser's output, an *hclsyntax.Body, is exposed to callers as the interface hcl.Body, and that interface is deliberately opaque. Its comment says "the content of a body cannot be meaningfully interpreted without a schema", and it offers exactly three ways in: Content, PartialContent and JustAttributes (hcl/structure.go:38-77) from the code. This is the first of the three design choices from §01, "parse without meaning", and this section is about what Terraform does with it.

A schema is a list of names

An hcl.BodySchema is shallow. It lists attribute names, each with a Required flag, and block types, each with its label names. It has no types and no nesting (hcl/schema.go:6-24) from the code. PartialContent(schema) pulls out the attributes and blocks the schema names and returns a second body, the remain, that hides them. Content(schema) is PartialContent plus an error for anything left over: "Unsupported argument" or "Unsupported block type", with a "did you mean" suggestion (hclsyntax/structure.go:30-42, 56-231). Even the number of labels is checked here, not in the parser: "Extraneous label for resource" and "Missing name for resource" come from applying the schema (structure.go:178-218).

So a .tf file is understood one level at a time. configs.parseConfigFile first sniffs required_version and experiments with partial schemas, then applies configFileSchema with Content, and hands each block to its own decode*Block function (internal/configs/parser_config.go:98-322) from the code. §06 lists the fifteen block types; §07 explains why the version is sniffed first.

The first decode keeps most of the block

A resource block holds two kinds of thing: arguments that mean something to Terraform (count, for_each, provider, depends_on, lifecycle) and arguments that mean something only to the provider (bucket, ami, tags). Terraform does not know the second kind; the provider's schema arrives over gRPC much later. So decodeResourceBlock takes only what it owns and keeps the rest as an undecoded body. internal/configs/resource.go:136-138 and 961-970 from the code: 

	content, remain, moreDiags := block.Body.PartialContent(ResourceBlockSchema)
	diags = append(diags, moreDiags...)
	r.Config = remain
…
var ResourceBlockSchema = &hcl.BodySchema{
	Attributes: commonResourceAttributes,
	Blocks: []hcl.BlockHeaderSchema{
		{Type: "locals"}, // reserved for future use
		{Type: "lifecycle"},
		{Type: "connection"},
		{Type: "provisioner", LabelNames: []string{"type"}},
		{Type: "_"}, // meta-argument escaping block
	},
}

r.Config is an hcl.Body with the meta-arguments hidden. Nothing checks it at load time. A misspelled provider argument is not an error yet, because nobody can say what the provider's arguments are. The meta-arguments, by contrast, are checked at once. count and for_each are kept as unevaluated expressions for the walk, but having both is rejected during this first decode with "Invalid combination of "count" and "for_each"" (resource.go:161-172) measured here. The third entry point, JustAttributes, is for bodies that have no schema at all: locals is decoded that way, so any name is legal there and only duplicates across locals blocks are errors (named_values.go:525-550).

The second decode happens during the walk

When the graph walk reaches a resource (Part 2), the provider's schema is available as a configschema.Block. DecoderSpec() turns that schema into an hcldec.ObjectSpec, using tuple or object specs where nested blocks have dynamic types, and caches the spec per schema pointer (internal/configs/configschema/decoder_spec.go:76-182). Then two scope methods do the work. internal/lang/eval.go:33-43 from the code: 

func (s *Scope) ExpandBlock(body hcl.Body, schema *configschema.Block) (hcl.Body, tfdiags.Diagnostics) {
	spec := schema.DecoderSpec()

	traversals := dynblock.ExpandVariablesHCLDec(body, spec)
	refs, diags := langrefs.References(s.ParseRef, traversals)

	ctx, ctxDiags := s.EvalContext(refs)
	diags = diags.Append(ctxDiags)

	return dynblock.Expand(body, ctx), diags
}

ExpandBlock finds the references inside any dynamic blocks, builds an evaluation context with their values, and wraps the body in dynblock's expanding body. EvalBlock then collects the references in the block, builds a context, applies blocktoattr.FixUpBlockAttrs (a compatibility shim that lets list-of-object attributes be written as nested blocks, as in Terraform 0.11), and calls hcldec.Decode(body, spec, ctx). The result is a cty.Value object of the schema's implied type (eval.go:45-80) from the code. Figure 4 puts the two decodes on one page.

Two quirks that fall straight out

dynamic cannot generate lifecycle. dynamic is not Terraform syntax; it is an HCL extension. dynblock adds a dynamic block type, with one label, to every schema it is asked about, and its body takes for_each (required), iterator, labels and one content block (hcl/ext/dynblock/schema.go:8-53) from the code. Terraform only wraps the provider remainder with it. lifecycle was taken out by ResourceBlockSchema before any dynblock existed, so dynamic "lifecycle" is just an unknown block type at the first decode, and terraform validate says "Unsupported block type" measured here. The same holds for provisioner, connection and every other meta-argument block.

Expansion is lazy: it happens when Content or PartialContent is called on the wrapped body. A known for_each makes one child iteration per element. An unknown one makes a single placeholder. hcl/ext/dynblock/expand_body.go:222-236 from the code:

Meta-arguments must be literals. Everything Terraform must know before a graph exists is decoded with gohcl.DecodeExpression(attr.Expr, nil, …): a nil EvalContext. That covers prevent_destroy, create_before_destroy, the destroy flag in lifecycle and in removed, and on variables sensitive, nullable, const and default (resource.go:206-229; named_values.go:114-174) from the code. With no context, any reference fails in HCL's Traversal.TraverseAbs with "Variables not allowed" and "Variables may not be used here." (hcl/traversal.go:96-103). v1.17.0 then adds a second error, "Unsuitable value type" measured here. Type constraints are stricter still: they are never evaluated at all. typeexpr reads list(string) structurally with hcl.ExprAsKeyword and hcl.ExprCall, so no function named list ever runs, and optional(type, default) evaluates its default with a nil context (hcl/ext/typeexpr/get_type.go:22-70, 195-288).

Two lifecycle arguments look like expressions but are read as syntax. ignore_changes is either the keyword all or a list of relative traversals; the legacy quoted-string form is still shimmed, and ["*"] is now an error (resource.go:231-290). replace_triggered_by is a static list of resource references in which only count.index and each.key may appear inside index brackets (resource.go:735-800) from the code. Neither is ever evaluated as a value; Terraform inspects the expression's shape, the way typeexpr does, and turns it into addresses.

The practical consequence: a value that has to differ per environment cannot go into prevent_destroy, a destroy flag or a type constraint. It has to be written as a literal in each configuration that needs it.

The JSON syntax reuses everything after parsing

.tf.json files show how little the decoder depends on syntax. JSON has no distinction between an attribute and a block, so the schema decides: a property is a block if the schema asks for a block of that name. Block labels become nested object levels, arrays allow repeated blocks, and a property named "//" is a comment (hcl/json/spec.md:45-95) from the code. Every JSON string in an expression position is parsed as a native template, so "${ a + b }" is an expression. In static contexts such as depends_on and ignore_changes, the string is parsed as a native expression instead (json/spec.md:327-405). A .tf.json with "count": "${length(var.names)}" planned two instances, and type(local.count_str) was number, because the template unwrapped measured here.

That is the shape of the whole design. The parser builds an untyped tree. Terraform applies a tiny schema for what it owns and defers the rest to whoever owns it. Every new language feature, from import to action, has arrived as one more small schema in internal/configs plus a decoder function, which is what §06 maps reconstruction.

05Values: numbers, unknowns and marks

Every value Terraform evaluates is a go-cty cty.Value, and the type is small enough to quote. go-cty/cty/value.go:30-33 from the code: 

type Value struct {
	ty Type
	v  any
}

ty is one of a closed set: Bool, Number and String; List, Map and Set; Object (including objects with optional attributes) and Tuple; Capsule for opaque Go values; and DynamicPseudoType, the "any" type (cty/list_type.go:17 and siblings) from the code. v is where the interesting things live: a real payload, or a sentinel meaning "unknown", or a wrapper carrying marks. The comment above the struct divides cty's methods into "operation methods", which stay inside the type system and handle unknowns, and "integration methods", which leave it and may panic on an unknown or marked value. Terraform lives almost entirely in the first kind. The go-cty citations here are from an untagged clone past v1.19.0; Terraform pins v1.18.1, and equivalence of these lines was not verified.

Numbers are 512-bit

A number literal becomes a big.Float through cty.ParseNumberVal, which calls big.ParseFloat(s, 10, 512, big.ToNearestEven) (cty/value_init.go:42-56) from the code. That is more precision than any float64, and it shows measured here: 

$ echo '1 + 2 * 3 - 4 / 2' | terraform console      → 5
$ echo '0.1 + 0.2 == 0.3' | terraform console       → true
$ echo '9007199254740993 + 0' | terraform console   → 9007199254740993
$ echo 'pow(2, 1024)' | terraform console
  Error: Error in function call ... Call to function "pow" failed: result is not a number.

The HCL spec says numbers have "arbitrary precision"; the implementation is a 512-bit mantissa, and functions such as pow and log go through float64. Since v1.17.0 (#39304) a result of infinity is an error instead of a value. For a practitioner the arithmetic is exact enough that 0.1 + 0.2 == 0.3 holds, which it does not in most languages; the edges are the float64 functions.

Operators convert; equality does not

Each operator is a cty function with typed parameters, and BinaryOpExpr.Value converts both operands to those types with convert.Convert before calling it (expression_ops.go:217-243) from the code. cty's string-to-number and string-to-bool conversions are "unsafe" conversions that may fail at run time, and operators accept them. Equality takes any two values and converts nothing. So measured here: 

$ echo '"1" + 1' | terraform console                → 2         # unsafe conversion
$ echo '1 == "1"' | terraform console               → false     # equality never converts
$ echo 'type("${true}")' | terraform console        → bool      # unwrapped
$ echo 'true ? "a" : {}' | terraform console
  Error: Inconsistent conditional result types ... The 'true' value is string, but the 'false' value is object.

"5" > 3 is true and tobool("yes") is an error. Only tuples and objects have literal syntax, so [1] == tolist([1]) is false: a tuple is not equal to a list with the same elements. The rule worth remembering is that == compares type as well as value, so compare like with like, or convert explicitly with tostring or tolist first.

The conditional is stricter than it looks. ConditionalExpr.Value evaluates both arms and unifies their types with convert.UnifyUnsafe (expression.go:757) before it evaluates the predicate (line 777), so true ? "a" : {} fails even though the predicate is a constant. Errors from the arm that is not selected are discarded (expression.go:726-790, 898-899) from the code.

for expressions have their own ordering rules, which matter whenever a result feeds an index or a for_each. With one symbol the loop binds the value, with two the key and value; maps and objects iterate in lexicographic key order, while sets are "undefined but consistent"; and a trailing ... groups duplicate keys into tuples (hclsyntax/spec.md:455-496) from the code. Without the ..., a duplicate key in an object for is the error "Duplicate object key" measured here.

&& and || evaluate both sides

The v1.12.0 CHANGELOG says "Logical binary operators can now short-circuit" (#36224). That is true of the result, not of evaluation. BinaryOpExpr.Value evaluates the left operand, then the right, then asks the operator's ShortCircuit callback which result and which diagnostics survive. hcl/hclsyntax/expression_ops.go:217, 231 and 255-266, identical at v2.24.0 from the code:

	rhsVal, rhsMarks := rhsVal.Unmark()

Two consequences follow reconstruction. The guard idiom var.x != null && var.x.enabled works since v1.12 when var.x is null, because the error from reading an attribute of null on the right is dropped. But the right side was still evaluated. And a known value on either side can decide a result whose other side is unknown, which matters at plan time.

Unknowns are not all alike

An unknown value's v is a pointer to unknownType, a struct whose only field is an optional refinement (cty/unknown.go:3-32) from the code. A refinement records what is known about a value that is not: for any type, that it is not null; for strings, a known prefix; for numbers, lower and upper bounds; for collections, bounds on length. The totally unknown cty.DynamicVal can never be refined (unknown_refinement.go:30-80). Refinements are produced in ordinary places. A template with unknown parts returns an unknown string refined with up to 128 bytes of its known prefix, and always not-null, because "a template rendering result is never null" (hclsyntax/expression_template.go:92-114). The built-in terraform_data resource plans a new instance's id as cty.UnknownVal(cty.String).RefineNotNull() (internal/builtin/providers/terraform/resource_data.go:140-144).

Marks ride along

A mark is an annotation that propagates through operations. cty stores it by wrapping the payload in a marker{realV, marks}, where marks is a ValueMarks map[any]struct{} used as a set; integration methods refuse marked values "in order to ensure that calling applications don't inadvertently drop marks" (cty/marks.go:11-30) from the code. Terraform defines Sensitive, Ephemeral, TypeType (used by the console's type()) and a struct mark, DeprecationMark{Message, OriginDescription} (internal/lang/marks/marks.go:101-124).

Operators handle marks the same way every time. The excerpt above shows it: unmark both operands, compute, and re-mark the result with the union of both sets. So length(local.secret) and "${local.secret}-x" are both "(sensitive value)" measured here. terraform.applying is a boolean marked ephemeral, true only during the apply walk, available since v1.10.0 (internal/terraform/evaluate_data.go:105-157). Marks are the mechanism behind sensitive outputs, ephemeral values and write-only arguments, and they are also what a later stage can drop: Part 3 follows them to the places where they stop.

06The language surface: a dozen small schemas

"The Terraform language" is not a grammar. It is a set of schemas applied to HCL bodies, each with its own decoder in internal/configs. Resources: four meta-arguments and an escape hatch

resource, data and ephemeral share count, for_each, provider and depends_on. resource adds the blocks lifecycle, connection and provisioner, and all three accept a reserved locals block and a block named _ (internal/configs/resource.go:941-988) from the code. _ is the meta-argument escape. A provider whose resource has an argument called count or provider cannot have it set at the top of the block, because Terraform takes those names first; inside _ { … } the same names go to the provider, because the block's body is merged into the provider-config body with hcl.MergeBodies (resource.go:347-365). It arrived in v1.1.0 (commit 27ad9861ce, 14 May 2021) and has never been mentioned in a CHANGELOG.

lifecycle accepts create_before_destroy, prevent_destroy, ignore_changes, replace_triggered_by, destroy (v1.16.0, #38784) and the blocks precondition, postcondition and action_trigger (resource.go:990-1017). action_trigger and the top-level action block show how a schema can run ahead of its decoder: in v1.13.0 both were decoded only behind experiments, but the root schema already listed action, so a stable 1.13 binary accepts an action block and silently drops it. Actions shipped in v1.14.0 (#37553). If an action appears to do nothing, check the binary is at least 1.14.

The other blocks are tiny fixed schemas

provider takes alias, version and the provider's own configuration; count, depends_on, for_each and source are reserved, so Terraform, unlike OpenTofu, has no provider for_each (provider.go:262-284). module requires source and accepts version, count, for_each, depends_on, providers and ignore_nested_deprecations, and those names are therefore reserved as variable names: variable "source" is "Invalid variable name" (module_call.go:204-237) measured here. output takes description, value, depends_on, sensitive, ephemeral and, since v1.15, type and deprecated.

The refactoring and checking blocks are smaller still. moved is { from, to }; removed is { from } plus lifecycle { destroy }, connection and provisioner; import is to (required), id, identity, for_each and provider (moved.go:64-72; removed.go:137-154; import.go:117-133) from the code. check holds assert blocks and scoped data blocks; a check with no asserts, or an assert whose condition references nothing, is rejected, and checks cannot appear in override files. action "type" "name" takes count, for_each, provider and one config block (action.go:300-339). Part 3 follows what these blocks do once decoded.

07From a directory to a configs.Module

A module is a directory, and configs.Parser is what reads one. It wraps HCL's hclparse.Parser and an afero filesystem, and the file name's suffix alone picks the syntax: a name ending in .json goes to the JSON parser, everything else to native HCL (internal/configs/parser.go:21-33, 79-84) from the code. The parser keeps every file's bytes so diagnostics can print source snippets, and a saved plan re-injects them later. LoadConfigDir is short. internal/configs/parser_config_dir.go:48-64 from the code: 

func (p *Parser) LoadConfigDir(path string, opts ...Option) (*Module, hcl.Diagnostics) {
	fileSet, diags := p.dirFileSet(path, opts...)
	if diags.HasErrors() {
		return nil, diags
	}

	// Load the .tf configuration files
	primary, fDiags := p.loadFiles(fileSet.Primary, false)
	diags = diags.Extend(fDiags)

	override, fDiags := p.loadFiles(fileSet.Override, true)
	diags = diags.Extend(fDiags)

	// Initialize the module
	mod, modDiags := NewModule(primary, override)
	mod.SourceDir = path
	diags = diags.Extend(modDiags)

After this it attaches test, query and state-migration files if the caller asked for them.

Five categories, chosen by name

dirFileSet sorts the directory into five categories: primary (.tf, .tf.json), override, tests (.tftest.hcl/.json), queries (.tfquery.hcl/.json) and state migrations (.tfmigrate.hcl). Only primary and override files always match; the others need an option from the command (parser_file_matcher.go:18-24, 63-68, 138-158). An override file is any .tf or .tf.json whose base name is exactly override or ends in _override. Hidden files, vim ~ backups and emacs #…# autosaves are skipped silently, and subdirectories are never scanned for configuration; only tests/ is read, for test files (parser_config_dir.go:339-343; parser_file_matcher.go:105-108, 172-243) from the code. A .tf file in a subfolder is simply not part of the module unless a module block points at that folder.

Files are processed in directory-listing order, so when two files declare the same thing the first one wins and the duplicate error names the later file (parser_file_matcher.go:95-133). The .tfmigrate.hcl category is the odd one: its files describe a migration from { backend | state_store }, they are validated for mutual exclusivity at load (parser_config_dir.go:80-165), and no CHANGELOG mentions them, so their maturity is unknown.

The version check comes first, on purpose

Each file's required_version and experiments are sniffed with a partial schema before the full decode (parser_config.go:98-111, 300-322). The ordering exists so that a configuration written for a newer Terraform gets the error "this needs a newer Terraform" instead of a confusing syntax error about a block the old binary has never heard of. The sniff is the first of three places the rule is applied. The module installer drops every other diagnostic when the version requirement fails, "as they may reflect language changes from future Terraform versions" (internal/initwd/module_install.go:111-114). And terraform init loads the root module early but holds its parse errors until after the core-version check over the whole tree. internal/command/init_run.go:120-123 from the code: 

	// There may be parsing errors in config loading but these will be shown later _after_
	// checking for core version requirement errors. Not meeting the version requirement should
	// be the first error displayed if that is an issue, but other operations are required
	// before being able to check core version requirements.

Prerelease segments are not allowed in a required_version constraint, and a prerelease Terraform build matches on its version core only (module.go:945-970). The practical reading: when init complains about the Terraform version, fix that first; the other errors may be noise.

configs.Module is a set of maps keyed by name: variables, locals, outputs, module calls, managed, data, ephemeral and list resources, actions and checks, plus one backend, state store or cloud block and the provider requirements, including the deferred ProviderRequirementExprs that §08 evaluates (module.go:18-73). NewModule handles required_providers from all primary files first, since only one is allowed per module, then override entries, then the rest of each file; only one of cloud, state_store and backend may appear (module.go:152-207, 244-324) from the code.

One ingress block in an override file hides every ingress block in the base, including dynamic "ingress" blocks. Override attributes replace same-named base attributes one by one; blocks are replaced by type, never matched up and merged reconstruction. Variable overrides keep per-attribute "set" flags (DescriptionSet, SensitiveSet, ConstSet…) so an override changes only what it sets, and a module-call override may replace source, version, count, for_each and providers but not depends_on (module_merge.go:41-60, 183-220).

08The init graph and early evaluation

Through v1.14, a module's source was decoded at parse time with a nil evaluation context, gohcl.DecodeExpression(attr.Expr, nil, …), so only a literal string worked (git show v1.14.0:internal/configs/module_call.go, lines 74-87) from the code. Three releases changed that. v1.15.0 (29 April 2026, #38217) let module source and version use variables and locals, and gave most commands a -var flag (#38276). v1.17.0 (#39153) did the same for provider requirements. Its commit, 03847224e, is also the point where the v1.17 branch left main. To evaluate an expression before any module is installed, Terraform needed an evaluator that runs before the configuration tree exists. It reused the one it had: a graph walk.

Building the tree by walking a graph

The init graph arrived on 26 February 2026 (28b76c110, first tagged in v1.15.0), and on 4 September 2026 c6e867653 deleted configs.BuildConfig, the old recursive builder. In v1.17.0 every command builds its tree with terraform.BuildConfigWithGraph: an init-graph walk for the root, a separate walk for each run { module {} } in test files, then configs.FinalizeConfig (internal/terraform/config_graph_build.go:15-38). The walk itself runs in a fresh Context. config_graph_build.go:97-112 from the code: 

func initConfigWithGraph(rootMod *configs.Module, walker configs.ModuleWalker, vars InputValues, modulePathPrefix addrs.Module) (*configs.Config, tfdiags.Diagnostics) {
	ctx, ctxDiags := NewContext(&ContextOpts{
		// To avoid access issues with manifest and lock files, we don't want to
		// parallelize module installation/loading here
		Parallelism: 1,
	})
	if ctxDiags.HasErrors() {
		return nil, ctxDiags
	}

	return ctx.Init(rootMod, InitOpts{
		Walker:           walker,
		SetVariables:     vars,
		ModulePathPrefix: modulePathPrefix,
	})
}

Context.Init seeds a root configs.Config with an empty Children map, builds the init graph, and walks it with operation walkInit; the walk fills in the children (context_init.go:27-55). InitGraphBuilder.Steps is eight transformers: root (or module) variables, ModuleTransformer, ProviderRequirementExprTransformer, LocalTransformer, ReferenceTransformer, a filter, variable validation and transitive reduction (graph_builder_init.go:36-96). The filter is what keeps the graph tiny. internal/terraform/graph_builder_init.go:70-86 from the code: 

		// Filters out any vertices that aren't relevant to the init graph
		&TransformFilter{
			Keep: func(v dag.Vertex) bool {
				switch n := v.(type) {
				case *nodeInstallModule:
					return true
				case *nodeResolveProviderRequirements:
					return true
				case *NodeRootVariable:
					return n.Config.Const
				case *nodeExpandModuleVariable:
					return n.Config.Const
				default:
					return false
				}
			},
		},

Install nodes, provider-requirement nodes and const variables survive, plus everything they depend on, so a local is evaluated during init only if some source, version or requirement reaches it (transform_filter.go:17-42). ModuleTransformer adds one nodeInstallModule per module block, keyed addrs.NoKey, not one per count instance. Each install node references its source, its version and every input argument, because a child may use an input as a const variable in its own nested source. Execute evaluates the version, then the source, asks the walker to load the module, and splices the child *configs.Config into its parent. Then the node DynamicExpands into a fresh InitGraphBuilder graph for that child, which is how grandchildren get installed (node_module_install.go:59-227) from the code.

What the evaluator knows during init

The restriction is not a list of rules; it is what the evaluator returns. In walkInit a non-const variable is an unknown of its type. internal/terraform/evaluate.go:305-316 from the code:

		// We should still capture the statically-configured marks during
		// the validate walk.
		ret := cty.UnknownVal(config.Type)
		if config.Sensitive {
			ret = ret.Mark(marks.Sensitive)
		}
		if config.Ephemeral {
			ret = ret.Mark(marks.Ephemeral)
		}
		return ret, diags
	}

Resources, module outputs, count, each and terraform.* are cty.DynamicVal during init (evaluate.go:407-411, 648-652, 1204-1208). Const variables get real values from -var, TF_VAR_* or an auto-loaded terraform.tfvars, and their validation blocks run during init; non-const validations are skipped there. The module install node then gates the result: first a whitelist of reference types (var, local, path for a source; var and local for a version), then evaluation, then checks that the value is not null, is wholly known, and is neither sensitive nor ephemeral, failing with "Only literal values and const variables can be evaluated during init." (node_module_install.go:240-293).

Two quieter relaxations apply during the init walk. The evaluator skips static reference validation, and it tolerates calls to provider-defined functions it cannot resolve yet (IgnoreUnknownProviderFunctions), since the providers that define them are not installed (evaluate.go:105, 169-175) from the code. And only a const variable that is required and unset is an error at load time; a plain required variable can stay unset until plan. What is not allowed looks like this measured here:

When a child module is installed, init also checks what it found: a list block in a child module is rejected, and a backend or cloud block there only warns "Backend configuration ignored" (node_module_install.go:168-199). Because each install node references every input argument, a const value passed into a child should be able to steer a grandchild's source; the code implies it, but it was not measured.

Provider requirements in 1.17, and the backend that stayed literal

decodeRequiredProvidersBlock still decodes the legacy string form at once, but any object-form entry with source or version becomes a deferred ProviderRequirementExpr, even a pure literal. A comment in module.go:40-44 says these are resolved in the init graph "regardless of whether they contain variables"; only Stacks resolves them statically (provider_requirements.go:57-79, 99-209) from the code. One nodeResolveProviderRequirements per module evaluates them with the same checks as module sources, except that path.* is not allowed and a null version is treated, in the code's words, "like an empty constraint set". The measured three-vertex graph in Figure 6 came from a configuration with source = "${local.ns}/random" and version = "~> ${var.random_version}"; the lock file recorded the evaluated constraints = "~> 3.9.1". With a plain variable instead, init failed with "Unknown provider version" measured here. The variable documentation, as fetched on 23 October 2026, describes const only for module source and version; the 1.17 code also accepts it here.

Backends were left out. A backend block is decoded with a nil EvalContext, so even a const variable fails with HCL's "Variables not allowed" (internal/configs/backend.go:43-59) measured here. OpenTofu v1.13.2 takes the other road: its StaticEvaluator evaluates backend blocks, and path = var.p configured the backend (opentofu:internal/configs/backend.go:92-104). In Terraform the per-environment backend route is still -backend-config. Why one init builds the init graph twice, and what that costs on a large module tree, is still open; the trace shows that it does, not why.

09Installing modules and providers

InitCommand.run fixes the order of everything terraform init does (internal/command/init_run.go:28-467) from the code. It loads the root module early, reads the lock file, installs the provider for an experimental state_store if there is one, initialises the backend, reads the state (so providers of resources that exist only in state are installed too, and can destroy them), installs modules, loads the full tree, checks required_version, installs providers, and saves the lock file. §07 and §08 covered loading; backends are Part 3. This section is the two installers.

Modules: three kinds of address, no lock

initwd.ModuleInstaller dispatches on the evaluated source address (internal/initwd/module_install.go:295-320). A source starting ./ or ../ is local: it is joined to the parent's recorded directory, nothing is downloaded, and a version on it is an error. Anything that parses as a registry address goes to the registry. Everything else goes to go-getter, which means a malformed registry address is silently treated as a remote URL (moduleaddrs/source_parsing.go:29-97) from the code. When a version is present the source is parsed strictly as a registry address, so that mistake gets a better error. Shorthand detection is frozen at six legacy detectors (GitHub, Git over SSH, Bitbucket, GCS, S3 and absolute paths), and Terraform pins its own go-getter getters and disables go-getter's detectors; new schemes must use type::url.

A registry module install is four requests: modules.v1 service discovery, GET …/versions (cached per run), selection of the newest matching version, and GET …/<version>/download, whose answer is only a header. The real location comes from X-Terraform-Get, on a 200 or 204; local paths and registry addresses are refused there, and the HTTP getter follows at most ten X-Terraform-Get redirections (internal/registry/client.go:236-272; getmodules/getter.go:83-87). Results are recorded in .terraform/modules/modules.json, keyed by module call path. Module versions are never locked: .terraform.lock.hcl holds providers only, and a module block in it merely warns "Dependency locks for modules are not yet supported" (internal/depsfile/locks_file.go:166-234). Pin modules with an exact version if you need reproducibility.

Providers: select, query, link or download

The provider set is the union of required_providers, implicit dependencies of every resource whose provider is not listed, provider blocks, test files and the state. An unqualified name means registry.terraform.io/hashicorp/<name>, except terraform, which is the built-in provider (internal/addrs/provider.go:66-93). A third-party resource with no required_providers entry therefore fails as hashicorp/mongodbatlas, and the error suggests mongodb/mongodbatlas.

providercache.Installer.EnsureProviderVersions then runs in steps (Figure 7). Step 1 narrows each provider with a satisfying lock entry to exactly its locked version, unless -upgrade; a lock that conflicts with the current constraints fails here, before any network call. Step 2 queries the source's AvailableVersions for every provider, locked or not, and walks backwards to the newest acceptable one (installer.go:293-352) from the code. A trace showed the GET …/hashicorp/random/versions with a lock file present measured here. Step 3a links from the global plugin cache only if a lock entry exists and the cached package matches one of its hashes; the comment says why: "If there was no lock file entry at all then we need to install the package for real so that we can lock as complete as possible a set of checksums" (installer.go:402-433).

That has a cost on a shared machine. With TF_PLUGIN_CACHE_DIR set and no lock file, init printed "Installed hashicorp/random v3.9.1 (signed by HashiCorp)": it downloaded into the shared cache and rewrote the entry. With a lock, it printed "Using … from the shared cache directory" measured here. On this box a no-lock init failed with "text file busy" because another process was running that provider binary, and concurrent inits rewrote the cache mid-run and broke a plan's lock check. Commit the lock file, and let one process populate a shared cache.

Three checks, and two hashes

A downloaded zip goes to a temp file, then through source authentication, then the lock-file hashes, and only then is unzipped; installing into a symlinked target is refused (package_install.go:27-142). For a registry package, authentication is three checks in order: the SHA256SUMS document lists the file with its sum, the archive's SHA-256 equals the registry's shasum, and the GPG signature on SHA256SUMS verifies against a key the registry returned (key 34365D9472D7468F for HashiCorp). An expired signing key is tolerated: ErrKeyExpired is downgraded to "[WARN] expired openpgp key from HashiCorp Security", which appeared in a live trace measured here. v1.17 accepts plugin protocol 5 or 6 only.

The lock file, .terraform.lock.hcl, is regenerated from scratch with hclwrite each time, providers sorted, never edited in place. Each entry has version, constraints and a sorted set of hashes, so h1: lines always precede zh: (depsfile/locks_file.go:114-164; locks.go:177-212). zh: is the hex SHA-256 of a release zip, taken from SHA256SUMS. h1: is Go's dirhash.Hash1 over the unpacked files, and it can be recomputed by hand: SHA-256 each file, sort the "<hex> <path>" lines, SHA-256 the list, base64 the result. For random 3.9.1 on linux_amd64 that gives h1:g40qr7yDmIpaur4SsK5BcOda3HSo1RJ6zHVMqN4EJ+0=, the same value as the lock file measured here. Which hashes are recorded is decided here. internal/providercache/installer.go:710-724 from the code: 

		var signedHashes []getproviders.Hash
		if authResult.SignedByAnyParty() {
			// We'll trust new hashes from upstream only if they were verified
			// as signed by a suitable key. Otherwise, we'd record only
			// a new hash we just calculated ourselves from the bytes on disk,
			// and so the hashes would cover only the current platform.
			signedHashes = append(signedHashes, meta.AcceptableHashes()...)
		}

		var newHashes []getproviders.Hash
		newHashes = append(newHashes, newHash)
		newHashes = append(newHashes, priorHashes...)
		newHashes = append(newHashes, signedHashes...)

		locks.SetProvider(provider, version, reqs[provider], newHashes)

AcceptableHashes takes every line of SHA256SUMS, so the lock for random 3.9.1 has one h1: and 13 zh:: twelve zips and one for terraform-provider-random_3.9.1_manifest.json, which is not a package measured here. A corrupted hash makes every later command stop: plan failed with "Required plugins are not installed … does not match any of the checksums". -lockfile=readonly errors if the provider set changed and otherwise only warns.

Offline means a mirror

Because step 2 always asks the source, terraform init under the default installation method is not offline, even with a lock file and a warm cache. In a namespace with no network it failed with "could not connect to registry.terraform.io" measured here; the lab's own README had claimed otherwise and was corrected. The offline route is a provider_installation block in the CLI configuration with a filesystem_mirror, which accepts packed or unpacked layouts and performs no authentication: init printed "Installed … (unauthenticated)". Mirror installs lock only the local h1: and warn "Incomplete lock file information for providers"; terraform providers lock -platform=… fills in the rest, and two platforms gave 2 h1: plus 13 zh: measured here. A no-lock init with the requirement written as an expression took 1.0 s, one cold-ish run on a 2-vCPU box. The configuration was now loaded, the tree built, and every provider on disk; Part 2 builds the graph.
