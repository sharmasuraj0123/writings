{{S}}One plan, five data structures

Terraform is a compiler whose intermediate representation is a dependency graph and whose back end is somebody else's process. A terraform plan turns bytes into tokens, tokens into a syntax tree, the tree into a configuration tree, the configuration into a graph, the graph into calls to provider processes, and the answers into a plan file. Each stage hands the next a different Go type. This collection reads Terraform v1.17.0 along those boundaries, because that is where its surprises live. Part 1 covers the front end: everything up to the moment a configs.Config exists and its providers are installed. Parts 2 to 4 take the graph, the state and the outside world.

Three design choices explain most of what follows. HCL parses without meaning: its parser builds attributes and blocks without knowing which names are legal, and meaning arrives only when a schema is applied. The graph is the program: ordering, parallelism and failure isolation are edges, not code paths. And trust lives in core while data lives outside: providers are untrusted child processes whose answers are checked, and the record of what exists is one JSON document. This part is about the first choice and what it costs.

The five hand-offs

Bytes to a syntax tree. HCL's native syntax is three sub-languages in one file: structural (bodies, blocks, attributes), expression, and template (hcl/hclsyntax/spec.md:10-21) from the code. hclsyntax.ParseConfig runs a scanner generated by Ragel from five state machines, then a hand-written recursive-descent parser, and returns an *hclsyntax.Body: a map of attributes and a slice of blocks. §02 and §03 take those two apart.

Syntax tree to configuration. configs.Parser.LoadConfigDir sorts a directory's files into categories, decodes each .tf file against configFileSchema (15 block types, no attributes) and folds the results into one configs.Module (internal/configs/parser_config_dir.go:48-64; parser_config.go:324-387) from the code. Since v1.15 the tree of modules, a configs.Config, is built by walking a small graph of its own, the init graph, with operation walkInit and parallelism 1 (internal/terraform/config_graph_build.go:15-38, 97-112). In v1.17.0 the old recursive builder, configs.BuildConfig, is gone; it was deleted on 4 September 2026 in c6e867653. The init graph is small: for a configuration whose only early expression is a provider requirement, a trace shows three vertices, and one terraform init builds and walks it twice measured here. §04 to §09 cover this stage, including what terraform init installs.

Configuration to graph. The plan builder runs 31 top-level GraphTransformers (36 counting the five provider sub-steps) over a dag.AcyclicGraph of resources, checks it for cycles with Tarjan's strongly-connected-components algorithm, and walks it with one goroutine per vertex under a -parallelism semaphore of 10 (internal/terraform/graph_builder_plan.go:174-331; internal/dag/dag.go:244-265) from the code. Resource instances do not exist in that graph; they appear in subgraphs once count and for_each are known. That is Part 2.

Graph to provider calls. Each provider is a separate executable started by go-plugin, which checks a magic cookie in the environment and then talks gRPC: the tfplugin6 service declares 36 RPCs (docs/plugin-protocol/tfplugin6.proto:350-430) from the code. One terraform plan of one random resource started the provider three times: once for the schema, once for the validate walk, once for the plan walk measured here. Part 2 follows those processes.

Answers to a plan and a state. A saved plan is a ZIP holding a protobuf plan, two state snapshots, a snapshot of the configuration and the lock file (internal/plans/planfile/writer.go:54-139). State is one version-4 JSON document per workspace, rewritten whole through a statemgr.Full (internal/states/statemgr/statemgr.go:12-29) from the code. Part 3 starts there.

Where the surprises sit

Each boundary in Figure {{fig-pipeline}} is a point where one stage knows something the next does not, and the well-known Terraform puzzles line up with them. dynamic "lifecycle" is rejected because the syntax tree is decoded twice, and only the second decode, against the provider's schema, expands dynamic blocks (§04). prevent_destroy = var.protect fails with "Variables not allowed" because meta-arguments are decoded at the configuration stage, before any value exists (§04). local.u == "x" || true is true at plan time although local.u is unknown, because values carry more information than "known" or "unknown" (§05). A module source may now be local.mod_dir, but only if that local comes from a const variable, because the configuration tree is built on a graph where nothing else has a value yet (§08). And terraform init asks the registry for versions even with a lock file and a warm cache, because the installer was built to complete the lock file, not to work offline (§09). The later boundaries have their own: core rejects a provider's answer that contradicts its own plan (Part 2), and an S3 backend configured with neither use_lockfile nor a DynamoDB table takes no lock at all (Part 3).

None of these is a bug. Each follows from which stage owns which fact. A practitioner reading a confusing error can usually ask one question first: which of the five structures existed when this was checked?
