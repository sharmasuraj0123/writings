{{S}}Values: numbers, unknowns and marks

Every value Terraform evaluates is a go-cty cty.Value, and the type is small enough to quote. go-cty/cty/value.go:30-33 from the code: 

type Value struct {
	ty Type
	v  any
}

ty is one of a closed set: Bool, Number and String; List, Map and Set; Object (including objects with optional attributes) and Tuple; Capsule for opaque Go values; and DynamicPseudoType, the "any" type (cty/list_type.go:17 and siblings) from the code. v is where the interesting things live: a real payload, or a sentinel meaning "unknown", or a wrapper carrying marks. The comment above the struct divides cty's methods into "operation methods", which stay inside the type system and handle unknowns, and "integration methods", which leave it and may panic on an unknown or marked value. Terraform lives almost entirely in the first kind. The go-cty citations here are from an untagged clone past v1.19.0; Terraform pins v1.18.1, and equivalence of these lines was not verified.

Numbers are 512-bit

A number literal becomes a big.Float through cty.ParseNumberVal, which calls big.ParseFloat(s, 10, 512, big.ToNearestEven) (cty/value_init.go:42-56) from the code. That is more precision than any float64, and it shows measured here: 

$ echo '1 + 2 * 3 - 4 / 2' | terraform console      → 5
$ echo '0.1 + 0.2 == 0.3' | terraform console       → true
$ echo '9007199254740993 + 0' | terraform console   → 9007199254740993
$ echo 'pow(2, 1024)' | terraform console
  Error: Error in function call ... Call to function "pow" failed: result is not a number.

The HCL spec says numbers have "arbitrary precision"; the implementation is a 512-bit mantissa, and functions such as pow and log go through float64. Since v1.17.0 (#39304) a result of infinity is an error instead of a value. For a practitioner the arithmetic is exact enough that 0.1 + 0.2 == 0.3 holds, which it does not in most languages; the edges are the float64 functions.

Operators convert; equality does not

Each operator is a cty function with typed parameters, and BinaryOpExpr.Value converts both operands to those types with convert.Convert before calling it (expression_ops.go:217-243) from the code. cty's string-to-number and string-to-bool conversions are "unsafe" conversions that may fail at run time, and operators accept them. Equality takes any two values and converts nothing. So measured here: 

$ echo '"1" + 1' | terraform console                → 2         # unsafe conversion
$ echo '1 == "1"' | terraform console               → false     # equality never converts
$ echo 'type("${true}")' | terraform console        → bool      # unwrapped
$ echo 'true ? "a" : {}' | terraform console
  Error: Inconsistent conditional result types ... The 'true' value is string, but the 'false' value is object.

"5" > 3 is true and tobool("yes") is an error. Only tuples and objects have literal syntax, so [1] == tolist([1]) is false: a tuple is not equal to a list with the same elements. The rule worth remembering is that == compares type as well as value, so compare like with like, or convert explicitly with tostring or tolist first.

The conditional is stricter than it looks. ConditionalExpr.Value evaluates both arms and unifies their types with convert.UnifyUnsafe (expression.go:757) before it evaluates the predicate (line 777), so true ? "a" : {} fails even though the predicate is a constant. Errors from the arm that is not selected are discarded (expression.go:726-790, 898-899) from the code.

for expressions have their own ordering rules, which matter whenever a result feeds an index or a for_each. With one symbol the loop binds the value, with two the key and value; maps and objects iterate in lexicographic key order, while sets are "undefined but consistent"; and a trailing ... groups duplicate keys into tuples (hclsyntax/spec.md:455-496) from the code. Without the ..., a duplicate key in an object for is the error "Duplicate object key" measured here.

&& and || evaluate both sides

The v1.12.0 CHANGELOG says "Logical binary operators can now short-circuit" (#36224). That is true of the result, not of evaluation. BinaryOpExpr.Value evaluates the left operand, then the right, then asks the operator's ShortCircuit callback which result and which diagnostics survive. hcl/hclsyntax/expression_ops.go:217, 231 and 255-266, identical at v2.24.0 from the code: 

	givenLHSVal, lhsDiags := e.LHS.Value(ctx)
	…
	givenRHSVal, rhsDiags := e.RHS.Value(ctx)
	…
	lhsVal, lhsMarks := lhsVal.Unmark()
	rhsVal, rhsMarks := rhsVal.Unmark()

	if e.Op.ShortCircuit != nil {
		forceResult, diags := e.Op.ShortCircuit(lhsVal, rhsVal, lhsDiags, rhsDiags)
		if forceResult != cty.NilVal {
			// It would be technically more correct to insert rhs diagnostics if
			// forceResult is not known since we didn't really short-circuit. That
			// would however not match the behavior of conditional expressions which
			// do drop all diagnostics from the unevaluated expressions
			return forceResult.WithMarks(lhsMarks, rhsMarks), diags
		}

For && the callback returns cty.False with only the left diagnostics when the left side is a known false, and the mirror for a known false on the right; for || a known true on either side decides (expression_ops.go:33-98). Two consequences follow reconstruction. The guard idiom var.x != null && var.x.enabled works since v1.12 when var.x is null, because the error from reading an attribute of null on the right is dropped. But the right side was still evaluated. And a known value on either side can decide a result whose other side is unknown, which matters at plan time.

Unknowns are not all alike

An unknown value's v is a pointer to unknownType, a struct whose only field is an optional refinement (cty/unknown.go:3-32) from the code. A refinement records what is known about a value that is not: for any type, that it is not null; for strings, a known prefix; for numbers, lower and upper bounds; for collections, bounds on length. The totally unknown cty.DynamicVal can never be refined (unknown_refinement.go:30-80). Refinements are produced in ordinary places. A template with unknown parts returns an unknown string refined with up to 128 bytes of its known prefix, and always not-null, because "a template rendering result is never null" (hclsyntax/expression_template.go:92-114). The built-in terraform_data resource plans a new instance's id as cty.UnknownVal(cty.String).RefineNotNull() (internal/builtin/providers/terraform/resource_data.go:140-144).

terraform console -plan shows the effect. The configuration is one terraform_data and four locals (measured here): 

resource "terraform_data" "a" { input = "hello" }
locals {
  u      = terraform_data.a.id
  pfx    = "https://${terraform_data.a.id}"
  lst    = [terraform_data.a.id, "x"]
  secret = sensitive("s3cr3t")
}
local.u                          → (known after apply)
local.u == null                  → false      # provider refined id as not-null
length(local.lst)                → 2
startswith(local.pfx, "https:")  → true       # template prefix refinement
local.u == "x" || true           → true       # short-circuit
length(local.secret)             → (sensitive value)
terraform.applying               → (ephemeral value)

Every line in Figure {{fig-cty-value}}'s right column except the first is decided at plan time. The id is unknown, but it is known not to be null; the list has an unknown element but a known length; the URL's prefix is known. Refinements survive in the plan file and on the wire as msgpack extension 12 (Part 2). A practitioner sees the payoff wherever the deciding fact is a length, a nullness or a prefix: a count = length(local.lst) or a startswith check can be settled during plan even though the list's contents are not reconstruction.

Marks ride along

A mark is an annotation that propagates through operations. cty stores it by wrapping the payload in a marker{realV, marks}, where marks is a ValueMarks map[any]struct{} used as a set; integration methods refuse marked values "in order to ensure that calling applications don't inadvertently drop marks" (cty/marks.go:11-30) from the code. Terraform defines Sensitive, Ephemeral, TypeType (used by the console's type()) and a struct mark, DeprecationMark{Message, OriginDescription} (internal/lang/marks/marks.go:101-124).

Operators handle marks the same way every time. The excerpt above shows it: unmark both operands, compute, and re-mark the result with the union of both sets. So length(local.secret) and "${local.secret}-x" are both "(sensitive value)" measured here. terraform.applying is a boolean marked ephemeral, true only during the apply walk, available since v1.10.0 (internal/terraform/evaluate_data.go:105-157). Marks are the mechanism behind sensitive outputs, ephemeral values and write-only arguments, and they are also what a later stage can drop: Part 3 follows them to the places where they stop.
