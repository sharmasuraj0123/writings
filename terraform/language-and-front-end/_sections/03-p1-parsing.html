{{S}}Recursive descent, and why parser shape is graph shape

HCL's parser is hand-written recursive descent: one Go function per grammar rule, each calling the next. It reads tokens through a peeker, and the interesting state in the peeker is a single slice of booleans. Line numbers below are from HCL main; at v2.24.0, the version Terraform v1.17.0 ships, parser.go lines above about 370 sit 9 or 10 lower, with identical code.

Newlines are a stack

The grammar says an attribute ends with a newline, but nobody wants a newline inside a function call's argument list to end anything. The peeker solves this with IncludeNewlinesStack, initialised to []bool{true} (hclsyntax/peeker.go:41-48). Opening a parenthesis, a bracket, a call or a for expression pushes false; an object constructor pushes true; each closer pops. While the top is false, Peek skips TokenNewline. ParseConfig checks that the stack is back to its one entry at the end (peeker.go:106-123; parser.go:882, 968, 1239, 1426-1434, 1590) from the code. The consequences are easy to reproduce with terraform validate measured here: 

x = 1 +⏎ 2          → Error: Invalid expression
x = (1 +⏎ 2)        → Success!
x = true⏎ ? 1⏎ : 2  → Error: Argument or block definition required
locals { x = 1, y = 2 } → Error: Invalid single-argument block definition
x = foo.0.0         → Error: Invalid legacy index syntax

At body level the newline after + ends the attribute, so the expression is incomplete. Inside parentheses the same newline is invisible. A ternary cannot start a continuation line with ?, because by then the attribute has ended and the parser expects a new attribute or block. The practical rule: to break a long expression across lines, wrap it in parentheses. The last line is a lexer effect, not a parser one: 0.0 scans as one number, so the legacy foo.0 index syntax still works once but not twice (parser.go:660-705) from the code.

A body is a map and a slice, with no schema

ParseBody loops until its end token. It skips newlines, and for each identifier calls ParseBodyItem, which decides between attribute and block by looking one token ahead. hcl/hclsyntax/parser.go:157-161 from the code: 

	switch next.Type {
	case TokenEqual:
		return p.finishParsingBodyAttribute(ident, false)
	case TokenOQuote, TokenOBrace, TokenIdent:
		return p.finishParsingBodyBlock(ident)

Attributes go into a map keyed by name, where a duplicate is the only structural error ("Attribute redefined"). Blocks go into a slice in source order (parser.go:27-139). Nothing here knows that resource takes two labels or that count is special. A misspelled block type parses perfectly; it fails later, when a schema is applied (§04). The parser does have opinions about block shape, and they show as specific messages: locals = {} is "Unsupported argument", locals followed by { on the next line is "Argument or block definition required", and commas between arguments are "Unexpected comma after argument" measured here.

Precedence is the order of a slice

Expressions descend through four functions. parseTernaryConditional parses a condition with parseBinaryOps(binaryOps), and if a ? follows, parses both arms with the full ParseExpression, which makes ?: right-associative and looser than || (parser.go:491-550). parseBinaryOps handles the operators. parseExpressionWithTraversals handles .attr, [index] and splats after a term. parseExpressionTerm handles literals, names, calls, parentheses and the unary - and !, whose operand is a term with traversals, so -46+5 is (-46)+5 and a negative number is a UnaryOpExpr, not a literal (parser.go:1074-1103) from the code.

There is no precedence table in the usual sense, and no operation.go. The levels are the order of a Go slice of maps, lowest first. hcl/hclsyntax/expression_ops.go:167-193 from the code: 

	binaryOps = []map[TokenType]*Operation{
		{
			TokenOr: OpLogicalOr,
		},
		{
			TokenAnd: OpLogicalAnd,
		},
		{
			TokenEqualOp:  OpEqual,
			TokenNotEqual: OpNotEqual,
		},
		{
			TokenGreaterThan:   OpGreaterThan,
			TokenGreaterThanEq: OpGreaterThanOrEqual,
			TokenLessThan:      OpLessThan,
			TokenLessThanEq:    OpLessThanOrEqual,
		},
		{
			TokenPlus:  OpAdd,
			TokenMinus: OpSubtract,
		},
		{
			TokenStar:    OpMultiply,
			TokenSlash:   OpDivide,
			TokenPercent: OpModulo,
		},
	}

parseBinaryOps(ops) takes ops[0] as "this level" and ops[1:] as everything tighter. It parses a left operand by recursing on the tighter levels, then loops while the next token is one of this level's operators, folding left. hcl/hclsyntax/parser.go:585-607 (576-598 at v2.24.0) from the code: 

	for {
		next := p.Peek()
		var newOp *Operation
		var ok bool
		if newOp, ok = thisLevel[next.Type]; !ok {
			break
		}

		// Are we extending an expression started on the previous iteration?
		if operation != nil {
			lhs = &BinaryOpExpr{
				LHS: lhs,
				Op:  operation,
				RHS: rhs,

				SrcRange: hcl.RangeBetween(lhs.Range(), rhs.Range()),
			}
		}

		operation = newOp
		p.Read() // eat operator token
		var rhsDiags hcl.Diagnostics
		rhs, rhsDiags = p.parseBinaryOps(remaining)

This is precedence climbing with the table as data. When the slice runs out, the recursion bottoms out in parseExpressionWithTraversals. Adding an operator level would be one more map in the slice. The measured results match the table: 1 + 2 * 3 - 4 / 2 is 5, true || false && false is true, -2 * -3 is 6, and false ? 1 : true ? 2 : 3 is 2 measured here. true, false and null are keywords only in term position and only when not followed by ( or ::; every other leading identifier becomes a ScopeTraversalExpr (parser.go:1016-1050).

Traversals: extended in place, or broken out

After a term, parseExpressionWithTraversals loops over .name, [key], .* and [*]. For an attribute step, or an index whose key is a literal or a literal-only string template, it calls makeRelativeTraversal, which appends the step to an existing ScopeTraversalExpr "in place (mutating it)". For any other key, such as var.i, it wraps what it has so far in an IndexExpr, and later steps become a RelativeTraversalExpr around that (parser.go:901-927, 938-959) from the code. Splats compile to SplatExpr{Source, Each, Item}, where Item is an AnonSymbolExpr placeholder that Each is evaluated against once per element (parser.go:859-877).

The two splat spellings are not synonyms. The full splat [*] applies every following step to each element, so x[*].a[0] takes element 0 of each a. The attribute-only splat .*, kept from Terraform 0.11's HIL, stops absorbing steps at the first index, so x.*.a[0] indexes the resulting list and returns the first element's a (spec.md:594-610; parser.go:707-811) from the code. A splat on a single non-list value wraps it in a one-element tuple, and on a null non-list value gives [], while a splat of a null list is the error "Splat of null value" (expression.go:1807-1823, 1800-1816 at v2.24.0) measured here. A splat is a cheap way to turn "maybe one object" into "a list of zero or one".

The reason this is more than tidiness: Terraform builds its dependency graph from references, and it finds references by calling Expression.Variables(), which returns the expression's root traversals, then parsing each with addrs.parseRef. The roots it understands are count, each, data, resource, ephemeral, list, local, module, path, self, caller, terraform, var and action; template, lazy and arg are reserved; any other root is a managed resource type (internal/addrs/parse_ref.go:199-437) from the code. So aws_instance.web[0].id arrives as one traversal that names an instance, and aws_instance.web[var.i].id arrives as two: the resource as a whole, and var.i. The parser decides which references exist, and the graph in Part 2 is built from exactly those reconstruction.

Templates that unwrap, and the newest token

Two more parser rules surprise people. A template that is exactly one interpolation is a passthrough: when the parts are one interpolation plus the synthetic end token, parseTemplateInner sets passthru, and the result is a TemplateWrapExpr that keeps the inner value's type (parser_template.go:39-60). So type("${true}") is bool, while type("x${true}") is string measured here. That is why terraform fmt can rewrite a lone "${var.x}" to var.x without changing meaning.

And :: is the newest token. Namespaced function calls such as provider::aws::arn_parse(…) arrived in HCL v2.20.0 for Terraform 1.8. The scanner emits TokenDoubleColon, and the parser glues the segments into one name string, nameStr + "::" + …, with a comment explaining that this keeps the API unchanged for code written before namespaces existed (parser.go:1178-1208) from the code. The grammar in spec.md still has no :: in its FunctionCall rule; it is one more place where the code is the specification.
