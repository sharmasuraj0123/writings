{{S}}From a directory to a configs.Module

A module is a directory, and configs.Parser is what reads one. It wraps HCL's hclparse.Parser and an afero filesystem, and the file name's suffix alone picks the syntax: a name ending in .json goes to the JSON parser, everything else to native HCL (internal/configs/parser.go:21-33, 79-84) from the code. The parser keeps every file's bytes so diagnostics can print source snippets, and a saved plan re-injects them later. LoadConfigDir is short. internal/configs/parser_config_dir.go:48-64 from the code: 

func (p *Parser) LoadConfigDir(path string, opts ...Option) (*Module, hcl.Diagnostics) {
	fileSet, diags := p.dirFileSet(path, opts...)
	if diags.HasErrors() {
		return nil, diags
	}

	// Load the .tf configuration files
	primary, fDiags := p.loadFiles(fileSet.Primary, false)
	diags = diags.Extend(fDiags)

	override, fDiags := p.loadFiles(fileSet.Override, true)
	diags = diags.Extend(fDiags)

	// Initialize the module
	mod, modDiags := NewModule(primary, override)
	mod.SourceDir = path
	diags = diags.Extend(modDiags)

After this it attaches test, query and state-migration files if the caller asked for them.

Five categories, chosen by name

dirFileSet sorts the directory into five categories: primary (.tf, .tf.json), override, tests (.tftest.hcl/.json), queries (.tfquery.hcl/.json) and state migrations (.tfmigrate.hcl). Only primary and override files always match; the others need an option from the command (parser_file_matcher.go:18-24, 63-68, 138-158). An override file is any .tf or .tf.json whose base name is exactly override or ends in _override. Hidden files, vim ~ backups and emacs #…# autosaves are skipped silently, and subdirectories are never scanned for configuration; only tests/ is read, for test files (parser_config_dir.go:339-343; parser_file_matcher.go:105-108, 172-243) from the code. A .tf file in a subfolder is simply not part of the module unless a module block points at that folder.

Files are processed in directory-listing order, so when two files declare the same thing the first one wins and the duplicate error names the later file (parser_file_matcher.go:95-133). The .tfmigrate.hcl category is the odd one: its files describe a migration from { backend | state_store }, they are validated for mutual exclusivity at load (parser_config_dir.go:80-165), and no CHANGELOG mentions them, so their maturity is unknown.

The version check comes first, on purpose

Each file's required_version and experiments are sniffed with a partial schema before the full decode (parser_config.go:98-111, 300-322). The ordering exists so that a configuration written for a newer Terraform gets the error "this needs a newer Terraform" instead of a confusing syntax error about a block the old binary has never heard of. The sniff is the first of three places the rule is applied. The module installer drops every other diagnostic when the version requirement fails, "as they may reflect language changes from future Terraform versions" (internal/initwd/module_install.go:111-114). And terraform init loads the root module early but holds its parse errors until after the core-version check over the whole tree. internal/command/init_run.go:120-123 from the code: 

	// There may be parsing errors in config loading but these will be shown later _after_
	// checking for core version requirement errors. Not meeting the version requirement should
	// be the first error displayed if that is an issue, but other operations are required
	// before being able to check core version requirements.

Prerelease segments are not allowed in a required_version constraint, and a prerelease Terraform build matches on its version core only (module.go:945-970). The practical reading: when init complains about the Terraform version, fix that first; the other errors may be noise.

NewModule, and overrides that merge late

configs.Module is a set of maps keyed by name: variables, locals, outputs, module calls, managed, data, ephemeral and list resources, actions and checks, plus one backend, state store or cloud block and the provider requirements, including the deferred ProviderRequirementExprs that §08 evaluates (module.go:18-73). NewModule handles required_providers from all primary files first, since only one is allowed per module, then override entries, then the rest of each file; only one of cloud, state_store and backend may appear (module.go:152-207, 244-324) from the code.

Override files are merged by mergeFile, and overriding something that has no base declaration is an error ("Missing resource to override"). An override's required_version replaces the list rather than extending it, and a backend in an override clears any cloud or state_store. Bodies merge through MergeBodies, which returns a lazy mergeBody that implements hcl.Body and merges only when someone asks for content (module_merge_body.go:18-57). The merge is shallow. module_merge_body.go:95-115 from the code: 

	overriddenBlockTypes := make(map[string]bool)
	for _, block := range override.Blocks {
		if block.Type == "dynamic" {
			overriddenBlockTypes[block.Labels[0]] = true
			continue
		}
		overriddenBlockTypes[block.Type] = true
	}
	for _, block := range base.Blocks {
		// We skip over dynamic blocks whose type label is an overridden type
		// but note that below we do still leave them as dynamic blocks in
		// the result because expanding the dynamic blocks that are left is
		// done much later during the core graph walks, where we can safely
		// evaluate the expressions.
		if block.Type == "dynamic" && overriddenBlockTypes[block.Labels[0]] {
			continue
		}
		if overriddenBlockTypes[block.Type] {
			continue
		}

One ingress block in an override file hides every ingress block in the base, including dynamic "ingress" blocks. Override attributes replace same-named base attributes one by one; blocks are replaced by type, never matched up and merged reconstruction. Variable overrides keep per-attribute "set" flags (DescriptionSet, SensitiveSet, ConstSet…) so an override changes only what it sets, and a module-call override may replace source, version, count, for_each and providers but not depends_on (module_merge.go:41-60, 183-220).
