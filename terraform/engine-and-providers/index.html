01Building the plan graph

Terraform is a compiler whose intermediate representation is a dependency graph and whose back end is somebody else's process. Part 1 followed a directory of .tf files as far as a loaded configs.Config. This part takes that tree through the engine: a graph built by 31 transformers, a walker with a goroutine per vertex, instances that appear only at walk time, a provider that proposes while core decides, child processes reached through a one-line handshake, a 36-RPC wire contract, and an apply that plans again instead of replaying the plan.

Two claims carry the part. The graph is the program: ordering, parallelism, failure isolation, destroy order and create-before-destroy are all edges, not code paths. And trust lives in core: providers are untrusted processes, and core checks every answer they give. This first section builds the graph. Its claim is narrow. The graph that terraform plan builds is resource-level. Instances do not exist in it yet.

From the command to planWalk

terraform plan runs Context.Validate first and Context.Plan second. Plan is a thin wrapper around PlanAndEval (internal/terraform/context_plan.go:204, 218). PlanAndEval takes the context's run lock (acquireRun, a sync.Cond wait), checks that the option combination is legal, and dispatches to a normal, destroy or refresh-only plan from the code. The option checks are where some flags quietly constrain each other: -replace is allowed only in normal mode, -invoke only in refresh-only mode, and -minimal-refresh only in normal or destroy mode and never with -refresh=false (context_plan.go:280-333).

All three modes end in planWalk (context_plan.go:792-938). It deep-copies the prior state, applies moved blocks to the copy with prePlanFindAndApplyMoves, builds the plan graph, walks it into a fresh plans.Changes, validates the moves, computes drift, and encodes the changes against the provider schemas into a plans.Plan. Moves are applied before any graph exists but validated only after the walk. The authors explain why at context_plan.go:867-873: 

		// If any of the move statements are invalid then those errors take
		// precedence over any other errors because an incomplete move graph
		// is quite likely to be the _cause_ of various errors. This oddity
		// comes from the fact that we need to apply the moves before we
		// actually validate them, because validation depends on the result
		// of first trying to plan.

So a bad moved block replaces every other error in the output. If a plan reports only move errors, fix those first; the rest may be consequences. Part 3 covers what the move graph does to state.

One builder, 31 steps

A single PlanGraphBuilder serves plan, plan-destroy, validate and import. It swaps the concrete node factories (initPlan, initDestroy, initValidate, initImport) and keeps the pipeline (graph_builder_plan.go:159-172). Its Steps method returns 31 top-level GraphTransformers, 36 if you count the five provider sub-steps inside one GraphTransformMulti (graph_builder_plan.go:174-331) from the code. BasicGraphBuilder.Build runs them in order, logs Executing graph transform %T for each, dumps changed graphs when TF_GRAPH_TRACE is set, and validates the result at the end (graph_builder.go:36-90). A TF_LOG=trace plan prints the same 31 names in the same order measured here. Figure 8 lists them beside the apply builder's.

Read in order of effect, the pipeline does six things.

  • Nodes from configuration. ConfigTransformer adds one resource-level (expand) node per resource, data and action block. Variables, locals, outputs, checks, orphans from state and removed modules follow as their own transformers.
  • Provider wiring. Five sub-steps attach every consumer to exactly one provider configuration (transform_provider.go:20-43). MissingProviderTransformer always adds implied default configurations in the root module. ProviderTransformer walks up the module tree through Inherited() and falls back to those defaults. PruneProviderTransformer then removes providers nothing uses, so an unused provider is never launched or configured. A provider configuration that survives only in state fails with "Provider configuration not present".
  • Schemas before references. AttachSchemaTransformer runs before ReferenceTransformer because finding the references inside a resource body needs that body's schema. This is the second decode from Part 1: the undecoded hcl.Body meets the provider's schema here.
  • Module brackets. ModuleExpansionTransformer gives each module call an (expand) and a (close) node. Members depend on the expander; the closer depends on all members; outer closers depend on inner ones (transform_module_expansion.go:32-150). References to a module's outputs go through its closer.
  • Reference edges. ReferenceTransformer builds a map from every vertex's ReferenceableAddrs() and connects each References() target. Static references resolve at whole-resource granularity: aws_x.a[0] falls back to aws_x.a, because no instance nodes exist yet (transform_reference.go:566-619). A data source gets an implicit depends_on on any managed resource it references. Actions, new in v1.14, are connected in a second pass so an action may reference the resource that triggers it; any other loop is "action reference cycle involving …" (transform_reference.go:128-188).
  • Destroy, targets, closers. DestroyEdgeTransformer, the destroy-only pruner, TargetsTransformer and QueryTransformer follow. ForcedCBDTransformer only detects create-before-destroy here; the edges that implement it exist only in the apply builder (section 07). CloseProviderTransformer adds one (close) node per provider configuration that depends on all of its consumers. CloseRootModuleTransformer adds an empty-address nodeCloseModule, rendered [root] root, connected to every vertex with no in-edges. There is no single-root requirement in v1.17 (transform_root.go:6-29). TransitiveReductionTransformer runs last and deletes every direct edge that is also reachable another way, documented as O(V(V+E)) (dag.go:172-200).

Cycles, and the direction of an edge

Edges point from dependent to dependency. The final Validate runs Tarjan's strongly connected components; any component with more than one vertex is a cycle, and a self-edge is reported separately as "Self reference" (internal/dag/dag.go:202-265). The cycle text is normalised so the same loop always prints the same way: names reversed, rotated to start at the shortest name, one per line. Two terraform_data resources that read each other's output fail validate and plan alike with Cycle: followed by terraform_data.a and terraform_data.b, exit 1 measured here. TransitiveReductionTransformer silently skips a cyclic graph, so the cycle reaches you from Validate, not from the reducer.

What the graph looks like

The engine lab's small configuration has two random_pets by count, two terraform_datas by for_each, and a child module called twice: 

variable "names" {
  type    = set(string)
  default = ["a", "b"]
}
resource "random_pet" "p" {
  count  = 2
  length = 2
}
resource "terraform_data" "d" {
  for_each = var.names
  input    = "${each.key}-${random_pet.p[0].id}"
}
module "child" {
  source = "./modules/child"
  count  = 2
  seed   = random_pet.p[count.index].id
}

Since v1.7 (#34288) plain terraform graph prints a reduced, resources-only view; the real graph needs -type=plan (internal/command/graph.go:108-180). The two differ a lot measured here: 

$ terraform graph            # resource-only (v1.7+ default): 3 nodes, 2 edges
  "terraform_data.d" -> "random_pet.p";
  "module.child.random_id.r" -> "random_pet.p";
$ terraform graph -type=plan  # 16 distinct vertices, 18 edges after transitive reduction
  "[root] module.child.var.seed (expand)" -> "[root] module.child (expand)"
  "[root] module.child.var.seed (expand)" -> "[root] random_pet.p (expand)"
  "[root] output.child_ids (expand)" -> "[root] module.child (close)"
  "[root] random_pet.p (expand)" -> "[root] provider[\"registry.terraform.io/hashicorp/random\"]"
  "[root] root" -> "[root] output.joined (expand)"

Sixteen vertices and eighteen edges, and not one of them is random_pet.p[0]. Every resource node is an (expand) node. module.child.random_id.r has no direct edge to its provider: the reducer removed it, because the node already reaches the provider through random_pet.p. The lab project in Part 4 has a 115-vertex, 217-edge plan graph, 84 of them (expand) nodes, and a 37-vertex resource-only view. Figure 10 in section 03 draws both graphs. If you debug ordering with terraform graph, pass -type=plan; the default hides every variable, local, output, provider and closer that actually orders the walk.

02Walking the DAG

A built graph does nothing until something walks it. Terraform's walker gives every vertex its own goroutine, runs a vertex as soon as its dependencies finish, and treats an error as a local event: only the dependents of a failed vertex are skipped. The -parallelism flag does not limit any of those goroutines. It limits one function call.

What a walk carries

Context.walk builds a ContextGraphWalker, starts a stop-watcher that turns Ctrl-C into provider Stop() calls, and blocks in graph.Walk(walker) (internal/terraform/context_walk.go:94-110) from the code. Plan-like walks (walkPlan, walkPlanDestroy, walkImport) carry three deep copies of state: the working State, a RefreshState and a PrevRunState. Validate walks start from empty states, and apply carries only State (context_walk.go:112-158). Every walk also gets a fresh instances.Expander, namedvals.State, ephemeral.Resources, deferring.Deferred, checks.State and its own provider and schema caches (context_walk.go:187-222). Nothing in those structures survives from one walk to the next, which is why section 05 finds a new provider process in every walk.

There are eight kinds of walk: apply, plan, plan-destroy, validate, destroy, import, eval and, since v1.15.0, init (graph_walk_operation.go:11-21). One terraform plan performs four of them. It walks an init graph for the root module, which expands into a nested init graph for the child module; then it walks a validate graph and the plan graph. If the plan has changes, it then builds but does not walk the apply graph, so that create-before-destroy cycles that exist only at apply time are reported now (checkApplyGraph, context_plan.go:478-496) measured here in a trace of the lab configuration.

A goroutine per vertex

The walker itself lives in internal/dag/walk.go. Its doc comment states the cost plainly (walk.go:16-25): 

// Walker is used to walk every vertex of a graph in parallel.
//
// A vertex will only be walked when the dependencies of that vertex have
// been walked. If two vertices can be walked at the same time, they will be.
//
// Non-parallelism can be enforced by introducing a lock in your callback
// function. However, the goroutine overhead of a walk will remain.
// Walker will create V*2 goroutines (one for each vertex, and dependency
// waiter for each vertex). In general this should be of no concern unless
// there are a huge number of vertices.

Each vertex gets walkVertex, and each vertex with dependencies also gets a waitDeps. The waiter selects on every dependency's DoneCh in turn and logs vertex %q is waiting for %q at TRACE level every five seconds while it waits (walk.go:291-310). Because edges point from dependent to dependency, "everything I have an edge to" is exactly "everything that must finish first".

A DoneCh closes whether its vertex succeeded or not. Success is a separate question, answered by reading the walker's diagsMap after all the channels have closed. This is the whole scheduling rule, walk.go:312-332: 

	// If the vertex implements [AlwaysRunVertex], then
	// return ignore the errored dependecies and return success.
	if _, ok := v.(AlwaysRunVertex); ok {
		doneCh <- true
		return
	}

	// Dependencies satisfied! We need to check if any errored
	w.diagsLock.Lock()
	defer w.diagsLock.Unlock()
	for dep := range deps {
		if w.diagsMap[dep].HasErrors() {
			// One of our dependencies failed, so return false
			doneCh <- false
			return
		}
	}

	// All dependencies satisfied and successful
	doneCh <- true
}

When the waiter answers false, walkVertex does not run the callback. It records a synthetic error, upstream dependencies failed (walk.go:264), which is filtered out of what the user sees. The vertex's own DoneCh then closes with an error recorded, and the skip propagates to its dependents in turn. Nothing else is affected from the code.

An error does not halt the walk

The consequence for a user is that a failed plan is still a partial plan. PlanAndEval returns it with Errored = true, the UI prints "Terraform planned the following actions, but then encountered a problem", and Apply refuses it with "Cannot apply failed plan" (context_plan.go:467-476, context_apply.go:127-134). In the engine lab, a terraform_data.many whose count came from another resource's unknown output failed with "Invalid count argument", and the plan still printed terraform_data.seed will be created above the error measured here. That run shows the partial plan surviving; in it, seed is many's dependency. The stronger claim, that an unrelated branch keeps planning, rests on the code above: only a dependent's waiter ever reads the failed vertex's diagnostics.

Terraform's own architecture document says otherwise. docs/architecture.md:307-310 reads: "Evaluation can fail with one or more errors, in which case the graph walk is halted and the errors are returned to the user." The code skips dependents and keeps walking. The same document describes an EnterPath method at lines 238-244 that no longer exists; the walker now caches one BuiltinEvalContext per module instance through enterScope (graph_walk_context.go:95-112). Both are documentation drift, and the code wins from the code.

The callback, and the semaphore around one call

The function the walker calls for each vertex is Graph.walk's walkFn (internal/terraform/graph.go:37-188). It applies test overrides, picks the module-scoped evaluation context, calls Execute if the vertex is a GraphNodeExecutable, then calls DynamicExpand if it is expandable, validates the returned subgraph and walks it recursively. A subgraph that fails validation is reported as a Terraform bug: "Graph node has invalid dynamic subgraph" (graph.go:161).

Only Execute takes a slot from the parallelism semaphore (graph_walk_context.go:169-175): 

func (w *ContextGraphWalker) Execute(ctx EvalContext, n GraphNodeExecutable) tfdiags.Diagnostics {
	// Acquire a lock on the semaphore
	w.Context.parallelSem.Acquire()
	defer w.Context.parallelSem.Release()

	return n.Execute(ctx, w.Operation)
}

The semaphore is a buffered channel (semaphore.go:13-25). Its size comes from -parallelism: 0 means the default of 10, and a negative value is rejected with "Invalid parallelism value" (context.go:141-157). The comment there gives two reasons for the limit: "to limit CPU pressure but also to have an extra guard against rate throttling from providers". DynamicExpand and the nested walk run outside the semaphore, so an expanding node holds no slot while its instances run. The dossier's guess is that this avoids a deadlock between a parent holding a slot and children waiting for one; that rationale is not written in the code reconstruction.

In practice, -parallelism=N caps how many vertices are inside Execute at once, which is where provider RPCs happen. It does not cap goroutines, graph size or memory: a walk with 10,000 vertices still starts about 20,000 goroutines, and they block on the channel. Lower it to stay under a cloud API's rate limit. Raising it will not make a slow provider start faster.

Policy evaluation has a semaphore of its own, sized by TF_POLICY_PARALLELISM or else GOMAXPROCS and independent of -parallelism (context.go:171-230). It was wired into core in v1.16 behind experiments and is GA in the v1.17.0 CLI. Its two node types, nodePolicyEval and nodePolicyEvalFinish, are the only implementers of dag.AlwaysRunVertex (node_policy_eval.go:21, 56), added in #39030: they run even when what they depend on failed. Part 3 covers what policy does with that: plan and apply fail open when the policy engine cannot start, init -policies fails closed, and HCP's documentation still calls the feature beta.

Watching a walk, and stopping one

The callback logs vertex %q: starting visit (%T) on entry and visit complete on exit (graph.go:47, 65-67), so a TF_LOG=trace log is a full record of the walk order, with the Go type of every node. Grepping it for starting visit is the quickest way to see which instance nodes a DynamicExpand produced; section 03 reads one such log. A vertex stuck behind a slow dependency shows up as the five-second is waiting for lines.

Ctrl-C does not cancel the walk. The stop-watcher copies the walk's provider cache and calls Stop() on each provider, which sends StopProvider. The comment at context.go:359-361 is frank about what that buys: "the stop is still advisory: Terraform will exit once the graph node completes." Whatever the provider is doing when you press it, Terraform waits for that node to finish from the code.

A rewrite the CHANGELOG does not mention

The walker in v1.17.0 is new. A "dag simplification" series by James Bardin, dated 2026-07-31 to 2026-08-04 and ending at 882f39051, turned it into a single-shot Walk(g). It removed mid-walk graph mutation (Update/Wait), the Reverse flag, the single-root check, edge sets and the Hasher. A second call on one walker now panics with "graph walker already started" (walk.go:100-108). Neither the rewrite nor AlwaysRunVertex appears in the v1.17.0 CHANGELOG from the code. Whether it changed any observable ordering or speed would need a v1.16 binary to compare against, and none was measured.

03Expansion and evaluation

The static graph knows random_pet.p; it does not know random_pet.p[0]. Instances are created during the walk, when a resource's (expand) node finally knows its count or for_each. They fan out in a small subgraph of their own, outside the parallelism semaphore.

The expander

Every walk gets one instances.Expander. Its doc comment calls it "a coordination point for gathering object repetition values (count and for_each in configuration) and then later making use of them to fully enumerate all of the instances of an object" (internal/instances/expander.go:18-47). It is guarded by a sync.RWMutex, and it expects a strict order: "each object must have its repetition mode set exactly once, and this must be done before any calls that depend on the repetition mode … If this ordering is violated, the methods will panic." The graph's edges are what guarantee that order from the code.

An expansion has one of four modes (expansion_mode.go:35-124). expansionSingle yields one instance with NoKey. expansionCount yields IntKeys 0 to n−1. expansionForEach yields StringKeys sorted lexically. expansionDeferred stands for keys that are not known yet. For each key, the mode also returns the RepetitionData that becomes count.index, each.key and each.value during evaluation.

Module expansion, then resource expansion

A module's (expand) node evaluates the call's count or for_each once per instance of the parent module, and registers the result (node_module_expand.go:118-176). The expander's comment warns that "module expansion in particular has a recursive effect that can cause deep objects to expand exponentially", and it assumes "that all instances of a module have the same static objects inside, and that they differ only in the repetition count for some of those objects". That assumption is why the static graph can stay resource-level: the shape of a module is fixed, only the counts vary. If the value is unknown, the node may register it as unknown only when deferrals are allowed.

A resource's (expand) node does its work in DynamicExpand. It first checks count and for_each for references to the resource itself (validateMetaSelfRef), then iterates every instance of its containing module, records the repetition with recordResourceData, and builds a subgraph with a miniature BasicGraphBuilder named nodeExpandPlannableResource (node_resource_plan.go:99-131, 666-812). The subgraph has five steps: three DynamicTransformers, AttachStateTransformer and TargetsTransformer. The first two are node_resource_plan.go:732-753: 

		DynamicTransformer(func(graph *Graph) error {
			// We'll add a node for all the known instance keys.
			for _, key := range knownInstKeys {
				graph.Add(n.concreteResource(ctx, knownImports, unknownImports, n.skipPlanChanges)(NewNodeAbstractResourceInstance(addr.Instance(key))))
			}
			return nil
		}),

		DynamicTransformer(func(graph *Graph) error {
			// We'll add a node if there are unknown instance keys.
			if haveUnknownKeys {
				addr := addr.Module.UnexpandedResource(addr.Resource)

				graph.Add(&nodePlannablePartialExpandedResource{
					addr:              addr,
					config:            n.Config,
					resolvedProvider:  n.ResolvedProvider,
					skipPlanChanges:   n.skipPlanChanges,
					preDestroyRefresh: n.preDestroyRefresh,
				})
			}
			return nil
		}),

The third adds orphans: state instances whose key is no longer in the expansion become concreteResourceOrphan nodes and plan a delete. When some keys are unknown, an unmatched state instance is only a "maybe orphan", planned with skipPlanChanges=true so it is refreshed but not deleted (node_resource_plan.go:768-793). No transformer in the list adds an edge between instances, so random_pet.p[0] and random_pet.p[1] plan concurrently. One practical effect: a resource whose for_each keys are partly unknown never plans a delete for an unmatched instance in that run; the delete can only come in a later run, once the keys are known reconstruction. And because section 02 showed that the nested walk runs outside the semaphore, the expanding node itself holds no slot while they do from the code.

A trace of the lab plan shows the order this produces measured here: module.child (expand), then module.child.var.seed (expand) and its two instances module.child[0].var.seed and module.child[1].var.seed, then module.child.random_id.r (expand) and its instances, then the outputs, then module.child (close) and root. Figure 10 puts the two graphs side by side.

When the keys are unknown

Expansion needs known keys. If count depends on something that will be known only after apply, and deferral is off, eval_count.go:42-43 raises the diagnostic most Terraform users have seen: 

Summary:  "Invalid count argument",
Detail:   `The "count" value depends on resource attributes that cannot be determined until apply, so Terraform cannot predict how many instances will be created. To work around this, use the -target argument to first apply only the resources that the count depends on.`,

A count derived from an ephemeral value is rejected separately, because it could not be persisted between plan and apply. The comment just above the diagnostic (eval_count.go:34-39) calls it "a rather bad outcome from a UX standpoint" and leaves a FIXME: "implement a built-in mechanism for deferring changes that can't yet be predicted, and use it to guide the user through several plan/apply steps". Until that ships, the workaround the message names is the only one a release build offers: apply the dependency first with -target, then plan the rest. A for_each whose keys are written in configuration expands even when its values are unknown: the lab's terraform_data.d had two known keys, "a" and "b", and inputs that were still unknown at plan time measured here.

Core has had a better answer since v1.8.0. The deferring package tracks deferred changes so that a partial plan can be applied and the rest planned later (internal/plans/deferring/doc.go:4-10). Deferral is transitive, plan files record five reasons for it (INSTANCE_COUNT_UNKNOWN, RESOURCE_CONFIG_UNKNOWN, PROVIDER_CONFIG_UNKNOWN, ABSENT_PREREQ, DEFERRED_PREREQ), and a resource with unknown keys becomes one nodePlannablePartialExpandedResource addressed like module.x[*].res. But the release CLI rejects -allow-deferral on plan, apply, refresh and test with "The -allow-deferral flag is only valid in experimental builds of Terraform." (internal/command/plan.go:204), and it is still behind the experiment gate on origin/main. Stacks always set DeferralAllowed. The evaluator's own comment (evaluate.go:656-662) says unknown instance keys should arise "only … in the stacks runtime (not the "normal terraform" modules runtime)", which overlooks that the test runtime carries a DeferralAllowed field too (internal/command/test.go:178) from the code. Part 3 lists deferral among the surfaces that are still gated.

Evaluating an expression

Every expression in a node goes through lang.Scope, a facade holding the data source (Data), SelfAddr, BaseDir, PureOnly, the function results table and the plan timestamp (internal/lang/scope.go:17-93). Its lang.Data is one getter per reference kind: GetResource, GetLocalValue, and so on to GetRunBlock. An errored getter yields an unknown of the right type rather than nothing (internal/lang/eval.go:544-553). The hcl.EvalContext is built lazily from the expression's own references: they are statically validated, instance subjects are widened to their resource or module call, and the whole resource object goes into the variable table (eval.go:285-420). self indexes that object by instance key.

GetResource assembles the value of a resource from three layers, in priority order (internal/terraform/evaluate.go:746-800). Deferred instances come first. Pending changes come next, with planned deletions hidden unless the operation is a destroy. State comes last, and an instance with no current object becomes cty.UnknownVal(ty). That is how random_pet.p[0].id is a known string in a second plan and an unknown string in the first. If the resource's (expand) node has not run at all, the result is "Reference to uninitialized resource"; during walkInit, every resource reference is simply cty.DynamicVal, because no state or schemas exist yet (evaluate.go:648-652, 668-686). Unknown values and their refinements are the subject of Part 1; here they are what lets the walk proceed before anything has been created.

04One instance's plan

Inside the instance subgraph, each random_pet.p[0] runs the same sequence. Core upgrades and refreshes the stored object, computes what the new object should look like, asks the provider for a plan, checks the answer, and only then decides the action, from values alone. The provider proposes; core decides. One v1.17 option, -minimal-refresh, changes the sequence, and it costs more RPCs, not fewer, as soon as anything changes.

Read, upgrade, refresh

The managed-resource path is NodePlannableResourceInstance.managedResourceExecute (internal/terraform/node_resource_plan_instance.go:191-520). It reads the instance from state and upgrades it with UpgradeResourceState, which deliberately receives no configuration: only the type, the stored schema version and the raw JSON or flatmap state, and it must return state valid under the current schema (tfplugin6.proto:506-540). The upgraded object is written into both prevRunState and refreshState. Then, unless refresh is skipped, core sends ReadResource, which also carries no configuration (current state, private bytes, provider_meta, capabilities and identity in; new state, private, deferral and identity out), and stores the result in refreshState. In refresh-only mode the work ends there from the code.

Keeping prevRunState and refreshState apart is what lets planWalk compute drift separately from proposed changes: the first is what the last apply left, the second is what the provider says exists now reconstruction.

The proposal core makes before the provider does

Before any RPC about the future, core computes a proposed new object itself with objchange.ProposedNew, after stripping marks from the config and prior values. The rule for each attribute is internal/plans/objchange/objchange.go:349-372: 

		case attr.Computed && configV.IsNull():
			// configV will always be null in this case, by definition.
			// priorV may also be null, but that's okay.
			newV = priorV

			// the exception to the above is that if the config is optional and
			// the _prior_ value contains non-computed values, we can infer
			// that the config must have been non-null previously.
			if optionalValueNotComputable(attr, priorV) {
				newV = configV
			}

		case attr.NestedType != nil:
			// For non-computed NestedType attributes, we need to descend
			// into the individual nested attributes to build the final
			// value, unless the entire nested attribute is unknown.
			newV = proposedNewNestedType(attr.NestedType, priorV, configV)
		default:
			// For non-computed attributes, we always take the config value,
			// even if it is null. If it's _required_ then null values
			// should've been caught during an earlier validation step, and
			// so we don't really care about that here.
			newV = configV
		}

Read it as a user. If an attribute is optional and computed and you delete it from your configuration, the proposal keeps the old value; the provider decides whether that means "leave it" or "reset it". If an attribute is not computed, deleting it from configuration proposes null, and the plan will show the removal.

The request, and the answer core distrusts

PlanResourceChange then carries the config, the prior state, the proposed new state, the prior private bytes, provider_meta, the client capabilities, the prior identity and, since v1.16, planned private bytes (node_resource_abstract_instance.go:998-1051). Every value crosses unmarked. Core keeps the mark paths and re-applies them afterwards, along with any paths the provider's schema calls sensitive (lines 990-993, 1180-1182). It has no choice: go-cty's msgpack encoder refuses a marked value with "value has marks, so it cannot be serialized". The consequence is that a provider never learns that you marked a value sensitive; it sees only its own schema's flags from the code.

When the answer comes back, core checks it before believing it. Write-only attributes must come back null, or the plan fails with "Provider produced invalid plan" and a message that the provider "returned a value for the write-only attribute". The planned value's type must conform to the schema. And objchange.AssertPlanValid must pass. Its doc comment is the clearest statement of what a provider may do during planning (internal/plans/objchange/plan_valid.go:26-37): 

// During planning, a provider may only make changes to attributes that are null
// (unset) in the configuration and are marked as "computed" in the resource
// type schema, in order to insert any default values the provider may know
// about. If the default value cannot be determined until apply time, the
// provider can return an unknown value. Providers are forbidden from planning a
// change that disagrees with any non-null argument in the configuration.
//
// As a special exception, providers _are_ allowed to provide attribute values
// conflicting with configuration if and only if the planned value exactly
// matches the corresponding attribute value in the prior state. The provider
// can use this to signal that the new value is functionally equivalent to the
// old and thus no change is required.

The exception is how a provider says that a differently spelled value means the same thing: it plans the prior value back, and the plan shows no change reconstruction. A response may also carry a Deferred reason; if the walk did not allow deferral and the provider returned no error, core turns that into an error itself (tfplugin6.proto:330-348). One class of provider is excused from AssertPlanValid, node_resource_abstract_instance.go:1118-1127: 

		if errs := objchange.AssertPlanValid(schema.Body, unmarkedPriorVal, unmarkedConfigVal, plannedNewVal); len(errs) > 0 {
			if resp.LegacyTypeSystem {
				// The shimming of the old type system in the legacy SDK is not precise
				// enough to pass this consistency check, so we'll give it a pass here,
				// but we will generate a warning about it so that we are more likely
				// to notice in the logs if an inconsistency beyond the type system
				// leads to a downstream provider failure.
				var buf strings.Builder
				fmt.Fprintf(&buf,
					"[WARN] Provider %q produced an invalid plan for %s, but we are tolerating it because it is using the legacy plugin SDK.\n    The following problems may be the cause of any confusing errors from downstream operations:",

LegacyTypeSystem is the SDKv2 flag that the protocol file labels "DO NOT USE THIS". If an apply fails with a confusing error from an SDKv2-based resource, the [WARN] … tolerating it line in a TF_LOG=warn log is where the real inconsistency is recorded.

Choosing the action

The provider's response lists requires_replace paths. Core keeps only those whose values actually changed, then picks the action from values in getAction, node_resource_abstract_instance.go:3065-3089: 

	switch {
	case priorVal.IsNull():
		action = plans.Create
	case forceReplace || !reqRep.Empty() || !writeOnly.Intersection(reqRep).Empty():
		// If the user "forced replace" of this instance of if there are any
		// "requires replace" paths left _after our filtering above_ then this
		// is a replace action.
		if createBeforeDestroy {
			action = plans.CreateThenDelete
		} else {
			action = plans.DeleteThenCreate
		}
		switch {
		case forceReplace:
			actionReason = plans.ResourceInstanceReplaceByRequest
		case !reqRep.Empty():
			actionReason = plans.ResourceInstanceReplaceBecauseCannotUpdate
		}
	case eq && !forceReplace:
		action = plans.NoOp
	default:
		action = plans.Update
		// "Delete" is never chosen here, because deletion plans are always
		// created more directly elsewhere, such as in "orphan" handling.
	}

Null prior means create. A forced or genuine replace path means replace, ordered by create_before_destroy. Equal means no-op. Anything else is an update. The order of a replace is fixed here, at plan time. The plan stores the action as one of the runes in plans.Action (internal/plans/action.go:6-30): + create, ~ update, ∓ delete-then-create, ± create-then-delete, - delete, and newer ones such as . forget.

A replace triggers a second request. The comment at lines 1207-1217 explains: "we'll ask the provider to plan again here, giving it a null object for the prior, and then we'll meld that with the _actual_ prior state to produce a correctly-shaped replace change." So a replaced instance costs two PlanResourceChange calls in plan. And because apply plans every instance once more (section 07), every instance sees at least two across a plan and an apply. Destroys work the other way: a provider without the plan_destroy capability is not asked at all, and the client stub returns the null proposed state as the plan (grpc_provider.go:648-654).

-minimal-refresh, counted

v1.17.0 added -minimal-refresh (#35290, 137cba0ae). When it is set, the instance node runs a plan before refreshing. If that pre-refresh plan is a no-op, the node reports it and returns without calling ReadResource. If not, it logs "Minimal refresh: refreshing resource as the initial plan produced a … change", refreshes, and plans again (node_resource_plan_instance.go:342-421). It never skips the refresh when the state or identity schema was just upgraded; orphan, deposed and destroy nodes treat it as plain -refresh=false; and on a destroy plan it simply becomes SkipRefresh from the code.

The engine lab counted the RPCs on the configuration from section 01, with existing state, four gRPC-backed instances and the two built-in terraform_data instances running in-process and uncounted measured here:

With nothing to change, the flag removes every ReadResource; the six skip lines include the two built-in instances. With one change, it costs 4 reads and 16 plans against the default's 4 and 8: the pre-refresh plan, the refresh, the real plan, and the replace re-plans on top. Use it on large configurations that are usually unchanged, where refresh dominates; leave it off for runs you expect to change things. It also does not look for drift on instances whose configuration did not change, since it never reads them reconstruction. Note what the CLI does not catch: -destroy -invoke=… reaches core and fails with "This is a bug in Terraform."; that edge is in Part 3.

05Providers are processes

Terraform does not link the AWS provider. It runs it. Every provider is an ordinary executable that core starts as a child process and talks to over gRPC on a Unix socket, with core as the client and the plugin as the server. A trivial plan of one random resource starts that binary three times. The three-cloud plan in Part 4 starts eighteen processes.

From the lock file to a factory

Meta.providerFactoriesFromLocks turns each entry in .terraform.lock.hcl into a providers.Factory, but only after the cached package matches one of the lock file's hashes. Otherwise the "factory" just returns the error: "the cached package for … does not match any of the checksums recorded in the dependency lock file" (internal/command/meta_providers.go:408-427) from the code. Part 1 explains where those hashes come from. Three other kinds of factory exist: in-process built-ins such as terraform.io/builtin/terraform, which serves terraform_data with no child process and no gRPC; CLI-config dev_overrides; and providers named in TF_REATTACH_PROVIDERS, which Terraform connects to but never starts or kills.

A managed factory call creates one process. The configuration it hands to go-plugin is meta_providers.go:456-479: 

func providerFactory(meta *providercache.CachedProvider) providers.Factory {

gRPC only, managed (so plugin.CleanupClients(), deferred in main, kills any child left running), mutual TLS on unless TF_DISABLE_PLUGIN_TLS is set, and both protocol majors offered: VersionedPlugins maps 5 to a provider and provisioner set and 6 to a provider set (internal/plugin/plugin.go:14-22). The comment on TF_DISABLE_PLUGIN_TLS says it exists for the SDK test harness's start-up cost and "is not intended to be set by end-users".

The handshake

The repository's protocol README admits that "the startup and handshake protocol is not currently documented" (docs/plugin-protocol/README.md:43-44). go-plugin's code is the specification. go-plugin adds four variables to the inherited environment: the magic cookie TF_PLUGIN_MAGIC_COOKIE, PLUGIN_MIN_PORT, PLUGIN_MAX_PORT and PLUGIN_PROTOCOL_VERSIONS (a comma list of majors), plus PLUGIN_CLIENT_CERT under AutoMTLS (go-plugin:client.go:633-692). The cookie value is a 64-hex-digit constant, identical in core and every SDK, under the comment "The magic cookie values should NEVER be changed." (internal/plugin/serve.go:34-36). It is a guard against running a plugin by accident, not a secret.

The provider checks the cookie, picks the highest major that both sides list, reserves a temp-file name under /tmp, deletes it and listens on a Unix socket there; only on Windows does it use TCP on 127.0.0.1 (go-plugin:server.go:145-222, 528-597). Then it prints one line to stdout, go-plugin:server.go:424-446: 

	if opts.Test == nil {

			listener.Addr().Network(),
			listener.Addr().String(),

		// seventh segment for gRPC broker multiplexing support, because old

		// segment will get appended to the sixth segment as "sixthpart|true".
		//

		// to handle a seventh segment, as it should now use
		// strings.Split(line, "|") and always handle each segment individually.
		if os.Getenv(envMultiplexGRPC) != "" {

		}
		fmt.Printf("%s\n", protocolLine)

The bare run exits 1. With the cookie, field 1 is go-plugin's core protocol, always 1. Field 2 is the negotiated Terraform protocol: 5, although 6 was offered, because this binary is a protocol-5 build. Offered only 6, it still answers 5 (1|5|unix|/tmp/plugin3779874446|grpc|), so the mismatch is caught by the client. Fields 3 and 4 are the socket, field 5 the transport, and field 6 the server certificate, empty here because no client certificate was passed. With one, field 6 grew to about 790 base64 characters (791 and 795 in two runs). Decoded, it is a self-signed ECDSA P-521 CA certificate for CN=localhost, O=HashiCorp, valid from 30 seconds ago for 262,980 hours, about 30 years.

The client is strict about that line. Fewer than four fields is "Unrecognized remote plugin message", a core protocol other than 1 is incompatible, the transport must be grpc, and field 6 counts as a certificate only if it is longer than 50 characters. It waits at most the default StartTimeout of one minute, which Terraform does not change; a provider that dies first gives "plugin exited before we could connect" (go-plugin:client.go:398-400, 823-929). After the handshake, core picks internal/plugin.GRPCProvider for major 5 or internal/plugin6.GRPCProvider for major 6, and keeps the *plugin.Client on it so Close() can kill the child.

Schemas, once per process unless the provider says otherwise

Before any graph is built, LoadSchemas fetches every provider's schema in a plain sequential loop (internal/schemarepo/loadschemas/load.go:36-80). For each provider it checks a process-global providers.SchemaCache; on a miss it starts a throwaway instance just to read the schema and closes it. A later process may skip the RPC only if the provider advertised get_provider_schema_optional, internal/plugin6/grpc_provider.go:96-113: 

func (p *GRPCProvider) GetProviderSchema() providers.GetProviderSchemaResponse {
	p.mu.Lock()
	defer p.mu.Unlock()

	// check the global cache if we can
	if !p.Addr.IsZero() {
		if resp, ok := providers.SchemaCache.Get(p.Addr); ok && resp.ServerCapabilities.GetProviderSchemaOptional {
			logger.Trace("GRPCProvider.v6: returning cached schema", p.Addr.String())
			return resp
		}
	}
	logger.Trace("GRPCProvider.v6: GetProviderSchema")

	// If the local cache is non-zero, we know this instance has called
	// GetProviderSchema at least once and we can return early.
	if p.schema.Provider.Body != nil {
		return p.schema
	}

The framework always advertises the capability, and so does the aws provider; in its trace every process after the first served the schema from core's cache measured here. That matters because schemas are large. The aws schema is 19,743,820 bytes of JSON with 1,742 resource types; the four cached providers' providers schema -json output is 32,820,418 bytes. Core asks gRPC for up to 64 MiB on this one response, through an option grpc-go marks experimental, where the default would be 4 MB (grpc_provider.go:52-55, 124-133). Serving the aws schema took 9–23 s depending on page cache.

A process per configuration, per walk

During a walk, provider instances are cached by provider configuration address (eval_context_builtin.go:166-214). aws and aws.west are two entries, so two processes. The provider[…] node starts its process and validates the configuration (in the validate walk) or validates and configures it (in plan and apply). The process dies when the provider's (close) node runs, after every consumer: Close() calls go-plugin's Kill(), which closes the connection, waits up to two seconds for a clean exit, then forces it (grpc_provider.go:1885-1904). Provider functions get a separate, unconfigured instance per provider type, closed at the end of the walk (eval_context_builtin.go:585-603). That is why provider::aws::arn_parse works with no provider "aws" block and no credentials, and why it costs an extra process.

The counts follow directly. A TF_LOG=trace plan of one random configuration measured here:

Three processes, one after another: schema, validate walk, plan walk. One aws configuration plus one arn_parse call also started five, with a peak of about 765–779 MB combined resident memory. The lab's three-cloud plan in Part 4 started 18: aws, google and azurerm five each, random three, at most seven alive, about 1.38 GB combined. A terraform_data-only configuration starts none.

Start-up and shutdown are cheap for small binaries and not for large ones. The random handshake took about 40–70 ms before the first RPC and exited 3–8 ms after Close; the 832 MB aws binary took 0.5–3.6 s to hand-shake and 80–260 ms to exit, both depending on page cache and load. A whole one-resource random plan ran in 0.75–0.9 s. If your plans are slow and small, count the provider configurations, aliases and function calls before you look anywhere else: each one is another launch of the binary in every walk.

Mocks do not avoid this. terraform test with mock_provider still starts the real binary once for its schema and still sends ValidateResourceConfig; only configure, plan and apply are faked, and CallFunction is forwarded to the real provider (internal/providers/mock.go:191-197, 410-412). Part 4 shows what that means for a list block in a test. When a provider crashes, core rebuilds the panic from the child's stderr, capturing lines from the first panic: or fatal error: even with logging off, and prints "The … plugin crashed!" (internal/logging/panic.go:92-217).

06The wire contract

Between core and a provider there is one file: docs/plugin-protocol/tfplugin6.proto. It is MPL-licensed while core is BUSL, it is what OpenTofu, the plugin framework and every provider build against, and it has grown from 12 RPCs to 36. Its values cross as schema-typed msgpack that can say "unknown, but not null, and starting with a-". Its version label stopped tracking its contents three releases ago.

36 RPCs, 35 methods

At v1.17.0 the Provider service declares 36 RPCs, in comment-delimited groups: information and validation, one-time configuration, the managed-resource lifecycle, ephemeral resources, list resources, functions, state stores, actions and shutdown (tfplugin6.proto:350-430). Four of them stream: ListResource, InvokeAction and ReadStateBytes stream responses, and WriteStateBytes streams requests. The header says "protocol version 6.11". The copy under internal/tfplugin6/ that the Go stubs are generated from is a git symlink to the docs file, not a duplicate from the code.

Core's side is providers.Interface, with 35 methods: the 36 RPCs minus two, plus Close (internal/providers/provider.go:17-152). The two it never calls are GetFunctions, because function signatures already arrive inside GetProviderSchema, and GetMetadata, which the proto file itself calls "CURRENTLY UNUSED", existing "mostly for convenience of code generation inside of terraform-plugin-mux" (tfplugin6.proto:353-358). plugin6.GRPCProvider is "mostly a translation layer" between those cty-typed methods and the proto types. Errors travel as diagnostics in the response, not as gRPC status codes; when a status does arrive, core maps it to one of four messages, such as "Plugin did not respond" for Unavailable (internal/plugin6/grpc_error.go:16-77). The ApplyResourceChange request has no create, update or delete flag. The provider infers which from whether the prior or planned state is null.

Protocol 5 is what the big providers speak

Protocol 6 first shipped in v0.15.0, although HashiCorp's protocol page describes it as "compatible with Terraform CLI version 1.0 and later". Protocol 5, labelled 5.10 in Terraform's tree, is still served by every provider in this machine's cache: aws 6.70.0, google 8.8.0, azurerm 5.10.0 and random 3.9.1 are all _x5 builds, and each negotiated version 5 with v1.17.0 measured here. Version 5 names the same operations differently (GetSchema, PrepareProviderConfig, Configure, Stop), keeps the provisioner service, which exists only in protocol 5, and lacks three things of 6: nested attributes (nested_type), the v1.16 computed blocks, and state stores. So none of the 4,229 resource schemas served by aws, google and azurerm contains a single nested attribute; they nest with blocks only. HashiCorp's own docs list terraform-plugin-sdk/v2 under protocol 5 only. The framework serves protocol 6 by default, which is why random, a framework provider, sets ProtocolVersion: 5 explicitly to stay on 5.

Inside a major version, negotiation is two bags of booleans (tfplugin6.proto:280-328). ServerCapabilities has plan_destroy, get_provider_schema_optional, move_resource_state and generate_resource_config. ClientCapabilities has deferral_allowed, write_only_attributes_allowed, store_planned_private and computed_blocks_allowed. CLI walks always send the last three as true, and deferral_allowed follows the walk. Protocol 5's client bag stops after the first two, and a provider's own logs show exactly those: deferral_allowed=false, write_only_attributes_allowed=true measured here.

Values: schema-typed msgpack

Every structured value crosses as a DynamicValue with two byte fields, msgpack = 1 and json = 2. Core always sends msgpack and reads msgpack when present. The wire-format document tells servers to answer in msgpack too, "because Terraform does not consistently support JSON responses across all request types and all Terraform versions"; JSON survives mainly for raw state in UpgradeResourceState. The encoding is driven by the schema: msgpack carries no type information, so both sides must agree on the schema's implied type. Strings are strings, numbers are integers, floats or decimal strings, lists, sets and tuples are arrays, maps and objects are string-keyed maps, null is c0, and only an attribute of type dynamic carries its type, as a two-element array of JSON type bytes and value. PlanResourceChange shows the pattern, internal/plugin6/grpc_provider.go:662-682:

A plain unknown is three bytes, d4 00 00. A refined one (the refinements are the not-null, prefix and bounds facts described in Part 1) is extension 12 wrapping an integer-keyed map. String prefixes are truncated below 256 bytes, and go-cty's decoder rejects a refinement payload over 1 KiB as oversize. Core's decoder is stricter than the specification: the wire-format document says a server "should treat _any_ MessagePack extension code as representing an unknown value", but core errors on any extension longer than one byte whose type is not 12. Where refinements die

Core produces refined unknowns, and providers built on terraform-plugin-go never see them. terraform-plugin-go:tftypes/value_msgpack.go:39-51, at v0.31.0, the version the framework and the aws, google and random providers use: 

func msgpackUnmarshal(dec *msgpack.Decoder, typ Type, path *AttributePath) (Value, error) {
	peek, err := dec.PeekCode()
	if err != nil {
		return Value{}, path.NewErrorf("error peeking next byte: %w", err)
	}
	if msgpackCodes.IsExt(peek) {
		// as with go-cty, assume all extensions are unknown values
		err := dec.Skip()
		if err != nil {
			return Value{}, path.NewErrorf("error skipping extension byte: %w", err)
		}
		return NewValue(typ, UnknownValue), nil
	}

Every extension becomes a plain unknown, and the provider re-encodes it as d4 00 00; the string "refine" does not appear in plugin-go's Go files. A framework provider therefore cannot use a known prefix or a known length bound to plan more precisely, even when core knows one. The refinement does survive on core's side, in the plan file, and terraform show -json drops it again, printing "input": true.

A label is not a version

The protocol README describes a rule: "A new minor release of Terraform should only introduce one new minor release of the plugin-protocol" (docs/plugin-protocol/README.md:218-220). Figure 14 reads the header and counts the RPCs at every minor tag.

The rule was followed until it was not. v1.0, v1.4, v1.5 and v1.7 kept the previous label without adding an RPC, which is harmless. Then PR #37005, first in v1.13.0, collapsed the per-minor files into one tfplugin6.proto, and v1.14 and v1.15 added eight RPCs under the same 6.10 header. The README still describes the abandoned "new file … for each new minor version" process a few lines above an "Edit the .proto files" section that contradicts it. Labels do not identify contents across repositories either. Terraform's files say 5.10 and 6.11; terraform-plugin-go v0.31.0's say 5.11 and 6.11, with the same RPC list but different messages: plugin-go's "6.11" lacks the v1.16 computed-block and planned-private fields. So framework providers on v0.31.0, which includes aws, google and random, cannot use those v1.16 features yet. OpenTofu's tfplugin6.10.proto defines all 36 RPCs, and its client calls 21 of them. Part 4 follows that divergence. If you need to know what a provider or a client supports, read its capabilities and its RPC list, not the number in the header.

On the provider side, the framework is four layers: plugin-go's tf6server speaks gRPC, the framework's proto6server converts proto to framework types, fwserver runs the logic, and the author's resource.Resource implements six required methods (Metadata, Schema, Create, Read, Update, Delete), with everything else optional. The framework always advertises four server capabilities, including get_provider_schema_optional, and it nulls write-only attributes in its own planned state before core checks that they are null. Both sides enforce the contract.

07Plan files and the apply re-plan

A saved plan looks like a script for apply to run. It is not. Apply builds a new graph from the plan's changes, plans every instance again with the inputs that are now known, and checks the new plan against the saved one. The saved plan is a contract the second plan must honour, not a list of steps.

What -out writes

terraform plan -out=p.tfplan writes a Deflate ZIP (internal/plans/planfile/writer.go:54-139). It holds a protobuf tfplan, two state snapshots (tfstate and tfstate-prev), a tfconfig/ snapshot of every module's source with a modules.json index, and the dependency lock file. Field 1 is the format version, and the reader is unforgiving about it and about the binary that wrote it, internal/plans/planfile/tfplan.go:57-62: 

	if rawPlan.Version != tfplanFormatVersion {
		return nil, fmt.Errorf("unsupported plan file format version %d; only version %d is supported", rawPlan.Version, tfplanFormatVersion)
	}

	if rawPlan.TerraformVersion != version.String() {
		return nil, fmt.Errorf("plan file was created by Terraform %s, but this is %s; plan files cannot be transferred between different Terraform versions", rawPlan.TerraformVersion, version.String())

tfplanFormatVersion is 3. A plan made by v1.17.0 can be applied only by v1.17.0: pin the exact Terraform version in the CI job that plans and the one that applies, or the hand-off fails at the door from the code.

Inside, each resource change records its address as a compact string (field 13; fields 1–6 are retired), its provider configuration (8) and the change (9) with an action and the before and after values. The protobuf Action enum skips 4: NOOP is 0 and UPDATE 3, DELETE 5, up to FORGET_THEN_CREATE 10. A DynamicValue here is "always encoded as msgpack", the same encoding as on the wire, and the provider's opaque private bytes are stored verbatim to be handed back at apply. Only root-module output changes are serialised; outputs of nested modules are recomputed at apply (tfplan.go:642-648). Root variables are stored as values, except ephemeral ones, which are stored only by name and must be supplied again at apply.

Three gates before apply starts

Applying a saved plan passes three checks. The format and version check above runs on read. Then the local backend compares the state snapshot embedded in the plan with the current state (internal/backend/local/backend_local.go:320-345). A different lineage gives "Saved plan does not match the given state". A different serial gives "Saved plan is stale": someone, possibly you, wrote state after this plan was made. A first plan embeds an empty state with serial 0 and an empty lineage. In the lab, applying p.tfplan a second time after a successful apply gave exactly Error: Saved plan is stale measured here. Last, Context.Apply refuses a plan marked Errored with "Cannot apply failed plan", the partial plans that section 02 showed are still printed.

Apply then decodes the changes, walks over a deep copy of the plan's prior state, and always sets DeferralAllowed: true (context_apply.go:198-232). One decision breaks a rule the plan format states for itself. planfile.proto:23-28 says the UI mode "must never be used to make decisions in Terraform Core during the applying of a plan", and context_apply.go:386-396 does exactly that: 

	operation := walkApply
	if plan.UIMode == plans.DestroyMode {
		// FIXME: Due to differences in how objects must be handled in the
		// graph and evaluated during a complete destroy, we must continue to
		// use plans.DestroyMode to switch on this behavior. If all objects
		// which require special destroy handling can be tracked in the plan,
		// then this switch will no longer be needed and we can remove the
		// walkDestroy operation mode.
		// TODO: Audit that and remove walkDestroy as an operation mode.
		operation = walkDestroy
	}

The apply graph is built from the diff

The apply builder (Figure 8) starts like the plan builder, then adds DiffTransformer, which creates one NodeApplyableResourceInstance per planned change, plus nodes for planned actions and deferred changes (graph_builder_apply.go:168-187). Instances exist from the start here, because the plan already enumerated them. Destroy ordering is the interesting part. DestroyEdgeTransformer explains itself at transform_destroy_edge.go:30-43: 

// DestroyEdgeTransformer is a GraphTransformer that creates the proper
// references for destroy resources. Destroy resources are more complex
// in that they must be depend on the destruction of resources that
// in turn depend on the CREATION of the node being destroy.
//
// That is complicated. Visually:
//
//	B_d -> A_d -> A -> B
//
// Notice that A destroy depends on B destroy, while B create depends on
// A create. They're inverted. This must be done for example because often
// dependent resources will block parent resources from deleting. Concrete
// example: VPC with subnets, the VPC can't be deleted while there are
// still subnets.

The dependencies it inverts are the ones recorded in state, in each instance's dependencies list, not the ones in the current configuration (transform_destroy_edge.go:126-256). That is the only way to order the destruction of something you have already deleted from your configuration. It also means a destroy follows the dependencies that were true at the last apply. No-op changes are left out. Edges across two providers are added only if they create no cycle, a check the code's own FIXME calls "the blunt hammer of checking for cycles" (lines 59-66).

create_before_destroy is an edge reversal

In plan, ForcedCBDTransformer only propagates create_before_destroy to every dependency of a node that has it, so that apply cannot form a cycle. The apply builder runs it again, under a FIXME admitting that the planned information "is lost for newly created instances". Then CBDEdgeTransformer does the actual work, transform_destroy_cbd.go:114-125: 

		// Find the resource edges
		for src := range g.EdgesTo(v).All() {

			// If source is a create node, invert the edge.
			// This covers both the node's own creator, as well as reversing
			// any dependants' edges.
			if _, ok := src.(GraphNodeCreator); ok {
				log.Printf("[TRACE] CBDEdgeTransformer: reversing edge %s -> %s", src.Name(), v.Name())
				g.RemoveEdge(src, v)
				g.Connect(v, src)
			}
		}

Every creator that waited for the destroyer now runs before it, so the old object is deleted after the new one exists and after dependents have been updated to point at it. The old object is first "deposed" under a key that DiffTransformer picks at random from unused keys, so the create node and the destroy node agree on it. A two-resource lab shows both shapes measured here: 

# create_before_destroy = false
"[root] terraform_data.base" -> "[root] terraform_data.base (destroy)"      # create waits for destroy
# create_before_destroy = true
"[root] terraform_data.base (destroy deposed 6ac341bf)" -> "[root] terraform_data.dep"   # destroy waits for dependent update
$ terraform apply p_cbd

The key in terraform graph -plan (6ac341bf) is not the key the apply used (5fd02ba5), because each graph build allocates its own; the verifier's re-run got two more different keys. Do not script against a deposed key you read from a graph.

Planning again, and two checks

Each apply node plans its instance again. The repository's lifecycle document says so plainly: "PlanResourceChange is actually called twice per run for each resource type", and on the second call the configuration is "guaranteed to have a wholly-known Configuration" (docs/resource-instance-change-lifecycle.md:160-173). Core compares the result with the saved plan in checkPlannedChange: any change of action, other than an update becoming a no-op, is "Provider produced inconsistent final plan" (node_resource_apply_instance.go:232-253, 403-468). The lifecycle document adds the value rule: "Any attribute that had a known value in the Initial Planned State must have an identical value in the Final Planned State." A provider that is asked to plan with real inputs may fill in unknowns, but may not change anything that was already known. Because the replace order was fixed in plan, a create-before-destroy that flips at apply also lands here, and Terraform calls it a bug.

Then comes ApplyResourceChange, with no create, update or delete flag, as section 06 noted. Its result must agree with the final plan: only values that were unknown may change, or the apply fails with "Provider produced inconsistent result after apply" (objchange.AssertObjectCompatible, node_resource_abstract_instance.go:2872-2916). Legacy-SDK providers again get a [WARN] instead. Applying the engine lab's saved six-create plan made 4 PlanResourceChange, 4 ApplyResourceChange and 1 ConfigureProvider gRPC calls; the two terraform_data instances ran in-process and are not counted measured here.

After each resource the local state hook writes state, and it persists on an interval too (internal/backend/local/hook_state.go:42-72). Every write bumps serial, so a fresh six-resource apply ended at serial 7. The file it writes is v4 JSON, sorted, with plaintext values and a path list of sensitive attributes. Part 3 opens it.

The JSON view is a view

terraform show -json renders a plan in its own format, format_version "1.2", and state in "1.0" (internal/command/jsonplan/plan.go:34). It is lossy. Where the plan file holds c7 07 0c 82 01 c2 02 a2 61 2d for terraform_data.d["a"].input (unknown, not null, starting a-), the JSON says only "input": true in after_unknown measured here. Tools that review plans through the JSON see less than core decided with.

That closes the engine. A configuration became a resource-level graph; a walker with a goroutine per vertex ran it and isolated failures; instances appeared at walk time; each instance was proposed by core, planned by a provider process, and checked; the result went into a ZIP that apply honours by planning again. Every step after the graph is built puts trust in core and data outside it. Part 3 follows the data that outlives the run: the state file, its locks, the refactoring blocks, and the features 1.5 through 1.17 built on this engine.
