{{S}}The wire contract

Between core and a provider there is one file: docs/plugin-protocol/tfplugin6.proto. It is MPL-licensed while core is BUSL, it is what OpenTofu, the plugin framework and every provider build against, and it has grown from 12 RPCs to 36. Its values cross as schema-typed msgpack that can say "unknown, but not null, and starting with a-". Its version label stopped tracking its contents three releases ago.

36 RPCs, 35 methods

At v1.17.0 the Provider service declares 36 RPCs, in comment-delimited groups: information and validation, one-time configuration, the managed-resource lifecycle, ephemeral resources, list resources, functions, state stores, actions and shutdown (tfplugin6.proto:350-430). Four of them stream: ListResource, InvokeAction and ReadStateBytes stream responses, and WriteStateBytes streams requests. The header says "protocol version 6.11". The copy under internal/tfplugin6/ that the Go stubs are generated from is a git symlink to the docs file, not a duplicate from the code.

Core's side is providers.Interface, with 35 methods: the 36 RPCs minus two, plus Close (internal/providers/provider.go:17-152). The two it never calls are GetFunctions, because function signatures already arrive inside GetProviderSchema, and GetMetadata, which the proto file itself calls "CURRENTLY UNUSED", existing "mostly for convenience of code generation inside of terraform-plugin-mux" (tfplugin6.proto:353-358). plugin6.GRPCProvider is "mostly a translation layer" between those cty-typed methods and the proto types. Errors travel as diagnostics in the response, not as gRPC status codes; when a status does arrive, core maps it to one of four messages, such as "Plugin did not respond" for Unavailable (internal/plugin6/grpc_error.go:16-77). The ApplyResourceChange request has no create, update or delete flag. The provider infers which from whether the prior or planned state is null.

Protocol 5 is what the big providers speak

Protocol 6 first shipped in v0.15.0, although HashiCorp's protocol page describes it as "compatible with Terraform CLI version 1.0 and later". Protocol 5, labelled 5.10 in Terraform's tree, is still served by every provider in this machine's cache: aws 6.70.0, google 8.8.0, azurerm 5.10.0 and random 3.9.1 are all _x5 builds, and each negotiated version 5 with v1.17.0 measured here. Version 5 names the same operations differently (GetSchema, PrepareProviderConfig, Configure, Stop), keeps the provisioner service, which exists only in protocol 5, and lacks three things of 6: nested attributes (nested_type), the v1.16 computed blocks, and state stores. So none of the 4,229 resource schemas served by aws, google and azurerm contains a single nested attribute; they nest with blocks only. HashiCorp's own docs list terraform-plugin-sdk/v2 under protocol 5 only. The framework serves protocol 6 by default, which is why random, a framework provider, sets ProtocolVersion: 5 explicitly to stay on 5.

Inside a major version, negotiation is two bags of booleans (tfplugin6.proto:280-328). ServerCapabilities has plan_destroy, get_provider_schema_optional, move_resource_state and generate_resource_config. ClientCapabilities has deferral_allowed, write_only_attributes_allowed, store_planned_private and computed_blocks_allowed. CLI walks always send the last three as true, and deferral_allowed follows the walk. Protocol 5's client bag stops after the first two, and a provider's own logs show exactly those: deferral_allowed=false, write_only_attributes_allowed=true measured here.

Values: schema-typed msgpack

Every structured value crosses as a DynamicValue with two byte fields, msgpack = 1 and json = 2. Core always sends msgpack and reads msgpack when present. The wire-format document tells servers to answer in msgpack too, "because Terraform does not consistently support JSON responses across all request types and all Terraform versions"; JSON survives mainly for raw state in UpgradeResourceState. The encoding is driven by the schema: msgpack carries no type information, so both sides must agree on the schema's implied type. Strings are strings, numbers are integers, floats or decimal strings, lists, sets and tuples are arrays, maps and objects are string-keyed maps, null is c0, and only an attribute of type dynamic carries its type, as a two-element array of JSON type bytes and value. PlanResourceChange shows the pattern, internal/plugin6/grpc_provider.go:662-682:

		return resp
	}

	propMP, err := msgpack.Marshal(r.ProposedNewState, resSchema.Body.ImpliedType())

		resp.Diagnostics = resp.Diagnostics.Append(err)

	protoReq := &proto6.PlanResourceChange_Request{

Unknown values need an encoding of their own, and msgpack's extension types provide it. go-cty's encoder, go-cty:cty/msgpack/unknown.go:18-41 (Terraform pins go-cty v1.18.1; this clone is a later, untagged commit): 

// unknownValBytes is the raw bytes of the msgpack fixext1 value we
// write to represent a totally unknown value. It's an extension value of
// type zero whose value is irrelevant. Since it's irrelevant, we
// set it to a single byte whose value is also zero, since that's
// the most compact possible representation.
//
// The representation of a refined unknown value is different. See
// marshalUnknownValue for more details.
var unknownValBytes = []byte{0xd4, 0, 0}

func (uv unknownType) MarshalMsgpack() ([]byte, error) {
	return unknownValBytes, nil
}

A plain unknown is three bytes, d4 00 00. A refined one (the refinements are the not-null, prefix and bounds facts described in Part 1) is extension 12 wrapping an integer-keyed map. String prefixes are truncated below 256 bytes, and go-cty's decoder rejects a refinement payload over 1 KiB as oversize. Core's decoder is stricter than the specification: the wire-format document says a server "should treat _any_ MessagePack extension code as representing an unknown value", but core errors on any extension longer than one byte whose type is not 12. A saved plan holds the same encoder's output, so a plan file shows the bytes. Two outputs added to the random configuration, "pfx-${random_pet.p.id}" and length(random_pet.p.id), decode as measured here: 

output refined_prefix (23 bytes): 92 c4 08 22 73 74 72 69 6e 67 22 c7 09 0c 82 01 c2 02 a4 70 66 78 2d
  decoded: [b'"string"', <unknown refined {1: False, 2: 'pfx-'}>]
output refined_len (21 bytes): 92 c4 08 22 6e 75 6d 62 65 72 22 c7 07 0c 82 01 c2 03 92 00 c3
  decoded: [b'"number"', <unknown refined {1: False, 3: [0, True]}>]

Read the first: 92 is the two-element dynamic wrapper, c4 08 and "string" are the type, c7 09 0c is an extension of nine bytes and type 12, 82 a two-entry map, 01 c2 "nullness: false", and 02 a4 70 66 78 2d "prefix: pfx-". The second says "a number, not null, at least 0, inclusive". Figure 13 lays out the rest of the file.

Where refinements die

Core produces refined unknowns, and providers built on terraform-plugin-go never see them. terraform-plugin-go:tftypes/value_msgpack.go:39-51, at v0.31.0, the version the framework and the aws, google and random providers use: 

func msgpackUnmarshal(dec *msgpack.Decoder, typ Type, path *AttributePath) (Value, error) {
	peek, err := dec.PeekCode()
	if err != nil {
		return Value{}, path.NewErrorf("error peeking next byte: %w", err)
	}
	if msgpackCodes.IsExt(peek) {
		// as with go-cty, assume all extensions are unknown values
		err := dec.Skip()
		if err != nil {
			return Value{}, path.NewErrorf("error skipping extension byte: %w", err)
		}
		return NewValue(typ, UnknownValue), nil
	}

Every extension becomes a plain unknown, and the provider re-encodes it as d4 00 00; the string "refine" does not appear in plugin-go's Go files. A framework provider therefore cannot use a known prefix or a known length bound to plan more precisely, even when core knows one. The refinement does survive on core's side, in the plan file, and terraform show -json drops it again, printing "input": true.

A label is not a version

The protocol README describes a rule: "A new minor release of Terraform should only introduce one new minor release of the plugin-protocol" (docs/plugin-protocol/README.md:218-220). Figure 14 reads the header and counts the RPCs at every minor tag.

The rule was followed until it was not. v1.0, v1.4, v1.5 and v1.7 kept the previous label without adding an RPC, which is harmless. Then PR #37005, first in v1.13.0, collapsed the per-minor files into one tfplugin6.proto, and v1.14 and v1.15 added eight RPCs under the same 6.10 header. The README still describes the abandoned "new file … for each new minor version" process a few lines above an "Edit the .proto files" section that contradicts it. Labels do not identify contents across repositories either. Terraform's files say 5.10 and 6.11; terraform-plugin-go v0.31.0's say 5.11 and 6.11, with the same RPC list but different messages: plugin-go's "6.11" lacks the v1.16 computed-block and planned-private fields. So framework providers on v0.31.0, which includes aws, google and random, cannot use those v1.16 features yet. OpenTofu's tfplugin6.10.proto defines all 36 RPCs, and its client calls 21 of them. Part 4 follows that divergence. If you need to know what a provider or a client supports, read its capabilities and its RPC list, not the number in the header.

On the provider side, the framework is four layers: plugin-go's tf6server speaks gRPC, the framework's proto6server converts proto to framework types, fwserver runs the logic, and the author's resource.Resource implements six required methods (Metadata, Schema, Create, Read, Update, Delete), with everything else optional. The framework always advertises four server capabilities, including get_provider_schema_optional, and it nulls write-only attributes in its own planned state before core checks that they are null. Both sides enforce the contract.
