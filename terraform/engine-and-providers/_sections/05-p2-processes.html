{{S}}Providers are processes

Terraform does not link the AWS provider. It runs it. Every provider is an ordinary executable that core starts as a child process and talks to over gRPC on a Unix socket, with core as the client and the plugin as the server. A trivial plan of one random resource starts that binary three times. The three-cloud plan in Part 4 starts eighteen processes.

From the lock file to a factory

Meta.providerFactoriesFromLocks turns each entry in .terraform.lock.hcl into a providers.Factory, but only after the cached package matches one of the lock file's hashes. Otherwise the "factory" just returns the error: "the cached package for … does not match any of the checksums recorded in the dependency lock file" (internal/command/meta_providers.go:408-427) from the code. Part 1 explains where those hashes come from. Three other kinds of factory exist: in-process built-ins such as terraform.io/builtin/terraform, which serves terraform_data with no child process and no gRPC; CLI-config dev_overrides; and providers named in TF_REATTACH_PROVIDERS, which Terraform connects to but never starts or kills.

A managed factory call creates one process. The configuration it hands to go-plugin is meta_providers.go:456-479: 

func providerFactory(meta *providercache.CachedProvider) providers.Factory {
	return func() (providers.Interface, error) {
		execFile, err := meta.ExecutableFile()
		if err != nil {
			return nil, err
		}

		config := &plugin.ClientConfig{
			HandshakeConfig:  tfplugin.Handshake,
			Logger:           logging.NewProviderLogger(""),
			AllowedProtocols: []plugin.Protocol{plugin.ProtocolGRPC},
			Managed:          true,
			Cmd:              exec.Command(execFile),
			AutoMTLS:         enableProviderAutoMTLS,
			VersionedPlugins: tfplugin.VersionedPlugins,
			SyncStdout:       logging.PluginOutputMonitor(fmt.Sprintf("%s:stdout", meta.Provider)),
			SyncStderr:       logging.PluginOutputMonitor(fmt.Sprintf("%s:stderr", meta.Provider)),
		}

		client := plugin.NewClient(config)
		rpcClient, err := client.Client()
		if err != nil {
			return nil, err
		}

gRPC only, managed (so plugin.CleanupClients(), deferred in main, kills any child left running), mutual TLS on unless TF_DISABLE_PLUGIN_TLS is set, and both protocol majors offered: VersionedPlugins maps 5 to a provider and provisioner set and 6 to a provider set (internal/plugin/plugin.go:14-22). The comment on TF_DISABLE_PLUGIN_TLS says it exists for the SDK test harness's start-up cost and "is not intended to be set by end-users".

The handshake

The repository's protocol README admits that "the startup and handshake protocol is not currently documented" (docs/plugin-protocol/README.md:43-44). go-plugin's code is the specification. go-plugin adds four variables to the inherited environment: the magic cookie TF_PLUGIN_MAGIC_COOKIE, PLUGIN_MIN_PORT, PLUGIN_MAX_PORT and PLUGIN_PROTOCOL_VERSIONS (a comma list of majors), plus PLUGIN_CLIENT_CERT under AutoMTLS (go-plugin:client.go:633-692). The cookie value is a 64-hex-digit constant, identical in core and every SDK, under the comment "The magic cookie values should NEVER be changed." (internal/plugin/serve.go:34-36). It is a guard against running a plugin by accident, not a secret.

The provider checks the cookie, picks the highest major that both sides list, reserves a temp-file name under /tmp, deletes it and listens on a Unix socket there; only on Windows does it use TCP on 127.0.0.1 (go-plugin:server.go:145-222, 528-597). Then it prints one line to stdout, go-plugin:server.go:424-446: 

	if opts.Test == nil {
		const grpcBrokerMultiplexingSupported = true
		protocolLine := fmt.Sprintf("%d|%d|%s|%s|%s|%s",
			CoreProtocolVersion,
			protoVersion,
			listener.Addr().Network(),
			listener.Addr().String(),
			protoType,
			serverCert)

		// Old clients will error with new plugins if we blindly append the
		// seventh segment for gRPC broker multiplexing support, because old
		// client code uses strings.SplitN(line, "|", 6), which means a seventh
		// segment will get appended to the sixth segment as "sixthpart|true".
		//
		// If the environment variable is set, we assume the client is new enough
		// to handle a seventh segment, as it should now use
		// strings.Split(line, "|") and always handle each segment individually.
		if os.Getenv(envMultiplexGRPC) != "" {
			protocolLine += fmt.Sprintf("|%v", grpcBrokerMultiplexingSupported)
		}
		fmt.Printf("%s\n", protocolLine)
		_ = os.Stdout.Sync()

You can hold the conversation by hand. Run the cached random binary bare, then with the cookie measured here: 

$ $R
This binary is a plugin. These are not meant to be executed directly.
Please execute the program that consumes these plugins, which will
load any plugins automatically
$ TF_PLUGIN_MAGIC_COOKIE=d602bf8f470bc67ca7faa0386276bbdd4330efaf76d1a219cb4d6991ca9872b2 \
  PLUGIN_PROTOCOL_VERSIONS=5,6 timeout 2 $R
1|5|unix|/tmp/plugin286704651|grpc|                       # stdout: the handshake

The bare run exits 1. With the cookie, field 1 is go-plugin's core protocol, always 1. Field 2 is the negotiated Terraform protocol: 5, although 6 was offered, because this binary is a protocol-5 build. Offered only 6, it still answers 5 (1|5|unix|/tmp/plugin3779874446|grpc|), so the mismatch is caught by the client. Fields 3 and 4 are the socket, field 5 the transport, and field 6 the server certificate, empty here because no client certificate was passed. With one, field 6 grew to about 790 base64 characters (791 and 795 in two runs). Decoded, it is a self-signed ECDSA P-521 CA certificate for CN=localhost, O=HashiCorp, valid from 30 seconds ago for 262,980 hours, about 30 years.

The client is strict about that line. Fewer than four fields is "Unrecognized remote plugin message", a core protocol other than 1 is incompatible, the transport must be grpc, and field 6 counts as a certificate only if it is longer than 50 characters. It waits at most the default StartTimeout of one minute, which Terraform does not change; a provider that dies first gives "plugin exited before we could connect" (go-plugin:client.go:398-400, 823-929). After the handshake, core picks internal/plugin.GRPCProvider for major 5 or internal/plugin6.GRPCProvider for major 6, and keeps the *plugin.Client on it so Close() can kill the child.

Schemas, once per process unless the provider says otherwise

Before any graph is built, LoadSchemas fetches every provider's schema in a plain sequential loop (internal/schemarepo/loadschemas/load.go:36-80). For each provider it checks a process-global providers.SchemaCache; on a miss it starts a throwaway instance just to read the schema and closes it. A later process may skip the RPC only if the provider advertised get_provider_schema_optional, internal/plugin6/grpc_provider.go:96-113: 

func (p *GRPCProvider) GetProviderSchema() providers.GetProviderSchemaResponse {
	p.mu.Lock()
	defer p.mu.Unlock()

	// check the global cache if we can
	if !p.Addr.IsZero() {
		if resp, ok := providers.SchemaCache.Get(p.Addr); ok && resp.ServerCapabilities.GetProviderSchemaOptional {
			logger.Trace("GRPCProvider.v6: returning cached schema", p.Addr.String())
			return resp
		}
	}
	logger.Trace("GRPCProvider.v6: GetProviderSchema")

	// If the local cache is non-zero, we know this instance has called
	// GetProviderSchema at least once and we can return early.
	if p.schema.Provider.Body != nil {
		return p.schema
	}

The framework always advertises the capability, and so does the aws provider; in its trace every process after the first served the schema from core's cache measured here. That matters because schemas are large. The aws schema is 19,743,820 bytes of JSON with 1,742 resource types; the four cached providers' providers schema -json output is 32,820,418 bytes. Core asks gRPC for up to 64 MiB on this one response, through an option grpc-go marks experimental, where the default would be 4 MB (grpc_provider.go:52-55, 124-133). Serving the aws schema took 9–23 s depending on page cache.

A process per configuration, per walk

During a walk, provider instances are cached by provider configuration address (eval_context_builtin.go:166-214). aws and aws.west are two entries, so two processes. The provider[…] node starts its process and validates the configuration (in the validate walk) or validates and configures it (in plan and apply). The process dies when the provider's (close) node runs, after every consumer: Close() calls go-plugin's Kill(), which closes the connection, waits up to two seconds for a clean exit, then forces it (grpc_provider.go:1885-1904). Provider functions get a separate, unconfigured instance per provider type, closed at the end of the walk (eval_context_builtin.go:585-603). That is why provider::aws::arn_parse works with no provider "aws" block and no credentials, and why it costs an extra process.

The counts follow directly. A TF_LOG=trace plan of one random configuration measured here:

Three processes, one after another: schema, validate walk, plan walk. Two aws configurations started five aws processes (one schema, two per walk), at most two alive at once, with total wall time between 11 and 48 s depending on page cache. One aws configuration plus one arn_parse call also started five, with a peak of about 765–779 MB combined resident memory. The lab's three-cloud plan in Part 4 started 18: aws, google and azurerm five each, random three, at most seven alive, about 1.38 GB combined. A terraform_data-only configuration starts none.

Start-up and shutdown are cheap for small binaries and not for large ones. The random handshake took about 40–70 ms before the first RPC and exited 3–8 ms after Close; the 832 MB aws binary took 0.5–3.6 s to hand-shake and 80–260 ms to exit, both depending on page cache and load. A whole one-resource random plan ran in 0.75–0.9 s. If your plans are slow and small, count the provider configurations, aliases and function calls before you look anywhere else: each one is another launch of the binary in every walk.

Mocks do not avoid this. terraform test with mock_provider still starts the real binary once for its schema and still sends ValidateResourceConfig; only configure, plan and apply are faked, and CallFunction is forwarded to the real provider (internal/providers/mock.go:191-197, 410-412). Part 4 shows what that means for a list block in a test. When a provider crashes, core rebuilds the panic from the child's stderr, capturing lines from the first panic: or fatal error: even with logging off, and prints "The … plugin crashed!" (internal/logging/panic.go:92-217).
