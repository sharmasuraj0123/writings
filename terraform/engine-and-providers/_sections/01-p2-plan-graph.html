{{S}}Building the plan graph

Terraform is a compiler whose intermediate representation is a dependency graph and whose back end is somebody else's process. Part 1 followed a directory of .tf files as far as a loaded configs.Config. This part takes that tree through the engine: a graph built by 31 transformers, a walker with a goroutine per vertex, instances that appear only at walk time, a provider that proposes while core decides, child processes reached through a one-line handshake, a 36-RPC wire contract, and an apply that plans again instead of replaying the plan.

Two claims carry the part. The graph is the program: ordering, parallelism, failure isolation, destroy order and create-before-destroy are all edges, not code paths. And trust lives in core: providers are untrusted processes, and core checks every answer they give. This first section builds the graph. Its claim is narrow. The graph that terraform plan builds is resource-level. Instances do not exist in it yet.

From the command to planWalk

terraform plan runs Context.Validate first and Context.Plan second. Plan is a thin wrapper around PlanAndEval (internal/terraform/context_plan.go:204, 218). PlanAndEval takes the context's run lock (acquireRun, a sync.Cond wait), checks that the option combination is legal, and dispatches to a normal, destroy or refresh-only plan from the code. The option checks are where some flags quietly constrain each other: -replace is allowed only in normal mode, -invoke only in refresh-only mode, and -minimal-refresh only in normal or destroy mode and never with -refresh=false (context_plan.go:280-333).

All three modes end in planWalk (context_plan.go:792-938). It deep-copies the prior state, applies moved blocks to the copy with prePlanFindAndApplyMoves, builds the plan graph, walks it into a fresh plans.Changes, validates the moves, computes drift, and encodes the changes against the provider schemas into a plans.Plan. Moves are applied before any graph exists but validated only after the walk. The authors explain why at context_plan.go:867-873: 

		// If any of the move statements are invalid then those errors take
		// precedence over any other errors because an incomplete move graph
		// is quite likely to be the _cause_ of various errors. This oddity
		// comes from the fact that we need to apply the moves before we
		// actually validate them, because validation depends on the result
		// of first trying to plan.

So a bad moved block replaces every other error in the output. If a plan reports only move errors, fix those first; the rest may be consequences. Part 3 covers what the move graph does to state.

One builder, 31 steps

A single PlanGraphBuilder serves plan, plan-destroy, validate and import. It swaps the concrete node factories (initPlan, initDestroy, initValidate, initImport) and keeps the pipeline (graph_builder_plan.go:159-172). Its Steps method returns 31 top-level GraphTransformers, 36 if you count the five provider sub-steps inside one GraphTransformMulti (graph_builder_plan.go:174-331) from the code. BasicGraphBuilder.Build runs them in order, logs Executing graph transform %T for each, dumps changed graphs when TF_GRAPH_TRACE is set, and validates the result at the end (graph_builder.go:36-90). A TF_LOG=trace plan prints the same 31 names in the same order measured here. Figure 8 lists them beside the apply builder's.

Read in order of effect, the pipeline does six things.

  • Nodes from configuration. ConfigTransformer adds one resource-level (expand) node per resource, data and action block. Variables, locals, outputs, checks, orphans from state and removed modules follow as their own transformers.
  • Provider wiring. Five sub-steps attach every consumer to exactly one provider configuration (transform_provider.go:20-43). MissingProviderTransformer always adds implied default configurations in the root module. ProviderTransformer walks up the module tree through Inherited() and falls back to those defaults. PruneProviderTransformer then removes providers nothing uses, so an unused provider is never launched or configured. A provider configuration that survives only in state fails with "Provider configuration not present".
  • Schemas before references. AttachSchemaTransformer runs before ReferenceTransformer because finding the references inside a resource body needs that body's schema. This is the second decode from Part 1: the undecoded hcl.Body meets the provider's schema here.
  • Module brackets. ModuleExpansionTransformer gives each module call an (expand) and a (close) node. Members depend on the expander; the closer depends on all members; outer closers depend on inner ones (transform_module_expansion.go:32-150). References to a module's outputs go through its closer.
  • Reference edges. ReferenceTransformer builds a map from every vertex's ReferenceableAddrs() and connects each References() target. Static references resolve at whole-resource granularity: aws_x.a[0] falls back to aws_x.a, because no instance nodes exist yet (transform_reference.go:566-619). A data source gets an implicit depends_on on any managed resource it references. Actions, new in v1.14, are connected in a second pass so an action may reference the resource that triggers it; any other loop is "action reference cycle involving …" (transform_reference.go:128-188).
  • Destroy, targets, closers. DestroyEdgeTransformer, the destroy-only pruner, TargetsTransformer and QueryTransformer follow. ForcedCBDTransformer only detects create-before-destroy here; the edges that implement it exist only in the apply builder (section 07). CloseProviderTransformer adds one (close) node per provider configuration that depends on all of its consumers. CloseRootModuleTransformer adds an empty-address nodeCloseModule, rendered [root] root, connected to every vertex with no in-edges. There is no single-root requirement in v1.17 (transform_root.go:6-29). TransitiveReductionTransformer runs last and deletes every direct edge that is also reachable another way, documented as O(V(V+E)) (dag.go:172-200).

Cycles, and the direction of an edge

Edges point from dependent to dependency. The final Validate runs Tarjan's strongly connected components; any component with more than one vertex is a cycle, and a self-edge is reported separately as "Self reference" (internal/dag/dag.go:202-265). The cycle text is normalised so the same loop always prints the same way: names reversed, rotated to start at the shortest name, one per line. Two terraform_data resources that read each other's output fail validate and plan alike with Cycle: followed by terraform_data.a and terraform_data.b, exit 1 measured here. TransitiveReductionTransformer silently skips a cyclic graph, so the cycle reaches you from Validate, not from the reducer.

What the graph looks like

The engine lab's small configuration has two random_pets by count, two terraform_datas by for_each, and a child module called twice: 

variable "names" {
  type    = set(string)
  default = ["a", "b"]
}
resource "random_pet" "p" {
  count  = 2
  length = 2
}
resource "terraform_data" "d" {
  for_each = var.names
  input    = "${each.key}-${random_pet.p[0].id}"
}
module "child" {
  source = "./modules/child"
  count  = 2
  seed   = random_pet.p[count.index].id
}

Since v1.7 (#34288) plain terraform graph prints a reduced, resources-only view; the real graph needs -type=plan (internal/command/graph.go:108-180). The two differ a lot measured here: 

$ terraform graph            # resource-only (v1.7+ default): 3 nodes, 2 edges
  "terraform_data.d" -> "random_pet.p";
  "module.child.random_id.r" -> "random_pet.p";
$ terraform graph -type=plan  # 16 distinct vertices, 18 edges after transitive reduction
  "[root] module.child.var.seed (expand)" -> "[root] module.child (expand)"
  "[root] module.child.var.seed (expand)" -> "[root] random_pet.p (expand)"
  "[root] output.child_ids (expand)" -> "[root] module.child (close)"
  "[root] random_pet.p (expand)" -> "[root] provider[\"registry.terraform.io/hashicorp/random\"]"
  "[root] root" -> "[root] output.joined (expand)"

Sixteen vertices and eighteen edges, and not one of them is random_pet.p[0]. Every resource node is an (expand) node. module.child.random_id.r has no direct edge to its provider: the reducer removed it, because the node already reaches the provider through random_pet.p. The lab project in Part 4 has a 115-vertex, 217-edge plan graph, 84 of them (expand) nodes, and a 37-vertex resource-only view. Figure 10 in section 03 draws both graphs. If you debug ordering with terraform graph, pass -type=plan; the default hides every variable, local, output, provider and closer that actually orders the walk.
