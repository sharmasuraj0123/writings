{{S}}Expansion and evaluation

The static graph knows random_pet.p; it does not know random_pet.p[0]. Instances are created during the walk, when a resource's (expand) node finally knows its count or for_each. They fan out in a small subgraph of their own, outside the parallelism semaphore.

The expander

Every walk gets one instances.Expander. Its doc comment calls it "a coordination point for gathering object repetition values (count and for_each in configuration) and then later making use of them to fully enumerate all of the instances of an object" (internal/instances/expander.go:18-47). It is guarded by a sync.RWMutex, and it expects a strict order: "each object must have its repetition mode set exactly once, and this must be done before any calls that depend on the repetition mode … If this ordering is violated, the methods will panic." The graph's edges are what guarantee that order from the code.

An expansion has one of four modes (expansion_mode.go:35-124). expansionSingle yields one instance with NoKey. expansionCount yields IntKeys 0 to n−1. expansionForEach yields StringKeys sorted lexically. expansionDeferred stands for keys that are not known yet. For each key, the mode also returns the RepetitionData that becomes count.index, each.key and each.value during evaluation.

Module expansion, then resource expansion

A module's (expand) node evaluates the call's count or for_each once per instance of the parent module, and registers the result (node_module_expand.go:118-176). The expander's comment warns that "module expansion in particular has a recursive effect that can cause deep objects to expand exponentially", and it assumes "that all instances of a module have the same static objects inside, and that they differ only in the repetition count for some of those objects". That assumption is why the static graph can stay resource-level: the shape of a module is fixed, only the counts vary. If the value is unknown, the node may register it as unknown only when deferrals are allowed.

A resource's (expand) node does its work in DynamicExpand. It first checks count and for_each for references to the resource itself (validateMetaSelfRef), then iterates every instance of its containing module, records the repetition with recordResourceData, and builds a subgraph with a miniature BasicGraphBuilder named nodeExpandPlannableResource (node_resource_plan.go:99-131, 666-812). The subgraph has five steps: three DynamicTransformers, AttachStateTransformer and TargetsTransformer. The first two are node_resource_plan.go:732-753: 

		DynamicTransformer(func(graph *Graph) error {
			// We'll add a node for all the known instance keys.
			for _, key := range knownInstKeys {
				graph.Add(n.concreteResource(ctx, knownImports, unknownImports, n.skipPlanChanges)(NewNodeAbstractResourceInstance(addr.Instance(key))))
			}
			return nil
		}),

		DynamicTransformer(func(graph *Graph) error {
			// We'll add a node if there are unknown instance keys.
			if haveUnknownKeys {
				addr := addr.Module.UnexpandedResource(addr.Resource)

				graph.Add(&nodePlannablePartialExpandedResource{
					addr:              addr,
					config:            n.Config,
					resolvedProvider:  n.ResolvedProvider,
					skipPlanChanges:   n.skipPlanChanges,
					preDestroyRefresh: n.preDestroyRefresh,
				})
			}
			return nil
		}),

The third adds orphans: state instances whose key is no longer in the expansion become concreteResourceOrphan nodes and plan a delete. When some keys are unknown, an unmatched state instance is only a "maybe orphan", planned with skipPlanChanges=true so it is refreshed but not deleted (node_resource_plan.go:768-793). No transformer in the list adds an edge between instances, so random_pet.p[0] and random_pet.p[1] plan concurrently. One practical effect: a resource whose for_each keys are partly unknown never plans a delete for an unmatched instance in that run; the delete can only come in a later run, once the keys are known reconstruction. And because section 02 showed that the nested walk runs outside the semaphore, the expanding node itself holds no slot while they do from the code.

A trace of the lab plan shows the order this produces measured here: module.child (expand), then module.child.var.seed (expand) and its two instances module.child[0].var.seed and module.child[1].var.seed, then module.child.random_id.r (expand) and its instances, then the outputs, then module.child (close) and root. When the keys are unknown

Expansion needs known keys. If count depends on something that will be known only after apply, and deferral is off, eval_count.go:42-43 raises the diagnostic most Terraform users have seen: 

Summary:  "Invalid count argument",
Detail:   `The "count" value depends on resource attributes that cannot be determined until apply, so Terraform cannot predict how many instances will be created. To work around this, use the -target argument to first apply only the resources that the count depends on.`,

A count derived from an ephemeral value is rejected separately, because it could not be persisted between plan and apply. The comment just above the diagnostic (eval_count.go:34-39) calls it "a rather bad outcome from a UX standpoint" and leaves a FIXME: "implement a built-in mechanism for deferring changes that can't yet be predicted, and use it to guide the user through several plan/apply steps". Until that ships, the workaround the message names is the only one a release build offers: apply the dependency first with -target, then plan the rest. A for_each whose keys are written in configuration expands even when its values are unknown: the lab's terraform_data.d had two known keys, "a" and "b", and inputs that were still unknown at plan time measured here.

Core has had a better answer since v1.8.0. The deferring package tracks deferred changes so that a partial plan can be applied and the rest planned later (internal/plans/deferring/doc.go:4-10). Deferral is transitive, plan files record five reasons for it (INSTANCE_COUNT_UNKNOWN, RESOURCE_CONFIG_UNKNOWN, PROVIDER_CONFIG_UNKNOWN, ABSENT_PREREQ, DEFERRED_PREREQ), and a resource with unknown keys becomes one nodePlannablePartialExpandedResource addressed like module.x[*].res. But the release CLI rejects -allow-deferral on plan, apply, refresh and test with "The -allow-deferral flag is only valid in experimental builds of Terraform." (internal/command/plan.go:204), and it is still behind the experiment gate on origin/main. Stacks always set DeferralAllowed. The evaluator's own comment (evaluate.go:656-662) says unknown instance keys should arise "only … in the stacks runtime (not the "normal terraform" modules runtime)", which overlooks that the test runtime carries a DeferralAllowed field too (internal/command/test.go:178) from the code. Part 3 lists deferral among the surfaces that are still gated.

Evaluating an expression

Every expression in a node goes through lang.Scope, a facade holding the data source (Data), SelfAddr, BaseDir, PureOnly, the function results table and the plan timestamp (internal/lang/scope.go:17-93). Its lang.Data is one getter per reference kind: GetResource, GetLocalValue, and so on to GetRunBlock. An errored getter yields an unknown of the right type rather than nothing (internal/lang/eval.go:544-553). The hcl.EvalContext is built lazily from the expression's own references: they are statically validated, instance subjects are widened to their resource or module call, and the whole resource object goes into the variable table (eval.go:285-420). self indexes that object by instance key.

GetResource assembles the value of a resource from three layers, in priority order (internal/terraform/evaluate.go:746-800). Deferred instances come first. Pending changes come next, with planned deletions hidden unless the operation is a destroy. State comes last, and an instance with no current object becomes cty.UnknownVal(ty). That is how random_pet.p[0].id is a known string in a second plan and an unknown string in the first. If the resource's (expand) node has not run at all, the result is "Reference to uninitialized resource"; during walkInit, every resource reference is simply cty.DynamicVal, because no state or schemas exist yet (evaluate.go:648-652, 668-686). Unknown values and their refinements are the subject of Part 1; here they are what lets the walk proceed before anything has been created.
