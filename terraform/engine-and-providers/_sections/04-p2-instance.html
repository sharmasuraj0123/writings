{{S}}One instance's plan

Inside the instance subgraph, each random_pet.p[0] runs the same sequence. Core upgrades and refreshes the stored object, computes what the new object should look like, asks the provider for a plan, checks the answer, and only then decides the action, from values alone. The provider proposes; core decides. One v1.17 option, -minimal-refresh, changes the sequence, and it costs more RPCs, not fewer, as soon as anything changes.

Read, upgrade, refresh

The managed-resource path is NodePlannableResourceInstance.managedResourceExecute (internal/terraform/node_resource_plan_instance.go:191-520). It reads the instance from state and upgrades it with UpgradeResourceState, which deliberately receives no configuration: only the type, the stored schema version and the raw JSON or flatmap state, and it must return state valid under the current schema (tfplugin6.proto:506-540). The upgraded object is written into both prevRunState and refreshState. Then, unless refresh is skipped, core sends ReadResource, which also carries no configuration (current state, private bytes, provider_meta, capabilities and identity in; new state, private, deferral and identity out), and stores the result in refreshState. In refresh-only mode the work ends there from the code.

Keeping prevRunState and refreshState apart is what lets planWalk compute drift separately from proposed changes: the first is what the last apply left, the second is what the provider says exists now reconstruction.

The proposal core makes before the provider does

Before any RPC about the future, core computes a proposed new object itself with objchange.ProposedNew, after stripping marks from the config and prior values. The rule for each attribute is internal/plans/objchange/objchange.go:349-372: 

		case attr.Computed && configV.IsNull():
			// configV will always be null in this case, by definition.
			// priorV may also be null, but that's okay.
			newV = priorV

			// the exception to the above is that if the config is optional and
			// the _prior_ value contains non-computed values, we can infer
			// that the config must have been non-null previously.
			if optionalValueNotComputable(attr, priorV) {
				newV = configV
			}

		case attr.NestedType != nil:
			// For non-computed NestedType attributes, we need to descend
			// into the individual nested attributes to build the final
			// value, unless the entire nested attribute is unknown.
			newV = proposedNewNestedType(attr.NestedType, priorV, configV)
		default:
			// For non-computed attributes, we always take the config value,
			// even if it is null. If it's _required_ then null values
			// should've been caught during an earlier validation step, and
			// so we don't really care about that here.
			newV = configV
		}

Read it as a user. If an attribute is optional and computed and you delete it from your configuration, the proposal keeps the old value; the provider decides whether that means "leave it" or "reset it". If an attribute is not computed, deleting it from configuration proposes null, and the plan will show the removal.

The request, and the answer core distrusts

PlanResourceChange then carries the config, the prior state, the proposed new state, the prior private bytes, provider_meta, the client capabilities, the prior identity and, since v1.16, planned private bytes (node_resource_abstract_instance.go:998-1051). Every value crosses unmarked. Core keeps the mark paths and re-applies them afterwards, along with any paths the provider's schema calls sensitive (lines 990-993, 1180-1182). It has no choice: go-cty's msgpack encoder refuses a marked value with "value has marks, so it cannot be serialized". The consequence is that a provider never learns that you marked a value sensitive; it sees only its own schema's flags from the code.

When the answer comes back, core checks it before believing it. Write-only attributes must come back null, or the plan fails with "Provider produced invalid plan" and a message that the provider "returned a value for the write-only attribute". The planned value's type must conform to the schema. And objchange.AssertPlanValid must pass. Its doc comment is the clearest statement of what a provider may do during planning (internal/plans/objchange/plan_valid.go:26-37): 

// During planning, a provider may only make changes to attributes that are null
// (unset) in the configuration and are marked as "computed" in the resource
// type schema, in order to insert any default values the provider may know
// about. If the default value cannot be determined until apply time, the
// provider can return an unknown value. Providers are forbidden from planning a
// change that disagrees with any non-null argument in the configuration.
//
// As a special exception, providers _are_ allowed to provide attribute values
// conflicting with configuration if and only if the planned value exactly
// matches the corresponding attribute value in the prior state. The provider
// can use this to signal that the new value is functionally equivalent to the
// old and thus no change is required.

The exception is how a provider says that a differently spelled value means the same thing: it plans the prior value back, and the plan shows no change reconstruction. A response may also carry a Deferred reason; if the walk did not allow deferral and the provider returned no error, core turns that into an error itself (tfplugin6.proto:330-348). One class of provider is excused from AssertPlanValid, node_resource_abstract_instance.go:1118-1127: 

		if errs := objchange.AssertPlanValid(schema.Body, unmarkedPriorVal, unmarkedConfigVal, plannedNewVal); len(errs) > 0 {
			if resp.LegacyTypeSystem {
				// The shimming of the old type system in the legacy SDK is not precise
				// enough to pass this consistency check, so we'll give it a pass here,
				// but we will generate a warning about it so that we are more likely
				// to notice in the logs if an inconsistency beyond the type system
				// leads to a downstream provider failure.
				var buf strings.Builder
				fmt.Fprintf(&buf,
					"[WARN] Provider %q produced an invalid plan for %s, but we are tolerating it because it is using the legacy plugin SDK.\n    The following problems may be the cause of any confusing errors from downstream operations:",

LegacyTypeSystem is the SDKv2 flag that the protocol file labels "DO NOT USE THIS". If an apply fails with a confusing error from an SDKv2-based resource, the [WARN] … tolerating it line in a TF_LOG=warn log is where the real inconsistency is recorded.

Choosing the action

The provider's response lists requires_replace paths. Core keeps only those whose values actually changed, then picks the action from values in getAction, node_resource_abstract_instance.go:3065-3089: 

	switch {
	case priorVal.IsNull():
		action = plans.Create
	case forceReplace || !reqRep.Empty() || !writeOnly.Intersection(reqRep).Empty():
		// If the user "forced replace" of this instance of if there are any
		// "requires replace" paths left _after our filtering above_ then this
		// is a replace action.
		if createBeforeDestroy {
			action = plans.CreateThenDelete
		} else {
			action = plans.DeleteThenCreate
		}
		switch {
		case forceReplace:
			actionReason = plans.ResourceInstanceReplaceByRequest
		case !reqRep.Empty():
			actionReason = plans.ResourceInstanceReplaceBecauseCannotUpdate
		}
	case eq && !forceReplace:
		action = plans.NoOp
	default:
		action = plans.Update
		// "Delete" is never chosen here, because deletion plans are always
		// created more directly elsewhere, such as in "orphan" handling.
	}

Null prior means create. A forced or genuine replace path means replace, ordered by create_before_destroy. Equal means no-op. Anything else is an update. The order of a replace is fixed here, at plan time. The plan stores the action as one of the runes in plans.Action (internal/plans/action.go:6-30): + create, ~ update, ∓ delete-then-create, ± create-then-delete, - delete, and newer ones such as . forget.

A replace triggers a second request. The comment at lines 1207-1217 explains: "we'll ask the provider to plan again here, giving it a null object for the prior, and then we'll meld that with the _actual_ prior state to produce a correctly-shaped replace change." So a replaced instance costs two PlanResourceChange calls in plan. And because apply plans every instance once more (section 07), every instance sees at least two across a plan and an apply. Destroys work the other way: a provider without the plan_destroy capability is not asked at all, and the client stub returns the null proposed state as the plan (grpc_provider.go:648-654).

-minimal-refresh, counted

v1.17.0 added -minimal-refresh (#35290, 137cba0ae). When it is set, the instance node runs a plan before refreshing. If that pre-refresh plan is a no-op, the node reports it and returns without calling ReadResource. If not, it logs "Minimal refresh: refreshing resource as the initial plan produced a … change", refreshes, and plans again (node_resource_plan_instance.go:342-421). It never skips the refresh when the state or identity schema was just upgraded; orphan, deposed and destroy nodes treat it as plain -refresh=false; and on a destroy plan it simply becomes SkipRefresh from the code.

The engine lab counted the RPCs on the configuration from section 01, with existing state, four gRPC-backed instances and the two built-in terraform_data instances running in-process and uncounted measured here: 

mode=''                ReadResource=4 PlanRC=4  Upgrade=4 minimal_skip=0
mode='-minimal-refresh' ReadResource=0 PlanRC=4  Upgrade=4 minimal_skip=6
mode='-refresh=false'  ReadResource=0 PlanRC=4  Upgrade=4
mode='-refresh-only'   ReadResource=4 PlanRC=0  Upgrade=4
# after changing random_pet length 2->3 (forces replacement downstream):
-minimal-refresh       ReadResource=4 PlanRC=16 refreshing=6   Plan: 4 to add, 2 to change, 4 to destroy.
# same change, default mode:
(default)              ReadResource=4 PlanRC=8
$ terraform plan -minimal-refresh -refresh=false
Error: Incompatible refresh options

With nothing to change, the flag removes every ReadResource; the six skip lines include the two built-in instances. With one change, it costs 4 reads and 16 plans against the default's 4 and 8: the pre-refresh plan, the refresh, the real plan, and the replace re-plans on top. Use it on large configurations that are usually unchanged, where refresh dominates; leave it off for runs you expect to change things. It also does not look for drift on instances whose configuration did not change, since it never reads them reconstruction. Note what the CLI does not catch: -destroy -invoke=… reaches core and fails with "This is a bug in Terraform."; that edge is in Part 3.
