{{S}}Walking the DAG

A built graph does nothing until something walks it. Terraform's walker gives every vertex its own goroutine, runs a vertex as soon as its dependencies finish, and treats an error as a local event: only the dependents of a failed vertex are skipped. The -parallelism flag does not limit any of those goroutines. It limits one function call.

What a walk carries

Context.walk builds a ContextGraphWalker, starts a stop-watcher that turns Ctrl-C into provider Stop() calls, and blocks in graph.Walk(walker) (internal/terraform/context_walk.go:94-110) from the code. Plan-like walks (walkPlan, walkPlanDestroy, walkImport) carry three deep copies of state: the working State, a RefreshState and a PrevRunState. Validate walks start from empty states, and apply carries only State (context_walk.go:112-158). Every walk also gets a fresh instances.Expander, namedvals.State, ephemeral.Resources, deferring.Deferred, checks.State and its own provider and schema caches (context_walk.go:187-222). Nothing in those structures survives from one walk to the next, which is why section 05 finds a new provider process in every walk.

There are eight kinds of walk: apply, plan, plan-destroy, validate, destroy, import, eval and, since v1.15.0, init (graph_walk_operation.go:11-21). One terraform plan performs four of them. It walks an init graph for the root module, which expands into a nested init graph for the child module; then it walks a validate graph and the plan graph. If the plan has changes, it then builds but does not walk the apply graph, so that create-before-destroy cycles that exist only at apply time are reported now (checkApplyGraph, context_plan.go:478-496) measured here in a trace of the lab configuration.

A goroutine per vertex

The walker itself lives in internal/dag/walk.go. Its doc comment states the cost plainly (walk.go:16-25): 

// Walker is used to walk every vertex of a graph in parallel.
//
// A vertex will only be walked when the dependencies of that vertex have
// been walked. If two vertices can be walked at the same time, they will be.
//
// Non-parallelism can be enforced by introducing a lock in your callback
// function. However, the goroutine overhead of a walk will remain.
// Walker will create V*2 goroutines (one for each vertex, and dependency
// waiter for each vertex). In general this should be of no concern unless
// there are a huge number of vertices.

Each vertex gets walkVertex, and each vertex with dependencies also gets a waitDeps. The waiter selects on every dependency's DoneCh in turn and logs vertex %q is waiting for %q at TRACE level every five seconds while it waits (walk.go:291-310). Because edges point from dependent to dependency, "everything I have an edge to" is exactly "everything that must finish first".

A DoneCh closes whether its vertex succeeded or not. Success is a separate question, answered by reading the walker's diagsMap after all the channels have closed. This is the whole scheduling rule, walk.go:312-332: 

	// If the vertex implements [AlwaysRunVertex], then
	// return ignore the errored dependecies and return success.
	if _, ok := v.(AlwaysRunVertex); ok {
		doneCh <- true
		return
	}

	// Dependencies satisfied! We need to check if any errored
	w.diagsLock.Lock()
	defer w.diagsLock.Unlock()
	for dep := range deps {
		if w.diagsMap[dep].HasErrors() {
			// One of our dependencies failed, so return false
			doneCh <- false
			return
		}
	}

	// All dependencies satisfied and successful
	doneCh <- true
}

When the waiter answers false, walkVertex does not run the callback. It records a synthetic error, upstream dependencies failed (walk.go:264), which is filtered out of what the user sees. The vertex's own DoneCh then closes with an error recorded, and the skip propagates to its dependents in turn. Nothing else is affected from the code.

An error does not halt the walk

The consequence for a user is that a failed plan is still a partial plan. PlanAndEval returns it with Errored = true, the UI prints "Terraform planned the following actions, but then encountered a problem", and Apply refuses it with "Cannot apply failed plan" (context_plan.go:467-476, context_apply.go:127-134). In the engine lab, a terraform_data.many whose count came from another resource's unknown output failed with "Invalid count argument", and the plan still printed terraform_data.seed will be created above the error measured here. That run shows the partial plan surviving; in it, seed is many's dependency. The stronger claim, that an unrelated branch keeps planning, rests on the code above: only a dependent's waiter ever reads the failed vertex's diagnostics.

Terraform's own architecture document says otherwise. docs/architecture.md:307-310 reads: "Evaluation can fail with one or more errors, in which case the graph walk is halted and the errors are returned to the user." The code skips dependents and keeps walking. The same document describes an EnterPath method at lines 238-244 that no longer exists; the walker now caches one BuiltinEvalContext per module instance through enterScope (graph_walk_context.go:95-112). Both are documentation drift, and the code wins from the code.

The callback, and the semaphore around one call

The function the walker calls for each vertex is Graph.walk's walkFn (internal/terraform/graph.go:37-188). It applies test overrides, picks the module-scoped evaluation context, calls Execute if the vertex is a GraphNodeExecutable, then calls DynamicExpand if it is expandable, validates the returned subgraph and walks it recursively. A subgraph that fails validation is reported as a Terraform bug: "Graph node has invalid dynamic subgraph" (graph.go:161).

Only Execute takes a slot from the parallelism semaphore (graph_walk_context.go:169-175): 

func (w *ContextGraphWalker) Execute(ctx EvalContext, n GraphNodeExecutable) tfdiags.Diagnostics {
	// Acquire a lock on the semaphore
	w.Context.parallelSem.Acquire()
	defer w.Context.parallelSem.Release()

	return n.Execute(ctx, w.Operation)
}

The semaphore is a buffered channel (semaphore.go:13-25). Its size comes from -parallelism: 0 means the default of 10, and a negative value is rejected with "Invalid parallelism value" (context.go:141-157). The comment there gives two reasons for the limit: "to limit CPU pressure but also to have an extra guard against rate throttling from providers". DynamicExpand and the nested walk run outside the semaphore, so an expanding node holds no slot while its instances run. The dossier's guess is that this avoids a deadlock between a parent holding a slot and children waiting for one; that rationale is not written in the code reconstruction.

In practice, -parallelism=N caps how many vertices are inside Execute at once, which is where provider RPCs happen. It does not cap goroutines, graph size or memory: a walk with 10,000 vertices still starts about 20,000 goroutines, and they block on the channel. Lower it to stay under a cloud API's rate limit. Raising it will not make a slow provider start faster.

Policy evaluation has a semaphore of its own, sized by TF_POLICY_PARALLELISM or else GOMAXPROCS and independent of -parallelism (context.go:171-230). It was wired into core in v1.16 behind experiments and is GA in the v1.17.0 CLI. Its two node types, nodePolicyEval and nodePolicyEvalFinish, are the only implementers of dag.AlwaysRunVertex (node_policy_eval.go:21, 56), added in #39030: they run even when what they depend on failed. Part 3 covers what policy does with that: plan and apply fail open when the policy engine cannot start, init -policies fails closed, and HCP's documentation still calls the feature beta.

Watching a walk, and stopping one

The callback logs vertex %q: starting visit (%T) on entry and visit complete on exit (graph.go:47, 65-67), so a TF_LOG=trace log is a full record of the walk order, with the Go type of every node. Grepping it for starting visit is the quickest way to see which instance nodes a DynamicExpand produced; section 03 reads one such log. A vertex stuck behind a slow dependency shows up as the five-second is waiting for lines.

Ctrl-C does not cancel the walk. The stop-watcher copies the walk's provider cache and calls Stop() on each provider, which sends StopProvider. The comment at context.go:359-361 is frank about what that buys: "the stop is still advisory: Terraform will exit once the graph node completes." Whatever the provider is doing when you press it, Terraform waits for that node to finish from the code.

A rewrite the CHANGELOG does not mention

The walker in v1.17.0 is new. A "dag simplification" series by James Bardin, dated 2026-07-31 to 2026-08-04 and ending at 882f39051, turned it into a single-shot Walk(g). It removed mid-walk graph mutation (Update/Wait), the Reverse flag, the single-root check, edge sets and the Hasher. A second call on one walker now panics with "graph walker already started" (walk.go:100-108). Neither the rewrite nor AlwaysRunVertex appears in the v1.17.0 CHANGELOG from the code. Whether it changed any observable ordering or speed would need a v1.16 binary to compare against, and none was measured.
