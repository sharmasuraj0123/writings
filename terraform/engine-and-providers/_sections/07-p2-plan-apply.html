{{S}}Plan files and the apply re-plan

A saved plan looks like a script for apply to run. It is not. Apply builds a new graph from the plan's changes, plans every instance again with the inputs that are now known, and checks the new plan against the saved one. The saved plan is a contract the second plan must honour, not a list of steps.

What -out writes

terraform plan -out=p.tfplan writes a Deflate ZIP (internal/plans/planfile/writer.go:54-139). It holds a protobuf tfplan, two state snapshots (tfstate and tfstate-prev), a tfconfig/ snapshot of every module's source with a modules.json index, and the dependency lock file. The engine lab's plan measured here:

Field 1 is the format version, and the reader is unforgiving about it and about the binary that wrote it, internal/plans/planfile/tfplan.go:57-62: 

	if rawPlan.Version != tfplanFormatVersion {
		return nil, fmt.Errorf("unsupported plan file format version %d; only version %d is supported", rawPlan.Version, tfplanFormatVersion)
	}

	if rawPlan.TerraformVersion != version.String() {
		return nil, fmt.Errorf("plan file was created by Terraform %s, but this is %s; plan files cannot be transferred between different Terraform versions", rawPlan.TerraformVersion, version.String())

tfplanFormatVersion is 3. A plan made by v1.17.0 can be applied only by v1.17.0: pin the exact Terraform version in the CI job that plans and the one that applies, or the hand-off fails at the door from the code.

Inside, each resource change records its address as a compact string (field 13; fields 1–6 are retired), its provider configuration (8) and the change (9) with an action and the before and after values. The protobuf Action enum skips 4: NOOP is 0 and UPDATE 3, DELETE 5, up to FORGET_THEN_CREATE 10. A DynamicValue here is "always encoded as msgpack", the same encoding as on the wire, and the provider's opaque private bytes are stored verbatim to be handed back at apply. Only root-module output changes are serialised; outputs of nested modules are recomputed at apply (tfplan.go:642-648). Root variables are stored as values, except ephemeral ones, which are stored only by name and must be supplied again at apply.

Three gates before apply starts

Applying a saved plan passes three checks. The format and version check above runs on read. Then the local backend compares the state snapshot embedded in the plan with the current state (internal/backend/local/backend_local.go:320-345). A different lineage gives "Saved plan does not match the given state". A different serial gives "Saved plan is stale": someone, possibly you, wrote state after this plan was made. A first plan embeds an empty state with serial 0 and an empty lineage. In the lab, applying p.tfplan a second time after a successful apply gave exactly Error: Saved plan is stale measured here. Last, Context.Apply refuses a plan marked Errored with "Cannot apply failed plan", the partial plans that section 02 showed are still printed.

Apply then decodes the changes, walks over a deep copy of the plan's prior state, and always sets DeferralAllowed: true (context_apply.go:198-232). One decision breaks a rule the plan format states for itself. planfile.proto:23-28 says the UI mode "must never be used to make decisions in Terraform Core during the applying of a plan", and context_apply.go:386-396 does exactly that: 

	operation := walkApply
	if plan.UIMode == plans.DestroyMode {
		// FIXME: Due to differences in how objects must be handled in the
		// graph and evaluated during a complete destroy, we must continue to
		// use plans.DestroyMode to switch on this behavior. If all objects
		// which require special destroy handling can be tracked in the plan,
		// then this switch will no longer be needed and we can remove the
		// walkDestroy operation mode.
		// TODO: Audit that and remove walkDestroy as an operation mode.
		operation = walkDestroy
	}

The apply graph is built from the diff

The apply builder (Figure 8) starts like the plan builder, then adds DiffTransformer, which creates one NodeApplyableResourceInstance per planned change, plus nodes for planned actions and deferred changes (graph_builder_apply.go:168-187). Instances exist from the start here, because the plan already enumerated them. Destroy ordering is the interesting part. DestroyEdgeTransformer explains itself at transform_destroy_edge.go:30-43: 

// DestroyEdgeTransformer is a GraphTransformer that creates the proper
// references for destroy resources. Destroy resources are more complex
// in that they must be depend on the destruction of resources that
// in turn depend on the CREATION of the node being destroy.
//
// That is complicated. Visually:
//
//	B_d -> A_d -> A -> B
//
// Notice that A destroy depends on B destroy, while B create depends on
// A create. They're inverted. This must be done for example because often
// dependent resources will block parent resources from deleting. Concrete
// example: VPC with subnets, the VPC can't be deleted while there are
// still subnets.

The dependencies it inverts are the ones recorded in state, in each instance's dependencies list, not the ones in the current configuration (transform_destroy_edge.go:126-256). That is the only way to order the destruction of something you have already deleted from your configuration. It also means a destroy follows the dependencies that were true at the last apply. No-op changes are left out. Edges across two providers are added only if they create no cycle, a check the code's own FIXME calls "the blunt hammer of checking for cycles" (lines 59-66).

create_before_destroy is an edge reversal

In plan, ForcedCBDTransformer only propagates create_before_destroy to every dependency of a node that has it, so that apply cannot form a cycle. The apply builder runs it again, under a FIXME admitting that the planned information "is lost for newly created instances". Then CBDEdgeTransformer does the actual work, transform_destroy_cbd.go:114-125: 

		// Find the resource edges
		for src := range g.EdgesTo(v).All() {

			// If source is a create node, invert the edge.
			// This covers both the node's own creator, as well as reversing
			// any dependants' edges.
			if _, ok := src.(GraphNodeCreator); ok {
				log.Printf("[TRACE] CBDEdgeTransformer: reversing edge %s -> %s", src.Name(), v.Name())
				g.RemoveEdge(src, v)
				g.Connect(v, src)
			}
		}

Every creator that waited for the destroyer now runs before it, so the old object is deleted after the new one exists and after dependents have been updated to point at it. The old object is first "deposed" under a key that DiffTransformer picks at random from unused keys, so the create node and the destroy node agree on it. A two-resource lab shows both shapes measured here:

# create_before_destroy = true
"[root] terraform_data.base (destroy deposed 6ac341bf)" -> "[root] terraform_data.dep"   # destroy waits for dependent update

The key in terraform graph -plan (6ac341bf) is not the key the apply used (5fd02ba5), because each graph build allocates its own; the verifier's re-run got two more different keys. Do not script against a deposed key you read from a graph.

Planning again, and two checks

Each apply node plans its instance again. The repository's lifecycle document says so plainly: "PlanResourceChange is actually called twice per run for each resource type", and on the second call the configuration is "guaranteed to have a wholly-known Configuration" (docs/resource-instance-change-lifecycle.md:160-173). Core compares the result with the saved plan in checkPlannedChange: any change of action, other than an update becoming a no-op, is "Provider produced inconsistent final plan" (node_resource_apply_instance.go:232-253, 403-468). The lifecycle document adds the value rule: "Any attribute that had a known value in the Initial Planned State must have an identical value in the Final Planned State." A provider that is asked to plan with real inputs may fill in unknowns, but may not change anything that was already known. Because the replace order was fixed in plan, a create-before-destroy that flips at apply also lands here, and Terraform calls it a bug.

Then comes ApplyResourceChange, with no create, update or delete flag, as section 06 noted. Its result must agree with the final plan: only values that were unknown may change, or the apply fails with "Provider produced inconsistent result after apply" (objchange.AssertObjectCompatible, node_resource_abstract_instance.go:2872-2916). Legacy-SDK providers again get a [WARN] instead. Applying the engine lab's saved six-create plan made 4 PlanResourceChange, 4 ApplyResourceChange and 1 ConfigureProvider gRPC calls; the two terraform_data instances ran in-process and are not counted measured here.

After each resource the local state hook writes state, and it persists on an interval too (internal/backend/local/hook_state.go:42-72). Every write bumps serial, so a fresh six-resource apply ended at serial 7. The file it writes is v4 JSON, sorted, with plaintext values and a path list of sensitive attributes. Part 3 opens it.

The JSON view is a view

terraform show -json renders a plan in its own format, format_version "1.2", and state in "1.0" (internal/command/jsonplan/plan.go:34). It is lossy. Where the plan file holds c7 07 0c 82 01 c2 02 a2 61 2d for terraform_data.d["a"].input (unknown, not null, starting a-), the JSON says only "input": true in after_unknown measured here. Tools that review plans through the JSON see less than core decided with.

That closes the engine. A configuration became a resource-level graph; a walker with a goroutine per vertex ran it and isolated failures; instances appeared at walk time; each instance was proposed by core, planned by a provider process, and checked; the result went into a ZIP that apply honours by planning again. Every step after the graph is built puts trust in core and data outside it. Part 3 follows the data that outlives the run: the state file, its locks, the refactoring blocks, and the features 1.5 through 1.17 built on this engine.
