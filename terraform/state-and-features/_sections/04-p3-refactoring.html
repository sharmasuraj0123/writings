{{S}}Refactoring in configuration

terraform state mv, rm and import edit the record directly, one command at a time, with nothing to review. Since v1.1 Terraform has been moving each of those edits into a block in the configuration: moved, then import in v1.5, removed in v1.7. The blocks run inside plan, show up in the plan like any change, and reach stored state only when that plan is applied. That is the whole argument for them.

Surgery, and what it does not do

The state subcommands only edit records. In the lab, state mv 'random_pet.a["x"]' 'random_pet.a["z"]' on a for_each resource succeeded and bumped serial from 4 to 5; the next plan then proposed to create a["x"] and destroy a["z"] "(because key ["z"] is not in for_each map)" measured here. The configuration still said x, so the move made the record disagree with it. state rm likewise leaves the object running and the next plan re-creates it. Both have -dry-run, and both write a timestamped backup, but only for local state; remote backends get none (internal/command/state_meta.go:29-97). Neither is reviewed by anyone before it lands.

moved: applied to a copy, before the graph

Moves run at the very start of planWalk, before the plan graph exists, against a deep copy of the prior state, at internal/terraform/context_plan.go:669-680 and 796-801:

Explicit moved blocks are joined by implied moves, which reproduce the pre-1.1 heuristic for adding or removing count: random_pet.single becomes random_pet.single[0], but only for resources that no explicit statement mentions (internal/refactoring/move_statement.go:104-125). ApplyMoves builds a small DAG of the statements, transitively reduces it and walks it in reverse topological order; if the graph is invalid, no move is applied (move_execute.go:33-104, 217-240). A move never clobbers: an object already at the destination blocks the move and wins (move_execute.go:119-127). A move that touches instances excluded by -target is an error that lists the extra -target= options needed (context_plan.go:682-748) from the code. Because the graph is built afterwards, everything downstream, including the engine walk of Part 2, sees the post-move addresses.

Since v1.8 a move may change resource type. Core then calls the target provider's MoveResourceState RPC to convert the object (internal/refactoring/cross_provider_move.go:59-200). Terraform's own first cross-type move is null_resource to terraform_data (v1.9.0). random 3.9.1 implements none, so moved { from = random_pet.new to = random_string.new } failed "Unable to Move Resource State … does not include move resource state support" measured here (not re-run by a verifier). HashiCorp's refactoring guide asks module authors to keep moved blocks forever in shared modules, because a consumer that has not yet applied the move needs them.

removed and the forget action

removed (v1.7, #34251) is the configuration form of state rm. Its CHANGELOG entry says "Removing an object from state is a new type of action which is planned and applied like any other." The commit added the plan action Forget and two apply nodes, NodeForgetResourceInstance for current objects and NodeForgetDeposedResourceInstanceObject for deposed ones; both only drop the object from state (internal/plans/action.go:16; internal/terraform/node_resource_forget.go:18). Read the default carefully: removed means destroy unless it says lifecycle { destroy = false } (internal/configs/removed.go:34-130) from the code. A removed block written to "stop managing" a resource without that line will delete it. The block takes only destroy-time provisioners and connection, and destroy is decoded with a nil evaluation context, so it must be a literal: destroy = var.d fails "Variables not allowed" (removed.go:72-75), the same rule as every meta-argument (Part 1).

v1.16 (#38784) put destroy = false on ordinary resource blocks too, and routed every would-be destroy of such a resource through forget. For an orphan the check is at internal/terraform/node_resource_plan_orphan.go:147-160: 

	if n.Config != nil && n.Config.Managed != nil {
		if n.Config.Managed.DestroySet && !n.Config.Managed.Destroy {
			forget = true
		}
	}

	if !n.skipRefresh && !forget {
		// Refresh this instance even though it is going to be destroyed, in
		// order to catch missing resources. If this is a normal plan,
		// providers expect a Read request to remove missing resources from the
		// plan before apply, and may not handle a missing resource during
		// Delete correctly.  If this is a simple refresh, Terraform is
		// expected to remove the missing resource from the state entirely
		refreshedState, refreshDeferred, refreshDiags := n.refresh(ctx, states.NotDeposed, oldState, ctx.Deferrals().DeferralAllowed())

A forget also skips the refresh, so ReadResource is never called for an object about to be released. Other paths go through resourceLifecycleForget (node_resource_abstract_instance.go:3487-3494). In the lab, a removed block with destroy = false and a count shrink on a destroy = false resource both planned ["forget"], with reasons delete_because_no_resource_config and delete_because_count_index, "0 to destroy", and the warning "Some objects will no longer be managed by Terraform" measured here. v1.17 adds ForgetThenCreate, so -replace on such a resource plans ["forget","create"] and says "must be replaced, but the existing object will not be destroyed"; v1.16 had only CreateThenForget, the create-before-destroy order (plans/action.go:16-18). On origin/main, 34210d4b5c rewrites forget handling as "forget removed objects by containment" with unchanged behaviour, and dce44bddf9 "handle forget in combination with CBD nodes" may change the create-before-destroy bookkeeping.

import: from literal IDs to identities

The import block started in v1.5.0 as "a configuration-driven, plannable action" with a literal id. v1.6 allowed any expression known at plan time, v1.7 added for_each, v1.12 added identity objects (#36703) and v1.16 lifted the root-module-only rule (#38352). At v1.17.0 importBlockSchema has five attributes, provider, for_each, id, to (the only required one) and identity; decodeImportBlock requires exactly one of id and identity, so that mistake is caught at load, before any provider starts (internal/configs/import.go:96-137) from the code. Both forms end in one RPC, at internal/terraform/node_resource_plan_instance.go:855-868: 

		if importTarget.Type().IsObjectType() {
			// Identity-based import
			resp = provider.ImportResourceState(providers.ImportResourceStateRequest{
				TypeName:           addr.Resource.Resource.Type,
				Identity:           importTarget,
				ClientCapabilities: ctx.ClientCapabilities(),
			})
		} else {
			// ID-based/string import
			resp = provider.ImportResourceState(providers.ImportResourceStateRequest{
				TypeName:           addr.Resource.Resource.Type,
				ID:                 importTarget.AsString(),
				ClientCapabilities: ctx.ClientCapabilities(),
			})

An import plans like any change and can be replaced in the same plan. The lab imported two random_ids with for_each; "aGVsbG8" is base64url for the five bytes "hello" and cannot fit byte_length = 4, so the plan said random_id.imported["b"] must be replaced with "Warning: this will destroy the imported resource", and "Plan: 2 to import, 1 to add, 0 to change, 1 to destroy." measured here. Read the import lines of a plan as carefully as the destroy lines.

plan -generate-config-out=PATH writes resource blocks for imports that have none. It asks the provider through GenerateResourceConfig (v1.14) when the provider advertises that capability, and otherwise guesses from the imported state with genconfig.ExtractLegacyConfigFromState (node_resource_plan_instance.go:1192-1209). random 3.9.1 does not, so the lab got keepers = null and prefix = null lines. At v1.17.0, three years after import went GA, the flag still prints "Warning: Config generation is experimental" whenever it writes a file (internal/backend/local/backend_plan.go:281-286), and the warning is unchanged on main. Generating config needs a target that is not expanded: a keyed to with no matching for_each resource fails "The target resource does not use for_each."

All three in one plan

The lab combined a rename, a count-to-for_each conversion with two moved blocks, a removed with destroy = false, a resource that gained count = 1 with no moved block, and an import measured here:
