{{S}}What is still gated

Three surfaces at the front of the arc are not finished in the open-source CLI. Deferred actions have been in core since v1.8 and still need an experimental build. Stacks is GA, but only as an HCP Terraform product, and the CLI command downloads a plugin to run it. Terraform Policy is GA in the v1.17 CLI, runs as a separate executable, and fails open for plan and apply. The newest surfaces are Terraform-only and partly run outside the terraform process.

Deferral: in core, not in the CLI

The deferring package (db07b905e, 26 January 2024, first tagged in v1.8.0) tracks resources whose plan must wait, so that a partial plan can be applied and the rest planned later (internal/plans/deferring/doc.go:4-10). Deferral is transitive: anything that depends on a deferred object is deferred too, and the whole mechanism is a no-op when deferral is not allowed (deferred.go:288-330). With deferral on, unknown count or for_each keys become nodePlannablePartialExpandedResource nodes addressed like module.x[*].res, and a plan file can record five reasons, from INSTANCE_COUNT_UNKNOWN to DEFERRED_PREREQ (internal/plans/planproto/planfile.proto:438-445) from the code.

The switch is -allow-deferral, added on 3 April 2024 and first tagged in v1.9.0. Every release binary through v1.17.0 rejects it, as a belated flag-parse error at internal/command/plan.go:195-207: "The -allow-deferral flag is only valid in experimental builds of Terraform." measured here. Two runtimes turn it on in code: the Stacks runtime always sets DeferralAllowed: true (internal/stacks/stackruntime/internal/stackeval/client_capabilities.go:12), and terraform test passes it through (internal/command/test.go:178). A plain CLI apply sets it only to honour deferrals already recorded. So in the CLI an unknown count still fails "Invalid count argument" (Part 2), and if a provider answers PlanAction with Deferred anyway, core reports UnexpectedProviderDeferralDiagnostic. The v1.17 experiments footer describes the feature as permitting unknown count and for_each in module, resource and data blocks. On origin/main it is still under EXPERIMENTS. In practice, deferral is GA only inside Stacks.

Stacks: a product with a CLI shim

HashiCorp announced Stacks GA at HashiConf on 25 September 2025, "for all new HCP Terraform plans based on resources under management (RUM)". It is an HCP product. terraform stacks (v1.13.0, #36931) "delegates all execution to an internal plugin": the CLI discovers the stacksplugin.v1 service on app.terraform.io, downloads the plugin and talks to it over go-plugin gRPC with the cookie key TF_STACKS_MAGIC_COOKIE (internal/command/stacks.go:58-77) from the code. The first terraform stacks -help, run under HOME=$PWD, downloaded tfstacks 1.4.0, 22,585,528 bytes, into .terraform.d/stacksplugin/; a verifier later deleted it. A tiny stack of one random component passed stacks init and validate locally once a .terraform-version file existed, a rule the plugin enforces and this repository does not measured here.

The language and runtime are not hidden: they live in internal/stacks/*, driven over terraform rpcapi, which v1.13.0 declared GA while saying it is "not intended for public consumption". Core carries a few Stacks-only switches, such as AllowRootEphemeralOutputs (§06) and always-on deferral, and some CHANGELOG lines are Stacks work in core: input-variable validation (#38240) and component no-op reporting (#38049) in v1.15. Part 4 places this in the commercial edge.

Terraform Policy: GA, out of process, fail-open

Policy is a second plugin protocol. policy.Connect execs tfpolicy-plugin rpcapi, found on $PATH or through TF_POLICY_PLUGIN, as a go-plugin child with AutoMTLS and magic cookie value 6F11ED78A2AB (internal/policy/client.go:31, 116-145; added in #38514, first tagged v1.16.0). The service has Setup, EvaluateResource, EvaluateProvider and EvaluateModule, plus a reverse CallbackService through which the plugin asks core for GetResources and GetDataSource; Setup returns version constraints checked against Terraform (internal/policy/proto/policy.proto:14-29) from the code.

It runs at three stages, InitEvaluationStage, PlanEvaluationStage and ApplyEvaluationStage (internal/policy/evaluation_stage.go:10-16). At init, the module and provider installers ask it about each source and version and refuse to download on an error (internal/command/meta_policy.go:83-180). At plan and apply, each instance's attributes and prior attributes go to EvaluateResource from a separate policy subgraph whose nodes run even after their dependencies fail, under a semaphore of TF_POLICY_PARALLELISM or GOMAXPROCS, independent of -parallelism (internal/terraform/policy.go:27-52; graph_policy.go:11-60). The lab's apply trace from §01, with no policy configured, logs "Using GOMAXPROCS=2 for policy evaluation parallelism" measured here. Part 2 shows the walker's AlwaysRunVertex that makes those nodes run.

Setup is where the asymmetry lives. plan logs a failed setup and carries on, at internal/command/plan.go:106-116: 

	if len(args.PolicyPaths) > 0 {

With no tfpolicy-plugin on the path, the lab saw both halves measured here: 

$ terraform plan -policies=policies -out=p.bin       (policies/ is an empty dir; no tfpolicy-plugin on PATH)
Error: Failed to connect to policy engine
Failed to connect to policy engine: failed to connect to plugin: exec: "tfpolicy-plugin": executable file not found in $PATH.
Terraform will perform the following actions: … Plan: 1 to add …                                  plan_rc=0
$ terraform apply -policies=policies p.bin  → Error: Failed to connect … / Apply complete! Resources: 1 added   apply_rc=0
$ terraform plan -policies=nope    → Terraform cannot find the policy path at nope. …
$ terraform query -policies=f.hcl  → … path of a policy set directory, not an individual policy file.

An "Error:" was printed, the plan and the apply both went ahead, and both exited 0; init -policies exits 1 (behaviour, measured, verified by a re-run of plan and apply). The fail-open is deliberate, as the comment says, and it has a second form. With the real plugin 0.5.0 installed, a local backend sends a nil entitlement, which internal/policy/policy.go:71-74 says means "the plugin skips the check"; the plugin instead rejected it with "entitlement check failed: client did not supply entitlement information.", and the plan again proceeded with exit 0. So a local plan -policies never enforced anything here (Part 4 has that run). In CI, do not treat exit 0 from plan -policies as a pass; check that policy results were actually reported.

Paths are checked before any of this: plan, apply and init accept a policy file or a directory (validatePolicyPaths), while query requires a policy-set directory (#39238) (internal/command/policy.go:13-80). The pieces that arrived in v1.16 faced HCP first: run policy summaries (#38715) and plugin credentials taken from the cloud or remote backend (#38716). The local -policies path stayed experimental until v1.17.

Which "GA"

The v1.17.0 CHANGELOG says -policies on plan, apply and query no longer needs an experimental build, and cites #38970. That PR is a replace-action split from 10 August 2026. The gate was removed by c0a2efe291 (#38996, 1 September 2026), whose changie entry carries Issue: "38970", and whose body was rewritten from "plan, apply, and init" to "plan, apply, and query" (CHANGELOG mistake, code, verified). The flag itself appears only in query -help. The entry says nothing about fail-open setup or the local entitlement failure. HCP's policy documentation still says "beta" and "requires v1.16alpha"; the install page says beta and "requires Terraform v1.16 or later"; HCP's public beta started on 16 July 2026. On origin/main, the 1.18.0 Unreleased CHANGELOG still lists terraform query -policies as experimental (CHANGELOG, code, per a verifier). Three surfaces, three maturity labels, for one flag.

Policies are *.policy.hcl files of resource_policy "TYPE" "NAME" blocks with enforce { condition, error_message, info_message }, filter, locals, operations and an enforcement_level of advisory, mandatory_overridable or mandatory, the default, according to HashiCorp's reference for v0.5.x. What a running plugin does with a mandatory_overridable failure in the local CLI, which has no override UI, could not be tested without an entitled engine.

Taken together, what is still gated at v1.17.0 is machinery rather than language: the cloud, test cleanup and state migrate commands, -allow-deferral, test backend and skip_cleanup, and provider state_store all need an experimental build (commands.go:453-466). The commercial engines, Stacks and Policy, ship as separate executables that the CLI downloads or execs. That is the same seam as the providers of Part 2, used this time for HashiCorp's own products reconstruction.
