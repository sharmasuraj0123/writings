{{S}}Locks, per backend

A state lock is whatever atomic primitive the backend's storage happens to offer: a POSIX record lock, a conditional object write, a blob lease, a database advisory lock. Core sees only a Lock method that returns an ID or an error. Two defaults decide how that works in practice. -lock-timeout is zero, so a held lock fails your command at once. And the S3 backend, configured with neither of its two lock options, takes no lock at all and says nothing about it.

One attempt by default

A lock request carries a LockInfo with seven fields, ID, Operation, Info, Who, Version, Created and Path; its ID comes from math/rand in UUID shape, with a comment that it "doesn't need to be cryptographically secure" (internal/states/statemgr/locker.go:118-172) from the code. The retry loop is LockWithContext, at locker.go:75-88 and 101-111 (the guard for an incomplete LockError in between is left out): 

func LockWithContext(ctx context.Context, s Locker, info *LockInfo) (string, error) {
	delay := time.Second
	maxDelay := 16 * time.Second
	for {
		id, err := s.Lock(info)
		if err == nil {
			return id, nil
		}

		le, ok := err.(*LockError)
		if !ok {
			// not a lock error, so we can't retry
			return "", err
		}
	…
		select {
		case <-ctx.Done():
			// return the last lock error with the info
			return "", err
		case <-time.After(delay):
			if delay < maxDelay {
				delay *= 2
			}
		}
	}
}

Only a *LockError whose Info has an ID is retried; anything else fails immediately. The wait starts at one second and doubles to a 16-second cap. Every state-touching command defaults -lock-timeout to 0s: plan, apply, refresh, init, state mv, rm, push and replace-provider (internal/command/arguments/extended.go:270-271, init.go:110-111 and the state command parsers) from the code. With a zero timeout the context is already done when the first LockError comes back, so there is exactly one attempt (internal/command/clistate/state.go:109-138). The CLI prints "Acquiring state lock…" only if the lock takes longer than its 400 ms LockThreshold (clistate/state.go:23).

Two processes against one local state show all of it. The lab ran a nine-second apply in the background, then tried everything else against the held lock measured here: 

$ terraform apply -auto-approve &        # holds the lock ~9 s
$ cat .terraform.tfstate.lock.info
{"ID":"b6aa29e9-…","Operation":"OperationTypeApply","Info":"","Who":"coder@…","Version":"1.17.0","Created":"2026-10-23T15:23:05.72…Z","Path":"terraform.tfstate"}
$ time terraform plan          → Error acquiring the state lock / Error message: resource temporarily unavailable   (real 0.350s)
$ terraform plan -lock=false   → Plan: 0 to add, 1 to change, 0 to destroy.
$ terraform force-unlock -force <ID>  → Failed to unlock state: LocalState not locked
$ terraform force-unlock <ID>         → Local state cannot be unlocked by another process
$ TF_LOG=trace terraform plan -lock-timeout=20s → attempts at 43.224, 44.225, 46.226, 50.229
                                                 → Plan: 1 to add, 0 to change, 1 to destroy.  (real 7.501s)

The immediate failure took 0.35 s here and 0.14 s on a verifier's re-run; that number moves with the box. The four attempts with a 20-second timeout sit at +0, +1, +3 and +7 s, which is waits of 1, 2 and 4 s, and the plan got the lock when the apply finished; a re-run saw the same shape. -lock=false really does bypass the lock: statemgr.LockDisabled turns Lock and Unlock into no-ops and passes reads and writes through (internal/states/statemgr/lock.go:13-48), and the bypassing plan completed while the other process held the apply lock.

plan takes the lock too, with operation OperationTypePlan, so a teammate's long plan blocks your apply, and with the default timeout your apply fails at once rather than waiting measured here (the plan-locking run, against the toy HTTP backend, was not re-run by a verifier). The practical setting is a non-zero -lock-timeout in CI, sized to your longest plan.

What each backend builds

local. A non-blocking POSIX fcntl F_SETLK on terraform.tfstate itself (LockFileEx on Windows), plus a 0600 sidecar .terraform.tfstate.lock.info holding the LockInfo (internal/states/statemgr/filesystem_lock_unix.go:15-41; filesystem.go:487-529). The kernel lock dies with the process that holds it, and force-unlock refuses local state either way: without -force it says the state "cannot be unlocked by another process", and with it the new process finds it holds nothing, "LocalState not locked" (internal/command/unlock.go:78-110; filesystem.go:345-351) from the code.

s3. Two mechanisms, both opt-in. use_lockfile writes the LockInfo JSON to <key>.tflock with a conditional PutObject carrying If-None-Match: *; on a 412 Terraform reads the existing .tflock to name the holder (s3/client.go:346-404). dynamodb_table does a PutItem with attribute_not_exists(LockID), where LockID is <bucket>/<key>, and keeps a -md5 digest item that drives a consistency loop retrying a mismatched Get every 2 s for up to 10 s (s3/client.go:39, 57-125, 406-436). The matrix is at internal/backend/remote-state/s3/client.go:285-288 and 327-340: 

	// no file, no dynamodb
	if !c.useLockFile && c.ddbTable == "" {
		return "", nil
	}
	…
	// double locking: dynamodb + file (design decision: both must succeed)
	log.Info("Attempting to lock remote state (S3 Native and DynamoDB)...")
	if err := c.lockWithFile(ctx, info, log); err != nil {
		return "", err
	}

	if err := c.lockWithDynamoDB(ctx, info); err != nil {
		// Release the file lock if attempting to acquire the DynamoDB lock fails.
		if unlockErr := c.unlockWithFile(ctx, info.ID, &statemgr.LockError{}, log); unlockErr != nil {
			return "", fmt.Errorf("failed to clean up file lock after DynamoDB lock error: %v; original error: %w", unlockErr, err)
		}

		return "", err
	}

The first three lines are the finding: with neither option set, Lock returns an empty ID and no error, so every command proceeds as if it held the lock from the code. Nothing warns. Native locking arrived in v1.10.0 alongside DynamoDB (code first committed on 1 September 2024, 8be88f76e) and was declared GA in v1.11.0 (#36338), which deprecated the DynamoDB arguments. The deprecation warning comes from PrepareConfig, so it appears at init and not at validate, which printed "Success!" for a dynamodb_table backend measured here (not re-run by a verifier). If you run S3 state, set use_lockfile = true. One open question sits under that advice: whether S3-compatible stores such as MinIO, R2 or Ceph honour If-None-Match; if one does not, use_lockfile may silently not lock there. Unlock in both modes reads the lock, compares the ID, then deletes, and a TODO notes that the DynamoDB comparison is not atomic (s3/client.go:508-589).

gcs and azurerm. GCS creates <prefix>/<workspace>.tflock with a DoesNotExist condition and uses the object's generation number as the lock ID; unlock is a delete with GenerationMatch (gcs/client.go:96-139). azurerm takes an infinite blob lease (LeaseDuration: -1) on the state blob itself, proposing the LockInfo ID as the lease ID, and stores the info base64-encoded in blob metadata terraformlockid (azure/client.go:25-27, 143-270) from the code.

http. Locking happens only if lock_address is set, using configurable LOCK/UNLOCK methods where 409 or 423 means "locked", and state writes carry the lock ID as ?ID=… (http/client.go:93-123, 205-243). Unlock(id) never sends id: it replays this process's own lock JSON (http/client.go:126-143). A fresh force-unlock process has no lock JSON, so the lab server received UNLOCK body=b''; a bogus ID "succeeded"; and a force-unlock during a live apply let a second plan lock and unlock while the apply was still running, after which the apply posted with its stale ID measured here. Those runs were not re-run by a verifier; the code half is confirmed. HashiCorp's locking page calls the lock ID "a nonce" that makes unlocks target the right lock; for HTTP the client does not enforce that, and the server must.

The rest. pg uses pg_try_advisory_lock; kubernetes a coordination.k8s.io/v1 Lease whose holder identity is the lock ID; oci a conditional PutObject with IfNoneMatch: "*"; oss a TableStore row (internal/backend/remote-state/{pg,kubernetes,oci,oss}). Backends are compiled in, not plugins: v1.17 ships 13 names plus the internal cloud (internal/backend/init/init.go:33-86). oci is the newest. Its CHANGELOG line in v1.12.0 cites #34465, while the commit that added it is #36872 (804e97021), and git tag --contains first lists v1.13.0 (CHANGELOG mistake, code, verified). A generic remote.State whose client has no Lock at all also "succeeds" silently (internal/states/remote/state.go:238-250).

HCP Terraform and state_store. The cloud backend's lock is a workspace lock ("Locked by Terraform"), and its force-unlock ID is literally <org>/<workspace> (internal/cloud/state.go:334-361, 452-520). Experimental pluggable state storage hands state to a provider through eight tfplugin6 RPCs, including LockState and UnlockState, with chunks negotiated at 8 MiB and capped at 128 MiB (docs/plugin-protocol/tfplugin6.proto:403-421; internal/backend/pluggable/chunks/chunks.go:6-18). LockState carries only type, state ID and operation, and the gRPC client returns a plain error, so -lock-timeout would never retry it (internal/states/remote/remote_grpc.go:118-130). That consequence is inferred from code; testing it needs an experimental build. The release binary rejects the block outright: "Blocks of type "state_store" are not expected here." measured here
