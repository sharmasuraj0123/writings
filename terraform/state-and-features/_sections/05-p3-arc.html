{{S}}A schema, a node, an RPC: 1.5 to 1.17

Thirteen minor releases run from v1.5.0 (12 June 2023) to v1.17.0 (21 October 2026). Almost every feature they added follows one recipe: a small hcl.BodySchema and decoder in internal/configs, a graph node or a change in node behaviour in internal/terraform, and usually one new RPC in the plugin protocol. Each one is small in code and large in surface, because the language, the CLI, the test runner and the protocol all have to agree on it. This section takes the features that are not about state or secrets; §06 to §08 take the rest.

The recipe follows from Part 1's first design choice. HCL parses without meaning and Terraform decodes each block against a schema of its own (Part 1), so a new block type costs a schema and a decoder, not a grammar change. The engine runs whatever nodes the transformers add (Part 2), so new behaviour is a node. And anything the provider must do is an RPC. Figure 18 places the features on the release line; Figure 19, in §07, lists the schema, node and RPC behind each one reconstruction.

Three examples show the shape. check is checkBlockSchema plus a nodeCheckAssert and needs no RPC at all. Provider functions are a namespace in lang.Scope, an unconfigured provider instance, and the GetFunctions and CallFunction RPCs. Cross-type moved is a field on an existing block, a step in ApplyMoves, and MoveResourceState. The pattern also explains how features fail: a feature that is a node can be switched off by not adding the node (§07's actions in 1.13), and one that is an RPC exists only for providers that implement it (§04's random 3.9.1 and cross-type moves).

check: preconditions that only warn

v1.5 added top-level check blocks with at least one assert and an optional scoped data block. checkBlockSchema allows only those two block types; the decoder rejects a second data, zero asserts, and check in override files (internal/configs/checks.go). The node reuses the precondition machinery with a different severity, at internal/terraform/node_check.go:153-173: 

func (n *nodeCheckAssert) Execute(ctx EvalContext, _ walkOperation) tfdiags.Diagnostics {

	// We only want to actually execute the checks during specific
	// operations, such as plan and applies.
	if n.executeChecks {
		if status := ctx.Checks().ObjectCheckStatus(n.addr); status == checks.StatusFail || status == checks.StatusError {
			// This check is already failing, so we won't try and evaluate it.
			// This typically means there was an error in a data block within
			// the check block.
			return nil
		}

		return evalCheckRules(
			addrs.CheckAssertion,
			n.config.Asserts,
			ctx,
			n.addr,
			EvalDataForNoInstanceKey,
			tfdiags.Warning)

	}
$ terraform apply -auto-approve
Warning: Check block assertion failed … prod should run at least 2 replicas.
Warning: Unable to find remote state … No stored state was found for the given workspace in the given backend.
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.     (exit=0)

A check-scoped data source is always planned as a read with reason ResourceInstanceReadBecauseCheckNested, re-read at apply, and its errors are downgraded to warnings with tfdiags.OverrideAll (node_resource_abstract_instance.go:2049-2101) from the code. In the lab, one failing assert plus a scoped terraform_remote_state pointing at a missing file produced two warnings, "Check block assertion failed" and "Unable to find remote state", and "Apply complete!" with exit 0. The second check's assertion was never reported, because its data source had already failed measured here. A check never blocks; if a condition must stop an apply, write it as a precondition or postcondition.

terraform test and mocks

terraform test became GA in v1.6 with run blocks in .tftest.hcl files, and v1.7 added mock_provider, override_resource, override_data and override_module. At v1.17.0 a test file takes eight top-level block types plus one test block, and a run takes command, providers, expect_failures, state_key, parallel and more (internal/configs/test_file.go:1111-1187). The mock is a wrapper, not a stub. Its comment at internal/providers/mock.go:21-22 says it "wraps an instance of an actual provider so it can return the correct schema and validate the configuration accurately", and it empties only the provider's own configuration schema. CallFunction and ListResource go straight to the real provider (mock.go:410-416) from the code. So the real binary starts, provider functions run for real, and a list block in a test would make real cloud calls (Part 2 counts the process).

The lab tested an AWS module with no AWS account: a bucket with count, an ephemeral random_password feeding a write-only SSM parameter, and a cross-variable validation measured here: 

mock_provider "aws" {
  override_during = plan
  mock_resource "aws_s3_bucket" { defaults = { arn = "arn:aws:s3:::mocked" } }
}
mock_provider "random" {
  mock_ephemeral "random_password" { defaults = { result = "not-a-real-secret" } }
}
run "prod_needs_two" {
  command = plan
  variables { env = "prod"  bucket_count = 1 }
  expect_failures = [var.bucket_count]
}
$ time flock ~/terraform-ref/lab/.cpu.lock terraform test -filter=tests/unit.tftest.hcl
run "plan_uses_mocked_arn"... pass
run "prod_needs_two"... pass
run "apply_with_override"... pass
Success! 3 passed, 0 failed.
real 0m46.348s     # first, cold run; warm re-runs took 8.8 s and 10 s

The cost is the real aws binary starting for its schema; the first run paid for a cold page cache. Three edges showed. Test assert blocks cannot read ephemeral resources, mocked or not ("Ephemeral resources cannot be asserted"), so probe them through a precondition. Runs in one file share state, so a later override_resource could not change an object an earlier run had already created. And mocks refuse imports, while an identity import under override_resource fails Terraform's own "didn't return an identity" check, still on origin/main (Part 4 has the run). Some test surface is experimental-build only: run-level backend, skip_cleanup (although the v1.16 CHANGELOG advertises an enhancement to it), and terraform test cleanup, which in a release build silently runs terraform test instead.

The test runner kept growing after v1.7, one CHANGELOG line at a time: -junit-xml GA, override_during and state_key in 1.11; parallel runs in 1.12; variable blocks in test files in 1.13; prevent_destroy ignored during cleanup in 1.14; functions in mocks in 1.15; ephemeral mocks in 1.17 (CHANGELOGs v1.11.0 to v1.17.0). The practical reading of all of it: a mocked test checks your module's logic against the provider's real schema and validation, offline. It is not isolation from the provider binary, and it says nothing about whether the cloud accepts the plan.

Provider functions and cross-object validation

v1.8 (#34394) added provider::NAME::FUNC(), where NAME is the module's local provider name, and exposed every built-in under core:: as well (internal/lang/functions.go:117-136). The functions run on a separate, unconfigured provider instance that functionProvider starts and caches (internal/terraform/eval_context_builtin.go:558-600). No provider block or credentials are needed: an outputs-only lab module with none evaluated provider::aws::arn_parse, google::region_from_zone, azurerm::parse_resource_id and terraform::encode_tfvars, in 12 s warm and 45 s on its first, cold run measured here. Results are pinned: FunctionResults stores SHA-256 hashes of provider, name, arguments and result in the plan and fails if apply gets a different answer (internal/lang/function_results.go:18-31, 54-110).

The inventories are small. Cached schemas list four functions for aws 6.70.0 (arn_build, arn_parse, trim_iam_role_path, user_agent), six for google 8.8.0, two for azurerm 5.10.0 and none for random 3.9.1 measured here. Terraform's own encode_tfvars, decode_tfvars and encode_expr (v1.8, #34718) come from the built-in provider, and calling them needs terraform = { source = "terraform.io/builtin/terraform" } in required_providers; without it the console answers "Unknown provider function". Because the instance is unconfigured and per walk, each provider used for functions adds a process to the run.

v1.9 (#34955) let a variable's validation refer to other objects in the module. The mechanism is a node: nodeVariableValidation returns everything its condition references except the variable itself (node_variable_validation.go:18-43, 76-92), so terraform graph -type=plan showed var.max_size (validation) with edges to local.hard_cap (expand) and var.min_size measured here. The diagnostic lists every value involved: 

$ terraform plan
│ local.hard_cap is 10 │ var.max_size is 2 │ var.min_size is 3
max_size (2) must be between min_size (3) and 10.

Before v1.9 a rule could refer only to the variable itself; now the rule is an ordinary vertex that waits for whatever it reads, and it fails during the walk like any other node. The experiment that introduced it, variable_validation_crossref, is registered as concluded.

1.15 to 1.17

v1.15 shipped variables in module source and version, deprecated on variables and outputs (decoded with a nil context, so literal only), typed outputs and convert. The switch that makes the module sources work, const = true (4da132e63), is mentioned in no CHANGELOG from v1.5.0 to v1.17.0. v1.17 extended const values to required_providers (Part 1), added -minimal-refresh (Part 2 counts its RPCs) and mock_ephemeral, which really substitutes the value: a precondition that the password equals "not-a-real-secret" passed under the mock and failed on the real provider measured here. Under all of it, no language experiment is current: all nine constants in internal/experiments/experiment.go are registered as concluded from the code. What remains experimental is not language but machinery, and §08 covers it.

The smaller lines of the arc are the ones that change daily use. v1.8 added applyable and complete to plan JSON, so automation can tell a no-op plan from an incomplete one; v1.9 added templatestring, init -json and multi-line console input; v1.16 added terraform graph -format=mermaid, which prints flowchart LR, and console -scope=module.m, which evaluates inside a child module measured here. Deprecations move slowly: -state on plan, apply and refresh has been deprecated since v1.10 and at v1.17.0 still only warns. One lab configuration exercised the 1.15 and 1.17 lines together: a const variable in required_providers.random.version locked constraints = "3.9.1", convert("42", number) in a typed output planned n = 42, and both deprecation warnings fired. The build floor moved too: v1.17.0 is built with Go 1.26.10.
