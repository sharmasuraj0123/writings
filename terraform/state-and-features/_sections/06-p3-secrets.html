{{S}}Ephemeral values and write-only arguments

§01 showed that state stores secrets in cleartext and that sensitive is only a display flag. v1.10 and v1.11 answered with two mechanisms that keep a value out of plan and state altogether. Core enforces them with a mark on the value and with checks on what providers send back. It does not scrub. A secret stays out of the files because every path that would write it is refused, and the one path that is allowed to persist it does so on purpose.

The ephemeral mark

v1.10.0 made ephemeral resources, ephemeral input variables and ephemeral outputs GA, together with the ephemeralasnull function; the ephemeral_values experiment was concluded by #35636 from the code. An ephemeral resource is not planned or stored. It is opened, possibly renewed, and closed, in every walk that needs it. The protocol has four RPCs for that lifecycle: ValidateEphemeralResourceConfig, OpenEphemeralResource, which may return a renew_at time and opaque private bytes, RenewEphemeralResource and CloseEphemeralResource, the last two receiving only the type name and those private bytes (docs/plugin-protocol/tfplugin6.proto:821-856). Core runs a renewal goroutine per instance that re-arms a timer to each RenewAt, and a dedicated (close) vertex sends the close before the provider is killed (internal/resources/ephemeral/ephemeral_resources.go:242-278).

Opening is ephemeralResourceOpen. If the configuration is not wholly known, no RPC is made; core builds a placeholder unknown and marks it (internal/terraform/node_resource_ephemeral.go:88-107). Otherwise it calls the provider, checks the answer, and marks the whole result, at node_resource_ephemeral.go:166-189 (trimmed): 

	resultVal := resp.Result.MarkWithPaths(configMarks)

	errs := objchange.AssertPlanValid(schema.Body, cty.NullVal(schema.Body.ImpliedType()), configVal, resultVal)
	for _, err := range errs {
		diags = diags.Append(tfdiags.AttributeValue(
			tfdiags.Error,
			"Provider produced invalid ephemeral resource instance",
	…
	// We are going to wholesale mark the entire resource as ephemeral. This
	// simplifies the model as any references to ephemeral resources can be
	// considered as such. Any input values that don't need to be ephemeral can
	// be referenced directly.
	resultVal = resultVal.Mark(marks.Ephemeral)

From there the mark travels with the value through every operator, the same way sensitive does (Part 1), and validation decides where it may land. One lab apply with an ephemeral "random_password" made two OpenEphemeralResource and two CloseEphemeralResource calls, one pair in the plan walk and one in the apply walk, and the CLI printed "Opening..." and "Closing complete" in both phases measured here. A value that is opened twice can differ between plan and apply; that is the point, and it is why an ephemeral value cannot be pinned in a saved plan.

The order inside one walk is visible in a trace of a plan with the same resource: the provider is configured, then ValidateEphemeralResourceConfig and OpenEphemeralResource run, and the (close) node sends CloseEphemeralResource before the provider process is stopped measured here. The unknown-config branch matters in practice. If an ephemeral resource's arguments depend on something that is only known after apply, nothing is opened at plan time, every consumer sees an unknown, and the real value exists only during the apply walk reconstruction. Mocks follow the same lifecycle since v1.17: Mock.OpenEphemeralResource fills the result from mock_ephemeral defaults, and renew and close are no-ops (internal/providers/mock.go:371-408). Before v1.17 a mocked provider failed any ephemeral resource with "No ephemeral resource types in mock providers".

Where the mark may go

Validation refuses the mark in any resource argument that is not write-only. The check walks up the attribute path, so a value nested inside a write-only attribute passes, and anything else fails, at internal/terraform/node_resource_validate.go:1012-1019: 

		} else if !attr.WriteOnly {
			diags = diags.Append(tfdiags.AttributeValue(
				tfdiags.Error,
				"Invalid use of ephemeral value",
				fmt.Sprintf("Ephemeral values are not valid for %q, because it is not a write-only attribute and must be persisted to state.", strings.TrimPrefix(format.CtyPath(path), ".")),
				path,
			))
		}

The other allowed places are provider configuration, input variables declared ephemeral = true, and ephemeral outputs of child modules. A root module may not declare an ephemeral output: "Ephemeral outputs are not allowed in context of a root module", unless AllowRootEphemeralOutputs is set, which only the Stacks and test runtimes do (internal/terraform/node_output.go:423-431) from the code. The lab's guard-rail directory hit both errors: terraform_data.input = ephemeral… failed "Invalid use of ephemeral value", and a root output { ephemeral = true } failed "Ephemeral output not allowed" measured here. terraform.applying is itself an ephemeral boolean, true only in the apply walk, so a root output derived from it fails unless wrapped in ephemeralasnull (internal/terraform/evaluate_data.go:128-134). And a test assert cannot read an ephemeral resource at all (§05).

Write-only: sent every time, never returned

v1.11.0 (#36031) added write-only attributes. They are a per-attribute flag in the provider schema, configschema.Attribute.WriteOnly, shown as "write_only": true in providers schema -json (field 10 in tfplugin5's schema message, 11 in tfplugin6's). The cached schemas count 37 write-only attributes in aws 6.70.0, 31 in google 8.8.0, 8 in azurerm 5.10.0 and none in random 3.9.1, for example aws_db_instance.password_wo, google_sql_user.password_wo and azurerm_key_vault_secret.value_wo measured here.

"Write-only" does not mean "never sent". Core sends the configured value to the provider in every PlanResourceChange and ApplyResourceChange config, because the provider needs it to do its job. What core demands is that the value never comes back. After planning it runs, at internal/terraform/node_resource_abstract_instance.go:1081-1093: 

		// Providers are supposed to return null values for all write-only attributes
		writeOnlyDiags := ephemeral.ValidateWriteOnlyAttributes(
			"Provider produced invalid plan",
			func(path cty.Path) string {
				return fmt.Sprintf(
					"Provider %q returned a value for the write-only attribute \"%s%s\" during planning. Write-only attributes cannot be read back from the provider. This is a bug in the provider, which should be reported in the provider's own issue tracker.",
					n.ResolvedProvider, n.Addr, tfdiags.FormatCtyPath(path),
				)
			},
			plannedNewVal,
			schema.Body,
		)
		diags = diags.Append(writeOnlyDiags)

The same check runs at refresh, apply and import ("Provider produced invalid object"). Core nulls write-only values itself, with ephemeral.StripWriteOnlyAttributes, keeping their marks, only where it fabricates an object: test overrides, mock providers and Stacks stubs (internal/lang/ephemeral/strip.go:14-39) from the code. A provider built on the plugin framework also nulls every write-only attribute in its planned state before returning it (plugin-framework internal/fwserver/server_planresourcechange.go:179-189). HashiCorp's documentation describes the outcome, values kept out of plan files and state; the code shows how it is reached. So the guarantee is two-sided and checked, not scrubbed: a provider that echoed the password would fail the run rather than leak it into a file.

With fake AWS credentials and the network behind a dead proxy, an aws_db_instance with password_wo = var.db_password planned measured here: 

$ terraform plan -var db_password=Sup3rS3cret-XYZ -out=p.bin
  + password_wo                           = (write-only attribute)
  + password_wo_version                   = 1
$ unzip -p p.bin | grep -a -c Sup3rS3cret-XYZ          → 0
$ terraform show -json p.bin | grep -c Sup3rS3cret-XYZ → 0
$ terraform apply p.bin
Error: No value for required variable … The ephemeral input variable "db_password" was set during the plan phase, and so must also be set during the apply phase.

The last line is the ephemeral-variable rule. A plan records only the names of ephemeral variables that were set, in Plan.ApplyTimeVariables; the comment says their values "can change between plan and apply, their "nullness" may not" (internal/plans/plan.go:58-67). Applying a saved plan therefore needs the secret supplied again, and fails before any provider call without it. Because the stored value is null, the provider cannot tell when a write-only argument changed; the convention is a companion *_wo_version argument you increment to rotate, and its type is the provider's choice, a number in one provider and a string in another. Write-only does not imply sensitive either: azurerm's administrator_password_wo is not marked sensitive. Part 4 follows a canary password through six write-only arguments on three clouds and finds it in no file of the saved plan.

The deliberate exception

v1.16.0 (#38298) gave terraform_data a store block. Its input is write-only and accepts ephemeral values; it is copied into a computed output, or into sensitive_output when sensitive = true, and that copy is persisted; version gates refresh and replace forces replacement (internal/builtin/providers/terraform/resource_data.go:32-56, 163-225) from the code. Storing ephemeral.random_password.db.result left the state with "input": null and "sensitive_output": { "value": "hXfxVb2yzX1xm5B9", … } measured here. It is a way to make a generated secret durable across runs, not a way to hide it: the value is back in the plaintext document of §01. Ephemeral resource types are still few: aws 6.70.0 has 11, google 8.8.0 six, azurerm 5.10.0 two and random 3.9.1 two (random_bytes, random_password) measured here.
