01One document per workspace

Terraform is a compiler whose intermediate representation is a dependency graph and whose back end is somebody else's process. Parts 1 and 2 followed one plan from bytes to provider calls. This part covers what lasts after the run. Terraform's record of what exists is one JSON document per workspace. It is rewritten whole, it stores secrets in plaintext, and two writers are kept apart only by an advisory lock that each backend builds from its own storage. No write does a compare-and-swap. The second half of this part follows the features added from v1.5 to v1.17. Almost every one is a small schema, a graph node and usually one new RPC, and the newest ones are the least finished: gated behind experiments, sold through HCP, or run in a separate process.

The manager contract

Every place Terraform keeps state is reached through a statemgr.Full. That is three interfaces in one: Transient (an in-memory snapshot, State and WriteState), Persistent (RefreshState, PersistState, GetRootOutputValues) and Locker (Lock, Unlock) (internal/states/statemgr/statemgr.go:12-29; persistent.go:25-29) from the code. A transient snapshot lives only inside the process; a persistent one is shared with other Terraform processes. The split lets a backend take a write after every resource but upload less often (transient.go:11-14; persistent.go:19-21). PersistState even takes the provider schemas as an argument, because HCP Terraform uploads a schema-aware JSON rendering beside the raw snapshot (persistent.go:83-88).

The contract says what a persister owes other processes. persistent.go:77-81 states that a Persister "must detect updates made by other processes that may be running concurrently and avoid destroying those changes". The next interface relaxes it at once: a manager that also implements Locker need only be concurrency-safe "within a single Terraform process", "under the assumption that the locking mechanism effectively prevents multiple Terraform processes from reading and writing state concurrently" (locker.go:28-34). The lock is also advisory by contract: "A Locker is not required to prevent non-cooperating processes from concurrently modifying the state" (locker.go:41-47) from the code. So the guarantee is a lock that cooperating Terraform processes respect. §02 shows what that lock is on each backend.

The v4 file

The document itself is version 4 JSON with seven top-level keys: version (hard-coded 4), terraform_version, serial, lineage, outputs, resources and check_results (internal/states/statefile/version4.go:668-675). Resources and their instances are sorted with sort.Stable by module, mode, type and name, so two equivalent states serialize identically and diffs stay small (version4.go:682-684). Each instance records its schema_version, attributes, sensitive_attributes, identity fields, private and dependencies; the struct also declares an each field that the v4 writer never sets, and measured states have none (version4.go:694-722) from the code. The dependencies list matters later: destroy order is computed from it, not from the current configuration (Part 2).

Sensitivity is metadata, not encryption. A lab apply with a sensitive variable, a random_password and a sensitive output left all three in cleartext. The output pw sits in the file as "value": "xdcJMevxyoflqcL6" next to "sensitive": true, and the variable's value sits inside terraform_data.app's input. sensitive_attributes is only a list of paths, here [input, secret]. The provider-computed copy of the same value in output.secret carries no path at all measured here. Why the mark does not follow that copy is an open question. The practical rule: anyone who can read the state blob can read every secret in it, so restrict reads of the state storage itself. HashiCorp's documentation says to keep secrets out of state with ephemeral values and write-only arguments (§06).

Lineage, serial, and where they are checked

Two fields identify a snapshot. lineage is a random UUID minted once, when state is first recorded at a location, and kept forever; serial counts snapshots within that lineage, and NewStateFile starts at serial 0 (statemgr/lineage.go:12-23; helper.go:16-24). SnapshotMeta.Compare sorts a pair into five relations: older, newer, equal, unrelated (different lineage) and legacy (empty lineage) (migrate.go:137-175) from the code. The gate that uses them is CheckValidImport, at internal/states/statemgr/migrate.go:195-210: 

	rel := new.Compare(existing)
	switch rel {
	case SnapshotNewer:
		return nil // a newer snapshot is fine
	case SnapshotLegacy:
		return nil // anything goes for a legacy state
	case SnapshotUnrelated:
		return fmt.Errorf("cannot import state with lineage %q over unrelated state with lineage %q", new.Lineage, existing.Lineage)
	case SnapshotEqual:
		if statefile.StatesMarshalEqual(newFile.State, existingFile.State) {
			// If lineage, serial, and state all match then this is fine.
			return nil
		}
		return fmt.Errorf("cannot overwrite existing state with serial %d with a different state that has the same serial", new.Serial)
	case SnapshotOlder:
		return fmt.Errorf("cannot import state with serial %d over newer state with serial %d", new.Serial, existing.Serial)

This gate guards one door: a non-forced terraform state push. Both the filesystem manager and remote.State run it only inside WriteStateForMigration when force is false (filesystem.go:420; internal/states/remote/state.go:102). Backend migration always passes true: statemgr.Migrate calls WriteStateForMigration(s, true) when both sides support it, and otherwise a plain WriteState that loses lineage and serial altogether (migrate.go:58-71). During init -migrate-state lineage is used only to skip copying a state that is already identical (internal/command/meta_backend_migrate.go:352-361); the overwrite is gated by a confirmation prompt, and -force-copy skips the prompt from the code. The other door is the saved plan: apply refuses "Saved plan is stale" when a new snapshot was persisted after the plan was written (Part 2). Everything else, including every write during an ordinary apply, goes through without a comparison.

The lab's state push run shows the gate at work on a local state at serial 6 with lineage 211cc19e-… measured here:

The pushed serial 20 landed as 21 because state push writes and persists again after the import, and a changed write bumps the counter (internal/command/state_push.go:139-158). The forced push stored serial 99 only because its content matched the current state; a verifier's re-run with different content got 100. A forced push replaced the lineage outright. The practical consequence is short: -force and -migrate-state are the two commands that can overwrite a teammate's newer state, and nothing but a prompt (or nothing, with -force-copy) stands in the way.

The local manager and the remote one count differently. 02Locks, per backend

A state lock is whatever atomic primitive the backend's storage happens to offer: a POSIX record lock, a conditional object write, a blob lease, a database advisory lock. Core sees only a Lock method that returns an ID or an error. Two defaults decide how that works in practice. -lock-timeout is zero, so a held lock fails your command at once. And the S3 backend, configured with neither of its two lock options, takes no lock at all and says nothing about it.

One attempt by default

A lock request carries a LockInfo with seven fields, ID, Operation, Info, Who, Version, Created and Path; its ID comes from math/rand in UUID shape, with a comment that it "doesn't need to be cryptographically secure" (internal/states/statemgr/locker.go:118-172) from the code. The retry loop is LockWithContext, at locker.go:75-88 and 101-111 (the guard for an incomplete LockError in between is left out): 

func LockWithContext(ctx context.Context, s Locker, info *LockInfo) (string, error) {
	delay := time.Second
	maxDelay := 16 * time.Second
	for {
		id, err := s.Lock(info)
		if err == nil {
			return id, nil
		}

		le, ok := err.(*LockError)
		if !ok {
			// not a lock error, so we can't retry
			return "", err
		}
	…
		select {
		case <-ctx.Done():
			// return the last lock error with the info
			return "", err
		case <-time.After(delay):
			if delay < maxDelay {
				delay *= 2
			}
		}
	}
}

Only a *LockError whose Info has an ID is retried; anything else fails immediately. The wait starts at one second and doubles to a 16-second cap. Every state-touching command defaults -lock-timeout to 0s: plan, apply, refresh, init, state mv, rm, push and replace-provider (internal/command/arguments/extended.go:270-271, init.go:110-111 and the state command parsers) from the code. With a zero timeout the context is already done when the first LockError comes back, so there is exactly one attempt (internal/command/clistate/state.go:109-138). The CLI prints "Acquiring state lock…" only if the lock takes longer than its 400 ms LockThreshold (clistate/state.go:23).

Two processes against one local state show all of it. The lab ran a nine-second apply in the background, then tried everything else against the held lock measured here:

What each backend builds

local. A non-blocking POSIX fcntl F_SETLK on terraform.tfstate itself (LockFileEx on Windows), plus a 0600 sidecar .terraform.tfstate.lock.info holding the LockInfo (internal/states/statemgr/filesystem_lock_unix.go:15-41; filesystem.go:487-529). The kernel lock dies with the process that holds it, and force-unlock refuses local state either way: without -force it says the state "cannot be unlocked by another process", and with it the new process finds it holds nothing, "LocalState not locked" (internal/command/unlock.go:78-110; filesystem.go:345-351) from the code.

s3. Two mechanisms, both opt-in. use_lockfile writes the LockInfo JSON to <key>.tflock with a conditional PutObject carrying If-None-Match: *; on a 412 Terraform reads the existing .tflock to name the holder (s3/client.go:346-404). dynamodb_table does a PutItem with attribute_not_exists(LockID), where LockID is <bucket>/<key>, and keeps a -md5 digest item that drives a consistency loop retrying a mismatched Get every 2 s for up to 10 s (s3/client.go:39, 57-125, 406-436). The matrix is at internal/backend/remote-state/s3/client.go:285-288 and 327-340: 

	// no file, no dynamodb
	if !c.useLockFile && c.ddbTable == "" {
		return "", nil

	// double locking: dynamodb + file (design decision: both must succeed)

	if err := c.lockWithFile(ctx, info, log); err != nil {
		return "", err
	}

	if err := c.lockWithDynamoDB(ctx, info); err != nil {
		// Release the file lock if attempting to acquire the DynamoDB lock fails.
		if unlockErr := c.unlockWithFile(ctx, info.ID, &statemgr.LockError{}, log); unlockErr != nil {
			return "", fmt.Errorf("failed to clean up file lock after DynamoDB lock error: %v; original error: %w", unlockErr, err)
		}

		return "", err

The first three lines are the finding: with neither option set, Lock returns an empty ID and no error, so every command proceeds as if it held the lock from the code. Nothing warns. Native locking arrived in v1.10.0 alongside DynamoDB (code first committed on 1 September 2024, 8be88f76e) and was declared GA in v1.11.0 (#36338), which deprecated the DynamoDB arguments. The deprecation warning comes from PrepareConfig, so it appears at init and not at validate, which printed "Success!" for a dynamodb_table backend measured here (not re-run by a verifier). If you run S3 state, set use_lockfile = true. One open question sits under that advice: whether S3-compatible stores such as MinIO, R2 or Ceph honour If-None-Match; if one does not, use_lockfile may silently not lock there. Unlock in both modes reads the lock, compares the ID, then deletes, and a TODO notes that the DynamoDB comparison is not atomic (s3/client.go:508-589).

gcs and azurerm. GCS creates <prefix>/<workspace>.tflock with a DoesNotExist condition and uses the object's generation number as the lock ID; unlock is a delete with GenerationMatch (gcs/client.go:96-139). azurerm takes an infinite blob lease (LeaseDuration: -1) on the state blob itself, proposing the LockInfo ID as the lease ID, and stores the info base64-encoded in blob metadata terraformlockid (azure/client.go:25-27, 143-270) from the code.

http. Locking happens only if lock_address is set, using configurable LOCK/UNLOCK methods where 409 or 423 means "locked", and state writes carry the lock ID as ?ID=… (http/client.go:93-123, 205-243). Unlock(id) never sends id: it replays this process's own lock JSON (http/client.go:126-143). A fresh force-unlock process has no lock JSON, so the lab server received UNLOCK body=b''; a bogus ID "succeeded"; and a force-unlock during a live apply let a second plan lock and unlock while the apply was still running, after which the apply posted with its stale ID measured here. Those runs were not re-run by a verifier; the code half is confirmed. HashiCorp's locking page calls the lock ID "a nonce" that makes unlocks target the right lock; for HTTP the client does not enforce that, and the server must.

The rest. pg uses pg_try_advisory_lock; kubernetes a coordination.k8s.io/v1 Lease whose holder identity is the lock ID; oci a conditional PutObject with IfNoneMatch: "*"; oss a TableStore row (internal/backend/remote-state/{pg,kubernetes,oci,oss}). Backends are compiled in, not plugins: v1.17 ships 13 names plus the internal cloud (internal/backend/init/init.go:33-86). oci is the newest. Its CHANGELOG line in v1.12.0 cites #34465, while the commit that added it is #36872 (804e97021), and git tag --contains first lists v1.13.0 (CHANGELOG mistake, code, verified). A generic remote.State whose client has no Lock at all also "succeeds" silently (internal/states/remote/state.go:238-250).

HCP Terraform and state_store. The cloud backend's lock is a workspace lock ("Locked by Terraform"), and its force-unlock ID is literally <org>/<workspace> (internal/cloud/state.go:334-361, 452-520). Experimental pluggable state storage hands state to a provider through eight tfplugin6 RPCs, including LockState and UnlockState, with chunks negotiated at 8 MiB and capped at 128 MiB (docs/plugin-protocol/tfplugin6.proto:403-421; internal/backend/pluggable/chunks/chunks.go:6-18). LockState carries only type, state ID and operation, and the gRPC client returns a plain error, so -lock-timeout would never retry it (internal/states/remote/remote_grpc.go:118-130). That consequence is inferred from code; testing it needs an experimental build. The release binary rejects the block outright: "Blocks of type "state_store" are not expected here." measured here

03Workspaces, remote state and HCP Terraform

Three features look like boundaries and are not. A CLI workspace is a second key in the same backend, reached with the same credentials. terraform_remote_state reads another configuration's whole state and hands its outputs over with the sensitive flag removed. And HCP Terraform, the one place that does isolate workspaces, does it by turning the CLI into a client of a run service.

Workspaces are key mappings

The selected workspace comes from TF_WORKSPACE if set, else from .terraform/environment, else default; a name must be non-empty and equal its own url.PathEscape (internal/command/meta.go:765-835) from the code. What a name maps to is up to the backend. The local backend keeps default at terraform.tfstate and every other workspace in terraform.tfstate.d/<name>/terraform.tfstate; its Workspaces() is default plus the sorted subdirectories, and DeleteWorkspace is an os.RemoveAll that refuses only default (internal/backend/local/backend.go:29-32, 199-258). S3 puts other workspaces at <workspace_key_prefix>/<name>/<key> with prefix env:; GCS uses a flat <prefix>/<name>.tfstate; azurerm appends env:<name> to the key; HTTP has no workspaces at all and answers workspace new dev with "workspaces not supported". Creating an S3 workspace takes a lock, re-reads to avoid a race and writes an empty state so the new name is listable (s3/backend_state.go:210-253).

The local backend's walk-through in the lab shows the shape measured here: 

$ terraform apply                    → ws = "ws=default"
$ terraform workspace new staging    → Created and switched to workspace "staging"!
$ terraform apply                    → ws = "ws=staging"
$ terraform workspace new "bad/name" → The workspace name "bad/name" is not allowed. The name must contain only URL safe …
$ TF_WORKSPACE=nope terraform output → Warning: No outputs found      (and terraform.tfstate.d/nope/ now exists)
$ terraform workspace select default; terraform workspace delete staging → Error: Workspace is not empty … - terraform_data.env
$ terraform workspace delete -force staging → Deleted workspace "staging"! WARNING: "staging" was non-empty.

Two lines bite. Asking for a workspace's state manager creates its directory, so a mistyped TF_WORKSPACE in a pipeline does not fail; it reads an empty state and leaves a new workspace behind that workspace list then shows (local/backend.go:260-289, 489-509). A plan in that workspace would propose creating everything reconstruction. And delete -force deletes the state of a non-empty workspace, so the real objects keep running with no record; it also releases the lock before deleting, because some backends cannot delete a locked object, and a TODO notes the gap (internal/command/workspace_delete.go:110-175). On origin/main the closing WARNING becomes a diagnostic, "Workspace %q was non-empty". HashiCorp's CLI documentation says the same thing in its own words: CLI workspaces are not an isolation mechanism, because they share one backend and one set of credentials, while HCP workspaces behave like separate working directories. If two environments need different access, give them different backends or different HCP workspaces.

The name rules have tightened release by release. v1.13 rejected an empty name in workspace new and delete (#37267, #37275); since v1.16 an invalid name in .terraform/environment is an error for every backend command (#38594), and workspace list -json (#38397) marks the current one (meta.go:808-813; v1.16.0 CHANGELOG) from the code. Inside configuration the name is terraform.workspace, which is how the lab's input = "ws=${terraform.workspace}" printed a different value per workspace. That interpolation is the usual way one configuration serves several environments, and it is also the reason a typo in the name silently changes what the configuration means.

Remote state drops sensitive

data "terraform_remote_state" lives in the built-in terraform provider. It instantiates a full backend inside the consumer's process, refreshes the producer's entire snapshot and then exposes only the root outputs (internal/builtin/providers/terraform/data_source_state.go:103-179). Two consequences follow. The consumer needs read access to the whole producer state, which (§01) holds every secret in cleartext. And the copy loses its marks, at data_source_state.go:143-146 and 172-176:

		diags = diags.Append(err)
		return cty.NilVal, diags

A consumer that read it through a local terraform_remote_state and re-exported it as output "token_is" printed token_is = "s3cr3t", with no error about a sensitive value reaching a non-sensitive output measured here. HCP Terraform turns the CLI into a client

The cloud block takes hostname (default app.terraform.io), organization, token and workspaces { name | tags | project }, with environment fallbacks such as TF_CLOUD_ORGANIZATION and TF_WORKSPACE (internal/cloud/backend.go:43, 145-180, 496-600). The package arrived in v1.1.0 as the successor to the remote backend, which is still registered in v1.17 from the code. With no token, init stops at "Initializing HCP Terraform..." with "Error: Required token could not be found" measured here; that is as far as this machine could go.

Unless the workspace uses local execution, plan and apply no longer run on your machine. The CLI creates a configuration version, uploads the directory (honouring .terraformignore), creates a run and streams its logs (internal/cloud/backend.go:918-935; backend_common.go:556-618). A plan without -out is a speculative run; plan -out makes a saved-plan run; -refresh-only, -destroy and -minimal-refresh map to run options (backend_plan.go:126-175). The CLI renders a run in a fixed order: pre-plan tasks, plan, post-plan tasks, cost estimate, Sentinel, then Terraform Policy evaluations (backend_plan.go:280-345). HCP's run-states page puts the OPA check before cost estimation and Sentinel after it, so the docs and the CLI's rendering disagree. The code half is verified; the web half was not re-checked.

The selector has two modes. With workspaces { name = … }, TF_WORKSPACE may only repeat that name; with tags, which takes a string list or, preferred since v1.10 (#35937), a key-value map, TF_WORKSPACE picks among the matching workspaces (internal/cloud/backend.go:538-600). Around the run, HCP adds things the CLI cannot see or test: run tasks at four stages with advisory or mandatory enforcement, a stored state version per run with rollback from the UI, and health assessments for drift on paid tiers. Those come from HashiCorp's documentation, fetched on 23 October 2026, and were not exercised here.

Persisting to HCP uploads three things: the raw state, a schema-aware JSON rendering when schemas are available, and the JSON outputs, with lineage, serial, an MD5 and the run ID (internal/cloud/state.go:164-331). That is why PersistState takes schemas (§01), and why state push and state mv load provider schemas first in cloud mode. Intermediate snapshots are off unless the API returns an X-Terraform-Snapshot-Interval header; final snapshots always upload. One more choice is deliberate. When the last state upload failed, the cloud manager does not unlock, at internal/cloud/state.go:462-466: "If so, we will not unlock the workspace to prevent any changes from being applied until the correct state is uploaded." A workspace stuck in "Locked by Terraform" after a network failure may be guarding a state that never arrived, and force-unlocking it with <org>/<workspace> should come after uploading the right state reconstruction.

04Refactoring in configuration

terraform state mv, rm and import edit the record directly, one command at a time, with nothing to review. Since v1.1 Terraform has been moving each of those edits into a block in the configuration: moved, then import in v1.5, removed in v1.7. The blocks run inside plan, show up in the plan like any change, and reach stored state only when that plan is applied. That is the whole argument for them.

Surgery, and what it does not do

The state subcommands only edit records. In the lab, state mv 'random_pet.a["x"]' 'random_pet.a["z"]' on a for_each resource succeeded and bumped serial from 4 to 5; the next plan then proposed to create a["x"] and destroy a["z"] "(because key ["z"] is not in for_each map)" measured here. 05A schema, a node, an RPC: 1.5 to 1.17

Thirteen minor releases run from v1.5.0 (12 June 2023) to v1.17.0 (21 October 2026). Almost every feature they added follows one recipe: a small hcl.BodySchema and decoder in internal/configs, a graph node or a change in node behaviour in internal/terraform, and usually one new RPC in the plugin protocol. Each one is small in code and large in surface, because the language, the CLI, the test runner and the protocol all have to agree on it. This section takes the features that are not about state or secrets; §06 to §08 take the rest.

The recipe follows from Part 1's first design choice. HCL parses without meaning and Terraform decodes each block against a schema of its own (Part 1), so a new block type costs a schema and a decoder, not a grammar change. The engine runs whatever nodes the transformers add (Part 2), so new behaviour is a node. And anything the provider must do is an RPC. Figure 18 places the features on the release line; Figure 19, in §07, lists the schema, node and RPC behind each one reconstruction.

Three examples show the shape. check is checkBlockSchema plus a nodeCheckAssert and needs no RPC at all. Provider functions are a namespace in lang.Scope, an unconfigured provider instance, and the GetFunctions and CallFunction RPCs. Cross-type moved is a field on an existing block, a step in ApplyMoves, and MoveResourceState. The pattern also explains how features fail: a feature that is a node can be switched off by not adding the node (§07's actions in 1.13), and one that is an RPC exists only for providers that implement it (§04's random 3.9.1 and cross-type moves).

06Ephemeral values and write-only arguments

§01 showed that state stores secrets in cleartext and that sensitive is only a display flag. v1.10 and v1.11 answered with two mechanisms that keep a value out of plan and state altogether. Core enforces them with a mark on the value and with checks on what providers send back. It does not scrub. A secret stays out of the files because every path that would write it is refused, and the one path that is allowed to persist it does so on purpose.

The ephemeral mark

v1.10.0 made ephemeral resources, ephemeral input variables and ephemeral outputs GA, together with the ephemeralasnull function; the ephemeral_values experiment was concluded by #35636 from the code. An ephemeral resource is not planned or stored. It is opened, possibly renewed, and closed, in every walk that needs it. The protocol has four RPCs for that lifecycle: ValidateEphemeralResourceConfig, OpenEphemeralResource, which may return a renew_at time and opaque private bytes, RenewEphemeralResource and CloseEphemeralResource, the last two receiving only the type name and those private bytes (docs/plugin-protocol/tfplugin6.proto:821-856). Core runs a renewal goroutine per instance that re-arms a timer to each RenewAt, and a dedicated (close) vertex sends the close before the provider is killed (internal/resources/ephemeral/ephemeral_resources.go:242-278).

Opening is ephemeralResourceOpen. If the configuration is not wholly known, no RPC is made; core builds a placeholder unknown and marks it (internal/terraform/node_resource_ephemeral.go:88-107). Otherwise it calls the provider, checks the answer, and marks the whole result, at node_resource_ephemeral.go:166-189 (trimmed):

			tfdiags.Error,
			"Provider produced invalid ephemeral resource instance",
	…
	// We are going to wholesale mark the entire resource as ephemeral. This
	// simplifies the model as any references to ephemeral resources can be
	// considered as such. Any input values that don't need to be ephemeral can
	// be referenced directly.

From there the mark travels with the value through every operator, the same way sensitive does (Part 1), and validation decides where it may land. One lab apply with an ephemeral "random_password" made two OpenEphemeralResource and two CloseEphemeralResource calls, one pair in the plan walk and one in the apply walk, and the CLI printed "Opening..." and "Closing complete" in both phases measured here. A value that is opened twice can differ between plan and apply; that is the point, and it is why an ephemeral value cannot be pinned in a saved plan.

The order inside one walk is visible in a trace of a plan with the same resource: the provider is configured, then ValidateEphemeralResourceConfig and OpenEphemeralResource run, and the (close) node sends CloseEphemeralResource before the provider process is stopped measured here. The unknown-config branch matters in practice. If an ephemeral resource's arguments depend on something that is only known after apply, nothing is opened at plan time, every consumer sees an unknown, and the real value exists only during the apply walk reconstruction. Mocks follow the same lifecycle since v1.17: Mock.OpenEphemeralResource fills the result from mock_ephemeral defaults, and renew and close are no-ops (internal/providers/mock.go:371-408). Before v1.17 a mocked provider failed any ephemeral resource with "No ephemeral resource types in mock providers".

A plan records only the names of ephemeral variables that were set, in Plan.ApplyTimeVariables; the comment says their values "can change between plan and apply, their "nullness" may not" (internal/plans/plan.go:58-67). Applying a saved plan therefore needs the secret supplied again, and fails before any provider call without it. Because the stored value is null, the provider cannot tell when a write-only argument changed; the convention is a companion *_wo_version argument you increment to rotate, and its type is the provider's choice, a number in one provider and a string in another. Write-only does not imply sensitive either: azurerm's administrator_password_wo is not marked sensitive. Part 4 follows a canary password through six write-only arguments on three clouds and finds it in no file of the saved plan.

The deliberate exception

v1.16.0 (#38298) gave terraform_data a store block. Its input is write-only and accepts ephemeral values; it is copied into a computed output, or into sensitive_output when sensitive = true, and that copy is persisted; version gates refresh and replace forces replacement (internal/builtin/providers/terraform/resource_data.go:32-56, 163-225) from the code. Storing ephemeral.random_password.db.result left the state with "input": null and "sensitive_output": { "value": "hXfxVb2yzX1xm5B9", … } measured here. It is a way to make a generated secret durable across runs, not a way to hide it: the value is back in the plaintext document of §01. Ephemeral resource types are still few: aws 6.70.0 has 11, google 8.8.0 six, azurerm 5.10.0 two and random 3.9.1 two (random_bytes, random_password) measured here.

07List resources and actions

v1.14 shipped two features that stretch the model. List resources let Terraform ask a cloud what exists and write configuration to adopt it. Actions let a configuration run an imperative operation, such as invoking a Lambda function, when a resource changes or on demand. Both were in the v1.13 code behind the experiments gate, both are GA in the v1.17 CLI, and both are built from the same recipe as everything else: a schema, a node, and an RPC. Their edges are rougher than the rest, and one of them is an internal error that the CLI lets users reach.

Query files and ListResource

List resources live in their own file type. A .tfquery.hcl file may contain only list blocks (two labels), provider, locals and variable (internal/configs/query_file.go:219-237), and it is loaded only by terraform query: plan and validate ignore it, and validate -query (v1.14, #37671) checks it offline measured here. The loader's default: branch, "This block type is not valid within a query file", is unreachable, because the schema has already rejected the block with HCL's generic "Unsupported block type" (query_file.go:83-91). A list block decodes to a configs.Resource with Mode: addrs.ListResourceMode; it takes count, for_each, a mandatory provider, include_resource and limit, with the filter in one nested config block (query_file.go:97-125, 153-214) from the code.

terraform query is a plan operation with Query = true (internal/command/query.go:84, 123-126). Per list instance, listResourceExecute requires a wholly known configuration, calls ValidateListResourceConfig, then the streaming ListResource RPC, at internal/terraform/node_resource_plan_instance_query.go:99-103 and 126-133: 

	// if we are generating config, we implicitly set include_resource to true
	if n.generateConfigPath != "" {
		includeRscCty = cty.True
		includeRsc = true
	}
	…
	// If we get down here then our configuration is complete and we're ready
	// to actually call the provider to list the data.
	resp := provider.ListResource(providers.ListResourceRequest{
		TypeName:              n.Config.Type,
		Config:                unmarkedBlockVal,
		Limit:                 limit,
		IncludeResourceObject: includeRsc,
	})

Core stops reading the stream at limit and requires a resource identity on every non-warning event (internal/plugin6/grpc_provider.go:1360-1455). That is what -generate-config-out uses: each result becomes an import { identity = … } block plus a resource block (node_resource_plan_instance.go:1114-1152), with the resource body written by the provider's GenerateResourceConfig where it has one. So bulk adoption stands on three releases: identity import (1.12), provider-written config (1.14), and list resources (1.14). Figure 19 draws that chain under the table of features from the code.

The chain has a hard limit: it needs a real cloud. With fake AWS credentials, terraform query -json emitted list_start and then failed inside ListResource with an EC2 DescribeInstances "401 … AuthFailure"; no file was written measured here (not re-run by a verifier; the request is listed in §09). Only validate -query works offline. The cached schemas count 259 list resource types in aws 6.70.0, 153 in google 8.8.0, 122 in azurerm 5.10.0 and none in random. HashiConf 2025 launched HCP Terraform's "Terraform search" as a public beta for AWS and Azure; whether plans.QueryInstance results are ever persisted is open, because query has no -out.

Actions

action "TYPE" "NAME" takes count, for_each, provider and at most one config block, decoded to configs.Action and evaluated against the provider's action schema (internal/configs/action.go:27-41, 224-318). A resource triggers it from lifecycle { action_trigger { … } }, which requires events and actions and takes an optional condition and on_failure; events are bare keywords (action.go:115-222). v1.14.0 accepted only before and after create and update; destroy events and on_failure arrived in v1.16 (#38668, #38722). on_failure defaults to halt, because ActionOnFailureHalt is the enum's zero value (action.go:56-72) from the code. The cached schemas count 12 action types in aws 6.70.0, for example aws_lambda_invoke, eight in azurerm and none in google measured here.

At plan time each triggered invocation costs one ValidateActionConfig and one PlanAction, and the plan lists it under action_invocations. InvokeAction runs only at apply, with the planned config unmarked, and streams Progress and Completed events into the UI hooks; a response with no event stream is an error (internal/terraform/action_trigger_instance_apply.go:114-166). caller refers to the triggering resource. It is a core addrs.SelfType value (internal/addrs/self.go:10-13) and works in any configuration; the lab's offline plan resolved function_name through it. The v1.16 CHANGELOG files it under "stacks:", which is misleading.

What happens on failure depends on the event. invokeDestroyActions (first block) knows only continue or error, and forces continue during a full destroy walk; invokeActions (second block) has the three-way switch, at internal/terraform/node_resource_abstract_instance.go:3380-3387 and 3423-3438: 

		invokeDiags := trigger.Invoke(ctx, n.Addr.Resource, cty.DynamicVal, true)

		// a full destroy walk must never be blocked
		onFailureContinue := op == walkDestroy || trigger.ActionInvocation.ActionTrigger.OnFailure() == configs.ActionOnFailureContinue
	…
		invokeDiags := trigger.Invoke(ctx, n.Addr.Resource, callerVal, false)
		if invokeDiags.HasErrors() {
			switch onFailure {
			case configs.ActionOnFailureHalt:
				return false, diags.Append(invokeDiags)
			case configs.ActionOnFailureTaint:
				// We can only taint a newly created resource, because that's
				// the only action which can be re-done from scratch. Recording
				// other action events which need to be reinvoked will require
				// new data to be saved in the state.
				return event == configs.AfterCreate, diags.Append(invokeDiags)
			case configs.ActionOnFailureContinue:
				// The resource still needs to use the usual failure mechanisms
				// in the graph walk, so in order to continue all diagnostics
				// must only be warnings.
				diags = diags.Append(tfdiags.OverrideAll(invokeDiags, tfdiags.Warning, nil))

So taint taints only on after_create, and never for a destroy event. The lab ran one action end to end measured here. The -invoke dead end

-invoke=action.X.Y runs one action ad hoc. The CLI accepts one only ("Only one action can be invoked at a time.") and quietly changes the plan mode, at internal/command/arguments/extended.go:232-237: 

	default:
		if len(o.ActionTargets) > 0 {
			o.PlanMode = plans.RefreshOnlyMode
		} else {
			o.PlanMode = plans.NormalMode
		}

A normal plan with -invoke becomes refresh-only, which is why the pending terraform_data create vanished from the second plan above: "Plan: 0 to add". Nothing says so. The default: arm is the last in the switch, and the case o.destroyRaw: arm before it sets DestroyMode first (extended.go:221-222), so plan -destroy -invoke=… reaches core unconverted. 08What is still gated

Three surfaces at the front of the arc are not finished in the open-source CLI. Deferred actions have been in core since v1.8 and still need an experimental build. Stacks is GA, but only as an HCP Terraform product, and the CLI command downloads a plugin to run it. Terraform Policy is GA in the v1.17 CLI, runs as a separate executable, and fails open for plan and apply. The newest surfaces are Terraform-only and partly run outside the terraform process.

Deferral: in core, not in the CLI

The deferring package (db07b905e, 26 January 2024, first tagged in v1.8.0) tracks resources whose plan must wait, so that a partial plan can be applied and the rest planned later (internal/plans/deferring/doc.go:4-10). Deferral is transitive: anything that depends on a deferred object is deferred too, and the whole mechanism is a no-op when deferral is not allowed (deferred.go:288-330). With deferral on, unknown count or for_each keys become nodePlannablePartialExpandedResource nodes addressed like module.x[*].res, and a plan file can record five reasons, from INSTANCE_COUNT_UNKNOWN to DEFERRED_PREREQ (internal/plans/planproto/planfile.proto:438-445) from the code.

The switch is -allow-deferral, added on 3 April 2024 and first tagged in v1.9.0. Every release binary through v1.17.0 rejects it, as a belated flag-parse error at internal/command/plan.go:195-207: "The -allow-deferral flag is only valid in experimental builds of Terraform." measured here. Two runtimes turn it on in code: the Stacks runtime always sets DeferralAllowed: true (internal/stacks/stackruntime/internal/stackeval/client_capabilities.go:12), and terraform test passes it through (internal/command/test.go:178). A plain CLI apply sets it only to honour deferrals already recorded. So in the CLI an unknown count still fails "Invalid count argument" (Part 2), and if a provider answers PlanAction with Deferred anyway, core reports UnexpectedProviderDeferralDiagnostic. The v1.17 experiments footer describes the feature as permitting unknown count and for_each in module, resource and data blocks. On origin/main it is still under EXPERIMENTS. In practice, deferral is GA only inside Stacks.

Stacks: a product with a CLI shim

HashiCorp announced Stacks GA at HashiConf on 25 September 2025, "for all new HCP Terraform plans based on resources under management (RUM)". It is an HCP product. terraform stacks (v1.13.0, #36931) "delegates all execution to an internal plugin": the CLI discovers the stacksplugin.v1 service on app.terraform.io, downloads the plugin and talks to it over go-plugin gRPC with the cookie key TF_STACKS_MAGIC_COOKIE (internal/command/stacks.go:58-77) from the code. The first terraform stacks -help, run under HOME=$PWD, downloaded tfstacks 1.4.0, 22,585,528 bytes, into .terraform.d/stacksplugin/; a verifier later deleted it. A tiny stack of one random component passed stacks init and validate locally once a .terraform-version file existed, a rule the plugin enforces and this repository does not measured here.

The language and runtime are not hidden: they live in internal/stacks/*, driven over terraform rpcapi, which v1.13.0 declared GA while saying it is "not intended for public consumption". Core carries a few Stacks-only switches, such as AllowRootEphemeralOutputs (§06) and always-on deferral, and some CHANGELOG lines are Stacks work in core: input-variable validation (#38240) and component no-op reporting (#38049) in v1.15. Part 4 places this in the commercial edge.

Terraform Policy: GA, out of process, fail-open

Policy is a second plugin protocol. policy.Connect execs tfpolicy-plugin rpcapi, found on $PATH or through TF_POLICY_PLUGIN, as a go-plugin child with AutoMTLS and magic cookie value 6F11ED78A2AB (internal/policy/client.go:31, 116-145; added in #38514, first tagged v1.16.0). The service has Setup, EvaluateResource, EvaluateProvider and EvaluateModule, plus a reverse CallbackService through which the plugin asks core for GetResources and GetDataSource; Setup returns version constraints checked against Terraform (internal/policy/proto/policy.proto:14-29) from the code.

It runs at three stages, InitEvaluationStage, PlanEvaluationStage and ApplyEvaluationStage (internal/policy/evaluation_stage.go:10-16). At init, the module and provider installers ask it about each source and version and refuse to download on an error (internal/command/meta_policy.go:83-180). At plan and apply, each instance's attributes and prior attributes go to EvaluateResource from a separate policy subgraph whose nodes run even after their dependencies fail, under a semaphore of TF_POLICY_PARALLELISM or GOMAXPROCS, independent of -parallelism (internal/terraform/policy.go:27-52; graph_policy.go:11-60). The lab's apply trace from §01, with no policy configured, logs "Using GOMAXPROCS=2 for policy evaluation parallelism" measured here. Part 2 shows the walker's AlwaysRunVertex that makes those nodes run.

Setup is where the asymmetry lives. plan logs a failed setup and carries on, at internal/command/plan.go:106-116: 

	if len(args.PolicyPaths) > 0 {
		client, policyDiags, stopClient := c.PolicyClient(c.CommandContext(), args.PolicyPaths, backendPolicyEntitlement(be, policy.PlanEvaluationStage))
		// if there has been any errors when setting up the policy client, we log them but
		// we still proceed with the operation, as a failure to set up the policy client

		if opReq.View != nil && policyDiags != nil {

		}
		opReq.PolicyClient = client

	}

The pieces that arrived in v1.16 faced HCP first: run policy summaries (#38715) and plugin credentials taken from the cloud or remote backend (#38716). The local -policies path stayed experimental until v1.17.

Which "GA"

The v1.17.0 CHANGELOG says -policies on plan, apply and query no longer needs an experimental build, and cites #38970. That PR is a replace-action split from 10 August 2026. The gate was removed by c0a2efe291 (#38996, 1 September 2026), whose changie entry carries Issue: "38970", and whose body was rewritten from "plan, apply, and init" to "plan, apply, and query" (CHANGELOG mistake, code, verified). The flag itself appears only in query -help. The entry says nothing about fail-open setup or the local entitlement failure. HCP's policy documentation still says "beta" and "requires v1.16alpha"; the install page says beta and "requires Terraform v1.16 or later"; HCP's public beta started on 16 July 2026. On origin/main, the 1.18.0 Unreleased CHANGELOG still lists terraform query -policies as experimental (CHANGELOG, code, per a verifier). Three surfaces, three maturity labels, for one flag.

Policies are *.policy.hcl files of resource_policy "TYPE" "NAME" blocks with enforce { condition, error_message, info_message }, filter, locals, operations and an enforcement_level of advisory, mandatory_overridable or mandatory, the default, according to HashiCorp's reference for v0.5.x. What a running plugin does with a mandatory_overridable failure in the local CLI, which has no override UI, could not be tested without an entitled engine.

Taken together, what is still gated at v1.17.0 is machinery rather than language: the cloud, test cleanup and state migrate commands, -allow-deferral, test backend and skip_cleanup, and provider state_store all need an experimental build (commands.go:453-466). The commercial engines, Stacks and Policy, ship as separate executables that the CLI downloads or execs. That is the same seam as the providers of Part 2, used this time for HashiCorp's own products reconstruction.
