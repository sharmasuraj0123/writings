{{S}}When loading means executing

A YAML tag can name a type, and a loader that honours every name builds whatever the file asks for. That produced a run of code-execution CVEs, published from 2018 to 2022 and each fixed by making the default loader refuse more tags. Safe does not mean bounded. Aliases and merge keys let a few hundred bytes describe hundreds of millions of values.

A tag names a constructor

YAML 1.2.2 says processors for a language "typically provide some form of local tags that map directly to the language’s native data structures" (§10.4). from the spec PyYAML's !!python/ tags play that role. NVD on CVE-2017-18342: "In PyYAML before 5.1, the yaml.load() API could execute arbitrary code if used with untrusted data." The maintainers wrote that load "has been unsafe since the first release in May 2006". from the docs

The repair ran from 5.1 to 6.0 (Figure {{fig-cve-ledger}}). PyYAML 5.1 (13 March 2019) made a bare yaml.load warn and fall back to a new FullLoader. FullLoader was bypassed three times. Version 5.4 "moves arbitrary python tags to UnsafeLoader", and 6.0 (13 October 2021) made the Loader argument mandatory. from the docs In the research probes, a bare yaml.load raises TypeError in 6.0.3. FullLoader still turns !!python/name:os.getcwd into the function object: a reference, not a call. measured here

Others broke their APIs too. SnakeYAML 2.0 (26 February 2023) stopped allowing global tags by default, to fix CVE-2022-1471. Psych PR #487, released in 4.0.0 on 13 May 2021, "changes the default Psych.load to use safe_load", and Ruby 3.1 shipped it. js-yaml 4.0 moved !!js/function and its other JavaScript tags to a separate package. from the docs RFC 9512 states the rule: "Code execution in deserializers should be disabled by default and only be enabled explicitly." (§4.1) from the spec SnakeYAML's README tells config users: "When you use SnakeYAML to configure your application you are totally safe." from the docs That holds only while nobody untrusted writes the file, and agents now write config too (When the program writes back). reconstruction

One harmless payload, fourteen readers

The harness sends _cases/yaml/python_tag.yaml, one 45-byte line that calls str: 

x: !!python/object/apply:builtins.str ["hi"]

PyYAML's unsafe_load calls it and returns {"x": "hi"}. safe_load, the C loader, full_load, ruamel safe and both js-yaml versions raise errors. The other seven return ["hi"]: yaml.v3, sigs.k8s.io/yaml, goccy, serde_yaml, serde-saphyr, eemeli's yaml (with a warning) and ruamel's round-trip loader. measured here Nothing runs, but a value meant to be a string arrives as a list. reconstruction !!js/function fails in both js-yaml versions; Go and Rust return its body as a string. measured here

Safe is not bounded

The CVE-2019-11253 payload was a Kubernetes ConfigMap of nine anchored lists. List a holds nine strings, and lists b to i each hold nine aliases to the list before, so i names 99 = 387,420,489 strings. NVD says it let authorised users "send malicious YAML or JSON payloads". The reporter saw the CPU cost client-side, in kubectl. PR #83261 (merged 3 October 2019) limited decode size, and normal API request bodies "are now limited to 3MB". from the docs

The harness sends that payload (y_bomb9, 446 bytes). Seven loaders accept it in milliseconds and return shared references: 12 containers that a full walk would expand to 435,848,053 leaves (the harness counts them without walking). That is 9 + 92 + … + 99 = 435,848,049 strings, plus the four strings outside data. Five loaders refuse it (Figure {{fig-alias-bomb}}). A six-level cut (y_bomb6, 335 bytes) loads in the same seven, and Python's json.dumps of the result is 4,334,696 bytes, 12,939 times the input. measured here js-yaml's safety guide says the graph "stays cheap until you fully walk it", yet js-yaml 5's maxAliases defaults to −1, unlimited. from the docs

Merge keys, the newest vector

The research probes chained merge keys, each mapping merging the previous one twice. Lines 1–3 of ~/config-ref/bench/yaml/merge20.yaml (it ends at L20, line 21): 

L0: &L0 {k: v}
L1: &L1 {<<: [*L0, *L0]}
L2: &L2 {<<: [*L1, *L1]}

PyYAML 6.0.3's safe_load took two to three seconds at 20 levels (557 bytes) over two runs (about two seconds with CSafeLoader), and about half a minute at 24 (673 bytes): about 4× per two levels. ruamel's pure safe loader took about five seconds at 20. measured here Wall-clock time here varied by about ±50%, so only orders of magnitude count: seconds at 20 levels, tens of seconds at 24. The fix, PR #937, merged to main on 17 June 2026, notes that "A small document under 1 KB can trigger millions of element list extensions". On 9 October 2026 PyPI's latest release is still 6.0.3, from 25 September 2025. from the docs

js-yaml has had six merge-key advisories since November 2025. They run from prototype pollution to a "Quadratic-complexity DoS in merge key handling via repeated aliases". js-yaml 5 turned merge off by default; two of the six cover 5.x users who turn it back on. from the docs

JSON's version, and TOML's

JSON has no tags or aliases. from the spec Its analogue is prototype pollution when config layers are merged (the JSON section). reconstruction The Kubernetes PR was titled "limit yaml/json decode size". from the docs TOML has no tags, aliases or merge keys. from the spec Its denial-of-service surface is nesting depth. reconstruction On a = [[[…]]] (t_depth), Rust's toml and toml_edit refuse at 81 levels, tomlkit at 101 and tomli at 402. BurntSushi and @iarna/toml accept 100,000, the search cap. measured here TOML's unreleased main text says: "It's recommended to allow at least 100 levels of nesting." from the spec Rust's limit of 80 sits below that. reconstruction The rules follow in the practice section.
