{{S}}One configuration, three ways

Write one realistic configuration in all three formats and hand it to every parser. Twenty-eight of 32 hear the same data; the other four hear Norway as false. Parse times span three orders of magnitude and barely matter. What is heard does.

The file

The configuration, _cases/cross/agent.json and its .yaml and .toml twins, describes a code-review agent service: model, timeouts, retries, a country allow-list, a three-line system prompt, a deployment date-time and three MCP servers with environment maps. The JSON is 1,707 bytes in 69 lines, the YAML 1,525 in 66, the TOML 1,560 in 67. YAML and TOML each carry six comments. measured here JSON's grammar has none (JSON: a strict grammar, loose readers). from the spec

Figure {{fig-three-ways}} shows four differences. JSON and TOML quote every country code; YAML leaves them bare, and a bare NO is a YAML 1.1 boolean (YAML: the type you did not write). from the spec JSON has no multi-line string: RFC 8259 §7 requires control characters, newline included, to be escaped. YAML's | keeps the line breaks and one final newline (clip chomping, YAML 1.2.2 §8.1.1.2); TOML's """ trims the newline after the opening delimiter. from the spec So the JSON prompt sits on line 29, 157 characters long, and all three yield the same string. measured here The date-time differs in type. YAML 1.2's Core schema has no timestamp (What each format can say). from the spec Six loaders still build a date-time object (PyYAML's two, ruamel's two, yaml.v3, js-yaml 4); the other six return a string. measured here And TOML 1.0 says inline tables "are intended to appear on a single line", so the env map on line 53 runs to 85 characters. from the spec

What each parser heard

The harness reads each file with every parser of its format, the 32 configurations of the main matrix, and compares the result with py json's reading of agent.json, date-times as UTC instants and numbers canonically. All 10 JSON parsers, all 10 TOML parsers and 8 of 12 YAML loaders agree. The four that do not, PyYAML 6.0.3 through safe_load and CSafeLoader, sigs.k8s.io/yaml v1.6.0 and serde-saphyr 1.3.0, hear routing.allowed_countries[4] as false. Putting "NO" back makes each identical to the reference. None raises an error. measured here

That is the Norway problem in a file that looks like production config: one wrong value among the file's 56 scalars, in a list whose other entries are strings, and nothing fails unless something checks the element type (A practice that holds). reconstruction The instant comparison is generous. Counted by type, only 14 of 32 match: 28, less the 10 TOML parsers and the four agreeing YAML loaders (ruamel's two, yaml.v3, js-yaml 4) that return a date-time object where JSON has a string. measured here

Parse time, in tiers

Each parser ran 50 warm-up parses, then 501 timed ones, in its own runtime; the median is reported. Only the parse is timed, with default options into an untyped target. jq (process start dominates) and the Python 3.15 release candidate were not timed, which leaves 30. measured here The machine was not quiet. Its 2-CPU cgroup was shared with another tenant's bundler benchmark and was throttled in 395 of 473 scheduler periods during the final run. Across seven runs, medians moved by up to 2.7× (py json between 18.4 and 49.3 µs). measured here Figure {{fig-parse-tiers}} supports tiers, nothing finer.

Strict JSON parsers take about 10 to 50 µs. Eight of nine TOML parsers take about 30 µs to 0.4 ms; tomlkit takes about 4 ms. YAML loaders run from about 0.1 ms (serde_yaml) to about 10 ms (ruamel's round-trip loader). PyYAML's safe_load, which uses the pure-Python loader, is about ten times slower than CSafeLoader (9.3× to 10.2× across the seven runs). measured here The slowest reader of all is a JSON one: the Python json5 package, 0.15.0, at about 20 ms (18.2 to 38.8 ms across the seven runs), roughly three orders of magnitude slower than serde_json. measured here The format sets a floor; the implementation sets the time. A service parses its config at start-up and on reload, so even the slowest reader costs tens of milliseconds per load. What would reach production is one value heard differently by 4 of 32 readers. reconstruction

One list, four shapes

Key layout varies too. Claude Desktop's claude_desktop_config.json keeps MCP servers under mcpServers, an object keyed by server name, and Claude Code's .mcp.json uses the same wrapper key and entry shape. from the docs VS Code's .vscode/mcp.json "defines servers in a top-level servers object"; its portable .mcp.json uses mcpServers. from the docs Codex gives each server a TOML table, [mcp_servers.<id>], with environment variables in mcp_servers.<id>.env. from the docs The agent file is a fourth shape, an array of entries with a name. A block pasted under the wrong key is still valid JSON, and a reader that does not validate hears zero servers. reconstruction

The syntaxes also charge differently for depth. JSON and YAML nest; a TOML header spells out the full path. from the spec Below, my rewrite of the agent file's first server in Codex's shape (not a file from any project) needs two headers, both repeating mcp_servers.github. Python 3.14's tomllib reads it as the same server, keyed by id. measured here 

[mcp_servers.github]
command = "npx"
args = ["-y", "@modelcontextprotocol/server-github"]
enabled = true

[mcp_servers.github.env]
GITHUB_TOKEN = "${GITHUB_TOKEN}"
GITHUB_API_URL = "https://api.github.com"

Every key typed below the second header belongs to env until the next one, the trap of TOML: obvious until the second table. from the spec The agent file's [[mcp_servers]] shape has its own: written as a header, each server's environment would read [mcp_servers.env], which names no server and attaches to whichever was defined last, so moving a block moves its environment. from the spec The way out is the one-line inline table. TOML 1.1 lets it span lines. from the spec Python 3.14's tomllib and @iarna/toml reject that (TOML 1.1 and the version nobody declares). measured here In TOML, depth costs headers or line length. reconstruction
