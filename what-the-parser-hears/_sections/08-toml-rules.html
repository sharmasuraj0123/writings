{{S}}TOML: obvious until the second table

TOML's grammar is small and its types are fixed by syntax, so its traps are not about types. They are about where a line lands and which redefinitions a parser lets through. The one projects warn about is valid TOML. Every parser agrees on it; only the author is surprised.

Where a key lands

The goals quoted in Three formats, three intentions promise obvious semantics. The table rule is one sentence. A header opens a table, and "Under that, and until the next header or EOF, are the key/values of that table." The root table "starts at the beginning of the document and ends just before the first table header (or EOF). Unlike other tables, it is nameless and cannot be relocated." from the spec No syntax returns to the root. A top-level key added at the bottom of a file joins whichever table came last, and neither a blank line nor a comment stops it. reconstruction Call it the scope trap.

The case t_scope_trap is 97 bytes: a title, a [server] table, a blank line, a comment saying "meant as a top-level setting", and debug = true. All 10 TOML configurations in the harness put debug inside server and leave the root holding only title, with no error and no warning (Figure {{fig-scope-trap}}). measured here The research probe behind the TOML dossier sent the same document through 16 configurations: these 10 plus smol-toml in BigInt mode, @iarna/toml 3.0.0, @ltd/j-toml, npm toml 5.0.0 in two modes, and Rust toml 0.8.23. All 16 did the same. measured here

The tools that read these files mostly let it pass. Cargo 1.97.1 accepted a probe crate with workspace.exclude after [profile.release] and warned only of an "unused manifest key". Appending dependencies = ["numpy>=2", "scipy"] to a copy of fly-lab's pyproject.toml put it under pytest's table; pytest 9.1.1 ran the tests and printed "Unknown config option: dependencies". measured here

Upstream makepad's root Cargo.toml keeps its workspace.* settings as top-level dotted keys on lines 1 to 294, opens its first header at line 297, and its last, [profile.test.package.makepad-stitch], at line 315. from the tree In a copy, an appended workspace.exclude = ["experiments/scratch"] landed inside that last table, and nothing reported a clash with the real workspace.exclude on line 179, because the two keys sit in different tables. measured here

Alacritty had moved from YAML to TOML in 0.13.0, released on 27 December 2023 (PR #6673), after its maintainer cited YAML files with broken indentation in issue #6592. Ten months later, 0.14.0 (22 October 2024) added a [general] table because of TOML's own table rule. from the docs Projects now design around the rule. Alacritty's PR #8192, merged on 2 October 2024, says "Some users struggle with TOML, since root options must always be at the top of the file, since they're otherwise associated with the last table." It removed every root-level option. Zola's docs warn that a section "ends at the next section or EOF." from the docs Writers fall in too: tomlkit 0.15.1 (17 July 2026) fixed a bug in which appending a top-level scalar from code, after a dotted-key entry whose table had a child header, "placed the scalar inside that table's scope, silently re-nesting it on round-trip." from the docs

Arrays of tables repeat the rule: "Any reference to an array of tables points to the most recently defined table element of the array." from the spec After two [[servers]] blocks, [servers.limits] belongs to the second server only, in tomllib 3.14.4. Writing [servers] twice where [[servers]] was meant fails in all 16 research configurations. measured here

Defined once, never reopened

The remaining structural rules are about definition. "Like keys, you cannot define a table more than once. Doing so is invalid." A super-table may follow its sub-table; the spec's example comment reads "defining a super-table afterward is ok". Headers and dotted keys may not redefine each other's tables. Inline tables "are fully self-contained and define all keys and sub-tables within them. Keys and sub-tables cannot be added outside the braces." from the spec

Most of these hold everywhere (Figure {{fig-toml-disagree}}). Three invalid documents do not, two of them the spec's own examples. BurntSushi/toml v1.6.0 lets a dotted key extend a header-defined table and an inline table, merging the keys both times. @iarna/toml 2.2.5 accepts the example the spec marks # [fruit.apple]  # INVALID. measured here That version is still what npm install @iarna/toml installs: a TOML 0.5 parser published on 22 April 2020. On 9 October 2026 BurntSushi's issue #470 was open, fix PRs #486 and #487 were unmerged, and v1.6.0 was still the newest release. from the docs In a verification probe, BurntSushi also read a.b = "hello" then a = 7 and silently discarded a = 7. measured here A file a Go tool accepts can be refused by a Python or Rust tool. reconstruction

Numbers, dates and the missing null

TOML has no implicit octal: 0755 is an error in all 10 configurations and 0o755 is 493 in all 10. measured here The integer rule is strict: "If an integer cannot be represented losslessly, an error must be thrown." from the spec At 263, one past the int64 maximum, the parsers split three ways. Rust, Go and smol-toml raise an error. @iarna/toml returns the BigInt −9223372036854775808: the sign flips and nothing complains. tomllib, tomli and tomlkit return the exact Python int. measured here TOML 1.1 allows any integer size (What each format can say). from the spec smol-toml errs the other way: by default it refuses the valid int64 values 263 − 1 and 253 + 1, as "integer value cannot be represented losslessly". measured here In the research probe's run of toml-test, the official conformance suite, tomlkit read 1٠, a 1 followed by U+0660 ARABIC-INDIC DIGIT ZERO, as 10. from the docs measured here Python's int() accepts any Unicode decimal digit, the likely cause. reconstruction

inf, -inf, nan and -0.0 parse in all 10. Mixed-type arrays have been valid since 1.0: "Values of different types may be mixed." from the spec @iarna/toml 2.2.5 still refuses a = [1, "a"]: "Inline lists must be a single type". measured here

The four date-time types (What each format can say) arrive as different native types. On t_datetimes, Python returns datetime, date and time; Rust one Datetime struct with optional parts; go-toml v2 time.Time plus its own three local types; BurntSushi time.Time for all four, with a local time placed on 0000-01-01; smol-toml a TomlDate each time. @iarna/toml returns a JavaScript Date for the offset value, which keeps the instant (14:32 UTC) but not the −07:00 offset. measured here In the research probe, smol-toml 1.9.0 and @iarna/toml turned 2020-02-30 into 1 March 2020; the Python, Go and Rust parsers refused it. measured here smol-toml's README says "certain invalid datetimes (e.g. 2020-02-30) are gracefully accepted." from the docs

TOML has no null, so the trouble moves to writers. In the research probe, tomli_w and tomlkit raise on None. smol-toml 1.9.0 and @iarna/toml 2.2.5 drop keys whose value is null, and @iarna writes [1, null] as arr = [ 1 ], one element shorter, with no error. go-toml v2.4.3 writes a Go field []*int{&one, nil} as ports = [1, 0]. measured here A program that saves its own config can change a list for the next reader (When the program writes back). reconstruction

Bytes and shapes

Two byte-level details split the parsers. "TOML parsers should feel free to normalize newline to whatever makes sense for their platform." from the spec For a multi-line string with CRLF endings, tomllib and tomli return line1\nline2; the other 7 configurations keep \r\n, on the same Linux machine. measured here A leading UTF-8 BOM split the 16 research configurations 8 to 8: BurntSushi, smol-toml, npm toml, both Rust toml versions and toml_edit accept it; go-toml v2, @iarna/toml, j-toml and every Python parser refuse it. measured here toml-test notes that the spec "does not explicitly say if a document can start with a UTF-8 BOM". from the docs

The last cost is shape. Every header names its table by the full path, so deep data repeats itself. from the spec A constructed fragment shaped like a Kubernetes Deployment: 

[[spec.template.spec.containers]]
name = "app"
image = "app:1.4"

[spec.template.spec.containers.resources.limits]
cpu = "500m"

The second header names a path but binds to a position: the most recent container, as with [servers.limits] above. from the spec In the research probe, a Deployment-shaped document written with headers only took 14 headers, 9 repeating spec.template.spec.containers; it ran to 44 lines and 934 bytes, against 46 lines and 848 bytes of YAML and 76 lines and 1,541 bytes of two-space JSON. measured here Size is not the problem. Distance is: the further a key sits from the header that owns it, the easier it is to misplace. reconstruction One configuration, three ways shows the same cost on MCP server lists; the next section covers which TOML a parser reads.
