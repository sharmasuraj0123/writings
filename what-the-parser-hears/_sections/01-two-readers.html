{{S}}Two readers, one file

A configuration file has two readers. One is the person who writes it. The other is the program that loads it. Most of the time they agree on what the file says. Every pitfall in this guide is a place where they do not, and the program's reading is the one that runs.

The disagreements come in three kinds. The first is syntax the author did not expect to matter. A UTF-8 byte-order mark before {"a": 1} is reported as an error by 7 of the 10 JSON parsers measured here, including JSON.parse, Python's json and both Go APIs (jsonc-parser flags it but still returns the object); jq and the two json5 parsers skip it silently. A tab in YAML indentation is an error in all 12 YAML loaders, and a trailing comma in JSON is accepted silently only by the two json5 parsers; jsonc-parser flags it and returns the object anyway. measured here jsonc-parser is Microsoft's fault-tolerant parser for JSON with comments, built to return a result even from invalid input. from the docs RFC 8259 §8.1 lets a parser ignore a BOM, and YAML 1.2.2 §6.1 forbids the tab. from the spec Syntax disagreements are mostly loud: the program refuses to start, and someone fixes the file. reconstruction The JSON cases return in JSON: a strict grammar, loose readers.

The second kind is typing the author did not intend, and it is silent. In YAML the country code NO becomes false in 4 of 12 loaders. The version 3.10 becomes the float 3.1 in all 12. A file mode written 0755 has three readings: 493 in five loaders, 755 in six, and the string "0755" in one. None of these raises an error. measured here Each one is taken apart in YAML: the type you did not write.

The third kind is structure the author did not see. In TOML, the lines after a table header, "until the next header or EOF, are the key/values of that table" (TOML 1.0.0 and 1.1.0, section Table). from the spec A debug = true appended at the end of a file, under a comment calling it a top-level setting, lands at server.debug in all 10 TOML parsers, with no error. measured here Helm issue #9793 (10 June 2021, Helm v3.6.0) reported that the unindented lines after an indented first line of values.yaml were ignored. from the docs The reported file still loses them: yaml.v3 v3.0.1, sigs.k8s.io/yaml v1.6.0 and serde-saphyr 1.3.0 return only the first mapping, and nine other loaders refuse the file. measured here sigs.k8s.io/yaml is the library Kubernetes uses, and serde-saphyr is a Rust crate. from the docs The two traps have their own sections, TOML: obvious until the second table and YAML: the structure you did not see.

A fourth kind arrives when programs write configuration back, as cargo add has done to Cargo.toml since Rust 1.62 and Claude Code does to ~/.claude/settings.json from its /config menu. from the docs Every such writer is a reader first, and it writes down what it heard. reconstruction Load the 66-line YAML agent config this guide returns to with PyYAML's safe_load, change one value, save it with safe_dump, and NO comes back as false, with the keys sorted and none of the six comments. Re-read by PyYAML, ruamel.yaml and eemeli's yaml (the npm package named yaml), it is false all three times, though the last two heard NO in the original. measured here The writer has changed what every later reader hears. How this guide listens

Most results badged measured here come from one harness, _compute.py, beside this page. The rest come from research probes run on the same machine (unpublished, in ~/config-ref/bench), and the text names the probe wherever one is used. The harness sends 71 cases (30 YAML, 17 JSON, 24 TOML) to the parsers for their format, 34 configurations in Python, Node, Rust, Go and jq, and records what each heard, with its native type, or its exact error. The main matrix is 32 of them: 12 YAML, 10 JSON, 10 TOML. PyYAML's full_load and unsafe_load run only on the tag case. Parsers are called as a loader without a schema calls them: default options, untyped target. Typed targets were not measured. What a parser heard is exact and repeatable: repeated full runs gave the same readings, and only timings, alias-bomb load times and two stack-bound depth limits moved. measured here

The answer, up front

You can stop reading after this list. Each item is my judgement. reconstruction

  1. For configuration people edit, in a tool you control: TOML. Write to the 1.0 subset unless you pin the parser, and put top-level keys before the first table header. Python 3.14.4's tomllib rejects all four TOML 1.1 features measured here. measured here
  2. For configuration a program writes, or that crosses language boundaries: strict JSON, validated by JSON Schema. If people also edit it, use JSONC through one named parser that fails on errors, or keep the file's format and write it with a format-preserving editor (tomlkit, toml_edit, ruamel.yaml round-trip). JSONC here means JSON with comments as VS Code reads it. from the docs Failing on errors is not automatic: jsonc-parser flags a trailing comma and still returns {"a": 1, "b": 2}. measured here
  3. YAML only where the ecosystem expects it. GitHub Actions documents only YAML for workflows, the Compose specification defines its file as YAML, Ansible chose it, and Kubernetes says "By convention, manifests are YAML". from the docs There, quote every scalar that is not obviously a string and lint with yamllint 1.38.0, whose truthy rule allows only true and false by default. from the docs Validate against a schema, and load with a YAML 1.2 safe loader that limits aliases.
  4. For all three: name and pin the parser, validate against a schema, use a loader that rejects duplicate and unknown keys and a typed target, check in CI, and never run load-and-dump on a file people edit.
  5. If a file needs computed values or types shared across files, use a configuration language (CUE, Pkl, Nickel) or configuration as code, and guard its output the same way.

The rest of the guide earns that answer, one format at a time and then side by side, and A practice that holds turns it into rules. A companion post, Where the JSON Lives, treats JSON as stored data. This one treats JSON, YAML and TOML as written configuration: files a person edits and a program trusts.
