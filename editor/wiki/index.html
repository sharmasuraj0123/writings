The Composable Post SystemInternal docs

Every post in this publication is one self-contained HTML file. composable-post/1 makes that file editable as parts without giving up the single-file property: inert comment fences name every region, one embedded JSON manifest indexes them, and an editor — or plain grep — can recompose the page. This page documents the grammar, the manifest, the composition rules, and the tools, using the annotated flagship as the worked example throughout.

01Why composable posts

The flagship post of this publication, what-is-quirq/index.html, is a single HTML file of 16,571 lines: one <style> block, eight chapters, twenty-four sub-sections, two inline scripts, three navigation surfaces. That is by design — the operating contract (writings/AGENTS.md §1) requires every post to be one self-contained static file that renders over file:// with no build step, no webfonts, and no external JS. The property that makes a post archivable is the same property that makes it painful to edit.

The pain is concrete. Different readers want different cuts of the flagship: an investor deck wants Section 3 (business impact) before Section 2 (the measurement calculus); a research audience wants the calculus and the references and nothing else; a draft review wants the four placeholder chapters gone. Producing any of those today means hand-surgery on a 16,000-line file — find the section's true byte range, find every nav entry in three separate surfaces that points into it, find the CSS regions only it uses, and hope nothing else referenced any of it. Every step is manual, and every step can silently break the scroll-spy, which by design ignores anchors it cannot resolve.

composable-post/1 is the answer, and it is deliberately not a build system. The spec (shared/composable-post.md) puts it in one sentence:

The core guarantee — spec, preamble "Annotations are inert: comments, data-* attributes, and one JSON <script> — stripping them all must reproduce the un-annotated page byte-for-byte. A post remains one self-contained file that renders over file://."

In other words: the composable version of a post is the post. The annotation layer adds comment fences around every extractable region, a few data-* attributes on the movable elements, and one machine-readable manifest — 1,229 added lines on the flagship (16,571 → 17,800), every one of them invisible to a reader and removable by a deterministic strip. Four artifacts make up the system:

02The block model

A block is a named, contiguous region of the file. Every block lives in one of seven namespaces, and the namespace tells you what the block is allowed to do: whether it can move, whether it can be removed, and what happens to the rest of the page if it is.

The annotated flagship carries exactly 53 blocks: 3 doc + 11 css + 4 chrome + 8 chapter + 24 part + 2 script + 1 data — a count you can verify in ten seconds with the grep census in §03, or by reading manifest.blocks.length. The chapter census:

Figure 1 is the whole annotated file, top to bottom, with the real block names and the real line ranges of the current build. Note where the weight is: the head (one <style>, 11 fenced regions) is more than half the file; the four chrome blocks and the masthead are thin bands; the manifest and two scripts close the file.

03Marker grammar & data attributes

Everything in the annotation layer is designed to be found with one grep and removed with one pass. There are three kinds of marks: fence comments, data-block* attributes on movable elements, and data-for attributes on nav links.

Fences

Every extractable region is wrapped in a comment pair (spec §1): 

<!-- ══════ BLOCK <ns>:<id> ══════ -->
…
<!-- ══════ END <ns>:<id> ══════ -->

The whole grammar is one regex, quoted from the spec: <!-- ═+ (BLOCK|END) ([a-z]+:[a-z0-9-]+) ═+ -->. Fences sit on their own lines, indented to match the fenced content, so removing a block is a pure line-range deletion. The census is one command: 

# every fence, with line numbers (this exact recipe is printed
# in the ANATOMY banner at the top of the annotated file)
grep -n 'BLOCK \|END ' what-is-quirq-test/index.html
# → 107 lines: 53 BLOCK + 53 END fences, plus the banner line itself

# one chapter, fence to fence (trailing space keeps
# chapter:measure from matching part:measure-*)
sed -n '/BLOCK chapter:measure /,/END chapter:measure /p' \
    what-is-quirq-test/index.html > measure.html

Data attributes

Fences carry identity; attributes carry behavior. The opening tag of every chapter and part element repeats the block id and adds what tooling needs to build an outline without parsing the manifest. The real opening tag of the measurement chapter (one line in the source, wrapped here for display): 

<section class="measure-chapter" aria-labelledby="measure-heading"
    data-block="chapter:measure"
    data-block-title="2 · How to measure"
    data-block-category="calculus"
    data-block-status="complete"
    data-block-optional>

Five attributes, all defined in spec §2: data-block matches the fence; data-block-title is the full nav label in NN · Title form; data-block-category names a category from the manifest (§04); data-block-status is complete or placeholder; and the bare data-block-optional is "present iff the page still works with the block removed (nav is regenerated; no other block references it)."

Nav links get the third mark. Every entry in the .toc-menu and the .contents-rail carries data-for="<anchor>" naming its target, "so tooling can rebuild nav without parsing hrefs." Real lines from the rail: 

<a class="contents-parent" href="#introduction" data-for="introduction">1 · Introduction</a>
<a href="#workspace" data-for="workspace">1.1 · What is a unit of work</a>

Figure 2 dissects one complete block — part:workspace, the first part of the introduction chapter — mark by mark.

04The manifest

Markers make blocks findable; the manifest makes them understandable. It is one <script type="application/json" id="block-manifest"> element sitting before the first runtime script, itself fenced as data:manifest (lines 16,363–17,477 of the current build — a 1,115-line fenced block, the single largest piece of the annotation layer).

The schema (spec §3) has five top-level members: format, always "composable-post/1"; page with the slug and title; categories, the post's own taxonomy; blocks, one entry per block — 53 in the flagship; and shared plus nav.order, the two lists composition logic actually consults. Here is the real entry for chapter:measure, unabridged, with the field meanings annotated: 

{
  "id": "chapter:measure",          // ns:id — matches the fence
  "kind": "chapter",                // doc|css|chrome|chapter|part|script|data
  "title": "2 · How to measure",    // display title (nav form)
  "railLabel": "2 · How to measure",// ≤28 chars, contents-rail form
  "anchor": "measure",              // in-page id nav points at; null if none
  "category": "calculus",
  "status": "complete",             // complete|placeholder|n/a
  "movable": true,                  // may be reordered among siblings
  "optional": true,                 // may be removed entirely
  "parent": null,                   // enclosing block id, or null
  "children": [                     // ordered; the chapter's 11 parts
    "part:measure-score",      "part:measure-mint",
    "part:measure-cost",       "part:measure-unit",
    "part:measure-portfolio",  "part:measure-estimation",
    "part:measure-validity",   "part:measure-time",
    "part:measure-identification", "part:measure-bridge",
    "part:measure-limitations"
  ],
  "deps": {
    "css": [                        // non-shared css regions it needs
      "css:calculus-treatment", "css:intro-environment",
      "css:operating-loop", "css:references",
      "css:research-primitives"
    ],
    "js": [                         // script block, #feature optional
      "script:reading-chrome#measure-weights",
      "script:reading-chrome#cost-model",
      "script:reading-chrome#settlement"
    ]
  }
}

And the two lists that close the manifest, verbatim from the reference document: 

"shared": [
  "css:base", "css:canvas-sizes", "css:collapsible-rail",
  "css:sticky-topbar", "css:tokens",
  "chrome:progress", "chrome:threadbar", "chrome:floating-toc",
  "chrome:contents-rail", "script:reading-chrome", "doc:head"
],
"nav": {
  "order": [
    "chapter:introduction", "chapter:measure", "chapter:impact",
    "chapter:research", "chapter:other-applications",
    "chapter:data-experiments", "chapter:roadmap",
    "chapter:references"
  ]
}

shared is the survival kit: eleven blocks every composition keeps, no matter how aggressive the cut. nav.order is the current chapter order — the thing a reorder rewrites. The categories table is the flagship's own taxonomy (spec §4 — "extend per post"):

The truth rules — spec §3 "Markers are truth for extraction (byte ranges), the manifest is truth for tooling (order, titles, deps, categories). The editor regenerates both together; hand edits must keep them consistent."

One more identification rule closes the loop (spec §6): annotated pages carry <meta name="post-format" content="composable-post/1" /> in <head>, and "tooling must refuse files without it rather than guess." Figure 3 draws the whole schema as a graph.

05Composition rules

A composition is any page you can produce from the annotated original by removing and reordering blocks. Spec §5 gives six rules that any tool — the editor, a script, or your hands — must enforce. They are short enough to hold in your head.

  1. Removal is surgical. "Removing a block removes its fence-to-fence bytes, its nav entries (matched by data-for against the block's anchor and its children's), and nothing else. Only optional blocks may be removed."
  2. Reorder moves bytes and regenerates nav. "Reordering movable siblings reorders their fence-to-fence byte ranges and regenerates both nav surfaces and nav.order to match document order. Section numbers inside headings/data-block-title are names, not positions — never renumber on move."
  3. Shared blocks always survive. "A composition always keeps every block listed in shared" — the eleven ids in §04.
  4. CSS pruning is optional and conservative. "A css:* region may be dropped only when no remaining block lists it in deps.css and it is not in shared."
  5. Every operation ends valid. After any operation: every nav href="#…"/data-for resolves to an existing anchor, fences still pair, the manifest matches the DOM in order and presence, and the AGENTS.md §8 validation passes — adapted so that nav anchors must resolve, not equal the h2 list, because chapters use their own heading structure.
  6. Strip-equivalence. "Removing every fence comment, every data-block* and data-for attribute (with the single space that precedes each), the manifest script element and the format meta tag reproduces a valid, identically-rendering page."

Rules 1 and 2 are the two operations; rules 3–4 bound what may disappear; rules 5–6 are the invariants that make the whole system safe to automate. Figure 4 shows both operations on the real flagship blocks, before and after.

06The editor

The editor at editor/index.html is one self-contained HTML app — no build step, no external resources, no network calls, works opened directly via file://. It is a tool, not a post: it does not use the paper design system, and its feature set is fixed by the eight-point contract in editor/README.md, which is "normative for implementation and docs."

The contract names eight core functions. The shipped build exports further helpers on window.CPF alongside them — insert, pruneCss, blockText, sourceTree and friends — but these eight are the normative surface: 

window.CPF = {
  parse(text)                      → model   // fences + manifest → block model
  serialize(model)                 → text    // model → the exact file
  reorder(model, id, beforeId|null)          // move among movable siblings
  remove(model, id)                          // drop an optional block
  replaceBlockHtml(model, id, html)          // the HTML drawer's Apply
  regenNav(model)                            // rebuild toc-menu + rail + nav.order
  strip(text)                      → text    // annotated → plain page
  validate(text)                   → issues[]
}
// the round-trip law:
// serialize(parse(text)) === text — byte-for-byte

Two guarantees shape every interaction. First, the round-trip law above: opening a file and immediately exporting it changes nothing, byte for byte — so the editor can never corrupt a page it merely viewed. Second, the refusal rule: a file without <meta name="post-format" content="composable-post/1" /> never gets parsed, so the editor cannot half-understand an ordinary post. Click-to-edit is the subtle feature: a click in the preview iframe maps the element back to its enclosing block, the edit is committed as a change to that block's source text via replaceBlockHtml, and the preview is re-serialized — the DOM you see is always a render of the text you will export, never a divergent copy. 07Working without the editor

The format was designed grep-first: every operation the editor performs has a command-line equivalent, and the annotator that produced the reference document is a script you can re-run. This section is the toolbox.

Census, extraction, and reading the manifest

# the census — every block, in file order
grep -n 'BLOCK \|END ' index.html

# extract one block, fence to fence (works for any ns:id;
# keep the trailing space so chapter:measure ≠ part:measure-*)
sed -n '/BLOCK part:measure-score /,/END part:measure-score /p' index.html

# read the manifest without a browser
python3 - <<'PY'
import json, re
s = open("index.html", encoding="utf-8").read()
m = re.search(r'id="block-manifest">\n(.*?)\n\s*</script>', s, re.S)
man = json.loads(m.group(1))
print(man["format"], "·", len(man["blocks"]), "blocks")
print("order:", *man["nav"]["order"], sep="\n  ")
PY

Removing a block by hand

Removal is three edits, straight from rule 1 and the truth rules. Using chapter:roadmap as the example: delete the fenced lines, delete the nav entries that data-for ties to the block's anchor, and update the manifest. 

# 1 · the bytes: fence to fence, inclusive
sed -i '/BLOCK chapter:roadmap /,/END chapter:roadmap /d' index.html

# 2 · the nav: one entry in .toc-menu, one in .contents-rail
sed -i '/data-for="roadmap"/d' index.html

# 3 · the manifest: remove the "chapter:roadmap" entry from
#     blocks[] and its id from nav.order — by hand or via python.
#     (For a chapter with parts, data-for lines for every child
#     anchor go too; roadmap has none.)

Then prove you did it right — the §8 validation from AGENTS.md, adapted per spec §5.5 so nav anchors must resolve rather than equal the h2 list: 

python3 - <<'PY'
import re
s = open("index.html", encoding="utf-8").read()
fences = re.findall(r'<!-- ═+ (BLOCK|END) ([a-z]+:[a-z0-9-]+) ═+ -->', s)
stack = []
for kind, bid in fences:
    if kind == "BLOCK": stack.append(bid)
    else: assert stack.pop() == bid, f"interleaved fence: {bid}"
assert not stack, f"unclosed: {stack}"
ids = set(re.findall(r'id="([^"]+)"', s))
for anchor in re.findall(r'data-for="([^"]+)"', s):
    assert anchor in ids, f"dangling nav entry: #{anchor}"
for href in re.findall(r'href="#([^"]+)"', s):
    assert href in ids, f"dangling href: #{href}"
print("OK:", len(fences) // 2, "blocks, all anchors resolve")
PY

Stripping to a plain page

Strip is the five removals of rule 6 — fence comments, data-block* attributes, data-for attributes (each with the single space that precedes it), the data:manifest element, and the post-format meta — plus the ANATOMY banner the annotator adds at the top of the file, which the spec's fence regex does not cover but the tools remove. Don't hand-roll it: CPF.strip(text) in the editor and strip() in editor/tools/annotate.py are the reference implementations, and the annotator refuses to write its output unless strip(annotated) == original holds byte-for-byte.

Re-annotating after upstream edits

The flagship keeps evolving. When what-is-quirq/index.html changes, the annotated copy is not patched — it is regenerated by editor/tools/annotate.py, a deterministic transform: 

cd writings/
cp what-is-quirq/index.html what-is-quirq-test/index.html  # fresh copy
python3 editor/tools/annotate.py
# → OK: annotated (16571 -> 16679 lines), strip-equivalence proven
# → blocks: 53  css regions: 11  fences: 106

The 16,679 the script reports is its internal list length, not a physical line count: the inserted manifest and ANATOMY banner each enter that list as a single multi-line element. wc -l on the written file reads 17,800 — the build every line range on this page cites.

The script never uses stored line numbers. It finds everything by landmark: element boundaries come from an html.parser pass (chapters located by class — section.measure-chapter — or by id for the placeholders); CSS regions are found by their unique banner comments inside the <style> block ("THREE CANVAS SIZES" marks css:canvas-sizes, and the script asserts each banner occurs exactly once); nav labels are read out of the existing .toc-menu and rail markup. Dependencies are derived, not declared: deps.css intersects each block's class and id tokens with each CSS region's selector tokens, and deps.js checks four hook strings — data-tabs, data-measure-weight, data-cost-input, settlement-mode — against which script block defines them. If the flagship gains a chapter or a style banner, the script's landmark assertions fail loudly rather than mis-fence; you extend its chapters_def/banners tables and re-run.

Two caveats, both visible in the source. The target path is a constant at the top of the script (PATH = "what-is-quirq-test/index.html"), so it must be run from the writings/ root and it overwrites its input in place — always feed it a fresh copy. And the strip-equivalence gate compares against whatever it was given: it proves the annotation is inert, not that your upstream edit was sound. Validate the un-annotated page first, annotate second.
