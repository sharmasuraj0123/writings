Parsing bash, taken apartTeardown

GNU bash parses with a Bison LALR(1) grammar, but only because its hand-written lexer reads and writes parser state on every word, calls the parser recursively for each $( ) and leaves every word as text for a second parser at expansion time. This teardown follows one command line from bytes to fork through bash@9c46586, then sets bash beside dash, mvdan/sh, Oils, ShellCheck, tree-sitter-bash and brush, measured on 148 tricky inputs and a 100,000-line script.

01A language you cannot tokenize first

Most languages lex the file, then parse the tokens. A Bourne-family shell cannot. GNU bash keeps a Bison LALR(1) grammar anyway and pays for it: a lexer that reads parser state, a recursive parse inside words, a second parser at expansion time, and a loop that parses one line and runs it before reading the next.

Two terms first. Bison is GNU's yacc: it compiles a grammar into tables, and the generated function yyparse pulls one token at a time from a lexer, either shifting it onto a stack of numbered states or reducing the top of the stack to a grammar rule's left-hand side. LALR(1) names the table construction: each step is chosen from the current state and one token of lookahead. Nothing in that model lets the lexer know which state the parser is in, and a shell lexer needs exactly that reconstruction.

With /usr/bin/bash 5.3.9 measured here: 

$ bash -c 'for for in for; do for=for; done; echo $for'
for

One spelling is a reserved word, a loop variable, a list item and an assignment; Chet Ramey's bash chapter in The Architecture of Open Source Applications (AOSA, vol. 1, §3.4) uses the example from the docs. The instrumented build lexes the loop as (lab/results/trace-b.txt) measured here: 

FOR WORD IN WORD ';' DO ASSIGNMENT_WORD ';' DONE

Only position separates them.

Four places the split breaks

Keyword status depends on position. "Further distinction on TOKEN is context-dependent" (XCU §2.10.1; XCU is the Shell and Utilities volume of POSIX 1003.1-2024, XRAT its rationale), and nine numbered rules in §2.10.2, from command name to function body, tell the lexer which reading the parser wants. The rationale defines rule 1 by "the LR(1) lookahead set" (XRAT §C.2.10) from the docs.

Here-document bodies are not tokens. XCU §2.3 makes them a second major mode: the lines "immediately following the next NEWLINE token form the body". They "do not appear in the grammar directly" (XRAT) from the docs.

Finding a word's end takes nested parsing. §2.3 rule 5: on $(, ${ or a backquote "the shell shall recursively process them in the manner specified for the construct that is found" from the docs. Calling that a recursive parser is this research's inference from §2.6.3 reconstruction; bash makes it literal (§07).

Parsing and running interleave. "The complete_command shall be executed before the next complete_command is tokenized and parsed" (XCU §2.3) from the docs. What runs changes what the lexer accepts: an alias rewrites later lines, and extglob is read at run time, so on the same line it arrives too late measured here: 

$ bash -c 'shopt -s extglob; echo @(a|b)'
bash: -c: line 1: syntax error near unexpected token `('
bash: -c: line 1: `shopt -s extglob; echo @(a|b)'

What bash's maintainer says

Chet Ramey, AOSA §3.4: the parser "is derived from an early version of the Posix grammar, and is, as far as I know, the only Bourne-style shell parser implemented using Yacc or Bison", and needs "a lot of cooperation between the parser and the lexical analyzer". §3.7.2, "What I Would Have Done Differently": "Were I starting bash from scratch, I probably would have written a parser by hand." from the docs. The hedge stays: it is the only source for the "only yacc shell" claim.

02Bytes in: the input layer and the line buffer

Before a single token exists, bash has already changed the text. In an interactive shell history expansion has run; backslash-newline pairs are gone, and alias bodies may stand in for the real input. The lexer reads only a one-line buffer, refilled one physical line at a time. That is where "one line is the unit" (§09) starts.

One vtable for four sources

All parser input goes through one global BASH_INPUT bash_input: a stream type, a name, a location union and a getter/ungetter pair. The type is one of st_none, st_stdin, st_stream, st_string, st_bstream (bash/input.h:29, 72-84), and init_yy_io installs the pair that yy_getc calls through (bash/parse.y:1583-1597) from the code. set_bash_input picks readline, bash's buffered-fd reader or stdio (bash/shell.c:1728-1755); bash -c never reaches it. -c, eval, source and traps arrive as strings through parse_and_execute, which calls push_stream and installs the string getter (bash/shell.c:1483; bash/builtins/evalstring.c:340, 357) from the code.

Scripts: a buffer that rewinds before each fork

A script on a seekable fd gets a buffer of min(file size, MAX_INPUT_BUFFER_SIZE), which is 8192 bytes, or 8172 under bash's own malloc. An unseekable fd gets one byte (bash/input.c:129-133, 392). Before each fork, sync_buffered_stream seeks the fd back to the byte the parser actually consumed (bash/input.c:552-565; bash/jobs.c:2297-2302) from the code. Two oddities follow. A script piped into bash shares stdin, one byte at a time, with the commands it runs measured here, /usr/bin/bash 5.3.9: 

$ printf 'read line\necho "read got: $line"\necho done\n' | bash
done

read took the script's second line as data. And text appended to a running script runs, not because of the buffer size: b_fill_buffer calls read() again on every refill and tests only B_ERROR first ("try making read errors `sticky'"), so EOF is not sticky (bash/input.c:488-530) from the code.

The line buffer

Apart from the two exceptions at the bottom of Figure 2, the lexer never calls the getter. shell_getc serves bytes from a static buffer, shell_input_line (bash/parse.y:303-309), and refills it only when the line is used up and no pushed string waits on pushed_string_list (2498-2504). A refill reads to the newline and skips NUL bytes; when history is on (remember_on_history) it runs history expansion through pre_process_line (2645-2680); under set -v it echoes the line unless shell_eof_token is set, which is how a nested $( ) parse avoids echoing twice (2704-2717); and it puts the newline back (2729-2747) from the code.

Backslash-newline dies here, below the tokenizer. bash/parse.y:2842-2868, the alias comment trimmed:

#if defined (ALIAS)

prompt_again only selects and decodes PS2; it prints nothing. The jump to restart_read fetches the next physical line, so the two halves meet before any token is formed from the code. Callers turn the deletion off inside single quotes: read_token_word passes cd != '\'', and no pending literal-next character, as remove_quoted_newline (bash/parse.y:5718-5719) from the code. The consequence is visible in row lc02 of E1, this post's matrix of 148 tricky inputs run through ten parse-only columns, one accept/reject bit each (§13). The row is this 19-byte input: 

echo a &\
& echo b

Bash and dash read && and print a and b. shfmt, OSH, ShellCheck, tree-sitter and the brush 0.4.0 release reject it; brush-parser at bd19d10 accepts (lab/scripts/run_e1.py → lab/results/e1-matrix.md) measured here. Tree-sitter's grammar lists /\\\r?\n/ among its extras, tokens allowed between tokens, so a continuation can never sit inside one (tree-sitter-bash/grammar.js:103-108) from the code.

One check runs before the line buffer exists. A NUL byte in a script's first line makes bash refuse the file: cannot execute binary file, exit 126, nothing parsed (bash/shell.c:1685-1691) from the code; confirmed with /usr/bin/bash on a one-line file measured here. That is E1 row mi03, where every parser except bash accepts, and §13 explains why the row is a scoring artifact.

03The lexer that knows where the parser is

Bison pulls bash's tokens one at a time from inside yyparse. Each decision the lexer makes depends on state that the lexer and the grammar actions both write. State flows in both directions, and the grammar can stay small because this channel exists.

yylex is a wrapper with a memory

The function Bison calls is short. It is bash/parse.y:3054-3094 from the code, with the 9-line mailbox check and the 5-line YYERRCODE block marked …, and two comments trimmed: 

static int
yylex (void)
{
  if (interactive && (current_token == 0 || current_token == '\n'))
    {
      …
      if (token_to_read == 0 && SHOULD_PROMPT ())
	prompt_again (0);
    }

  two_tokens_ago = token_before_that;
  token_before_that = last_read_token;
  last_read_token = current_token;
  current_token = read_token (READ);

  if ((parser_state & PST_EOFTOKEN) && current_token == shell_eof_token)
    {
      return (current_token);
    }

  if (current_token < 0)
    …
  return (current_token);
}

It prompts at a command boundary, shifts a three-token history and calls read_token. The history also moves in push_token, whose only caller is bash/builtins/evalfile.c:333, a fake newline after a sourced file that ends at EOF. parse_compound_assignment calls read_token without shifting at all from the code.

read_token checks one slot before any input (bash/parse.y:3569-3580): 

if (token_to_read) { result = token_to_read; …
      token_to_read = 0; … return (result); }

The slot carries '\n' after an error or after a bare time, COND_END after a [[ … ]], and the synthetic DOLPAREN and DOLBRACE tokens that open nested parses (§07) from the code. Operators are hand-coded if/switch blocks with one or two characters of lookahead, for <<-, <<<, &>> and ;;& (bash/parse.y:3688-3762). other_token_alist (2389-2425) exists only to name tokens in error messages. Character classes come from the generated sh_syntaxtab; the metacharacters are ()<>;&| (bash/syntax.h:29-32, 73-75). # starts a comment only at the start of a token: bash -c 'echo a#b #c' prints a#b measured here.

Three stores of context

First, the token history. Second, counters: open_brace_count, esacs_needed_count, expecting_in_token, and the 256-deep compoundcmd_lineno stack (MAX_COMPOUND_NEST, bash/parse.y:344-359). Grammar actions read it for the start line of for, select and case commands (bash/parse.y:895-1049); the EOF error reads it to name the open construct in "unexpected end of file from `while' command on line 1" (6892-6902) from the code. Third, parser_state: one int holding 28 PST_* flags, five of them commented unused (bash/parser.h:29-56). bash's own DEBUG printer, dump_pflags, tests 27 of the 28; it skips PST_FORCMD from the code. Flags outlive their code: 11 of 16 LEX_* flags are dead leftovers of the pre-2021 scanner for command substitutions (comsubs, bash's own abbreviation for $( )), present only in their #define and the debug printer (bash/parse.y:3835-3850) from the code.

Both sides write these stores. The lexer sets flags while recognising text. ;;, ;& and ;;& set PST_CASEPAT (bash/parse.y:3709-3718, 3757-3761). A ( outside a pattern list or [[, not after a WORD, sets PST_SUBSHELL and pushes compoundcmd_top. A ) after WORD ( sets PST_ALLOWOPNBRC, so the next { opens a function body (bash/parse.y:3765-3791). Keyword matches set PST_CASESTMT and PST_CONDCMD (§04) from the code.

The grammar writes back. make_simple_command sets PST_REDIRLIST when it starts a fresh command and clears it when the first word arrives (bash/make_cmd.c:480-490). The lexer reads that bit to decide whether a word after a leading redirection is in command position. Loop actions pop compoundcmd_top, which the lexer pushed (bash/parse.y:904-905). The timespec actions plant token_to_read (bash/parse.y:1436-1442). A grep for parser_state |=, &= and = outside the generated y.tab.c finds 74 sites: 71 in parse.y, 3 in make_cmd.c measured here. On error reset_parser zeroes parser_state and the counters, frees the line and plants token_to_read = '\n' (bash/parse.y:3494-3539) from the code.

Ramey describes the channel from the parser's side: "the parser has to tell it something about how far it has progressed parsing a command" (aosabook.org/en/v1/bash.html, §3.4) from the docs. Figure 3 draws the loop.

Watching the bits move

The running example needs none of this. Its trace prints parser_state=0x0 at all 19 yylex returns, 18 tokens plus yacc_EOF (lab/results/trace-a.txt) measured here. The token history alone classifies it; PST_REDIRLIST is set and cleared inside one make_simple_command call, between two trace lines.

A case makes the flags visible. Trace (c) prints the state after each token of $(case x in x) echo y;; esac) (lab/results/trace-c.txt). The three comsub bits, 0x408040, are constant. CASE adds PST_CASESTMT (0x4080c0). IN adds PST_CASEPAT (0x4080c1). The pattern's ) clears it, ;; sets it again, and ESAC clears both measured here. Figure 4 plots the eleven columns.

State the parser never sees

The lexer also reads globals that only executing a command can change. With extglob, @( is lexed as the start of one pattern word, but only if extended_glob is on at the moment the word is read (bash/parse.y:5464-5466) from the code: 

#ifdef EXTENDED_GLOB
      /* Parse a ksh-style extended pattern matching specification. */

bash parses a whole line before running it (§09), so on one line shopt runs too late: that is the syntax error near ( shown in §01. On two lines the script runs and prints @(a|b); no file matches. bash -n rejects even the two-line form with rc=2, because -n never executes shopt; bash -O extglob -n accepts it (lab/results/tricky.txt; reproduced with /usr/bin/bash 5.3.9) measured here. A syntax check that does not run the script cannot know which language the script is written in reconstruction.

04Is it a keyword? Classifying a word

The grammar sees WORD, ASSIGNMENT_WORD, NUMBER, REDIR_WORD and 22 keyword tokens. Which one a word becomes is decided in C at the end of read_token_word, in a fixed order, each step a POSIX rule that the yacc listing hands back to the lexer. A keyword is a word in command position, nothing more.

The order

When a word ends at an unquoted break character, control reaches got_token. The checks are bash/parse.y:5742-5772, with its five comments trimmed from the code:

    {

      return result;

NUMBER and the special cases

An all-digit word is a NUMBER only if the character that ended it is < or >, or the previous token was LESS_AND or GREATER_AND (bash/parse.y:5727-5740). The comment above says "a `<', or a `&'"; the code tests the two tokens, and the code wins from the code. One line shows all three cases:

The in of a case sets PST_CASEPAT; while it is set, CHECK_FOR_RESERVED_WORD accepts only esac. esac is not a keyword after | (rule 4) or after (, which the code comments as "phantom Posix grammar rule 4" (bash/parse.y:3181-3184) from the code, added on 2/19/2021 (bash/CWRU/changelog:461-466) from the docs. Right after in it is always ESAC measured here:

POSIX's pattern_list applies rule 4 to the first pattern word only (XCU §2.10.2) from the docs, so bash is right and brush, which accepts it, is wrong (§13).

Reserved words are a position

CHECK_FOR_RESERVED_WORD (bash/parse.y:3166-3209) matches only a word with no $ and no quoting, where reserved_word_acceptable holds for the previous token. That is the lexer's oracle for command position: a switch of 34 case labels whose default: ignores its argument and reads globals, for a WORD after function or coproc (bash/parse.y:5896-5947) from the code. ARITH_CMD and COND_END joined the list on 2/16/2021 (bash/CWRU/changelog:441-447) from the docs. A match writes state: case sets PST_CASESTMT, esac clears it with PST_CASEPAT, [[ sets PST_CONDCMD. word_token_alist holds 22 words: POSIX's 16 plus select, function, time, [[, ]] and coproc (bash/parse.y:2353-2387).

05Aliases are text pushed back into the lexer

bash expands an alias by pushing its value back into the lexer's input and lexing it again as source text. So an alias can hold half an if, an unclosed quote or a lone {, an alias defined on a line misses that line, and no other parser reproduces bash exactly.

Ramey: "The bash parser implements aliasing completely in the lexical phase, though the parser has to inform the analyzer when alias expansion is permitted" (aosabook.org/en/v1/bash.html, §3.4) from the docs.

Push, re-read, pop

The check runs at every word end (§04). alias_expand_token is bash/parse.y:3248-3282, with the 8-line OLD_ALIAS_HACK comment block marked … from the code: 

static int

{
  char *expanded;
  alias_t *ap;

  if ((parser_state & PST_ALEXPNEXT) || assignment_acceptable (last_read_token))
    {
      ap = find_alias (tokstr);

      /* Currently expanding this token. */
      if (ap && (ap->flags & AL_BEINGEXPANDED))
	return (NO_EXPANSION);
      …
      expanded = ap ? mk_alexpansion (ap->value) : (char *)NULL;

	{
	  push_string (expanded, ap->flags & AL_EXPANDNEXT, ap);

push_string saves shell_input_line and its index on pushed_string_list, marks the alias AL_BEINGEXPANDED and makes the value the current line (bash/parse.y:2018-2076). 08The Bison grammar and the COMMAND tree

With the context work done in the lexer, the grammar that remains is small and has no unresolved conflicts. Precedence declarations, not one nonterminal per level, decide the shape of lists and pipelines. The tree is a C tagged union whose words are still unparsed text, and a printer turns any tree back into source, showing what the tree dropped.

The tables

The checked-in y.tab.c is GNU Bison 3.8.2 output with YYNTOKENS 63, YYNNTS 40, YYNRULES 180 (counting $accept) and YYNSTATES 358 (bash/y.tab.c:1037-1048) from the code. The 63 terminals are 3 specials, 11 character literals and 49 names: 48 on %token lines plus yacc_EOF, which enters only through %left (bash/parse.y:389-406, 430) from the code.

Reading those numbers needs three terms. A state is a set of items: rules with a dot marking how much of the right-hand side is already on the stack. The table maps each state and lookahead token to shift, reduce by a numbered rule, or error. A shift/reduce conflict is a state where one lookahead allows both. Bison compares the rule's precedence with the token's, as declared by %left or %right; on a tie the associativity decides, and where either has no precedence "the default is to shift" and the conflict is reported (Bison 3.8.2 manual, §5.2 "Shift/Reduce Conflicts", §5.3.5 "How Precedence Works") from the docs.

lab/scripts/e3_bison.sh rebuilt the parser with bison 3.8.2 in 0.53 s, one run on the shared 2-vCPU lab VM. The result differs from the shipped file in 0 lines outside #line directives. Bison reports no unresolved conflicts, and 45 shift/reduce conflicts resolved by %left/%right (lab/results/e3-bison.txt) measured here. So bash-2.0's "all 66 shift-reduce conflicts are gone" (bash/NEWS:2728-2729) means unresolved ones from the docs.

Precedence instead of levels

Three lines of bash/parse.y, 428-432, settle every list and pipeline from the code: 

%start inputunit

%left '&' ';' '\n' yacc_EOF
%left AND_AND OR_OR
%right '|' BAR_AND

The list rules are ambiguous binary recursions. The top-level ones, as numbered in Bison's report (lab/build/e3/parse.output, Grammar section), are measured here: 

  163 simple_list1: simple_list1 AND_AND newline_list simple_list1

09One unit at a time: reading, running, failing

bash never holds a tree for a whole script. reader_loop parses one inputunit, executes it, disposes it and reads on. A unit is one line, extended only as far as an open construct needs. That one fact explains four behaviours: earlier lines run before a later syntax error is found, PS2 is printed from inside the lexer, an error drops a whole line, and bash -c returns 127 for a broken $( ).

The loop

reader_loop sets a setjmp target, calls read_command, takes global_command, runs execute_command, then dispose_command, and repeats until EOF_Reached (bash/eval.c:61-211). parse_command calls yyparse (bash/eval.c:338-423) from the code. The grammar decides how much one call takes. simple_list admits no significant newline, so a top-level unit ends at the end of its line. && and || may be followed by a newline; ; and & may not (bash/parse.y:1334-1339, 1390-1405) from the code.

bash -n is the same loop with one branch swapped. In bash/eval.c:147-153, when read_but_dont_execute is set in a non-interactive shell, the parsed unit goes straight to dispose_command from the code: 

      if (read_command () == 0)
	{
	  if (interactive_shell == 0 && read_but_dont_execute)
	    {
	      set_exit_status (last_command_exit_value);
	      dispose_command (global_command);
	      global_command = (COMMAND *)NULL;

bash -c takes another route to the same alternation. With ONESHOT, main calls run_one_command, which calls parse_and_execute on the string; that function loops parse_command and execute_command_internal (bash/shell.c:766-768, 1483; bash/builtins/evalstring.c:567-568) from the code. The rationale defends it: "It makes it possible to create self-extracting tarballs" (XRAT §C.2.3, Defect 1055) from the docs. brush parses the whole file first and refuses to run any of it (lab/results/tricky.txt) measured here; §12 has the details.

10Expansion is a second parser

yyparse stops at words. A WORD_DESC reaches the executor spelled as it was in the source, quotes and dollar signs intact. subst.c parses each word again, character by character, every time the command runs. It is a second tokenizer with its own matchers for ${ } and $( ), and it carries quoting through splitting and globbing as marker bytes inside the string. Quote removal is a function that strips them.

Where, and in what order

execute_simple_command calls expand_words on each execution (bash/execute_cmd.c:4605-4617). The work happens in expand_word_list_internal, and its order is fixed in code (bash/subst.c:13219-13279): copy the list; separate the leading assignments; brace expansion; shell_expand_word_list, which is one pass of tilde, parameter, arithmetic, command and process substitution followed by splitting; then glob_expand_word_list, or dequote_list when globbing is off; the assignments last from the code. The manual lists the same stages (bash/doc/bash.1:3372-3384). POSIX has no brace step and says quote removal "shall always be performed last" (XCU §2.6). AOSA calls the expansions "a small pipeline unto themselves" (§3.5.5) from the docs.

In the running example, expand_words receives [LC_ALL=C] [sort] [-u] and returns [sort] [-u] (lab/results/trace-a.txt, lines 367-368) measured here. The assignment is held back and performed after the other words expand, into the temporary environment because a command word remains (bash/subst.c:13270-13273) from the code.

A tokenizer that runs at execution

expand_word_internal (bash/subst.c:11229) is a switch on each character: '\0', CTLESC, < and >, [, =, :, ~, $, backquote, backslash, double and single quote, space (cases at 11331-11933). It returns a list of zero, one or many words from the code. The lexer only brace-matched ${…} (bash/parse.y:5506-5513). The operators inside are parsed here: parameter_brace_expand calls extract_dollar_brace_string, a third } matcher beside the lexer's (bash/subst.c:9865-9893, 10150) from the code.

Brace expansion runs first. The manual says it "is strictly textual" (bash/doc/bash.1:3444-3450) from the docs. The code is not. brace_gobbler lexes quotes, and on $( it calls extract_command_subst, which reaches the yacc parser through xparse_dolparen, to skip over the substitution (bash/braces.c:679-760) from the code. The code wins, and both sides of that are visible: 

$ echo {a,$(echo x,y)}
a x,y
$ n=3; echo {1..$n}
{1..3}

The comma inside $( ) is not a separator, so the result is two words. {1..$n} is not a sequence, because $n is still text when braces run measured here (/usr/bin/bash 5.3.9).

Data cannot pose as a marker, because the lexer escapes a literal \001 or \177 with an extra CTLESC (bash/parse.y:5694-5700) from the code.

11Parsers that run on data: arithmetic, [[ ]], eval, imports

Some of bash's parsers run on run-time strings, not on the script. expr.c parses a variable's value as an expression, and a subscript inside that value gets full word expansion: data becomes code. eval, source, traps and function import share one parse-one-run-one loop. Shellshock was that loop run on environment text.

Arithmetic evaluates while it parses

expr.c is recursive descent with one C function per precedence level, expcomma down to exp0 (bash/expr.c:214-229), over intmax_t with "no checking for overflow" (21-23). It builds no tree. Each level returns a value. A skipped operand is still parsed, under a file-static noeval counter that suppresses assignment, lookup and division by zero (179, 630-703) from the code.

12Six other ways to write a shell parser

Every shell parser answers two questions. Who owns the lexer's context? When is each sub-language parsed: $( ), arithmetic, ${ }, here-doc bodies, aliases? Bash answers shared globals, and late, as text. The answers predict what each parser accepts and costs (§13).

Lineage

Thompson's V6 shell read a whole line into words, then parsed (Research-V6:usr/source/s2/sh.c:152-163) from the code: the last clean lex-then-parse split. Nothing depended on position; if and goto were separate programs from the docs (Wikipedia, "Thompson shell"). Bourne's V7 sh (version string 1978-11-06) is recursive descent in C, dressed as ALGOL 68 by mac.h. term() does reserv++, and word() checks keywords only while reserv is set, clearing it after every token (Research-V7:usr/src/cmd/sh/word.c:45-67, cmd.c:128-142). comsubst() parsed backquoted text during expansion (macro.c:168-185) from the code. Tom Duff wrote that "nobody really knows what the Bourne shell's grammar is", because its routines "all have a flag argument that subtly changes their operation" (doc.cat-v.org/plan_9/4th_edition/papers/rc). KornShell contributed $( ), (( )), [[ ]] and ;&. POSIX.2 published the first grammar in 1992 (XRAT §C.2.6.4, §C.2.9.4; bash/POSIX:12-19) from the docs. Figure 14 places the six beside bash and V7.

dash: a flag channel

dash keeps the V7 shape: one C function per level, list, andor, pipeline, command, simplecmd (dash src/parser.c:116-120, master 49f04dd). Before each readtoken() the parser sets a three-bit checkkwd, CHKALIAS|CHKKWD|CHKNL, keyword before alias (src/parser.h:72-74; src/parser.c:181-182). Unlike bash, it parses $( ) with a recursive list(2) at lex time and keeps the tree (src/parser.c:1523-1636) from the code. It is the fastest parser measured, 0.054 s for 100,000 lines, peak RSS flat at 1.7-2.5 MiB. It accepts 101 of 148 tricky inputs, rejecting mostly bash extensions measured here.

OSH's lexer stores no mode. The caller passes it on every call (oils/frontend/lexer.py:336-349, the first 14 lines of Read):

ShellCheck: no lexer at all

ShellCheck's parser is one 3,673-line Haskell module over ParsecT String, with no token stream. Parsec is a parser-combinator library: each grammar rule is a Haskell function that consumes characters, and rules compose by sequence and alternative (shellcheck/src/ShellCheck/Parser.hs:56-57). The linefeed combinator itself reads pending here-doc bodies (60-66). Ambiguity is resolved by backtracking: readAmbiguous tries the expected parse, then the alternative, and notes SC1102 or SC1105 if it won (1689-1700; the notes at 1637, 2882). The undecidable a[k] is re-parsed after the fact, as a string key if a declare -A (or local, typeset) of the name appears anywhere in the file (3558-3602; ASTLib.hs:630-649). A real syntax error yields no AST (prRoot = Nothing), only SC1072, SC1073 and SC1009 (3494-3556) from the code. Linting 100,000 lines takes 121.8 s and 1,855 MiB measured here.

tree-sitter-bash: the generated parser asks the lexer

A 1,201-line grammar.js generates a 350,631-line parser.c with STATE_COUNT 7571 (tree-sitter-bash/src/parser.c:17-24). tree-sitter generates GLR tables, generalized LR: where the grammar declares a conflict, the parser forks and runs both readings until one dies. bash's grammar declares six, among them [$.command, $.variable_assignments] (grammar.js:47-54). The generated lexer looks only for tokens valid in the current state. The rest goes to a 1,217-line external scanner handed a valid_symbols mask: here-doc pieces, _concat, variable_name, regexes, extglobs (src/scanner.c:9-39). For incremental reparsing its here-doc stack must serialize into at most 1,024 bytes each time the scanner recognises a token (src/tree_sitter/parser.h:14; scanner.c:87-155) from the code. Error recovery always yields a tree, with ERROR nodes. It accepts 8 inputs bash -n rejects, including echo a; }, and rejects 21 that bash accepts measured here.

brush: tokenize everything, then PEG

brush's tokenizer knows no grammar and emits only Operator and Word tokens (brush/brush-parser/src/tokenizer.rs:45-50) and reorders the stream so each here-doc body follows its tag (513-648). A peg 0.8.6 grammar whose rules mirror POSIX §2.10 then backtracks over the tokens: compound_command tries arithmetic_command before subshell, and an unmatched ) means "we need to backtrack" (src/parser/peg.rs:97-130). Words, arithmetic and comsub bodies stay strings until expansion. Parsing the whole file first, brush forces extglob on (brush-core/src/shell.rs:241-244) and expands aliases at execution, "a total hack" (src/interp.rs:1243) from the code. A syntax error after exit 0 makes brush run nothing; bash, dash and OSH run up to the exit. 100,000 lines take 0.865 s and 241.9 MiB, ~2.5 KiB a line measured here.

13Where they disagree, and what it costs

On 148 tricky inputs the parsers disagree where a parser must decide when to parse. Late textual parsing makes bash -n accept what static parsers reject. A lexer that reads run-time state makes it reject what runs. Here-documents diverge most. Cost follows the same architecture: parse-one-run-one stays flat, whole-file trees grow linearly, a linter pays two orders of magnitude.

14Writing your own

The implementations amount to a decision list, and each decision has a measured cost. What you build fixes most answers. A shell that executes must match bash's late parsing and its one-command loop. A formatter, linter or editor wants a typed tree of the whole file, and pays in memory and in the inputs where bash defers reconstruction. Figure 18 is the list; each paragraph below cites the evidence.

1. Decide when each sub-language is parsed. Eager typed trees catch $(( 1 + )) statically; bash -n does not (§13). But POSIX says $(( is a command substitution when arithmetic cannot parse it (XCU §2.6.3) from the docs, and only bash and brush accept G72 below, which bash runs as hi there; dash, shfmt, OSH, ShellCheck and tree-sitter reject it measured here. Parse eagerly for a tool, but keep each substitution's source text so a fallback stays possible (§07) reconstruction.

2. Decide who owns lexer context, and make it explicit. bash's lexer and grammar actions share globals (§03). OSH passes the mode into Read(lex_mode) and the lexer stores none (oils/frontend/lexer.py:336-363); mvdan's parser sets p.quote; tree-sitter's scanner receives a valid_symbols mask from the code. Any of these lets a test drive the lexer directly reconstruction. It is also the coupling behind Ramey's hand-written-parser regret, quoted in §01.

3. Model here-docs as a FIFO drained at the next newline token. Every working implementation converged on it (§06, §12). Oils got there after retracting a tree walk (§06). tree-sitter keeps the body inside one redirect node, so two bodies on one line, G46, are an ERROR measured here.

4. Handle (( and $(( on purpose. OSH scans the rest of the line with LookAheadDParens for ((; brush backtracks by ordered choice (brush/brush-parser/src/parser/peg.rs:97-130) from the code. Or refuse, and document it, as mvdan's README does, to keep streaming over an io.Reader (§12).

5. Choose an alias policy. Compatibility needs text pushed back inside the lexer: push_string saves the current line and makes the alias text the line (bash/parse.y:2018-2076) from the code. OSH re-parses a built string and cannot do { aliases; brush substitutes at run time, by its own comment a hack (§12). Approximate, and list the failures (§05).

6. If you execute, parse one complete command at a time. POSIX requires it (XCU §2.3, quoted in §09), and it is what lets an alias or shopt on one line change how the next is lexed (§03, §05) reconstruction. Memory stays flat (§13). brush parses whole files, so it forces extglob on "because we parse the entire script with the same settings" (brush-core/src/shell.rs:241-244) from the code.

7. Keep source positions and a printer. A printer gives idempotence tests: bash's is idempotent on all 118 printable inputs, shfmt on 110 of 111 measured here. It also shows what the tree drops (§08). OSH goes further: "the source text can be reconstructed byte-for-byte from this tree" (oils/frontend/syntax.asdl:1-4) from the code.

8. Test differentially against real bash. brush runs 3,209 YAML cases with bash as oracle, 718 marked known_failure. mvdan's syntax tests "confirm parses against bash 5.3, dash, mksh R59, and zsh 5.9" (sh/CLAUDE.md:65) from the docs. OSH's spec suite has 223 files and 3,968 cases, and at least one BUG-bash annotation is stale for 5.3.9 (oils/spec/alias.test.sh:467-478) measured here. Re-run the oracle.

A build order

The decisions fix a shape. Here is one buildable order for a parser meant to execute scripts and also serve tools, assembled from the mechanisms above; each step names what it copies reconstruction.

  1. A line reader with a push-back stack. Hand out one physical line at a time, delete backslash-newline before any token exists, and serve pushed strings before the next refill, as bash's pushed_string_list does for alias text (§02, §05). Record line and column per byte now; positions added later touch every token.
  2. A lexer that stores no mode. The caller passes the mode and gets one token with its span, as in OSH's Read(lex_mode). Start with modes for command words, double-quoted text, arithmetic, here-doc bodies, case patterns and [[ ]]; OSH has 22 at efaa863, so expect the list to grow (§12). Operators are longest match with up to two characters of lookahead, for <<-, <<<, &>> and ;;& (§03).
  3. A recursive-descent command parser. One function per POSIX level, and_or, pipeline, command, simple_command (XCU §2.10.2), as in dash. The parser decides keyword status: a keyword is a plain word it interprets only where a keyword may stand, mvdan/sh's gotStmtPipe and the effect of dash's checkkwd (§12). Assignments, NUMBER and {fd} are tests on the word and the character after it (§04).
  4. A here-doc queue. On <<, append a record with the delimiter and whether any of it was quoted. When the lexer is about to return a newline token, read every pending body raw, in order, ending each on an exact delimiter line (§06). Decide now what an unterminated body is: bash warns, five of the six others reject (§13).
  5. A word parser that recurses. A word is a list of typed parts: literal, quoted, parameter, ${…}, $( ), $(( )), backquote. On $(, call the command parser on the same lexer with ) as its end token, as OSH does, instead of saving globals the way save_parser_state must (§07, §12). On $((, try arithmetic and, if it fails, rewind and parse a command substitution, as XCU §2.6.3 asks and G72 tests. The rewind needs the input buffered back to $((; mvdan/sh refuses the case to stay streaming. Keep every part's source span.
  6. A driver with two loops. To execute: parse one complete command, run it, free it, read on, so an alias or shopt -s extglob takes effect on the next line and memory stays flat (§09, §13). For tools: the same call looped to end of file, collecting the list; then aliases need a policy (§05) and extglob can be forced on, as brush does.
  7. A printer and two oracles. Print any tree back to source and check that printing the re-parse gives the same text, as E3 did for bash (§08). Diff accept/reject against bash -n and against a real run, as E1 did; the two disagree on eight inputs (§13). Start from the ten below.

The four breaks, answered

§01 named four places where "lex the file, then parse the tokens" breaks. Each is one of the decisions above. Keyword status by position is decision 2: bash answers it with shared globals written from 74 sites (§03); the others use a parser-set field, a mode argument, a valid-symbol mask or backtracking. Here-doc bodies as a second mode are decision 3, and every implementation but one converged on the same queue. Nested parsing to find a word's end is decisions 1 and 4: bash parses a $( ) up to three times and keeps only text (§07); the typed-tree parsers parse it once and lose the $(( fallback that G72 needs. Parsing interleaved with running is decision 6: the flat 3.6–5.5 MiB of bash -n and the same-line alias miss are one fact seen twice (§09, §13). Most of the 69 disagreement rows in Figure 16 are a place where another parser answered one of these four questions differently reconstruction. So a new shell parser picks its four answers first, from what it is for, and its parsing algorithm second.
