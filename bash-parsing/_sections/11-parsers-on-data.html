{{S}}Parsers that run on data: arithmetic, [[ ]], eval, imports

Some of bash's parsers run on run-time strings, not on the script. expr.c parses a variable's value as an expression, and a subscript inside that value gets full word expansion: data becomes code. eval, source, traps and function import share one parse-one-run-one loop. Shellshock was that loop run on environment text.

Arithmetic evaluates while it parses

expr.c is recursive descent with one C function per precedence level, expcomma down to exp0 (bash/expr.c:214-229), over intmax_t with "no checking for overflow" (21-23). It builds no tree. Each level returns a value. A skipped operand is still parsed, under a file-static noeval counter that suppresses assignment, lookup and division by zero (179, 630-703) from the code. 

$ echo $(( 0 && 1/0 ))
0
$ echo $(( 2 ** 3 ** 2 )) $(( -2 ** 2 ))
512 4

** is right-associative and binds looser than unary minus measured here (/usr/bin/bash 5.3.9). When readtok meets a name not followed by =, it calls expr_streval, which fetches the value and parses it (bash/expr.c:1227-1241; 13 lines omitted): 

  value = (e == ']') ? get_array_value (tok, aflag, &es) : get_variable_value (v);
  ...
  tval = (value && *value) ? subexpr (value) : 0;

Recursion stops at MAX_EXPR_RECURSION_LEVEL, 1024 (101-104) from the code. The value itself is not word-expanded measured here: 

$ x=x; echo $((x))
bash: x: expression recursion level exceeded (error token is "x")
$ c='$(echo 3)'; echo $((c))
bash: $(echo 3): arithmetic syntax error: operand expected (error token is "$(echo 3)")

A subscript inside the value is. array_expand_index calls expand_arith_string, full word expansion, before evalexp (bash/arrayfunc.c:1366-1376) from the code. Figure {{fig-data-to-code}} follows the path.

Two defences exist, and neither covers the value path. Since 5.2, expand_array_subscript expands a subscript written in the expression once and backslash-quotes the result (bash/subst.c:11102-11150, 11393-11405). The option array_expand_once sets AV_NOEXPAND only when the caller passed EXP_EXPANDED (bash/expr.c:425, 1171), and at the default compat level only let passes it (bash/builtins/let.def:102) from the code. The manual says it "suppresses multiple evaluation of associative and indexed array subscripts during arithmetic expression evaluation" (bash/doc/bash.1:11843-11851) from the docs. The code wins. test demands a plain integer first (bash/test.c:357-379). OSH disallows command substitution in dynamic arithmetic by default (oils/doc/known-differences.md:41-60) from the docs; brush fails to parse the value measured here.

[[ ]] at run time

cond_expand_word never splits. It dequotes the left side and passes the right side of == or =~ through quote_string_for_globbing, so quoted parts become escaped literals (bash/subst.c:4077-4124). Pattern matching forces extended_glob = 1 around the call (bash/execute_cmd.c:4109-4111) from the code. 

$ x="a*"; [[ abc == $x ]] && echo match; [[ abc == "$x" ]] || echo no-match
match
no-match
$ set -x; [[ $x == "$x"* ]]
+ [[ a* == a\** ]]

The trace shows the pattern as the matcher sees it: a literal a*, then a live * measured here.

One loop for every string

parse_and_execute parses one command, runs it and repeats (bash/builtins/evalstring.c:359, 451, 567-569). -c, eval, source, traps, PROMPT_COMMAND, comsub children and function import differ only in SEVAL_* flags (bash/builtins/common.h:44-55) from the code. The consequences are §09's rules applied to strings. An alias defined inside an eval string misses the rest of that line, exit 127, as in §05's last row; split by a newline, the string prints e3-ran. A trap string is parsed only when it fires measured here: 

$ trap "echo ok; if" EXIT; echo defined
defined
bash: exit trap: line 2: syntax error: unexpected end of file from `if' command on line 1

The definition succeeds; the syntax error surfaces at exit.

Shellshock: the loop run on environment text

Before 2014 the importer pasted name onto any environment value starting () { and called parse_and_execute with SEVAL_NONINT|SEVAL_NOHIST. The loop did its job: it ran the definition, then whatever followed it. Three patches closed it (ftp.gnu.org/gnu/bash/bash-4.3-patches/): bash43-025 added SEVAL_FUNCDEF|SEVAL_ONECMD, bash43-027 moved imports into BASH_FUNC_name%% variables, and bash43-030 added the remaining-input test from the docs. Today the parser is the validator, before anything runs (bash/builtins/evalstring.c:465-478, a five-line comment trimmed): 

	      if (flags & SEVAL_FUNCDEF)
		{
		  char *x;

		  if (command->type != cm_function_def ||
		      ((x = parser_remaining_input ()) && *x) ||
		      (STREQ (from_file, command->value.Function_def->name->word) == 0))
		    {
		      internal_warning (_("%s: ignoring function definition attempt"), from_file);

parser_remaining_input returns the unread tail of shell_input_line (bash/parse.y:2976-2983) from the code. On 5.3.9 the classic probe prints only probe-done measured here: 

$ env 'x=() { :;}; echo VULN' bash -c 'echo probe-done'
probe-done

The value it parses is not the user's text: export -f writes bash's re-printed body (bash/variables.c:4720-4746), two spaces after the brace, so the importer parses printer output measured here. POSIX left exported functions out: "There are numerous security problems associated with functions appearing in the environment" (XRAT §C.2.9.5) from the docs. Bash kept export -f; it still works.
