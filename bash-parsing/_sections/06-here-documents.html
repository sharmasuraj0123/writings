{{S}}Here-documents: a queue drained at the newline

Here-document bodies are not tokens and not grammar. bash queues the redirect when the grammar reduces << WORD, and reads the bodies raw, in order, when the lexer is about to hand the parser the next unquoted newline. Every working implementation converged on that FIFO. The edge cases are where they diverge.

Queued at the reduce, drained at the newline

Only the << and <<- productions call push_heredoc; here-strings do not (bash/parse.y:622-681). push_heredoc appends the REDIRECT to redir_stack, which holds HEREDOC_MAX = 16 entries (bash/shell.h:172). The 17th is a fatal syntax error that calls exit_shell (bash/parse.y:3106-3117) from the code. Seventeen cat <<En; on one line print "maximum here-document count exceeded" and exit 2 measured here. gather_here_documents walks the stack from index 0 and calls make_here_document on each entry with PST_HEREDOC set (bash/parse.y:3120-3136). Its main caller is read_token, just before it returns a newline (bash/parse.y:3646-3651) from the code: 

  if MBTEST(character == '\n')
    {
      /* If we're about to return an unquoted newline, we can go and collect
	 the text of any pending here document. */
      if (need_here_doc)
	gather_here_documents ();

Backstops: the compound_list and simple_list actions (bash/parse.y:1265-1266, 1343-1344, 1362, 1377), and so do parse_comsub (4566) and parse_command after yyparse returns (bash/eval.c:371-372) from the code. Trace (c) shows which fires first. Rule 26 reduces LESS_LESS WORD; the next token, ';', shows need_here_doc=1 on line 1, no body read. Inside the $( ) the count reads 0 (§07 owns that save). After the comsub word, read_token gathers before returning the outer newline (lab/results/trace-c.txt, lines 337-338) measured here: 

LAB HEREDOC gather_here_documents need_here_doc=1 line=1
LAB LEX tok='\n'(10) last_read_token=WORD token_before_that=WORD two_tokens_ago=';'
        parser_state=0x0{} need_here_doc=0 line=3

(The second line is wrapped.) The line counter jumps from 1 to 3 between them: the parser gets '\n' only after both body lines are consumed. Figure {{fig-heredoc-timeline}} lays this out.

Reading a body

read_secondary_line points the prompt at PS2 and calls read_a_line, which takes characters from yy_getc directly. The line buffer of §02 is bypassed (bash/parse.y:2197-2345). Any quoting in the delimiter clears expansion: delim_unquoted tests W_QUOTED (bash/make_cmd.c:533), so E"N"D counts as quoted. <<- strips leading tabs only. The terminator must match exactly and be followed by a newline (bash/make_cmd.c:587-603) from the code. So EOFX, and EOF with two trailing spaces, are body text; bash 5.3.9 prints both back measured here. Running to end of file is a warning (bash/make_cmd.c:626-627), and POSIX permits that. The shell "should, but need not, treat this as a redirection error" (XCU §2.7.4). POSIX frames bodies as a second "major mode": "one or more of the subsequent lines immediately following the next NEWLINE token form the body" (XCU §2.3) from the docs.

The EOF) branch

One compatibility branch survives in the body loop, bash/make_cmd.c:605-611 from the code: 

      /* Backwards compatibility here */
      if (STREQN (line, redir_word, redir_len) && (parser_state & PST_EOFTOKEN) && shell_eof_token && strchr (line+redir_len, shell_eof_token))
	{
	  shell_ungets (line + redir_len);
	  full_line = 0;
	  break;
	}

Inside $( ), shell_eof_token is ')' (§07); a line starting with the delimiter and containing it ends the body. The rest is pushed back with shell_ungets, whose only caller is this branch (bash/parse.y:2924-2973). Setting full_line = 0 breaks the loop and also trips the end-of-file warning at line 626. bash CHANGES for 5.1 reads "Changed here-document parsing to no longer allow the end of the here document to delimit a command substitution" (bash/CHANGES:1812-1813) from the docs. The code still accepts it: the entry did not remove the form. On 5.3.9 measured here: 

x=$(cat <<EOF ⏎ hi ⏎ EOF) ; echo "[$x]"
  → warning: here-document at line 1 delimited by end-of-file (wanted `EOF')
  → [hi]
echo "[$(cat <<EOF)]" ⏎ hi ⏎ EOF
  → warning: command substitution: 1 unterminated here-document
  → [hi]

The second case is the parse_comsub backstop: bodies still pending when the inner parse ends are read from the outer input (bash/parse.y:4563-4567) from the code.

One algorithm, different edges

mvdan/sh keeps a FIFO and drains it when its lexer emits a newline (sh/syntax/parser.go:779-815). OSH fills a pending list at the next Op_Newline (oils/osh/cmd_parse.py:660-686). ShellCheck reads bodies inside its linefeed combinator (shellcheck/src/ShellCheck/Parser.hs:60-66). brush's tokenizer reorders tokens so each body follows its tag (brush/brush-parser/src/tokenizer.rs:513-648). tree-sitter's generated parser hands context-sensitive tokens to a hand-written C hook, its external scanner (§12); that scanner keeps a stack of pending tags and ends a body on a prefix match. Its heredoc_redirect rule swallows the rest of the line, so two here-docs on one line have no derivation (tree-sitter-bash/src/scanner.c:226-244, grammar.js:542-557) from the code. OSH got there after Andy Chu retracted a 2016 tree walk: "In retrospect, this is the obvious algorithm. I was being too clever." (oilshell.org/blog/2017/11/28.html) from the docs.

On EOF with two trailing spaces, bash keeps reading body text. OSH 0.38.0 ends the body there and runs the next EOF as a command. ShellCheck v0.11.0 ends it with SC1118, and brush rejects the script. tree-sitter rejects both two-on-a-line forms (E1 rows hd02, hd03) measured here (lab/results/e1-matrix.csv). Unterminated bodies and the other here-doc rows are in §13, where they form the largest group of disagreements.
