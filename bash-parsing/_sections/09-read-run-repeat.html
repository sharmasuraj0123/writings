{{S}}One unit at a time: reading, running, failing

bash never holds a tree for a whole script. reader_loop parses one inputunit, executes it, disposes it and reads on. A unit is one line, extended only as far as an open construct needs. That one fact explains four behaviours: earlier lines run before a later syntax error is found, PS2 is printed from inside the lexer, an error drops a whole line, and bash -c returns 127 for a broken $( ).

The loop

reader_loop sets a setjmp target, calls read_command, takes global_command, runs execute_command, then dispose_command, and repeats until EOF_Reached (bash/eval.c:61-211). parse_command calls yyparse (bash/eval.c:338-423) from the code. The grammar decides how much one call takes. simple_list admits no significant newline, so a top-level unit ends at the end of its line. && and || may be followed by a newline; ; and & may not (bash/parse.y:1334-1339, 1390-1405) from the code.

bash -n is the same loop with one branch swapped. In bash/eval.c:147-153, when read_but_dont_execute is set in a non-interactive shell, the parsed unit goes straight to dispose_command from the code: 

      if (read_command () == 0)
	{
	  if (interactive_shell == 0 && read_but_dont_execute)
	    {
	      set_exit_status (last_command_exit_value);
	      dispose_command (global_command);
	      global_command = (COMMAND *)NULL;

bash -c takes another route to the same alternation. With ONESHOT, main calls run_one_command, which calls parse_and_execute on the string; that function loops parse_command and execute_command_internal (bash/shell.c:766-768, 1483; bash/builtins/evalstring.c:567-568) from the code. Figure {{fig-reader-loop}} draws both.

Lines run before the error is found

A four-line file (echo line1, echo line2, if then, echo line4) prints line1 and line2, then "line 3: syntax error near unexpected token `then'", and exits 2. Line 4 is never parsed. One line is all or nothing: 

$ /usr/bin/bash -c 'echo a; fi; echo b'
/usr/bin/bash: -c: line 1: syntax error near unexpected token `fi'
/usr/bin/bash: -c: line 1: `echo a; fi; echo b'

a never prints measured here (/usr/bin/bash 5.3.9). The non-interactive parse error sets EOF_Reached (bash/eval.c:200-205) from the code. POSIX Issue 8 states this model normatively: a complete_command "shall be executed before the next complete_command is tokenized and parsed" (XCU §2.3). The rationale defends it: "It makes it possible to create self-extracting tarballs" (XRAT §C.2.3, Defect 1055) from the docs. brush parses the whole file first and refuses to run any of it (lab/results/tricky.txt) measured here; §12 has the details.

Running the example

Trace (a) shows what happens between the parse and the dispose (lab/results/trace-a.txt, lines 360-375), from an instrumented bash@9c46586. execute_command_internal switches on cm_connection and calls execute_connection for &&. The left side runs through execute_command with CMD_IGNORE_RETURN set (bash/execute_cmd.c:2943). A second execute_connection for '|' calls execute_pipeline, which makes one pipe per element: sort gets pipe_out=4, head pipe_in=3. In a pipeline, execute_simple_command forks before expand_words. Its comment (bash/execute_cmd.c:4524-4529) says this "keeps assignment statements from affecting the parent shell's environment when they should not" from the code. The expand_words lines carry child pids 263969 and 263970, not the shell's 263968. The child sets CMD_NO_FORK, so execute_disk_command execs in place with cmdflags=0x48. echo done runs as a builtin in pid 263968 measured here.

PS2 comes from the lexer

An interactive shell prompts only at a command boundary when SHOULD_PROMPT() holds (bash/parse.y:3057-3073), and prompt_again points later lines at PS2 (bash/parse.y:6143-6183) from the code. lab/scripts/trace/pty_interactive.py drives a pty with --noediting. After for i in 1 2 and a newline, the LR stack in lab/results/trace-interactive.txt reads: 

Stack now 0 4 66 151 218 255 295 318
Reading a token

LAB PROMPT print_prompt() called from shell_getc, current_prompt_string=PS2

State 318 is the for_command item with the dot just before DO. The lexer printed the prompt while fetching bytes for the next token measured here. yyparse never returned.

Errors

yyerror reports unless PST_NOERROR is set, then calls reset_parser, which plants token_to_read = '\n' so the rule error '\n' can match (bash/parse.y:6723-6730, 3493-3539). That rule accepts only in an interactive shell outside parse_and_execute; otherwise it aborts (bash/parse.y:469-515). The status is EX_BADUSAGE 2, or EX_BADSYNTAX 257 inside a builtin running parse_and_execute (bash/parse.y:6842; bash/shell.h:56, 70) from the code.

The 127

lab/scripts/trace/exit127.sh runs each text under -c and as a file. Results in lab/results/trace-exit127-matrix.txt are identical on 5.3.9, the pinned build and the trace build measured here: 

echo $(for)       -c:127  file:2
for)              -c:2    file:2
: ${x?unset}      -c:127  file:1
echo $((1+))      -c:1    file:1

The nested parse in parse_comsub fails with the status already 2 and, in a non-interactive shell, calls jump_to_top_level (FORCE_EOF) (bash/parse.y:4588-4597). Each parse_and_execute level catches it, runs its unwind frame and rethrows (bash/builtins/evalstring.c:395-402). Under -c the catcher is run_one_command (bash/shell.c:1457-1483, the preamble and default case trimmed) from the code: 

  code = setjmp_nosigs (top_level);

  if (code != NOT_JUMPED)
    {
      …
      switch (code)
	{
	  /* Some kind of throw to top_level has occurred. */
	case FORCE_EOF:
	  return last_command_exit_value = 127;
	case ERREXIT:
	case EXITPROG:
	case EXITBLTIN:
	  return last_command_exit_value;
	case DISCARD:
	  return last_command_exit_value = 1;

Any FORCE_EOF becomes a literal 127. For a script, reader_loop takes the same jump at bash/eval.c:104-109, sets EOF_Reached and keeps the 2. run_wordexp does the same (bash/shell.c:1381-1396). A plain -c syntax error never longjmps: parse_and_execute sets EX_BADUSAGE and breaks (bash/builtins/evalstring.c:584-599) from the code. ${x?} throws FORCE_EOF from subst.c (the exact site was not traced); $((1+)) returns an expansion error that bash/subst.c:4296 turns into DISCARD, hence 1 from the code. The manual promises only that bash "exits with a non-zero value" on a syntax error and reserves 127 for a command not found (bash/doc/bash.1:5927-5928, 5943-5945) from the docs. Whether the mapping is deliberate is open.
