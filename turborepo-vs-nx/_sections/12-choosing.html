{{S}}Choosing

Start from the problem, not the tool. Four questions settle almost every case, and the first "yes" decides.

Three cases

A product team, Next.js plus shared packages

20 packages · GitHub Actions · deploys on Vercel

Turborepo. Add turbo.json and the free remote cache, and use --affected in CI. The whole adoption is one afternoon and one file. Revisit if CI time stops falling once the cache is warm.

A platform group, React front ends plus Spring services

300 projects · 40 engineers · Gradle and pnpm

Nx. The Gradle plugin puts both halves in one graph, so nx affected is honest across the language line. Boundaries and nx migrate pay for themselves at this headcount. Price Nx Agents against your current runner bill.

An agent-first lab, many worktrees, small repo

parallel agents · tight CPU · fast inner loop

Turborepo, on today's evidence. A 48 ms no-op check and shared worktree caches suit many agents on small machines. Re-evaluate after Nx's 22 October event, which promises "faster caching, smarter distribution, up to 50% less CI compute".

Already on one, unhappy

migration in either direction

Turborepo to Nx is mostly automated by nx init. Nx to Turborepo is ten manual steps and is cheapest before you adopt inferred targets. Either way, port the cache-key rules first and check them with a deliberate leaf edit, as in §04.
