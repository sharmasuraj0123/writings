01Two pools and a queue

A broker is two thread pools and one queue. One rule, the muted socket, gives every connection one request at a time. Requests that must wait hold no thread, and a timeout undoes nothing. This collection reads Kafka as one append-only log used five times, with each promise a line in such a log. Part 1 read that log on disk. This part follows one request from the socket to the log and back: the threads it crosses, its real bytes, where it waits, and what it can and cannot take back. Part 3 picks up at the line an ack moves.

The class comment in core/…/network/SocketServer.scala:60-70 gives the shape: "1 Acceptor thread per listener", "N Processor threads that each have their own selector", and "M Handler threads that handle requests and produce responses back to the processor threads for writing" from the code. A second fact sits at :99-100: one map of acceptors, but a single RequestChannel. Every listener of a SocketServer drains into one request queue. The same comment opens with "two types of request planes" and then lists one, because control.plane.listener.name is gone (register D14, class C, doc drift; still there at trunk 09f2dc1320, read only).

The network thread

The acceptor assigns each socket round-robin to a processor whose new-connection queue has room, and blocks only if all of them are full (SocketServer.scala:635-637). The queue holds 20 sockets, and at most that many are registered per loop, so new connections cannot starve existing traffic. Accepted sockets are non-blocking, with Nagle off and TCP keepalive on (:689-695). The whole job of a network thread is at SocketServer.scala:871-883 from the code: 

  override def run(): Unit = {
    try {
      while (shouldRun.get()) {
        try {
          // setup any new connections that have been queued up
          configureNewConnections()
          // register any new responses for writing
          processNewResponses()
          poll()
          processCompletedReceives()
          processCompletedSends()
          processDisconnected()
          closeExcessConnections()

A frame is four bytes of size, then a payload. A size above socket.request.max.bytes, 100 MiB by default, is refused before any body is read (clients/…/common/network/NetworkReceive.java:89-96). The lab's oversized header, 104,857,601 bytes, got the socket closed after 4 ms measured here. An optional memory pool, off by default with queued.max.request.bytes=-1, can make that read wait for memory. A frame's buffer allocation then fails softly: the read waits, the selector records out-of-memory, and it unmutes channels when memory returns (Selector.java:691-692).

Parsing happens here, not on a handler. The header is parsed first, and a disabled version throws before any handler sees it. server/…/network/Processor.java:33-42: 

    public static RequestHeader parseRequestHeader(ApiVersionManager apiVersionManager, ByteBuffer buffer) {
        RequestHeader header = RequestHeader.parse(buffer);
        if (apiVersionManager.isApiEnabled(header.apiKey(), header.apiVersion())) {
            return header;
        } else if (header.isApiVersionSupported()) {
            throw new InvalidRequestException("Received request for disabled api with key " + header.apiKey().id + " (" + header.apiKey().name() + ") and version " + header.apiVersion());
        } else {
            throw new UnsupportedVersionException("Received request for api with key " + header.apiKey().id + " (" + header.apiKey().name + ") and unsupported version " + header.apiVersion());
        }
    }

The body follows, because the Request constructor runs parseRequest (server/…/network/Request.java:101). ApiVersions is even peeked at on this thread, to capture the client's software name (KIP-511). Then come the two lines that shape everything else, SocketServer.scala:1019-1021: 

                requestChannel.sendRequest(req)
                selector.mute(connectionId)
                handleChannelMuteEvent(connectionId, ChannelMuteEvent.REQUEST_RECEIVED)

sendRequest is a blocking put on a bounded queue (RequestChannel.scala:76-79; queued.max.requests, default 500). So if handlers fall behind, the network thread blocks, and every connection it owns stalls, including those with nothing to do with the slow work. Parsing and back-pressure share the thread (D59, class D, gotcha). That is read in the code and stated in the config's own doc string, "before blocking the network threads"; it was not measured here, and trunk was not checked.

The handler

A handler blocks up to 300 ms on the queue and charges the wait to the idle meter behind RequestHandlerAvgIdlePercent. It takes callback work first, because those requests "have already waited in line" (RequestChannel.scala:157-163). KafkaApis.handle is one match on the API key, and controller-owned APIs such as CreateTopics are forwarded rather than handled. Responses return through a per-processor deque with a selector wakeup, in five kinds: send, no-op, close, throttle start and throttle end (SocketServer.scala:920-945) from the code.

Two details keep the handlers honest about locks and threads. Finishing a parked operation after an append is not done on the spot. In the words of KafkaApis.scala:262-263, "In order to avoid conflicting locking, the actions to complete delayed requests are kept in a queue", and that queue is drained at the end of handle. And async work that finishes on some other thread is sent back through sendCallbackRequest, so that it runs again on a handler (KafkaRequestHandler.scala:73-83). So the request's path has a simple outline: socket, network thread, queue, handler, and then either a response on the deque or a parked operation.

The Processor comment at SocketServer.scala:770 says it handles requests "from a single connection"; a processor owns many (D15, class C; still at trunk).

02The muted socket

selector.mute is one line, and it decides the shape of the protocol. A muted channel is not read. clients/…/common/network/Selector.java:580-583 from the code: 

                if (channel.ready() && (key.isReadable() || channel.hasBytesBuffered()) && !hasCompletedReceive(channel)
                        && !explicitlyMutedChannels.contains(channel)) {
                    attemptRead(channel);
                }

A second request on that connection is not refused, and is not read either. It stays in the kernel's socket buffer. The channel opens again only when the response has been fully sent, and then only if no throttle is active (SocketServer.scala:1049-1053). So each connection has one request in progress, and its answers come back in order. This is the documented contract, not an accident. docs/design/protocol.md:45: "The broker's request processing allows only a single in-flight request per connection in order to guarantee this ordering", and clients "can send requests even while awaiting responses for preceding requests since the outstanding requests will be buffered in the underlying OS socket buffer".

No thread is involved in that wait. Pipelining is a client's right, but pipelined requests get no parallelism on one socket. The cost shows the moment a request has to wait.

The lab sent a Fetch at the log end, with a 4,000 ms wait, and an ApiVersions right behind it on the same socket. The first response came at 4,004 ms and the second at 4,005 ms. The same ApiVersions on another connection took 2 ms measured here. This is D56, class D, a gotcha confirmed by verification; trunk was not checked.

Routine Java traffic does not do this. The Java consumer fetches with at most one request in flight per node (Part 4 has why). The lower panel of the figure is the exception: the session-closing Fetch went out while an ordinary one was parked, and it waited its turn. Here is that moment in the real frame log. The first column is the connection, and sizes exclude the length prefix. The FindCoordinator and heartbeat requests were filtered out for length, which is why corr 61 shows only its response measured here:

So clients keep several sockets

If one long poll can hold up a socket, a client that also needs to heartbeat cannot share it. The Java consumer gives the group coordinator a connection of its own, through an id string prefixed with + (clients/…/consumer/internals/GroupCoordinatorNode.java:21-34). That is new in 4.4.0; through 4.3 the id was Integer.MAX_VALUE - nodeId. The capture shows it working: Fetch on connection 7, heartbeat and commit on connection 8, same broker measured here.

franz-go goes further, with up to five connections per broker, chosen by request type so that long polls cannot block other traffic. franz-go/pkg/kgo/broker.go:683-700 from the code:

librdkafka adds logical broker handles for its coordinators, each with its own thread. That this means a separate socket is inferred from the code; librdkafka was read, never run.

When there is no response to wait for

acks=0 tests the rule from the other side. There is no response, so nothing would ever unmute the socket. The broker therefore sends an internal NoOpResponse, whose handler comment is plain: "There is no response to send to the client, we need to read more pipelined requests that are sitting in the server's socket buffer" (SocketServer.scala:922-923). And since no frame can carry an error, an error closes the socket (core/…/server/KafkaApis.scala:512-529). The lab saw both paths. An acks=0 Produce to an unknown topic id closed the connection in 9 ms, and on a good send, the next frame on the wire belonged to the following request measured here.

Any exception while turning a frame into a request ends the same way, with a closed connection and no error frame (SocketServer.scala:907-912, :1031-1035). The last section of this part comes back to that.

03One Produce, byte by byte

Here is one real request. A Java kafka-console-producer 4.4.0 sent the record hello-wire with acks=all and no compression, through a logging proxy on loopback. The frame was then decoded by hand, one field at a time, until every byte was accounted for measured here. Figure 3 is all 139 bytes.

One convention, because the numbers would otherwise disagree. A frame's size field does not count itself. This frame's prefix says 135, so 139 bytes crossed the socket. Offsets and the total of 139 in this section include the 4-byte prefix. Every "frame of N bytes" elsewhere in this part is the prefix's own value, and leaves it out.

The header

The header version is not on the wire. It is derived from the key and the version, so the parser reads those two shorts first and rewinds. clients/…/common/requests/RequestHeader.java:126-127 from the code: 

            // We derive the header version from the request api version, so we read that first.
            // The request api version is part of `RequestHeaderData`, so we reset the buffer position after the read.

Flexible messages use request header v2 and response header v1. Request header v0 has been gone since 4.0. And at offset 12 is an oddity: the client id has a two-byte length, not a compact one, inside an otherwise compact header. message/RequestHeader.json:36-41 explains: 

    // The ClientId string must be serialized with the old-style two-byte length prefix.
    // The reason is that older brokers must be able to read the request header for any
    // ApiVersionsRequest, even if it is from a newer version.

That is one of two exceptions built so that a client and a broker that have never met can still talk. The other is in the response.

The body

Flexible versions replace fixed lengths with unsigned varints and add a tagged section to every component (docs/design/protocol.md:141). A compact length is stored plus one, so 0 can mean null. The capture shows all three cases: TransactionalId is 00, null; the topic and partition arrays are 02, one element; and in the response, RecordErrors is 01, empty.

Three bytes at the very end, offsets 136 to 138, are the partition, topic and request tag sections, each empty. Each costs one byte in every message that has nothing to say. They are what buys the ability to add fields later, and the schemas section shows that trade. Acks is ffff, or -1. TimeoutMs is 05dc, 1,500 ms, a number that matters in purgatory.

At offset 36 there is no topic name. Produce v13 replaced it with a topic id, as a pair of fields split at that version. message/ProduceRequest.json:61-63: 

      { "name": "Name", "type": "string", "versions": "0-12", "entityType": "topicName", "mapKey": true, "ignorable": true,
        "about": "The topic name." },
      { "name": "TopicId", "type": "uuid", "versions": "13+", "mapKey": true, "ignorable": true, "about": "The unique topic ID" },

So a proxy or sniffer needs a metadata lookup to name the topic in this capture (D99, class E, behaviour change; KAFKA-10551, first tag 4.1.0).

From offset 58 the frame stops being a Kafka API message and becomes a record batch, in the format Part 1 reads on disk. producerId 0, epoch 0 and sequence 0 are the idempotence fields, which Part 4 takes up. Records are not copied out of the request either: readRecords wraps a slice of the request buffer (clients/…/common/protocol/Readable.java:65-72) from the code.

The answer is a frame of 62 bytes: correlation id, one header tag byte, and then the result. These are the fields that matter, from the same decode, offsets again counting the prefix:

The same batch, read back

A real kafka-console-consumer then fetched it, with Fetch v18. The request is a frame of 100 bytes, and it says how long the consumer is willing to wait and how little it will accept: MaxWaitMs 500, MinBytes 1, MaxBytes 52,428,800, IsolationLevel 0. Those two wait fields are exactly what purgatory enforces. SessionId and SessionEpoch are 0. The response frame is 150 bytes, and before any record it reports where the lines stand. From the same decode:

The collection's claim is visible right here: every Fetch response carries the high watermark and the last stable offset as plain numbers, and Part 3 and Part 5 are about who moves them. The 78-byte batch starts at offset 73. Compare the two runs of bytes and exactly four differ, as Figure 4 shows measured here.

The four bytes are partitionLeaderEpoch, from ffffffff to 00000000. The broker stamped it. Base offset is broker-assigned as well and also outside the CRC. It matched here only because this was offset 0, so one capture cannot show that field moving. Part 1 has why those fields were left out of the CRC.

This is the collection's "disk format is wire format" with bytes attached, and the reason the read path can be cheap. Fetch response data can stay on disk until send, because non-memory records become their own Send. The plaintext transport hands the file channel straight to the socket. clients/…/common/network/PlaintextTransportLayer.java:213-215 from the code: 

    public long transferFrom(FileChannel fileChannel, long position, long count) throws IOException {
        return fileChannel.transferTo(position, count, socketChannel);
    }

TLS gives this up, and reads the file through a 32 KiB direct buffer to encrypt it. This topic did not observe sendfile itself; Part 1 did. Which thread issues it is read from the code, not traced: strace is absent on this box.

04Parked, not waiting

Some requests cannot be answered yet. A Fetch at the end of the log has nothing to return. An acks=-1 Produce has written locally, but the followers have not caught up. If each of those held a handler thread, eight slow requests would stop the broker. They hold nothing. The handler does its work, builds a small object describing what it is waiting for, and goes back to the queue. That object is a DelayedOperation, and the place it sits is the purgatory. The socket stays muted, so the client sees one slow request, and the broker has spent a list entry on it from the code.

Parking has one subtle step. An event could arrive between "not done yet" and "watching for that event", and be missed forever. So the check runs twice, around the watch, under the operation's own lock. server-common/…/server/purgatory/DelayedOperation.java:115-127: 

    boolean safeTryCompleteOrElse(Action action) {
        lock.lock();
        try {
            if (tryComplete()) return true;
            else {
                action.apply();
                // last completion check
                return tryComplete();
            }
        } finally {
            lock.unlock();
        }
    }

Why the lock is held across all of it is written down at DelayedOperationPurgatory.java:133-154, as a "story about lock": a real three-thread deadlock with TransactionStateManager, and a warning that another stays possible if checkAndComplete is called under an exclusive lock. Only after the watch does an unfinished operation go on the timer. Watch lists are sharded into 512 buckets, and an event wakes waiters by key: checkAndComplete walks that key's list, retries each operation and drops the finished ones. Completion and expiry both go through forceComplete, guarded so that only one wins.

A Produce is born timed out

Only acks=-1 ever parks. acks=1 answers right after the local append (ReplicaManager.scala:1361-1367). By the time a Produce parks, its records are already in the leader's log, and KafkaApis drops its reference to them, "since it is already appended to log", so a parked Produce does not pin the request bytes (KafkaApis.scala:559-561). Then the constructor does the most revealing thing in this part. server/…/server/purgatory/DelayedProduce.java:110-122 from the code: 

        // first update the acks pending variable according to the error code
        produceStatus.forEach((topicPartition, status) -> {
            if (status.responseStatus.error == Errors.NONE) {
                // Timeout error state will be cleared when required acks are received
                status.acksPending = true;
                status.responseStatus.error = Errors.REQUEST_TIMED_OUT;
            } else {
                status.acksPending = false;
            }

            LOGGER.trace("Initial partition status for {} is {}", topicPartition, status);
        });
    }

The pending answer is the timeout. Expiry has nothing to undo and no way to undo it: it sends what is already there. Success is the thing that gets written in, when Partition.checkEnoughReplicasReachOffset finds the replicas have caught up (Part 3 reads that check). A high-watermark rise wakes Produce, Fetch, DeleteRecords and ShareFetch waiters. An unchanged one wakes only Fetch.

The lab ran this on three nodes with replication factor 3, min.insync.replicas=2 and two followers stopped with SIGSTOP, in one run on loopback measured here:

followers stopped, acks=1: 4 ms {'index': 0, 'error': 0, 'baseOffset': 1, ...}
followers stopped, acks=-1 timeout=3000: 3005 ms {'index': 0, 'error': 7, 'baseOffset': 2, ...}
followers stopped 2 s then SIGCONT, acks=-1 timeout=15000: 2013 ms {'index': 0, 'error': 0, 'baseOffset': 3, ...}

Read line three, then line five. Error 7 is REQUEST_TIMED_OUT, and it arrived with a base offset. The record it refers to was read back after the followers resumed. A produce timeout does not say a record is absent (D55, class D, gotcha, confirmed by verification; trunk not checked). Line four shows the release: with the followers resumed after 2 seconds, the parked Produce came back clean at 2,013 ms, well inside its 15,000 ms timeout.

Which number to watch

Completed operations stay on watch lists until the key is touched again or a purge runs. So PurgatorySize can exceed the real number waiting. Figure 5 shows it at 2 right after an expiry and a new park, with one request waiting, and it falls when the key is next touched. The Fetch panel opens at 0,1 for the same reason: a stale entry from the earlier console consumer. Watch NumDelayedOperations instead (D58, class D; upstream not checked).

A parked Fetch

A Fetch answers at once if it does not want to wait, needs nothing, already has enough, hit an error, or found a diverging epoch or a preferred replica. Otherwise it parks. What counts as "enough bytes" depends on who is reading: the log end for followers, the high watermark for ordinary consumers, the last stable offset for read_committed. On completion it re-reads the log rather than reusing the first read. The lab's three runs match measured here: 

E3a expiry: empty fetch at LEO max_wait=6000 returned in 6005 ms, recordBytes 0 hw 2
E3b wake: fetch max_wait=20000 + produce at 2000ms: returned at 2004 ms; produce rtt 3 ; batch b'wake-up'
E3c min_bytes=1000: 100B at 1000ms stays parked, 1200B at 2003 ms; returned at 2009 ms, recordBytes 1440 batches 2

Expired operations run on a single executor-Fetch thread, so a timed-out Fetch's log read happens there and not on a handler. Expiry is therefore serial per purgatory. Whether a slow read delays other expiries was not measured (D60, class D; read in the code; upstream not checked).

The wait also has a place in the metrics. Request timing is split into queue, local, remote, response queue, response send and total, and purgatory time lands in remote. Seven consumer Fetches recorded a maximum RemoteTimeMs of 6,002 ms against a maximum LocalTimeMs of 25 ms. Fetch metrics appear under FetchConsumer and FetchFollower as well as Fetch, so a broker's own replication traffic can be separated measured here.

05The timing wheel

Every parked request needs a timeout, and most never fire. The docs for the structure give that as its reason: "The hierarchical timing wheels works especially well when operations are completed before they time out" (server-common/…/server/util/timer/TimingWheel.java:89). So cancel has to be cheap, and insert nearly so. A hierarchical timing wheel gives O(m) insert for m wheels and O(1) cancel from the code.

The default timer has a 1 ms tick and 20 buckets per wheel (SystemTimer.java:44-46). Each overflow wheel's tick is the previous wheel's whole span. Spans and ticks are derived from those two numbers:

WheelTickSpan of 20 buckets
11 ms20 ms
220 ms400 ms
3400 ms8 s
48 s160 s

Overflow wheels are created lazily, the first time an entry does not fit. The class comment explains the contrast it is drawing: priority-queue timers "have O(log n) insert/delete cost", and a simple wheel cannot hold a timeout past its own span, which is "an overflow". Insert is one method. TimingWheel.java:147-179, with the first two branches and part of a comment elided: 

    public boolean add(TimerTaskEntry timerTaskEntry) {
        long expiration = timerTaskEntry.expirationMs;
        …
        } else if (expiration < currentTimeMs + interval) {
            // Put in its own bucket
            long virtualId = expiration / tickMs;
            int bucketId = (int) (virtualId % (long) wheelSize);
            TimerTaskList bucket = buckets[bucketId];
            bucket.add(timerTaskEntry);

            // Set the bucket expiration time
            if (bucket.setExpiration(virtualId * tickMs)) {
                // The bucket needs to be enqueued because it was an expired bucket
                …
                queue.offer(bucket);
            }

            return true;
        } else {
            // Out of the interval. Put it into the parent timer
            if (overflowWheel == null) addOverflowWheel();
            return overflowWheel.add(timerTaskEntry);
        }
    }

The elided branches refuse an entry that is cancelled or already expired. Note what goes into the DelayQueue: queue.offer(bucket). It holds buckets, not tasks, and a bucket enters only when its expiry changes. A heap costs log n per item, and here n counts active buckets rather than requests. That is why a broker can park a great many requests cheaply.

Walk the figure in terms of the code. An entry due at 517 ms arrives with the clock at 0. It does not fit under 20 or under 400, so add recurses twice and lands in the 400 ms wheel, in bucket 1, whose expiry is 400. Nothing happens for 400 ms. Then the bucket expires, the entry is re-added, and 517 now fits in the 20 ms wheel, in bucket 5. At 500 it drops into the 1 ms wheel, in bucket 17. At 517, add finds it already expired and returns false, and only then does the task run. That is one placement and two moves over its whole life, and if the request completes first, the moves never happen.

The clock moves only when a bucket expires. SystemTimer.java:89-101 polls the queue, advances the clock to that bucket's expiry, and flushes the bucket by re-adding each entry. That re-add either drops the entry to a finer wheel or runs it. A read/write lock excludes adds during the tick from the code.

One number here gets misread. The reaper calls advanceClock(200L) (DelayedOperationPurgatory.java:409-421). That is not a 200 ms tick. It is the longest the poll idles, because DelayQueue.poll returns as soon as the earliest bucket expires. The lab's 6,000 ms wait took 6,005 ms, in a single run on loopback measured here.

ReplicaManager owns six purgatories at the pin, and the live thread dump shows a reaper for each: Produce, Fetch, DeleteRecords, RemoteFetch, RemoteListOffsets, ShareFetch. Two more ExpirationReaper-1-AlterAcls threads come from outside it measured here.

06Answer first, then silence

A quota in Kafka does not refuse work. It delays the next request. Produce shows it most plainly, because usage is recorded in the response callback, after the append. By the time a delay is computed, the data is in the log. core/…/server/KafkaApis.scala:492-512 from the code: 

      // Record both bandwidth and request quota-specific values and throttle by muting the channel if any of the quotas
      // have been violated. If both quotas have been violated, use the max throttle time between the two quotas. Note
      // that the request quota is not enforced if acks == 0.
      val timeMs = time.milliseconds()
      val requestSize = request.sizeInBytes
      val bandwidthThrottleTimeMs = quotas.produce.maybeRecordAndGetThrottleTimeMs(request.session, request.header.clientId(), requestSize, timeMs)
      val requestThrottleTimeMs =
        if (produceRequest.acks == 0) 0
        else quotas.request.maybeRecordAndGetThrottleTimeMs(request, timeMs)
      val maxThrottleTimeMs = Math.max(bandwidthThrottleTimeMs, requestThrottleTimeMs)
      if (maxThrottleTimeMs > 0) {
        request.apiThrottleTimeMs(maxThrottleTimeMs)
        if (bandwidthThrottleTimeMs > requestThrottleTimeMs) {
          requestHelper.throttle(quotas.produce, request, bandwidthThrottleTimeMs)
        } else {
          requestHelper.throttle(quotas.request, request, requestThrottleTimeMs)
        }
      }

      // Send the response immediately. In case of throttling, the channel has already been muted.
      if (produceRequest.acks == 0) {

The order is the point. The response goes out at once, carrying the throttle time. The mute happens separately: creating a ThrottledChannel starts it, a delay queue holds it, and one reaper thread per quota type ends it. Those are the ThrottledChannelReaper threads in the dump. The socket reopens only when both the send and the throttle are done. It is the same gate as the muted socket, held for a second reason.

It used to work the other way, and KIP-219 (release 2.0.0 per the page) changed it. Holding the response made clients see only a timeout, so they could not tell a quota violation from a network problem.

The arithmetic

The delay is whatever brings the average back to quota. server-common/…/server/quota/QuotaUtils.java:34-36: "to bring O down to T, we need to add a delay of X to W such that O * W / (W + X) = T. Solving for X, we get X = (O - T)/T * W." Two details make it bite. Request-time throttles are capped at one quota window, but bandwidth throttles use the unbounded formula (ClientRequestQuotaManager.java:95-97, ClientQuotaManager.java:438-440). And a rate window pretends to be at least N-1 full windows long even when the sensor is new, because otherwise "the measured rate will be very high" (clients/…/common/metrics/stats/Rate.java:90-92). With the defaults of 11 samples of 1 second, a fresh client's first burst is divided by about 10 seconds. So first bursts are nearly free from the code.

The lab set producer_byte_rate=10240 on one client id and wrote 102,400 value bytes at a time, with an ApiVersions pipelined behind each write. That is one run on loopback, with the no-quota comparison cut to its first round here measured here: 

quota producer_byte_rate=10240 round 0 produce response at 23 ms throttleMs 12 ; pipelined ApiVersions response at 37 ms
quota producer_byte_rate=10240 round 1 produce response at 18 ms throttleMs 9937 ; pipelined ApiVersions response at 9956 ms
quota producer_byte_rate=10240 round 2 produce response at 18 ms throttleMs 19942 ; pipelined ApiVersions response at 19961 ms
no quota round 0 produce response at 16 ms throttleMs 0 ; pipelined ApiVersions response at 17 ms

The response came in about 20 ms every round. The next request paid: 12 ms, then 9.9 s, then 19.9 s, with no cap. This is D57, class D, a gotcha, and intended per franz-go's comment below. Clients wait on their side as well. The Java client marks the connection throttled for response versions where the broker answers first (Fetch v8+, Produce v6+), and franz-go insists on it at franz-go/pkg/kgo/broker.go:2029-2036: "Capping it would break the quota mechanism; an absurd throttle is equivalent to a slow broker, which is always possible. Do not add a cap."

Fetch does the opposite

A consumer over quota has nothing in the log to protect. So Fetch un-records the bytes and returns an empty response, since nothing is read for the client (KafkaApis.scala:712-721). The lab saw it: over consumer_byte_rate=10240, a 21-byte frame with no topics and throttleMs 7, where the same fetch without a quota returned 328,200 record bytes measured here. That is one quota round only. The second response overran the lab's decoder, which also failed the first version of the script, and both tracebacks are on file; only rows before each crash are cited. So the cap below is read, not measured.

A consumer's fetch size is capped to what the quota window can hold, because otherwise "trying to fetch more bytes would result in a guaranteed throttling" (KafkaApis.scala:740-748). Follower fetches bypass client quotas altogether: they are recorded against the leader replication quota, and the response is exempt from throttling from the code.

Three smaller rules live nearby. The request-time quota is not enforced for acks=0, though the bandwidth quota is, and the larger of the two throttles wins. Request quotas are a percentage of thread time across I/O and network threads, and network-thread time is recorded after the fact, so it counts only toward later throttling. Quota accounting is skipped entirely until any quota exists.

One more line in that path decides who may write to internal topics: internalTopicsAllowed compares the client id to the fixed string "__admin_client" (KafkaApis.scala:545). Topic authorization has already run by then, so ACLs still apply (D61, class D; still at trunk 09f2dc1320, read only).

07Generated from 203 JSON files

None of the bytes above are written by hand. The protocol is data. message/README.md:6-13: "The JSON files in this directory define the Apache Kafka message protocol", and "When Kafka is compiled, these specification files are translated into Java code to read and write messages" from the code.

The Gradle task at build.gradle:2125-2130 runs the generator on that directory, with ApiMessageTypeGenerator, MessageDataGenerator and JsonConverterGenerator. Three rules from the README shape everything that follows. One generated class covers every version of a message: "a single MessageData object represents every possible version of a Message", and the version is passed to read and write. Field order in the JSON is the wire order: "Changing the order of the fields in a message is an incompatible change". And by default, writing a non-default field into a version that lacks it throws, unless the field is marked ignorable. In the README's words, "we assume that information loss is not acceptable".

The schema comments double as a changelog. message/ProduceRequest.json opens with "Versions 0-2 were removed in Apache Kafka 4.0, version 3 is the new baseline", and then walks forward: "Version 3 adds the transactional ID".

What flexible versions bought

Before flexible versions, any new field meant a new version, and a new version meant both sides had to agree on it. A tag section changes that. message/README.md:127-129: 

Unlike mandatory fields, tagged fields can be added to message versions that
already exists.  Older servers will ignore new tagged fields which they do not
understand.

This is the trade behind the three empty bytes at the end of the Produce frame. Each component spends one byte on a count of zero. In return, a sender can add a field that an old receiver skips safely. "Ignore" is also stronger than it sounds: unknown tags are kept, not dropped. The generated reader stores them and the writer merges them back, with reads bounded at 10,000 tags.

Tagged fields do not replace versions, though. message/ApiVersionsRequest.json added ClusterId and NodeId at version 5 as ordinary fields, "versions": "5+". The two mechanisms sit side by side from the code.

The generator enforces the direction of travel. It rejects any range that closes. From generator/…/message/MessageSpec.java:73-78: "flexibleVersions must be either none, or an open-ended range (that ends with a plus sign)". Tagged versions have the same rule. Once a message goes flexible it stays flexible. At the pin, only two live request schemas have no flexible version: OffsetDelete and SaslHandshake.

The same flag picks the header. Each schema's flexibleVersions starts somewhere different (Produce 9+, Fetch 12+, Metadata 9+, JoinGroup 6+, ApiVersions 3+), and the generator turns it into the header version. ApiMessageTypeGenerator.java:371-377: 

                ifMember(__ -> {
                    if (type.equals("request")) {
                        buffer.printf("return (short) 2;%n");
                    } else {
                        buffer.printf("return (short) 1;%n");
                    }
                }).

Retiring things

Two schema markers do the removals. validVersions of none retires an API but reserves its key, with no data class and no listeners. ApiKeys.java:259-266 gives the reason: "the api key remains assigned to the removed api so we do not accidentally reuse it for a different api". LeaderAndIsr, key 4, is one of these.

latestVersionUnstable does the opposite job for what is not ready. It hides a schema's top version unless an internal flag is set. message/InitProducerIdRequest.json:32-33 says "latestVersionUnstable": true and "validVersions": "0-6", and the live broker advertised 0 to 5 measured here.

Other people's copies

The JSON is Kafka's own. franz-go generates its Go types from a custom DSL: "The generator reads definition files from definitions/" (franz-go/generate/README.md). So a new Kafka field reaches it only when someone writes it in; that last clause is an inference. At the pin it is level with Kafka for Produce (13), Fetch (18) and ApiVersions (5) from the code.

librdkafka at v2.16.0 caps Produce at v10 (librdkafka/src/rdkafka_msgset_writer.c:49), three behind the broker. So it still sends topic names, and the topic-id capture above would look different from it. That is computed from the code. librdkafka was read, never run.

08ApiVersions, and Produce v0

If everything is versioned, something has to be readable without knowing the version. That is ApiVersions, key 18, the protocol's one fixed point. A client treats a node as ready only after its response (NetworkClient.java:1151-1157), and every captured Java connection, 8 of 8, opened with it measured here.

The client sends its highest version blind, so the broker has to accept anything. clients/…/common/protocol/ApiKeys.java:247-250 from the code: 

        // ApiVersions API is a particular case. The client always send the highest version
        // that it supports and the server fails back to version 0 if it does not know it.
        // Hence, we have to accept any versions here, even unsupported ones.
        if (this == ApiKeys.API_VERSIONS) return true;

A version the broker does not know is not parsed. It is treated as v0, and the answer uses the v0 schema. The header holds still too, hard-coded by the generator for this one key. generator/…/message/ApiMessageTypeGenerator.java:362-365: 

            if (type.equals("response") && apiKey == 18) {
                buffer.printf("// ApiVersionsResponse always includes a v0 header.%n");
                buffer.printf("// See KIP-511 for details.%n");
                buffer.printf("return (short) 0;%n");

So a client that knows nothing about this broker can still read the answer. Here is the lab's ApiVersions v99, whose whole response is 16 bytes measured here: 

00000007   correlation id = 7, then no header tag byte
0023       error 35, UNSUPPORTED_VERSION
00000001   one entry, in a fixed-width v0 array
0012       key 18
0000 0005  supports 0 to 5

The Java client retries with the stated maximum. franz-go detects the case from raw bytes, because the error's low byte sits at position 1 of a v0 body, and caches the maximum to skip the extra round trip. For every other API, the client picks the highest version both sides allow, per node. The docs say those results hold only for that connection.

The live v5 answer is 876 bytes and starts 00000001 0000 4e: correlation id, error, then a compact array length for 77 entries, with no header tag byte between them. Its first entry is 0000 0000 000d 00: key 0, Produce, minimum 0, maximum 13. Remember that zero.

A client that gets an unknown key sets it aside, so brokers can add APIs without breaking older clients. The broker also answers before authentication, which reveals its version on a SASL listener (KafkaApis.scala:1545-1550). Forwardable APIs are advertised as the intersection of broker and active controller ranges.

The line at 2.1, and the exception

The project kept every version since 0.8.0 until KIP-896 set the baseline at Kafka 2.1 for 4.0, with exceptions where existing clients needed older versions. At the pin, Produce starts at v3 and Fetch at v4. The README now says "Dropping support for old message versions is no longer allowed without a KIP". The compatibility docs' summary, "Pre-0.10.x protocols are fully removed in Kafka 4.0", is not the real rule: the code keeps Metadata 0-13 and JoinGroup 0-9 (D16, class C; still at trunk). JoinGroup v0 and v1 are a restoration, brought back in 4.0.1 and 4.1.0 by KAFKA-19444 because librdkafka's SASL GSSAPI check needed v0.

Then the oddest line in the protocol. ApiKeys.java:157-160: 

    // Versions 0-2 were removed in Apache Kafka 4.0, version 3 is the new baseline. Due to a bug in librdkafka,
    // version `0` has to be included in the api versions response (see KAFKA-18659). In order to achieve that,
    // we adjust `toApiVersion` to return `0` for the min version of `produce` in the broker listener.
    public static final short PRODUCE_API_VERSIONS_RESPONSE_MIN_VERSION = 0;

The adjustment is at ApiKeys.java:290-291: 

        short oldestVersion = (this == PRODUCE && listenerType.map(l -> l == ApiMessageType.ListenerType.BROKER).orElse(false)) ?
            PRODUCE_API_VERSIONS_RESPONSE_MIN_VERSION : oldestVersion();

The bug: older librdkafka asked whether Produce v0 was supported before compressing, through this call: 

rd_kafka_broker_ApiVersion_supported(rkb, RD_KAFKAP_Produce, 0, ApiVersion, NULL)

With gzip and snappy at the zero default, that asked for exactly v0. A broker without v0 would have turned compression off, with a NOTICE at most once a day. The accepted fix was to advertise v0 to v2 and reject them. Figure 8 is the result.

So the advertised Produce minimum is false by design: advertised 0, usable 3 (D53, class D, intended; still at trunk). A client that trusts the range and picks low gets end-of-file, not an error. KAFKA-18659's plan said reject "with UnsupportedVersion error". What reaches the client is a closed socket and zero bytes, because the header check throws on the network thread and that path has no response to send (D17, class C). docs/design/protocol.md:102 says only "reject", which is accurate.

At librdkafka's pin, the check that caused this is fixed: rd_kafka_broker_ApiVersion_at_least now tests an open range. So the workaround protects only older builds, which is an inference from reading, not a run. Whether Kafka can drop the advertisement depends on how many pre-v2.11.1 clients remain, and nothing here measures that. The metric KIP-896 relied on cannot help: DeprecatedRequestsPerSec is wired, but no schema at the pin declares deprecatedVersions, so in 4.4 it cannot fire (D54, class D).
