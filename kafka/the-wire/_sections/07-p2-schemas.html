The Gradle task at build.gradle:2125-2130 runs the generator on that directory, with ApiMessageTypeGenerator, MessageDataGenerator and JsonConverterGenerator. Three rules from the README shape everything that follows. One generated class covers every version of a message: "a single MessageData object represents every possible version of a Message", and the version is passed to read and write. Field order in the JSON is the wire order: "Changing the order of the fields in a message is an incompatible change". And by default, writing a non-default field into a version that lacks it throws, unless the field is marked ignorable. In the README's words, "we assume that information loss is not acceptable".

The schema comments double as a changelog. message/ProduceRequest.json opens with "Versions 0-2 were removed in Apache Kafka 4.0, version 3 is the new baseline", and then walks forward: "Version 3 adds the transactional ID".

What flexible versions bought

Before flexible versions, any new field meant a new version, and a new version meant both sides had to agree on it. A tag section changes that. message/README.md:127-129: 

Unlike mandatory fields, tagged fields can be added to message versions that
already exists.  Older servers will ignore new tagged fields which they do not
understand.

This is the trade behind the three empty bytes at the end of the Produce frame. Each component spends one byte on a count of zero. In return, a sender can add a field that an old receiver skips safely. "Ignore" is also stronger than it sounds: unknown tags are kept, not dropped. The generated reader stores them and the writer merges them back, with reads bounded at 10,000 tags.

Tagged fields do not replace versions, though. message/ApiVersionsRequest.json added ClusterId and NodeId at version 5 as ordinary fields, "versions": "5+". The two mechanisms sit side by side from the code.

The generator enforces the direction of travel. It rejects any range that closes. From generator/…/message/MessageSpec.java:73-78: "flexibleVersions must be either none, or an open-ended range (that ends with a plus sign)". Tagged versions have the same rule. Once a message goes flexible it stays flexible. At the pin, only two live request schemas have no flexible version: OffsetDelete and SaslHandshake.

The same flag picks the header. Each schema's flexibleVersions starts somewhere different (Produce 9+, Fetch 12+, Metadata 9+, JoinGroup 6+, ApiVersions 3+), and the generator turns it into the header version. ApiMessageTypeGenerator.java:371-377:

Retiring things

Two schema markers do the removals. validVersions of none retires an API but reserves its key, with no data class and no listeners. ApiKeys.java:259-266 gives the reason: "the api key remains assigned to the removed api so we do not accidentally reuse it for a different api". LeaderAndIsr, key 4, is one of these.

latestVersionUnstable does the opposite job for what is not ready. It hides a schema's top version unless an internal flag is set. message/InitProducerIdRequest.json:32-33 says "latestVersionUnstable": true and "validVersions": "0-6", and the live broker advertised 0 to 5 measured here.

Other people's copies

The JSON is Kafka's own. franz-go generates its Go types from a custom DSL: "The generator reads definition files from definitions/" (franz-go/generate/README.md). So a new Kafka field reaches it only when someone writes it in; that last clause is an inference. At the pin it is level with Kafka for Produce (13), Fetch (18) and ApiVersions (5) from the code.

librdkafka at v2.16.0 caps Produce at v10 (librdkafka/src/rdkafka_msgset_writer.c:49), three behind the broker. So it still sends topic names, and the topic-id capture above would look different from it. That is computed from the code. librdkafka was read, never run.
