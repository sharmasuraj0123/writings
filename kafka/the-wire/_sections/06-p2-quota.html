{{S}}Answer first, then silence

A quota in Kafka does not refuse work. It delays the next request. Produce shows it most plainly, because usage is recorded in the response callback, after the append. By the time a delay is computed, the data is in the log. core/…/server/KafkaApis.scala:492-512 from the code: 

      // Record both bandwidth and request quota-specific values and throttle by muting the channel if any of the quotas
      // have been violated. If both quotas have been violated, use the max throttle time between the two quotas. Note
      // that the request quota is not enforced if acks == 0.
      val timeMs = time.milliseconds()
      val requestSize = request.sizeInBytes
      val bandwidthThrottleTimeMs = quotas.produce.maybeRecordAndGetThrottleTimeMs(request.session, request.header.clientId(), requestSize, timeMs)
      val requestThrottleTimeMs =
        if (produceRequest.acks == 0) 0
        else quotas.request.maybeRecordAndGetThrottleTimeMs(request, timeMs)
      val maxThrottleTimeMs = Math.max(bandwidthThrottleTimeMs, requestThrottleTimeMs)
      if (maxThrottleTimeMs > 0) {
        request.apiThrottleTimeMs(maxThrottleTimeMs)
        if (bandwidthThrottleTimeMs > requestThrottleTimeMs) {
          requestHelper.throttle(quotas.produce, request, bandwidthThrottleTimeMs)
        } else {
          requestHelper.throttle(quotas.request, request, requestThrottleTimeMs)
        }
      }

      // Send the response immediately. In case of throttling, the channel has already been muted.
      if (produceRequest.acks == 0) {

The order is the point. The response goes out at once, carrying the throttle time. The mute happens separately: creating a ThrottledChannel starts it, a delay queue holds it, and one reaper thread per quota type ends it. Those are the ThrottledChannelReaper threads in the dump. The socket reopens only when both the send and the throttle are done. It is the same gate as the muted socket, held for a second reason.

It used to work the other way, and KIP-219 (release 2.0.0 per the page) changed it. Holding the response made clients see only a timeout, so they could not tell a quota violation from a network problem.

The arithmetic

The delay is whatever brings the average back to quota. server-common/…/server/quota/QuotaUtils.java:34-36: "to bring O down to T, we need to add a delay of X to W such that O * W / (W + X) = T. Solving for X, we get X = (O - T)/T * W." Two details make it bite. Request-time throttles are capped at one quota window, but bandwidth throttles use the unbounded formula (ClientRequestQuotaManager.java:95-97, ClientQuotaManager.java:438-440). And a rate window pretends to be at least N-1 full windows long even when the sensor is new, because otherwise "the measured rate will be very high" (clients/…/common/metrics/stats/Rate.java:90-92). With the defaults of 11 samples of 1 second, a fresh client's first burst is divided by about 10 seconds. So first bursts are nearly free from the code.

The lab set producer_byte_rate=10240 on one client id and wrote 102,400 value bytes at a time, with an ApiVersions pipelined behind each write. That is one run on loopback, with the no-quota comparison cut to its first round here measured here: 

quota producer_byte_rate=10240 round 0 produce response at 23 ms throttleMs 12 ; pipelined ApiVersions response at 37 ms
quota producer_byte_rate=10240 round 1 produce response at 18 ms throttleMs 9937 ; pipelined ApiVersions response at 9956 ms
quota producer_byte_rate=10240 round 2 produce response at 18 ms throttleMs 19942 ; pipelined ApiVersions response at 19961 ms
no quota round 0 produce response at 16 ms throttleMs 0 ; pipelined ApiVersions response at 17 ms

The response came in about 20 ms every round. The next request paid: 12 ms, then 9.9 s, then 19.9 s, with no cap. This is D57, class D, a gotcha, and intended per franz-go's comment below. Clients wait on their side as well. The Java client marks the connection throttled for response versions where the broker answers first (Fetch v8+, Produce v6+), and franz-go insists on it at franz-go/pkg/kgo/broker.go:2029-2036: "Capping it would break the quota mechanism; an absurd throttle is equivalent to a slow broker, which is always possible. Do not add a cap."

Fetch does the opposite

A consumer over quota has nothing in the log to protect. So Fetch un-records the bytes and returns an empty response, since nothing is read for the client (KafkaApis.scala:712-721). The lab saw it: over consumer_byte_rate=10240, a 21-byte frame with no topics and throttleMs 7, where the same fetch without a quota returned 328,200 record bytes measured here. That is one quota round only. The second response overran the lab's decoder, which also failed the first version of the script, and both tracebacks are on file; only rows before each crash are cited. So the cap below is read, not measured.

A consumer's fetch size is capped to what the quota window can hold, because otherwise "trying to fetch more bytes would result in a guaranteed throttling" (KafkaApis.scala:740-748). Follower fetches bypass client quotas altogether: they are recorded against the leader replication quota, and the response is exempt from throttling from the code.

Three smaller rules live nearby. The request-time quota is not enforced for acks=0, though the bandwidth quota is, and the larger of the two throttles wins. Request quotas are a percentage of thread time across I/O and network threads, and network-thread time is recorded after the fact, so it counts only toward later throttling. Quota accounting is skipped entirely until any quota exists.

One more line in that path decides who may write to internal topics: internalTopicsAllowed compares the client id to the fixed string "__admin_client" (KafkaApis.scala:545). Topic authorization has already run by then, so ACLs still apply (D61, class D; still at trunk 09f2dc1320, read only).
