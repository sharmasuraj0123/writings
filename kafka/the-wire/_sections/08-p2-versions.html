{{S}}ApiVersions, and Produce v0

If everything is versioned, something has to be readable without knowing the version. That is ApiVersions, key 18, the protocol's one fixed point. A client treats a node as ready only after its response (NetworkClient.java:1151-1157), and every captured Java connection, 8 of 8, opened with it measured here.

The client sends its highest version blind, so the broker has to accept anything. clients/…/common/protocol/ApiKeys.java:247-250 from the code: 

        // ApiVersions API is a particular case. The client always send the highest version
        // that it supports and the server fails back to version 0 if it does not know it.
        // Hence, we have to accept any versions here, even unsupported ones.
        if (this == ApiKeys.API_VERSIONS) return true;

A version the broker does not know is not parsed. It is treated as v0, and the answer uses the v0 schema. The header holds still too, hard-coded by the generator for this one key. generator/…/message/ApiMessageTypeGenerator.java:362-365: 

            if (type.equals("response") && apiKey == 18) {
                buffer.printf("// ApiVersionsResponse always includes a v0 header.%n");
                buffer.printf("// See KIP-511 for details.%n");
                buffer.printf("return (short) 0;%n");

So a client that knows nothing about this broker can still read the answer. Here is the lab's ApiVersions v99, whose whole response is 16 bytes measured here: 

00000007   correlation id = 7, then no header tag byte
0023       error 35, UNSUPPORTED_VERSION
00000001   one entry, in a fixed-width v0 array
0012       key 18
0000 0005  supports 0 to 5

The Java client retries with the stated maximum. franz-go detects the case from raw bytes, because the error's low byte sits at position 1 of a v0 body, and caches the maximum to skip the extra round trip. For every other API, the client picks the highest version both sides allow, per node. The docs say those results hold only for that connection.

The live v5 answer is 876 bytes and starts 00000001 0000 4e: correlation id, error, then a compact array length for 77 entries, with no header tag byte between them. Its first entry is 0000 0000 000d 00: key 0, Produce, minimum 0, maximum 13. Remember that zero.

A client that gets an unknown key sets it aside, so brokers can add APIs without breaking older clients. The broker also answers before authentication, which reveals its version on a SASL listener (KafkaApis.scala:1545-1550). Forwardable APIs are advertised as the intersection of broker and active controller ranges.

New in 4.4: am I talking to the right broker?

ApiVersions v5 (KIP-1242) lets a client name the cluster and node it meant to reach. A mismatch returns REBOOTSTRAP_REQUIRED (D100, class E; KAFKA-20246, fix version 4.4.0). The capture shows both forms. A bootstrap connection's frame has size 54; a node connection's has size 76, and the 22 extra bytes are the cluster id. The line at 2.1, and the exception

The project kept every version since 0.8.0 until KIP-896 set the baseline at Kafka 2.1 for 4.0, with exceptions where existing clients needed older versions. At the pin, Produce starts at v3 and Fetch at v4. The README now says "Dropping support for old message versions is no longer allowed without a KIP". The compatibility docs' summary, "Pre-0.10.x protocols are fully removed in Kafka 4.0", is not the real rule: the code keeps Metadata 0-13 and JoinGroup 0-9 (D16, class C; still at trunk). JoinGroup v0 and v1 are a restoration, brought back in 4.0.1 and 4.1.0 by KAFKA-19444 because librdkafka's SASL GSSAPI check needed v0.

Then the oddest line in the protocol. ApiKeys.java:157-160: 

    // Versions 0-2 were removed in Apache Kafka 4.0, version 3 is the new baseline. Due to a bug in librdkafka,
    // version `0` has to be included in the api versions response (see KAFKA-18659). In order to achieve that,
    // we adjust `toApiVersion` to return `0` for the min version of `produce` in the broker listener.
    public static final short PRODUCE_API_VERSIONS_RESPONSE_MIN_VERSION = 0;

The adjustment is at ApiKeys.java:290-291: 

        short oldestVersion = (this == PRODUCE && listenerType.map(l -> l == ApiMessageType.ListenerType.BROKER).orElse(false)) ?
            PRODUCE_API_VERSIONS_RESPONSE_MIN_VERSION : oldestVersion();

The bug: older librdkafka asked whether Produce v0 was supported before compressing, through this call: 

rd_kafka_broker_ApiVersion_supported(rkb, RD_KAFKAP_Produce, 0, ApiVersion, NULL)

With gzip and snappy at the zero default, that asked for exactly v0. A broker without v0 would have turned compression off, with a NOTICE at most once a day. The accepted fix was to advertise v0 to v2 and reject them. Figure {{fig-versions}} is the result.

So the advertised Produce minimum is false by design: advertised 0, usable 3 (D53, class D, intended; still at trunk). A client that trusts the range and picks low gets end-of-file, not an error. KAFKA-18659's plan said reject "with UnsupportedVersion error". What reaches the client is a closed socket and zero bytes, because the header check throws on the network thread and that path has no response to send (D17, class C). docs/design/protocol.md:102 says only "reject", which is accurate.

At librdkafka's pin, the check that caused this is fixed: rd_kafka_broker_ApiVersion_at_least now tests an open range. So the workaround protects only older builds, which is an inference from reading, not a run. Whether Kafka can drop the advertisement depends on how many pre-v2.11.1 clients remain, and nothing here measures that. The metric KIP-896 relied on cannot help: DeprecatedRequestsPerSec is wired, but no schema at the pin declares deprecatedVersions, so in 4.4 it cannot fire (D54, class D).
