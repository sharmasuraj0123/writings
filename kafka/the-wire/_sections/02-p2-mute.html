{{S}}The muted socket

selector.mute is one line, and it decides the shape of the protocol. A muted channel is not read. clients/…/common/network/Selector.java:580-583 from the code: 

                if (channel.ready() && (key.isReadable() || channel.hasBytesBuffered()) && !hasCompletedReceive(channel)
                        && !explicitlyMutedChannels.contains(channel)) {
                    attemptRead(channel);
                }

A second request on that connection is not refused, and is not read either. It stays in the kernel's socket buffer. The channel opens again only when the response has been fully sent, and then only if no throttle is active (SocketServer.scala:1049-1053). So each connection has one request in progress, and its answers come back in order. This is the documented contract, not an accident. docs/design/protocol.md:45: "The broker's request processing allows only a single in-flight request per connection in order to guarantee this ordering", and clients "can send requests even while awaiting responses for preceding requests since the outstanding requests will be buffered in the underlying OS socket buffer".

No thread is involved in that wait. Pipelining is a client's right, but pipelined requests get no parallelism on one socket. The cost shows the moment a request has to wait.

The lab sent a Fetch at the log end, with a 4,000 ms wait, and an ApiVersions right behind it on the same socket. The first response came at 4,004 ms and the second at 4,005 ms. The same ApiVersions on another connection took 2 ms measured here. This is D56, class D, a gotcha confirmed by verification; trunk was not checked.

Routine Java traffic does not do this. The Java consumer fetches with at most one request in flight per node (Part 4 has why). So clients keep several sockets

If one long poll can hold up a socket, a client that also needs to heartbeat cannot share it. The Java consumer gives the group coordinator a connection of its own, through an id string prefixed with + (clients/…/consumer/internals/GroupCoordinatorNode.java:21-34). That is new in 4.4.0; through 4.3 the id was Integer.MAX_VALUE - nodeId. The capture shows it working: Fetch on connection 7, heartbeat and commit on connection 8, same broker measured here.

franz-go goes further, with up to five connections per broker, chosen by request type so that long polls cannot block other traffic. franz-go/pkg/kgo/broker.go:683-700 from the code:

librdkafka adds logical broker handles for its coordinators, each with its own thread. That this means a separate socket is inferred from the code; librdkafka was read, never run.

When there is no response to wait for

acks=0 tests the rule from the other side. There is no response, so nothing would ever unmute the socket. The broker therefore sends an internal NoOpResponse, whose handler comment is plain: "There is no response to send to the client, we need to read more pipelined requests that are sitting in the server's socket buffer" (SocketServer.scala:922-923). And since no frame can carry an error, an error closes the socket (core/…/server/KafkaApis.scala:512-529). The lab saw both paths. An acks=0 Produce to an unknown topic id closed the connection in 9 ms, and on a good send, the next frame on the wire belonged to the following request measured here.

Any exception while turning a frame into a request ends the same way, with a closed connection and no error frame (SocketServer.scala:907-912, :1031-1035). The last section of this part comes back to that.
