{{S}}Two pools and a queue

A broker is two thread pools and one queue. One rule, the muted socket, gives every connection one request at a time. Requests that must wait hold no thread, and a timeout undoes nothing. This collection reads Kafka as one append-only log used five times, with each promise a line in such a log. Part 1 read that log on disk. This part follows one request from the socket to the log and back: the threads it crosses, its real bytes, where it waits, and what it can and cannot take back. Part 3 picks up at the line an ack moves.

The class comment in core/…/network/SocketServer.scala:60-70 gives the shape: "1 Acceptor thread per listener", "N Processor threads that each have their own selector", and "M Handler threads that handle requests and produce responses back to the processor threads for writing" from the code. A second fact sits at :99-100: one map of acceptors, but a single RequestChannel. Every listener of a SocketServer drains into one request queue. The same comment opens with "two types of request planes" and then lists one, because control.plane.listener.name is gone (register D14, class C, doc drift; still there at trunk 09f2dc1320, read only).

The network thread

The acceptor assigns each socket round-robin to a processor whose new-connection queue has room, and blocks only if all of them are full (SocketServer.scala:635-637). The queue holds 20 sockets, and at most that many are registered per loop, so new connections cannot starve existing traffic. Accepted sockets are non-blocking, with Nagle off and TCP keepalive on (:689-695). The whole job of a network thread is at SocketServer.scala:871-883 from the code: 

  override def run(): Unit = {
    try {
      while (shouldRun.get()) {
        try {
          // setup any new connections that have been queued up
          configureNewConnections()
          // register any new responses for writing
          processNewResponses()
          poll()
          processCompletedReceives()
          processCompletedSends()
          processDisconnected()
          closeExcessConnections()

A frame is four bytes of size, then a payload. A size above socket.request.max.bytes, 100 MiB by default, is refused before any body is read (clients/…/common/network/NetworkReceive.java:89-96). The lab's oversized header, 104,857,601 bytes, got the socket closed after 4 ms measured here. An optional memory pool, off by default with queued.max.request.bytes=-1, can make that read wait for memory. A frame's buffer allocation then fails softly: the read waits, the selector records out-of-memory, and it unmutes channels when memory returns (Selector.java:691-692).

Parsing happens here, not on a handler. The header is parsed first, and a disabled version throws before any handler sees it. server/…/network/Processor.java:33-42: 

    public static RequestHeader parseRequestHeader(ApiVersionManager apiVersionManager, ByteBuffer buffer) {
        RequestHeader header = RequestHeader.parse(buffer);
        if (apiVersionManager.isApiEnabled(header.apiKey(), header.apiVersion())) {
            return header;
        } else if (header.isApiVersionSupported()) {
            throw new InvalidRequestException("Received request for disabled api with key " + header.apiKey().id + " (" + header.apiKey().name() + ") and version " + header.apiVersion());
        } else {
            throw new UnsupportedVersionException("Received request for api with key " + header.apiKey().id + " (" + header.apiKey().name + ") and unsupported version " + header.apiVersion());
        }
    }

The body follows, because the Request constructor runs parseRequest (server/…/network/Request.java:101). ApiVersions is even peeked at on this thread, to capture the client's software name (KIP-511). Then come the two lines that shape everything else, SocketServer.scala:1019-1021: 

                requestChannel.sendRequest(req)
                selector.mute(connectionId)
                handleChannelMuteEvent(connectionId, ChannelMuteEvent.REQUEST_RECEIVED)

sendRequest is a blocking put on a bounded queue (RequestChannel.scala:76-79; queued.max.requests, default 500). So if handlers fall behind, the network thread blocks, and every connection it owns stalls, including those with nothing to do with the slow work. Parsing and back-pressure share the thread (D59, class D, gotcha). That is read in the code and stated in the config's own doc string, "before blocking the network threads"; it was not measured here, and trunk was not checked.

The handler

A handler blocks up to 300 ms on the queue and charges the wait to the idle meter behind RequestHandlerAvgIdlePercent. It takes callback work first, because those requests "have already waited in line" (RequestChannel.scala:157-163). KafkaApis.handle is one match on the API key, and controller-owned APIs such as CreateTopics are forwarded rather than handled. Responses return through a per-processor deque with a selector wakeup, in five kinds: send, no-op, close, throttle start and throttle end (SocketServer.scala:920-945) from the code.

Two details keep the handlers honest about locks and threads. Finishing a parked operation after an append is not done on the spot. In the words of KafkaApis.scala:262-263, "In order to avoid conflicting locking, the actions to complete delayed requests are kept in a queue", and that queue is drained at the end of handle. And async work that finishes on some other thread is sent back through sendCallbackRequest, so that it runs again on a handler (KafkaRequestHandler.scala:73-83). So the request's path has a simple outline: socket, network thread, queue, handler, and then either a response on the deque or a parked operation.
