{{S}}One Produce, byte by byte

Here is one real request. A Java kafka-console-producer 4.4.0 sent the record hello-wire with acks=all and no compression, through a logging proxy on loopback. The frame was then decoded by hand, one field at a time, until every byte was accounted for measured here. Figure {{fig-bytes}} is all 139 bytes.

One convention, because the numbers would otherwise disagree. A frame's size field does not count itself. This frame's prefix says 135, so 139 bytes crossed the socket. Offsets and the total of 139 in this section include the 4-byte prefix. Every "frame of N bytes" elsewhere in this part is the prefix's own value, and leaves it out.

The header

The header version is not on the wire. It is derived from the key and the version, so the parser reads those two shorts first and rewinds. clients/…/common/requests/RequestHeader.java:126-127 from the code: 

            // We derive the header version from the request api version, so we read that first.
            // The request api version is part of `RequestHeaderData`, so we reset the buffer position after the read.

Flexible messages use request header v2 and response header v1. Request header v0 has been gone since 4.0. And at offset 12 is an oddity: the client id has a two-byte length, not a compact one, inside an otherwise compact header. message/RequestHeader.json:36-41 explains: 

    // The ClientId string must be serialized with the old-style two-byte length prefix.
    // The reason is that older brokers must be able to read the request header for any
    // ApiVersionsRequest, even if it is from a newer version.

That is one of two exceptions built so that a client and a broker that have never met can still talk. The other is in the response.

The body

Flexible versions replace fixed lengths with unsigned varints and add a tagged section to every component (docs/design/protocol.md:141). A compact length is stored plus one, so 0 can mean null. The capture shows all three cases: TransactionalId is 00, null; the topic and partition arrays are 02, one element; and in the response, RecordErrors is 01, empty.

Three bytes at the very end, offsets 136 to 138, are the partition, topic and request tag sections, each empty. Each costs one byte in every message that has nothing to say. They are what buys the ability to add fields later, and the schemas section shows that trade. Acks is ffff, or -1. TimeoutMs is 05dc, 1,500 ms, a number that matters in purgatory.

At offset 36 there is no topic name. Produce v13 replaced it with a topic id, as a pair of fields split at that version. message/ProduceRequest.json:61-63: 

      { "name": "Name", "type": "string", "versions": "0-12", "entityType": "topicName", "mapKey": true, "ignorable": true,
        "about": "The topic name." },
      { "name": "TopicId", "type": "uuid", "versions": "13+", "mapKey": true, "ignorable": true, "about": "The unique topic ID" },

So a proxy or sniffer needs a metadata lookup to name the topic in this capture (D99, class E, behaviour change; KAFKA-10551, first tag 4.1.0).

From offset 58 the frame stops being a Kafka API message and becomes a record batch, in the format Part 1 reads on disk. producerId 0, epoch 0 and sequence 0 are the idempotence fields, which Part 4 takes up. Records are not copied out of the request either: readRecords wraps a slice of the request buffer (clients/…/common/protocol/Readable.java:65-72) from the code.

The answer is a frame of 62 bytes: correlation id, one header tag byte, and then the result. These are the fields that matter, from the same decode, offsets again counting the prefix: 

   4  00000006            correlation id = 6
   8  00                  header tagged fields (header v1) = 0
  31  0000                ErrorCode = 0
  33  0000000000000000    BaseOffset = 0
  41  ffffffffffffffff    LogAppendTimeMs = -1
  61  00000000            ThrottleTimeMs = 0

The same batch, read back

A real kafka-console-consumer then fetched it, with Fetch v18. The request is a frame of 100 bytes, and it says how long the consumer is willing to wait and how little it will accept: MaxWaitMs 500, MinBytes 1, MaxBytes 52,428,800, IsolationLevel 0. Those two wait fields are exactly what purgatory enforces. SessionId and SessionEpoch are 0. The response frame is 150 bytes, and before any record it reports where the lines stand. From the same decode: 

  15  0eeff87d            SessionId = 250607741
  43  0000000000000001    HighWatermark = 1
  51  0000000000000001    LastStableOffset = 1
  59  0000000000000000    LogStartOffset = 0
  67  00                  AbortedTransactions len+1 (0=null) = 0
  68  ffffffff            PreferredReadReplica = -1
  72  4f                  Records len+1 = 79

The collection's claim is visible right here: every Fetch response carries the high watermark and the last stable offset as plain numbers, and Part 3 and Part 5 are about who moves them. The 78-byte batch starts at offset 73. Compare the two runs of bytes and exactly four differ, as Figure {{fig-two-directions}} shows measured here.

The four bytes are partitionLeaderEpoch, from ffffffff to 00000000. The broker stamped it. Base offset is broker-assigned as well and also outside the CRC. It matched here only because this was offset 0, so one capture cannot show that field moving. Part 1 has why those fields were left out of the CRC.

This is the collection's "disk format is wire format" with bytes attached, and the reason the read path can be cheap. Fetch response data can stay on disk until send, because non-memory records become their own Send. The plaintext transport hands the file channel straight to the socket. clients/…/common/network/PlaintextTransportLayer.java:213-215 from the code: 

    public long transferFrom(FileChannel fileChannel, long position, long count) throws IOException {
        return fileChannel.transferTo(position, count, socketChannel);
    }

TLS gives this up, and reads the file through a 32 KiB direct buffer to encrypt it. This topic did not observe sendfile itself; Part 1 did. Which thread issues it is read from the code, not traced: strace is absent on this box.
