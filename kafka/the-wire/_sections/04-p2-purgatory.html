{{S}}Parked, not waiting

Some requests cannot be answered yet. A Fetch at the end of the log has nothing to return. An acks=-1 Produce has written locally, but the followers have not caught up. If each of those held a handler thread, eight slow requests would stop the broker. They hold nothing. The handler does its work, builds a small object describing what it is waiting for, and goes back to the queue. That object is a DelayedOperation, and the place it sits is the purgatory. The socket stays muted, so the client sees one slow request, and the broker has spent a list entry on it from the code.

Parking has one subtle step. An event could arrive between "not done yet" and "watching for that event", and be missed forever. So the check runs twice, around the watch, under the operation's own lock. server-common/…/server/purgatory/DelayedOperation.java:115-127: 

    boolean safeTryCompleteOrElse(Action action) {
        lock.lock();
        try {
            if (tryComplete()) return true;
            else {
                action.apply();
                // last completion check
                return tryComplete();
            }
        } finally {
            lock.unlock();
        }
    }

Why the lock is held across all of it is written down at DelayedOperationPurgatory.java:133-154, as a "story about lock": a real three-thread deadlock with TransactionStateManager, and a warning that another stays possible if checkAndComplete is called under an exclusive lock. Only after the watch does an unfinished operation go on the timer. Watch lists are sharded into 512 buckets, and an event wakes waiters by key: checkAndComplete walks that key's list, retries each operation and drops the finished ones. Completion and expiry both go through forceComplete, guarded so that only one wins.

A Produce is born timed out

Only acks=-1 ever parks. acks=1 answers right after the local append (ReplicaManager.scala:1361-1367). By the time a Produce parks, its records are already in the leader's log, and KafkaApis drops its reference to them, "since it is already appended to log", so a parked Produce does not pin the request bytes (KafkaApis.scala:559-561). Then the constructor does the most revealing thing in this part. server/…/server/purgatory/DelayedProduce.java:110-122 from the code: 

        // first update the acks pending variable according to the error code
        produceStatus.forEach((topicPartition, status) -> {
            if (status.responseStatus.error == Errors.NONE) {
                // Timeout error state will be cleared when required acks are received
                status.acksPending = true;
                status.responseStatus.error = Errors.REQUEST_TIMED_OUT;
            } else {
                status.acksPending = false;
            }

            LOGGER.trace("Initial partition status for {} is {}", topicPartition, status);
        });
    }

The pending answer is the timeout. Expiry has nothing to undo and no way to undo it: it sends what is already there. Success is the thing that gets written in, when Partition.checkEnoughReplicasReachOffset finds the replicas have caught up (Part 3 reads that check). A high-watermark rise wakes Produce, Fetch, DeleteRecords and ShareFetch waiters. An unchanged one wakes only Fetch.

The lab ran this on three nodes with replication factor 3, min.insync.replicas=2 and two followers stopped with SIGSTOP, in one run on loopback measured here: 

baseline acks=-1 all up: 49 ms 0 err 0
followers stopped, acks=1: 4 ms {'index': 0, 'error': 0, 'baseOffset': 1, ...}
followers stopped, acks=-1 timeout=3000: 3005 ms {'index': 0, 'error': 7, 'baseOffset': 2, ...}
followers stopped 2 s then SIGCONT, acks=-1 timeout=15000: 2013 ms {'index': 0, 'error': 0, 'baseOffset': 3, ...}
read-back hw 4 [(0, b'base'), (1, b'acks-1'), (2, b'timed-out-but-appended'), (3, b'released')]

Read line three, then line five. Error 7 is REQUEST_TIMED_OUT, and it arrived with a base offset. The record it refers to was read back after the followers resumed. A produce timeout does not say a record is absent (D55, class D, gotcha, confirmed by verification; trunk not checked). Line four shows the release: with the followers resumed after 2 seconds, the parked Produce came back clean at 2,013 ms, well inside its 15,000 ms timeout.

Which number to watch

Completed operations stay on watch lists until the key is touched again or a purge runs. So PurgatorySize can exceed the real number waiting. Figure {{fig-purgatory}} shows it at 2 right after an expiry and a new park, with one request waiting, and it falls when the key is next touched. The Fetch panel opens at 0,1 for the same reason: a stale entry from the earlier console consumer. Watch NumDelayedOperations instead (D58, class D; upstream not checked).

A parked Fetch

A Fetch answers at once if it does not want to wait, needs nothing, already has enough, hit an error, or found a diverging epoch or a preferred replica. Otherwise it parks. What counts as "enough bytes" depends on who is reading: the log end for followers, the high watermark for ordinary consumers, the last stable offset for read_committed. On completion it re-reads the log rather than reusing the first read. The lab's three runs match measured here: 

E3a expiry: empty fetch at LEO max_wait=6000 returned in 6005 ms, recordBytes 0 hw 2
E3b wake: fetch max_wait=20000 + produce at 2000ms: returned at 2004 ms; produce rtt 3 ; batch b'wake-up'
E3c min_bytes=1000: 100B at 1000ms stays parked, 1200B at 2003 ms; returned at 2009 ms, recordBytes 1440 batches 2

Expired operations run on a single executor-Fetch thread, so a timed-out Fetch's log read happens there and not on a handler. Expiry is therefore serial per purgatory. Whether a slow read delays other expiries was not measured (D60, class D; read in the code; upstream not checked).

The wait also has a place in the metrics. Request timing is split into queue, local, remote, response queue, response send and total, and purgatory time lands in remote. Seven consumer Fetches recorded a maximum RemoteTimeMs of 6,002 ms against a maximum LocalTimeMs of 25 ms. Fetch metrics appear under FetchConsumer and FetchFollower as well as Fetch, so a broker's own replication traffic can be separated measured here.
