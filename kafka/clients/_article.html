01Two threads around a queue

Producer and consumer guarantees stop at sessions and retries. Idempotence depends on broker state that can be absent or expired, and a consumer's position describes what was handed over, not what was finished. KIP-848 trades best-case speed for isolating a slow member. This collection reads Kafka as one append-only log used five times, with each promise a line in such a log. Part 1 read that log, Part 2 carried a request to it, and Part 3 read what an ack says. This part reads the clients at either end. Part 5 picks up where idempotence runs out.

Start with send(). It does not send. It runs on the caller's thread, hands bytes to an in-memory queue, and returns a future. One background thread, the Sender, does all the network work (producer/KafkaProducer.java:1110-1126, :513-515) from the code.

The order inside doSend is fixed: wait for metadata, serialize the key, serialize the value, choose a partition, check the size, append (KafkaProducer.java:1069-1105). So your serializer and any custom partitioner run on your thread. The queue is the RecordAccumulator: one ArrayDeque<ProducerBatch> per partition, and each deque is its own lock (producer/internals/RecordAccumulator.java:320-321). Appends and the Sender's checks contend per partition, not globally.

max.block.ms, 60 s by default, is one budget. Metadata time is subtracted before the append is called, and serializer and partitioner time are not counted (KafkaProducer.java:1076). The second wait is memory. buffer.memory, 32 MiB, is a pool of batch.size buffers with a free list, and only buffers of exactly that size are recycled (producer/internals/BufferPool.java:156, :484-488). Waiters queue FIFO. Past the timeout they get BufferExhaustedException. Memory exhaustion is back-pressure on your thread, not a dropped record, until the budget runs out.

Append is careful about that wait. It tries the last batch under the lock, allocates a buffer outside the lock, then retakes the lock and tries again before creating a batch, because another thread may have made one while this one blocked on memory (RecordAccumulator.java:326-343). A record larger than batch.size is not an error. It gets its own larger buffer (:332-333), limited by max.request.size and buffer.memory. Such a buffer goes back as raw accounting and leaves to the garbage collector. batch.size=0 means a batch size of 1, which the builder treats as one record per batch (KafkaProducer.java:458).

Waking the Sender is rarer than people assume. KafkaProducer.java:1122-1125: 

            if (result.batchIsFull || result.newBatchCreated) {
                log.trace("Waking up the sender since topic {} partition {} is either full or getting a new batch", record.topic(), appendCallbacks.getPartition());
                this.sender.wakeup();
            }

Later records appended to a non-full batch do not wake it, because the Sender already sleeps for the remaining linger.

Errors from send() come back two ways: ApiException through the future and callback, anything else thrown at the caller (KafkaProducer.java:1128-1146). A producer that only checks the future misses InterruptException. One that only uses try/catch misses timeouts.

On the other side, sendProducerData is the pipeline in Figure 1 (producer/internals/Sender.java:383-453). One Produce carries batches for many partitions led by one node, at most one per partition, and the broker rejects two (common/requests/ProduceRequest.java:228-230). max.request.size bounds the request, but a single oversized batch still goes alone (RecordAccumulator.java:937-940). Each node keeps a rotating drain index, so a large partition set cannot starve its tail. Callbacks fire in append order on the Sender thread (producer/internals/ProducerBatch.java:322-331), so a slow callback stalls I/O for every partition. flush() makes every partition sendable and waits for all batches, split ones included. On shutdown the Sender keeps running until undrained batches and in-flight requests are done, unless forced (Sender.java:258-295). A close() whose timeout expires is what turns unsent records into failures.

Two more things happen on that one thread. Closing a batch is the expensive step, and it runs outside the deque lock. This is where the v2 header from Part 1, with its producer ID, epoch and base sequence, gets written (RecordAccumulator.java:976-978). And a partition with an unknown leader makes the Sender request metadata while its batches stay queued, subject only to the delivery timeout (:765).

02What linger actually does

Linger is usually described as "wait a little to batch more". The test is simpler, and it has more exits than that. producer/internals/RecordAccumulator.java:656-667 from the code: 

        if (!readyNodes.contains(leader) && !isMuted(part)) {
            long timeToWaitMs = backingOff ? retryBackoff.backoff(backoffAttempts > 0 ? backoffAttempts - 1 : 0) : lingerMs;
            boolean expired = waitedTimeMs >= timeToWaitMs;
            boolean transactionCompleting = transactionManager != null && transactionManager.isCompleting();
            boolean sendable = full
                    || expired
                    || exhausted
                    || closed
                    || flushInProgress()
                    || transactionCompleting;
            if (sendable && !backingOff) {
                readyNodes.add(leader);

Three details change how this reads. linger.ms is measured from the batch's creation, not from the last append, so new records do not extend the wait (ProducerBatch.java:98, :484). A partition with more than one queued batch counts as full, so once a batch is closed behind another the head stops lingering (RecordAccumulator.java:759). And exhausted means a thread is waiting on the pool: a full pool cancels linger for every partition (:713).

Batching also happens at linger.ms=0. A node that cannot take another request leaves the drain set, so records pile into batches while requests are in flight (Sender.java:403-408). Linger is not the only source of batches. The limit that triggers this, max.in.flight.requests.per.connection, is 5 per connection, not per partition (InFlightRequests.java:98-99). A due metadata refresh gates sending the same way (NetworkClient.java:586). Linger's default has been 5 ms since 4.0, and that upgrade changes behaviour for anyone who relied on 0 (register D103, class E, behaviour change, documented).

At a low rate, linger sets the batch: at 1,000 records/s, 0, 5 and 50 ms gave 4.2, 7.3 and 53.1 records per request. The perf tool throttles in bursts, so part of the 4.2 is its burstiness. At a high rate batch.size takes over: at 20,000 records/s, linger 5 and 50 both reached about 78 records, the 16 KiB limit. Linger 5 averaged 17.65 ms produce latency and linger 50 averaged 8.33 ms, the reverse of what queueing predicts. That gap is noise, which is why only the batch counts should be read.

Too small a batch.size collapses the producer: 1,024 bytes took 30,004 requests against 1,551, and queue time rose to 6,277 ms from 14 ms. Raising it to 262,144 cut requests to 803 at about 31.5 KB per batch, well below the limit, because the batch leaves on linger first. Compression fits more records in a batch by the ratio it achieves, because batch.size bounds estimated compressed bytes. That estimate learns asymmetrically, 0.05 up and 0.005 down, on purpose (common/record/internal/CompressionRatioEstimator.java:29-31). When it is wrong and the broker answers MESSAGE_TOO_LARGE, the client splits the batch and resends without spending a retry (Sender.java:678-688). That split matters again below.

One warning about the tool itself. --command-property keeps only its last occurrence when repeated, silently. An invalid first run of this table differed from the corrected one by a factor of 19.5 (register D78, class D, gotcha; upstream status not checked).

03Choosing a partition

The order is fixed: explicit partition, custom partitioner, key hash, then "unknown", which means the accumulator picks inside append (KafkaProducer.java:1557-1574) from the code. The key hash is toPositive(murmur2(key)) % numPartitions (producer/internals/BuiltInPartitioner.java:412). The mapping is a function of the partition count, so adding partitions moves keys. Per-key order holds only while the count does, and only per producer instance.

Unkeyed records stick to one partition until about batch.size bytes are appended, then switch. The switch waits for a batch boundary, up to twice that. BuiltInPartitioner.java:249-258: 

        if (producedBytes >= stickyBatchSize * 2) {
            log.trace("Produced {} bytes, exceeding twice the batch size of {} bytes, with switching set to {}",
                producedBytes, stickyBatchSize, enableSwitch);
        }

        if (producedBytes >= stickyBatchSize && enableSwitch || producedBytes >= stickyBatchSize * 2) {
            // We've produced enough to this partition, switch to next.
            StickyPartitionInfo newPartitionInfo = new StickyPartitionInfo(nextPartition(cluster));
            stickyPartitionInfo.set(newPartitionInfo);
        }

Counting bytes, not batches, is KIP-794's fix for a feedback loop: under the earlier partitioner, slow brokers held the sticky assignment longer and got more data. Adaptive partitioning, on by default, then picks the next partition by inverse queue length, and stays off until every partition has had a batch queued (RecordAccumulator.java:701-702). A custom partitioner turns it off entirely (KafkaProducer.java:448). New in 4.4, and off by default, partitioner.rack.aware applies only to the unkeyed choice. In one run, 60,000 unkeyed records over 6 partitions landed 8,096 to 12,364 per partition, at about 13.3 KB per batch measured here.

The clients disagree, and Figure 3 sets them side by side. The librdkafka column was read, not run. Its unkeyed sticky partitioner switches on time, sticky.partitioning.linger.ms, by default twice the linger, which is the pre-KIP-794 idea in a different form (librdkafka/src/rdkafka_msg.c:1140-1141). franz-go switches at 64 KiB, not at batch.size.

Keyed placement is the practical trap. Java and franz-go agreed on all 1,000 test keys measured here. librdkafka's default hashes with CRC32. Its figure is computed from the formula with its own crc_table, at 12 partitions, and librdkafka was not run: 85 of 1,000 keys match Java. That is near the 1-in-12 chance rate, it scales as 1/N, and it is not a property of those keys. The same key lands elsewhere unless partitioner=murmur2_random is set, which the config text names as the Java equivalent (librdkafka/src/rdkafka_conf.c:1836, register D77, class D, gotcha). franz-go's own comment is stale: "This client's default is to disable lingering", where the default has been 10 ms since v1.20.0 (franz-go/pkg/kgo/partitioner.go:273, register D31, class C, doc drift, still on master).

04Idempotence, and where it runs out

enable.idempotence is on by default, and it is built on a TransactionManager even with no transactions. A producer gets a producer ID (PID) from any broker, at epoch 0, from a block of 1,000 leased from the controller. Every instance burns a fresh PID, and a restart cannot resume the old one (core/…/coordinator/transaction/TransactionCoordinator.scala:127-130). Sequence numbers are per partition, count records, and are assigned at drain, not at send. Once assigned they never change on retry. RecordAccumulator.java:958-967 from the code: 

                    // If the batch already has an assigned sequence, then we should not change the producer id and
                    // sequence number, since this may introduce duplicates. In particular, the previous attempt
                    // may actually have been accepted, and if we change the producer id and sequence here, this
                    // attempt will also be accepted, causing a duplicate.
                    //
                    // Additionally, we update the next sequence number bound for the partition, and also have
                    // the transaction manager track the batch so as to ensure that sequence ordering is maintained
                    // even if we receive out of order responses.
                    batch.setProducerState(producerIdAndEpoch, transactionManager.sequenceNumber(batch.topicPartition), isTransactional);
                    transactionManager.incrementSequenceNumber(batch.topicPartition, batch.recordCount);

The other half is on the broker. Per partition and per PID it keeps a ProducerStateEntry: the epoch and the metadata of the last 5 batches. NUM_BATCHES_TO_RETAIN is why the client's limit is 5. A duplicate is an exact match, with no partial case. log/ProducerStateEntry.java:128-137: 

    Optional<BatchMetadata> findDuplicateBatch(RecordBatch batch) {
        return batch.producerEpoch() != producerEpoch ? Optional.empty() : batchWithSequenceRange(batch.baseSequence(), batch.lastSequence());
    }

    // Return the batch metadata of the cached batch having the exact sequence range, if any.
    private Optional<BatchMetadata> batchWithSequenceRange(int firstSeq, int lastSeq) {
        return batchMetadata.stream()
            .filter(metadata -> firstSeq == metadata.firstSeq() && lastSeq == metadata.lastSeq())
            .findFirst();
    }

A match is answered with the first write's offsets and writes nothing, so the callback looks like a first-time success (log/UnifiedLog.java:1261-1270). Anything else must start exactly one past the last sequence, unless the broker has no epoch for this PID. log/ProducerAppendInfo.java:186-188: 

            // If there is no current producer epoch (possibly because all producer records have been deleted due to
            // retention or the DeleteRecords API) accept writes with any sequence number
            if (!(currentEntry.producerEpoch() == RecordBatch.NO_PRODUCER_EPOCH || inSequence(currentLastSeq, appendFirstSeq))) {

With no state, a late retry is just new data. Every edge below comes from that condition, or from the client's half of the bargain.

The case it was built for

A proxy swallowed one response and closed the connection, a fault injected on purpose. Broker and client were real. Without idempotence the log holds two copies and the callback names the second offset. With it, the same request bytes arrive twice, one copy lands, and the callback gets offset 0. franz-go behaved the same way in both cases.

Order, and the first-batch overtake

Muting a partition is only used when max.in.flight=1 (Sender.java:420-424). With 5 in flight, order rests on the sequence check: a failed head makes every later request fail too, and they retry in sequence order. That needs the broker to have a last sequence to compare against. On a producer's first batch to a partition it has none.

Reject A while B is in flight. The broker has no state, so B lands at a non-zero sequence. A then fails OUT_OF_ORDER_SEQUENCE_NUMBER on every retry, 9 in the proxy run, until the delivery timeout expires it. With idempotence on and acks=all, the log holds B and not A. This is not silent: the application gets a TimeoutException for A, and B stays. An application that logs the failure and moves on has a hole in its order.

It needs no proxy. A batch over the topic's max.message.bytes is split while the next batch lands, in 5 of 5 runs, and max.in.flight=1 kept order. Those sizes were chosen to force it. In practice the route would be a wrong compression estimate or a batch.size above the topic limit, and neither was run. How often this happens in production is unknown; nothing here measures it. Transactions v2 producers are excluded by the check at ProducerAppendInfo.java:158-163 (KAFKA-18202).

Upstream knows, and its position is mixed. The never-written case (register D7, class B) is fixed after 4.4.0 in 81b993044e, KAFKA-15591, fix version 4.5.0, absent from the 4.4 branch. Its commit message says "silent", which is true only if callbacks are ignored. The case of a partition that already holds records (register D4, class A) stands: a non-zero first sequence can be legitimate there after retention or expiry. KAFKA-19880 reports it and is Open; KAFKA-14312 was closed Won't Fix in 2024 as not a bug. It stands on trunk by the fix commit's own statement; trunk was not run. By reading, this path is a fatal error in librdkafka, not run. franz-go holds back pipelining until the first ack, a gate built for this race and not run here (franz-go/pkg/kgo/sink.go:1285-1291).

What "failed" means

The delivery timeout also fires on batches already in flight. Sender.java:195-205: 

                    if (batch.hasReachedDeliveryTimeout(accumulator.getDeliveryTimeoutMs(), now)) {
                        iter.remove();
                        // expireBatches is called in Sender.sendProducerData, before client.poll.
                        // The !batch.isDone() invariant should always hold. An IllegalStateException
                        // exception will be thrown if the invariant is violated.

                            expiredBatches.add(batch);
                        } else {
                            throw new IllegalStateException(batch.topicPartition + " batch created at " +

A batch's final state cannot change once set, so a late broker success is only a debug log line (ProducerBatch.java:301-302). "Failed" means unknown. The docs warn: "avoid application level re-sends since these cannot be de-duplicated" (KafkaProducer.java:177-178). The message does not (register D74, class D, gotcha, documented).

kgo enforces its timeout only when safe, never on a record whose request has no answer yet (franz-go/pkg/kgo/config.go:1507-1512), and it marks a batch unsure when the broker's answer leaves the outcome open. franz-go/pkg/kgo/sink.go:1081-1088:

	// a retryable error the NEXT time we produce, we still are unsure of
	// the final state, and we need to block canceling producing.

Two more ends, and the traps in the config

Producer state expires. With producer.id.expiration.ms set to 3 s, a 500 ms check, and a proxy withholding the response for 6 s, the log held the same PID, epoch and sequence twice, and the callback said success. That 3 s is a lab setting, not default behaviour. The default is 24 h, checked every 10 min, against a 2 min delivery timeout. With defaults the same result needs retention or DeleteRecords to remove the write, or an old CreateTime, because the clock is record time; that route was read, not run (register D79, class D, documented in part).

delivery.timeout.ms is documented as "An upper bound", and there is one case where it is not. While InitProducerId cannot complete, a pass of the Sender returns early and never reaches expiry. Sender.java:333-344:

With two controllers killed (Part 3), a first idempotent Java producer's record stayed pending for 210 s against an 8 s timeout, over 1,943 InitProducerId round trips, all errorCode=14. In a second run, with the quorum restored, it failed at once when the PID arrived: "92904 ms has passed since batch creation". Config conflicts differ by case. acks=1 or retries=0 turn idempotence off with an INFO log as the only signal (D75, class D). max.in.flight=6 throws, though the doc says conflicts disable idempotence (D30, class C, still at trunk). DUPLICATE_SEQUENCE_NUMBER handling is dead against a 4.4 broker, because in-window duplicates get success (D76, class D). franz-go 5d3342df, dated 2026-10-06, changes what follows a failed sent batch, so check which side you pin (D104, class E).

05A pull loop and a stored number

A consumer pulls. A fetch reads only up to the high watermark, or the last stable offset under read_committed (server-common/…/server/storage/log/FetchIsolation.java:31-39) from the code. With nothing to return it parks in purgatory, as Part 2 showed, for fetch.min.bytes=1 or fetch.max.wait.ms=500.

The Java client fetches per broker, with at most one request in flight per node. It also skips a node entirely while any of that node's partitions still has buffered data, so that the omitted partitions do not fall out of the fetch session (consumer/internals/AbstractFetch.java:462-469). That is why routine Java traffic never queues behind the muted socket. The one exception is the session-closing Fetch. Sessions keep the loop cheap, since every fetch would otherwise relist every partition, and losing one heals itself with a full fetch. max.poll.records, 500 by default, applies when the client drains its buffer. It limits what poll() returns, not what the broker sends.

Now the line this section is about. The in-memory position advances when records are handed to poll(), before the application has processed them (consumer/internals/FetchCollector.java:185-204). Auto-commit commits allConsumed(), the current positions, inside the next poll(), every 5 s by default (consumer/internals/SubscriptionState.java:797-801). A single-threaded loop therefore gets at-least-once. A SIGKILL redelivered 34 and 52 records in two single runs measured here.

A commit is a record. A group lives on one __consumer_offsets partition, chosen by the Java hash of the group id, and that partition's leader is its coordinator. Here is a real commit of new OffsetAndMetadata(42L, "hello"), which carries no leader epoch, decoded by hand, with the long line wrapped measured here:

Offsets are kept 7 days, but expiry only touches topics the group is not subscribed to. They disagree by design, up to 5 s with auto-commit, and neither counts records (register D84, class D). The project's docs state that exactly-once for other destination systems needs cooperation from those systems (docs/design/design.md:207), which Part 5 takes up.

06The barrier and the heartbeat

Groups decide who owns what. The classic protocol is a five-state machine around one barrier: any change moves the group to PreparingRebalance, heartbeats tell members to come, and their join requests park until everyone is in or a timer fires. group/GroupMetadataManager.java:7847-7858 from the code: 

        if (group.hasAllMembersJoined()) {
            // All members have joined. Proceed to sync phase.
            return completeClassicGroupJoin(group);
        } else {
            timer.schedule(
                classicGroupJoinKey,
                group.rebalanceTimeoutMs(),
                TimeUnit.MILLISECONDS,
                false,
                () -> completeClassicGroupJoin(group.groupId())
            );
            return EMPTY_RESULT;

That timeout is the largest across the group, and the Java client sets it from max.poll.interval.ms, 5 minutes, so one busy member can hold a rebalance open that long (clients/GroupRebalanceConfig.java:55). A heartbeat during PreparingRebalance still renews the session, so heartbeats keep a stuck member alive while it holds up the group. The broker never computes a classic assignment: the leader gets the member list in its join response and returns the assignment in SyncGroup.

Under eager, a client revokes every partition before it rejoins. Under cooperative it revokes only those it no longer owns, keeps the rest during the rebalance, and needs a follow-up round whenever a partition moves (KIP-429). The Java default lists Range and CooperativeSticky, and the client takes the highest protocol all listed assignors share, so the out-of-the-box classic consumer is eager (consumer/internals/ConsumerCoordinator.java:257-271).

KIP-848: one member at a time

KIP-848 replaces Join, Sync and Heartbeat with one RPC, where the epoch does the signalling: 0 joins, −1 leaves, −2 is a static member stepping out. A heartbeat updates the member, updates the target assignment if the group epoch is ahead, and reconciles this member. The broker computes the assignment, inline on the heartbeat path, and client-side assignors from the KIP's design are not implemented. An offload setting defaults to true, but nothing at the pin reads it, and the configs became internal (register D32, class C, doc drift; getters only at trunk). Reconciliation holds no barrier.     static boolean canComputeNextTargetAssignment(
        long assignmentTimestampMs,
        int assignmentIntervalMs,
        long currentTimeMs
    ) {
        // The next target assignment can be computed immediately
        //  * when there is no existing target assignment,
        //  * or we do not know when the existing target assignment was computed.
        if (assignmentTimestampMs == 0) {
            return true;
        }

        // The next target assignment can be computed immediately when the assignment interval is
        // zero. This provides an escape hatch if the wall clock undergoes a large backwards
        // correction.
        if (assignmentIntervalMs == 0) {
            return true;
        }

        // Otherwise, we wait for the assignment interval to elapse.
        return currentTimeMs >= assignmentTimestampMs + assignmentIntervalMs;
    }

Cooperative sits between them. Other partitions kept flowing, 89 ms global gap, but the joiner got nothing until the barrier cleared, 28 s against 5.5 s. It also redelivered 175 records in one run. A classic client refuses offset commits while rebalancing (ConsumerCoordinator.java:1312-1322), so partition 8 kept being consumed with commits failing, then moved. The refusal is read in code; the link to 175 is inferred, and it holds arithmetically: 175 ÷ 8.33 records/s is 21 s, and the rebalance was open about 22 s (register D82, class D, gotcha).

After a SIGKILL the group first reacted at about 44.7 s and 43 s, in one run each: the session timeout, plus the next heartbeat carrying the news. Then they differ. Under eager, 8 surviving partitions idled about 3.1 s, because one member's heartbeat came 3 s after the others' and the barrier waited for it, and why it was out of phase was not determined. Under the consumer protocol no surviving partition idled.

07Static members and share groups

group.instance.id gives a member an identity that outlives its process. A static classic member on the default close sends no LeaveGroup, and a rejoin during Stable with the same protocol just swaps the member id (group/GroupMetadataManager.java:8142-8143) from the code. Under KIP-848 a static leave writes epoch −2 and keeps the assignment for the returning instance. In one run under each protocol, a 10 s restart caused no rebalance: other partitions saw at most 148 ms gaps, and the member got its same two partitions back measured here. A static member still needs the session timer: CloseOptions.LEAVE_GROUP is how it leaves for good, and otherwise it is removed only when the session expires (consumer/internals/ConsumerMembershipManager.java:507-508).

The protocols treat a duplicate id in opposite ways (GroupMetadataManager.java:1723-1727, :7219-7226). Classic replaces the old holder, at its next heartbeat. Both consumed the same partitions for about 2.6 s, and that run counted 76 duplicate deliveries, which also include the newcomer re-reading from the last commit. KIP-848 refuses the newcomer with UNRELEASED_INSTANCE_ID, immediately, and the Java client treats that as fatal, so no duplicates. This is intended: KIP-848 says the new member "is rejected" and "the consumer should fail". It follows that a crashed static member, which never sent −2, blocks its own replacement until session expiry, 45 s by default. That was derived from code and the live-duplicate test; a crash-restart was not run end to end (register D80, class D, intended per KIP-848).

Share groups: leases, not ownership

Share groups, production-ready since 4.2, drop partition ownership. Several members can read one partition, and the broker holds per-record state: five states in the code, one more than KIP-932's four, because KIP-1191 added ARCHIVING for the dead-letter queue (server/…/server/share/fetch/RecordState.java:27-31). Defaults per partition: 2,000 record locks in flight, a 30 s lock and a delivery limit of 5. At the cap the partition just stops acquiring, so a slow consumer stalls it at 2,000 records.

The code also shrinks batches as the count rises (core/…/server/share/SharePartition.java:2006-2017). The lab shows only the last-attempt rule. An unacknowledged lock with a 15 s setting lapsed about 15 s later, and another consumer got the records with a raised count. The KIP itself says the delivery count is imprecise and delivery is at-least-once, and order is promised only within a batch. Durable state lives in __share_group_state, not __consumer_offsets, with snapshots after 500 updates. Acquisition is not persisted, and one unacknowledged record pins the start offset. share.auto.offset.reset defaults to latest, so records produced before the group first reads are skipped. The state topic defaults to 50 partitions, RF 3 and min ISR 2, so a cluster of fewer than three brokers must lower them first. The persisted start offset never moves backwards, whatever a stale writer sends (share-coordinator/…/coordinator/share/ShareCoordinatorShard.java:662-700).

Consumers acknowledge in one of two modes. In implicit mode the next poll() or commit acknowledges everything fetched. In explicit mode, unacknowledged records make it throw (consumer/internals/ShareConsumerImpl.java:1208-1220). There are four types: ACCEPT, RELEASE, REJECT and RENEW, the last extending a lock (KIP-1222). Assignment reuses the same rate-limited heartbeat path as KIP-848, with SimpleAssignor allowing several members on a partition, and a default limit of 200 members where consumer groups are unbounded. A default-bootstrapped 4.4 cluster had share groups usable without setting a feature flag by hand, and on disk acknowledged state is range-compressed, using state ids 0, 2 and 4 measured here. A lock-expiry release that fails to persist is applied anyway, so memory can run ahead of the state topic (SharePartition.java:3024; read, not run).

Three edges. In implicit mode, close() right after poll() releases that batch: 400 records were delivered and handed over, then left available at count 1 with lag 400. The Javadoc says so (consumer/KafkaShareConsumer.java:130), but finished work is redelivered and counts against the limit (register D81, class D, documented). The schema documents state ids 0:Available,2:Acked,4:Archived, while the lock-expiry path can persist 3 with a DLQ (register D33, class C; read, no DLQ run).
