{{S}}A pull loop and a stored number

A consumer pulls. A fetch reads only up to the high watermark, or the last stable offset under read_committed (server-common/…/server/storage/log/FetchIsolation.java:31-39) from the code. With nothing to return it parks in purgatory, as Part 2 showed, for fetch.min.bytes=1 or fetch.max.wait.ms=500.

The Java client fetches per broker, with at most one request in flight per node. It also skips a node entirely while any of that node's partitions still has buffered data, so that the omitted partitions do not fall out of the fetch session (consumer/internals/AbstractFetch.java:462-469). That is why routine Java traffic never queues behind the muted socket. The one exception is the session-closing Fetch. Sessions keep the loop cheap, since every fetch would otherwise relist every partition, and losing one heals itself with a full fetch. max.poll.records, 500 by default, applies when the client drains its buffer. It limits what poll() returns, not what the broker sends.

Now the line this section is about. The in-memory position advances when records are handed to poll(), before the application has processed them (consumer/internals/FetchCollector.java:185-204). Auto-commit commits allConsumed(), the current positions, inside the next poll(), every 5 s by default (consumer/internals/SubscriptionState.java:797-801). A single-threaded loop therefore gets at-least-once. A SIGKILL redelivered 34 and 52 records in two single runs measured here.

A commit is a record. A group lives on one __consumer_offsets partition, chosen by the Java hash of the group id, and that partition's leader is its coordinator. Here is a real commit of new OffsetAndMetadata(42L, "hello"), which carries no leader epoch, decoded by hand, with the long line wrapped measured here:

Key: 00 01 is record type 1, then the group, the topic name and the partition. Value: version 4, eight bytes of offset (2a is 42), leader epoch −1, a compact string, the timestamp, then one tagged field holding the topic UUID. The key uses int16-length strings and the value is flexible, inside an ordinary v2 batch from Part 1. Classic, consumer-protocol and standalone groups all wrote this same shape.

Deleting an offset is a tombstone on the same key, which is what lets a compacted topic forget it. From a real segment, the second batch begins at 0x8b:

The last two bytes are the point: 01 is a zigzag −1, a null value, and 00 is zero headers. Commits append with requiredAcks = 1, and the runtime parks the response until the high watermark passes the written offset (core/…/coordinator/group/CoordinatorPartitionWriter.scala:169-172), so a commit answers only once that line in that log has moved. Offsets are kept 7 days, but expiry only touches topics the group is not subscribed to. A requireStable fetch reports UNSTABLE_OFFSET_COMMIT around an open transactional offset, though a service comment still says the coordinator cannot easily do that (register D34, class C, no effect).

Two lag numbers follow. kafka-consumer-groups reports end offset minus committed offset: 50 − 42 = 8 in the lab. The client's records-lag is high watermark or LSO minus position. They disagree by design, up to 5 s with auto-commit, and neither counts records (register D84, class D). The project's docs state that exactly-once for other destination systems needs cooperation from those systems (docs/design/design.md:207), which Part 5 takes up.
