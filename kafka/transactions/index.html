Exactly-once, as it isTeardown

A Kafka transaction is two logs agreeing after the fact: a decision in one, markers in others, a stall in between. This last part of a five-part teardown reads Apache Kafka 4.4.0 and takes one apart byte by byte: the coordinator's state machine, Transaction Version 2, a 78-byte marker, the last stable offset that stalls plain records too, the epoch fence, and KAFKA-20734, known upstream, where a marker for an offline partition is dropped and the coordinator says complete. That bug has no tagged fix as of 6 November 2026. The part ends where exactly-once ends, and with the whole collection's findings register.

01Two logs, one transaction

A Kafka transaction is two logs agreeing after the fact: a decision in one, markers in others, a stall in between, and a known bug when the marker has nowhere to go. Exactly-once stops where Kafka stops. This collection's claim is that Kafka is one log used five times, and that nearly every promise is a line in a log: which line, in which log, moved by whom. This part reads the last stable offset, the line that makes a transaction visible. It ends with the findings register for all five parts.

Every broker runs a transaction coordinator. A transactional id maps to one by hashing onto a partition of an internal topic, __transaction_state (core/…/txn/TransactionStateManager.scala:439). Changing that topic's partition count would break the mapping, so the coordinator refuses to load if the count moved (:645). The topic defaults to 50 partitions, replication factor 3, min ISR 2 and 100 MiB segments (TransactionLogConfig.java:32-45) from the code.

That topic is the first log. It is compacted, with the transactional id as the only key, so compaction keeps the latest state of each id (TransactionLogKey.json:19-23). It sets unclean.leader.election.enable=false whatever the cluster default says (core/…/txn/TransactionCoordinator.scala:1017-1019), and that flag does not stop last-known-leader election; that much is code reading, not run on this topic. The coordinator's memory follows its log: it updates only after the append is replicated with acks=-1, and the replication timeout is the transaction's own timeout, not request.timeout.ms (TransactionStateManager.scala:802-803).

Each value stores the producer id and epoch, the timeout, the status byte, the partitions and two timestamps. PreviousProducerId, NextProducerId, NextProducerEpoch and ClientTransactionVersion are tagged fields of value version 1 (TransactionLogValue.json:28-50). Some of that schema promises more than the code does: PreviousProducerId always holds the current id in practice, and nobody sets NextProducerEpoch (D36, D37).

A client's requested timeout above the broker's cap fails InitProducerId outright. The cap defaults to 15 minutes; the Java client default is 60 seconds (TransactionStateManager.scala:436, ProducerConfig.java:579-581). A null transactional id takes the short path: a fresh producer id at epoch 0 and no log write. That is the plain idempotent producer from Part 4 (TransactionCoordinator.scala:127-130).

The second log is every data partition the transaction touches. It keeps state of its own: the leader's ProducerStateManager tracks each producer's epoch and open transaction, with a sorted map of open transactions and a second map of decided-but-unreplicated ones (ProducerStateManager.java:89-93). Nothing but markers joins the two.

Commit, in order

EndTxn first appends PREPARE_COMMIT or PREPARE_ABORT to the transaction log (TransactionCoordinator.scala:856-857). That durable record is the decision. The client gets its reply next, before any marker is written. core/…/txn/TransactionCoordinator.scala:973-979: 

                case Right((txnMetadata, newPreSendMetadata)) =>
                  // we can respond to the client immediately and continue to write the txn markers if
                  // the log append was successful
                  responseCallback(Errors.NONE, newPreSendMetadata.producerId, newPreSendMetadata.producerEpoch)

                  txnMarkerChannelManager.addTxnMarkersToSend(coordinatorEpoch, txnMarkerResult, txnMetadata, newPreSendMetadata)
              }

Markers are grouped by partition leader and sent as WriteTxnMarkers by one dedicated sender thread per broker, over its own network client (TransactionMarkerChannelManager.scala:123, :345). The leader appends each with acks=-1 as a coordinator-origin write, unless the partition is in __consumer_offsets, where it goes through the group coordinator (KafkaApis.scala:1834-1835, :1872-1874). As each partition acks, it leaves the transaction's partition set; when the set is empty the coordinator writes COMPLETE_* (TransactionMarkerRequestCompletionHandler.scala:138-139) from the code.

Retries have no count limit: disconnects and not-leader or not-enough-replicas errors re-enqueue against possibly new leaders (:149-158). Two endings are final. INVALID_PRODUCER_EPOCH or TRANSACTION_COORDINATOR_FENCED drops the marker for good, and UNSUPPORTED_* removes the partition as if done (:160-166). A third ending, an empty leader lookup, is the subject of Hanging, and KAFKA-20734.

Decided, not visible

The lab probed the coordinator straight after commitTransaction or abortTransaction returned, in all 10 commits and 3 aborts across Java TV2, Java TV0 and franz-go. Every one showed PrepareCommit or PrepareAbort measured here. That shows COMPLETE_* not yet applied, not that no marker had landed. This is register D86. One init plus three transactions wrote ten records to __transaction_state, so under TV2 a transaction costs three coordinator writes: Ongoing, Prepare* and Complete*. After the last marker, describe-producers shows the partition holding the bumped epoch, last sequence -1 and no open transaction.

Markers land partition by partition. There is no global commit point, so a reader of two partitions can see one side of a committed transaction before the other reconstruction.

Eight states

There are eight states, and the status byte on disk is 0 to 7 (TransactionState.java:39-82). Two of them never reach the log. PREPARE_EPOCH_FENCE exists only as an in-memory pending state on the way to PREPARE_ABORT (TransactionMetadata.java:414-415), and DEAD is a tombstone plus removal from memory (:426). Every transition has two steps: prepareTransitionTo sets a pending state that blocks others, and completeTransitionTo applies it after the append (:341-349, :444). A request that arrives meanwhile gets the retriable CONCURRENT_TRANSACTIONS, not a queue slot (TransactionCoordinator.scala:439-444). The legal moves are a table of previous states. transaction-coordinator/…/TransactionState.java:94-103: 

    public static final Map<TransactionState, Set<TransactionState>> VALID_PREVIOUS_STATES = Map.of(
        EMPTY, Set.of(EMPTY, COMPLETE_COMMIT, COMPLETE_ABORT),
        ONGOING, Set.of(ONGOING, EMPTY, COMPLETE_COMMIT, COMPLETE_ABORT),
        PREPARE_COMMIT, Set.of(ONGOING),
        PREPARE_ABORT, Set.of(ONGOING, PREPARE_EPOCH_FENCE, EMPTY, COMPLETE_COMMIT, COMPLETE_ABORT),
        COMPLETE_COMMIT, Set.of(PREPARE_COMMIT),
        COMPLETE_ABORT, Set.of(PREPARE_ABORT),
        DEAD, Set.of(EMPTY, COMPLETE_ABORT, COMPLETE_COMMIT),
        PREPARE_EPOCH_FENCE, Set.of(ONGOING)
    );

02Transaction Version 2

transaction.version is a cluster feature with three levels. TV1 only turns on flexible log records. TV2 turns on the per-transaction epoch bump, and it is the latest production level (server-common/…/TransactionVersion.java:28-35). It is on by default from 4.0 (docs/getting-started/upgrade.md:280; register D106). KIP-890's wiki state still says "Approved"; the code wins (D38).

No request says which protocol it speaks. The broker infers it from wire versions: EndTxn above v4 means TV2, and AddPartitionsToTxn above v3, which only brokers send, also means TV2 (TransactionVersion.java:69-74). The Java client picks from the finalized feature it saw in ApiVersions, and upgrading mid-life forces an epoch bump first (TransactionManager.java:524-529) from the code.

Under TV2 the coordinator bumps the epoch at PREPARE_* (TransactionMetadata.java:248). That gives a retry a meaning: same epoch is the next transaction, epoch plus one is a retry (TransactionCoordinator.scala:795-800). A client can now abort with no partitions added, which bumps the epoch, but a commit from Empty is still INVALID_TXN_STATE (:739-743). A Java client sends no EndTxn at all if the transaction had no send or offset commit (TransactionManager.java:939-943). Server-side retry for the add stops at 100 ms total with a 20 ms backoff by default, then the client sees CONCURRENT_TRANSACTIONS (AddPartitionsToTxnConfig.java:30-35). The docs say TV2 moves this wait into produce latency without raising total transaction time (docs/operations/transaction-protocol.md:47) from the code.

A marker now carries a bumped epoch, so the leader's check tightens from "not older" to "strictly newer". An equal-epoch marker with no open transaction is let through and written again, a livelock fix (KAFKA-19999). So the log can hold a duplicate marker; the lab did not produce one. storage/…/log/ProducerAppendInfo.java:117-139: 

    private void checkProducerEpoch(short producerEpoch, long offset, short transactionVersion) {
        short current = updatedEntry.producerEpoch();
        boolean invalidEpoch = (transactionVersion >= 2) ? (producerEpoch <= current) : (producerEpoch < current);

        if (invalidEpoch) {
            // TV2 Idempotent Marker Retry Detection (KAFKA-19999):
            // When markerEpoch == currentEpoch and no transaction is ongoing, this indicates
            // a retry of a marker that was already successfully written. Common scenarios:
            // 1. Coordinator recovery: reloading PREPARE_COMMIT/ABORT from transaction log
            // 2. Network retry: marker was written but response was lost due to disconnection
            // In both cases, the transaction has already ended (currentTxnFirstOffset is empty).
            // We suppress the InvalidProducerEpochException and allow the duplicate marker to
            // be written to the log.
            // In some buggy scenarios we may start transaction with MAX_VALUE.  We allow
            // code to gracefully recover from that.
            if (transactionVersion >= 2 &&
                    producerEpoch == current &&
                    (updatedEntry.currentTxnFirstOffset().isEmpty() || producerEpoch == Short.MAX_VALUE)) {
                log.info("Idempotent transaction marker retry detected for producer {} epoch {}. " +
                                "Transaction already completed, allowing duplicate marker write.",
                        producerId, producerEpoch);
                return;
            }

Followers cannot apply that rule, because the version is not in the log. They use the looser check, which is why WriteTxnMarkers v2 carries the version to the leader only (KIP-1228). The rule hardened in 4.2 and relaxed for retries in 4.3 (D107). An epoch is a short with its top value reserved, so at one bump per transaction a producer id rotates after about 32,766 transactions, inside EndTxn; that was read, not run (D95).

Who runs it

franz-go opts in when the feature level is 2 and its versions are not capped below it (franz-go/pkg/kgo/client.go:1030-1034). At the pin it runs TV2 against 4.4.0, stepping the epoch once per transaction with markers one above data, as the Java client does measured here. A live kafka-features.sh downgrade to level 0 kept the Java client on one epoch throughout. librdkafka v2.16.0 does not run it: Produce caps at v10 and EndTxn at v1, and it relies on the broker's verification path for hanging defence (D94). That was read, never run. librdkafka/src/rdkafka_request.c:6686-6689: 

        int16_t ApiVersion = 0;

        ApiVersion = rd_kafka_broker_ApiVersion_supported(rkb, RD_KAFKAP_EndTxn,
                                                          0, 1, NULL);

Cost stayed unknown. Single perf runs on this shared machine did not rank the protocols: plain idempotent came out slowest at 6,655 records/s and TV0 at a 50 ms commit interval fastest at 16,767, a spread larger than any effect that could be attributed. That is not capacity, and not evidence that TV0 is faster.

03Markers on disk

Part 1 took a data batch apart. A marker is the same structure with one record in it: a batch with the transactional and control attribute bits set, sequence -1, carrying the producer id and epoch (MemoryRecords.java:710-714). The flags are bits 4 and 5 of the attributes (DefaultRecordBatch.java:134-135). The key is version and type, four bytes: ABORT is 0, COMMIT is 1, and KRaft reuses the same control-record space for types 2 to 6 (ControlRecordType.java:32-54). The value holds only the coordinator epoch (EndTxnMarker.json:22-23) from the code.

Here is one real log, from kafka-dump-log.sh reduced by exp1b.sh: three transactions and one plain record from another producer. Annotations on the right are payloads and marker types measured here.

04The last stable offset

A data partition does not know a transaction exists until its first transactional batch, which records the first offset (ProducerAppendInfo.java:239-242). The transaction's end on that partition is the marker and nothing else (:288). Between the two sits the offset every read_committed reader stops at. UnifiedLog.java:678-686: 

    public long lastStableOffset() {
        // cache the first unstable offset metadata to avoid a concurrent update breaking the isPresent check
        Optional<LogOffsetMetadata> firstUnstableOffsetMetadataCopy = firstUnstableOffsetMetadata;
        if (firstUnstableOffsetMetadataCopy.isPresent() && firstUnstableOffsetMetadataCopy.get().messageOffset < highWatermark()) {
            return firstUnstableOffsetMetadataCopy.get().messageOffset;
        } else {
            return highWatermark();
        }
    }

The LSO equals the first unstable offset, capped at the high watermark. The consumer config doc says the LSO "is the one less than the offset of the first open transaction" (ConsumerConfig.java:377). Code and lab show it equals that offset (D35).

"Unstable" covers two things: undecided transactions, and decided ones whose marker is still above the high watermark. So the LSO waits for marker replication too. storage/…/log/ProducerStateManager.java:246-258: 

    public Optional<LogOffsetMetadata> firstUnstableOffset() {
        Optional<LogOffsetMetadata> unreplicatedFirstOffset = Optional.ofNullable(unreplicatedTxns.firstEntry()).map(e -> e.getValue().firstOffset);
        Optional<LogOffsetMetadata> undecidedFirstOffset = Optional.ofNullable(ongoingTxns.firstEntry()).map(e -> e.getValue().firstOffset);

        if (unreplicatedFirstOffset.isEmpty())
            return undecidedFirstOffset;
        else if (undecidedFirstOffset.isEmpty())
            return unreplicatedFirstOffset;
        else if (undecidedFirstOffset.get().messageOffset < unreplicatedFirstOffset.get().messageOffset)
            return undecidedFirstOffset;
        else
            return unreplicatedFirstOffset;
    }

That state survives restarts. Producer state goes to .snapshot files, including an open transaction's first offset, which returns to ongoingTxns on load (ProducerStateManager.java:326). A producer entry with an open transaction never expires, while an idle one goes after producer.id.expiration.ms, default one day (:330). Both facts matter later.

Plain records wait too

The read bound is a single offset, so non-transactional records after an open transaction wait as well (UnifiedLog.java:1671; register D87). The lab opened a transaction at offset 1 and wrote three plain records after it (exp1.out, one run, loopback, relative only) measured here:

[  5.798s] read_uncommitted [0:before-0, 1:open-1, 2:plain-a, 3:plain-b, 4:plain-c]
[ 11.901s] read_committed   [0:before-0]

The LSO moved within about 15 ms of the commit returning. The first probe, 13 ms after return, had already moved, so that is an upper bound on one run, not a latency. The output above is trimmed by one line, HW=5 LSO=6. That line is a probe artefact: the driver reads HW and LSO in two separate ListOffsets calls, so it does not show LSO above HW.

Lag tools see none of this as lag. ListOffsets for latest under read_committed returns the LSO (Partition.scala:1442), so endOffsets said 1 while five records sat in the log, and lag computed from it reads "caught up". The signal is the per-partition LastStableOffsetLag gauge, HW minus LSO (Partition.scala:226) from the code.

How long can it last? For a dead producer, the transaction's timeout plus up to one 10 s scan interval (see Hanging). So about 70 s at the Java default of 60 s, and about 15 minutes 10 s at the broker's default cap. Those two figures are arithmetic from the configs, not runs reconstruction. The stall is partition-wide for that whole time, and it also holds back compaction (LogCleaner.java:87-89).

The client does the filtering

The broker's read_committed fetch filters nothing. It caps the read at the LSO and attaches the overlapping aborted transactions (UnifiedLog.java:1673, LocalLog.java:546). clients/…/consumer/internals/CompletedFetch.java:208-224: 

                if (fetchConfig.isolationLevel == IsolationLevel.READ_COMMITTED && currentBatch.hasProducerId()) {
                    // remove from the aborted transaction queue all aborted transactions which have begun
                    // before the current batch's last offset and add the associated producerIds to the
                    // aborted producer set
                    consumeAbortedTransactionsUpTo(currentBatch.lastOffset());

                    long producerId = currentBatch.producerId();
                    if (containsAbortMarker(currentBatch)) {
                        abortedProducerIds.remove(producerId);
                    } else if (isBatchAborted(currentBatch)) {
                        log.debug("Skipping aborted record batch from partition {} with producerId {} and " +
                                        "offsets {} to {}",
                                partition, producerId, currentBatch.baseOffset(), currentBatch.lastOffset());
                        nextFetchOffset = currentBatch.nextOffset();
                        continue;
                    }
                }

Walk it over the log above, assuming one fetch from offset 0. Offsets 0 to 2 are not in any aborted range. At offset 4 the queue yields the entry for producer 1001 that begins there, so batches 4 and 5 are skipped, and the abort marker at 6 removes the producer from the set. Offset 8 is read normally reconstruction. So aborted bytes cross the wire and sit in the log, and the offsets of aborted records and markers leave permanent gaps. The isolation default differs by client: Java and franz-go use read_uncommitted, librdkafka read_committed (D93).

Pending offsets stall reads differently. The Java consumer always asks for stable offsets, at either isolation level, so while a transaction holds pending offsets it gets UNSTABLE_OFFSET_COMMIT and retries rather than reading a stale position (ConsumerCoordinator.java:1502). In the lab, while offsets are pending in an open transaction, consumer.committed on that partition retried until its timeout. The admin client does not retry: with requireStable=true and the partition named it returned an empty map after 12 ms, because the handler logs a warning and drops any partition with an error (ListConsumerGroupOffsetsHandler.java:179; D89). The result looks like "no offset" measured here.

05Fencing and a dead coordinator

A transactional id keeps its producer id across restarts and gets the next epoch (TransactionMetadata.java:161-190). That bump is the fence. If a transaction is open, the coordinator bumps the epoch, aborts it, and replies CONCURRENT_TRANSACTIONS, so the new producer retries and bumps a second time (TransactionCoordinator.scala:283-285). The check itself is on the partition leader: a data batch with an older epoch than the partition has seen is rejected (ProducerAppendInfo.java:119-151) from the code.

A rejection needs a partition that has seen the new epoch. The abort marker delivers it to each partition of the old transaction, so that marker does the fencing reconstruction.

The zombie's exception changes as it goes. Send and commit report the abortable InvalidProducerEpochException. Its abortTransaction then reaches the coordinator and gets ProducerFencedException, and it is fatally fenced (D88). A franz-go zombie is fenced on data with INVALID_PRODUCER_EPOCH, but its first error on EndTransaction is OPERATION_NOT_ATTEMPTED, raised by franz-go itself, with a doc saying retry with TryAbort (franz-go/pkg/kgo/txn.go:717-719, :856) measured here.

Offsets are one more partition

Offsets join a transaction by treating the group's __consumer_offsets partition as one more participant (KafkaApis.scala:2046-2049). On disk they are a transactional batch followed by a control marker, the same shape as data measured here. Pending offsets sit in a separate per-producer map; a commit marker moves them to the main store, and an abort drops them (OffsetMetadataManager.java:1214-1216). When a regular and a transactional commit mix, the one with the higher record offset wins (:1283-1286). TxnOffsetCommit carries generation or member epoch, so a member rebalanced away is fenced by the group coordinator; KIP-447 added this so one producer per consumer can replace one per input partition.

The coordinator dies

Coordinator failover has its own fence. The marker's coordinator epoch, which is the transaction log partition's leader epoch, must not go backward (ProducerAppendInfo.java:247-252). A new coordinator rebuilds its state by reading the partition from log start to log end, last value per key winning. During the load, requests get COORDINATOR_LOAD_IN_PROGRESS. Then it finishes every PREPARE_* it found. core/…/txn/TransactionStateManager.scala:563-575: 

          loadedTransactions.forEach((transactionalId, txnMetadata) => {
            txnMetadata.inLock(() => {
              // if state is PrepareCommit or PrepareAbort we need to complete the transaction
              txnMetadata.state match {
                case TransactionState.PREPARE_ABORT =>
                  transactionsPendingForCompletion +=
                    new TransactionalIdCoordinatorEpochAndTransitMetadata(transactionalId, coordinatorEpoch, TransactionResult.ABORT, txnMetadata, txnMetadata.prepareComplete(time.milliseconds()))
                case TransactionState.PREPARE_COMMIT =>
                  transactionsPendingForCompletion +=
                    new TransactionalIdCoordinatorEpochAndTransitMetadata(transactionalId, coordinatorEpoch, TransactionResult.COMMIT, txnMetadata, txnMetadata.prepareComplete(time.milliseconds()))
                case _ =>
                // nothing needs to be done
              }

An ONGOING transaction needs no action: its start timestamp was persisted, so the timeout clock still runs from the original start (:573-574). A failed COMPLETE_* append with COORDINATOR_NOT_AVAILABLE retries forever with the pending state retained (TransactionMarkerChannelManager.scala:322-336). A stale coordinator detects a changed epoch after its append callback fires and reports NOT_COORDINATOR (TransactionStateManager.scala:773).

The lab killed a coordinator in PrepareCommit with the data leader stopped by SIGSTOP, so no marker could land. The leader was stopped about 6 s, under the 9 s broker session, and it was back before the new coordinator appeared, so this is the healthy-reload case (exp2d.out, one run, loopback, relative only) measured here:

Coordinator epoch 1 shows the new coordinator wrote the marker. So the decision survives a crash, provided the partition has a leader when the successor sends. Without one, the same kill loses the marker, which the next section takes up. With the coordinator killed while ONGOING, a separate run saw the next send stall 7.9 s and the commit take 410 ms, with nothing lost and the partition loaded in 39 ms. That stall is probably the data leader failing over, not the coordinator: a send on a partition with an open transaction does not call the coordinator (UnifiedLog.java:897), and the driver did not record that leader. One run, loopback; it is not a recovery figure.

06Hanging, and KAFKA-20734

A hanging transaction is a partition that believes a transaction is open while the coordinator will never send its marker reconstruction. KIP-890 names three symptoms: LSO stuck, compaction blocked, read_committed consumers stuck. Nothing clears it, because only the coordinator's knowledge drives the timeout. core/…/txn/TransactionStateManager.scala:128-143: 

  def timedOutTransactions(): Iterable[TransactionalIdAndProducerIdEpoch] = {
    val now = time.milliseconds()
    inReadLock(stateLock, () => {
      transactionMetadataCache.flatMap { case (_, entry) =>
        entry.metadataPerTransactionalId.asScala.filter { case (_, txnMetadata) =>
          if (txnMetadata.pendingTransitionInProgress) {
            false
          } else {
            txnMetadata.state match {
              case TransactionState.ONGOING =>
                // Do not apply timeout to distributed two phase commit transactions.
                (!txnMetadata.isDistributedTwoPhaseCommitTxn) &&
                (txnMetadata.txnStartTimestamp + txnMetadata.txnTimeoutMs < now)
              case _ => false
            }
          }

For a transaction the coordinator does know, that scan works. It runs every 10 s by default, and the clock starts at the first partition added, not at beginTransaction. Activity does not extend it. The abort goes through the fence path, so a slow but live producer finds itself fenced. A producer killed mid-transaction with a 15 s timeout held the LSO for about 21.3 s after its send, inside that bound measured here.

The old way in, and its defence

KIP-890 part 1 makes the partition leader ask the coordinator before the first transactional write, and guards the answer with a unique token against an ABA race with an abort marker (UnifiedLog.java:1430-1434). It is on by default through a broker config and unconditional for TV2 requests (ReplicaManager.scala:1014). The lab used a client that deliberately skips the add. That is a stand-in for KIP-890's delayed-message race, and it is not that race (exp4.out, one run) measured here:

Two tools exist, and kafka/docs describes neither (D39). kafka-transactions.sh find-hanging compares producer state on a broker with the coordinator's description, with a 15 minute default window (TransactionsCommand.java:560, :689). abort writes an ABORT marker on one partition by start offset. It has no commit mode (:107, :194; D91). A PartitionsWithLateTransactionsCount gauge flags a leader whose oldest open transaction's last write is older than the maximum transaction timeout plus five minutes (ProducerStateManager.java:132).

At replication factor 3

Replication does not stop this; it narrows it. The verifier reran it at RF 3 with min.insync.replicas=2 and ELR on. A one-of-three leader kill was the control: leader=5 isr=[5, 6], commit in 30 ms, COMMIT marker on disk, clean. 07What exactly-once does not cover

The design doc draws the line itself. Exactly-once is for "reading, processing and writing data on Kafka topics", and "Exactly-once delivery for other destination systems generally requires cooperation with such systems" (docs/design/design.md:207). For external sinks its prescription is not two-phase commit. It is to store the consumer's offset beside the output (:205) from the code.

Inside the line, the mechanism is the one this part has read. The consumer's position is a message in an internal topic, so the program writes offset and output in one transaction (:203). The markers then decide both together, and the epoch shuts out a zombie. That guarantee needs all of it: the program must send offsets through the producer, its output readers must opt into read_committed, and its producer must hold a stable transactional id reconstruction.

The lab ran that line. One read-process-write program took 20 inputs, wrote each to a Kafka topic in a transaction and to a local file, and crashed once before commit, after 7 records. The 7 is the driver's crashAfter argument, a dial measured here, one run: 

[  7.689s] crash after 7 records, before commit
crash exit; external lines so far: 7
[ 35.112s] drained, processed 20
external lines: 27 unique: 20
duplicates: r0 r1 r2 r3 r4 r5 r6
read_committed eout: records 20 unique 20
read_uncommitted eout: records 27 unique 20

KIP-98 itself lists what a consumer does not get: all of a committed transaction together, given compaction, segment deletion, seeks and partial subscriptions. Markers are per partition, so there is no global commit point. commitTransaction returns before markers, so an immediate read_committed read can miss the commit. That read-your-writes gap is reasoned from the code reconstruction; the lab never caught a stale read.

Compaction meets transactions too. The cleaner removes aborted data batches regardless of keys, and cannot go past the first unstable offset, so an open transaction holds compaction back (LogCleaner.java:87-89). Markers stay until no batch of their transaction remains, then until the delete horizon, sharing tombstone retention (Cleaner.java:330-335). The last marker of an active producer stays as an empty batch, to preserve the epoch for fencing (:344-345).

Kafka 4.4 has broker-side scaffolding for external two-phase commit (KIP-939), off by default, with its key operation unimplemented: keepPreparedTxn returns UNSUPPORTED_VERSION (TransactionCoordinator.scala:145-146), still so on trunk's coordinator check, and InitProducerId v6 is still marked unstable. No target release is on the KIP page.

franz-go's GroupTransactSession takes a different trade: it favours aborting if any rebalance happens before commit, instead of blocking the rebalance (franz-go/pkg/kgo/txn.go:55-57). It defaults to a 40 s transaction timeout and ReadUncommitted, so its users must also opt in on the read side (config.go:679, :1792).

The run also had a void first attempt, kept in the log because it shows a dependency. The restart's 12 s idle window ended before the dead member's 45 s session did, so it processed nothing (exp1.out § F). A transaction says nothing about when a group gets its partitions back. Part 4 reads that side.

Five lines, one reading

This is where the collection's claim comes back. Nearly every promise Kafka makes is a statement about where a line sits in a log, not about a disk or an outcome. The recovery point says what a restart will not recheck. The high watermark says every in-sync member's page cache has it. The metadata commit says a quorum of voters has it. The committed offset records a position, and a position says what was handed over, not what was finished. The last stable offset says the markers below it have landed and replicated. Read a guarantee as which line, in which log, moved by whom, and both the guarantee and its edge follow.
