{{S}}Hanging, and KAFKA-20734

A hanging transaction is a partition that believes a transaction is open while the coordinator will never send its marker reconstruction. KIP-890 names three symptoms: LSO stuck, compaction blocked, read_committed consumers stuck. Nothing clears it, because only the coordinator's knowledge drives the timeout. core/…/txn/TransactionStateManager.scala:128-143: 

  def timedOutTransactions(): Iterable[TransactionalIdAndProducerIdEpoch] = {
    val now = time.milliseconds()
    inReadLock(stateLock, () => {
      transactionMetadataCache.flatMap { case (_, entry) =>
        entry.metadataPerTransactionalId.asScala.filter { case (_, txnMetadata) =>
          if (txnMetadata.pendingTransitionInProgress) {
            false
          } else {
            txnMetadata.state match {
              case TransactionState.ONGOING =>
                // Do not apply timeout to distributed two phase commit transactions.
                (!txnMetadata.isDistributedTwoPhaseCommitTxn) &&
                (txnMetadata.txnStartTimestamp + txnMetadata.txnTimeoutMs < now)
              case _ => false
            }
          }

For a transaction the coordinator does know, that scan works. It runs every 10 s by default, and the clock starts at the first partition added, not at beginTransaction. Activity does not extend it. The abort goes through the fence path, so a slow but live producer finds itself fenced. A producer killed mid-transaction with a 15 s timeout held the LSO for about 21.3 s after its send, inside that bound measured here.

The old way in, and its defence

KIP-890 part 1 makes the partition leader ask the coordinator before the first transactional write, and guards the answer with a unique token against an ABA race with an abort marker (UnifiedLog.java:1430-1434). It is on by default through a broker config and unconditional for TV2 requests (ReplicaManager.scala:1014). The lab used a client that deliberately skips the add. That is a stand-in for KIP-890's delayed-message race, and it is not that race (exp4.out, one run) measured here: 

=== transaction.partition.verification.enable=true
InitProducerId v1 error=0 producerId=1 epoch=0
Produce v8 partition=0 error=48 baseOffset=-1
=== transaction.partition.verification.enable=false
Produce v8 partition=0 error=0 baseOffset=0
HW=1 LSO=0 state=Empty coordinator=1 pid=1 epoch=0 partitions=[]

With verification off, the partition holds an open transaction, the coordinator says Empty, and the 10 s transaction timeout did nothing over a 25 s watch (D90; the config does not affect TV2 requests). Old clients see misleading translations of these errors (D92).

Two tools exist, and kafka/docs describes neither (D39). kafka-transactions.sh find-hanging compares producer state on a broker with the coordinator's description, with a 15 minute default window (TransactionsCommand.java:560, :689). abort writes an ABORT marker on one partition by start offset. It has no commit mode (:107, :194; D91). A PartitionsWithLateTransactionsCount gauge flags a leader whose oldest open transaction's last write is older than the maximum transaction timeout plus five minutes (ProducerStateManager.java:132).

At replication factor 3

Replication does not stop this; it narrows it. The verifier reran it at RF 3 with min.insync.replicas=2 and ELR on. This is one run, on seven combined nodes, so the coordinator lived on a node outside the partition's replicas and survived with every replica down. A one-of-three leader kill was the control: leader=5 isr=[5, 6], commit in 30 ms, COMMIT marker on disk, clean. Then the replicas died in two steps until off leader=none isr=[] elr=[5, 6], with the transaction spanning that partition and a healthy one (verify-d/v2_rf3.out) measured here.

The commit returned OK in 9 ms. The coordinator logged "likely deleted" and went to CompleteCommit. The healthy partition's record was readable. After all three replicas restarted, the other two records were hidden from read_committed and returned by read_uncommitted, with HW=2 LSO=0. That is one committed transaction, half visible. The same producer's next transaction on that partition, aborted, made the split permanent for read_committed: no exception, one ABORT at offset 3, .txnindex with firstOffset: 0 lastOffset: 3. The bytes stay.

Not run: simultaneous loss of all three, a partial return, and a 3-broker cluster with RF 3 everywhere, where "all replicas down" also takes the coordinator. That route is inferred.

A pause, and when it loses the marker

No kill is needed, but a pause alone does not lose the marker. It is lost if the lookup runs while the partition has no leader. Three runs, one each: five nodes, single-replica topics, SIGSTOP only, default 9 s session (verify-d/v1_pause.out) measured here.

Two earlier runs (exp2b.out, exp2c.out) lost the marker with a pause that outlasted the session, but those also killed the coordinator.

The fix returns Node.noNode() for a known partition with no endpoint, which sends markers down the existing retry path. That is read in code only: no fixed release is tagged and trunk was not built. The lookup at tag 4.3.2 is the same as at the pin; 4.3.2 was read, not run.
