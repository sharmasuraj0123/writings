{{S}}Transaction Version 2

transaction.version is a cluster feature with three levels. TV1 only turns on flexible log records. TV2 turns on the per-transaction epoch bump, and it is the latest production level (server-common/…/TransactionVersion.java:28-35). It is on by default from 4.0 (docs/getting-started/upgrade.md:280; register D106). KIP-890's wiki state still says "Approved"; the code wins (D38).

No request says which protocol it speaks. The broker infers it from wire versions: EndTxn above v4 means TV2, and AddPartitionsToTxn above v3, which only brokers send, also means TV2 (TransactionVersion.java:69-74). The Java client picks from the finalized feature it saw in ApiVersions, and upgrading mid-life forces an epoch bump first (TransactionManager.java:524-529) from the code.

Under TV2 the coordinator bumps the epoch at PREPARE_* (TransactionMetadata.java:248). That gives a retry a meaning: same epoch is the next transaction, epoch plus one is a retry (TransactionCoordinator.scala:795-800). A client can now abort with no partitions added, which bumps the epoch, but a commit from Empty is still INVALID_TXN_STATE (:739-743). A Java client sends no EndTxn at all if the transaction had no send or offset commit (TransactionManager.java:939-943). Server-side retry for the add stops at 100 ms total with a 20 ms backoff by default, then the client sees CONCURRENT_TRANSACTIONS (AddPartitionsToTxnConfig.java:30-35). The docs say TV2 moves this wait into produce latency without raising total transaction time (docs/operations/transaction-protocol.md:47) from the code.

A marker now carries a bumped epoch, so the leader's check tightens from "not older" to "strictly newer". An equal-epoch marker with no open transaction is let through and written again, a livelock fix (KAFKA-19999). So the log can hold a duplicate marker; the lab did not produce one. storage/…/log/ProducerAppendInfo.java:117-139: 

    private void checkProducerEpoch(short producerEpoch, long offset, short transactionVersion) {
        short current = updatedEntry.producerEpoch();
        boolean invalidEpoch = (transactionVersion >= 2) ? (producerEpoch <= current) : (producerEpoch < current);

        if (invalidEpoch) {
            // TV2 Idempotent Marker Retry Detection (KAFKA-19999):
            // When markerEpoch == currentEpoch and no transaction is ongoing, this indicates
            // a retry of a marker that was already successfully written. Common scenarios:
            // 1. Coordinator recovery: reloading PREPARE_COMMIT/ABORT from transaction log
            // 2. Network retry: marker was written but response was lost due to disconnection
            // In both cases, the transaction has already ended (currentTxnFirstOffset is empty).
            // We suppress the InvalidProducerEpochException and allow the duplicate marker to
            // be written to the log.
            // In some buggy scenarios we may start transaction with MAX_VALUE.  We allow
            // code to gracefully recover from that.
            if (transactionVersion >= 2 &&
                    producerEpoch == current &&
                    (updatedEntry.currentTxnFirstOffset().isEmpty() || producerEpoch == Short.MAX_VALUE)) {
                log.info("Idempotent transaction marker retry detected for producer {} epoch {}. " +
                                "Transaction already completed, allowing duplicate marker write.",
                        producerId, producerEpoch);
                return;
            }

Followers cannot apply that rule, because the version is not in the log. They use the looser check, which is why WriteTxnMarkers v2 carries the version to the leader only (KIP-1228). The rule hardened in 4.2 and relaxed for retries in 4.3 (D107). An epoch is a short with its top value reserved, so at one bump per transaction a producer id rotates after about 32,766 transactions, inside EndTxn; that was read, not run (D95).

Who runs it

franz-go opts in when the feature level is 2 and its versions are not capped below it (franz-go/pkg/kgo/client.go:1030-1034). At the pin it runs TV2 against 4.4.0, stepping the epoch once per transaction with markers one above data, as the Java client does measured here. A live kafka-features.sh downgrade to level 0 kept the Java client on one epoch throughout. librdkafka v2.16.0 does not run it: Produce caps at v10 and EndTxn at v1, and it relies on the broker's verification path for hanging defence (D94). That was read, never run. librdkafka/src/rdkafka_request.c:6686-6689:

Cost stayed unknown. Single perf runs on this shared machine did not rank the protocols: plain idempotent came out slowest at 6,655 records/s and TV0 at a 50 ms commit interval fastest at 16,767, a spread larger than any effect that could be attributed. That is not capacity, and not evidence that TV0 is faster.
