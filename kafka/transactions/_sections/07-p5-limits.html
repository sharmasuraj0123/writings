{{S}}What exactly-once does not cover

The design doc draws the line itself. Exactly-once is for "reading, processing and writing data on Kafka topics", and "Exactly-once delivery for other destination systems generally requires cooperation with such systems" (docs/design/design.md:207). For external sinks its prescription is not two-phase commit. It is to store the consumer's offset beside the output (:205) from the code.

Inside the line, the mechanism is the one this part has read. The consumer's position is a message in an internal topic, so the program writes offset and output in one transaction (:203). The markers then decide both together, and the epoch shuts out a zombie. That guarantee needs all of it: the program must send offsets through the producer, its output readers must opt into read_committed, and its producer must hold a stable transactional id reconstruction.

The lab ran that line. One read-process-write program took 20 inputs, wrote each to a Kafka topic in a transaction and to a local file, and crashed once before commit, after 7 records. The 7 is the driver's crashAfter argument, a dial measured here, one run: 

[  7.689s] crash after 7 records, before commit
crash exit; external lines so far: 7
[ 35.112s] drained, processed 20
external lines: 27 unique: 20
duplicates: r0 r1 r2 r3 r4 r5 r6
read_committed eout: records 20 unique 20
read_uncommitted eout: records 27 unique 20

KIP-98 itself lists what a consumer does not get: all of a committed transaction together, given compaction, segment deletion, seeks and partial subscriptions. Markers are per partition, so there is no global commit point. commitTransaction returns before markers, so an immediate read_committed read can miss the commit. That read-your-writes gap is reasoned from the code reconstruction; the lab never caught a stale read.

Compaction meets transactions too. The cleaner removes aborted data batches regardless of keys, and cannot go past the first unstable offset, so an open transaction holds compaction back (LogCleaner.java:87-89). Markers stay until no batch of their transaction remains, then until the delete horizon, sharing tombstone retention (Cleaner.java:330-335). The last marker of an active producer stays as an empty batch, to preserve the epoch for fencing (:344-345).

Kafka 4.4 has broker-side scaffolding for external two-phase commit (KIP-939), off by default, with its key operation unimplemented: keepPreparedTxn returns UNSUPPORTED_VERSION (TransactionCoordinator.scala:145-146), still so on trunk's coordinator check, and InitProducerId v6 is still marked unstable. No target release is on the KIP page.

franz-go's GroupTransactSession takes a different trade: it favours aborting if any rebalance happens before commit, instead of blocking the rebalance (franz-go/pkg/kgo/txn.go:55-57). It defaults to a 40 s transaction timeout and ReadUncommitted, so its users must also opt in on the read side (config.go:679, :1792).

The run also had a void first attempt, kept in the log because it shows a dependency. The restart's 12 s idle window ended before the dead member's 45 s session did, so it processed nothing (exp1.out § F). A transaction says nothing about when a group gets its partitions back. Part 4 reads that side.

Five lines, one reading

This is where the collection's claim comes back. Nearly every promise Kafka makes is a statement about where a line sits in a log, not about a disk or an outcome. The recovery point says what a restart will not recheck. The high watermark says every in-sync member's page cache has it. The metadata commit says a quorum of voters has it. The committed offset records a position, and a position says what was handed over, not what was finished. The last stable offset says the markers below it have landed and replicated. Read a guarantee as which line, in which log, moved by whom, and both the guarantee and its edge follow.
