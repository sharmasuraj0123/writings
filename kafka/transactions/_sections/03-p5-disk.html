{{S}}Markers on disk

Part 1 took a data batch apart. A marker is the same structure with one record in it: a batch with the transactional and control attribute bits set, sequence -1, carrying the producer id and epoch (MemoryRecords.java:710-714). The flags are bits 4 and 5 of the attributes (DefaultRecordBatch.java:134-135). The key is version and type, four bytes: ABORT is 0, COMMIT is 1, and KRaft reuses the same control-record space for types 2 to 6 (ControlRecordType.java:32-54). The value holds only the coordinator epoch (EndTxnMarker.json:22-23) from the code.

The ABORT marker differs in key (0000 0000), epoch, timestamp and CRC. A commit writes nothing else. An abort also writes .txnindex, four int64s and a version short per entry (AbortedTxn.json:22-31), and that is the whole file here, 34 bytes: 

00000000: 0000 0000 0000 0000 03e9 0000 0000 0000   ................
00000010: 0004 0000 0000 0000 0006 0000 0000 0000   ................
00000020: 0007                                      ..

Version 0, producer 1001, first offset 4, last offset 6, LSO 7. The last offset is the marker's, not the last data record's. The index belongs to the segment holding the marker, even when the transaction began in an earlier one (TransactionIndex.java:44-46), and the stored LSO lets a fetch stop scanning once an entry reaches its upper bound (:171-175). A marker for a partition with no open transaction changes no LSO and adds no entry (ProducerAppendInfo.java:281-282). The two commits added nothing to this file. Sequence numbers restart at 0 with each epoch, and the marker carries -1 measured here.
