01The commit ladder

An acks=all ack says the record reached the page cache of every in-sync replica, and that the in-sync set met a floor. It says nothing about disk. The metadata log, which does fsync, decides who is in that set, so losing it freezes the line while data keeps moving. This collection's claim is that Kafka is one log used five times, and that nearly every promise is a line in a log: which line, in which log, moved by whom. This part reads the high watermark and the metadata commit. All-replica loss here runs on a mock.

Part 1 left a record in one broker's file. To reach another broker it has to be asked for. Followers pull. A follower's fetcher thread does two things in a loop: truncate whatever is marked for truncation, then fetch (core/…/server/AbstractFetcherThread.scala:112-114). A follower append runs the same append as a leader append, and takes the leader's offsets instead of assigning its own (UnifiedLog.java:1094-1097) from the code.

There is no replication ack. The offset a follower asks for in its next Fetch is its log end offset (LEO) as far as the leader knows, because updateFollowerFetchState takes it from the read (core/…/cluster/Partition.scala:1313-1321). A fetch offset is an ack. The leader keeps six fields per follower: log start, LEO, the leader's LEO at the last fetch, last fetch time, last caught-up time and broker epoch (ReplicaState.java:32-39) from the code.

The broker accepts three acks values. acks=1 answers straight after the leader's local append. Only acks=-1 waits, parked in the purgatory Part 2 reads (ReplicaManager.scala:1370, :1364-1366, :913-916). It is also the only value that meets a durability check before the append. core/…/cluster/Partition.scala:1227-1243: 

    val (info, leaderHWIncremented) = inReadLock(leaderIsrUpdateLock, () => {
      leaderLogIfLocal match {

The rule for the line sits in one method. The new high watermark (HW) is the smallest LEO among the leader, the maximal ISR, and any replica outside the ISR that is caught up and eligible to join. core/…/cluster/Partition.scala:1010-1033: 

  private def maybeIncrementLeaderHW(leaderLog: UnifiedLog, currentTimeMs: Long = time.milliseconds): Boolean = {
    if (isUnderMinIsr) {
      trace(s"Not increasing HWM because partition is under min ISR(ISR=${partitionState.isr})")
      return false
    }
    // maybeIncrementLeaderHW is in the hot path, the following code is written to
    // avoid unnecessary collection generation
    val leaderLogEndOffset = leaderLog.logEndOffsetMetadata
    var newHighWatermark = leaderLogEndOffset
    remoteReplicasMap.forEach { (_, replica) =>
      val replicaState = replica.stateSnapshot

      def shouldWaitForReplicaToJoinIsr: Boolean = {
        replicaState.isCaughtUp(leaderLogEndOffset.messageOffset, currentTimeMs, replicaLagTimeMaxMs) &&
        isReplicaIsrEligible(replica.brokerId)
      }

      // Note here we are using the "maximal", see explanation above
      if (replicaState.logEndOffsetMetadata.messageOffset < newHighWatermark.messageOffset &&
          (partitionState.maximalIsr.contains(replica.brokerId) || shouldWaitForReplicaToJoinIsr)
      ) {
        newHighWatermark = replicaState.logEndOffsetMetadata
      }
    }

Three details in that method matter later. The first return is strict min ISR: below min.insync.replicas the HW does not move at all, whichever acks the writes used. A caught-up replica outside the ISR holds the HW back on purpose, otherwise it would chase a moving line on a sole-ISR leader and never rejoin (:995-997). "Maximal" means a pending ISR change counts in the stricter direction: an expansion counts the new member at once, and a shrink keeps waiting for the departing one until the controller confirms (:1614-1615, :1640-1641) from the code.

The leader's TRACE log shows the gap. The offset is exclusive, so "offset 1299" asks for the record at 1298 (kafka.cluster.Partition=TRACE, single run) measured here: 

[2026-11-06 16:25:18,579] TRACE [Partition t-0 broker=2] Progress awaiting ISR acks for offset 1299: acked: HashSet(broker 2: 1299), awaiting HashSet(broker 3: 1298, broker 4: 1298) (kafka.cluster.Partition)

Below the HW, readers split by line: followers read to the LEO, read_uncommitted consumers to the HW, read_committed consumers to the last stable offset (FetchIsolation.java:32-37). A follower learns the HW only from a Fetch response and clamps it to its own LEO, so its HW trails the leader's by at least one round trip (ReplicaFetcherThread.scala:143). On disk the HW is a checkpoint, written every 5 s by default and on clean shutdown, so after a restart it is a stale hint (ReplicaManager.scala:265) from the code.

A floor, not a quorum

min.insync.replicas does not say how many acks are enough. It says how few members the ISR may have. With a full ISR, every member must catch up, and the config's own doc says so. clients/…/common/config/TopicConfig.java:222-223: "then all three replicas must acknowledge an acks=all write for it to succeed, even if min.insync.replicas happens to be less than 3." The register lists this as D63, class D (gotcha), documented. The defaults are the weak half of the pair: the producer defaults to acks=all, the broker to min.insync.replicas=1 and default.replication.factor=1, so a default acks=all on a default topic is one copy (ServerLogConfigs.java:155, ReplicationConfigs.java:42).

Who counts as caught up is a time test with an exact-LEO escape hatch (ReplicaState.java:66). The javadoc above it has the subtraction backwards (D22, class C, doc drift, still on trunk). So acks=all commits when the slowest ISR member's next fetch arrives.

One test turns that into an answer. core/…/cluster/Partition.scala:968-979:

02What the ack promises

That test is Partition.checkEnoughReplicasReachOffset, and it is everything an acks=all success means. Two conditions: the HW has passed the record, and the maximal ISR is at least the effective min ISR (Partition.scala:969-979). Neither mentions a disk. The design doc defines "committed" by the same two conditions and states the guarantee in one sentence. docs/design/design.md:309: "The guarantee that Kafka offers is that a committed message will not be lost, as long as there is at least one in sync replica alive, at all times." from the code

Read that test's other branch too. When the HW has passed but the ISR has since dropped below min, the answer is NOT_ENOUGH_REPLICAS_AFTER_APPEND: an error, for a record that is committed. The exception is retriable, which is a duplicate path without idempotence (Errors.java:225). The record is there; the client is told otherwise. D55 collects the cases.

Now the disk. By default Kafka never fsyncs on a timer or on a message count: both knobs default to Long.MAX_VALUE (ServerLogConfigs.java:101, :109). The only flush in the append path is the message-count check Part 1 quotes, and leader and follower appends share it, so neither side syncs before an ack (UnifiedLog.java:1300). The follower half of that is code reading plus the recovery points below; the fsync-counting shim ran at replication factor 1.

Two things do get fsynced by default: a rolled segment, asynchronously, on the scheduler, up to the new segment's base offset; and everything, on clean shutdown (UnifiedLog.java:2242-2245). A real flush covers the log and its offset, time and transaction indexes, then moves the recovery point (LogSegment.java:631-634) from the code. In the run counted in Part 1, about 15,573 records were acked into a topic whose .log saw one fsync, from kafka-scheduler, for the roll, in a window of about 25 s with segment.bytes=8388608 and replication factor 1. At the 1 GiB default that window has no roll measured here.

Here is the same thing at replication factor 3. Two topics, about 2,000 acked records each, and the checkpoint read 70 s later, past its 60 s interval. Topic t has defaults; tf has flush.messages=1 (./a_hw_isr.sh, one run) measured here: 

t+0184.0s HW t=t:0:2005  HW tf=tf:0:2000
t+0184.0s n2 recovery-point: tf 0 2000 t 0 0
t+0184.0s n3 recovery-point: tf 0 2000 t 0 0
t+0184.0s n4 recovery-point: tf 0 2000 t 0 0

2,005 acknowledged records sat above a recovery point of 0 on all three replicas. flush.messages=1 kept the recovery point at the HW. The label matters: a recovery point of 0 shows Kafka did not flush. Kernel writeback may still have written the bytes. That writeback runs on the kernel's clock, and no Kafka line records it. The HW checkpoint on every replica did agree with the leader's HW, once its 5 s timer had fired.

That gives three lines on one partition, moved by three different actors. Fetches move the HW. The scheduler moves the recovery point. The kernel moves the bytes, and tells nobody. Part 1 shows what depends on the second: CRCs are checked only above the recovery point.

The design, not an oversight

None of this is hidden. docs/operations/hardware-and-os.md:64: "Note that durability in Kafka does not require syncing data to disk, as a failed node will always recover from its replicas." Two lines on, :66: "We recommend using the default flush settings which disable application fsync entirely." The register files this as D41, class D, status intended. The design doc gives the cost of the alternative as "two to three orders of magnitude" (design.md:335). That figure was not reproduced here.

"Will always recover" has an edge: it is not true when the failed node is elected before the others. That is D18, class C, minor, because it falls outside the design doc's stated guarantee, and its example, which §05 walks through, is measured-vs-mock. KIP-966's Motivation names the same scenario: the last ISR member loses unflushed data, is re-elected, and followers truncate to it. Its next sentence states the limit: "MinISR-1 tolerance to data loss unclean shutdown events".

So the ack is a statement about the HW. It moves on fetches, and fetches read page cache. Replication covers one machine going away, not a window in which every copy loses its unflushed tail. How often that window opens on real hardware was not measured here.

03Two ways out of the ISR

Every ISR member holds the HW down, so a stuck member holds every acks=all ack. The ladder only moves again when somebody removes it. Two detectors can, and they run in different processes.

The first is the leader's lag check. It runs every replica.lag.time.max.ms / 2, so with the 30 s default a stuck follower can hold acks for up to 45 s if nothing else removes it (ReplicaManager.scala:284-285). Stuck and slow are one case: the same lastCaughtUpTimeMs test, with no offset-lag threshold anywhere (Partition.scala:1149). The leader proposes and the controller decides. One ISR change is in flight per partition, and most rejections leave it stuck in that pending state until new metadata arrives (:877, :1725) from the code.

The second never involves the leader. When a broker's session expires, the controller strips it from every ISR (metadata/…/controller/ReplicationControlManager.java:1433-1434). The session default is 9 s with a 2 s heartbeat, shorter than the lag limit, so a dead or frozen broker normally leaves through fencing (KRaftConfigs.java:40, :44). A broker that keeps heartbeating while its fetcher is stuck is the case the lag check exists for reconstruction.

Coming back

The rejoin test is shorter than people expect. core/…/cluster/Partition.scala:907-911:

    leaderLogIfLocal.exists { leaderLog =>
      val followerEndOffset = followerReplica.stateSnapshot.logEndOffset
      followerEndOffset >= leaderLog.highWatermark && leaderEpochStartOffsetOpt.exists(followerEndOffset >= _)

HW and the start of the current epoch, not the leader's LEO. Records between HW and LEO may still be unread. The epoch clause exists because committed data can sit between a new leader's HW and LEO, and a follower admitted too early could be elected and lose it (:865-867). The replica must also be unfenced, not shutting down, and on a matching broker epoch, checked by the leader and again by the controller (:929-931) from the code.

The design doc says more than the code does. docs/design/design.md:335: "it must fully re-sync again even if it lost unflushed data in its crash." Only the missing suffix is fetched, and an elected replica does not re-sync at all (D19, class C, doc drift, still at trunk 09f2dc1320). Part 1 shows the local half: recovery only has to produce a clean prefix.

04Forks and truncation

Replicas diverge when leadership moves. Kafka's answer is a number stamped in every batch: the leader epoch. Each replica rebuilds its epoch-to-start-offset map from those stamps as it appends (UnifiedLog.java:1226-1229). A new leader records its epoch's start offset as its current LEO, and never truncates itself: everything up to its LEO becomes authoritative, including records never committed under the old leader (Partition.scala:636-638, :649) from the code.

A follower of a new leader does not truncate first either. It keeps fetching from its LEO and carries its last epoch, and the leader decides. If that epoch does not match the leader's cache, the leader returns an empty read plus a diverging-epoch hint (:1401-1408). A diverging fetch does not count as progress (:1313). An epoch's end offset is the start of the next higher epoch the leader knows (LeaderEpochFileCache.java:297). The follower truncates to the lower of the two end offsets, or to an intermediate point if it does not know that epoch, and asks again (AbstractFetcherThread.scala:634-641). The truncating fetch applies no data, so the follower never exposes a HW over bytes it is about to delete (:357-359). Purgatory does not delay any of it: a parked follower fetch completes as soon as divergence is seen (DelayedFetch.scala:109).

Every epoch-bearing read also compares epochs: an older request is fenced, a newer one told to retry (Partition.scala:375-378). A deposed leader finds out on its next request. That sentence is the whole problem, as a frozen leader shows.

The last known leader

The first time a partition goes leaderless, the controller records its last leader in lastKnownElr (PartitionChangeBuilder.java:493-498). metadata/…/controller/PartitionChangeBuilder.java:286-295, then :305-315, with a comment between them elided: 

    private boolean canElectLastKnownLeader() {
        if (!eligibleLeaderReplicasEnabled || !useLastKnownLeaderInBalancedRecovery) {
            log.trace("Try to elect last known leader for {}-{} but elrEnabled={}, useLastKnownLeaderInBalancedRecovery={}",
                    topicId, partitionId, eligibleLeaderReplicasEnabled, useLastKnownLeaderInBalancedRecovery);
            return false;
        }
        if (!targetElr.isEmpty() || !targetIsr.isEmpty()) {
            log.trace("Try to elect last known leader for {}-{} but ELR/ISR is not empty. ISR={}, ELR={}",
                    topicId, partitionId, targetIsr, targetElr);
            return false;
        if (partition.lastKnownElr.length != 1) {
            log.trace("Try to elect last known leader for {}-{} but lastKnownElr does not only have 1 member. lastKnownElr={}",
                    topicId, partitionId, Arrays.toString(partition.lastKnownElr));
            return false;
        }
        if (!isAcceptableLeader.test(partition.lastKnownElr[0])) {
            log.trace("Try to elect last known leader for {}-{} but last known leader is not alive. last known leader={}",
                    topicId, partitionId, partition.lastKnownElr[0]);
            return false;
        }
        return true;

Last-known-leader election runs without consulting unclean.leader.election.enable, as KIP-966's Delivery plan specifies: intended, a design choice, not a coding error. It is flagged unclean and sets RECOVERING. No production switch exists: the field defaults to true, and its setter has callers only in tests (:104, :180). It compares nothing, because KIP-966's Unclean Recovery half has no code at this pin (D20, class C). The ops doc says only "This is a similar behavior prior to the 4.0 when all the replicas are offline" (eligible-leader-replicas.md:35), and leaves out the flag and the unclean label (D21, class C, still on trunk).

This is simulated damage on one host (./e34_tail_loss.sh, E4). With unclean.leader.election.enable at its default of false, min.insync.replicas=2 and acks=all, the last leader came back without its tail, was elected anyway, and 987 of 2,000 acked records were deleted from all three replicas, including two that still held them. The other two replicas were SIGKILLed and kept their bytes, so this models one machine lost plus two process deaths. Half the file was cut by hand, so 987 is a dial set by the mock, not a loss rate. KIP-966 promises MinISR-1 tolerance; this has two unclean exits at min ISR 2. No real power cut was run. D62 files it as class D, intended per KIP-966's Delivery plan.

The controls isolate the bytes. With no cut, the same kill-and-restart sequence and the same election kept all 2,000. With a clean ELR member (V3), 0 of 2,000 were lost. With ELR off and the same cut, 774 were lost, also a dial: there the ISR keeps the dead last member, its return is a clean election, and the metadata records carry no trace. That run is not a last-known election at all. With three combined voters, fencing order after quorum returned, not who died last, decided the last known leader. V1 and V1b lost 0 only because the mocked broker was not elected.

How close is this to a real crash? On inference, not measurement: E4's producer finished about t+128 and n4 died at t+167.4, and with vm.dirty_expire_centisecs=3000 on ext4, stock writeback would probably have put those bytes on disk. A real loss needs the last leader to die within about 35 s of the last acked write.

Afterwards the partition reports a full ISR and three logs of one size, so an ISR-based dashboard shows no sign. n2 and n3 logged Truncating z-0 to offset 1013 below high water… as WARN. By the code, UncleanLeaderElectionsPerSec counts this election and misses the ELR-off case; it was not scraped (D65). Offsets at and above 1013 will be reassigned, and a consumer's reaction was not run (D66).

06The metadata log

Who is in the ISR is itself a record in a log. The fifth use of the data structure is __cluster_metadata, one single-partition log for the whole cluster: a request for any other partition is rejected, with a comment that "multi-raft" is not supported yet (raft/…/KafkaRaftClient.java:1495). The class comment states the design in one sentence. raft/…/KafkaRaftClient.java:129-133: 

/**
 * This class implements a Kafkaesque version of the Raft protocol. Leader election
 * is more or less pure Raft, but replication is driven by replica fetching and we use Kafka's
 * log reconciliation protocol to truncate the log to a common point following each leader
 * election.

Followers pull here too, so a new leader needs an announcement RPC standard Raft lacks: BeginQuorumEpoch, which KIP-595 and the code both explain by the pull design (:149-152). All Raft work runs on one thread, and any throwable from it is fatal (KafkaRaftClientDriver.java:31-66). Voters elect; observers, which include every broker, fetch the same log and never campaign (QuorumState.java:71-73) from the code.

The controller on top

The controller is a state machine on one event thread. It replays its own records into memory before Raft has them, and any failure there is fatal. metadata/…/controller/QuorumController.java:828-852: 

                        // Start by trying to apply the record to our in-memory state. This should always
                        // succeed; if it does not, that's a fatal error. It is important to do this before
                        // scheduling the record for Raft replication.
                        int recordIndex = 0;
                        long lastOffset = raftClient.prepareAppend(controllerEpoch, records);
                        long baseOffset = lastOffset - records.size() + 1;
                        for (ApiMessageAndVersion message : records) {
                            long recordOffset = baseOffset + recordIndex;
                            try {
                                replay(message.message(), Optional.empty(), recordOffset);
                            } catch (Throwable e) {
                                String failureMessage = String.format("Unable to apply %s " +
                                    "record at offset %d on active controller, from the " +
                                    "batch with baseOffset %d",
                                    message.message().getClass().getSimpleName(),
                                    recordOffset, baseOffset);
                                throw fatalFaultHandler.handleFault(failureMessage, e);
                            }
                            recordIndex++;
                        }
                        raftClient.schedulePreparedAppend();
                        offsetControl.handleScheduleAppend(lastOffset);
                        return lastOffset;
                    }
                );

The write's future then waits in a deferred queue keyed by offset, so an admin success means committed (:860-862, :170-171). Losing leadership rolls a snapshot registry back to the last stable offset, with no log read (:1123). Standbys replay each committed batch as it arrives, which is why they are hot (:993-1012).

Every broker is a reader

No controller-to-broker LeaderAndIsr RPC exists. A broker's MetadataLoader packages committed records into an image; the publisher swaps one volatile reference, then tells ReplicaManager the delta (BrokerMetadataPublisher.scala:130-148). A decoded log is plain to read (kafka-dump-log.sh --cluster-metadata-decoder) measured here:

| offset: 55 ... payload: {"type":"TOPIC_RECORD","version":0,"data":{"name":"registry","topicId":"ybHiwpZ4T4uom9SjvS1ejQ"}}
| offset: 57 ... payload: {"type":"CLEAR_ELR_RECORD","version":0,"data":{"topicName":"registry"}}

A broker's epoch is its registration record's offset; here epoch 10 sits at offset 10. "fenced":-1 means unfenced. On an idle cluster 65 of 93 records were NO_OP_RECORD, at a median 500 ms gap. Each node writes its own snapshots, by default at 20 MiB or 1 hour, and a new replica is sent to a snapshot even if the log still reaches offset 0 (KafkaRaftClient.java:1622-1625); a real new broker did exactly that.

Inspecting this has edges. The metadata shell shows image and local at the root, not the layout in the docs (D23). It reports a snapshot's internal offset as provenance, refuses live directories, and logs ERROR for normal control records (D73). Config docs drift too: election.timeout.ms is documented with the fetch timeout's meaning (D25) and election.backoff.max.ms as a binary exponential backoff against gridlock, when in code it is only read on graceful resignation (D26). Also in the register are the class comment (D27), the format-time sentence (D28), KIP status pages (D29) and addAt (D72).

07Losing a controller

Timers default low on purpose: election 1000 ms, fetch 2000 ms, and the comment says standbys are hot, so leader change is cheap (raft/…/QuorumConfig.java:48-49, :77-104). The election timeout is randomised in [T, 2T) (QuorumState.java:748) from the code.

Three dedicated controllers, two brokers, default timers, milliseconds after the signal, from the first matching log line on a surviving controller (exp2_failover.sh, exp2b_probe_fence.sh) measured here:

After SIGKILL, a follower's fetch timer fired 1.6 to 2.0 s later and a new controller was active 1.9 to 2.6 s after the kill, over 7 usable rounds. Fetch timeout to leader took 116 to 435 ms. The wait for the timer is most of it. SIGSTOP looks the same to followers, at 2.1 s: a pause longer than the fetch timeout costs leadership.

SIGTERM took 527 to 610 ms, about a quarter of a kill. A graceful resignation sends EndQuorumEpoch, which shortens each follower's fetch timer by its rank, and the best-replicated voter starts at once (KafkaRaftClient.java:1305-1313). That removes the fetch timeout from the sum.

A leader has its own detector. With both followers stopped, it logged the check-quorum expiry about 3.25 s after the SIGSTOP. That matches 1.5 × fetch timeout (LeaderState.java:153), not the fetch timeout the config doc names (D24, class C, still at trunk 09f2dc1320).

What a client saw: an alter-config loop through a broker got its first success 2.4 to 2.8 s after each SIGKILL, with one failed call per round. That failure is the probe's own 1500 ms request timeout, not a count of lost writes. A SIGKILLed broker was fenced 8.2 to 9.0 s after the kill, and a SIGSTOPped one 9.7 s after, inside the 7 to 10.1 s window the session, heartbeat and sweep predict. A SIGCONTed broker came back in the same epoch within 22 ms; a restarted one re-registered with a new epoch. A pause does not cost a registration, and a restart does. No iptables here, so SIGSTOP stands in for a silent peer, not for an asymmetric partition.

The KIPs match the code on intent, and lag it on status. KIP-595 states the pull design and the reason for BeginQuorumEpoch. KIP-996 states the pre-vote rule, and its page still says "Implementing". KIP-631's timeouts differ from the code's, and code wins (D29). KIP-833 marked KRaft production-ready for new clusters in 3.3.

08Losing the quorum

Kill two of three controllers and the log that decides everything stops moving. The data plane does not stop. Existing leaders and ISRs need no controller for the normal path, because the line in §01 moves on fetches. Every state change stops, and that reaches further than it first looks.

A broker has no self-fencing. A failed heartbeat just schedules another (BrokerLifecycleManager.java:623-635). It finds the controller by asking its Raft client who leads, and with no leader it has no controller node (RaftControllerNodeProvider.java:61-65) from the code.

With a controller alive, fencing is a sweep. Heartbeats update a lock-free contact-time map from the request handler thread, so a backlogged controller cannot make a healthy broker look dead. The sweep samples eight times per session, for at most 112.5% of the session timeout, 10,125 ms by default, and fences one broker per pass (QuorumController.java:1987-1989, :1681-1689). All of that is a controller writing records. With no quorum, none of it can land.

Killing a broker with no quorum freezes the view of the cluster. A leader cannot shrink the ISR without the controller, so the HW cannot pass the dead follower, and acks=1 keeps acking:

A timeout that does not fire

A broker with no producer-ID block answers InitProducerId with a retriable error while it asks the controller for one (RPCProducerIdManager.java:97-100). The Java producer's sender loop returns early while that request is in flight or queued, and batch expiry lives in the step it skips (Sender.java:333-344; Part 4 reads it). So delivery.timeout.ms cannot fire. From two re-runs, as logged, one line each (verify-b/q-run1/, q-run2/): 

+210398ms future.isDone=false
+105603ms callback FAILED TimeoutException: Expiring 1 record(s) for q-0:92904 ms has passed since batch creation.

1,943 round trips, all errorCode=14. Once a controller returned and the PID arrived, the record failed at once. The doc calls the setting "An upper bound". This is D3, class A, a latent bug, still at trunk 09f2dc1320. No Jira matched two text searches, which is not proof none exists. franz-go failed at 27.9 s in one run, for a reason not traced. librdkafka was not tested. By code flush() and no-arg close() wait on it too (not run), and only the no-block case was run. A broker that already holds a block passes the same test; on this evidence blocks hold 1000 IDs.

The one way a broker gives up

A running broker keeps retrying. A starting one has a deadline. server/…/server/BrokerLifecycleManager.java:732-740: 

    private class RegistrationTimeoutEvent implements EventQueue.Event {
        @Override
        public void run() {
            if (!initialRegistrationSucceeded) {
                logger.error("Shutting down because we were unable to register with the controller quorum.");
                eventQueue.beginShutdown("registrationTimeout");

initial.broker.registration.timeout.ms is 60 s. Measured: exactly 60 s from STARTING to the shutdown line, and the process exited 70.0 s after launch, about 10 s of it JVM start. It does not serve in those 60 s. A rolling restart during a controller outage removes brokers that were serving (D69). A young cluster is more exposed, since it cannot form a first consumer group or auto-create anything (D70).

Coming back

The lone surviving voter cycled through Prospective 34 times in the first two minutes, and the epoch did not move: the next leader, 4.5 minutes later, was epoch 2. That is pre-vote seen from outside. On restore, a broker dead for 4.5 minutes was fenced 9.06 s after the new controller activated, not at once, because a new active controller gives every unfenced broker a fresh session (ClusterControlManager.java:315-323; D71). The 13.7 s to a leader in the run includes restarting a JVM and the polling tool, so it is not an election time.
