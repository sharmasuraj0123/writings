{{S}}What the ack promises

That test is Partition.checkEnoughReplicasReachOffset, and it is everything an acks=all success means. Two conditions: the HW has passed the record, and the maximal ISR is at least the effective min ISR (Partition.scala:969-979). Neither mentions a disk. The design doc defines "committed" by the same two conditions and states the guarantee in one sentence. docs/design/design.md:309: "The guarantee that Kafka offers is that a committed message will not be lost, as long as there is at least one in sync replica alive, at all times." from the code

Read that test's other branch too. When the HW has passed but the ISR has since dropped below min, the answer is NOT_ENOUGH_REPLICAS_AFTER_APPEND: an error, for a record that is committed. The exception is retriable, which is a duplicate path without idempotence (Errors.java:225). The record is there; the client is told otherwise. D55 collects the cases.

Now the disk. By default Kafka never fsyncs on a timer or on a message count: both knobs default to Long.MAX_VALUE (ServerLogConfigs.java:101, :109). The only flush in the append path is the message-count check Part 1 quotes, and leader and follower appends share it, so neither side syncs before an ack (UnifiedLog.java:1300). The follower half of that is code reading plus the recovery points below; the fsync-counting shim ran at replication factor 1.

Two things do get fsynced by default: a rolled segment, asynchronously, on the scheduler, up to the new segment's base offset; and everything, on clean shutdown (UnifiedLog.java:2242-2245). A real flush covers the log and its offset, time and transaction indexes, then moves the recovery point (LogSegment.java:631-634) from the code. In the run counted in Part 1, about 15,573 records were acked into a topic whose .log saw one fsync, from kafka-scheduler, for the roll, in a window of about 25 s with segment.bytes=8388608 and replication factor 1. At the 1 GiB default that window has no roll measured here.

Here is the same thing at replication factor 3. Two topics, about 2,000 acked records each, and the checkpoint read 70 s later, past its 60 s interval. Topic t has defaults; tf has flush.messages=1 (./a_hw_isr.sh, one run) measured here: 

t+0184.0s HW t=t:0:2005  HW tf=tf:0:2000
t+0184.0s n2 recovery-point: tf 0 2000 t 0 0
t+0184.0s n3 recovery-point: tf 0 2000 t 0 0
t+0184.0s n4 recovery-point: tf 0 2000 t 0 0

2,005 acknowledged records sat above a recovery point of 0 on all three replicas. flush.messages=1 kept the recovery point at the HW. The label matters: a recovery point of 0 shows Kafka did not flush. Kernel writeback may still have written the bytes. That writeback runs on the kernel's clock, and no Kafka line records it. The HW checkpoint on every replica did agree with the leader's HW, once its 5 s timer had fired.

That gives three lines on one partition, moved by three different actors. Fetches move the HW. The scheduler moves the recovery point. The kernel moves the bytes, and tells nobody. Part 1 shows what depends on the second: CRCs are checked only above the recovery point.

The design, not an oversight

None of this is hidden. docs/operations/hardware-and-os.md:64: "Note that durability in Kafka does not require syncing data to disk, as a failed node will always recover from its replicas." Two lines on, :66: "We recommend using the default flush settings which disable application fsync entirely." The register files this as D41, class D, status intended. The design doc gives the cost of the alternative as "two to three orders of magnitude" (design.md:335). That figure was not reproduced here.

"Will always recover" has an edge: it is not true when the failed node is elected before the others. That is D18, class C, minor, because it falls outside the design doc's stated guarantee, and its example, which §05 walks through, is measured-vs-mock. KIP-966's Motivation names the same scenario: the last ISR member loses unflushed data, is re-elected, and followers truncate to it. Its next sentence states the limit: "MinISR-1 tolerance to data loss unclean shutdown events".

So the ack is a statement about the HW. It moves on fetches, and fetches read page cache. Replication covers one machine going away, not a window in which every copy loses its unflushed tail. How often that window opens on real hardware was not measured here.
