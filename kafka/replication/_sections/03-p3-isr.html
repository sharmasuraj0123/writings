{{S}}Two ways out of the ISR

Every ISR member holds the HW down, so a stuck member holds every acks=all ack. The ladder only moves again when somebody removes it. Two detectors can, and they run in different processes.

The first is the leader's lag check. It runs every replica.lag.time.max.ms / 2, so with the 30 s default a stuck follower can hold acks for up to 45 s if nothing else removes it (ReplicaManager.scala:284-285). Stuck and slow are one case: the same lastCaughtUpTimeMs test, with no offset-lag threshold anywhere (Partition.scala:1149). The leader proposes and the controller decides. One ISR change is in flight per partition, and most rejections leave it stuck in that pending state until new metadata arrives (:877, :1725) from the code.

The second never involves the leader. When a broker's session expires, the controller strips it from every ISR (metadata/…/controller/ReplicationControlManager.java:1433-1434). The session default is 9 s with a 2 s heartbeat, shorter than the lag limit, so a dead or frozen broker normally leaves through fencing (KRaftConfigs.java:40, :44). A broker that keeps heartbeating while its fetcher is stuck is the case the lag check exists for reconstruction.

Every ack stopped for 9.2 s, with no send error. Min ISR was 2, and two copies existed, and it made no difference. The byte counts line up: offset 41 begins at position 2088 and offset 42 at 2160, so the frozen follower was exactly one 72-byte batch behind. The record sat on two of three logs, unacknowledged and invisible. The fence record landed at 16:24:24.840 and the HW moved at 16:24:24.893, 53 ms apart, and the leader logged no Shrinking ISR line: the shrink came from the controller. Resumed after 34 s, the follower was back in the ISR about 4.8 s later, its unfence record ahead of the ISR change.

That stall outlasted the 30 s request timeout. Requests began failing 30.0 s in, and 3 of the 602 records the client was told had failed were in the log anyway (stall_session120_timedout_check.txt, read back with kafka-dump-log.sh). The run used retries=0, which also disables idempotence; a default producer would retry until delivery.timeout.ms. Timeouts undo nothing, and Part 2 shows why: a parked Produce starts with REQUEST_TIMED_OUT already set. The register has this as D55, confirmed by verifier.

Coming back

The rejoin test is shorter than people expect. core/…/cluster/Partition.scala:907-911: 

  private def isFollowerInSync(followerReplica: Replica): Boolean = {
    leaderLogIfLocal.exists { leaderLog =>
      val followerEndOffset = followerReplica.stateSnapshot.logEndOffset
      followerEndOffset >= leaderLog.highWatermark && leaderEpochStartOffsetOpt.exists(followerEndOffset >= _)
    }

HW and the start of the current epoch, not the leader's LEO. Records between HW and LEO may still be unread. The epoch clause exists because committed data can sit between a new leader's HW and LEO, and a follower admitted too early could be elected and lose it (:865-867). The replica must also be unfenced, not shutting down, and on a matching broker epoch, checked by the leader and again by the controller (:929-931) from the code.

The design doc says more than the code does. docs/design/design.md:335: "it must fully re-sync again even if it lost unflushed data in its crash." Only the missing suffix is fetched, and an elected replica does not re-sync at all (D19, class C, doc drift, still at trunk 09f2dc1320). Part 1 shows the local half: recovery only has to produce a clean prefix.
