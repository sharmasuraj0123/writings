{{S}}The metadata log

Who is in the ISR is itself a record in a log. The fifth use of the data structure is __cluster_metadata, one single-partition log for the whole cluster: a request for any other partition is rejected, with a comment that "multi-raft" is not supported yet (raft/…/KafkaRaftClient.java:1495). The class comment states the design in one sentence. raft/…/KafkaRaftClient.java:129-133: 

/**
 * This class implements a Kafkaesque version of the Raft protocol. Leader election
 * is more or less pure Raft, but replication is driven by replica fetching and we use Kafka's

Followers pull here too, so a new leader needs an announcement RPC standard Raft lacks: BeginQuorumEpoch, which KIP-595 and the code both explain by the pull design (:149-152). All Raft work runs on one thread, and any throwable from it is fatal (KafkaRaftClientDriver.java:31-66). Voters elect; observers, which include every broker, fetch the same log and never campaign (QuorumState.java:71-73) from the code.

The controller on top

The controller is a state machine on one event thread. It replays its own records into memory before Raft has them, and any failure there is fatal. metadata/…/controller/QuorumController.java:828-852: 

                        // Start by trying to apply the record to our in-memory state. This should always
                        // succeed; if it does not, that's a fatal error. It is important to do this before
                        // scheduling the record for Raft replication.
                        int recordIndex = 0;
                        long lastOffset = raftClient.prepareAppend(controllerEpoch, records);
                        long baseOffset = lastOffset - records.size() + 1;
                        for (ApiMessageAndVersion message : records) {
                            long recordOffset = baseOffset + recordIndex;
                            try {
                                replay(message.message(), Optional.empty(), recordOffset);
                            } catch (Throwable e) {
                                String failureMessage = String.format("Unable to apply %s " +
                                    "record at offset %d on active controller, from the " +
                                    "batch with baseOffset %d",
                                    message.message().getClass().getSimpleName(),
                                    recordOffset, baseOffset);
                                throw fatalFaultHandler.handleFault(failureMessage, e);
                            }
                            recordIndex++;
                        }
                        raftClient.schedulePreparedAppend();
                        offsetControl.handleScheduleAppend(lastOffset);
                        return lastOffset;
                    }
                );

The write's future then waits in a deferred queue keyed by offset, so an admin success means committed (:860-862, :170-171). Losing leadership rolls a snapshot registry back to the last stable offset, with no log read (:1123). Standbys replay each committed batch as it arrives, which is why they are hot (:993-1012).

Every broker is a reader

No controller-to-broker LeaderAndIsr RPC exists. A broker's MetadataLoader packages committed records into an image; the publisher swaps one volatile reference, then tells ReplicaManager the delta (BrokerMetadataPublisher.scala:130-148). A decoded log is plain to read (kafka-dump-log.sh --cluster-metadata-decoder) measured here: 

| offset: 22 ... payload: {"type":"BROKER_REGISTRATION_CHANGE_RECORD","version":0,"data":{"brokerId":2,"brokerEpoch":10,"fenced":-1}}
| offset: 55 ... payload: {"type":"TOPIC_RECORD","version":0,"data":{"name":"registry","topicId":"ybHiwpZ4T4uom9SjvS1ejQ"}}
| offset: 57 ... payload: {"type":"CLEAR_ELR_RECORD","version":0,"data":{"topicName":"registry"}}

A broker's epoch is its registration record's offset; here epoch 10 sits at offset 10. "fenced":-1 means unfenced. On an idle cluster 65 of 93 records were NO_OP_RECORD, at a median 500 ms gap. Each node writes its own snapshots, by default at 20 MiB or 1 hour, and a new replica is sent to a snapshot even if the log still reaches offset 0 (KafkaRaftClient.java:1622-1625); a real new broker did exactly that.

Inspecting this has edges. The metadata shell shows image and local at the root, not the layout in the docs (D23). It reports a snapshot's internal offset as provenance, refuses live directories, and logs ERROR for normal control records (D73). Config docs drift too: election.timeout.ms is documented with the fetch timeout's meaning (D25) and election.backoff.max.ms as a binary exponential backoff against gridlock, when in code it is only read on graceful resignation (D26). Also in the register are the class comment (D27), the format-time sentence (D28), KIP status pages (D29) and addAt (D72).
