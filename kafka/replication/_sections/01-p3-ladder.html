{{S}}The commit ladder

An acks=all ack says the record reached the page cache of every in-sync replica, and that the in-sync set met a floor. It says nothing about disk. The metadata log, which does fsync, decides who is in that set, so losing it freezes the line while data keeps moving. This collection's claim is that Kafka is one log used five times, and that nearly every promise is a line in a log: which line, in which log, moved by whom. This part reads the high watermark and the metadata commit. All-replica loss here runs on a mock.

Part 1 left a record in one broker's file. To reach another broker it has to be asked for. Followers pull. A follower's fetcher thread does two things in a loop: truncate whatever is marked for truncation, then fetch (core/…/server/AbstractFetcherThread.scala:112-114). A follower append runs the same append as a leader append, and takes the leader's offsets instead of assigning its own (UnifiedLog.java:1094-1097) from the code.

There is no replication ack. The offset a follower asks for in its next Fetch is its log end offset (LEO) as far as the leader knows, because updateFollowerFetchState takes it from the read (core/…/cluster/Partition.scala:1313-1321). A fetch offset is an ack. The leader keeps six fields per follower: log start, LEO, the leader's LEO at the last fetch, last fetch time, last caught-up time and broker epoch (ReplicaState.java:32-39) from the code.

The broker accepts three acks values. acks=1 answers straight after the leader's local append. Only acks=-1 waits, parked in the purgatory Part 2 reads (ReplicaManager.scala:1370, :1364-1366, :913-916). It is also the only value that meets a durability check before the append. core/…/cluster/Partition.scala:1227-1243: 

    val (info, leaderHWIncremented) = inReadLock(leaderIsrUpdateLock, () => {

The rule for the line sits in one method. The new high watermark (HW) is the smallest LEO among the leader, the maximal ISR, and any replica outside the ISR that is caught up and eligible to join. core/…/cluster/Partition.scala:1010-1033: 

  private def maybeIncrementLeaderHW(leaderLog: UnifiedLog, currentTimeMs: Long = time.milliseconds): Boolean = {
    if (isUnderMinIsr) {
      trace(s"Not increasing HWM because partition is under min ISR(ISR=${partitionState.isr})")
      return false
    }
    // maybeIncrementLeaderHW is in the hot path, the following code is written to
    // avoid unnecessary collection generation
    val leaderLogEndOffset = leaderLog.logEndOffsetMetadata
    var newHighWatermark = leaderLogEndOffset
    remoteReplicasMap.forEach { (_, replica) =>
      val replicaState = replica.stateSnapshot

      def shouldWaitForReplicaToJoinIsr: Boolean = {
        replicaState.isCaughtUp(leaderLogEndOffset.messageOffset, currentTimeMs, replicaLagTimeMaxMs) &&
        isReplicaIsrEligible(replica.brokerId)
      }

      // Note here we are using the "maximal", see explanation above
      if (replicaState.logEndOffsetMetadata.messageOffset < newHighWatermark.messageOffset &&
          (partitionState.maximalIsr.contains(replica.brokerId) || shouldWaitForReplicaToJoinIsr)
      ) {
        newHighWatermark = replicaState.logEndOffsetMetadata
      }
    }

Three details in that method matter later. The first return is strict min ISR: below min.insync.replicas the HW does not move at all, whichever acks the writes used. A caught-up replica outside the ISR holds the HW back on purpose, otherwise it would chase a moving line on a sole-ISR leader and never rejoin (:995-997). "Maximal" means a pending ISR change counts in the stricter direction: an expansion counts the new member at once, and a shrink keeps waiting for the departing one until the controller confirms (:1614-1615, :1640-1641) from the code.

The leader's TRACE log shows the gap. The offset is exclusive, so "offset 1299" asks for the record at 1298 (kafka.cluster.Partition=TRACE, single run) measured here: 

[2026-11-06 16:25:18,579] TRACE [Partition t-0 broker=2] Progress awaiting ISR acks for offset 1299: acked: HashSet(broker 2: 1299), awaiting HashSet(broker 3: 1298, broker 4: 1298) (kafka.cluster.Partition)

Below the HW, readers split by line: followers read to the LEO, read_uncommitted consumers to the HW, read_committed consumers to the last stable offset (FetchIsolation.java:32-37). A follower learns the HW only from a Fetch response and clamps it to its own LEO, so its HW trails the leader's by at least one round trip (ReplicaFetcherThread.scala:143). On disk the HW is a checkpoint, written every 5 s by default and on clean shutdown, so after a restart it is a stale hint (ReplicaManager.scala:265) from the code.

A floor, not a quorum

min.insync.replicas does not say how many acks are enough. It says how few members the ISR may have. With a full ISR, every member must catch up, and the config's own doc says so. clients/…/common/config/TopicConfig.java:222-223: "then all three replicas must acknowledge an acks=all write for it to succeed, even if min.insync.replicas happens to be less than 3." The register lists this as D63, class D (gotcha), documented. The defaults are the weak half of the pair: the producer defaults to acks=all, the broker to min.insync.replicas=1 and default.replication.factor=1, so a default acks=all on a default topic is one copy (ServerLogConfigs.java:155, ReplicationConfigs.java:42).

Who counts as caught up is a time test with an exact-LEO escape hatch (ReplicaState.java:66). The javadoc above it has the subtraction backwards (D22, class C, doc drift, still on trunk). So acks=all commits when the slowest ISR member's next fetch arrives.

One test turns that into an answer. core/…/cluster/Partition.scala:968-979:
