ELR

ELR is populated exactly when the target ISR falls below min ISR: members leaving the ISR move into it, unless they had an unclean shutdown (:536-553). It is safe only because of strict min ISR. The HW froze when the ISR fell below min, so every replica in the ISR at that moment holds everything committed (docs/operations/eligible-leader-replicas.md:31). A broker's shutdown counts as clean only if its clean-shutdown file names the epoch on record (ClusterControlManager.java:439-441). The last known leader

The first time a partition goes leaderless, the controller records its last leader in lastKnownElr (PartitionChangeBuilder.java:493-498). metadata/…/controller/PartitionChangeBuilder.java:286-295, then :305-315, with a comment between them elided: 

    private boolean canElectLastKnownLeader() {
        if (!eligibleLeaderReplicasEnabled || !useLastKnownLeaderInBalancedRecovery) {
            log.trace("Try to elect last known leader for {}-{} but elrEnabled={}, useLastKnownLeaderInBalancedRecovery={}",
                    topicId, partitionId, eligibleLeaderReplicasEnabled, useLastKnownLeaderInBalancedRecovery);
            return false;
        }
        if (!targetElr.isEmpty() || !targetIsr.isEmpty()) {
            log.trace("Try to elect last known leader for {}-{} but ELR/ISR is not empty. ISR={}, ELR={}",
                    topicId, partitionId, targetIsr, targetElr);
            return false;
        if (partition.lastKnownElr.length != 1) {
            log.trace("Try to elect last known leader for {}-{} but lastKnownElr does not only have 1 member. lastKnownElr={}",
                    topicId, partitionId, Arrays.toString(partition.lastKnownElr));
            return false;
        }
        if (!isAcceptableLeader.test(partition.lastKnownElr[0])) {
            log.trace("Try to elect last known leader for {}-{} but last known leader is not alive. last known leader={}",
                    topicId, partitionId, partition.lastKnownElr[0]);
            return false;
        }
        return true;

Last-known-leader election runs without consulting unclean.leader.election.enable, as KIP-966's Delivery plan specifies: intended, a design choice, not a coding error. It is flagged unclean and sets RECOVERING. No production switch exists: the field defaults to true, and its setter has callers only in tests (:104, :180). It compares nothing, because KIP-966's Unclean Recovery half has no code at this pin (D20, class C). The ops doc says only "This is a similar behavior prior to the 4.0 when all the replicas are offline" (eligible-leader-replicas.md:35), and leaves out the flag and the unclean label (D21, class C, still on trunk).

This is simulated damage on one host (./e34_tail_loss.sh, E4). With unclean.leader.election.enable at its default of false, min.insync.replicas=2 and acks=all, the last leader came back without its tail, was elected anyway, and 987 of 2,000 acked records were deleted from all three replicas, including two that still held them. The other two replicas were SIGKILLed and kept their bytes, so this models one machine lost plus two process deaths. Half the file was cut by hand, so 987 is a dial set by the mock, not a loss rate. KIP-966 promises MinISR-1 tolerance; this has two unclean exits at min ISR 2. No real power cut was run. D62 files it as class D, intended per KIP-966's Delivery plan.

The controls isolate the bytes. With no cut, the same kill-and-restart sequence and the same election kept all 2,000. With a clean ELR member (V3), 0 of 2,000 were lost. With ELR off and the same cut, 774 were lost, also a dial: there the ISR keeps the dead last member, its return is a clean election, and the metadata records carry no trace. That run is not a last-known election at all. With three combined voters, fencing order after quorum returned, not who died last, decided the last known leader. V1 and V1b lost 0 only because the mocked broker was not elected.

How close is this to a real crash? On inference, not measurement: E4's producer finished about t+128 and n4 died at t+167.4, and with vm.dirty_expire_centisecs=3000 on ext4, stock writeback would probably have put those bytes on disk. A real loss needs the last leader to die within about 35 s of the last acked write.

Afterwards the partition reports a full ISR and three logs of one size, so an ISR-based dashboard shows no sign. n2 and n3 logged Truncating z-0 to offset 1013 below high water… as WARN. By the code, UncleanLeaderElectionsPerSec counts this election and misses the ELR-off case; it was not scraped (D65). Offsets at and above 1013 will be reassigned, and a consumer's reaction was not run (D66).
