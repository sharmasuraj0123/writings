{{S}}Losing the quorum

Kill two of three controllers and the log that decides everything stops moving. The data plane does not stop. Existing leaders and ISRs need no controller for the normal path, because the line in §01 moves on fetches. Every state change stops, and that reaches further than it first looks.

A broker has no self-fencing. A failed heartbeat just schedules another (BrokerLifecycleManager.java:623-635). It finds the controller by asking its Raft client who leads, and with no leader it has no controller node (RaftControllerNodeProvider.java:61-65) from the code.

With a controller alive, fencing is a sweep. Heartbeats update a lock-free contact-time map from the request handler thread, so a backlogged controller cannot make a healthy broker look dead. The sweep samples eight times per session, for at most 112.5% of the session timeout, 10,125 ms by default, and fences one broker per pass (QuorumController.java:1987-1989, :1681-1689). All of that is a controller writing records. With no quorum, none of it can land.

A line of acked writes nobody can see

Killing a broker with no quorum freezes the view of the cluster. A leader cannot shrink the ISR without the controller, so the HW cannot pass the dead follower, and acks=1 keeps acking: 

1793983285876 prod p0 acks=1 OK offset=9 6
1793983288610 prod p0 acks=allni TimeoutException: Expiring 1 record(s) for q-0:8004 ms has passed since batch creation. ...
1793983299724 prod p1 acks=1 TimeoutException: Expiring 1 record(s) for q-1:8001 ms has passed since batch creation. ...
q:0:8

q:0:8 is the HW, with offset 9 acked above it. After quorum returned with the follower still dead, the HW stayed frozen, now by the below-min-ISR gate. It moved only when the follower rejoined, and the acked records then became readable: held, not lost, in this run (D68, class D, confirmed by verifier). The non-idempotent send that timed out also wrote two copies (request timeout 4 s, delivery 8 s), a count inferred from the offsets and one send.

A timeout that does not fire

A broker with no producer-ID block answers InitProducerId with a retriable error while it asks the controller for one (RPCProducerIdManager.java:97-100). The Java producer's sender loop returns early while that request is in flight or queued, and batch expiry lives in the step it skips (Sender.java:333-344; Part 4 reads it). So delivery.timeout.ms cannot fire. From two re-runs, as logged, one line each (verify-b/q-run1/, q-run2/): 

+210398ms future.isDone=false
+105603ms callback FAILED TimeoutException: Expiring 1 record(s) for q-0:92904 ms has passed since batch creation.

1,943 round trips, all errorCode=14. Once a controller returned and the PID arrived, the record failed at once. The doc calls the setting "An upper bound". This is D3, class A, a latent bug, still at trunk 09f2dc1320. No Jira matched two text searches, which is not proof none exists. franz-go failed at 27.9 s in one run, for a reason not traced. librdkafka was not tested. By code flush() and no-arg close() wait on it too (not run), and only the no-block case was run. A broker that already holds a block passes the same test; on this evidence blocks hold 1000 IDs.

The one way a broker gives up

A running broker keeps retrying. A starting one has a deadline. server/…/server/BrokerLifecycleManager.java:732-740: 

    private class RegistrationTimeoutEvent implements EventQueue.Event {
        @Override
        public void run() {
            if (!initialRegistrationSucceeded) {
                logger.error("Shutting down because we were unable to register with the controller quorum.");
                eventQueue.beginShutdown("registrationTimeout");
            }
        }
    }

initial.broker.registration.timeout.ms is 60 s. Measured: exactly 60 s from STARTING to the shutdown line, and the process exited 70.0 s after launch, about 10 s of it JVM start. It does not serve in those 60 s. A rolling restart during a controller outage removes brokers that were serving (D69). A young cluster is more exposed, since it cannot form a first consumer group or auto-create anything (D70).

Coming back

The lone surviving voter cycled through Prospective 34 times in the first two minutes, and the epoch did not move: the next leader, 4.5 minutes later, was epoch 2. That is pre-vote seen from outside. On restore, a broker dead for 4.5 minutes was fenced 9.06 s after the new controller activated, not at once, because a new active controller gives every unfenced broker a fresh session (ClusterControlManager.java:315-323; D71). The 13.7 s to a leader in the run includes restarting a JVM and the polling tool, so it is not an election time.

A partition with no leader meets one more line in another log. Part 5 covers KAFKA-20734 (D10), where a transaction marker has nowhere to go; it has no tagged fix as of 6 November 2026.
