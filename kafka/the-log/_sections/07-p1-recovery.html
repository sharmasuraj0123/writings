{{S}}What recovery does to damage

Recovery wants a contiguous prefix of valid batches and has no other goal. It does not try to save records; replication is meant to supply those. That one aim explains why damage injected by hand has such uneven results here, from one lost batch to a broker that will not start. Everything in this section marked as damage is simulated: bytes cut or bits flipped by hand with the broker dead, one sample each, on one broker with replication factor 1. No real power cut was run, and no loss figure here is a rate.

The path

Startup reads the clean-shutdown marker and deletes it immediately, so a crash during loading counts as unclean on the next boot (LogManager.java:630-634). Loading runs in passes: delete temp files and collect swaps, delete segments the swap replaced, rename swaps, then load segments and recover. A .cleaned file is always discarded, and any .swap at or above the smallest .cleaned offset is treated as an incomplete split and discarded too (LogLoader.java:129-195, :290-309). On a clean shutdown, recovery is skipped. Otherwise it visits only segments at or above the checkpointed recovery point, the first offset not flushed (LogLoader.java:457-459, LocalLog.java:102) from the code.

Every later unflushed segment goes, whole, without being read. A log must be contiguous. The design doc states why that is acceptable: a crashed replica is not assumed to have its data and must re-sync before rejoining the ISR "even if it lost unflushed data in its crash" (design.md:335). In code only the missing suffix is fetched, not the whole log (D19). Recovery on one broker only has to produce a clean prefix. Replication supplies the rest, if another in-sync copy holds it.

A plain SIGKILL costs nothing

One undamaged run first. SIGKILL at acks=all mid-write lost no acked record: highest acked offset 15588, log end offset 15589 after restart measured here. SIGKILL kills the process and leaves the page cache, so this says nothing about power loss. Recovery rescanned all 14 segments, even though the rolled ones had been flushed in the background, because the on-disk recovery point had no entry yet for this young partition: the 60 s checkpoint timer had not fired (D48, class D). Each progress line read 0 recovered, because numFlushed / numUnflushed at LogLoader.java:469 is integer division, which truncates to 0 until the end (D2, class A, cosmetic, still at trunk).

Reading the table

The tail rows simulate pages that never reached disk. A batch that claims more bytes than remain just ends iteration quietly, while a length below the minimum, all zeros say, throws CorruptRecordException (FileLogInputStream.java:66-82). Chopping 37 bytes cost the whole batch: offsets 15572-15588, acked, gone on this one replica. The zero tail lost nothing beyond the zeros. Which of those a real power cut would leave wasn't tested.

The payload rows are the CRC doing its job, and the loader doing its. One flipped bit at a mid-file batch took a young log from 24,413 offsets to 561 (D46, class D, intended by design). The recovery point was still 0 on that partition. One with an advanced checkpoint exposes only the region above it. After a true clean shutdown the same kind of bit went unnoticed: recovery was skipped, the broker logged no CRC or corruption line, and it served the batch. The Java consumer caught it: stored crc = 3573743101, computed crc = 517507933, and it stopped at offset 561 (D47, class D). Nothing on the broker's read path checks a CRC.

The base offset takes another road

The base offset is outside the CRC, so a flip there passes ensureValid. ensureOffsetInRange then throws overflow, and the loader assumes a legacy overflowed segment and tries to split it. The split's guard reads only the segment's last batch. storage/…/log/LocalLog.java:918: 

        require(segment.hasOverflow(), "Split operation is only permitted for segments with overflow, and the problem path is " + segment.log().file().getAbsoluteFile());

A mid-segment flip leaves that last batch healthy, the guard throws, nothing handles it, and the broker exits. It repeats on every start, and one partition takes down the whole broker. Undoing the bit by hand let the same files load with every record intact. A flip in the last batch satisfies the guard, so the split succeeds and the log end jumps to 72057594037936912, in a new file 00072057594037936895.log. Bit 24 is small enough to reach the InvalidOffsetException route, which empties the segment instead of failing (LogLoader.java:473-476). Bit 0 stays in range and passes reconstruction.

The register carries this as D1, class A: a robustness defect, shown only by injection. It is measured-vs-mock, and no natural trigger is established. The path is unchanged at trunk 09f2dc1320, which was read, not built, and no Jira names it. Operators have reported the same fatal message: a forum thread (2023, with a workaround resting on one poster) and a mail (2020, on an upgrade). Neither establishes a cause. By the code the route is not limited to an unclean start, since a corrupt index also calls recoverSegment (LogLoader.java:383-386); that wasn't run with a clean start. Nothing here was reported upstream.
