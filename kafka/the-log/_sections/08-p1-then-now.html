Everything so far follows from a sentence about formats. docs/design/design.md:92: the log holds message sets "written to disk in the same format used by the producer and consumer". That is what makes file-to-socket transfer possible, and it is why the broker works so hard not to touch a batch. On a plaintext connection the fetch path ends in three lines. clients/…/common/network/PlaintextTransportLayer.java:213-215: 

    public long transferFrom(FileChannel fileChannel, long position, long count) throws IOException {

The shim saw it reach the kernel: 87 sendfile calls on the partition's .log moved 14,544,114 bytes, from a data-plane-kafk thread, which is a network thread by code reading. Reading everything back from a warm page cache caused zero physical reads: read_bytes in /proc/<pid>/io stayed 0 while rchar rose about 14.9 MB. After evicting those files with fsync plus posix_fadvise(DONTNEED), the same read caused 14,389,248 bytes of physical reads measured here. A single run on one disk, and it says nothing about speed. It does show where the data came from.

The price of this path is visible at the same line. The file-level write checks only that the file has not shrunk; nothing validates a CRC (FileRecords.java:280-291), which is the clean-start row of Figure {{fig-damage}}. And TLS gives it up entirely: the broker reads the file into a 32 KiB direct buffer in user space and encrypts it (SslTransportLayer.java:1021-1026; D51, class D).

What survives from 2011

The 2011 NetDB paper by Kreps, Narkhede and Rao describes most of this directory.

Idea in § 3.1At 4.4.0
Segment files of about 1 GB, appended at the lastStill true; 1 GiB is still the default
"we rely on the underlying file system page cache"Stands, warm-cache-across-restart argument included
sendfile to deliver log bytesStands for plaintext only; the paper does not mention TLS
Stateless broker, "simple time-based SLA"7 days survives as default retention, but the broker now stores consumer offsets in a topic
A message is exposed only after a flushGone. The high watermark governs visibility, and the default produce path does not fsync
Offsets are byte positions, "increasing but not consecutive", no indexGone. Offsets count records, and each segment has indexes
"built-in replication" as future workPart 3

The 4 copies and 2 system calls that sendfile avoids appear in both the paper and the current design doc (design.md:103). The two ideas that went are not small. Visibility moved from a disk event to a line in the log. An offset moved from a place in a file to a count of records, which is why §04 needs indexes at all. The v2 producer fields of §02 came later still.

Tiering is the same files, further away

Tiered storage is a broker switch plus a topic switch, with two plugin interfaces, and Apache ships no production RemoteStorageManager: the doc says "Kafka server doesn't provide out-of-the-box implementation", and the only one in the tree is for tests (docs/operations/tiered-storage.md:39-60). Only rolled segments are uploaded, and only those below the last stable offset, subject to new copy-lag settings. An upload carries the files a local segment has: the log, both indexes, the optional transaction index, the producer snapshot and the leader-epoch data (RemoteLogManager.java:930-959, :1117-1119). With tiering on, a local segment is deletable only once uploaded or passed by the log start offset, an active segment past retention is rolled so it can be uploaded, and tiering excludes compaction, in code and in the docs (LogConfig.java:604). Tiering was read here, not run.

So the log is a directory, the batch is the unit, and the guarantees are lines. Part 2 takes this file to a socket and shows how one request travels through a broker.
