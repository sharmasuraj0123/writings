{{S}}From an offset to a byte

A consumer asks for an offset. The file only knows bytes. Two sparse, unchecksummed indexes and a short scan turn one into the other. An offset index entry is 8 bytes: a 4-byte offset relative to the segment base and a 4-byte file position. That relative offset is why a segment cannot span more than Integer.MAX_VALUE offsets. A time index entry is 12 bytes: an 8-byte timestamp and a 4-byte relative offset (OffsetIndex.java:44-56, TimeIndex.java:35-56) from the code.

The entries are sparse, and the rule lives in the append loop. storage/…/log/LogSegment.java:263-278: 

            for (RecordBatch batch : records.batches()) {
                long batchMaxTimestamp = batch.maxTimestamp();
                long batchLastOffset = batch.lastOffset();
                if (batchMaxTimestamp > maxTimestampSoFar()) {
                    maxTimestampAndOffsetSoFar = new TimestampOffset(batchMaxTimestamp, batchLastOffset);
                }

                if (bytesSinceLastIndexEntry > indexIntervalBytes) {
                    offsetIndex().append(batchLastOffset, physicalPosition);
                    timeIndex().maybeAppend(maxTimestampSoFar(), shallowOffsetOfMaxTimestampSoFar());
                    bytesSinceLastIndexEntry = 0;
                }
                var sizeInBytes = batch.sizeInBytes();
                physicalPosition += sizeInBytes;
                bytesSinceLastIndexEntry += sizeInBytes;
            }

Read the order. The check runs before the current batch's bytes are counted, so the first batch of a segment never gets an entry. And the entry pairs a batch's last offset with the position where that batch starts. At the default 4,096-byte interval, one entry covers about 4 KiB of log. The lab shows the rule exactly: with two-record batches of about 283 bytes and a 400-byte interval, the first slot is relative offset 5 at position 566, the third batch's start, whose records are offsets 4 and 5 measured here.

Below the first entry, lookup returns the pair (base offset, 0), so a segment with no entries is scanned from the top (OffsetIndex.java:94-102, LogSegment.java:399-400, FileRecords.java:302-332). The binary search has one performance scar: it first tries a "warm" tail of 8,192 bytes of entries, to keep in-sync lookups on recently used pages. The comment records that plain binary search caused page faults that pushed produce latency to about a second (AbstractIndex.java:354-355, :498-502) from the code.

The time index is not a second view of the same entries. Its timestamps only go up within a file: an entry records the largest timestamp seen so far and the offset of the batch that had it (TimeIndex.java:42, :196). One out-of-order batch is enough to split the two.

Believed on open

Neither index has a checksum; the design is to rebuild on a crash. A pre-existing index file is believed on open: the position is set to the end of the file, and startup deliberately skips sanity checks of the offset and time indexes (AbstractIndex.java:483-484, LogSegment.java:185-188). By the code, corruption below the recovery point is not noticed at load; that was not tested here. Upstream treats it as an open gap: KAFKA-19200, "Indexes should be sanity checked on startup", was In Progress with no fix version on 6 November 2026. Two 4.4.0 commits (beae700199, 72b21c706e) closed a related hole, an index length that a clean shutdown could leave not durable. The commit text says it does not cover unclean shutdown.

The other two files

The .txnindex is created lazily, holds one fixed-size entry per aborted transaction, and is attached to the segment holding the abort marker, not the segment where the transaction started. Commit, abort, commit from one producer left one entry, 34 bytes measured here: 

00000000: 00 00 00 00 00 00 00 00 00 04 00 00 00 00 00 00
00000010: 00 03 00 00 00 00 00 00 00 05 00 00 00 00 00 00
00000020: 00 06
entry: version=0 producerId=4 firstOffset=3 lastOffset=5 lastStableOffset=6

A .snapshot has a 2-byte version, a 4-byte CRC-32C checked on read, and a producer array (ProducerStateManager.java:74-76). A one-producer snapshot was 56 bytes, named for the first offset it does not cover. It exists to bound recovery: a segment can be recovered from the snapshot plus a scan of that segment (UnifiedLog.java:2231-2232). It is written without fsync under the log lock, then flushed by the scheduler with the old segment.
