{{S}}Compaction, and a tombstone's two clocks

Retention deletes by age. Compaction deletes by key: it recopies segments, keeping the latest value for each key and keeping every offset unchanged. A delete in this world is itself a record, and it has to stay around long enough for readers to see it. How long is decided by two clocks, and the second one needs someone to look at it.

Which log, and how far

The cleaner picks the partition with the highest ratio of cleanable bytes to clean-plus-cleanable bytes, from those above min.cleanable.dirty.ratio or overdue on max.compaction.lag.ms (LogToClean.java:54, LogCleanerManager.java:282, :290). The defaults are a 0.5 ratio, one thread, a 128 MiB dedupe buffer at 0.9 load factor, and 15 s of sleep when idle. The load factor's key is spelled log.cleaner.io.buffer.load.factor, though it configures the dedupe buffer, not I/O buffers (D13, class C). What it may touch is one expression. storage/…/log/LogCleanerManager.java:726-742: 

        // Find the first segment that cannot be cleaned. We cannot clean past:
        // 1. The active segment
        // 2. The last stable offset (including the high watermark)
        // 3. Any segments closer to the head of the log than the minimum compaction lag time
        long firstUncleanableDirtyOffset = Stream.of(
                        // we do not clean beyond the last stable offset
                        Optional.of(log.lastStableOffset()),

                        // the active segment is always uncleanable
                        Optional.of(log.activeSegment().baseOffset()),

                        // the first segment whose largest message timestamp is within a minimum time lag from now
                        minCompactionLagMs > 0 ? findFirstUncleanableSegment(log, firstDirtyOffset, now, minCompactionLagMs) : Optional.<Long>empty()
                )
                .flatMap(Optional::stream)
                .min(Long::compare)
                .orElseThrow(() -> new IllegalStateException("No uncleanable offset found"));

So a low-traffic compacted topic is not compacted until its active segment rolls. With defaults that can take 7 days of record time, or never if nothing is written, since a roll is checked on append (§05). The docs make the first half of the point; the "never" is my synthesis reconstruction. If a cleaner fails on one partition, that partition is marked uncleanable and the thread carries on, so the partition grows until someone notices uncleanable-partitions-count (LogCleaner.java:538-539).

The dedupe map stores a key hash and an offset, never the key: MD5 by default, so 16 + 8 = 24 bytes per entry. With defaults that is 134,217,728 / 24 = 5,592,405 slots, times 0.9, about 5,033,164 usable keys per pass per thread share. When the map is full the pass cleans only as far as it reached, and the next pass continues. Aborted batches are never added to it, so an aborted update can't shadow an older committed value (Cleaner.java:737-739, :746-749).

Keep or drop

storage/…/log/Cleaner.java:505-529:

        boolean pastLatestOffset = record.offset() > map.latestOffset();
        if (pastLatestOffset) {
            return true;
        }

        if (record.hasKey()) {
            ByteBuffer key = record.key();
            long foundOffset = map.get(key);
            /* First,the message must have the latest offset for the key
             * then there are two cases in which we can retain a message:
             *   1) The message has value
             *   2) The message doesn't have value but it can't be deleted now.
             */
            boolean latestOffsetForKey = record.offset() >= foundOffset;
            boolean legacyRecord = batch.magic() < RecordBatch.MAGIC_VALUE_V2;

            boolean shouldRetainDeletes;
            if (!legacyRecord) {
                shouldRetainDeletes = batch.deleteHorizonMs().isEmpty() || currentTime < batch.deleteHorizonMs().getAsLong();
            } else {
                shouldRetainDeletes = retainDeletesForLegacyRecords;
            }

            boolean isRetainedValue = record.hasValue() || shouldRetainDeletes;
            return latestOffsetForKey && isRetainedValue;

A keyless record that reaches the cleaner is dropped, while new keyless writes to a compacted topic are refused at produce time. By my reading, switching an existing delete topic to compact therefore removes its keyless history reconstruction. Records of aborted transactions go at once, and markers follow the tombstone clock after all the transaction's data is gone (LogCleaner.java:89-90).

A batch that would be empty is still kept, header only, if it holds an active producer's last sequence, or is the last batch before the high watermark (Cleaner.java:357-362). KAFKA-20452, in 4.4.0, narrowed the second case to the high watermark. So a compacted log never quite reaches one record per key: D52, class D.

Physically the cleaner copies a group of neighbouring segments into one new .cleaned file named for the first segment's base, flushes it, keeps the old mtime, and swaps it in. The swap is two-phase: .cleaned becomes .swap, the old files become .deleted, and the .swap suffix is removed last (LocalLog.java:1026-1033, :1060). In the run, each pass merged into one growing file named for offset 0: 116, 177, 238, 299, 377, 444, then 522 bytes. On 4.4.0 a cleaned segment can still overflow after a compression change, because the KAFKA-20036 fix was reverted for the 4.4 line before release, citing a bug (D6, class B). That JIRA is Reopened with fix version 4.5.0. Trunk has a form of it; trunk was read, never built.

The two clocks

The first clock starts at the first cleaning that sees the tombstone, not when it was written. The horizon is the cleaner's current time plus delete.retention.ms, default 24 hours, and it is stored in the batch itself: attribute bit 6 is set, BaseTimestamp is overwritten, and record deltas are rewritten to match (MemoryRecords.java:171-179, DefaultRecordBatch.java:258). The second clock is whichever later pass finds the horizon past. There is no timer that removes it. The run used delete.retention.ms=20000 measured here:

                     rec off=15 key=b'k0' value=None raw=1400abfd0300046b300100

consumer now sees  11 k1 g3 / 12 k2 g3 / 13 k3 g3 / 14 k4 g3 / 16 s1 / 17 s2 / 18 s3 / 19 s4

Look at ab fd 03 in that record. It is the timestamp delta, now a negative zigzag varlong, so base plus delta is still the original write time. The 1793978771483 is 15:26:11.483, exactly 20,000 ms after the cleaner began.

A consumer that had cached k0 and came back after that pass would never learn of the delete. The docs state the consequence exactly: "it is possible for a consumer to miss delete markers if it lags by more than delete.retention.ms" (design.md:424). Offsets never change under compaction, so offsets can be missing, and a read for a missing one lands on the next batch with a higher base offset.

One log line reads as if it governs all this and doesn't. The cleaner's INFO line says "discarding tombstones prior to upper bound deletion horizon". The code says that value applies only to pre-v2 formats (Cleaner.java:146). At 15:25:51 it named 15:25:17, while the tombstone written at 15:25:38 was in fact given a horizon of 15:26:11 (D12, class C).
