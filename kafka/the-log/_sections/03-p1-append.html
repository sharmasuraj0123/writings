{{S}}Writing, not syncing

An append is mostly bookkeeping around one plain write. Every append, leader or follower, runs the same CRC check before anything touches the file (storage/…/log/UnifiedLog.java:1572-1575, :1141). Then the offset, epoch-cache, roll and file-write steps all happen inside one per-partition lock, so appends to one partition are serial (:1150-1276) from the code.

On the leader the broker assigns offsets starting at the log end offset; a follower takes the offsets it is given and rejects going backwards (:1157-1204). Part 3 owns the follower path. For an uncompressed batch, assigning offsets is an in-place header edit. Only the base offset field and the leader epoch change, and neither is under the CRC, so the record bytes and the CRC the client computed reach disk untouched (LogValidator.java:264-267, DefaultRecordBatch.java:377-378, :396-397).

Two conditions keep that from being absolute. Compressed batches stay in place only when the producer's codec matches the topic's target codec; otherwise the broker recompresses (LogValidator.java:294-304). And the broker recomputes the CRC if the maximum timestamp or timestamp type really changes, which is the LogAppendTime case (DefaultRecordBatch.java:384-392). A single append larger than segment.bytes is rejected outright, since a batch never spans segments (UnifiedLog.java:1242-1243) from the code.

Here is the write, with a comment that explains an ordering few readers would guess. storage/…/log/UnifiedLog.java:1270-1277:

Nobody on the produce path calls that by default. The only flush on the append path is one line, gated on flush.messages. storage/…/log/UnifiedLog.java:1300: 

                                if (localLog.unflushedMessages() >= config().flushInterval) flush(false);

flush.messages defaults to Long.MAX_VALUE, and the periodic flusher's default interval is also Long.MAX_VALUE (ServerLogConfigs.java:101, :109). A small aside: unflushedMessages is arithmetic on offsets, not a count of records, so on a compacted or gapped log it overstates (LocalLog.java:252-253) from the code.

This is the design, stated in the design doc. docs/design/design.md:64: "All data is immediately written to a persistent log on the filesystem without necessarily flushing to disk. In effect this just means that it is transferred into the kernel's pagecache." The register lists it as D41, class D (gotcha), status intended: acked data can sit on an active segment with no Kafka fsync, while the kernel's writeback still runs.

Counting the calls

An LD_PRELOAD shim counted sync calls by thread and file while a producer ran at acks=all for 12 s on one broker. The tally window was about 25 s around that run, with defaults except segment.bytes=8388608, replication factor 1 measured here:

About 15,573 records were acked into topic pc, and its .log saw exactly one fsync, from kafka-scheduler. That one came from the roll. Rolling schedules an asynchronous flush of everything below the new base, and it is the one routine fsync on the data path (UnifiedLog.java:2289-2291). At the 1 GiB default, this window has no roll, and so, by the code, no data fsync at all. The same window shows who does flush: the metadata log, 49 times, from kafka-1-raft-io. That is KRaft.

With flush.messages=1 the fsyncs move: 1,108 each of .log, .index and .timeindex, once per append and not per record. The thread name data-plane-kafk covers network and handler threads alike, so "on the request path" comes from reading the code (SocketServer.scala:746, KafkaRequestHandler.scala:275), not from the shim.

What does fsync cost? This lab can't say. flush.messages=1 did not lower the acked count, 18,819 against 15,572 in equal 12 s runs. That is not evidence that fsync is free: it is one pair on a shared disk under other load, with a cold JVM in the first run, and these are not rates. Replication's own single pair points the other way, 239 ms against 510 ms mean latency. The design doc's "two to three orders of magnitude" (design.md:335) was neither reproduced nor properly tested. All timing here is loopback on a shared 2-vCPU box.

So the first line in this log, the log end offset, moves without any disk being involved. The next line down, what has been flushed, moves on the scheduler's time. §07 is what that gap costs.
