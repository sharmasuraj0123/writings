{{S}}A partition is a directory

Kafka is one data structure used five times: an append-only log whose disk format is its wire format, replicated by followers pulling. Nearly every promise it makes is a statement about where a line sits in such a log, not about a disk or an outcome: the high watermark, the last stable offset, the recovery point, the committed offset, the metadata commit. Read a guarantee as "which line, in which log, moved by whom", and both the guarantee and its edges follow. This collection reads Apache Kafka 4.4.0 that way, in five parts. This first part is the log itself. A partition is a directory of segments holding batches exactly as the producer sent them. The broker stamps only fields outside the CRC, syncs nothing on append by default, and checks CRCs only above the recovery point, which is why hand-injected damage has such uneven results.

Most of the design is visible in ls. Here is a fresh partition of a topic named bytes, holding nine records from three lab producers, on one broker over loopback. Real output, with the owner columns dropped measured here: 

10485760  00000000000000000000.index
     424  00000000000000000000.log
10485756  00000000000000000000.timeindex
       8  leader-epoch-checkpoint
      43  partition.metadata

Five files. There is no .snapshot or .txnindex yet; those wait until something asks for one. The twenty-digit name is the segment's base offset, the first offset it can hold. The .log holds the records. It is 424 bytes because nine small records were written. The two indexes look enormous beside it, and they hold nothing: du reports 0 KiB of real blocks for each, and 4 KiB each once a few entries are written. They are sparse files, created at full length and memory-mapped. The 10 MiB comes from segment.index.bytes, rounded down to a multiple of the entry size, which is why the time index, with 12-byte entries, is 10,485,756 bytes and not 10,485,760 from the code.

The classes follow the files. UnifiedLog is the public face of one partition's log, and it spans a local part and an optional remote part: tiered segments first, then an optional overlap, then local segments including the active one (storage/…/log/UnifiedLog.java:95-100). It hands local segment handling to an encapsulated LocalLog. A LogSegment is a FileRecords, a lazily opened offset index, a lazily opened time index and a transaction index, and it is not thread-safe on its own (LogSegment.java:63-82). That class's own comment still says a segment is "stored in two files", against the listing above. The register carries it as D11, class C (doc drift).

The full vocabulary is a fixed set of suffixes in LogFileUtils.java:27-58: .log, .index, .timeindex, .txnindex and .snapshot, plus three transient ones used for crash-safe replacement and deletion: .cleaned, .swap and .deleted. A file's suffix is part of the recovery protocol, as §07 shows.

The two sidecars are small and human-readable. partition.metadata carries the topic ID, which differs per run. leader-epoch-checkpoint is a version line, a count, and epoch startOffset pairs; on this partition it reads 0, 1, 0 0 measured here.

One level up, the log directory holds the lines. recovery-point-offset-checkpoint and log-start-offset-checkpoint are named offset checkpoints for the log layer, and they are written on a 60-second timer, not on each flush (LogManager.java:85-86, server-common/…/ServerLogConfigs.java:115-120) from the code. That timer matters later. A file on disk can be flushed while the file that says so is a minute behind.

A clean shutdown adds one more file. LogManager writes a marker holding the broker epoch, and only after recovery points and log start offsets are checkpointed (LogManager.java:898-911). On disk it was one line of JSON named .kafka_cleanshutdown: {"version":0,"brokerEpoch":15}. The same stop trimmed the active segment: .index to 0 bytes, .timeindex to 12 bytes, one entry, and a .snapshot named for the next offset appeared measured here. That marker is a one-bit answer to a large question. Its presence decides whether recovery runs at the next start.

So the map of this part is the listing. §02 opens the .log. §03 asks when its bytes reach the disk. §04 reads the two indexes. §05 is what rolls a segment and what deletes one. §06 is what rewrites one. §07 is what happens when the bytes are wrong. Part 2 then follows the same bytes onto the wire, and Part 3 follows them to other brokers.
