{{S}}The batch, byte by byte

A segment is not a list of records. It is a list of batches, and the batch is the unit of everything: what a producer sends, what a broker appends, what a follower copies, what a consumer receives, what compaction rewrites. Here is the top of that 424-byte .log, produced with a fixed base timestamp of 1767225600000 (2026-01-01T00:00:00Z) so the bytes reproduce. The run was python3 -I results/log/hexd.py, because xxd is not installed on this box measured here:

The header

The schema is fixed: 8-byte base offset, 4-byte length, 4-byte partition leader epoch, 1-byte magic, 4-byte CRC, 2-byte attributes, then the delta, two timestamps, the producer fields and a record count. Adding the lengths gives 8+4+4+1+4+2+4+8+8+8+2+4+4 = 61, and the first record of every measured uncompressed batch began at byte 61 of its batch (clients/…/record/internal/DefaultRecordBatch.java:48-60, :104-131) from the code.

Length excludes the first 12 bytes, so a reader finds the next batch at position + 12 + Length. This batch says 0x52, which is 82, so it occupies 94 bytes, and the next batch began at 94. That is the whole trick behind scanning a log: you hop from header to header and never look inside.

What the CRC leaves out

The source comment says it plainly. clients/…/record/internal/DefaultRecordBatch.java:67-71: 

 * The CRC covers the data from the attributes to the end of the batch (i.e. all the bytes that follow the CRC). It is
 * located after the magic byte, which means that clients must parse the magic byte before deciding how to interpret
 * the bytes between the batch length and the magic byte. The partition leader epoch field is not included in the CRC
 * computation to avoid the need to recompute the CRC when this field is assigned for every batch that is received by
 * the broker. The CRC-32C (Castagnoli) polynomial is used for the computation.

So base offset, length, leader epoch and magic are all outside the CRC. The comment gives the reason for the epoch. The base offset is excluded by position, and it is the other field the broker assigns. An independent Python CRC-32C over byte 21 to end of batch matched the stored value for all five batches of this log measured here. This one layout choice carries two consequences through the rest of the part. A broker can append a producer's bytes without recomputing anything (§03). And a damaged base offset is not a CRC failure, so it takes a different road through recovery (§07).

The attributes field uses seven low bits: three for compression, then timestamp type, transactional, control and delete horizon (DefaultRecordBatch.java:100-136). The measured values match that map: 0x0000 plain, 0x0001 gzip, 0x0010 transactional data, 0x0030 a transaction control batch measured here.

A record is mostly deltas

A record carries only deltas against its batch: a varint length, an attributes byte that is always 0, a zigzag varlong timestamp delta, a zigzag varint offset delta, then key, value and headers (DefaultRecord.java:175-181). The smallest record in the lab, k1→v1, took 11 bytes: 

14    00     00      00      04     6b 31  04       76 31  00
len   attrs  ts-Δ    off-Δ   keylen "k1"   vallen   "v1"   headers
=10   =0     =0      =0      =2            =2              =0

Zigzag doubles small positive numbers, so 0x14 means 10 and 0x04 means 2. The second record shows the deltas at work: offset delta and timestamp delta both 1, each encoded as 02. Six bytes of payload per record cost 11 bytes on disk plus a share of the 61-byte header. Batching pays for itself quickly. A batch of one record, at position 170 of this file, is 70 bytes for a 2-byte key.

That one-record batch is a tombstone, and it shows how little marks a delete. A tombstone is a record whose value length is the varint for −1, which encodes as the single byte 01: raw 10 00 00 00 04 6b 31 01 00. Nothing else flags it. Headers are as plain. The record at position 94 ends 02 02 68 02 31: one header, key h, value 1 measured here.

With compression, the whole record area after RecordsCount is one blob. At byte 301 of the file the gzip magic 1f 8b begins, and 48 stored bytes inflate to 123 bytes of records. Each batch has its own compression context; there is no per-record compression (DefaultRecordBatch.java:64-65).

The fields that look unused

The bytes above show ProducerId 0, epoch 0 and base sequence 0 on a batch from a Java producer with no configuration. That is not an unset field. The default producer in 4.4.0 is idempotent: three batches from one producer carried sequence 0, 3, 4, tracking its record count, and the next producer started again at sequence 0 with a new ID. A batch from a non-idempotent producer writes −1 in all three fields, visible as 14 ff bytes at the end of this file measured here. These fields came with the v2 format, from the "Message Format" section of KIP-98, which bumps the magic byte to 2. Part 4 is what the broker does with them.

The header's first and last offset and sequence also have a job the records can't do. Compaction relies on them surviving, so lastOffsetDelta stays even if the records go (DefaultRecordBatch.java:55, :73); §06 shows batches with no records at all. And a control batch is an ordinary batch holding one record whose 4-byte key is version plus type, with ABORT 0 and COMMIT 1 (ControlRecordType.java:32-45). The lab's abort marker key was 00 00 00 00 and its commit marker key 00 00 00 01. What those markers mean is Part 5.
