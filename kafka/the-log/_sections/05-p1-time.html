{{S}}Rolls and retention run on record time

Two jobs need to know how old a segment is, and both answer from the records. A record's timestamp is, by default, whatever the producer wrote. So a producer can roll segments early, stall retention, or have its data deleted in seconds. The register carries this as D42, class D (gotcha).

The roll

A segment rolls on any of five conditions: too big for the incoming batch, too old, offset index full, time index full, or next offset not representable relative to the base. storage/…/log/LogSegment.java:167-173: 

    public boolean shouldRoll(RollParams rollParams) throws IOException {
        boolean reachedRollMs = timeWaitedForRoll(rollParams.now(), rollParams.maxTimestampInMessages()) > rollParams.maxSegmentMs() - rollJitterMs;
        int size = size();
        return size > rollParams.maxSegmentBytes() - rollParams.messagesSize() ||
            (size > 0 && reachedRollMs) ||
            offsetIndex().isFull() || timeIndex().isFull() || !canConvertToRelativeOffset(rollParams.maxOffsetInMessages());
    }

The defaults are 1 GiB and 7 days. "Too old" is the surprising one. LogSegment.java:709-716: 

    public long timeWaitedForRoll(long now, long messageTimestamp) {
        // Load the timestamp of the first message into memory
        loadFirstBatchTimestamp();
        long ts = rollingBasedTimestamp.orElse(-1L);
        if (ts >= 0)
            return messageTimestamp - ts;
        return now - created;
    }

That compares the incoming batch's record timestamp with the first batch's timestamp in the segment. The wall clock is used only if that batch has no timestamp. And since the check runs inside append (UnifiedLog.java:1248), a segment that gets no writes never rolls at this check from the code.

The lab shows this three ways, in single runs measured here:

  • With segment.ms=60000, a segment rolled on one record stamped 81 s ahead of the first batch, while the wall clock moved 5 s between the two surrounding date calls.
  • A default topic rolled straight after a backdated transactional batch. The control marker carries wall-clock time, 10 months ahead of the data's timestamp, which exceeded the 7-day default. The first segment held 2 offsets and 95 bytes.
  • An old-stamped record does not trigger a roll at all. Record timestamp minus first-batch timestamp is negative, so offsets 2 and 3 joined a segment despite segment.ms=1000.

A roll does four things in order: complete the old segment, open a new one at max(expected, LEO), snapshot producer state, and schedule an asynchronous flush of everything below the new base (LocalLog.java:592, :633, UnifiedLog.java:2245). Becoming inactive appends the largest timestamp to the time index and trims both indexes to real size: the 72 and 120 bytes of Figure {{fig-directory}}.

Retention

Retention is a broker timer, every 5 minutes by default, with 7-day time retention and unlimited size retention. The policy decides which checks run: delete runs start-offset, size and time; compact alone runs only the start-offset check (UnifiedLog.java:1984-2000). Time retention compares the clock with the segment's largest record timestamp, falling back to file mtime only if no record has a timestamp. A future timestamp makes the difference negative, so the segment waits; since 4.1.0 this logs a warning (KAFKA-18929). Bounds on the producer are lopsided. message.timestamp.after.max.ms defaults to one hour, while the "before" bound defaults to unlimited, so arbitrarily old timestamps are accepted (ServerLogConfigs.java:132-139).

The walk is the part to read. storage/…/log/UnifiedLog.java:1906-1919:

It walks from the oldest segment and stops at the first one not eligible, so one young segment shields every older-stamped segment behind it. Nothing at or above the high watermark can go. Size retention removes only whole segments, and only while the excess still covers the whole segment, so a log settles between retention.bytes and retention.bytes plus one segment reconstruction. If every segment qualifies, including the active one, the log first rolls a new empty one, because a log must always have one. The log start offset moves before segments leave the lookup map. Files are then renamed .deleted and removed after file.delete.delay.ms, default 60 s, so in-flight readers of the open channels are safe.

One run, two topics, with retention.ms=1h, records stamped 2 h old, and a 2 s check interval measured here. In the control, segments went away as soon as they stopped being last, and .deleted files sat on disk for the configured 6 s. In the second topic, retention removed an active segment holding only old records. The topic's first record was gone within seconds, before the script's next produce arrived, so backdated data can vanish fast. Then two 2-hour-old records sat in a segment whose first record was fresh, and 14 s of checks left them alone. One young record protects its whole segment. The cross-segment half of that shielding (D43) is read in code and not measured.
