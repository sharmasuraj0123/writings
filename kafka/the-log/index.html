01A partition is a directory

Kafka is one data structure used five times: an append-only log whose disk format is its wire format, replicated by followers pulling. Nearly every promise it makes is a statement about where a line sits in such a log, not about a disk or an outcome: the high watermark, the last stable offset, the recovery point, the committed offset, the metadata commit. Read a guarantee as "which line, in which log, moved by whom", and both the guarantee and its edges follow. This collection reads Apache Kafka 4.4.0 that way, in five parts. This first part is the log itself. A partition is a directory of segments holding batches exactly as the producer sent them. The broker stamps only fields outside the CRC, syncs nothing on append by default, and checks CRCs only above the recovery point, which is why hand-injected damage has such uneven results.

Most of the design is visible in ls. Here is a fresh partition of a topic named bytes, holding nine records from three lab producers, on one broker over loopback. Real output, with the owner columns dropped measured here: 

10485760  00000000000000000000.index
     424  00000000000000000000.log
10485756  00000000000000000000.timeindex
       8  leader-epoch-checkpoint
      43  partition.metadata

Five files. There is no .snapshot or .txnindex yet; those wait until something asks for one. The twenty-digit name is the segment's base offset, the first offset it can hold. The .log holds the records. It is 424 bytes because nine small records were written. The two indexes look enormous beside it, and they hold nothing: du reports 0 KiB of real blocks for each, and 4 KiB each once a few entries are written. They are sparse files, created at full length and memory-mapped. The 10 MiB comes from segment.index.bytes, rounded down to a multiple of the entry size, which is why the time index, with 12-byte entries, is 10,485,756 bytes and not 10,485,760 from the code.

The classes follow the files. UnifiedLog is the public face of one partition's log, and it spans a local part and an optional remote part: tiered segments first, then an optional overlap, then local segments including the active one (storage/…/log/UnifiedLog.java:95-100). It hands local segment handling to an encapsulated LocalLog. A LogSegment is a FileRecords, a lazily opened offset index, a lazily opened time index and a transaction index, and it is not thread-safe on its own (LogSegment.java:63-82). That class's own comment still says a segment is "stored in two files", against the listing above. The register carries it as D11, class C (doc drift).

The full vocabulary is a fixed set of suffixes in LogFileUtils.java:27-58: .log, .index, .timeindex, .txnindex and .snapshot, plus three transient ones used for crash-safe replacement and deletion: .cleaned, .swap and .deleted. A file's suffix is part of the recovery protocol, as §07 shows.

The two sidecars are small and human-readable. partition.metadata carries the topic ID, which differs per run. leader-epoch-checkpoint is a version line, a count, and epoch startOffset pairs; on this partition it reads 0, 1, 0 0 measured here.

One level up, the log directory holds the lines. recovery-point-offset-checkpoint and log-start-offset-checkpoint are named offset checkpoints for the log layer, and they are written on a 60-second timer, not on each flush (LogManager.java:85-86, server-common/…/ServerLogConfigs.java:115-120) from the code. That timer matters later. A file on disk can be flushed while the file that says so is a minute behind.

A clean shutdown adds one more file. LogManager writes a marker holding the broker epoch, and only after recovery points and log start offsets are checkpointed (LogManager.java:898-911). On disk it was one line of JSON named .kafka_cleanshutdown: {"version":0,"brokerEpoch":15}. The same stop trimmed the active segment: .index to 0 bytes, .timeindex to 12 bytes, one entry, and a .snapshot named for the next offset appeared measured here. That marker is a one-bit answer to a large question. Its presence decides whether recovery runs at the next start.

So the map of this part is the listing. §02 opens the .log. §03 asks when its bytes reach the disk. §04 reads the two indexes. §05 is what rolls a segment and what deletes one. §06 is what rewrites one. §07 is what happens when the bytes are wrong. Part 2 then follows the same bytes onto the wire, and Part 3 follows them to other brokers.

02The batch, byte by byte

A segment is not a list of records. It is a list of batches, and the batch is the unit of everything: what a producer sends, what a broker appends, what a follower copies, what a consumer receives, what compaction rewrites. Here is the top of that 424-byte .log, produced with a fixed base timestamp of 1767225600000 (2026-01-01T00:00:00Z) so the bytes reproduce. The run was python3 -I results/log/hexd.py, because xxd is not installed on this box measured here: 

00000000: 00 00 00 00 00 00 00 00 00 00 00 52 00 00 00 00  ...........R....
00000010: 02 39 07 c8 f6 00 00 00 00 00 02 00 00 01 9b 76  .9.............v
00000020: da a8 00 00 00 01 9b 76 da a8 02 00 00 00 00 00  .......v........
00000030: 00 00 00 00 00 00 00 00 00 00 00 00 03 14 00 00  ................
00000040: 00 04 6b 31 04 76 31 00 14 00 02 02 04 6b 32 04  ..k1.v1......k2.
00000050: 76 32 00 14 00 04 04 04 6b 33 04 76 33 00 00 00  v2......k3.v3...

The header

The schema is fixed: 8-byte base offset, 4-byte length, 4-byte partition leader epoch, 1-byte magic, 4-byte CRC, 2-byte attributes, then the delta, two timestamps, the producer fields and a record count. Adding the lengths gives 8+4+4+1+4+2+4+8+8+8+2+4+4 = 61, and the first record of every measured uncompressed batch began at byte 61 of its batch (clients/…/record/internal/DefaultRecordBatch.java:48-60, :104-131) from the code.

Length excludes the first 12 bytes, so a reader finds the next batch at position + 12 + Length. This batch says 0x52, which is 82, so it occupies 94 bytes, and the next batch began at 94. That is the whole trick behind scanning a log: you hop from header to header and never look inside.

What the CRC leaves out

The source comment says it plainly. clients/…/record/internal/DefaultRecordBatch.java:67-71: 

 * The CRC covers the data from the attributes to the end of the batch (i.e. all the bytes that follow the CRC). It is
 * located after the magic byte, which means that clients must parse the magic byte before deciding how to interpret
 * the bytes between the batch length and the magic byte. The partition leader epoch field is not included in the CRC
 * computation to avoid the need to recompute the CRC when this field is assigned for every batch that is received by
 * the broker. The CRC-32C (Castagnoli) polynomial is used for the computation.

So base offset, length, leader epoch and magic are all outside the CRC. The comment gives the reason for the epoch. The base offset is excluded by position, and it is the other field the broker assigns. An independent Python CRC-32C over byte 21 to end of batch matched the stored value for all five batches of this log measured here. This one layout choice carries two consequences through the rest of the part. A broker can append a producer's bytes without recomputing anything (§03). And a damaged base offset is not a CRC failure, so it takes a different road through recovery (§07).

The attributes field uses seven low bits: three for compression, then timestamp type, transactional, control and delete horizon (DefaultRecordBatch.java:100-136). The measured values match that map: 0x0000 plain, 0x0001 gzip, 0x0010 transactional data, 0x0030 a transaction control batch measured here.

A record is mostly deltas

A record carries only deltas against its batch: a varint length, an attributes byte that is always 0, a zigzag varlong timestamp delta, a zigzag varint offset delta, then key, value and headers (DefaultRecord.java:175-181). The smallest record in the lab, k1→v1, took 11 bytes: 

14    00     00      00      04     6b 31  04       76 31  00
len   attrs  ts-Δ    off-Δ   keylen "k1"   vallen   "v1"   headers
=10   =0     =0      =0      =2            =2              =0

Zigzag doubles small positive numbers, so 0x14 means 10 and 0x04 means 2. The second record shows the deltas at work: offset delta and timestamp delta both 1, each encoded as 02. Six bytes of payload per record cost 11 bytes on disk plus a share of the 61-byte header. Batching pays for itself quickly. A batch of one record, at position 170 of this file, is 70 bytes for a 2-byte key.

That one-record batch is a tombstone, and it shows how little marks a delete. A tombstone is a record whose value length is the varint for −1, which encodes as the single byte 01: raw 10 00 00 00 04 6b 31 01 00. Nothing else flags it. Headers are as plain. The record at position 94 ends 02 02 68 02 31: one header, key h, value 1 measured here.

With compression, the whole record area after RecordsCount is one blob. At byte 301 of the file the gzip magic 1f 8b begins, and 48 stored bytes inflate to 123 bytes of records. Each batch has its own compression context; there is no per-record compression (DefaultRecordBatch.java:64-65).

The fields that look unused

The bytes above show ProducerId 0, epoch 0 and base sequence 0 on a batch from a Java producer with no configuration. That is not an unset field. The default producer in 4.4.0 is idempotent: three batches from one producer carried sequence 0, 3, 4, tracking its record count, and the next producer started again at sequence 0 with a new ID. A batch from a non-idempotent producer writes −1 in all three fields, visible as 14 ff bytes at the end of this file measured here. These fields came with the v2 format, from the "Message Format" section of KIP-98, which bumps the magic byte to 2. Part 4 is what the broker does with them.

The header's first and last offset and sequence also have a job the records can't do. Compaction relies on them surviving, so lastOffsetDelta stays even if the records go (DefaultRecordBatch.java:55, :73); §06 shows batches with no records at all. And a control batch is an ordinary batch holding one record whose 4-byte key is version plus type, with ABORT 0 and COMMIT 1 (ControlRecordType.java:32-45). The lab's abort marker key was 00 00 00 00 and its commit marker key 00 00 00 01. What those markers mean is Part 5.

None of this rests on one decoder. kafka-dump-log.sh --print-data-log --deep-iteration printed the same fields for the same file measured here: 

baseOffset: 0 lastOffset: 2 count: 3 baseSequence: 0 lastSequence: 2 producerId: 0
  producerEpoch: 0 partitionLeaderEpoch: 0 isTransactional: false isControl: false …
| offset: 0 CreateTime: 1767225600000 keySize: 2 valueSize: 2 sequence: 0 headerKeys: [] key: k1 payload: v1

03Writing, not syncing

An append is mostly bookkeeping around one plain write. Every append, leader or follower, runs the same CRC check before anything touches the file (storage/…/log/UnifiedLog.java:1572-1575, :1141). Then the offset, epoch-cache, roll and file-write steps all happen inside one per-partition lock, so appends to one partition are serial (:1150-1276) from the code.

On the leader the broker assigns offsets starting at the log end offset; a follower takes the offsets it is given and rejects going backwards (:1157-1204). Part 3 owns the follower path. For an uncompressed batch, assigning offsets is an in-place header edit. Only the base offset field and the leader epoch change, and neither is under the CRC, so the record bytes and the CRC the client computed reach disk untouched (LogValidator.java:264-267, DefaultRecordBatch.java:377-378, :396-397).

Two conditions keep that from being absolute. Compressed batches stay in place only when the producer's codec matches the topic's target codec; otherwise the broker recompresses (LogValidator.java:294-304). And the broker recomputes the CRC if the maximum timestamp or timestamp type really changes, which is the LogAppendTime case (DefaultRecordBatch.java:384-392). A single append larger than segment.bytes is rejected outright, since a batch never spans segments (UnifiedLog.java:1242-1243) from the code.

Here is the write, with a comment that explains an ordering few readers would guess. storage/…/log/UnifiedLog.java:1270-1277: 

                                // Append the records, and increment the local log end offset immediately after the append because a
                                // write to the transaction index below may fail, and we want to ensure that the offsets
                                // of future appends still grow monotonically. The resulting transaction index inconsistency
                                // will be cleaned up after the log directory is recovered. Note that the end offset of the
                                // ProducerStateManager will not be updated and the last stable offset will not advance
                                // if the append to the transaction index fails.
                                localLog.append(appendInfo.lastOffset(), validRecords);
                                updateHighWatermarkWithLogEndOffset();

Beneath that sits a channel write and an in-memory size. Durability is a different method, a few lines further down the same file. clients/…/record/internal/FileRecords.java:200-209: 

        int written = records.writeFullyTo(channel);
        size.getAndAdd(written);
        return written;
    }

    /**
     * Commit all written data to the physical disk
     */
    public void flush() throws IOException {
        channel.force(true);

Nobody on the produce path calls that by default. The only flush on the append path is one line, gated on flush.messages. storage/…/log/UnifiedLog.java:1300: 

                                if (localLog.unflushedMessages() >= config().flushInterval) flush(false);

flush.messages defaults to Long.MAX_VALUE, and the periodic flusher's default interval is also Long.MAX_VALUE (ServerLogConfigs.java:101, :109). A small aside: unflushedMessages is arithmetic on offsets, not a count of records, so on a compacted or gapped log it overstates (LocalLog.java:252-253) from the code.

This is the design, stated in the design doc. docs/design/design.md:64: "All data is immediately written to a persistent log on the filesystem without necessarily flushing to disk. In effect this just means that it is transferred into the kernel's pagecache." The register lists it as D41, class D (gotcha), status intended: acked data can sit on an active segment with no Kafka fsync, while the kernel's writeback still runs.

Counting the calls

An LD_PRELOAD shim counted sync calls by thread and file while a producer ran at acks=all for 12 s on one broker. The tally window was about 25 s around that run, with defaults except segment.bytes=8388608, replication factor 1 measured here:

About 15,573 records were acked into topic pc, and its .log saw exactly one fsync, from kafka-scheduler. That one came from the roll. Rolling schedules an asynchronous flush of everything below the new base, and it is the one routine fsync on the data path (UnifiedLog.java:2289-2291). At the 1 GiB default, this window has no roll, and so, by the code, no data fsync at all. The same window shows who does flush: the metadata log, 49 times, from kafka-1-raft-io. That is KRaft.

With flush.messages=1 the fsyncs move: 1,108 each of .log, .index and .timeindex, once per append and not per record. The thread name data-plane-kafk covers network and handler threads alike, so "on the request path" comes from reading the code (SocketServer.scala:746, KafkaRequestHandler.scala:275), not from the shim.

What does fsync cost? This lab can't say. flush.messages=1 did not lower the acked count, 18,819 against 15,572 in equal 12 s runs. That is not evidence that fsync is free: it is one pair on a shared disk under other load, with a cold JVM in the first run, and these are not rates. Replication's own single pair points the other way, 239 ms against 510 ms mean latency. The design doc's "two to three orders of magnitude" (design.md:335) was neither reproduced nor properly tested. All timing here is loopback on a shared 2-vCPU box.

So the first line in this log, the log end offset, moves without any disk being involved. The next line down, what has been flushed, moves on the scheduler's time. §07 is what that gap costs.

04From an offset to a byte

A consumer asks for an offset. The file only knows bytes. Two sparse, unchecksummed indexes and a short scan turn one into the other. An offset index entry is 8 bytes: a 4-byte offset relative to the segment base and a 4-byte file position. That relative offset is why a segment cannot span more than Integer.MAX_VALUE offsets. A time index entry is 12 bytes: an 8-byte timestamp and a 4-byte relative offset (OffsetIndex.java:44-56, TimeIndex.java:35-56) from the code.

The entries are sparse, and the rule lives in the append loop. storage/…/log/LogSegment.java:263-278: 

            for (RecordBatch batch : records.batches()) {
                long batchMaxTimestamp = batch.maxTimestamp();
                long batchLastOffset = batch.lastOffset();
                if (batchMaxTimestamp > maxTimestampSoFar()) {
                    maxTimestampAndOffsetSoFar = new TimestampOffset(batchMaxTimestamp, batchLastOffset);
                }

                if (bytesSinceLastIndexEntry > indexIntervalBytes) {
                    offsetIndex().append(batchLastOffset, physicalPosition);
                    timeIndex().maybeAppend(maxTimestampSoFar(), shallowOffsetOfMaxTimestampSoFar());
                    bytesSinceLastIndexEntry = 0;
                }
                var sizeInBytes = batch.sizeInBytes();
                physicalPosition += sizeInBytes;
                bytesSinceLastIndexEntry += sizeInBytes;
            }

Read the order. The check runs before the current batch's bytes are counted, so the first batch of a segment never gets an entry. And the entry pairs a batch's last offset with the position where that batch starts. At the default 4,096-byte interval, one entry covers about 4 KiB of log. The lab shows the rule exactly: with two-record batches of about 283 bytes and a 400-byte interval, the first slot is relative offset 5 at position 566, the third batch's start, whose records are offsets 4 and 5 measured here.

Below the first entry, lookup returns the pair (base offset, 0), so a segment with no entries is scanned from the top (OffsetIndex.java:94-102, LogSegment.java:399-400, FileRecords.java:302-332). The binary search has one performance scar: it first tries a "warm" tail of 8,192 bytes of entries, to keep in-sync lookups on recently used pages. The comment records that plain binary search caused page faults that pushed produce latency to about a second (AbstractIndex.java:354-355, :498-502) from the code.

The time index is not a second view of the same entries. Its timestamps only go up within a file: an entry records the largest timestamp seen so far and the offset of the batch that had it (TimeIndex.java:42, :196). One out-of-order batch is enough to split the two.

Believed on open

Neither index has a checksum; the design is to rebuild on a crash. A pre-existing index file is believed on open: the position is set to the end of the file, and startup deliberately skips sanity checks of the offset and time indexes (AbstractIndex.java:483-484, LogSegment.java:185-188). By the code, corruption below the recovery point is not noticed at load; that was not tested here. Upstream treats it as an open gap: KAFKA-19200, "Indexes should be sanity checked on startup", was In Progress with no fix version on 6 November 2026. Two 4.4.0 commits (beae700199, 72b21c706e) closed a related hole, an index length that a clean shutdown could leave not durable. The commit text says it does not cover unclean shutdown.

The other two files

The .txnindex is created lazily, holds one fixed-size entry per aborted transaction, and is attached to the segment holding the abort marker, not the segment where the transaction started. Commit, abort, commit from one producer left one entry, 34 bytes measured here: 

00000000: 00 00 00 00 00 00 00 00 00 04 00 00 00 00 00 00
00000010: 00 03 00 00 00 00 00 00 00 05 00 00 00 00 00 00
00000020: 00 06
entry: version=0 producerId=4 firstOffset=3 lastOffset=5 lastStableOffset=6

A .snapshot has a 2-byte version, a 4-byte CRC-32C checked on read, and a producer array (ProducerStateManager.java:74-76). A one-producer snapshot was 56 bytes, named for the first offset it does not cover. It exists to bound recovery: a segment can be recovered from the snapshot plus a scan of that segment (UnifiedLog.java:2231-2232). It is written without fsync under the log lock, then flushed by the scheduler with the old segment.

05Rolls and retention run on record time

Two jobs need to know how old a segment is, and both answer from the records. A record's timestamp is, by default, whatever the producer wrote. So a producer can roll segments early, stall retention, or have its data deleted in seconds. The register carries this as D42, class D (gotcha).

The roll

A segment rolls on any of five conditions: too big for the incoming batch, too old, offset index full, time index full, or next offset not representable relative to the base. storage/…/log/LogSegment.java:167-173: 

    public boolean shouldRoll(RollParams rollParams) throws IOException {
        boolean reachedRollMs = timeWaitedForRoll(rollParams.now(), rollParams.maxTimestampInMessages()) > rollParams.maxSegmentMs() - rollJitterMs;
        int size = size();
        return size > rollParams.maxSegmentBytes() - rollParams.messagesSize() ||
            (size > 0 && reachedRollMs) ||
            offsetIndex().isFull() || timeIndex().isFull() || !canConvertToRelativeOffset(rollParams.maxOffsetInMessages());
    }

The defaults are 1 GiB and 7 days. "Too old" is the surprising one. LogSegment.java:709-716: 

    public long timeWaitedForRoll(long now, long messageTimestamp) {
        // Load the timestamp of the first message into memory
        loadFirstBatchTimestamp();
        long ts = rollingBasedTimestamp.orElse(-1L);
        if (ts >= 0)
            return messageTimestamp - ts;
        return now - created;
    }

That compares the incoming batch's record timestamp with the first batch's timestamp in the segment. The wall clock is used only if that batch has no timestamp. And since the check runs inside append (UnifiedLog.java:1248), a segment that gets no writes never rolls at this check from the code.

The lab shows this three ways, in single runs measured here:

  • With segment.ms=60000, a segment rolled on one record stamped 81 s ahead of the first batch, while the wall clock moved 5 s between the two surrounding date calls.
  • A default topic rolled straight after a backdated transactional batch. The control marker carries wall-clock time, 10 months ahead of the data's timestamp, which exceeded the 7-day default. The first segment held 2 offsets and 95 bytes.
  • An old-stamped record does not trigger a roll at all. Record timestamp minus first-batch timestamp is negative, so offsets 2 and 3 joined a segment despite segment.ms=1000.

A roll does four things in order: complete the old segment, open a new one at max(expected, LEO), snapshot producer state, and schedule an asynchronous flush of everything below the new base (LocalLog.java:592, :633, UnifiedLog.java:2245). Becoming inactive appends the largest timestamp to the time index and trims both indexes to real size: the 72 and 120 bytes of Figure 1.

Retention

Retention is a broker timer, every 5 minutes by default, with 7-day time retention and unlimited size retention. The policy decides which checks run: delete runs start-offset, size and time; compact alone runs only the start-offset check (UnifiedLog.java:1984-2000). Time retention compares the clock with the segment's largest record timestamp, falling back to file mtime only if no record has a timestamp. A future timestamp makes the difference negative, so the segment waits; since 4.1.0 this logs a warning (KAFKA-18929). Bounds on the producer are lopsided. message.timestamp.after.max.ms defaults to one hour, while the "before" bound defaults to unlimited, so arbitrarily old timestamps are accepted (ServerLogConfigs.java:132-139).

The walk is the part to read. storage/…/log/UnifiedLog.java:1906-1919: 

                // We don't delete segments with offsets at or beyond the high watermark to ensure that the log start
                // offset can never exceed it.
                boolean predicateResult = highWatermark() >= upperBoundOffset && predicate.execute(segment, nextSegmentOpt);

                // Roll the active segment when it breaches the configured retention policy. The rolled segment will be
                // eligible for deletion and gets removed in the next iteration.
                if (predicateResult && remoteLogEnabled() && nextSegmentOpt.isEmpty() && segment.size() > 0) {
                    shouldRoll = true;
                }
                if (predicateResult && !isLastSegmentAndEmpty && isSegmentEligibleForDeletion(nextSegmentOpt, upperBoundOffset)) {
                    deletable.add(segment);
                    segmentOpt = nextSegmentOpt;
                } else {
                    segmentOpt = Optional.empty();

It walks from the oldest segment and stops at the first one not eligible, so one young segment shields every older-stamped segment behind it. Nothing at or above the high watermark can go. Size retention removes only whole segments, and only while the excess still covers the whole segment, so a log settles between retention.bytes and retention.bytes plus one segment reconstruction. If every segment qualifies, including the active one, the log first rolls a new empty one, because a log must always have one. The log start offset moves before segments leave the lookup map. Files are then renamed .deleted and removed after file.delete.delay.ms, default 60 s, so in-flight readers of the open channels are safe.

One run, two topics, with retention.ms=1h, records stamped 2 h old, and a 2 s check interval measured here. In the control, segments went away as soon as they stopped being last, and .deleted files sat on disk for the configured 6 s. In the second topic, retention removed an active segment holding only old records. The topic's first record was gone within seconds, before the script's next produce arrived, so backdated data can vanish fast. Then two 2-hour-old records sat in a segment whose first record was fresh, and 14 s of checks left them alone. One young record protects its whole segment. The cross-segment half of that shielding (D43) is read in code and not measured.

06Compaction, and a tombstone's two clocks

Retention deletes by age. Compaction deletes by key: it recopies segments, keeping the latest value for each key and keeping every offset unchanged. A delete in this world is itself a record, and it has to stay around long enough for readers to see it. How long is decided by two clocks, and the second one needs someone to look at it.

Which log, and how far

The cleaner picks the partition with the highest ratio of cleanable bytes to clean-plus-cleanable bytes, from those above min.cleanable.dirty.ratio or overdue on max.compaction.lag.ms (LogToClean.java:54, LogCleanerManager.java:282, :290). The defaults are a 0.5 ratio, one thread, a 128 MiB dedupe buffer at 0.9 load factor, and 15 s of sleep when idle. The load factor's key is spelled log.cleaner.io.buffer.load.factor, though it configures the dedupe buffer, not I/O buffers (D13, class C). What it may touch is one expression. storage/…/log/LogCleanerManager.java:726-742: 

        // Find the first segment that cannot be cleaned. We cannot clean past:
        // 1. The active segment
        // 2. The last stable offset (including the high watermark)
        // 3. Any segments closer to the head of the log than the minimum compaction lag time
        long firstUncleanableDirtyOffset = Stream.of(
                        // we do not clean beyond the last stable offset
                        Optional.of(log.lastStableOffset()),

                        // the active segment is always uncleanable
                        Optional.of(log.activeSegment().baseOffset()),

                        // the first segment whose largest message timestamp is within a minimum time lag from now
                        minCompactionLagMs > 0 ? findFirstUncleanableSegment(log, firstDirtyOffset, now, minCompactionLagMs) : Optional.<Long>empty()
                )
                .flatMap(Optional::stream)
                .min(Long::compare)
                .orElseThrow(() -> new IllegalStateException("No uncleanable offset found"));

So a low-traffic compacted topic is not compacted until its active segment rolls. With defaults that can take 7 days of record time, or never if nothing is written, since a roll is checked on append (§05). The docs make the first half of the point; the "never" is my synthesis reconstruction. If a cleaner fails on one partition, that partition is marked uncleanable and the thread carries on, so the partition grows until someone notices uncleanable-partitions-count (LogCleaner.java:538-539).

The dedupe map stores a key hash and an offset, never the key: MD5 by default, so 16 + 8 = 24 bytes per entry. With defaults that is 134,217,728 / 24 = 5,592,405 slots, times 0.9, about 5,033,164 usable keys per pass per thread share. When the map is full the pass cleans only as far as it reached, and the next pass continues. Aborted batches are never added to it, so an aborted update can't shadow an older committed value (Cleaner.java:737-739, :746-749).

Keep or drop

A keyless record that reaches the cleaner is dropped, while new keyless writes to a compacted topic are refused at produce time. By my reading, switching an existing delete topic to compact therefore removes its keyless history reconstruction. Records of aborted transactions go at once, and markers follow the tombstone clock after all the transaction's data is gone (LogCleaner.java:89-90).

A batch that would be empty is still kept, header only, if it holds an active producer's last sequence, or is the last batch before the high watermark (Cleaner.java:357-362). KAFKA-20452, in 4.4.0, narrowed the second case to the high watermark. So a compacted log never quite reaches one record per key: D52, class D.

Physically the cleaner copies a group of neighbouring segments into one new .cleaned file named for the first segment's base, flushes it, keeps the old mtime, and swaps it in. The swap is two-phase: .cleaned becomes .swap, the old files become .deleted, and the .swap suffix is removed last (LocalLog.java:1026-1033, :1060). In the run, each pass merged into one growing file named for offset 0: 116, 177, 238, 299, 377, 444, then 522 bytes. On 4.4.0 a cleaned segment can still overflow after a compression change, because the KAFKA-20036 fix was reverted for the 4.4 line before release, citing a bug (D6, class B). That JIRA is Reopened with fix version 4.5.0. Trunk has a form of it; trunk was read, never built.

The two clocks

The first clock starts at the first cleaning that sees the tombstone, not when it was written. The horizon is the cleaner's current time plus delete.retention.ms, default 24 hours, and it is stored in the batch itself: attribute bit 6 is set, BaseTimestamp is overwritten, and record deltas are rewritten to match (MemoryRecords.java:171-179, DefaultRecordBatch.java:258). The second clock is whichever later pass finds the horizon past. There is no timer that removes it. The run used delete.retention.ms=20000 measured here:

Look at ab fd 03 in that record. It is the timestamp delta, now a negative zigzag varlong, so base plus delta is still the original write time. The 1793978771483 is 15:26:11.483, exactly 20,000 ms after the cleaner began.

A consumer that had cached k0 and came back after that pass would never learn of the delete. The docs state the consequence exactly: "it is possible for a consumer to miss delete markers if it lags by more than delete.retention.ms" (design.md:424). Offsets never change under compaction, so offsets can be missing, and a read for a missing one lands on the next batch with a higher base offset.

One log line reads as if it governs all this and doesn't. The cleaner's INFO line says "discarding tombstones prior to upper bound deletion horizon". The code says that value applies only to pre-v2 formats (Cleaner.java:146). At 15:25:51 it named 15:25:17, while the tombstone written at 15:25:38 was in fact given a horizon of 15:26:11 (D12, class C).

07What recovery does to damage

Recovery wants a contiguous prefix of valid batches and has no other goal. It does not try to save records; replication is meant to supply those. That one aim explains why damage injected by hand has such uneven results here, from one lost batch to a broker that will not start. Everything in this section marked as damage is simulated: bytes cut or bits flipped by hand with the broker dead, one sample each, on one broker with replication factor 1. No real power cut was run, and no loss figure here is a rate.

The path

Startup reads the clean-shutdown marker and deletes it immediately, so a crash during loading counts as unclean on the next boot (LogManager.java:630-634). Loading runs in passes: delete temp files and collect swaps, delete segments the swap replaced, rename swaps, then load segments and recover. A .cleaned file is always discarded, and any .swap at or above the smallest .cleaned offset is treated as an incomplete split and discarded too (LogLoader.java:129-195, :290-309). On a clean shutdown, recovery is skipped. Otherwise it visits only segments at or above the checkpointed recovery point, the first offset not flushed (LogLoader.java:457-459, LocalLog.java:102) from the code.

One segment's recovery resets all three indexes and rebuilds them while validating every batch. storage/…/log/LogSegment.java:489-492 and :514-522:

Every later unflushed segment goes, whole, without being read. A log must be contiguous. The design doc states why that is acceptable: a crashed replica is not assumed to have its data and must re-sync before rejoining the ISR "even if it lost unflushed data in its crash" (design.md:335). In code only the missing suffix is fetched, not the whole log (D19). Recovery on one broker only has to produce a clean prefix. Replication supplies the rest, if another in-sync copy holds it.

A plain SIGKILL costs nothing

One undamaged run first. SIGKILL at acks=all mid-write lost no acked record: highest acked offset 15588, log end offset 15589 after restart measured here. SIGKILL kills the process and leaves the page cache, so this says nothing about power loss. Recovery rescanned all 14 segments, even though the rolled ones had been flushed in the background, because the on-disk recovery point had no entry yet for this young partition: the 60 s checkpoint timer had not fired (D48, class D). Each progress line read 0 recovered, because numFlushed / numUnflushed at LogLoader.java:469 is integer division, which truncates to 0 until the end (D2, class A, cosmetic, still at trunk).

Reading the table

The tail rows simulate pages that never reached disk. A batch that claims more bytes than remain just ends iteration quietly, while a length below the minimum, all zeros say, throws CorruptRecordException (FileLogInputStream.java:66-82). Chopping 37 bytes cost the whole batch: offsets 15572-15588, acked, gone on this one replica. The zero tail lost nothing beyond the zeros. Which of those a real power cut would leave wasn't tested.

The payload rows are the CRC doing its job, and the loader doing its. One flipped bit at a mid-file batch took a young log from 24,413 offsets to 561 (D46, class D, intended by design). The recovery point was still 0 on that partition. One with an advanced checkpoint exposes only the region above it. After a true clean shutdown the same kind of bit went unnoticed: recovery was skipped, the broker logged no CRC or corruption line, and it served the batch. The Java consumer caught it: stored crc = 3573743101, computed crc = 517507933, and it stopped at offset 561 (D47, class D). Nothing on the broker's read path checks a CRC.

The base offset takes another road

The base offset is outside the CRC, so a flip there passes ensureValid. ensureOffsetInRange then throws overflow, and the loader assumes a legacy overflowed segment and tries to split it. The split's guard reads only the segment's last batch. storage/…/log/LocalLog.java:918: 

        require(segment.hasOverflow(), "Split operation is only permitted for segments with overflow, and the problem path is " + segment.log().file().getAbsoluteFile());

A mid-segment flip leaves that last batch healthy, the guard throws, nothing handles it, and the broker exits. It repeats on every start, and one partition takes down the whole broker. Undoing the bit by hand let the same files load with every record intact. A flip in the last batch satisfies the guard, so the split succeeds and the log end jumps to 72057594037936912, in a new file 00072057594037936895.log. Bit 24 is small enough to reach the InvalidOffsetException route, which empties the segment instead of failing (LogLoader.java:473-476). Bit 0 stays in range and passes reconstruction.

The register carries this as D1, class A: a robustness defect, shown only by injection. It is measured-vs-mock, and no natural trigger is established. The path is unchanged at trunk 09f2dc1320, which was read, not built, and no Jira names it. Operators have reported the same fatal message: a forum thread (2023, with a workaround resting on one poster) and a mail (2020, on an upgrade). Neither establishes a cause. By the code the route is not limited to an unclean start, since a corrupt index also calls recoverSegment (LogLoader.java:383-386); that wasn't run with a clean start. Nothing here was reported upstream.

08sendfile, tiering, and the 2011 paper

Everything so far follows from a sentence about formats. docs/design/design.md:92: the log holds message sets "written to disk in the same format used by the producer and consumer". That is what makes file-to-socket transfer possible, and it is why the broker works so hard not to touch a batch. On a plaintext connection the fetch path ends in three lines. clients/…/common/network/PlaintextTransportLayer.java:213-215: 

    public long transferFrom(FileChannel fileChannel, long position, long count) throws IOException {
        return fileChannel.transferTo(position, count, socketChannel);
    }

The shim saw it reach the kernel: 87 sendfile calls on the partition's .log moved 14,544,114 bytes, from a data-plane-kafk thread, which is a network thread by code reading. Reading everything back from a warm page cache caused zero physical reads: read_bytes in /proc/<pid>/io stayed 0 while rchar rose about 14.9 MB. After evicting those files with fsync plus posix_fadvise(DONTNEED), the same read caused 14,389,248 bytes of physical reads measured here. A single run on one disk, and it says nothing about speed. It does show where the data came from.

The price of this path is visible at the same line. The file-level write checks only that the file has not shrunk; nothing validates a CRC (FileRecords.java:280-291), which is the clean-start row of Figure 8. And TLS gives it up entirely: the broker reads the file into a 32 KiB direct buffer in user space and encrypts it (SslTransportLayer.java:1021-1026; D51, class D).

What survives from 2011

The 2011 NetDB paper by Kreps, Narkhede and Rao describes most of this directory.

Idea in § 3.1At 4.4.0
Segment files of about 1 GB, appended at the lastStill true; 1 GiB is still the default
"we rely on the underlying file system page cache"Stands, warm-cache-across-restart argument included

A message is exposed only after a flushGone. The high watermark governs visibility, and the default produce path does not fsync

"built-in replication" as future workPart 3

The 4 copies and 2 system calls that sendfile avoids appear in both the paper and the current design doc (design.md:103). The two ideas that went are not small. Visibility moved from a disk event to a line in the log. An offset moved from a place in a file to a count of records, which is why §04 needs indexes at all. The v2 producer fields of §02 came later still.

Tiering is the same files, further away

Tiered storage is a broker switch plus a topic switch, with two plugin interfaces, and Apache ships no production RemoteStorageManager: the doc says "Kafka server doesn't provide out-of-the-box implementation", and the only one in the tree is for tests (docs/operations/tiered-storage.md:39-60). Only rolled segments are uploaded, and only those below the last stable offset, subject to new copy-lag settings. An upload carries the files a local segment has: the log, both indexes, the optional transaction index, the producer snapshot and the leader-epoch data (RemoteLogManager.java:930-959, :1117-1119). With tiering on, a local segment is deletable only once uploaded or passed by the log start offset, an active segment past retention is rolled so it can be uploaded, and tiering excludes compaction, in code and in the docs (LogConfig.java:604). Tiering was read here, not run.

So the log is a directory, the batch is the unit, and the guarantees are lines. Part 2 takes this file to a socket and shows how one request travels through a broker.
