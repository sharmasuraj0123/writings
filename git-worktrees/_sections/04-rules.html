{{S}}The rules that keep worktrees apart

Git enforces two rules for you. A branch can be checked out in at most one worktree, and garbage collection treats every worktree's HEAD and index as live. Everything else in the shared column of Figure {{fig-split}} is unguarded, and that is where parallel agents step on each other.

Rule 1: one branch, one worktree

die_if_checked_out walks every worktree and dies if any has the branch (branch.c:847-863). Its callers are git worktree add (builtin/worktree.c:488), git switch and git checkout (builtin/checkout.c:1652, which --ignore-other-worktrees skips) and git rebase (builtin/rebase.c:1704). The check that matters is is_shared_symref, worktree.c:504-519 from the code: 

	if (wt->is_bare)
		return 0;

	if (wt->is_detached && !strcmp(symref, "HEAD")) {
		if (is_worktree_being_rebased(wt, target))
			return 1;
		if (is_worktree_being_bisected(wt, target))
			return 1;
	}

	refs = get_worktree_ref_store(wt);
	symref_target = refs_resolve_ref_unsafe(refs, symref, 0,
						NULL, &flags);
	if ((flags & REF_ISSYMREF) &&
	    symref_target && !strcmp(symref_target, target))
		return 1;

The detached case is the subtle part. During a rebase, HEAD is detached, yet the branch is still claimed: the rebase will move it when it finishes. A second worktree that checked it out in the meantime would have its branch moved underneath it. The reason for the rule is simple. A branch is a shared ref. Two indexes building commits on top of it would each advance it from a parent the other has already left behind. reconstruction

The lab hit the rule both ways measured here: 

$ git -C ../wt1 checkout agent-2
fatal: 'agent-2' is already used by worktree at '/home/coder/git-ref/lab/work/wt2'
$ git worktree add ../wtX agent-3
fatal: 'agent-3' is already used by worktree at '/home/coder/git-ref/lab/work/wt3'

--force skips the check (builtin/worktree.c:487). For agents, don't. Give each agent its own branch, or use --detach and create the branch only when the work is ready.

Rule 2: gc sees every worktree

An agent's staged but uncommitted file is only a blob in the shared object store, and nothing in refs/ points to it. If gc only looked at refs, a git gc started in any other worktree could delete it. It doesn't, because reachability walks every worktree. add_index_objects_to_pending reads each worktree's index file (revision.c:1829-1857), and other_head_refs adds each worktree's HEAD (reachable.c:314, 322) from the code.

The lab tested it measured here. I staged a new file in wt3, never committed it, and ran git gc --prune=now from the hub. Afterwards git cat-file -t 974785ff still answered blob. Two limits remain. A file that was never staged isn't in the object store at all, so gc has nothing to protect. And a worktree whose directory was deleted stops protecting anything once it is pruned (§06).

What is shared and unguarded

Everything else in the common directory has no owner. Figure {{fig-ledger}} lists what the lab showed for each.

Config is the one with a built-in fix. With extensions.worktreeConfig set to true, git config --worktree writes to .git/worktrees/<name>/config.worktree, and other worktrees don't read it. In the lab, wt1 then read vi and wt2 still read ed measured here. git sparse-checkout set turns this extension on by itself, so that one worktree's sparse settings don't leak into the others (Documentation/git-sparse-checkout.adoc:51-57) from the docs.
