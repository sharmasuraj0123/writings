{{S}}Remove, prune, lock, repair

A worktree exists in two places, its directory and its admin entry, and they can drift apart. Agents create and abandon worktrees all the time, so the cleanup rules matter. The main one: git worktree prune deletes stale entries immediately, while git gc waits three months.

remove

git worktree remove <path> deletes the directory and the admin entry together. First it runs git status --porcelain --ignore-submodules=none inside the worktree and refuses if that prints anything: "contains modified or untracked files, use --force to delete it" (builtin/worktree.c:1340-1356) from the code. Ignored files don't appear in --porcelain output. So an agent's node_modules/, target/ or .venv/ is deleted without a warning, while one stray untracked scratch file blocks removal. reconstruction from the status flags. A locked worktree needs remove -f -f (1407-1409).

prune, and the two clocks

If the directory is deleted by hand, as /tmp cleanup or a container restart would do, the admin entry stays behind and git worktree list marks it prunable. should_prune_worktree (worktree.c:929-1018) decides. Figure {{fig-prune}} shows its checks in order.

The lab ran it measured here. After rm -rf ../wt4, git worktree list showed /home/coder/git-ref/lab/work/wt4 b2213c1c3e [agent-4] prunable. A plain git worktree prune -n -v answered "Removing worktrees/wt4: gitdir file points to non-existent location", the same as with --expire now, even though wt4's index had been written seconds earlier. That fits the source: the subcommand's default expiry is TIME_MAX, so every timestamp passes check 5.

Two consequences for agents. First, an orphaned worktree keeps its branch claimed (Rule 1) and its index's blobs alive (Rule 2) until something prunes it, so a crashed agent's branch can't be checked out elsewhere for up to three months. Second, if the directory lives on a mount that comes and goes, run git worktree lock --reason "…" so that check 2 protects it.

move and repair

git worktree move moves a linked worktree and rewrites both links. If you moved things by hand, git worktree repair fixes the links from whichever side you run it on (Documentation/git-worktree.adoc, "prune" and "repair") from the docs. Relative links (§03) avoid most of this when the repository and its worktrees move together.
