01One checkout is single-occupancy

A git repository has two parts. The history (objects and refs) can be shared by any number of readers. The checkout can't: it has one HEAD saying which commit you are on, one index saying what the next commit will contain, and one set of files on disk. Two agents working in one checkout share all three, and each one undoes the other's work.

The failure is mundane. Agent A runs git switch fix-login while agent B is halfway through editing src/auth.ts on main. B's edits now sit on A's branch. Or A stages a file and B runs git commit -a, so A's half-finished change ships in B's commit. Neither agent made a mistake. They shared the three things git assumes only one writer touches.

Before 2015 there were two fixes. You could clone the repository again and pay for a second copy of the history. Or you could serialise the agents. git worktree is the third option. builtin/worktree.c first appears in commit df0b6cfbda (29 June 2015), and the first tag that contains it is v2.5.0 from the code. It splits a repository into a common directory that every checkout shares and a small per-worktree directory that holds each checkout's own HEAD, index and private refs. Figure 1 shows the difference.

This guide covers how that split works and what it costs. I read the mechanism from git's source at v2.55.0, timed it against five other ways to get a second checkout, and ran several worktrees at once to see where they collide. The short answer: for parallel agents, the real dangers are the things worktrees still share, not lock contention. §04 and §05 list them.

02What is shared and what is private

A linked worktree has two directories behind it: its own small admin directory under .git/worktrees/<name>/, and the main repository's .git, which git calls the common directory. Every path git resolves inside .git goes to one of the two, and a short hard-coded table decides which.

The table is common_list in path.c:98-124 from the code. Each row has three flags: whether the path is ignored by garbage reporting, whether it is a directory, and whether it belongs to the common directory (the struct is at path.c:89-96). Lines 98-123, verbatim: 

static struct common_dir common_list[] = {
	{ 0, 1, 1, "branches" },
	{ 0, 1, 1, "common" },
	{ 0, 1, 1, "hooks" },
	{ 0, 1, 1, "info" },
	{ 0, 0, 0, "info/sparse-checkout" },
	{ 1, 1, 1, "logs" },
	{ 1, 0, 0, "logs/HEAD" },
	{ 0, 1, 0, "logs/refs/bisect" },
	{ 0, 1, 0, "logs/refs/rewritten" },
	{ 0, 1, 0, "logs/refs/worktree" },
	{ 0, 1, 1, "lost-found" },
	{ 0, 1, 1, "objects" },
	{ 0, 1, 1, "refs" },
	{ 0, 1, 0, "refs/bisect" },
	{ 0, 1, 0, "refs/rewritten" },
	{ 0, 1, 0, "refs/worktree" },
	{ 0, 1, 1, "remotes" },
	{ 0, 1, 1, "worktrees" },
	{ 0, 1, 1, "rr-cache" },
	{ 0, 1, 1, "svn" },
	{ 0, 0, 1, "config" },
	{ 1, 0, 1, "gc.pid" },
	{ 0, 0, 1, "packed-refs" },
	{ 0, 0, 1, "shallow" },
	{ 0, 0, 0, NULL }

Read the third column. A path is shared when it, or the nearest listed directory above it, has a 1 there. objects, refs, config, hooks, packed-refs and rr-cache are shared. Inside the shared refs directory, three subtrees are carved back out as private: refs/bisect, refs/rewritten and refs/worktree. So is info/sparse-checkout, which lets each worktree have its own sparse patterns (§07). Anything not in the table at all, such as HEAD, index, ORIG_HEAD, MERGE_HEAD and the rebase-merge/ state directory, defaults to private. reconstruction of the lookup from the trie code that follows the table.

The ref store makes the same split by name. refs.c:881-886 from the code: 

int is_per_worktree_ref(const char *refname)
{
	return starts_with(refname, "refs/worktree/") ||
	       starts_with(refname, "refs/bisect/") ||
	       starts_with(refname, "refs/rewritten/");
}

Root refs count as per-worktree too. is_current_worktree_ref (refs.c:941-943) accepts any all-caps name such as HEAD, ORIG_HEAD or AUTO_MERGE. Everything else, notably every refs/heads/* branch, every tag, every remote-tracking ref and refs/stash, is shared. A worktree can still read another worktree's private refs by spelling them worktrees/<name>/refs/worktree/... or main-worktree/HEAD (parse_worktree_ref, 945-991) from the code.

I checked this on a hub with four worktrees measured here. A ref written in wt1 as refs/worktree/mark was invisible to for-each-ref in wt2. In wt2, git rev-parse worktrees/wt1/refs/worktree/mark resolved it to e9019fcafe. A branch written in wt1 showed up in wt2 immediately.

03What git worktree add writes

git worktree add ../wt1 agent-1 copies no history. It writes three small pointer files, creates a HEAD, and runs git reset --hard in the new directory. Everything happens in add_worktree, builtin/worktree.c:461-633 from the code.

The steps, in order

  1. Check the target. check_candidate_path refuses a path that is already a registered worktree, unless --force is given (479).
  2. Check the branch. If the argument names an existing branch, die_if_checked_out refuses it when another worktree already has it (484-489). §04 covers this rule.
  3. Name the admin directory. The name is the target path's basename, sanitised into a valid ref component. mkdir .git/worktrees/<name> runs in a loop: on EEXIST it appends a counter, so a second wt1 becomes wt11, then wt12 (494-515).
  4. Lock it. Before anything else, git writes worktrees/<name>/locked containing "initializing", so a concurrent prune cannot delete a half-built worktree (524-532). It also registers an atexit handler that removes the junk if the process dies.
  5. Write the links. write_worktree_linking_files writes the new checkout's .git file and the admin directory's gitdir file, each pointing at the other (542; worktree.c:1092-1120). Then it writes commondir containing ../.. (544-545).
  6. Create HEAD. In the new worktree's own ref store, HEAD becomes a symref to the branch, or a detached commit id with --detach (550-568).
  7. Copy per-worktree settings. If the current worktree uses sparse checkout, its patterns are copied. If extensions.worktreeConfig is on, its config.worktree is copied (570-583).
  8. Populate files. checkout_worktree runs git reset --hard --no-recurse-submodules with GIT_DIR and GIT_WORK_TREE set to the new paths (400-410, 592-594). This writes the index and the files.
  9. Unlock, then hook. The locked file is removed unless --lock was given, and post-checkout runs in the new directory. A failing hook does not delete the worktree (600-623).

The three pointer files

Here is what that left on disk in the lab hub measured here: 

$ cat wt1/.git
gitdir: /home/coder/git-ref/lab/work/hub/.git/worktrees/wt1
$ ls hub/.git/worktrees/wt1
COMMIT_EDITMSG  FETCH_HEAD  HEAD  ORIG_HEAD  commondir  gitdir  index  logs  refs
$ cat hub/.git/worktrees/wt1/commondir
../..
$ cat hub/.git/worktrees/wt1/gitdir
/home/coder/git-ref/lab/work/wt1/.git
$ cat hub/.git/worktrees/wt1/HEAD
ref: refs/heads/agent-1

Any git command run inside wt1 finds the repository in two hops. Setup reads the .git file and requires the gitdir: prefix (setup.c:999). That gives the admin directory, which holds HEAD and index. get_common_dir_noenv then reads commondir and, because ../.. is relative, resolves it against the admin directory, which lands on hub/.git (setup.c:323-350) from the code. The gitdir file points the other way. Git does not need it to run commands in the worktree. It needs it to know where the worktree is: worktree list, prune and the one-branch check all read it.

Paths are absolute by default. When worktree.useRelativePaths is true, or --relative-paths is passed, both links are written relative to each other. The first such write sets extensions.relativeWorktrees, which older gits refuse to open (worktree.c:1106-1116; Documentation/config/worktree.adoc) from the code. Relative links let you move the repository and its worktrees together, for example between a container and its host.

04The rules that keep worktrees apart

Git enforces two rules for you. A branch can be checked out in at most one worktree, and garbage collection treats every worktree's HEAD and index as live. Everything else in the shared column of Figure 2 is unguarded, and that is where parallel agents step on each other.

Rule 1: one branch, one worktree

die_if_checked_out walks every worktree and dies if any has the branch (branch.c:847-863). Its callers are git worktree add (builtin/worktree.c:488), git switch and git checkout (builtin/checkout.c:1652, which --ignore-other-worktrees skips) and git rebase (builtin/rebase.c:1704). The check that matters is is_shared_symref, worktree.c:504-519 from the code: 

	if (wt->is_bare)
		return 0;

	if (wt->is_detached && !strcmp(symref, "HEAD")) {
		if (is_worktree_being_rebased(wt, target))
			return 1;
		if (is_worktree_being_bisected(wt, target))
			return 1;
	}

	refs = get_worktree_ref_store(wt);
	symref_target = refs_resolve_ref_unsafe(refs, symref, 0,
						NULL, &flags);
	if ((flags & REF_ISSYMREF) &&
	    symref_target && !strcmp(symref_target, target))
		return 1;

The detached case is the subtle part. During a rebase, HEAD is detached, yet the branch is still claimed: the rebase will move it when it finishes. A second worktree that checked it out in the meantime would have its branch moved underneath it. The reason for the rule is simple. A branch is a shared ref. Two indexes building commits on top of it would each advance it from a parent the other has already left behind. reconstruction

The lab hit the rule both ways measured here: 

$ git -C ../wt1 checkout agent-2
fatal: 'agent-2' is already used by worktree at '/home/coder/git-ref/lab/work/wt2'
$ git worktree add ../wtX agent-3
fatal: 'agent-3' is already used by worktree at '/home/coder/git-ref/lab/work/wt3'

--force skips the check (builtin/worktree.c:487). For agents, don't. Give each agent its own branch, or use --detach and create the branch only when the work is ready.

Rule 2: gc sees every worktree

An agent's staged but uncommitted file is only a blob in the shared object store, and nothing in refs/ points to it. If gc only looked at refs, a git gc started in any other worktree could delete it. It doesn't, because reachability walks every worktree. add_index_objects_to_pending reads each worktree's index file (revision.c:1829-1857), and other_head_refs adds each worktree's HEAD (reachable.c:314, 322) from the code.

The lab tested it measured here. I staged a new file in wt3, never committed it, and ran git gc --prune=now from the hub. Afterwards git cat-file -t 974785ff still answered blob. Two limits remain. A file that was never staged isn't in the object store at all, so gc has nothing to protect. And a worktree whose directory was deleted stops protecting anything once it is pruned (§06).

What is shared and unguarded

Everything else in the common directory has no owner. Figure 4 lists what the lab showed for each.

Config is the one with a built-in fix. With extensions.worktreeConfig set to true, git config --worktree writes to .git/worktrees/<name>/config.worktree, and other worktrees don't read it. In the lab, wt1 then read vi and wt2 still read ed measured here. git sparse-checkout set turns this extension on by itself, so that one worktree's sparse settings don't leak into the others (Documentation/git-sparse-checkout.adoc:51-57) from the docs.

05Trying to make agents collide

I expected lock errors. Four worktrees committing as fast as they could, and six fetching the same remote at once, produced none. The one race that did fail, two worktrees moving the same branch, failed cleanly: exactly one winner, and an error message for the loser.

Probe P6: commits on separate branches

Each of four worktrees made 100 commits on its own branch. A fifth process ran git pack-refs --all 40 times in the hub at the same time. Every branch ended with exactly 100 new commits, and no stderr lines were written measured here. A commit takes two locks: index.lock in its own admin directory, which no other worktree touches, and the lock on its own branch ref. The only shared lock it can meet is packed-refs.lock. Git retries that one for core.packedRefsTimeout, 1000 ms by default, and retries a single ref lock for core.filesRefLockTimeout, 100 ms by default (Documentation/config/core.adoc:580-590) from the docs. At this rate, the retries absorbed every collision. The hub uses the files ref backend (git rev-parse --show-ref-format).

Probes P9 and P9b: fetches into the same remote-tracking refs

Here every worktree writes the same refs. A bare remote had 50 branches. Each round, I moved all 50 to a new commit, then fetched from three worktrees at once. That ran 10 rounds. The stress version used six fetchers, 20 rounds and a pack-refs in each round, for 120 fetches in total. Nothing failed and nothing was written to stderr measured here. My reading is that concurrent fetches write the same new value to each ref, so a fetch that loses a lock and retries finds the work already done. reconstruction; I did not trace the fetch transaction code.

Probe P10: two writers, one branch, different values

The real conflict is two agents moving one shared ref to different commits. The one-branch rule stops the usual way this happens, but not an agent that runs update-ref, push or branch -f on a branch it doesn't have checked out. I raced wt1 and wt2, each running update-ref refs/heads/shared-target <mine> <base>, 50 times. A won 34 rounds and B won 16. Both never succeeded. Every loser got the same message measured here: 

fatal: update_ref failed for ref 'refs/heads/shared-target': cannot lock ref
'refs/heads/shared-target': is at <oid> but expected <oid>

That is a compare-and-swap. The old value passed to update-ref is checked while the lock is held, so the loser fails instead of silently overwriting the winner. The catch is that commands that don't pass an old value, such as git branch -f, git update-ref with one argument and git push --force, have nothing to compare against. With those, the last writer wins. reconstruction; I only measured the guarded form.

So the dangers for parallel agents are mostly semantic, not mechanical. The ones that matter are a shared stash, shared config, shared branch names, and unguarded force updates. §09 turns that into a recipe.

06Remove, prune, lock, repair

A worktree exists in two places, its directory and its admin entry, and they can drift apart. Agents create and abandon worktrees all the time, so the cleanup rules matter. The main one: git worktree prune deletes stale entries immediately, while git gc waits three months.

remove

git worktree remove <path> deletes the directory and the admin entry together. First it runs git status --porcelain --ignore-submodules=none inside the worktree and refuses if that prints anything: "contains modified or untracked files, use --force to delete it" (builtin/worktree.c:1340-1356) from the code. Ignored files don't appear in --porcelain output. So an agent's node_modules/, target/ or .venv/ is deleted without a warning, while one stray untracked scratch file blocks removal. reconstruction from the status flags. A locked worktree needs remove -f -f (1407-1409).

prune, and the two clocks

If the directory is deleted by hand, as /tmp cleanup or a container restart would do, the admin entry stays behind and git worktree list marks it prunable. should_prune_worktree (worktree.c:929-1018) decides. Figure 5 shows its checks in order.

The lab ran it measured here. After rm -rf ../wt4, git worktree list showed /home/coder/git-ref/lab/work/wt4 b2213c1c3e [agent-4] prunable. A plain git worktree prune -n -v answered "Removing worktrees/wt4: gitdir file points to non-existent location", the same as with --expire now, even though wt4's index had been written seconds earlier. That fits the source: the subcommand's default expiry is TIME_MAX, so every timestamp passes check 5.

Two consequences for agents. First, an orphaned worktree keeps its branch claimed (Rule 1) and its index's blobs alive (Rule 2) until something prunes it, so a crashed agent's branch can't be checked out elsewhere for up to three months. Second, if the directory lives on a mount that comes and goes, run git worktree lock --reason "…" so that check 2 protects it.

move and repair

git worktree move moves a linked worktree and rewrites both links. If you moved things by hand, git worktree repair fixes the links from whichever side you run it on (Documentation/git-worktree.adoc, "prune" and "repair") from the docs. Relative links (§03) avoid most of this when the repository and its worktrees move together.

07Fewer files, fewer objects

A worktree avoids copying history, but it still checks out every file. Sparse checkout reduces the files an agent gets. Partial clone reduces the objects the repository fetches in the first place. They work at different layers and combine with worktrees.

Sparse checkout: fewer files per worktree

git sparse-checkout set <dir>… limits the working tree to the listed directories. Cone mode, the default, takes directory names and always includes the files at the top level (Documentation/git-sparse-checkout.adoc:25-26, 68) from the docs. Files outside the cone stay in the index with the skip-worktree bit set, and git does not expect them on disk (233-242). The patterns are stored in info/sparse-checkout, which §02 showed is private to each worktree. Running set turns on extensions.worktreeConfig so that the cone settings stay per-worktree as well (51-57).

For an agent assigned one area of a repository, this is the right default. In the lab, a worktree limited to Documentation/ held 1,503 of git's 4,765 tracked files, used 16.6 MB instead of 58.8 MB, and took 304 ms instead of 1,026 ms to create measured here. The order matters. Use worktree add --no-checkout, then sparse-checkout set, then checkout. Otherwise the full tree is written first and then deleted. And when the current worktree is sparse, add copies its patterns into the new one (builtin/worktree.c:574-575). 

git worktree add --no-checkout ../wt-docs -b agent/docs-7
git -C ../wt-docs sparse-checkout set --cone Documentation
git -C ../wt-docs checkout agent/docs-7

Partial clone: fewer objects in the store

git clone --filter=blob:none fetches every commit and tree but only the blobs the checkout needs. The pack it receives is marked as a promisor packfile by a sibling <name>.promisor file. Any object it refers to but doesn't contain is treated as promised by the remote and fetched on demand when needed (Documentation/technical/partial-clone.adoc:95-125) from the docs. A partial clone and its worktrees share one promisor store, so a blob one agent fetched is there for the rest.

In the lab, a blobless clone of git.git was 128.8 MB of .git instead of 312.1 MB, and took 33.0 s instead of 61.9 s measured here. Both were served over file:// by a local upload-pack on the same two cores. A real network would change the times but not which method wins. The cost moves to later: git log -p, blame or a checkout of an old commit fetches blobs as it goes, and each fetch needs the remote to be reachable.

Two kinds of clone that share objects

A clone from a local path hardlinks the object files rather than copying them. All three object files in the lab's local clone had a link count above one, and its .git took 712 KB of new disk space measured here. clone --shared goes further. It copies nothing and writes the source's object directory into objects/info/alternates. The manual calls this "a possibly dangerous operation": if the source repository later drops a commit that the clone still uses, maintenance in the source can delete it (Documentation/git-clone.adoc:87-93) from the docs. Both kinds of clone are separate repositories with their own refs, config and stash, so they avoid every red row in Figure 4. In exchange, the agents no longer see each other's branches without a fetch.

08What a second checkout costs

I timed six ways to give an agent its own checkout of git.git at v2.55.0, three runs each. Four of them finish in about a second and add about 60 MB, which is the size of the checked-out files. The two that transfer a pack take 30 to 60 times longer. A sparse worktree beats them all.

How the numbers were taken: lab/costs.sh ran each method three times on a 2-vCPU box, against the pinned clone in ~/git-ref/src, which has one 320 MiB pack measured here. "New disk" is du -sk of the new directory plus, for worktrees, the 0.5 MB admin entry. The exception is the hardlinked clone, where du run on the source and the clone together showed 712 KB of new .git. The individual runs, in ms: full clone 62,441 / 61,916 / 59,810; blobless 34,578 / 33,006 / 32,939; worktree 1,026 / 823 / 1,218; sparse worktree 304 / 291 / 517.

Disk use is the more important number. Ten agents on ten full clones of this repository would use about 3.7 GB, and ten worktrees about 0.6 GB. Ten sparse worktrees limited to Documentation/ would use about 0.17 GB. That is arithmetic from the medians, not a measured run of ten. On a box with 9 GB free, which is this one, that difference decides how many agents fit.

09A recipe for N agents

Everything above comes down to a short procedure. A supervisor owns the hub repository. Each agent gets a locked worktree on its own namespaced branch, with its own config, and never uses the stash. When it finishes, the branch is pushed and the worktree removed. Figure 7 shows the lifecycle.

Once per hub

git config extensions.worktreeConfig true      # lets step 2 stay private
git worktree prune                             # clear entries left by crashed agents
mkdir -p ../wt

Per agent

id=7; b="agent/$id/fix-login"; wt="../wt/agent-$id"
git fetch origin
git worktree add --lock --reason "agent $id" -b "$b" "$wt" origin/main
git -C "$wt" config --worktree user.name  "agent-$id"
git -C "$wt" config --worktree user.email "agent-$id@example.invalid"

# … the agent works in "$wt": edit, git add, git commit (never git stash) …

git -C "$wt" push --force-with-lease -u origin "$b"
git worktree unlock "$wt"
git worktree remove "$wt"          # refuses if anything is uncommitted

I ran this in the lab hub, with a local bare remote standing in for origin measured here. The agent's commit was authored by agent-7 <agent-7@example.invalid>, while the hub's user.name stayed lab. worktree list showed [agent/7/fix-login] locked. Removing it before unlocking failed with "cannot remove a locked working tree, lock reason: agent 7". After unlocking, an untracked tmp.txt still blocked removal. Once that was deleted, remove succeeded and the entry was gone.

The rules behind it

  • One branch per agent, under a namespace. Branches are shared (§02), so agent/<id>/… keeps one agent from reusing another's name, and Rule 1 (§04) keeps two agents off one branch.
  • No stash. refs/stash is shared (P2). An agent that runs stash pop can apply another agent's work. Commit WIP to the agent's branch and squash it later.
  • Identity and hooks per worktree. With extensions.worktreeConfig, config --worktree keeps author names and core.hooksPath out of other agents' worktrees (P4).
  • Guarded updates only. Use --force-with-lease, or update-ref <ref> <new> <old>, so a lost race fails (P10) instead of overwriting the winner.
  • Lock while running, prune on startup. A lock protects a worktree from prune. Startup prune clears what crashed agents left, which would otherwise hold their branches for three months (§06).
  • Dependencies are not shared. node_modules/, target/ and virtualenvs are ignored files inside each worktree. Each agent rebuilds them, and §08's numbers don't include them. A shared package cache (pnpm's store, CARGO_TARGET_DIR, uv's cache) is how you share that cost; git plays no part. reconstruction
  • Ports, databases and env files are not git's job. A worktree keeps agents' checkouts apart and nothing more.

10What this guide skipped

This guide treated the common directory as a box: objects go in, refs point into it, and gc keeps what is reachable. Every one of those boxes has its own machinery in git's source, and most of the costs measured above come from inside them. These are the topics for a follow-up that takes git itself apart. That follow-up is now Git, taken apart, a three-part collection read from the same pinned source.

Objects and hashing

STORAGE

Blobs, trees, commits and tags as hashed bytes; loose objects; the SHA-1 to SHA-256 transition, from its design doc in technical/.

Packfiles

STORAGE

Delta chains and how pack-objects chooses bases; .idx, .rev, bitmaps (pack-bitmap.c), multi-pack index (midx.c). The 320 MiB in §08 is all here.

The index

STATE

The format and its extensions (gitformat-index.adoc, read-cache.c, 4,051 lines): cache-tree, the untracked cache, fsmonitor, and the sparse index that §07's cone mode enables (sparse-index.c).

Refs and their backends

STATE

Loose refs, packed-refs and ref transactions (the compare-and-swap of P10), then reftable/, the binary backend that replaces both.

Transport

NETWORK

Protocol v2 (gitprotocol-v2.adoc), have/want negotiation, server-side filters behind partial clone, and bundle URIs (bundle-uri.c).

Merging

ALGORITHMS

merge-ort.c (5,598 lines): rename detection, the three-way tree merge, conflict representation in the index, and rerere's shared rr-cache from §02.

Maintenance

UPKEEP

git maintenance, the commit-graph (commit-graph.c), geometric repacking, cruft packs, and how gc --auto decides to run, which is what can delete a --shared clone's borrowed objects.

Git at scale

PERFORMANCE

scalar.c: the opinionated bundle of partial clone, sparse checkout, fsmonitor and background maintenance that large monorepos use.

Worktree edge cases

THIS TOPIC, DEEPER

Submodules inside worktrees (why move refuses them), bare hubs, and how repair rebuilds broken links.

The first four are the core of "how git stores things". Transport and merging are how it moves and combines them. Maintenance and scale are what keep a repository with many agents fast. reconstruction: this is my reading of which parts of the tree matter most, not a structure git documents.
