Who chooses

On the web, compression belongs to the content. RFC 9110 §8.4 calls the codings in Content-Encoding "a characteristic of the representation"; RFC 9112 §6.1 says "Transfer-Encoding is a property of the message, not of the representation." from the spec HTTP/2 forbids Transfer-Encoding (RFC 9113 §8.2.2), so web compression is Content-Encoding, negotiated by Accept-Encoding with optional q-values (RFC 9110 §12.5.3). from the spec

A dictionary sent once

Compression Dictionary Transport, RFC 9842 (September 2025, Standards Track), lets one response serve as the dictionary for later ones. from the spec The response opts in with Use-As-Dictionary, whose match pattern names the URLs it covers. A later matching request sends Available-Dictionary, the SHA-256 of the stored bytes, and Dictionary-ID if the server set an id. The server may answer dcb, a 36-byte header (ff 44 43 42 and the hash) before a Shared Brotli stream (RFC 9841) with at most a 16 MB window, or dcz, a 40-byte zstd skippable frame holding the hash before a zstd frame. from the spec Clients must not offer dcb or dcz without a matching dictionary, and cacheable responses must vary on accept-encoding, available-dictionary. from the spec zstd, unlike Brotli, reaches the dictionary only within its window, so dcz decoders must accept a window of 8 MB or 1.25 times the dictionary, whichever is greater, up to 128 MB. from the spec Matching is same-origin only (RFC 9842 §9.3.1; When compression is the attack). from the spec
