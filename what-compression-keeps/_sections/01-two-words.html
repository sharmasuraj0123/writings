{{S}}Fewer bits, or fewer things

Compression and compaction make two different promises. Compression keeps all the information and spends fewer bits on it. Compaction keeps only what a reader can still observe, the present state, and rewrites it densely. Lossless compression can be undone. Compaction, as a rule, cannot.

In lossless compression a model predicts each symbol, a coder spends bits on the model's surprise, and the decoder runs the same model to get every byte back (Information is surprise, A model and a coder). Lossy compression keeps what a perceptual model says a person will notice, and its decoder returns a close copy (Throwing away what nobody sees). Neither drops anything for being old. reconstruction

Compaction does. The Raft paper describes log cleaning and log-structured merge (LSM) trees this way: "They first select a region of data that has accumulated many deleted and overwritten objects, then they rewrite the live objects from that region more compactly and free the region." (Ongaro and Ousterhout, "In Search of an Understandable Consensus Algorithm", extended version of the USENIX ATC 2014 paper, §7) from the paper What is freed is what no reader can observe: superseded versions, expired tombstones (records that mark a key deleted), dead tuples, unreachable objects (Compaction: keeping only the present). None of it comes back. Some compactions only move live data and drop nothing; Compression and compaction, side by side sorts them. reconstruction KurrentDB's docs say so of its scavenge: "Once a scavenge has run, you cannot recover any deleted events except from a backup" (v26.0, "Scavenging"). from the docs

The words have traded places before. Visvalingam's 1976 paper "Indexing with coded deltas—a data compaction technique" (Software: Practice and Experience 6(3)) describes coded deltas "for compacting the 1971 U.K. census data": compression, in today's words. The UNIX compact utility was an adaptive Huffman coder (Lelewer and Hirschberg, "Data Compression", ACM Computing Surveys 19(3), 1987). from the paper The other way round, the log-structured file system's segment cleaner "regenerates empty segments by compressing the live data from heavily fragmented segments" (Rosenblum and Ousterhout, "The Design and Implementation of a Log-Structured File System", SOSP 1991). from the paper This post keeps the later, cleaner split, and Figure {{fig-two-pipelines}} draws it. reconstruction

One log, three treatments

_compute.py generates a seeded update log: 200,000 JSON Lines records over 5,000 keys. The first 5,000 create every key; each later update picks a key by a Zipf law (s = 0.9) and changes one data field; 250 keys are deleted by a tombstone. It is 39,366,976 bytes, a mean of 196.8 per record. Figure {{fig-three-treatments}} shows it compressed with zstd at levels 3 and 19 (libzstd 1.5.7, via Python 3.14's compression.zstd), compacted to the last value per key, and both. measured here

zstd level 19 keeps the whole log in 2,780,146 bytes (14.16×), and the round trip is byte-identical. Compaction alone reaches 933,174 bytes (42.19×) by keeping 4,750 records: 5,000 keys minus the 250 deleted. The raw log, its zstd round trip and the compacted file replay to the same final state; only the first two replay the history. Compacting and then compressing at level 19 leaves 86,914 bytes, 31.99 times smaller than level 19 alone (2,780,146 ÷ 86,914). measured here The factor tracks versions per key, 40 on average here (200,000 records over 5,000 keys); a log of mostly distinct keys gains little from compaction. The other order costs a full decode, because a zstd frame is one opaque stream. reconstruction

The answer, up front

Each item is my judgement. reconstruction

  1. Compress when every byte or frame must survive and you want it smaller: files at rest, bytes on the wire. Go lossy only for media, where a perceptual model may choose what is lost. Per-format recipes are in What Each File Wants.
  2. Compact when old versions have no reader: LSM stores, Kafka changelog topics, PostgreSQL and SQLite tables (VACUUM), garbage-collected heaps. If anyone may ask for the past, keep it elsewhere first.
  3. When you do both, compact first and compress what is left, as in Figure {{fig-three-treatments}}. Some tools do both in one command: git's manual (Documentation/git-gc.adoc, DESCRIPTION) lists "compressing file revisions" and "removing unreachable objects" among its tasks. from the docs
  4. An agent's context is compacted when it fills, but its past may still have a reader: keep the transcript beside the summary (Compacting a conversation).
