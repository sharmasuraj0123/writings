{{S}}When compression is the attack

Compression makes output length depend on content, so a length can leak a secret. It lets a few hundred bytes stand for a gigabyte, so a small file can exhaust a machine. And in 2024 a compression library's release tarballs carried a backdoor.

A length that leaks

CRIME (CVE-2012-4929; Duong and Rizzo, ekoparty, September 2012) recovered cookies from TLS-level compression by injecting chosen plaintext and measuring the encrypted size. from the docs BREACH (CVE-2013-3587; Black Hat USA 2013) did the same to HTTP bodies: any compressed page that reflects user input beside a secret is exposed, for "just a few thousand requests". from the docs

HEIST (Vanhoef and Van Goethem, Black Hat USA 2016) moves the attacker into the browser: a script times whether a response fits in TCP's initial congestion window to learn "the exact size of any cross-origin response". from the paper TLS 1.3 offers only the null compression method (RFC 8446 §4.1.2), from the spec which ends CRIME but not the other two. reconstruction

The BREACH authors rank seven mitigations, from disabling HTTP compression through masking secrets to rate limiting, and admit: "Unfortunately, we are unaware of a clean, effective, practical solution to the problem." from the docs Masking works here: sent as a fresh 16-byte mask plus the secret XORed with it, the token keeps DEFLATE between 759 and 762 bytes at every k tried. measured here Dictionary transport inherits the risk. RFC 9842 §9.3.3 warns of a timing attack when an attacker controls part of the dictionary, or reads it and controls part of the content; §9.3.2 has browsers use a dictionary only when "both the dictionary and the compressed response are fully readable by the client" (Compression on the wire). from the spec

Small in, enormous out

David Fifield's "A better zip bomb" (USENIX WOOT 2019) notes that DEFLATE "cannot achieve a compression ratio greater than 1032", which is why 42.zip nests six layers. Overlapping files inside one zip container instead, his bombs turn 42 kB into 5.5 GB and 10 MB into 281 TB. from the paper

The harness streamed 1 GiB of zeros through five codecs, then asked each Python decoder for at most 64 MiB in one call. measured here

A backdoor in the release tarball

On 29 March 2024 Andres Freund reported on oss-security that "The upstream xz repository and the xz tarballs have been backdoored". His ssh login timings read "before: real 0m0.299s" and "after: … real 0m0.807s". from the docs NVD scores CVE-2024-3094 at CVSS 3.1 10.0. Only the XZ Utils 5.6.0 and 5.6.1 release tarballs carried it. from the docs

The trigger, a modified m4/build-to-host.m4, existed only in the tarballs. At configure time it extracted a payload from two test files in git, among them tests/files/bad-3-corrupt_lzma2.xz, and injected it only into x86-64 Linux builds with gcc and GNU ld inside Debian or RPM packaging. It replaced liblzma's IFUNC resolvers and redirected sshd's RSA_public_decrypt. OpenSSH itself does not use liblzma; distributions' systemd-notification patches pull it in through libsystemd. from the docs 5.6.2 (29 May 2024) removed it; the git history was not rebased. from the docs The weak point was the release, not the codec: only the tarball armed what git already held. reconstruction Figure {{fig-hazard-ledger}} lines the five incidents up.
