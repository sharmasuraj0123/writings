{{S}}Compaction: keeping only the present

A system that writes out of place leaves old versions behind. Compaction rewrites what is still live and lets the rest go. Each kind keeps an invariant, drops what no reader can see, waits for a trigger, and pays in writes, spare disk or a pause.

What each one promises to keep

The sources state the invariant themselves. SQLite's VACUUM INTO output "will contain the same logical content as the original database, fully vacuumed" (lang_vacuum.html, §2.1). Delta Lake: "a read before and after an OPTIMIZE has the same results" (Delta 4.4.1). Kafka: "The offset for a message never changes" (4.3 docs, Design). Cassandra keeps "the most up-to-date version (by timestamp)" of each column ("Compaction overview"). from the docs

The promises cover logical content, not physical identity. SQLite's VACUUM "may change the ROWIDs" of tables without an explicit INTEGER PRIMARY KEY (§3). from the docs In one test here on 3.46.1 it changed none of 2,000. measured here A copying collector moves every survivor; in V8's scavenger each copied object "leaves a forwarding-address" ("Trash talk", 3 January 2019). from the docs

LSM trees

A log-structured merge tree buffers writes in memory and merges them down through ever larger sorted files (Figure {{fig-lsm}}). O'Neil et al. (Acta Informatica, 1996) called this the "rolling merge"; their preprint never says compaction. Its "delete node entry" migrates down and "annihilates the associated entry when it is encountered" (§2.3), the ancestor of the tombstone. from the paper Bigtable (OSDI 2006, §5.4) named the steps: a minor compaction flushes the memtable (the sorted in-memory buffer) to an SSTable (a sorted, immutable file), a merging compaction bounds how many SSTables a read must merge, and a major compaction "produces an SSTable that contains no deletion information or deleted data". from the paper

RocksDB defines the costs. Write amplification is "the ratio of bytes written to storage versus bytes written to the database"; space amplification is bytes on disk over data size. Leveled compaction keeps space low and rewrites more; universal compaction writes less but "may temporarily increase size amplification by a factor of two" (Tuning Guide). from the docs The RUM conjecture generalises: "An access method that can set an upper bound for two out of the read, update, and memory overheads, also sets a lower bound for the third overhead" (Athanassoulis et al., EDBT 2016, §3). from the paper

RocksDB compresses as it compacts. Since 11.5.0 (16 June 2026) the default block codec is LZ4 where compiled in; v11.8.1, the latest tagged release, ships it. The wiki recommends ZSTD for the bottommost level, which "contains majority of the data". With dictionary compression on, a dictionary is trained per SST file during compaction. from the docs The codecs themselves are in The codecs that matter in 2026.

Cassandra 5.0's docs recommend the Unified Compaction Strategy "for most workloads" over the size-tiered, leveled and time-window strategies. 5.0.9 (7 August 2026) is the latest GA release; 6.0 exists only as alphas. A tombstone may be purged only after gc_grace_seconds (default 864000, ten days), by a compaction that includes every SSTable with older data for its partition. Purge sooner, and a replica that missed the delete can spread the row back as a "zombie". from the docs

Kafka: at least the last value

A topic with cleanup.policy=compact keeps "at least the last known value for each message key" in a partition (4.3 docs, "Log Compaction"). At least, not only. The cleaner recopies closed segments, never the active one, once the dirty share reaches min.cleanable.dirty.ratio (default 0.5): "at most 50% of the log could be duplicates". A tombstone, a key with a null payload, is itself removed after delete.retention.ms (default one day), so a consumer lagging longer can miss the delete. Batch compression is a separate setting (why batches compress). from the docs Figure {{fig-kafka-compact}} shows one cleaning.

_compute.py runs a cleaner modelled on Kafka's (a model, not Kafka) over the 39,366,976-byte update log from the opening section, with 1 MiB segments and dirty ratio 0.5. It cleaned 37 times and rewrote 35,691,994 bytes: write amplification (39,366,976 + 35,691,994) ÷ 39,366,976 = 1.91. The log peaked at 2,024,373 bytes (2.17× the 933,174 live bytes) and ended at 1,501,846 (1.61×). measured here

Databases: deleting is not freeing

PostgreSQL keeps old row versions for multiversion concurrency control (MVCC) (Where the JSON Lives). Plain VACUUM marks their space reusable without blocking reads or writes. VACUUM FULL "actively compacts tables by writing a complete new version of the table file with no dead space", under an ACCESS EXCLUSIVE lock, and autovacuum "will never issue VACUUM FULL" (PostgreSQL 18 docs, §24.1.2 and "VACUUM"). PostgreSQL 19's REPACK, in beta, takes that lock only to swap files when run with CONCURRENTLY. from the docs

SQLite's VACUUM "rebuilds the database file, repacking it into a minimal amount of disk space", and may need twice the file size free. With auto_vacuum off, the default, freed pages go on a freelist; auto_vacuum=FULL truncates it at each commit but "can actually make fragmentation worse". from the docs In Figure {{fig-maintenance}}, deleting 90% of 100,000 generated JSON documents leaves the 47,034,368-byte file exactly that size, with 10,332 of its 11,483 pages free. VACUUM brings it to 4,714,496 bytes and writes 14,154,268 to get there, three times what it leaves (14,154,268 ÷ 4,714,496 = 3.00). After a scattered delete, incremental_vacuum ended 12% larger than VACUUM (5,300,224 against 4,722,688 bytes) and left 78 deleted documents readable in unused gaps of live pages; VACUUM left none. measured here This build compiles in SECURE_DELETE, so the remnant count does not generalise. reconstruction

MongoDB's compact "Attempts to release unneeded disk space to the operating system", and 8.0 added a background autoCompact. etcd splits the job: compaction drops superseded key versions, and a separate defragmentation, which blocks the member, returns the space (v3.7 docs, "Maintenance"). from the docs

Iceberg's rewrite_data_files bin-packs small files towards 512 MB, and each compaction is a new snapshot: old files stay for time travel until expire_snapshots (Iceberg 1.12.0 docs). Its default Parquet codec is zstd. from the docs Because these rewrites, and Delta's OPTIMIZE, write new files, compaction is when a changed codec reaches old data. reconstruction

Memory, disks, git and logs of record

V8's mark–sweep–compact collector compacts only some highly fragmented pages: "You can think of compaction sort of like hard-disk defragmentation on an old PC." G1 compacts as it evacuates live objects (Java 26 tuning guide); ZGC relocates concurrently and has been generational only since JDK 24 (JEP 490). Linux compacts physical memory for huge pages, in per-node kcompactd threads since 4.6, and its docs warn of latency spikes. from the docs These move live data and drop nothing live. reconstruction

The log-structured file system (Rosenblum and Ousterhout, SOSP 1991, §3.4) prices cleaning as write cost: disk time per byte of new data. from the paper Reading N segments at utilisation u, writing back N·u of live data and filling N·(1 − u) with new data moves 2N segments for N·(1 − u) of new data: 2 ÷ (1 − u), or 10 at 80% live. reconstruction F2FS cleans the same way on flash. from the docs

git gc does both jobs (its manual is quoted in the opening section); a pack holds objects "individually compressed, with delta compression applied" (git-repack.adoc). from the docs On a synthetic 300-commit repository (24 files; a deleted five-commit branch adds five 256 KiB files), git 2.55.0's git gc --prune=now packed 1,646 of 1,661 loose objects, 1,010 as deltas, dropped the 15 unreachable ones, and cut .git/objects from 7,561,216 bytes on disk to 253,952 (1,931,211 to 241,355 apparent bytes). measured here Each loose object occupies whole 4 KiB filesystem blocks, so on-disk bytes overstate the drop. reconstruction By default, unreachable objects get two weeks' grace (gc.pruneExpire). from the docs

Raft compacts by snapshot: "the entire current system state is written to a snapshot on stable storage, then the entire log up to that point is discarded" (extended version, 2014, §7). from the paper Event sourcing as Martin Fowler defines it (2005) keeps the events "for the same lifetime as the application state itself"; its snapshots are a cache. from the docs Yjs, a CRDT, discards a deleted item's content but keeps the item as a tombstone, because it fixes the order; doc.gc = false keeps the content too. from the docs An agent's context is the newest sense: Compacting a conversation.
