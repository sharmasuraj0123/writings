{{S}}The tree configures the fleet

//infra/config is a compiler. 125 Starlark files go in, 3,555 generated files come out, and the LUCI services read those files back out of git. Nothing is deployed. A change to the fleet is a CL.

The directory's own README says what it is for: the configuration rooted at main.star "defines the LUCI services configuration for the chromium project on the production instance of LUCI", written in Starlark, executed by lucicfg into the raw cfg files under generated/, with "a presubmit check" that "enforces that the generated files are kept in sync" from the docs [src/infra/config/README.md:15-30]. At f288fed6 the directory is itself a lucicfg package. PACKAGE.star declares @chromium-project with a minimum lucicfg of 1.44.1, two entry points — main.star for production and dev.star for the dev instance — and two dependencies: a local @chromium-targets rooted at infra/config/targets, and @chromium-luci, fetched from the separate infra/chromium repository and pinned at revision 3c067cfcf061330718cee8a4c74d9cd7232595c6. PACKAGE.lock records the lucicfg that actually ran: 1.46.7 from the tree [src/infra/config/PACKAGE.star:7-43; PACKAGE.lock:2-9].

That pin is recent history. On 2025-07-22, commit b711da6e4f deleted the library code under infra/config/lib in chromium/src — builders.star, ci.star, try.star, builder_config.star, gn_args.star, targets.star, bootstrap.star, branches.star, notifiers.star, orchestrator.star — and replaced every call site with an import of the form load("@chromium-luci//ci.star", "ci"), so that chromium and the internal chrome project execute one library instead of two copies from the tree. Ninety-eight of the 125 Starlark files now name @chromium-luci.

What survived in lib/ is constants, not logic. CI defaults: executable recipe:chromium, a three-hour execution timeout, pool luci.chromium.ci, shadow pool luci.chromium.try [lib/ci_constants.star:5-14]. Try defaults: recipe:chromium_trybot, four hours, luci.chromium.try [lib/try_constants.star:5-10]. The Siso remote-execution tiers — 250 jobs by default, 80 and 500 for low- and high-parallelism CI, 150 for low CQ, and -1 for high CQ, which the comment says is "Calculated based on the number of CPUs inside Siso" [lib/siso.star:5-21]. The default iOS toolchain, Xcode 27.0 RC 27a266a [lib/xcode.star:7-14]. Twelve gardener rotations [lib/gardener_rotations.star:10-23]. And a file of grandfathered exemptions carrying a banner warning that the lists "should only decrease" [lib/builder_exemptions.star:5-11].

main.star is the contract between the Starlark and the tree. It checks the lucicfg version, enables the crbug.com/1182002 Scheduler experiment, and then declares, by hand, every path lucicfg is allowed to own. This is src/infra/config/main.star:36-68, condensed with elision markers: 

lucicfg.config(
    config_dir = "generated",
    tracked_files = [
        "builders/*/*/*",
        "builders/*/*/*/*",
        "builders/alerting-builders.txt",
        "builders/gn_args_locations.json",
        "builder-owners/*.txt",
        "cq-builders.md",

        "luci/testhaus.cfg",

        "project.pyl",
        "testing/*.pyl",
    ],
    fail_on_warnings = True,
)

Two things fall out of that block. fail_on_warnings = True means, in lucicfg's own words, "treat validation warnings as errors" — a warning is a build break, not a note from the docs. And tracked_files makes the generated tree closed in both directions: "only files that are in this set will be actually written to the disk (and all other files are discarded)", and a tracked file that disappears from the output "must be deleted from the disk as well" from the docs. Three configs are explicitly not generated — testhaus.cfg, luci-analysis.cfg and luci-bisection.cfg are hand-written at the top of the directory and copied verbatim into generated/luci/ by lucicfg.emit [main.star:70-86]. Everything else comes out of the luci.project call quoted in §01, which binds the six appspot hosts [main.star:88-96]. Figure {{fig-lucicfg}} counts both ends of that compile and the poll that carries the result to the services.

The output is large and mechanical, and each of the thirteen generated luci/*.cfg files opens with the same two-line banner: "Auto-generated by lucicfg. / Do not modify manually." — the eight files in luci/ that do not are the hand-copied ones and the two email templates. cr-buildbucket.cfg alone is 139,286 lines and 5,544,282 bytes — 5.29 MiB, which ls -lh rounds to 5.3M, and 5.54 MB decimal — holding 18 buckets and 1,211 builders. The figure’s right-hand column carries the same reading for the other five large ones from the tree.

Getting that tree to the services involves no deploy step. LUCI Config (config.luci.app) runs an import cron whose importAllConfigsInterval is ten minutes; it enqueues one task per config set at a deterministic offset inside that window, asks Gitiles for the latest commit touching the configured path, and commits the new revision only if every interested service's ValidateConfigs comes back without an ERROR-severity message [luci-go config_service/internal/importer/importer.go:62-74,323-337,520-543]. On 2026-09-22 the projects/chromium config set was imported from refs/heads/main, path infra/config/generated/luci, at revision f7de74e13efc (08:25:50Z), with lastImportAttempt reading Up-to-date — a reading off the live service, dated per §01 rather than badged. Consumers then poll on their own clock — Buildbucket, Scheduler and CV each about once a minute — so a landed infra/config CL is live in roughly one to eleven minutes, dominated by the import window reconstruction: that range is derived from the constants, not measured against a real change.

The validation that gates the import also runs long before it. depot_tools' CheckLucicfgGenOutput builds a presubmit command that runs lucicfg validate <entry_script>, which regenerates the configs, diffs them against what is checked in, and ships each config set to the same validation RPC the importer uses [depot_tools/presubmit_canned_checks.py:3744-3778]; infra/config/PRESUBMIT.py calls it twice, once for main.star and once for dev.star [src/infra/config/PRESUBMIT.py:74-84]. Four dedicated trybots guard the per-builder files that lucicfg writes under builders/ — branch-config-verifier, builder-config-verifier, targets-config-verifier and gn-args-verifier [src/infra/config/subprojects/chromium/try/presubmit.star:73,116,128,161]. A misconfigured fleet is therefore a red trybot, reviewed and reverted like any other bad CL. What that costs, and what one line of Starlark actually expands into, is the next section.
