{{S}}The waterfall and its humans

Pre-submit is a funnel. Post-submit is a fan-out, one regular expression, twelve rotations of people and a bisection service. Look at the regular expression: it names seven steps that close the Chromium tree, and the first cannot fire.

One scheduler job does the fan-out. chromium-gitiles-trigger polls refs/heads/main on chromium/src and names 386 builders it starts directly, counted from the triggers: lines of one block at infra/config/generated/luci/luci-scheduler.cfg:6647–7040 from the tree. The ci bucket holds 641, so the other 255 never hear from the scheduler at all. Their parents trigger them from inside the recipe: chromium_tests/api.py's trigger_child_builds emits a scheduler.GitilesTrigger for the same repo, ref and revision, carrying parent_got_* and deps_revision_overrides so the tester pins the exact inputs its builder used. That is the builder/tester split of §07 seen from the scheduler's side: the scheduler knows about compilers, compilers know about their testers.

133 of those builders are tree closers, against 252 notifiers in the generated luci-notify.cfg (counted at f288fed6). What all 133 watch is a single constant. The source is infra/config/notifiers.star:85–125, condensed here to the regexp and the two closers declared against it: 

TREE_CLOSING_STEPS_REGEXP = "\\b({})\\b".format("|".join([
    "bot_update",
    "compile",
    "gclient runhooks",
    "generate_build_files",
    "runhooks",
    "update",
    "\\w*nocompile_test",
]))

# … tree_closer() wraps luci.tree_closer in notifiers.tree_closer_branch(),
# so on a release branch the name resolves to a notifier with no recipients.

tree_closer(
    name = "chromium-tree-closer",
    tree_status_host = "chromium-status.appspot.com",
    failed_step_regexp = TREE_CLOSING_STEPS_REGEXP,
)

tree_closer(
    name = "close-on-any-step-failure",
    tree_status_host = "chromium-status.appspot.com",
)

Read the first entry against how LUCI Notify behaves. Notify will not touch the tree unless a build ends SUCCESS or FAILURE — "infra failures, for example, shouldn't cause us to close or re-open the tree" (luci-go luci_notify/notify/notify.go:392–404) from the tree. And bot_update runs with kwargs.setdefault("infra_step", True) (depot_tools bot_update/api.py:310), so a failed checkout ends the build purple, as INFRA_FAILURE, not red. The step named first in the regexp is the one step in the list that structurally cannot close the tree. What closes it on a broken checkout is the next step: hooks are excluded from the sync bot_update runs (--nohooks --noprehooks, depot_tools bot_update/resources/bot_update.py:459–460) and run as gclient runhooks, which gclient/api.py:302–306 runs with infra_step=False. I found no recipe path in tools/build that runs bot_update that way, which would make the entry live again; absent one it reads as a Buildbot-era holdover, like update, the name of no step a modern Chromium build emits reconstruction.

Closure is asymmetric, and the asymmetry is policy encoded in a state machine. luci-go's luci_notify/notify/tree_status.go leaves a manually closed tree unchanged forever, while an automatically closed one reopens when all tree-closer builds pass, or when every still-failing build started before the last automated revert. throttled and maintenance are read as closed from the tree. The host every closer names is a facade: chromium-status.appspot.com's status.py:39–40 sets TREE_STATUS_SERVICE to luci-tree-status.appspot.com/prpc/luci.tree_status.v1.TreeStatus/ and proxies GetStatus/ListStatus to it. Queried both ways on 2026-09-22 they returned one record: createTime 2026-09-20T12:19:05.626463Z, "Tree is open (Automatic: All tree-closer builders are passing)".

Twelve rotations and a bisector

The people are organised as twelve gardener rotations, declared in infra/config/lib/gardener_rotations.star:10–23. Eleven have a generated builder list under generated/sheriff-rotations/, 436 lines in all, led by chromium with 141 builders, chromium.gpu with 94, dawn 56, chromium.clang 46 and android 43 from the tree. The directory keeps the old name. Rotations were renamed from "sheriffs" to "gardeners" on 17 May 2023, and docs/sheriff.md is now a redirect stub. docs/gardener.md:3–35 gives the job in priority order: "The tree is open, because when the tree is closed nobody can make progress", then no new test failures, then repair the old ones. Gardeners may revert freely, using Owners-Override to skip OWNERS and the Rubber Stamper bot's Bot-Commit+1 to skip human review on a clean revert. A shift is eight hours: "if >8 hours have passed, that person is no longer gardener" (:62).

Beside them runs LUCI Bisection, "formerly GoFindit … the rewrite in Golang of the Python2 version of Findit". Its authority, hand-written and only copied by lucicfg, is infra/config/luci-bisection.cfg:4–24: 

compile_analysis_config {
  build_config: {
    builder: {
      project: "chromium",
      bucket: "findit",
      builder: "gofindit-culprit-verification"
    }
  }
  culprit_verification_enabled: true
  nthsection_enabled: true
  gerrit_config {
    actions_enabled: true
    create_revert_settings: {
      enabled: true
      daily_limit: 10
    }
    submit_revert_settings: {
      enabled: true
      daily_limit: 4
    }
    max_revertible_culprit_age: 21600

Ten reverts created a day; four submitted, and only when the culprit is younger than 21,600 seconds — six hours. The age is a submit-time gate, not a create-time one: MaxRevertibleCulpritAge is read in commitrevert.go:39–52, which also refuses to auto-commit any revert for a test failure. The test half points at findit/test-single-revision and creates reverts it never submits. The refusals, boxed at the right of Figure {{fig-tree-closure}}, live in code, not config: luci-go's bisection/culpritaction/revertculprit/createrevert.go declines a culprit whose author is an autoroller, whose description matches (NOAUTOREVERT)(\s)*=(\s)*true, which has merged changes depending on it, which is "a sub-commit inside a rolled dependency", or which broke a builder "not watched by gardeners, therefore less important" from the tree. A 2026 layer sits above this, added on 6 February 2026 and visible only as a note in one e-mail template: infra/config/templates/tree_closure_email.template tells gardeners "GardenerAI is currently attempting to identify and revert the culprit. Please defer investigation until you receive a IRM notification." I found no public design doc for it; that note is the whole public surface reconstruction.

The other waterfall

Performance CI is a second post-submit pipeline, in the internal chrome project, so the only public enumeration is src-side. testing/buildbot/chromium.perf.json holds 71 entries — 18 *-builder-perf*, 46 testers, 7 *-processor-perf — and summing swarming.shards across the testers gives 628 shards over the 39 primary platforms in docs/speed/perf_lab_platforms.md from the tree. Builders POST each isolate's CAS digest to Pinpoint's /api/isolate so a bisect can reuse a waterfall build, and testers do not run per commit: docs/speed/perf_waterfall.md:17–42 describes "a single tester job running continuously", each run covering "the set of commits from the end commit of the previous invocation to the latest built commit". Enforcement is social: no perf tester is a required CQ builder. Size is the exception. android-binary-size (no more than 16 kB on arm32, 64 kB on high-end arm64, 50 dex methods), compile-size (size_threshold_mib 200) and fuchsia-binary-size are all cq: required, and the only way past them is a Binary-Size: or Compile-Size: footer.
