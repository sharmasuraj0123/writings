{{S}}The release cycle and the branches

Almost everything written about Chrome's release cadence is stale, including one of Google's own pages. The tree is not. docs/process/release_cycle.md was rewritten on 2026-08-26 and it says two weeks, not four. Branch numbers, config size and merge rights all follow from that number, and all of it is legible from git.

Everything up to here has been one commit's journey onto main. Shipping is the other axis: a cut, a branch, and a fleet that has to follow the branch.

The document that changed

The overview is four sentences. A milestone is developed on main for two weeks from the previous milestone's branch point; the branch is cut; it stabilises for three weeks; it ships to stable; then it gets weekly refreshes from the docs [src/docs/process/release_cycle.md:8-15, read at f288fed6]. Extended Stable is the interesting clause: it now maintains "every fourth milestone branch for six additional weeks", so an ES milestone still ships every eight weeks even though the milestone cadence halved [:19-26]. Beta lasts two weeks [:78-80]. Each stable rollout ships "two separate builds which are identical, except for the build number" [:102-111], and refreshes are weekly for stable and extended stable alike [:115-117].

The change was announced 2026-03-03 and took effect with Chrome 153's stable release on 2026-09-08 from the docs. Before that it was four weeks, from Chrome 94 (announced 2021-03-04, stable 2021-09-21); before that six weeks, from July 2010. chromium.org's "Chrome Release Channels" page still says stable ships "every 4 weeks".

Figure {{fig-cadence}} draws the seam. M152 branched 2026-07-27 and shipped 2026-08-25 on the old rhythm, four weeks. M153 branched 2026-08-17 and shipped 2026-09-08, three weeks later; every milestone after it starts exactly fourteen days after the one before, until the holidays stretch the gap before M160.

What a version number encodes

chrome/VERSION is four lines. At f288fed6 it reads, verbatim (src/chrome/VERSION:1-4): 

MAJOR=156
MINOR=0
BUILD=8067
PATCH=0

On trunk only BUILD moves, bumped twice on weekdays — around 03:01 and 14:01 UTC — by chrome-official-brancher@chops-service-accounts, under commits titled "Updating trunk VERSION from 8067.0 to 8068.0" whose body reads "This is an automated release commit. Do not revert without consulting chrome-pmo@google.com. NOAUTOREVERT=true" from the tree.

The MAJOR bump is branch day. "Updating trunk VERSION from 8059.0 to 8060.0 and incrementing major version to 156" landed 2026-09-15T03:01:06Z, so M155's branch number is the last BUILD that was still M155: 8059. The identity holds for M153 = 8010 and M154 = 8037, and infra/config/project.star states it outright — "The 3rd portion of the version number is the branch number for the associated milestone" [:136-145]. Halving the cadence therefore cut the width of a milestone in build numbers by more than half: M155 spans 8037 → 8059, twenty-two builds, where the four-week M152 spanned 7922 → 7977, fifty-five.

One piece of folklore is worth killing here. "Chrome Release Bot (LUCI)" was never a separate account; it was the author display name on chrome-official-brancher@chops-service-accounts.iam.gserviceaccount.com, and around April 2026 the display string became the bare address. No account change happened from the tree.

Every build number is a branch

Every trunk BUILD, not just milestone ones, gets its own refs/branch-heads/NNNN. On branch 8067, @{#1} is "Create chrome_branch_deps.json for branch 8067." (2026-09-21 12:40:19 UTC), @{#2} is "Incrementing VERSION to 156.0.8067.1", @{#3} takes it to 8067.2, and all three carry Cr-Branched-From main@{#1701636}. That mechanism is younger than it looks. Per-build branches used to open with a "Publish DEPS for X" commit pinning floating DEPS refs to hashes, and the switch was made per branch at cut time on 2023-06-29: 117.0.5860.0 is still a Publish DEPS commit at 03:06 UTC, 117.0.5861.0 a chrome_branch_deps.json commit at 15:05 UTC.

Life on a branch is narrow and almost entirely robotic. PATCH advances by "Incrementing VERSION to 153.0.8010.53" commits carrying Merge-Approval-Bypass: Chrome release infra; dependencies advance by "Roll commits from side projects in M155" carrying Merge-Approval-Bypass: Chrome DEPS-autoroller; and not every PATCH ships: branch 8010 was at PATCH=56 on 2026-09-21 while stable was still on .53, the higher half of an A/B pair with .52.

Branch day is a config event

The half of branch day that §02 set up is the one that reshapes the fleet; Figure {{fig-branch-day}} puts both halves side by side. On main, chrome-branch-day@chops-service-accounts lands "Activate chromium M155", which adds one object to infra/config/milestones.json and regenerates commit-queue.cfg, luci-milo.cfg and realms.cfg. On the branch, the same account lands "Update LUCI config for M155" across 3,019 files, rewriting settings.json to project chromium-m155, ref refs/branch-heads/8059, is_main: false, and all seven platforms marked "beta/stable" with gardener rotation chrome_browser_release — exactly the dict that infra/config/scripts/branch.py:102-126 writes.

The consequence is a sieve. Every builder declaration carries a branch_selector, and the shared branches.star defines the resource only when the selector's platforms intersect the project's. The same Starlark, read against the branch's settings.json, yields 256 builders in 30,255 lines of cr-buildbucket.cfg against trunk's 1,211 in 139,286. A release branch is not a smaller fleet someone configured; it is the same configuration with is_main false.

milestones.json keeps seven milestones alive at f288fed6: 144, 150, 151, 152, 153, 154, 155. Five of those are the current milestone and its four predecessors. The two outliers, 144 and 150, are not Extended Stable; they are ChromeOS long-term-support milestones, and chromiumdash proves it by giving them two extra fields no other milestone has: LTC, the long-term-support candidate date, and LTR, the date it becomes the long-term-support release ChromeOS devices actually sit on. Read 2026-09-21, M144 carries LTC 2026-02-03 and LTR 2026-04-21; M150 carries LTC 2026-07-21 and LTR 2026-10-06; the next milestone with the pair is M160, LTC 2027-01-13 and LTR 2027-03-31. ChromeOS nominates one milestone every six months, and the branch it nominates stays alive through its whole support window — which is why milestones.json still carries two milestones whose Chrome successors left it months ago. The six-month reading is inferred from those three pairs of dates, not from a statement in the tree reconstruction.

Getting a fix onto a branch

The policy is main-first. A developer sets the Merge-Request field on the bug; "within the next hour", automation opens a Merge Request issue [src/docs/process/merge_request.md:115]; release managers and automation "review and approve, reject, or ask questions about the merge within two business days" [:43-44]. Approved, it lands by Gerrit's "Cherry Pick" button or git cl cherry-pick --branch=refs/branch-heads/#### --bug=######### [:201,218-221], and within 14 days of the original change the Rubber Stamper bot will vote Bot-Commit+1 to bypass code review — but not OWNERS approval [:207-212]. Criteria tighten as stable approaches: beta takes regressions, blockers and security; stable takes urgent regressions and medium-or-higher security; extended takes security only. Flag-definition changes are never merged [:345-352].
