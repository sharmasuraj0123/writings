{{S}}One builder, expanded

A CI builder is one keyword-argument call in Starlark. Ten artefacts come out of it. At run time it is a Swarming task whose command is a recipe the builder does not pin. ci/Linux Builder is the one to walk, because every other builder in the fleet is a variation of it.

The call is 51 lines and it declares almost nothing about machines. This is src/infra/config/subprojects/chromium/ci/chromium.linux.star:328-350, the first half of it from the tree: 

ci.builder(
    name = "Linux Builder",
    branch_selector = branches.selector.LINUX_BRANCHES,
    builder_spec = builder_config.builder_spec(
        gclient_config = builder_config.gclient_config(
            config = "chromium",
            apply_configs = [
                "use_clang_coverage",
                # This is necessary due to child builders running the
                # telemetry_perf_unittests suite.
                "chromium_with_telemetry_dependencies",
            ],
        ),
        chromium_config = builder_config.chromium_config(
            config = "chromium",
            apply_configs = [
                "mb",
            ],
            build_config = builder_config.build_config.RELEASE,
            target_bits = 64,
            target_platform = builder_config.target_platform.LINUX,
        ),
    ),

The remaining 28 lines (:351-378) name a six-entry gn_args.config — gpu_tests, release_builder, remoteexec, devtools_do_typecheck, linux, x64 — a targets.bundle holding chromium_linux_scripts with additional_compile_targets = ["all"], a console entry with category release and short name bld, and contact_team_email = "chrome-linux-engprod@google.com". That is the whole authored surface.

Everything about hardware is inherited. The file's own ci.defaults.set supplies builder group chromium.linux, pool luci.chromium.ci, cores = 8, os.LINUX_DEFAULT, gardener_rotations.CHROMIUM, tree_closing = True, the default three-hour execution_timeout and health_spec.default() [chromium.linux.star:20-44; lib/ci_constants.star:5-14]. One level up, ci.star sets the bucket-wide defaults: bucket ci, triggered_by = ["chromium-gitiles-trigger"], cpu.X86_64, free_space.standard, and the shadow pool luci.chromium.try [ci.star:16-26]. Its comment for the shadow bucket is one line: "Shadow bucket of `ci`, for led builds" [ci.star:73-76]. led is depot_tools' LUCI editor: led get-builder prints a builder's job definition as JSON, led edit-* patches it, and led launch runs the result as a Swarming task. The shadow bucket is where those hand-edited jobs land: a developer can run a modified version of any CI builder without landing a CL, and it runs in ci.shadow on the luci.chromium.try pool rather than in ci on the production one.

Ten files change when that call changes. lucicfg emits a Buildbucket builder block (cr-buildbucket.cfg:17817-17935, 119 lines), a Scheduler job (luci-scheduler.cfg:1369-1377), five Milo console entries — in main, mirrors, chromium rotation, chromium tree closers and chromium.linux — a luci-notify tree_closers entry against chromium-status.appspot.com (luci-notify.cfg:780-805), a health spec under specs.ci["Linux Builder"], the first line of builder-owners/chrome-linux-engprod@google.com.txt, and four per-builder files: properties.json (209 lines), shadow-properties.json (14), gn-args.json (14) and targets/chromium.linux.json (2,756). Fifty-one lines of Starlark; 3,112 lines of generated text from the tree. Figure {{fig-builder-fanout}} lays out the fan-out.

The generated block is where the interesting substitution happens. This is src/infra/config/generated/luci/cr-buildbucket.cfg:17817-17841, dedented by four spaces: 

builders {
  name: "Linux Builder"
  swarming_host: "chromium-swarm.appspot.com"
  dimensions: "builderless:1"
  dimensions: "cores:8"
  dimensions: "cpu:x86-64"
  dimensions: "free_space:standard"
  dimensions: "os:Ubuntu-22.04"
  dimensions: "pool:luci.chromium.ci"
  dimensions: "ssd:0"
  exe {
    cipd_package: "infra/chromium/bootstrapper/${platform}"
    cipd_version: "latest"
    cmd: "bootstrapper"
  }
  properties:
    '{'
    '  "$bootstrap/exe": {'
    '    "exe": {'
    '      "cipd_package": "infra/recipe_bundles/chromium.googlesource.com/chromium/tools/build",'
    '      "cipd_version": "refs/heads/main",'
    '      "cmd": ['
    '        "luciexe"'
    '      ]'
    '    }'

Seven dimensions, and an exe that is not a recipe. The builder runs infra/chromium/bootstrapper/${platform} at cipd_version: "latest". The real recipe bundle is buried in the $bootstrap/exe property at refs/heads/main, and $bootstrap/properties names infra/config/generated/builders/ci/Linux Builder/properties.json [:17843-17845]. The reason is versioning: the bootstrapper is a passthrough luciexe that reads the properties file from the source revision being built, so "property changes for CQ builders will be applied during the CQ run" and a build of an old revision gets that revision's properties from the docs [infra/chromium starlark-libs/chromium-luci/bootstrap.star:5-18]. It applies the CL's own diff to the file before reading it [infra/infra go/src/infra/chromium/bootstrapper/bootstrap/build.go:386-410]. Counted at f288fed6: 1,070 of the 1,211 builders run the bootstrapper; 141 run cmd: "luciexe" on a bundle directly.

One consequence follows and is worth stating as a guess rather than a reading. Neither an orchestrator nor the compilator it schedules pins the bundle — ScheduleBuildRequest.exe supports only cipd_version overrides — so each resolves refs/heads/main at its own start, and a bundle landing between them puts two recipe revisions in one logical build reconstruction.

At run time the abstraction collapses. Chromium's own documentation says it is "not inaccurate to conceptualize a Buildbucket build simply as a Swarming task whose command is its 'recipe'" [src/docs/infra/builder_types.md:51-52]. Swarming's own README calls it "purely a task scheduler service" in which "File I/O is done through RBE-CAS"; its design doc calls the fleet "a legion of dumb bots" [luci-py appengine/swarming/README.md; appengine/swarming/doc/Design.md]. The in-tree glossary supplies the matching rule and the boundary: "only bots that match all requested dimensions will execute the task", a pool "acts as a security boundary, enforcing who can view and trigger tasks on its bots", and CAS is glossed by "its predecessor's name: 'isolate'" from the docs [src/docs/infra/glossary.md:134-149]. On the bot, bbagent runs a LogDog butler, merges build.proto datagrams out of the luciexe, forwards them to Buildbucket and uploads every stream to LogDog; a luciexe that exits without a terminal status is recorded as INFRA_FAILURE [luci-go luciexe/doc.go].

Scale that call 1,211 times and you get the fleet. Eighteen buckets of cr-buildbucket.cfg hold it: ci 641 and try 500, ten small ones summing to 70, and six empty dynamic *.shadow buckets. Within them, 55 distinct builder_group values and 32 builders with no group at all: ci is 641 builders across 30 named groups plus 6 group-less, try is 500 across 21 plus 9. The ten small buckets are where the platform does something other than build Chrome, and Figure {{fig-buckets}} gives each one its clause.
