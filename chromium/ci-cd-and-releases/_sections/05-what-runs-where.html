{{S}}What runs, where, on how many machines

Four facts. Test configuration is mid-migration between two generations that share a directory. The shard count in the tree is not the shard count that runs. A pass-fail decision belongs to ResultDB, not to the test binary. And the machines are countable, today, from an API that needs no credentials.

§04 left a checkout on disk. What gets compiled out of it, and which tests run against it, is decided in two other directories — which are halfway through swapping roles.

Two generations, one directory

The legacy generation is //testing/buildbot. A 2,625-line generate_buildbot_json.py expands waterfalls.pyl, test_suites.pyl and test_suite_exceptions.pyl into one JSON file per waterfall, layered in a documented order: suite dictionary, bot entry, then per-bot exceptions, whose swarming keys win (README.md:506–519) from the tree. The exceptions file is deliberately crippled: it "can only be used to remove tests from a bot, modify how a test is run on a bot, or remove keys… The exceptions can not be used to add a test to a bot" (README.md:465–471), because a file that could add tests would let a bot drift out of every suite naming it. One Buildbot-era hatch survives: twelve Python functions substituted into $$MAGIC_SUBSTITUTION_ arguments, supplying GPU device ids and CrOS filter files (buildbot_json_magic_substitutions.py:7–20) from the tree.

The current generation is Starlark. The four non-builder-specific pyl files — gn_isolate_map.pyl, mixins.pyl, test_suites.pyl, variants.pyl — are now generated by lucicfg from //infra/config/targets into //infra/config/generated/testing, and the legacy script reads them from there (targets/README.md:114–141) from the tree. They moved one at a time, starting with gn_isolate_map.pyl on 2023-04-12 and mixins.pyl on 2023-06-28. Since 2024-01-04 a builder declares its tests inline with targets = targets.bundle(…), and lucicfg writes the expanded spec into that builder's own directory. The legacy path is now residue: waterfalls.pyl holds 16 builder groups and 104 machines. The package that replaced it is 20,113 lines naming 329 distinct test binaries, and Figure {{fig-target-lanes}} draws both lanes with the rest of the counts.

Between builder identity and GN sits MB, //tools/mb/mb.py. Given a builder group and name it looks first in gn_args_locations.json for a Starlark-generated gn-args.json, falling back to mb_config.pyl (mb.py:1213–1263) — 51 groups and 914 builders generated against 26 and 180 legacy. It writes args.gn, maps swarming target names to GN labels through gn_isolate_map.pyl (408 entries, itself now generated) and emits the .isolate files the recipe sends to CAS from the tree.

The shard count has two authorities

Sharding is environmental, not orchestrated. The recipe names each task <name>:<index>:<count> and, when shards > 1, hands the runner GTEST_SHARD_INDEX and GTEST_TOTAL_SHARDS in its environment (chromium_swarming/api.py, _trigger_task_shard_default) from the tree; the Test Executable API is the whole contract in one sentence — "the executable must run only every Nth test starting at test number M (i.e., every ith test where (i mod N) == M)" (test_executable_api.md:311–328) from the docs. Nothing balances by runtime.

What balances them is a bot, a day late. The autosharder builder sits in the infra bucket with schedule = "0 9 * * *" — 09:00 UTC daily — and target_runtime 15.0 minutes (subprojects/infra/subproject.star:73–113) from the tree. It takes the p80 shard runtime over 14 days of BigQuery data with at least 1,500 non-experimental samples and computes optimal = ceil(shards × (runtime − overhead) / (target − overhead)), floored at 1 so a mis-measured overhead cannot ask for zero shards. Then it rewrites autoshard_exceptions.json and uploads a CL the Rubber Stamper approves and auto-submits. Nobody reads it.

So every shard count has two authorities, and citing one is citing half the fact. browser_tests on ci/Linux Tests is shards = 20 at chromium.linux.star:695; the generated spec says 70. Between them sits autoshard_exceptions.json:118–121 — {"shards": 70, "try_builder": "linux-rel"} — which also lifts blink_web_tests from the authored 8 to 9. The generated side, from infra/config/generated/builders/ci/Linux Tests/targets/chromium.linux.json lines 218–243 — one of 123 entries (86 gtest suites, 37 isolated scripts) that together schedule 313 Swarming tasks for this one tester from the tree:

Where the results go

Those tasks produce results; ResultDB holds them. Since Q4 2021 "all tests on Chrome/Chromium builders have their test results uploaded to ResultDB, and nearly all pass-fail decisions on the builders are based on these results"; a test whose JSON claims a failure ResultDB does not carry "will not fail" the build (resultdb.md:5–12) from the docs. The transport is local: a harness calls a ResultSink that rdb stream started on the same machine, finding its address and token via LUCI_CONTEXT, at build/util/lib/results/result_sink.py:39–44,54–60:

The fleet, one Tuesday night

The config names pools; Swarming's anonymous CountBots RPC says what is behind them. On 2026-09-22 between 09:45 and 09:55Z, luci.chromium.ci held 590 bots for 490 declared builders and luci.chromium.try 2,113 for 382 try builders. The try pool is mostly builderful: only 513 carry builderless:1, the rest pinned by a multi-valued builder: dimension to 67 named builders. Test pools are an order of magnitude larger and breathe with load: chromium.tests read 20,694 bots at 09:45Z, 20,320 ten minutes later and 24,172 the previous afternoon, because 13,180 of its machines are GCE VMs against 7,395 physical machines in three labs; the counts are live readings. The elastic half has a named mechanism and a shape. chromium.tests is not one pool declaration but one per OS image, in Starlark, in the Google-internal infradata/config repository; each declaration wraps its bot count in chrome.robocrop(min_amount, max_amount), and the Robocrop autoscaler moves the live count inside that band. The playbook prints the Windows pair verbatim: chrome.gce_win10_22h2 at 100–3,700 e2-standard-8 instances beside chrome.gce_win11_24h2 at 30–150 from the docs [os_upgrade_playbook.md:338–385]. An OS migration is therefore a config diff, not a reimage: shift ≤ 5 % of the band from the old group to the new one, land the CL, and "the GCE provider / Robocrop autoscaler will automatically drain instances running the old OS image and spin up replacement instances running the new OS image". What moves the count inside the band minute to minute is not documented publicly; the band itself is. Figure {{fig-fleet}} draws it to scale.

A pool that swings by four thousand machines between Monday afternoon and Tuesday night is not provisioned. It is rented, per shard, at a shard count a cron job rewrites every morning at nine.
