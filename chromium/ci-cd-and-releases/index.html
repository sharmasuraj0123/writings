01Four pipelines on one substrate

Chromium does not have a CI/CD pipeline. It has four. The only thing that makes them one system is that all four are configured from files checked into chromium/src itself. The rest of this post is the proof.

The four divide by what they consume. A pre-submit pipeline verifies every CL before it can land. A post-submit pipeline rebuilds and retests every commit that reaches refs/heads/main. A performance pipeline measures a much smaller set of commits on real hardware. A release pipeline cuts branches, bumps versions, pins dependencies and packages binaries. They are different pipelines in the sense that matters — different triggers, different latency budgets, different owners — and they share machines, a scheduler, a result store and a UI.

That shared substrate is LUCI. The infra glossary defines it in two sentences: "LUCI is a collection of continuous integration services running on Google Cloud. These services largely make-up the backbone of Chromium's CI" [src/docs/infra/glossary.md:101-102] from the docs. The same page fixes the vocabulary the whole post runs on. A Build is "A Buildbucket job that runs a single CI-specific task", composed of steps rendered in Milo. A Builder is "A named configuration (or grouping) of builds in Buildbucket". And, the sentence that collapses two layers into one: "As of writing (Q3 2022), all Buildbucket builds are themselves Swarming tasks" [src/docs/infra/glossary.md:10-20].

That last claim is four years old, so check it against the tree rather than repeat it. In the generated Buildbucket config, swarming_host: "chromium-swarm.appspot.com" occurs 1,211 times — once for each of the 1,211 builder blocks in the file [src/infra/config/generated/luci/cr-buildbucket.cfg, re-counted locally at f288fed6] from the tree. Not one builder in the public project opts out. A newer document restates the claim with a hedge and a wider scope: "As of writing (Q2 2025), nearly 100% of all workloads in Chromium's infra run as Swarming tasks" [src/docs/infra/builder_types.md:20-32].

The service hosts the four lanes share are named once, in nine lines of src/infra/config/main.star (lines 88–96), and Figure 1 puts the four lanes against them: 

luci.project(
    name = settings.project,
    config_dir = "luci",

    milo = "luci-milo.appspot.com",
    notify = "luci-notify.appspot.com",

    swarming = "chromium-swarm.appspot.com",

The shape is legible only against what it replaced. LUCI stands for Layered Universal Continuous Integration, and it was built to break up Buildbot, "our existing single-threaded monolithic continuous integration system": one "master" process per set of builders had owned scheduling, distributing, collecting, archiving and logging, and LUCI split each concern into an independent service, "negating the need for a master." Masters survive as a naming convention — "groups" of builders, one per former master, with the builder names kept identical [src/docs/tour_of_luci_ui.md:279-297] from the docs. The turndown has a date. On 25 September 2019 Eric Foo of Chrome Operations posted to chromium-dev under the subject "Chrome is 100% on LUCI. Buildbot officially turned down": "Yesterday, we officially turned down the last Buildbot master and are now 100% on LUCI (ci.chromium.org) as the official build infrastructure for ChromeOS and Chrome official releases, CI/Waterfall, and CQ/tryjobs systems." Seven years on, the fossils are still load-bearing enough to name twice: the tree-closing step regexp still begins with bot_update, a step that can no longer close the tree (§09), and //testing/buildbot still carries a waterfalls.pyl (§05).

One reference frame, stated once and used throughout. Paths and line numbers are chromium/src at f288fed6 — chrome/VERSION 156.0.8067.0, refs/heads/main@{#1701190}, checked out 2026-09-18 — with depot_tools at 0306e468 and V8 15.6.0. Readings taken from a live service, as opposed to from the tree, are dated where they appear, because they move.

The order that follows is the order the machinery runs in: the configuration layer first, standing there with nothing to do (§§02–05); then one change moving through it, from git cl upload to a numbered commit and the people who watch what it broke (§§06–09); then release, the cadence and the scripts (§§10–11). §12 is the ledger — what this design buys and what each property costs.

02The tree configures the fleet

//infra/config is a compiler. 125 Starlark files go in, 3,555 generated files come out, and the LUCI services read those files back out of git. Nothing is deployed. A change to the fleet is a CL.

The directory's own README says what it is for: the configuration rooted at main.star "defines the LUCI services configuration for the chromium project on the production instance of LUCI", written in Starlark, executed by lucicfg into the raw cfg files under generated/, with "a presubmit check" that "enforces that the generated files are kept in sync" from the docs [src/infra/config/README.md:15-30]. At f288fed6 the directory is itself a lucicfg package. PACKAGE.star declares @chromium-project with a minimum lucicfg of 1.44.1, two entry points — main.star for production and dev.star for the dev instance — and two dependencies: a local @chromium-targets rooted at infra/config/targets, and @chromium-luci, fetched from the separate infra/chromium repository and pinned at revision 3c067cfcf061330718cee8a4c74d9cd7232595c6. PACKAGE.lock records the lucicfg that actually ran: 1.46.7 from the tree [src/infra/config/PACKAGE.star:7-43; PACKAGE.lock:2-9].

That pin is recent history. On 2025-07-22, commit b711da6e4f deleted the library code under infra/config/lib in chromium/src — builders.star, ci.star, try.star, builder_config.star, gn_args.star, targets.star, bootstrap.star, branches.star, notifiers.star, orchestrator.star — and replaced every call site with an import of the form load("@chromium-luci//ci.star", "ci"), so that chromium and the internal chrome project execute one library instead of two copies from the tree. Ninety-eight of the 125 Starlark files now name @chromium-luci.

What survived in lib/ is constants, not logic. CI defaults: executable recipe:chromium, a three-hour execution timeout, pool luci.chromium.ci, shadow pool luci.chromium.try [lib/ci_constants.star:5-14]. Try defaults: recipe:chromium_trybot, four hours, luci.chromium.try [lib/try_constants.star:5-10]. The Siso remote-execution tiers — 250 jobs by default, 80 and 500 for low- and high-parallelism CI, 150 for low CQ, and -1 for high CQ, which the comment says is "Calculated based on the number of CPUs inside Siso" [lib/siso.star:5-21]. The default iOS toolchain, Xcode 27.0 RC 27a266a [lib/xcode.star:7-14]. Twelve gardener rotations [lib/gardener_rotations.star:10-23]. And a file of grandfathered exemptions carrying a banner warning that the lists "should only decrease" [lib/builder_exemptions.star:5-11].

main.star is the contract between the Starlark and the tree. It checks the lucicfg version, enables the crbug.com/1182002 Scheduler experiment, and then declares, by hand, every path lucicfg is allowed to own. This is src/infra/config/main.star:36-68, condensed with elision markers:

Two things fall out of that block. fail_on_warnings = True means, in lucicfg's own words, "treat validation warnings as errors" — a warning is a build break, not a note from the docs. And tracked_files makes the generated tree closed in both directions: "only files that are in this set will be actually written to the disk (and all other files are discarded)", and a tracked file that disappears from the output "must be deleted from the disk as well" from the docs. Three configs are explicitly not generated — testhaus.cfg, luci-analysis.cfg and luci-bisection.cfg are hand-written at the top of the directory and copied verbatim into generated/luci/ by lucicfg.emit [main.star:70-86]. Everything else comes out of the luci.project call quoted in §01, which binds the six appspot hosts [main.star:88-96]. Figure 2 counts both ends of that compile and the poll that carries the result to the services.

The output is large and mechanical, and each of the thirteen generated luci/*.cfg files opens with the same two-line banner: "Auto-generated by lucicfg. / Do not modify manually." — the eight files in luci/ that do not are the hand-copied ones and the two email templates. cr-buildbucket.cfg alone is 139,286 lines and 5,544,282 bytes — 5.29 MiB, which ls -lh rounds to 5.3M, and 5.54 MB decimal — holding 18 buckets and 1,211 builders. The figure’s right-hand column carries the same reading for the other five large ones from the tree.

Getting that tree to the services involves no deploy step. LUCI Config (config.luci.app) runs an import cron whose importAllConfigsInterval is ten minutes; it enqueues one task per config set at a deterministic offset inside that window, asks Gitiles for the latest commit touching the configured path, and commits the new revision only if every interested service's ValidateConfigs comes back without an ERROR-severity message [luci-go config_service/internal/importer/importer.go:62-74,323-337,520-543]. On 2026-09-22 the projects/chromium config set was imported from refs/heads/main, path infra/config/generated/luci, at revision f7de74e13efc (08:25:50Z), with lastImportAttempt reading Up-to-date — a reading off the live service, dated per §01 rather than badged. Consumers then poll on their own clock — Buildbucket, Scheduler and CV each about once a minute — so a landed infra/config CL is live in roughly one to eleven minutes, dominated by the import window reconstruction: that range is derived from the constants, not measured against a real change.

The validation that gates the import also runs long before it. depot_tools' CheckLucicfgGenOutput builds a presubmit command that runs lucicfg validate <entry_script>, which regenerates the configs, diffs them against what is checked in, and ships each config set to the same validation RPC the importer uses [depot_tools/presubmit_canned_checks.py:3744-3778]; infra/config/PRESUBMIT.py calls it twice, once for main.star and once for dev.star [src/infra/config/PRESUBMIT.py:74-84]. Four dedicated trybots guard the per-builder files that lucicfg writes under builders/ — branch-config-verifier, builder-config-verifier, targets-config-verifier and gn-args-verifier [src/infra/config/subprojects/chromium/try/presubmit.star:73,116,128,161]. A misconfigured fleet is therefore a red trybot, reviewed and reverted like any other bad CL. What that costs, and what one line of Starlark actually expands into, is the next section.

03One builder, expanded

A CI builder is one keyword-argument call in Starlark. Ten artefacts come out of it. At run time it is a Swarming task whose command is a recipe the builder does not pin. ci/Linux Builder is the one to walk, because every other builder in the fleet is a variation of it.

The call is 51 lines and it declares almost nothing about machines. This is src/infra/config/subprojects/chromium/ci/chromium.linux.star:328-350, the first half of it from the tree:

The remaining 28 lines (:351-378) name a six-entry gn_args.config — gpu_tests, release_builder, remoteexec, devtools_do_typecheck, linux, x64 — a targets.bundle holding chromium_linux_scripts with additional_compile_targets = ["all"], a console entry with category release and short name bld, and contact_team_email = "chrome-linux-engprod@google.com". That is the whole authored surface.

Everything about hardware is inherited. The file's own ci.defaults.set supplies builder group chromium.linux, pool luci.chromium.ci, cores = 8, os.LINUX_DEFAULT, gardener_rotations.CHROMIUM, tree_closing = True, the default three-hour execution_timeout and health_spec.default() [chromium.linux.star:20-44; lib/ci_constants.star:5-14]. One level up, ci.star sets the bucket-wide defaults: bucket ci, triggered_by = ["chromium-gitiles-trigger"], cpu.X86_64, free_space.standard, and the shadow pool luci.chromium.try [ci.star:16-26]. Its comment for the shadow bucket is one line: "Shadow bucket of `ci`, for led builds" [ci.star:73-76]. led is depot_tools' LUCI editor: led get-builder prints a builder's job definition as JSON, led edit-* patches it, and led launch runs the result as a Swarming task. The shadow bucket is where those hand-edited jobs land: a developer can run a modified version of any CI builder without landing a CL, and it runs in ci.shadow on the luci.chromium.try pool rather than in ci on the production one.

Ten files change when that call changes. lucicfg emits a Buildbucket builder block (cr-buildbucket.cfg:17817-17935, 119 lines), a Scheduler job (luci-scheduler.cfg:1369-1377), five Milo console entries — in main, mirrors, chromium rotation, chromium tree closers and chromium.linux — a luci-notify tree_closers entry against chromium-status.appspot.com (luci-notify.cfg:780-805), a health spec under specs.ci["Linux Builder"], the first line of builder-owners/chrome-linux-engprod@google.com.txt, and four per-builder files: properties.json (209 lines), shadow-properties.json (14), gn-args.json (14) and targets/chromium.linux.json (2,756). Fifty-one lines of Starlark; 3,112 lines of generated text from the tree. Figure 3 lays out the fan-out.

Seven dimensions, and an exe that is not a recipe. The builder runs infra/chromium/bootstrapper/${platform} at cipd_version: "latest". The real recipe bundle is buried in the $bootstrap/exe property at refs/heads/main, and $bootstrap/properties names infra/config/generated/builders/ci/Linux Builder/properties.json [:17843-17845]. The reason is versioning: the bootstrapper is a passthrough luciexe that reads the properties file from the source revision being built, so "property changes for CQ builders will be applied during the CQ run" and a build of an old revision gets that revision's properties from the docs [infra/chromium starlark-libs/chromium-luci/bootstrap.star:5-18]. It applies the CL's own diff to the file before reading it [infra/infra go/src/infra/chromium/bootstrapper/bootstrap/build.go:386-410]. Counted at f288fed6: 1,070 of the 1,211 builders run the bootstrapper; 141 run cmd: "luciexe" on a bundle directly.

One consequence follows and is worth stating as a guess rather than a reading. Neither an orchestrator nor the compilator it schedules pins the bundle — ScheduleBuildRequest.exe supports only cipd_version overrides — so each resolves refs/heads/main at its own start, and a bundle landing between them puts two recipe revisions in one logical build reconstruction.

At run time the abstraction collapses. Chromium's own documentation says it is "not inaccurate to conceptualize a Buildbucket build simply as a Swarming task whose command is its 'recipe'" [src/docs/infra/builder_types.md:51-52]. Swarming's own README calls it "purely a task scheduler service" in which "File I/O is done through RBE-CAS"; its design doc calls the fleet "a legion of dumb bots" [luci-py appengine/swarming/README.md; appengine/swarming/doc/Design.md]. The in-tree glossary supplies the matching rule and the boundary: "only bots that match all requested dimensions will execute the task", a pool "acts as a security boundary, enforcing who can view and trigger tasks on its bots", and CAS is glossed by "its predecessor's name: 'isolate'" from the docs [src/docs/infra/glossary.md:134-149]. On the bot, bbagent runs a LogDog butler, merges build.proto datagrams out of the luciexe, forwards them to Buildbucket and uploads every stream to LogDog; a luciexe that exits without a terminal status is recorded as INFRA_FAILURE [luci-go luciexe/doc.go].

Scale that call 1,211 times and you get the fleet. Eighteen buckets of cr-buildbucket.cfg hold it: ci 641 and try 500, ten small ones summing to 70, and six empty dynamic *.shadow buckets. Within them, 55 distinct builder_group values and 32 builders with no group at all: ci is 641 builders across 30 named groups plus 6 group-less, try is 500 across 21 plus 9. The ten small buckets are where the platform does something other than build Chrome, and Figure 4 gives each one its clause.

04Materialising a checkout

Every build on every bot begins with one step called bot_update. It is not a program. It is a three-layer sandwich: a recipe module that builds a command line, a resource script that drives git, and depot_tools underneath. Knowing which layer you are in is the difference between reading a checkout failure and guessing.

Layer one is bot_update/api.py — 1,035 lines, class BotUpdateApi at line 298, whose docstring at line 5 says the purpose is to ensure a consistent checkout on a bot from the tree. ensure_checkout() turns a gclient config plus the build input into a command line, runs it as a step named exactly bot_update, and translates the JSON it reads back into build properties, an output commit and — since 2025-11-19 — a TurboCI check. TurboCI has no public design doc; from the API it is a 2026 LUCI layer that models a build as a graph of checks with declared dependencies, rather than as an ordered list of steps reconstruction. What bot_update contributes to that graph is one node. Before the command runs, create_check() writes a node with kind="CHECK_KIND_SOURCE" and state="CHECK_STATE_PLANNED" carrying a GobSourceCheckOptions that holds the revisions and the Gerrit change it intends to produce; afterwards set_result() attaches GobSourceCheckResults and BotUpdateResults — what was actually checked out — and moves the node to FINAL (api.py:147–165, 237–250, 252–295) from the tree. The compile check declares a dependency on that node, so the graph encodes "you cannot compile a checkout that does not exist" as data rather than as step ordering. Layer two is the 1,458-line resource script bot_update.py, which knows nothing about recipes. Layer three is depot_tools proper: git_cache.py, gclient.py, gclient_scm.py.

Figure 5 is the sandwich next to a real run of it: the live log of ci/Linux Builder #228485 on 2026-09-22, one build, cold builder cache. The pin ed7c7c79 was missing from the mirror, so git cat-file -e failed and populate ran. The step took 5 min 17 s, the manifest listed 168 git repositories, and the step text moved the bot's disk from [154GB/290GB used (53%)] to [178GB/290GB used (61%)]. gclient runhooks, a different step, took a further 1 min 42 s.

The mirror is what makes 66 seconds possible. It lives in [CACHE]/git and is re-bootstrapped wholesale from gs://chromium-git-cache/v2/… when it is missing, has zero pack files, or has more than GC_AUTOPACKLIMIT = 50 of them (git_cache.py:29, 628–633) from the tree; the log printed 12 for src. If the pin or a ref is still absent after the first populate, the script retries it three times, sleeping 60 seconds between attempts (bot_update.py:792–801). The bot's git_cache_epoch read 1789770839 — 2026-09-18 22:33:59 UTC, the moment the .cache_epoch marker was written on first use of that cache directory (bot_update.py:1240–1254).

The script then writes its own .gclient — solutions with managed=False, pointed at the same cache — and calls gclient sync with the flags below, plus --revision <solution>@unmanaged for every solution (bot_update.py:340, 453–461, 970–975).

             --nohooks --noprehooks --delete_unversioned_trees

unmanaged says the root is already positioned — the log prints ________ unmanaged solution; skipping src (gclient_scm.py:1102) — so gclient does only the DEPS below it. --nohooks is deliberate: deferring hooks to a separate step keeps a checkout failure (infra) and a hook failure (product) on two different rows. A GclientSyncFailed deletes the checkout and reruns ensure_checkout exactly once, wiping the whole git cache first if the output contains bad object, could not read or is corrupt (bot_update.py:1308–1332).

The patch model, and the fact everyone trips on

On a try build the recipe adds one flag, --patch_ref <repo>@<target_ref>:<fetch_ref>. apply_patch_ref in gclient_scm.py fetches it, cherry-picks target..patch with --keep-redundant-commits — unlanded dependent CLs come along, landed parents are skipped — then soft-resets to the base. Lines 777–783 and 812–815 hold both halves: 

                        self._Capture(
                            [
                                "cherry-pick",
                                target_rev + ".." + pr,
                                "--keep-redundant-commits",
                            ]
                        )
        …
        latest_commit = self.revinfo(None, None, None)
        if options.reset_patch_ref:
            self._Capture(["reset", "--soft", base_rev])
        return latest_commit

The CL is staged, not committed. That is why got_revision on a try build is the base commit and not the change under test — a fact that looks like a bug until you read line 814. A conflicting cherry-pick exits 88 (87 if git failed to download the patch, which is an infra problem instead), and exit 88 makes the recipe attach the patch error log, set the step to FAILURE, emit a PATCH_FAILURE tryjob result and call set_do_not_retry_build() — output property do_not_retry=true (api.py:766–790). The mirror image is deapply_patch(): re-pin the first solution to whichever got_*_revision property that solution maps to — the code refuses to assume it is got_revision, because some gclient configs remap it — resolve every other fixed revision to its observed value, rerun with patch=False as bot_update (without patch) (api.py:997–1027, 1029–1035). Pinning only src is what makes a DEPS-changing CL deapply correctly.

Three numbers bound the step from the tree. chromium_tests passes a 3,600-second timeout, CI and try alike. A subprocess silent on stdout for STALE_PROCESS_DURATION = 1200 seconds is killed, with a ps auxwwf tree dumped every 300 seconds (bot_update.py:38, 199–200). And git HTTP aborts below GIT_HTTP_LOW_SPEED_LIMIT 102,400 bytes per second held for 1,800 seconds (api.py:370–371).

05What runs, where, on how many machines

Four facts. Test configuration is mid-migration between two generations that share a directory. The shard count in the tree is not the shard count that runs. A pass-fail decision belongs to ResultDB, not to the test binary. And the machines are countable, today, from an API that needs no credentials.

§04 left a checkout on disk. What gets compiled out of it, and which tests run against it, is decided in two other directories — which are halfway through swapping roles.

Two generations, one directory

The legacy generation is //testing/buildbot. A 2,625-line generate_buildbot_json.py expands waterfalls.pyl, test_suites.pyl and test_suite_exceptions.pyl into one JSON file per waterfall, layered in a documented order: suite dictionary, bot entry, then per-bot exceptions, whose swarming keys win (README.md:506–519) from the tree. The exceptions file is deliberately crippled: it "can only be used to remove tests from a bot, modify how a test is run on a bot, or remove keys… The exceptions can not be used to add a test to a bot" (README.md:465–471), because a file that could add tests would let a bot drift out of every suite naming it. 07Inside a CQ build

A CQ build is not one build, and a test failure is not a verdict. What you click on is one row in Gerrit; underneath it are two machines on two core counts, four time-ordered test phases, and two independent subtractions before red is allowed to mean "your change is broken". That structure has one measured cause, stated plainly in the docs: "the CQ has roughly ~20,000 unique flaky tests" (docs/infra/cq.md:343–352) from the docs.

Two machines, one build row

docs/infra/builder_types.md names four patterns, and they are a progression from the docs. All-in-one with local tests does checkout, compile and test as steps of one build on one machine (:71–85). All-in-one with swarmed tests keeps the single build but fires each suite off as a raw Swarming task (:89–111). The builder/tester split separates compile and test into two builds so the parent need not wait (:113–155), at the cost that it "roughly doubles the amount of builds at-play, which would double the amount of results that may need inspecting" (:161–163). The orchestrator/compilator split fixes that last cost: "a single builder called the 'orchestrator' runs for the entire duration and is the sole/primary user-facing build", and it immediately triggers a compilator that "handles all compilation while the original orchestrator is simply sleeping" (:159–187).

The point is not parallelism. It is that the expensive machine is held only while it compiles. Static-analysis checks that need the whole checkout stay on the compilator, which is what lets the orchestrator skip syncing a source tree and run on 2- or 4-core bots; the compilator gets a "beefier >=16 core bot" and, once it has compiled and run those checks, "can immediately move on to pick up a new build" (docs/infra/builder_types.md:159–187, docs/infra/new_builder.md:403–407) from the docs. linux-rel is declared with try_.orchestrator_builder, mirrors ci/Linux Builder, ci/Linux Tests, ci/GPU Linux Builder and ci/Linux Release (NVIDIA), and names compilator = "linux-rel-compilator" (tryserver.chromium.linux.star:453–492) from the tree.

Four phases

The ladder is written down. docs/infra/cq.md:243–262, verbatim from the docs — the recipes that implement it live in chromium/tools/build, not in this checkout: 

The CQ has the following structure:

* Compile all test suites that might be affected by the CL.
* Runs all test suites that might be affected by the CL.
    * Many test suites are divided into shards. Each shard is run as a separate
      swarming task.
    * These steps are labeled '(with patch)'
* Retry each shard that has a test failure. The retry has the exact same
  configuration as the original run. No recompile is necessary.
    * If the retry succeeds, then the failure is ignored.
    * These steps are labeled '(retry shards with patch)'
    * It's important to retry with the exact same configuration. Attempting to
      retry the failing test in isolation often produces different behavior.
* Recompile each failing test suite without the CL. Rerun each failing test
  suite in isolation.
    * If the retry fails, then the fail is ignored, as it's assumed that the test
      is broken/flaky on tip of tree.
    * These steps are labeled '(without patch)'
* Fail the build if there are tests which failed in both '(with patch)' and
  '(retry shards with patch)' but passed in '(without patch)'.

The constants come from the recipe module. The (without patch) phase repeats each failing test 10 times with the launcher retry limit set to 0, and only runs when ≤ 100 tests need retrying. CI builders take the opposite tack: they retry failed shards with the limit raised to 5. The retry filter naming which tests to rerun is capped by the command line, 6,000 characters on Windows and 90,000 elsewhere; over the cap the filter is dropped and the whole suite reruns (tools/build recipes/recipe_modules/chromium_tests/steps.py:81–85, 229–245) from the tree. The unmodified default, the one every (with patch) shard runs under, is --isolated-script-test-launcher-retry-limit = 3, "so, for N+1 total invocations of the test" (docs/testing/test_executable_api.md:168–171) from the docs. Figure 10 puts the four phases on the two lanes that run them.

The second subtraction

The ladder removes failures that do not reproduce. Exoneration removes failures that reproduce and are still not yours. For each failing variant the recipe calls LUCI Analysis QueryStability with the build's gitiles commit and its Gerrit changes, then writes back ResultDB TestExoneration records with machine-readable reasons: OCCURS_ON_MAINLINE when the test also failed (without patch), OCCURS_ON_OTHER_CLS when "LUCI Analysis reported this test as being flaky or failing", and NOT_CRITICAL for experimental suites (tools/build recipes/recipe_modules/test_utils/api.py, _query_stability_rate and _exonerate_unrelated_failures) from the tree. If the query itself errors, nothing is exonerated and luci_analysis_query_error is set — the side channel fails closed.

What counts as unstable is configured in the repository. Under test_stability_criteria: failure_rate { failure_threshold: 6, consecutive_failure_threshold: 3 } and flake_rate { … flake_threshold: 3 … } (infra/config/generated/luci/luci-analysis.cfg:165–176) from the tree. Two other sets of numbers live in the same file and are easy to confuse with those, so name the field. The legacy top-level bug_filing_thresholds at :4–15 files on 75 exonerated critical failures in three days, or 10 builds failed by flaky tests in seven. The newer bug_management.policies at :80–163 are activation thresholds with their own deactivation floors: 30 exonerations in three days (deactivating below 1 in seven) at P2, 7 failed gardened builds in three days at P1, and 10 human CLs rejected in one day at P0 — the priority that fires when "exoneration can no longer mitigate the impact".

When a build is thrown away

Two rules, often conflated. Any patchset change cancels the Run. Only a REWORK — the one Gerrit revision kind that advances MinEquivalentPatchset — cancels the running builds, so a rebase-and-repush costs the queue position but not the compile. Two builders opt out with cancel_stale: NO, win-arm64-compile-dbg and win_chromium_compile_dbg_ng; the Starlark says why: "Remove once cancelling doesn't wipe out builder cache", crbug.com/40847153 (commit-queue.cfg:8489, 9098; tryserver.chromium.win.star:475–480, 306–311) from the tree. The budgets around it: retry_config { single_quota: 1, global_quota: 2, … timeout_weight: 2 }, so one timeout burns the whole global allowance (:9354–9360); 10 active runs per user, 20 for chromium-src-increased-quota, unlimited for chromium-src-emergency-quota and the Skia autoroller (:9375–9407); and a try build pending 2 hours is expired, a value try.star:18–20 asks you to "Keep this in sync" with CV.

Add it up honestly. Three of the four phases exist to distinguish "your change is broken" from "this test is broken", and the price is that a CQ run can compile the tree twice. That is affordable only because the second compile touches just the failing suites, and it is bounded by the same budget that governs admission to the CQ at all — the median cycle time under 40 minutes counted in §06's funnel (docs/infra/cq.md:304–305) from the docs. The 10 repeats, the 100-test guard, the 6,000-character filter cap: each is a local answer to that one number.

08From green to refs/heads/main

There is no commit-numbering daemon. The sequence in Cr-Commit-Position: refs/heads/main@{#1702467} is not issued by a service that counts. It falls out of three machines that never speak to each other — CV's single-submitter queue, Gerrit's REBASE_ALWAYS submit type, and a plugin whose entire rule is three lines long.

Divide the work first. CV owns the Run. Gerrit owns the merge: chromium/src's project config reads submit_type = "REBASE_ALWAYS", configured and inherited, with use_content_merge inherited true and reject_implicit_merges on. The git-numberer Gerrit plugin owns numbering, and docs/contributing.md:642–647 says so: Cr-Commit-Position is "automatically added by the git-numberer Gerrit plugin when a change is submitted" from the docs. The division shows in every commit object. The author is the CL owner; the committer is CV's project-scoped identity chromium-scoped@luci-project-accounts.iam.gserviceaccount.com — 397 of the last 400 commits on main. The other three were people clicking Submit in Gerrit.

The Run's states come from cv/internal/run/storage.proto:30–73 from the tree: PENDING, RUNNING, WAITING_FOR_SUBMISSION, SUBMITTING, then SUCCEEDED, FAILED or CANCELLED. The proto gives three reasons for waiting — a closed tree, "another Run in the same LUCI Project that is currently submitting", and rate limiting — and that state is cancellable. SUBMITTING is not: once CV has begun handing revisions to Gerrit, your CQ−1 does nothing. A Run that never resolves is force-cancelled when its total duration reaches MaxRunTotalDuration = 10 * 24 * time.Hour (cv/internal/common/run.go:35–39).

OnReadyForSubmission is where serialisation happens (run/impl/handler/submit.go:52–184). It acquires the SubmitQueue first and checks the tree second. The queue is one datastore entity per LUCI project: a Current Run, a FIFO Waitlist, and a History of submission timestamps inside the burst window (run/impl/submit/queue.go:38–58). Lose the race and you are waitlisted. Win it and the tree check runs — OPEN and THROTTLED both count as open (run/impl/state/state.go:153–200), closed or unknown releases the slot and pokes again after treeCheckInterval = time.Minute, and more than treeStatusFailureTimeLimit = 10 * time.Minute of status-service errors fails the Run (run/impl/handler/poke.go:37–42).

That acquire-check-release loop is visible from outside. Run 8832899183854-1-066668e19c71f84c finished its presubmit at 10:16:04 UTC on 2026-09-22 into a tree that had been closed since 10:08:05. Its event log then reads "Acquired Submit Queue", "Tree Status Check", "Released Submit Queue", over and over, roughly every 11 seconds, until the tree reopened at 10:19:19. It was waitlisted twice — 10:19:29 and 10:20:24 — acquired the queue at 10:20:39, and Gerrit reported the merge in the same second. Two things follow. The slot is genuinely surrendered on every failed tree check, which is why a closed tree does not head-of-line-block the Runs behind it; and the observed 11-second period is shorter than treeCheckInterval, so that constant is a floor on self-rescheduling, not the whole set of reasons a Run wakes up reconstruction.

Pacing lives in that same entity. src/infra/config/main.star:144–149 sets submit_max_burst = 2 and submit_burst_delay = time.minute, emitted by lucicfg as submit_options { max_burst: 2 burst_delay { seconds: 60 } } (commit-queue.cfg:8–13) from the tree. nextSubmissionETA (queue.go:75–90) returns now, unless the maxBurst-th most recent submission is newer than now minus burstDelay — in which case it returns that timestamp plus the delay. In plain language: the third commit in any 60-second window waits. Figure 11 puts the state machine, the queue and the rewrite on one page.

That is testable against public data, so I tested it. Over 400 consecutive commits on refs/heads/main — 2026-09-21 21:45 to 2026-09-22 10:20 UTC, 12.6 hours at 31.8 commits an hour — no three CV-committed commits fell inside 60 seconds. Exactly two windows held three commits at all, the tighter spanning 57.0 seconds, and each contained a direct human submit (iwells@chromium.org at 00:01:31). The pacing is real; the exceptions bypass the queue.

Submission itself is unglamorous. RunCLsSubmitter.Submit re-checks that it still holds the queue, then calls Gerrit SubmitRevision once per CL in dependency order, each with up to 10 exponential-backoff retries from a 200 ms base, doubling (submitter.go:161–222, 231–252). FailedPrecondition — Gerrit's 409, "either because the change can't be merged, or this revision isn't the latest" — is permanent (submitter.go:307–347), and when the Run ends CV removes the Commit-Queue votes, triggering vote last (gerrit/trigger/reset.go:156–186) from the tree. On a live CL the comment reads "Cannot rebase <sha>: Change N could not be rebased due to a conflict during merge" (CL 8431183, 2026-09-22). The whole submission is bounded by defaultSubmissionDuration = 20 * time.Minute, 40 for a CrOS kernel change (handler/submit.go:506–526).

Why the rebase is load-bearing

REBASE_ALWAYS is usually explained as history hygiene: Gerrit "always does a rebase, even if a fast-forward is possible", so main stays linear (Documentation/config-project-config.txt) from the docs. True, and beside the point. The consequence that matters is in Gerrit's plugin documentation: a Change Message Modifier can "modify commit message of the change being submitted by Rebase Always and Cherry Pick submit strategies" — and by nothing else (Documentation/dev-plugins.txt). git-numberer's generator is a ChangeMessageModifier. Numbering works only because the commit is rewritten at submit, and the plugin states the inverse itself: when baseCommit equals the original it returns the message untouched (GitNumberFooterGenerator.java:36–73). That causal chain is a reconstruction; each link in it is sourced.

The generator's rule fits on a screen. This is Generator.childMessage, lines 35–56 of Generator.java in infra/gerrit-plugins/git-numberer: 

  public static String childMessage(
      RevCommit expectedParent, String childCommitMessage, String destRef)
      throws GitNumberValidationError {
    checkNotNull(expectedParent);
    PositionFooters pfParent = PositionFooters.extract(expectedParent);
    if (!pfParent.errors.isEmpty())
      throw new GitNumberValidationError(pfParent.formatErrors(expectedParent));

    StringBuilder newMessage = MessageTweaker.copyAndModifyingFooters(childCommitMessage);
    // Post-condition: we are appending lines to last paragraph
    // and all prior footers like Change-Id are already in this paragraph.

    if (destRef.equals(pfParent.position.branch)) {
      PositionFooters.appendCommitPosition(newMessage, destRef, pfParent.position.number + 1);
    } else {
      PositionFooters.appendCommitPosition(newMessage, destRef, 1);
      PositionFooters.appendBranchedFrom(newMessage, expectedParent.getName(), pfParent.position);
    }
    PositionFooters.copyBranchedFrom(newMessage, pfParent);
    newMessage.append('\n');
    return newMessage.toString();
  }

Same destination ref as the parent: X+1. A different ref: position 1, plus a Cr-Branched-From footer naming the parent's sha and position, with the parent's lineage copied forward. That is the whole numbering system. The other half of the plugin is a verifier, bound as both RefOperationValidationListener and OnSubmitValidationListener (GitNumbererModule.java:22–63), so the same rule holds for a raw git push and a Gerrit submit alike: it rejects merge commits with "merge commit <sha> not allowed", non-fast-forward updates, wrong branches and wrong lineage (CommitValidator.java:169–242).

One last piece of folklore. Auto-Submit is not a CV feature either. CV knows the label only through HasAutoSubmit and uses it for one decision: quotaPayer charges the full-run quota to the CL owner rather than to whoever voted (prjmanager/triager/runs.go:703–720). The vote is cast in a browser. The chromium-behavior Gerrit frontend plugin watches the reply dialog and, when a reviewer sets Code-Review+1 on a CL carrying Auto-Submit+1 with no unresolved comments or drafts, sets Commit-Queue+2 in the same review (web/autosubmit.ts:225–283), under the notice "Your approval will also set CQ+2" (autosubmit.ts:288–298). Rubber Stamper does the same from the bot side. Three machines land the commit, and the button that starts them is in somebody else's browser.

10The release cycle and the branches

Almost everything written about Chrome's release cadence is stale, including one of Google's own pages. The tree is not. docs/process/release_cycle.md was rewritten on 2026-08-26 and it says two weeks, not four. Branch numbers, config size and merge rights all follow from that number, and all of it is legible from git.

Everything up to here has been one commit's journey onto main. Shipping is the other axis: a cut, a branch, and a fleet that has to follow the branch.

The document that changed

The overview is four sentences. A milestone is developed on main for two weeks from the previous milestone's branch point; the branch is cut; it stabilises for three weeks; it ships to stable; then it gets weekly refreshes from the docs [src/docs/process/release_cycle.md:8-15, read at f288fed6]. Extended Stable is the interesting clause: it now maintains "every fourth milestone branch for six additional weeks", so an ES milestone still ships every eight weeks even though the milestone cadence halved [:19-26]. Beta lasts two weeks [:78-80]. Each stable rollout ships "two separate builds which are identical, except for the build number" [:102-111], and refreshes are weekly for stable and extended stable alike [:115-117].

The change was announced 2026-03-03 and took effect with Chrome 153's stable release on 2026-09-08 from the docs. Before that it was four weeks, from Chrome 94 (announced 2021-03-04, stable 2021-09-21); before that six weeks, from July 2010. chromium.org's "Chrome Release Channels" page still says stable ships "every 4 weeks".

Figure 13 draws the seam. M152 branched 2026-07-27 and shipped 2026-08-25 on the old rhythm, four weeks. M153 branched 2026-08-17 and shipped 2026-09-08, three weeks later; every milestone after it starts exactly fourteen days after the one before, until the holidays stretch the gap before M160.

What a version number encodes

chrome/VERSION is four lines. At f288fed6 it reads, verbatim (src/chrome/VERSION:1-4): 

MAJOR=156
MINOR=0
BUILD=8067
PATCH=0

On trunk only BUILD moves, bumped twice on weekdays — around 03:01 and 14:01 UTC — by chrome-official-brancher@chops-service-accounts, under commits titled "Updating trunk VERSION from 8067.0 to 8068.0" whose body reads "This is an automated release commit. Do not revert without consulting chrome-pmo@google.com. NOAUTOREVERT=true" from the tree.

The MAJOR bump is branch day. "Updating trunk VERSION from 8059.0 to 8060.0 and incrementing major version to 156" landed 2026-09-15T03:01:06Z, so M155's branch number is the last BUILD that was still M155: 8059. The identity holds for M153 = 8010 and M154 = 8037, and infra/config/project.star states it outright — "The 3rd portion of the version number is the branch number for the associated milestone" [:136-145]. Halving the cadence therefore cut the width of a milestone in build numbers by more than half: M155 spans 8037 → 8059, twenty-two builds, where the four-week M152 spanned 7922 → 7977, fifty-five.

One piece of folklore is worth killing here. "Chrome Release Bot (LUCI)" was never a separate account; it was the author display name on chrome-official-brancher@chops-service-accounts.iam.gserviceaccount.com, and around April 2026 the display string became the bare address. No account change happened from the tree.

Every build number is a branch

Every trunk BUILD, not just milestone ones, gets its own refs/branch-heads/NNNN. On branch 8067, @{#1} is "Create chrome_branch_deps.json for branch 8067." (2026-09-21 12:40:19 UTC), @{#2} is "Incrementing VERSION to 156.0.8067.1", @{#3} takes it to 8067.2, and all three carry Cr-Branched-From main@{#1701636}. That mechanism is younger than it looks. Per-build branches used to open with a "Publish DEPS for X" commit pinning floating DEPS refs to hashes, and the switch was made per branch at cut time on 2023-06-29: 117.0.5860.0 is still a Publish DEPS commit at 03:06 UTC, 117.0.5861.0 a chrome_branch_deps.json commit at 15:05 UTC.

Life on a branch is narrow and almost entirely robotic. PATCH advances by "Incrementing VERSION to 153.0.8010.53" commits carrying Merge-Approval-Bypass: Chrome release infra; dependencies advance by "Roll commits from side projects in M155" carrying Merge-Approval-Bypass: Chrome DEPS-autoroller; and not every PATCH ships: branch 8010 was at PATCH=56 on 2026-09-21 while stable was still on .53, the higher half of an A/B pair with .52.

Branch day is a config event

The half of branch day that §02 set up is the one that reshapes the fleet; Figure 14 puts both halves side by side. On main, chrome-branch-day@chops-service-accounts lands "Activate chromium M155", which adds one object to infra/config/milestones.json and regenerates commit-queue.cfg, luci-milo.cfg and realms.cfg. On the branch, the same account lands "Update LUCI config for M155" across 3,019 files, rewriting settings.json to project chromium-m155, ref refs/branch-heads/8059, is_main: false, and all seven platforms marked "beta/stable" with gardener rotation chrome_browser_release — exactly the dict that infra/config/scripts/branch.py:102-126 writes.

The consequence is a sieve. Every builder declaration carries a branch_selector, and the shared branches.star defines the resource only when the selector's platforms intersect the project's. The same Starlark, read against the branch's settings.json, yields 256 builders in 30,255 lines of cr-buildbucket.cfg against trunk's 1,211 in 139,286. A release branch is not a smaller fleet someone configured; it is the same configuration with is_main false.

milestones.json keeps seven milestones alive at f288fed6: 144, 150, 151, 152, 153, 154, 155. Five of those are the current milestone and its four predecessors. The two outliers, 144 and 150, are not Extended Stable; they are ChromeOS long-term-support milestones, and chromiumdash proves it by giving them two extra fields no other milestone has: LTC, the long-term-support candidate date, and LTR, the date it becomes the long-term-support release ChromeOS devices actually sit on. Read 2026-09-21, M144 carries LTC 2026-02-03 and LTR 2026-04-21; M150 carries LTC 2026-07-21 and LTR 2026-10-06; the next milestone with the pair is M160, LTC 2027-01-13 and LTR 2027-03-31. ChromeOS nominates one milestone every six months, and the branch it nominates stays alive through its whole support window — which is why milestones.json still carries two milestones whose Chrome successors left it months ago. The six-month reading is inferred from those three pairs of dates, not from a statement in the tree reconstruction.

Getting a fix onto a branch

The policy is main-first. A developer sets the Merge-Request field on the bug; "within the next hour", automation opens a Merge Request issue [src/docs/process/merge_request.md:115]; release managers and automation "review and approve, reject, or ask questions about the merge within two business days" [:43-44]. Approved, it lands by Gerrit's "Cherry Pick" button or git cl cherry-pick --branch=refs/branch-heads/#### --bug=######### [:201,218-221], and within 14 days of the original change the Rubber Stamper bot will vote Bot-Commit+1 to bypass code review — but not OWNERS approval [:207-212]. Criteria tighten as stable approaches: beta takes regressions, blockers and security; stable takes urgent regressions and medium-or-higher security; extended takes security only. Flag-definition changes are never merged [:345-352].

11The release scripts

The scripts that actually ship a browser are small, old and deliberately boring. A list of Step classes with a JSON resume file. A regex over four #define lines. A DEPS hook writing one string into a file. The fleet has already done everything difficult; what is left is arithmetic and a git push.

V8's live in v8/tools/release/, and common_includes.py — Copyright 2013 — gives every one of them the same three things from the tree. A script is an ordered list of Step classes; Step.Run reloads a state file, runs the step, and in a finally: block writes the state back as JSON, so -s N resumes a half-finished push [common_includes.py:340–351, 741]. Git calls carry retry wait-plans: [5, 30] seconds in general [:401–407]; when a landed commit has yet to replicate, fetch and grep the remote branch for the unique commit title on a plan of 10, 30, 60, 60, 60, 60, 60, then die with "Maybe the git updater is lagging behind?" [:283–301]. And the version is grepped, not parsed — a regex over the four #define lines of include/v8-version.h [:487–498], which here reads 15.6.0 with V8_IS_CANDIDATE_VERSION 1.

The daily push is create_release.py, thirteen steps long [:211–226], and what feeds it is a ref, not a human. refs/heads/lkgr is V8's last known good revision, and it is maintained by a builder, not by the release script. On V8's refs/heads/infra/config branch, a builder named "V8 lkgr finder" carries "ref": "refs/heads/lkgr" and schedule = "2/6 * * * *" — every six minutes, offset two — and its job is to move that ref forward [v8 infra/config builders/tools.star:145] from the tree. The effect is that "the newest trunk commit that passed" is addressable as a git ref, so the release script never has to decide what is good. auto_push.py reads it in two lines — git fetch origin +refs/heads/lkgr:refs/heads/lkgr then git show-ref -s refs/heads/lkgr — and then declines to do anything if last_release..candidate is empty, printing "Already pushed current candidate" [auto_push.py:42–61]. A day on which V8 lands nothing produces no release, without a special case. Lines 41–57 of v8/tools/release/create_release.py are the whole version policy:

Build plus one, patch zero. The remaining steps push that revision to refs/heads/<x.y.z>, branch off it, rewrite the header, un-comment the v8-merges@googlegroups.com line in WATCHLISTS so the branch starts mailing merge reviewers [:115–125], and land the commit with --set-bot-commit --bypass-hooks then git cl land --bypass-hooks -f, next to a TODO conceding this might need to go through the CQ [:139–159]. Then tag.

Getting that version into Chromium is two-stage. detect_roll_candidate reads v8_revision out of Chromium's DEPS with gclient getdep, scans the 160 newest tags for the newest version carrying a matching -pgo tag — patched four-component versions get a three-hour priority window — and force-pushes the winner to refs/heads/roll. Skia's v8-chromium-autoroll, strategy BATCH since 2023-09-01, turns that ref into "Roll V8 from A to B" CLs carrying 50 try jobs. The -pgo tag is the real gate. V8 ships profile-guided-optimisation data alongside a version — execution profiles that the compiler consumes to lay out the binary — and a separate job publishes a git tag <version>-pgo once that data exists for exactly that revision. A version without the tag is a version whose profiles are missing, so nothing will roll it. roll_merge_gerrit.py makes the wait explicit: it polls tags/<version>-pgo, asserts the tagged revision is the commit it just landed, and prints "Waiting for PGO profile tag (%s-pgo), this can take 15-20 minutes" while it spins [roll_merge_gerrit.py:287–298] from the tree — which is why the back-merge path in Figure 15 ends there. Those back-merges never touch a local checkout. merge_to_branch_gerrit.py cherry-picks through Gerrit's REST API, prefixes "Merged: ", strips the Change-Id/Reviewed-on/Commit-Queue footers and appends (cherry picked from commit …) [:92–107]; roll_merge_gerrit.py bumps V8_PATCH_LEVEL by one inside a Gerrit change edit and adds the roll-merge hashtag so Rubber Stamper reads it as benign [roll_merge_gerrit.py:154–175].

12What the pipeline optimises for

A pipeline this size has an objective function, and it is not throughput. Four properties recur above, and each one is bought with a specific cost somewhere else. The four headings below name them; Figure 16 is the ledger — those four plus the bootstrapper indirection of §§03 and 11, each paired with what it costs and who pays.

Reviewable infrastructure, not fast deployment

Nothing here is deployed. A builder, a shard count, a CQ membership and a release branch's builder set are CLs in chromium/src, guarded by the same presubmit and commit queue as product code, reaching the services through a polling importer that refuses any revision whose ValidateConfigs returns ERROR (§02). Both costs in the table's third column are structural rather than incidental: the propagation floor applies to the urgent change as much as the routine one, and the generated tree is re-diffed whether or not a reviewer reads it. The fleet is legible because it is a diff, and slow for the same reason.

Reuse over recomputation

The system would rather prove an old result still valid than compute a new one. A tryjob's ReuseKey survives every Gerrit revision kind but REWORK, so CQ+1 then CQ+2 adopts builds younger than staleTryjobAge = 24h (§06); a Swarming task whose inputs already ran comes back DEDUPED rather than scheduled (§05). The bootstrapper reads properties at the built revision (§03); an unchanged reproducible binary re-registers in CIPD as the same instance (§11). Caching is the scheduling model, not a layer on top of it.

A green tree, paid for in compute

Three of the four CQ test phases exist only to separate a broken change from a broken test, and the table's "Retry, then exonerate" row prices it (§07). Past submit: 133 tree closers, twelve gardener rotations, and LUCI Bisection with a daily budget of ten reverts created and four submitted, for culprits under 21,600 seconds (§09).

A system that can be branched

branch_selector, milestones.json and settings.json mean one body of Starlark produces both fleets in the table's last row (§10). There is no second release infrastructure to keep in sync: the release machinery is the CI machinery with a filter applied.

Where the humans still sit

An OWNERS approval per file plus a committer's Code-Review+1 (§06). A gardener partway through a shift, deciding whether to revert a stranger's commit (§09). A release manager holding a merge request against a branch that is about to ship (§10). The Googler who promotes a clang package out of the staging bucket it was written to with x-goog-if-generation-match:0 (§11). And whoever is in chromium-src-emergency-quota when the CQ must be told the rules do not apply (§07).

The claim §01 opened with survives that split, because it was never a claim about visibility. You can read the whole configuration of the fleet by cloning the repository it tests. You just cannot watch it run.
